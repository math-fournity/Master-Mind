# 机械化过程描述+规范化审计+程序验证——提示词设计技术SOP

## WHEN to use

设计或修订第六代系统提示词时，当提示词涉及的认知任务有对应的机械化算法，且AI用直觉做但产出需要完备性保证时。

具体触发：用户要求"把机械化过程描述放到提示词中"、用户要求"审计要表现出完全格"、用户要求"AI输出JSON让程序验证"、rule `six-mechanization-reference.md` 被触发时。

## WHEN NOT to use

- 提示词涉及的认知任务没有对应的机械化算法（如纯创意生成）
- AI的产出不需要完备性保证（如开放性探索）
- 一般代码编写、非提示词设计任务

## SOP

### 步骤1：识别机械化算法

确认提示词涉及的认知任务有对应的机械化算法：

| 认知任务 | 机械化算法 | 程序验证什么 |
|---|---|---|
| 格化+trace识别 | FCA Next Closure枚举闭元素 | 完全格B(G,M,I)的完备性 |
| 去特化+tell匹配 | 跨上下文概念匹配 | tell库匹配的完备性 |
| 其他 | 对应的机械化算法 | 对应的完备性验证 |

如果没有对应的机械化算法，本技术不适用——退出。

### 步骤2：写机械化过程描述

在提示词中新增一节，给出机械化算法的完整步骤。

**格式模板**：

```markdown
═══════════════════════════════════════════════════════════════════════
机械化过程参考（不要求你按此执行，但你的产出应达到此标准）
═══════════════════════════════════════════════════════════════════════

如果用[算法名称]机械化地执行[认知任务]，完整步骤是：

1. [步骤1——构造输入数据结构]
2. [步骤2——核心计算步骤]
3. [步骤3——枚举/验证步骤]
4. [步骤4——输出步骤]

**你实际怎么做**：用你的直觉做——你擅长[AI擅长的直觉判断]。但你的产出
应该覆盖机械化算法会找出的所有有语义价值的结果。

**在审计中对照**：你的[产出名称]集合和机械化算法枚举的[完全结果]集合
差距在哪里？你有没有遗漏机械化算法会找出的[元素]？你有没有识别出机械化
算法不会找出的[AI优势元素]？
═══════════════════════════════════════════════════════════════════════
```

**关键措辞**：
- "不要求你按此执行"——明确不约束执行方式
- "但你的产出应达到此标准"——明确约束产出质量
- "犹如你执行过此过程了一般"——理想标准

### 步骤3：写规范化审计要求

在提示词的审计/反思部分，要求AI输出**完全枚举+每个元素判定**。

**格式模板**：

```markdown
### 审计项X：完全[元素]清单

你必须列出你能推理出的所有[元素]，对每个给出判定：

[元素]清单：
  [元素1]: 入选 → 理由：[为什么入选]
  [元素2]: 排除 → 理由：[为什么排除——如"不包含可泛化模式"/"平凡合并"/"不是闭元素"]
  ...

**要求**：
- 每个元素都有判定（入选或排除），附理由
- 排除的也要列——不只是列入选的
- 表现出"我考虑了所有元素"，不是"我考虑了我想到的"
```

### 步骤4：定义JSON输出格式

定义AI必须输出的结构化JSON schema。

**格式模板**：

```json
{
  "[输入数据结构]": {
    "[字段1]": [...],
    "[字段2]": [...],
    "[关系/矩阵]": [[...]]
  },
  "[元素清单]": [
    {
      "id": "...",
      "[元素标识字段]": [...],
      "[元素属性字段]": [...],
      "[验证字段]": "...",
      "[判定字段]": "included/excluded",
      "reason": "..."
    }
  ],
  "[最终产出]": [
    {
      "id": "...",
      "type": "...",
      "description": "...",
      "[关联元素id]": "..."
    }
  ]
}
```

### 步骤5：写验证脚本

编写程序验证脚本，做以下事情：

1. **解析AI输出的JSON**——提取输入数据结构和元素清单
2. **运行机械化算法**——从AI给出的输入数据结构出发，运行算法枚举所有元素
3. **对比**：
   - AI声称的元素 vs 程序枚举的元素
   - 遗漏的元素（程序有但AI没有）
   - 错误的元素（AI有但程序没有）
   - 正确识别的元素
4. **输出审计报告**：
   ```
   完全[元素集合]共 N 个
   AI声称 M 个
   正确识别：K 个
   遗漏：N-K 个（列出每个遗漏元素）
   错误：M-K 个（列出每个错误元素的问题）
   完备性得分：K/N
   ```

**脚本放置位置**：`six/`目录下，命名`verify_[验证内容].py`。

### 步骤6：POC验证

用新提示词跑一次POC：
1. 启动subagent——用新提示词分析测试题，要求输出结构化JSON
2. 收集JSON输出
3. 运行验证脚本——程序枚举完全结果，对比AI声称的清单
4. 分析审计报告——完备性得分如何？遗漏的是什么？有语义价值还是平凡？
5. 判定成功/部分成功/失败

### 步骤7：三处同步+元组更新

POC完成后：
1. 更新set_A的README.md——新版本验证状态
2. 更新`six/prompts.py`——新版本notes和verification_status
3. 更新`six/pipes.py` docstring——POC验证结果
4. 更新POC方案文档——执行结果和审计报告
5. commit

### 步骤8：实现运行时闭环反馈

POC验证通过后，把验证脚本从"研发工具"升级为"运行时组件"——在Pipe的实现中加入闭环反馈机制。

**实现步骤**：

1. **在Pipe函数中加入验证调用**——Pipe产出JSON后，调用验证脚本检查完备性

2. **实现反馈逻辑**：
   ```python
   def pipe_with_feedback(input, max_rounds=2, threshold=0.8):
       json_output = ai_analyze(input)
       report = verify(json_output)

       for round in range(max_rounds):
           if report.completeness_score >= threshold:
               break
           if all_trivial_missed(report.missed_elements):
               break
           # 反馈遗漏列表给AI（不给完整报告——避免照抄）
           json_output = ai_supplement(json_output, report.missed_elements)
           report = verify(json_output)

       return json_output
   ```

3. **反馈提示词设计**——给AI的补充请求中包含：
   - 遗漏的元素列表（外延+内涵）
   - "请补充对这些元素的判定（入选/排除+理由），并检查你的trace是否需要补充"
   - **不包含**程序对这些元素的建议判定——AI自己判断

4. **平凡合并检测**——验证脚本中实现`all_trivial_missed()`函数：
   - 判断遗漏的闭元素是否都是平凡的（B是空集或只有1个特征）
   - 如果都是平凡的，直接通过——AI的直觉已覆盖所有有语义价值的元素

5. **在pipes.py的docstring中记录闭环反馈机制**——说明这个Pipe使用了运行时闭环反馈，参数是什么，最大迭代轮数是多少

## 注意事项

- **机械化过程描述不是执行指令**——措辞必须是"不要求你按此执行，但你的产出应达到此标准"
- **程序验证不替代AI做**——程序只验证，不做。AI仍然是主执行者
- **完备性得分低不一定是失败**——如果遗漏的都是平凡合并（无语义价值），可接受
- **验证脚本本身也是认知载体**——脚本中的算法实现是系统认知的一部分，按代码为中心铁律管理

## 经验积累

### V7→V8的改进经验（332号§8.10-8.11）

**问题**：V7的AI优势元素定义太窄——只覆盖"跨Case非相邻合并"（`cross_case_merge`），没覆盖"跨闭元素元模式"（`cross_element_meta_pattern`）。导致V7漏掉了3个有价值trace：
- "关键变量x贯穿整个证明"——x的角色分散在不同闭元素中，不对应任何单一闭元素
- "最大元素aₙ作为跳过障碍的工具"——aₙ在三个Case中扮演不同角色，分散在不同闭元素中
- "归纳递降的三种方式"——强归纳从决定到应用跨两个闭元素

**修复**：V8在AI优势元素定义中新增第二种类型`cross_element_meta_pattern`，在提示词4处修改（§1.5优势节、审计项2注释、JSON schema、JSON字段说明）。

**验证结果**：V8成功补回2个极有价值trace（列为最有价值trace前2名），1个部分补回。闭元素完备性保持100%。

**经验**：`cross_element_meta_pattern`往往是最有价值的trace——它揭示"为什么这个证明能work"的核心。设计提示词时，两种AI优势元素类型都必须要求AI识别，特别是第二种。
