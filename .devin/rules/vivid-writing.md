# 生动写作规则（always-on）

## 什么叫"生动"

生动不是为了好看，不是为了修辞，不是为了别的。

**生动是为了让你在需要的时候看见。**

你的注意力机制是模式匹配。干巴巴的抽象描述（"应实时采集并整理"）不会在场景中触发你的注意。但具体的、场景化的、带画面感的描述（"你看到自己在sleep→停。你违反了并行运行原则"）会在你身处那个场景时，让你的注意力机制抓住它。

**生动 = 在未来的场景中可被注意力机制命中。**

## 什么时候必须生动

写以下内容时，必须检查是否足够生动：

1. **AGENTS.md中的SOP和角色定义**——这些内容会在未来实验场景中被加载，必须用场景化语言写，让未来的你在那个场景中能看见
2. **规则（.devin/rules/）中的行动指引**——触发后的行动描述必须具体到"你看到什么→你做什么"，不能是抽象指令
3. **Skill中的操作步骤**——步骤要写在真实操作场景中，不是抽象流程图
4. **任务追踪中的待办项**——待办要写成"你遇到什么问题→你该做什么"，不是"修复XX"

## 什么不需要生动

1. **代码注释**——给开发者看的，简洁准确即可
2. **技术方案的数据结构定义**——精确即可
3. **git commit message**——简洁即可
4. **API文档**——准确即可

## 生动的写法

### 不生动的写法（避免）

```
辅助智能体应实时采集推理AI的trajectory并整理两棵树，不应等待AI终止后再处理。
```

### 生动的写法（采用）

```
你看到自己在sleep或等待→停。你违反了并行运行原则。推理AI在工作时你也在工作。
你应该在采集、整理树、或在节点上做检索。如果你在等待，说明你退化成了
"事后处理器"——回到你的角色：园丁不等树长完才浇水，园丁在树生长的同时就在整理。
```

### 区别

- 不生动：抽象指令（"应实时采集"）——未来的你读到时不会产生场景联想
- 生动：场景触发（"你看到自己在sleep→停"）——未来的你身处那个场景时，这句话会跳出来

## 自检

写完元组或AGENTS.md内容后，问自己：

**"如果未来的我身处这个场景，这段文字会让我的注意力抓住它吗？"**

如果答案是"可能不会"→重写，更具体、更场景化、更有画面感。
