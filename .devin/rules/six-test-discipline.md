# 系统测试规矩——方案先行、按模块组织、内容全留存

**触发条件**：为系统模块编写测试、POC验证、回归验证时；在`system/tests/`下创建测试资产时；架构改动后需要验证不退化时。always-on——任何涉及系统测试的场景都必须遵守。

## 核心约束

**测试不是用完就扔的临时文件**。测试是系统质量的永久存档，和代码、文档同级。每次架构改动后都要重跑验证，确保不退化。

## 1. 测试目录结构——按模块组织

```
system/tests/
├── README.md                  # 测试目录总说明
├── <module_name>/             # 每个模块一个子目录
│   ├── <test_name>_plan.md    # 测试方案
│   ├── <test_name>_report.md  # 测试报告
│   ├── <test_name>.py         # 测试脚本
│   ├── baseline/              # 基线产出（对比基准）
│   └── new_arch/              # 新架构产出（待验证的产出）
└── <另一个module>/
    └── ...
```

**规则**：
- 每个模块一个子目录——`vein_analysis/`、`enter/`、`solve/`等
- 子目录名 = 模块名（和`system/`下的模块名一致）
- 不允许把测试文件直接放在`system/tests/`根目录——必须放在模块子目录下
- 不允许把测试文件放在`system/`根目录——必须移到`system/tests/<module>/`下

## 2. 方案先行——每个测试必须有方案文档

**每个测试必须有`<test_name>_plan.md`方案文档**，在编写测试脚本之前先写方案。

方案文档必须包含：
1. **测试目标**——验证什么？防止什么退化？
2. **测试方法**——怎么验证？对比什么和什么？
3. **验证维度**——检查哪些维度？每个维度的判定标准是什么？
4. **关键检查项**——有没有特别需要关注的检查项（如POC实证发现的关键内容）？
5. **判定标准**——什么算通过？什么算失败？
6. **失败处理**——如果失败怎么办？可能的修正方向？

**没有方案文档的测试不允许运行**——方案先行是硬约束。

## 3. 内容全留存——测试资产是永久存档

**以下资产必须永久保存，不能删除**：

| 资产 | 存放位置 | 性质 |
|---|---|---|
| 测试方案 | `<module>/<test_name>_plan.md` | 永久存档 |
| 测试脚本 | `<module>/<test_name>.py` | 永久存档 |
| 测试报告 | `<module>/<test_name>_report.md` | 每次运行后更新 |
| 基线产出 | `<module>/baseline/` | 永久存档——作为对比基准 |
| 新架构产出 | `<module>/new_arch/` | 永久存档——作为测试记录 |
| 对比结果 | `<module>/new_arch/comparison.json` | 每次运行后更新 |

**不允许**：
- ❌ 把测试产出放在`palyground/`或临时目录——必须放在`system/tests/`下
- ❌ 跑完测试后删除产出——产出是测试记录，必须留存
- ❌ 只留测试脚本不留产出——脚本+产出+报告三者缺一不可

## 4. 测试报告格式

每次运行测试后，`<test_name>_report.md`必须更新，包含：

```markdown
# <测试名称>报告

**日期**：<运行时间>
**测试题目/对象**：<测试用什么数据>
**基线架构**：<对比基准是什么>
**新架构**：<待验证的是什么>

## 总判定
✅通过 / ❌失败（列出失败的维度）

## 各维度详情
（每个验证维度的具体数值和判定）

## 关键检查项
（特别关注的检查项的结果）
```

## 5. 回归验证——架构改动后必须重跑

**触发条件**：当`system/`下的模块代码发生架构级改动时（不只是修bug），必须重跑该模块的所有测试。

**流程**：
1. 架构改动前：确认`baseline/`中的基线产出是最新的
2. 架构改动后：用同一道题/同一数据跑新架构，产出存到`new_arch/`
3. 运行测试脚本：`python3 system/tests/<module>/<test_name>.py`
4. 检查报告：`<test_name>_report.md`的判定结果
5. 如果失败：分析丢失原因，修正架构，重跑验证，直到通过

## 6. 基线的建立和更新

**基线 = 当前架构的产出**，作为新架构的对比基准。

**建立基线**：
- 用当前架构跑一道代表性题目
- 把产出（output.json/output.md等）复制到`baseline/`
- 在方案文档中记录基线数据摘要（trace数、闭元素数等关键指标）

**更新基线**：
- 基线一旦建立，**不能随意更新**——基线是对比基准，更新基线等于"移动球门"
- 只有以下情况可以更新基线：
  1. 当前架构本身做了改进（不是新架构），改进后的产出应该成为新基线
  2. 基线产出有明确错误（如AI truncated导致产出不完整）
- 更新基线时，必须在方案文档中记录更新原因和旧基线数据

## 和其他规则的关系

- 和`six-poc-organization.md`的关系：POC验证是测试的一种——POC验证方案按本rule的方案先行要求编写，POC产出按本rule的内容全留存要求存放到`system/tests/`下
- 和`six-asset-grading.md`的关系：测试资产是system的资产，按本rule分级管理（方案/脚本/产出/报告）
- 和`six-trace-preservation.md`的关系：测试产出是痕迹保留的一部分——测试记录必须可追溯
- 和`six-update-docs-action.md`的关系：架构改动后重跑测试是"更新文档"动作的一部分——测试报告是文档的一种
