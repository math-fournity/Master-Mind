# 机械化过程描述+规范化审计+程序验证——提示词设计技术

## 触发条件

设计或修订第六代系统提示词时，当提示词涉及的认知任务有对应的机械化算法（如FCA格化、Next Closure枚举、闭包运算等），且AI用直觉做但产出需要完备性保证时。

## 核心原则

**在提示词中给出机械化过程的完整描述——不要求AI按此执行，但要求AI的产出"犹如"执行过机械化过程了一般。同时要求AI输出结构化数据（JSON），让程序可以验证产出的完备性。**

这是提示词设计的一种技术——三层结构：

| 层 | 内容 | 作用 |
|---|---|---|
| **机械化过程描述** | 如果用算法机械化执行，完整步骤是什么 | 给AI"理想标准"——产出应达到的质量 |
| **自由执行** | AI实际怎么做（直觉做） | AI自由发挥，不强制机械化 |
| **规范化审计+程序验证** | AI输出结构化JSON，程序运行算法验证完备性 | 不依赖AI自评——程序验证 |

### 为什么不直接让AI机械化执行

1. **AI不擅长长序列机械计算**——FCA闭包运算需要精确的集合代数，AI在70-100次闭包运算中会累积错误
2. **AI擅长直觉判断**——AI能一眼看出"段3和段7在思维上属于同一层"，不需要算闭包
3. **机械化过程描述的目的是提高直觉产出的质量**——让AI知道"理想标准是什么"，向这个标准看齐

### 为什么需要程序验证

1. **AI无法保证完备性**——它没有运行算法，可能遗漏闭元素
2. **程序可以精确验证**——运行Next Closure算法枚举所有闭元素，和AI声称的闭元素清单对比
3. **不依赖AI自评**——AI说"我觉得没漏"不算数，程序算出来的才算数

## 具体规则

### 1. 机械化过程描述的写法

在提示词中新增一节，给出机械化算法的完整步骤。明确标注：

> **机械化过程参考**（不要求你按此执行，但你的产出应达到此标准——犹如你执行过此过程了一般）：
>
> 1. [算法步骤1]
> 2. [算法步骤2]
> ...
>
> **你实际怎么做**：用你的直觉做——你擅长一眼看出"哪些段在思维上属于同一层"。但你的产出应该覆盖机械化算法会找出的所有有语义价值的结果。

### 2. 规范化审计的写法

审计输出必须包含**完全格元素清单**——每个格元素都有明确判定：

```
格元素清单：
  (A₁,B₁): 入选trace → 理由：[为什么入选，trace描述]
  (A₂,B₂): 排除 → 理由：[为什么排除——如"B₂不包含可泛化思维模式"/"A₂是平凡合并"/"不是闭元素"]
  ...
```

**不允许**：
- "我觉得没漏"——这不是审计，这是自评
- 只列出入选的，不列排除的——排除的也要列，附理由
- 只列"我想到的"——要表现出"我考虑了所有格元素"

### 2.1 AI优势元素的两种类型（V8改进，来自332号§8.10-8.11）

AI优势元素 = 机械化算法不会找出但AI在思维上能识别出的跨元素模式。**有两种类型，都必须识别**：

| 类型 | 名称 | 描述 | V7状态 | V8状态 |
|---|---|---|---|---|
| `cross_case_merge` | 跨Case非相邻合并 | 段集合不相邻且属性不同，但思维上本质相同 | ✅ 已覆盖 | ✅ 保留 |
| `cross_element_meta_pattern` | 跨闭元素元模式 | 某个变量/技巧/策略贯穿多个闭元素，不对应任何单一闭元素，但AI能识别出它的统一角色 | ❌ 漏掉（导致V7漏掉3个有价值trace） | ✅ 新增 |

**关键经验**：`cross_element_meta_pattern`往往是最有价值的trace——它揭示"为什么这个证明能work"的核心。V7因为只覆盖了`cross_case_merge`而漏掉了"x贯穿整个证明"和"aₙ作为跳过障碍工具"这样的极有价值trace。V8通过新增第二种类型成功补回。

### 3. JSON输出的写法

AI必须输出结构化JSON，包含：
- **形式上下文** (G, M, I)——对象集、属性集、关系矩阵
- **闭元素清单**——每个闭元素含外延A、内涵B、闭包验证、trace判定（入选/排除）、理由
- **trace列表**——所有入选trace

程序读取JSON，运行算法枚举完全格，对比AI声称的闭元素清单，输出审计报告。

### 4. 程序验证脚本

每个使用本技术的提示词，必须配套一个验证脚本：
- 读取AI输出的JSON
- 运行对应的机械化算法（如Next Closure）
- 对比AI声称的结果和程序枚举的结果
- 输出：遗漏的元素、错误的元素、完备性得分

### 5. 运行时闭环反馈

程序验证不只在研发阶段（POC验证）使用——它也是系统运行时的闭环反馈机制。

**两种用法**：

| 用法 | 时机 | 目的 |
|---|---|---|
| **POC验证** | 研发阶段——验证提示词设计是否有效 | 判定提示词版本的成功/失败 |
| **运行时闭环反馈** | 系统运行时——Pipe 1每次产出后 | 检查AI产出完备性，不足则反馈让AI补充 |

**运行时闭环反馈的流程**：

```
Parser AI产出JSON
      ↓
程序运行验证脚本（如verify_lattice_completeness.py）
      ↓
完备性得分≥阈值？
  是 → 通过，进入下一个Pipe
  否 → 反馈审计报告给Parser AI：
       "你遗漏了以下N个闭元素：[列表]。
        请补充对这些闭元素的判定（入选/排除+理由），
        并检查你的trace是否需要补充。"
      ↓
Parser AI补充分析
      ↓
再次验证（最多K轮）
```

**闭环反馈的设计参数**：

| 参数 | 推荐值 | 理由 |
|---|---|---|
| 完备性阈值 | 80% | VMS-28c得了100%但那是简单题，难题可能做不到。80%留余地但要求基本完备 |
| 最大迭代轮数 | 2 | 1轮可能不够，3轮成本太高。2轮：第一次反馈后补充，第二次验证 |
| 反馈内容 | 只给遗漏列表+错误列表 | 不给完整报告——避免AI照着抄。只告诉它"你遗漏了这些"，让它自己判断这些元素是否有语义价值 |
| 遗漏都是平凡合并时 | 直接通过 | 如果遗漏的闭元素都是平凡合并（B是空集或只有1个特征），说明AI的直觉已覆盖所有有语义价值的元素，不需要迭代 |

**关键约束**：
- **反馈只告诉AI遗漏了什么，不告诉AI这些遗漏元素应该是什么判定**——AI自己判断入选/排除，避免AI照抄程序结果
- **程序只验证，不替代AI做**——程序枚举完全格，但不判断哪些闭元素有语义价值。语义价值判断是AI的事
- **闭环反馈不是惩罚**——目的是帮助AI发现遗漏，不是批评AI做得不好

## 适用场景

| 场景 | 机械化算法 | 程序验证什么 |
|---|---|---|
| Pipe 1 step_2 grid_vein | FCA Next Closure枚举闭元素 | 完全格B(G,M,I)的完备性——AI遗漏了哪些闭元素 |
| 未来Pipe 2 telling | 去特化+跨上下文概念匹配 | tell库匹配的完备性——AI遗漏了哪些tell匹配 |
| 任何"AI用直觉做但需要完备性保证"的Pipe阶段 | 对应的机械化算法 | 对应的完备性验证 |

## 不做的事

- **不把机械化过程描述变成执行指令**——"你必须按以下步骤执行"是错的。正确的是"不要求你按此执行，但你的产出应达到此标准"
- **不废弃AI的直觉做**——方式A（AI做全部）是主线，机械化过程描述是辅助
- **不用程序验证替代AI做**——程序只验证，不做。AI仍然是主执行者
- **不把程序验证结果作为唯一评判标准**——完备性得分低不一定是失败，如果遗漏的都是平凡合并（无语义价值），可接受

## 和其他rule的关系

| rule | 管什么 | 和本rule的关系 |
|---|---|---|
| 双轨术语rule | 术语怎么写——FCA定义+工程含义并重 | 互补——本rule管过程怎么描述，双轨术语管术语怎么定义 |
| 提示词自包含rule | 提示词必须自包含——术语必须在提示词内定义 | 互补——本rule的机械化过程描述中用到的术语也必须自包含 |
| 代码为中心铁律 | 代码是认知的最终载体 | 本rule的验证脚本是代码——验证脚本本身也是认知的载体 |
| 文档自包含rule | 研发过程文档自包含 | 互补——本rule管提示词，文档自包含rule管研发文档 |
