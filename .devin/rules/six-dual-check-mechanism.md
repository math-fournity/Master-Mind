# 双重检查机制——代码检查 + 流程审计AI

**触发条件**：设计或实现系统的任何运行阶段后；系统运行中检查健康状态时；系统运行后审计产出质量时。always-on——任何涉及系统运行检查的场景都必须考虑双重检查。

## 核心约束

**系统建立两种check机制：**

1. **代码能保证的**——assertions、type checks、completeness scores、文件存在性检查、JSON schema验证、程序验证（如verify_lattice_completeness.py的闭元素完备性验证）。这些是代码自动执行的，不需要AI参与。

2. **流程审计AI**——某些检查无法用代码完成，需要AI来判断。流程审计AI加载.ref中的参考文档→加载代码→加载.ai-check checklist文件→按checklist和检查标准对代码的运行情况进行详细检查。

**流程审计AI就是Master Agent（你）**——因为"系统就是你，不是脚本"。系统用代码运行了，但系统运行的健康情况需要你实时查看。代码能检查的是机械的部分（文件存不存在、完备性得分多少），AI需要检查的是认知的部分（产出质量够不够、trace有没有语义错误、AI的工作过程有没有跑偏）。

## .ai-check文件——第三个同名文件

system/目录下每个`.py`代码文件，除了有同名的`.ref`文件外，还有同名的`.ai-check`文件：

| 文件 | 后缀 | 内容 | 谁用 |
|---|---|---|---|
| `vein_analysis.py` | `.py` | 代码实现 | Python运行时 |
| `vein_analysis.ref` | `.ref` | 参考文档路径列表 | 理解模块时阅读 |
| `vein_analysis.ai-check` | `.ai-check` | AI审计checklist | 流程审计AI（Master Agent） |

### .ai-check文件格式

纯文本，包含以下部分：

```
# {模块名} AI审计checklist

## 模块职责
{这个模块应该做什么——一句话}

## 代码能检查的（不需要AI）
- {列出代码自动检查的项目，AI审计时不需要重复检查}

## AI需要检查的
- [ ] {检查项1}——{检查标准}
- [ ] {检查项2}——{检查标准}
- ...

## 审计流程
1. 加载 .ref 中的参考文档——理解这个模块的设计意图和上下文
2. 加载 .py 代码——理解实现逻辑
3. 加载本 .ai-check 文件——明确检查项目
4. 检查实际运行产出（工作目录中的output.json/output.md/audit_report.json等）
5. 按checklist逐项检查，记录结果

## 检查标准
{每个检查项的详细标准——什么算通过，什么算不通过}
```

### 审计流程

流程审计AI（Master Agent）检查某个模块时，按以下顺序加载：

```
步骤1：加载 .ref 文件
  → 读取参考文档路径列表
  → 按需阅读参考文档（理解设计意图、POC验证结果、提示词版本等）

步骤2：加载 .py 代码文件
  → 理解实现逻辑
  → 识别代码中的assertions和检查点（这些不需要AI重复检查）

步骤3：加载 .ai-check 文件
  → 明确AI需要检查的项目和标准

步骤4：检查实际运行产出
  → 读取工作目录中的output.json/output.md/audit_report.json
  → 读取tmux session的输出（tmux capture-pane）
  → 读取数据库中的会话记录

步骤5：按checklist逐项检查
  → 每项记录：✅通过 / ⚠️部分通过 / ❌不通过
  → 不通过的项目记录原因和建议
```

## 代码检查 vs AI检查的分工

| 检查类型 | 代码能做 | AI需要做 |
|---|---|---|
| 文件存在性 | ✅ os.path.exists() | ❌ |
| JSON格式正确性 | ✅ json.load() + schema验证 | ❌ |
| 闭元素完备性得分 | ✅ verify_lattice_completeness.py | ❌ |
| 关键实体贯穿性验证 | ✅ verify_lattice_completeness.py | ❌ |
| 伪元模式过滤 | ✅ verify_lattice_completeness.py | ❌ |
| trace语义质量 | ❌ | ✅ AI判断trace描述是否准确 |
| trace去重质量 | ❌ | ✅ AI判断合并后是否有语义重复 |
| 元反思trace是否有价值 | ❌ | ✅ AI判断元反思发现的新trace是否真的有价值 |
| AI工作过程是否跑偏 | ❌ | ✅ AI检查tmux输出中有没有异常行为 |
| 提示词版本选择是否正确 | ❌ | ✅ AI判断这个题目用哪个版本组合最合适 |
| 产出完整性 | ✅ 字段齐全检查 | ✅ 字段内容质量检查 |

**原则**：代码能检查的全部用代码检查（效率高、可自动化）。代码不能检查的才用AI检查（需要认知判断）。两者不重复——AI检查的清单中明确排除"代码能检查的"项目。

## 什么时候做流程审计

1. **系统运行中实时审计**——Master Agent作为辅助Pipe，在AI Agent运行过程中实时检查健康状态。不是等跑完再审计，而是边跑边看。
2. **系统运行后事后审计**——一轮运行结束后，Master Agent切回审计角色，按checklist逐项检查产出质量。
3. **代码变更后审计**——修改了某个模块的代码后，按该模块的.ai-check检查是否引入了问题。

## 和其他规则的关系

- 和`six-trace-preservation.md`的关系：痕迹保留是审计的前提——没有落盘的产出，AI审计时无物可查。痕迹保留rule保证"有东西可审计"，本规则保证"审计本身有标准可循"。
- 和`six-ai-agent-launch.md`的关系：AI Agent启动规范保证"启动前准备充分"，本规则保证"启动后运行健康"。
- 和`system-ref-sync.md`的关系：.ref文件是审计的第一步（理解设计意图），.ai-check文件是审计的第三步（明确检查项目）。三个同名文件（.py/.ref/.ai-check）构成完整的"实现-参考-审计"三件套。
- 和AGENTS.md"可审计性纪律"的关系：AGENTS.md要求"重大分析必须留下file:line定位+理解性产物"，本规则是这一要求在系统代码层面的具体化。
