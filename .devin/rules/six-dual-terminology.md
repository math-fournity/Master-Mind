# 双轨术语原则——FCA理论语言与工程人话并重

## 触发条件

编写或修订第六代系统提示词、技术文档、代码注释、POC方案时，涉及术语选择和使用。

## 核心原则

**FCA等理论语言和我们研发过程中使用的特有表达，是并重的。两者都有自己所承载的作用。**

- **FCA理论语言**承载精确性——提供数学定义、可验证性、和学术界的对接
- **工程人话**承载理解——是我们对系统的真正理解，是系统设计意图的直接表达

**不允许只用一种而废弃另一种。**

## 具体规则

### 1. 提示词中的术语

每个提示词文件开头建术语表时，对每个术语同时给出：
- FCA标准定义（数学语言）
- 工程对应（我们的人话）

例：
```
格化（计算概念格）：
  FCA定义：从形式上下文(G,M,I)枚举所有形式概念
  工程含义：把脉络分成段后，考虑段的不同合并方式，
           形成所有有意义的Level视图
```

**不允许只给FCA定义而不给工程含义——工程含义才是subagent理解"要做什么"的关键。**
**不允许只给工程含义而不给FCA定义——FCA定义确保术语的精确性和自包含性。**

### 2. 技术文档中的术语

技术说明书中记录每个术语时，同时记录：
- FCA标准术语和数学定义
- 我们的工程术语和含义
- 两者的对应关系和语义差距（如果有）

### 3. 代码注释中的术语

types.py / pipes.py / prompts.py 的docstring中，对每个数据结构和函数：
- 给出工程含义（人话——这个结构/函数做什么）
- 给出FCA对应（如果有——这个结构/函数对应FCA的什么概念）

### 4. 不做的事

- **不把工程术语全部换成FCA术语**——trace/tell/hint/格化/Level视图这些工程术语有自己的语义，承载我们对系统的理解，保持不变
- **不废弃FCA术语**——闭包算子/概念格/形式概念这些FCA术语提供精确性，在需要数学严格性时使用
- **不强行把两者合并为一个术语**——两者并重，各有各的位置

## 为什么两者并重

1. **FCA语言是后来找到的灯塔**（304号）——我们用工程直觉走了四代+两个POC的路，FCA在理论上已经铺好了这条路。FCA语言让我们知道"我们重新发明的东西在数学上叫什么"。

2. **工程人话是系统的灵魂**——"格化"、"trace"、"tell"、"hint"这些词不是随意起的，它们承载了我们对系统的设计意图。"tell"取自poker术语——"AI不会主动告诉你它没考虑这个方向，但它的thinking会暴露"——这个语义是FCA的"跨上下文概念"无法承载的。

3. **两者服务不同的读者**——FCA语言服务"需要数学严格性的场景"（算法分析、完备性论证、和学术界对接）；工程人话服务"需要理解系统意图的场景"（提示词、系统设计、AI执行）。
