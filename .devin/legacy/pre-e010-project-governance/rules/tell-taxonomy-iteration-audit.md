# tell-taxonomy-iteration-audit rule

## 核心铁律

**Tell分类学不是一次性建成的——它在不断看新题的过程中被修正。修正很重要，但修正的全历史审计更重要。警惕"吃了后面忘了前面"：后来的修正可能丢失对前面情况的覆盖。**

本rule锁定五件事：
1. **主agent/subagent分工**——主agent是流程管理者，subagent是具体分析者。主agent不自己做FCA再分析，委托给subagent做（铁律-1）
2. **启动前必须建立TODO List**——主agent每次启动一轮FCA再分析，必须从check list模板建立TODO List，逐项对照执行（铁律0）
3. **再分析SOP**——对已有profile做FCA再分析的标准流程（10步，步骤0-9），每步有规范化输入/输出定义。SOP由subagent执行
4. **产出验证**——subagent返回后，主agent用产出验证check list验证subagent的产出（铁律0.5）
5. **版本化审计铁律**——Tell分类学每次修正必须版本化、明面记录、做覆盖性检查（7条铁律）。修正由主agent执行，不委托subagent
6. **Schema同步**——修正后必须同步更新AGENTS.md Schema节，保持跨压缩边界保真（铁律7，详见`.devin/rules/tell-taxonomy-schema-maintenance.md`）

## 铁律-1：主agent/subagent分工

**FCA再分析采用主agent/subagent分工架构：主agent是流程管理者，subagent是具体分析者。**

### 主agent的职责（流程管理者）

1. **选择题目**——决定做哪道题的FCA再分析
2. **建立TODO List**——从check list模板建立TODO List（铁律0）
3. **构造subagent prompt**——从prompt模板填入problem_id和产出路径
4. **启动subagent**——用run_subagent启动，profile选`subagent_general`（需要写文件权限）
5. **验证产出**——subagent返回后，用产出验证check list验证产出（铁律0.5）
6. **分类学修正**——如果subagent发现分类学问题，主agent自己执行修正流程（7条铁律），不委托subagent
7. **产出落盘和commit**——主agent负责git commit

### subagent的职责（具体分析者）

1. 加载V6提示词全文（步骤0）
2. 读原始profile（步骤1）
3. 按10步SOP执行FCA再分析（步骤2-9）
4. 产出再分析报告落盘到指定路径
5. 返回执行摘要（check list完成情况、trace统计、是否发现分类学问题）

### 为什么分工

- **保障从"文本提示"升级为"流程控制"**——subagent的prompt是硬约束，主agent在prompt中明确要求"第一个动作是加载V6、建立TODO List"，subagent必须遵循。比靠always-on触发提示更可靠
- **上下文隔离**——subagent有自己的上下文窗口，加载V6（679行）、check list（126行）、profile数据不污染主agent的上下文
- **并行能力**——可以同时启动多个subagent做多道题的FCA再分析
- **分类学修正不适合委托**——修正流程涉及多文件同步（08号文件+AGENTS.md Schema节+09号文件），由主agent统一执行

### 关键文件

| 文件 | 用途 |
|---|---|
| `FCA学习笔记/fca-reanalysis-subagent-prompt-template.md` | subagent prompt模板——主agent从中复制prompt，填入problem_id和产出路径 |
| `FCA学习笔记/fca-reanalysis-checklist.md` | 执行check list模板——主agent建立TODO List用 |
| `FCA学习笔记/fca-reanalysis-output-verification-checklist.md` | 产出验证check list——主agent验证subagent产出用 |

## 铁律0：启动前必须建立TODO List

**主agent每次启动一轮FCA再分析时，必须先用todo_write工具建立TODO List。**

**check list模板文件**：`FCA学习笔记/fca-reanalysis-checklist.md`

**建立TODO List的流程**：
1. 读取check list模板文件
2. 把check list中的所有检查项复制到todo_write工具中，建立TODO List
3. 从"启动前检查"开始，逐项执行
4. 每完成一项，在TODO List中标记为completed
5. 不允许跳过任何检查项
6. 如果某项无法完成，标注"阻塞"并说明原因——不允许默默跳过

**为什么必须建立TODO List**：
- SOP有10个步骤、每步有多个检查项——不建立TODO List，容易漏掉某个步骤或某个检查项
- TODO List是执行进度的可见化——用户可以看到你在哪一步、完成了多少、还剩多少
- 跨压缩边界时，TODO List是恢复执行状态的依据——压缩后的AI看到TODO List就知道做到哪了

**不建立TODO List就开始分析 = 违反铁律0 = 必须停下来先建立TODO List。**

## 铁律0.5：subagent返回后必须验证产出

**subagent返回后，主agent必须用产出验证check list验证subagent的产出。**

**产出验证check list文件**：`FCA学习笔记/fca-reanalysis-output-verification-checklist.md`

**验证流程**：
1. 读取subagent返回的执行摘要
2. 读取subagent产出的报告文件
3. 从产出验证check list逐项检查
4. 如果V-0到V-2不通过 → 产出结构不完整，重新启动subagent
5. 如果V-3不通过 → 产出质量不合格，要求subagent重做
6. 如果V-4通过 → 分类学问题已处理
7. 如果V-5通过 → 全流程完成

**不验证产出就接受 = 违反铁律0.5 = 必须停下来先验证。**

## 触发条件

### 1. 对已有profile做FCA再分析时
用FCA先验分类学重新分析已完成的profile（455个Tier 1题目），识别原始profile遗漏的非局部/全局tell显现。

### 2. Tell分类学需要修正时
在再分析过程中发现分类学无法覆盖某道题的tell，或用FCA理论审查发现分类学不自洽时，触发修正。

### 3. FCA理论审查时
用FCA理论定期审查分类学的自洽性——形式背景的属性维度是否都是tell的固有特征、属性维度是否正交独立、概念格是否完备。

## 再分析SOP（标准操作流程）

对每道题做FCA再分析时，必须按以下步骤执行。**每步有明确的输入和输出定义——上一步的输出是下一步的输入，不允许跳步或在步骤之间插入未定义的操作。**

### 步骤0：加载V6提示词全文（ mandatory · 不可跳过）

**输入**：无（这是流程的起点）

**操作**：用read工具读取`第六代系统提示词积累目录/pipe_1_parser/step_2_grid_vein/set_A_fca_hassee/v6.md`全文（679行）

**输出**：V6全文进入当前上下文窗口

**验证**：确认V6的术语表、7种反模式、8种复杂情况检查、9项自我审计都在上下文中可见

**V6与v3分类学的对齐注意**：V6审计项5的8种复杂情况中，"模分析无尽追逐"还是独立项——但v3分类学已把它降级为"探索-诊断-修复"的子模式。在使用V6时，审计项5的检查应按v3分类学理解：把"模分析无尽追逐"作为"探索-诊断-修复"的子模式检查，不作为独立模式检查。

### 步骤1：读原始profile

**输入**：problem_id（题目ID）

**操作**：从`subagents-dirs/{problem_id}/profile.json`读取原始profile

**输出**（提取以下字段）：
- `tell_hint_pairs`：局部tell列表（每个含tell/hint/hint_level/situation_type/is_knowledge_bottleneck/tell_topology/tell_small_concepts）
- `global_tell_hint_pairs`：全局tell列表（每个含scope_type/scope/tell/hint/hint_level/generalizability/why_not_visible_locally/tell_topology/tell_small_concepts）
- `tell_topology`：题目级拓扑（problem_type/ai_method_type/gap_type）
- `tell_small_concepts`：题目级小概念列表
- `domain`：原始domain标注
- `key_insight`：关键洞察
- `solution_text`：解答文本
- `problem_text`：题目文本

**验证**：确认所有字段都成功提取，没有缺失

### 步骤2：确定domain（属性维度第一层）

**输入**：步骤1的`domain` + `solution_text` + `key_insight`

**操作**：
1. 看原始domain字段
2. 问"这道题的解答是否跨域？"——如果解答把问题从一个领域翻译到另一个领域，标多个domain
3. 参考v3分类学的6个domain：数论/代数/组合/几何/分析/跨域

**输出**：domain列表（1-3个domain，如["组合","跨域"]）

**验证**：每个domain都在v3分类学的6个domain中；如果有新domain，触发分类学修正流程（步骤9）

### 步骤3：识别段结构模式（属性维度第二层）

**输入**：步骤1的`solution_text` + 步骤2的domain列表

**操作**：用V6的格化方法（段划分→Level视图→有意义的合并）对解答做格化，然后逐一检查v3分类学的5大类段结构模式：
- 构造-分析-排除？（构造对象→分析性质→排除不可能）
- 探索-诊断-修复？（探索→发现gap→诊断→修复；无尽追逐是此模式的子模式）
- 跨域桥接？（把问题翻译到另一个领域）
- 归约策略？（大问题归约到小问题）
- 累积-收敛？（逐步累积信息→收敛到结论）

**输出**：段结构模式列表（0-5个模式，每个含模式名+在这道题中的具体表现+涉及的段）

**验证**：每个模式都在v3分类学的5大类中；如果有新模式，触发分类学修正流程（步骤9）

### 步骤4：确定具体概念（属性维度第三层）

**输入**：步骤2的domain列表 + 步骤3的段结构模式列表

**操作**：domain × 段结构模式的交叉，生成具体概念。子模式在此层体现（如"无尽追逐"是"探索-诊断-修复"的子模式）

**输出**：具体概念列表（每个含domain×模式交叉名+具体tell描述+对应的hint）

**验证**：每个具体概念都是domain和段结构模式的合法交叉

### 步骤5：从多个观察Level分析trace

**输入**：步骤1的`tell_hint_pairs` + `global_tell_hint_pairs` + 步骤3的段结构模式 + 步骤4的具体概念

**操作**：
1. 局部Level：看每一步——"AI在第N步做了什么/没做什么"——对应原始的局部tell
2. 非局部Level：看跨多段——"AI在这几步构成了什么模式/没构成什么模式"——对应原始的global tell + 新发现的非局部tell显现
3. 全局Level：看整体策略——"AI整体走了什么路线/没走什么路线"——新发现的全局tell显现
4. **关键**：同一个tell在三个Level下有三种显现——它们不是三个不同的tell，是同一个tell的三种观察方式（FLT例子）

**输出**：tell显现列表（每个含tell内容+观察Level（局部/非局部/全局）+对应的固有属性（domain+段结构模式+具体概念）+是原始profile已有的还是新发现的）

**验证**：每个tell显现都有明确的观察Level标注和固有属性标注；新发现的tell显现标注为"新发现"

### 步骤6：构造形式背景

**输入**：步骤5的tell显现列表

**操作**：把所有tell显现写成形式背景表格——行是tell，列是固有属性（domain + 段结构模式），打✓表示"这个tell有这个属性"。**列不包含观察Level**——观察Level在表格注释中说明

**输出**：形式背景表格（Markdown表格）+ 观察Level注释

**验证**：表格列只有固有属性（domain + 段结构模式），没有观察Level列

### 步骤7：算概念格

**输入**：步骤6的形式背景表格

**操作**：从形式背景算出所有形式概念（用FCA闭包算子的直觉——"查表格找共同特点再找有这些特点的tell"），排成层级

**输出**：概念格描述（顶层概念→第一层分化（按domain）→第二层分化（按段结构模式）→底层概念（每个tell自己一类））

**验证**：概念格中每个概念都有明确的外延（哪些tell）和内涵（哪些属性）

### 步骤8：对比原始profile

**输入**：步骤1的原始profile + 步骤5的tell显现列表 + 步骤7的概念格

**操作**：
1. 量化对比：局部tell数量、非局部tell显现数量、domain识别数量、段结构模式识别数量、观察Level覆盖
2. 质变对比：格化思考多看到什么（4个质变维度：从"每轮缺什么"到"整体没走什么路线"、从"没想到X"到"没跨域到Y"、从"两个独立缺口"到"同一模式的两个实例"、从"扁平topology"到"3层属性维度+观察Level"）
3. 记录"原始profile遗漏了什么"——列出所有新发现的tell显现

**输出**：对比报告（量化对比表 + 质变对比描述 + 遗漏清单）

**验证**：对比报告中的数字与步骤5的tell显现列表一致

### 步骤9：如果发现分类学问题，触发修正流程

**输入**：步骤2的domain列表 + 步骤3的段结构模式列表 + 步骤8的对比报告

**操作**：
1. 检查：分类学是否无法覆盖这道题的某个tell？→ 触发修正
2. 检查：用FCA理论审查分类学是否不自洽？→ 触发修正
3. 如果没有问题 → 分析完成，产出落盘

**输出**：修正决策（触发修正 / 不触发修正）。如果触发修正，进入版本化审计铁律的7条铁律流程

**验证**：如果触发修正，确认修正流程按7条铁律执行（包括铁律7：Schema同步更新）

## 版本化审计铁律

**Tell分类学文件是`FCA学习笔记/08-先验Tell分类学.md`。每次修正必须遵循以下铁律：**

### 铁律1：版本历史在文件明面上，不在git log中
- 版本历史在08号文件最顶部（`## 版本历史（明面审计 · 全修正历史）`节）
- 读者一打开就能看到分类学的演化全历史
- 不依赖git log追溯——git log是代码变更记录，不是分类学的认知演化记录

### 铁律2：每次修正必须记录四要素
1. **触发**：什么例子/什么理论审查触发了修正
2. **修正**：什么被改了（旧结构→新结构）
3. **FCA理论依据**：为什么在FCA理论下这个修正是必要的
4. **覆盖性检查**：旧版本的所有情况在新版本中是否可表达（逐项验证）

### 铁律3：覆盖性检查必须逐项验证
- 列出旧版本的每个分类/每个属性维度
- 对每一项，说明它在新版本中如何被表达
- 如果某项在新版本中无法表达 → 修正不通过，必须调整新版本直到能覆盖

### 铁律4：版本总表必须更新
- 版本总表在08号文件顶部（`### 版本总表`）
- 每次修正追加一行：版本号 | 触发 | 核心修正 | 覆盖性检查结论
- 版本号递增：v1, v2, v3, ...

### 铁律5：修正后的文件结构必须完整
- 所有章节标题与新版本一致（如v3把"模式1：无尽追逐"改为"模式1：构造-分析-排除"，后续模式重新编号）
- 形式背景表格与新版本一致（如v3把"无尽追逐"列改为"探索-诊断-修复"列）
- 概念格描述与新版本一致
- 一句话总结与新版本一致
- 不能有遗留的旧版本措辞（修正后用grep检查）

### 铁律6：关联文件必须同步修正
- 如果08号文件的分类学修正影响09号文件（对比分析文件）或其他文件，必须同步修正
- 同步修正后，关联文件中引用的分类学版本号必须更新

### 铁律7：AGENTS.md Schema节必须同步更新
- AGENTS.md中的"Tell分类学Schema"节是跨压缩边界保真的核心——session压缩后AI只靠这一节恢复分类学认知
- 08号文件修正后，必须同步更新AGENTS.md Schema节，使两者一致
- 具体维护SOP见`.devin/rules/tell-taxonomy-schema-maintenance.md`
- **不一致即违反本铁律**——08号文件和AGENTS.md Schema节必须在每次修正后保持一致

### 铁律8：高Level概念降低Level的审计（333号）

**高Level概念（如同构之桥）降低Level为具体形式时，必须审计两个风险（333号§2.3）：**

1. **组合爆炸审计**——降低Level后新增的tell/hint数量是否合理？如果领域数×具体形式数导致数量爆炸，需要评估是否改为启发式触发（334号）或动态生成（335号§3.5）替代预先全部展开
2. **覆盖缺口审计**——降低Level后的具体形式是否覆盖了所有相关子类？如果分类学后续细化新增了子类，已有的降低Level展开是否需要补充？

**降低Level后的具体形式必须标记`case_source`（333号§6.4）**：
- `case_source: mathematics`——有数学案例支撑（如FLT的Frey曲线构造）
- `case_source: system`——有系统运行案例支撑（系统运行中积累的成功案例）
- `case_source: none`——只有元模式支撑，没有具体案例

**`case_source: none`的具体形式在hint输出时必须是低压力的**（334号§5.4）——"你也可以考虑跨域"而不是"你应该跨域"。

### 铁律9：结构知识与内容知识分离的审计（336号）

**分类学修正时必须区分结构知识修改和内容知识修改：**

- **结构知识修改**（修改domain定义、段结构模式定义、子模式定义）——等于修改分类学的维度，影响所有使用该分类的tell，必须执行完整的7条铁律+覆盖性检查
- **内容知识修改**（增删具体tell条目）——不影响分类学的维度，只需要常规审计

**高Level概念（如同构之桥）是结构知识（坐标轴），降低Level后的具体形式是内容知识（点）。** 修改高Level概念的定义是结构知识修改，增删高Level概念降低Level后的具体tell是内容知识修改。

## 批量再分析的工作流

### 抽样验证优先
- 不直接对455题全量做FCA再分析
- 先抽10题做FCA再分析，验证格化思考的普适价值
- 如果10题都验证了价值，再决定是否全量或只做POC题

### 单题工作量基准
- 从IMO 2024 P5的分析看，单题FCA重做约45分钟
- 455题全量约341小时——不能手动做，需要用AI批量做

### 批量方案选择
- **方案A**：subagent批量重做（和原始profile提取类似的工作流）
- **方案B**：先抽样验证再决定（推荐）
- **方案C**：只对`suitable_for_poc=true`的题目做

## 不做什么

- **不自己做FCA再分析（主agent）**——主agent是流程管理者，不是分析者。FCA再分析委托给subagent做。主agent自己做的场景仅限于：只有1道题且不需要并行、或subagent失败后需要手动复现
- **不委托分类学修正给subagent**——修正流程涉及多文件同步（08号文件+AGENTS.md Schema节+09号文件），由主agent统一执行
- **不跳过铁律0（TODO List建立）**——不建立TODO List就开始分析 = 违反铁律0 = 必须停下来先建立TODO List
- **不跳过铁律0.5（产出验证）**——subagent返回后不验证产出就接受 = 违反铁律0.5 = 必须停下来先验证
- **不跳过步骤0（V6加载）**——V6是格化+全Level Trace识别的完整操作指南，不加载就做分析等于盲目操作。即使你认为自己记得V6的内容，也必须重新加载——因为你的"记忆"可能来自被压缩的上下文，可能不完整
- **不做没有FCA理论依据的修正**——每次修正必须有FCA理论依据（如"属性必须是对象的固有特征"）
- **不做没有覆盖性检查的修正**——每次修正必须逐项验证旧版本的所有情况在新版本中是否可表达
- **不把版本历史只放在git log中**——版本历史必须在08号文件明面上
- **不在再分析中跳过步骤**——10步SOP（步骤0-9）必须完整执行，特别是步骤0（V6加载）、步骤5（多Level观察）和步骤8（对比）
- **不把观察Level（局部/非局部/全局）当作tell的属性维度**——它是观察参数（FLT例子v2修正的结论）
- **不把trace特征（如无尽追逐）当作独立的段结构模式属性**——它是"探索-诊断-修复"的子模式（v3修正的结论）
