# 代码作为研发经验载体原则

## 触发条件

编写或修订six/目录下的代码（types.py / pipes.py / prompts.py / principles.py / reflection.py / references.py等）时。

## 核心原则

**代码不仅记录目标系统要实现什么（数据结构、接口、算法），也记录研发过程中学到的什么（POC验证结果、设计决策的为什么、版本演进原因）。**

代码是研发过程经验的最终沉淀点——不只是文档才是。开发者读代码时，不仅能看到"系统是什么"，还能看到"系统为什么是这样"。

## 具体规则

### 1. 代码中放什么——关键经验

代码的docstring / notes字段中放以下关键经验：

- **POC验证结果**——哪个POC验证了什么、成功还是失败、关键发现
- **设计决策的为什么**——为什么选方式A不选方式B/C、为什么加自我审计报告、为什么用FCA语言规范化术语
- **版本演进原因**——V4→V5改了什么为什么改、V5→V6改了什么为什么改
- **关键审计发现**——VMS-28审计发现V4反思太软、VMS-28b审计发现subagent自己识别了FCA框架局限性

### 2. 代码中不放什么——详细分析

以下内容放研发过程文档，不放代码：

- 完整的对比分析表格（V4 vs V5逐维度对比）
- subagent的完整产出文本
- 审计报告的完整9项内容
- 来源索引（每个认知来自哪份文档）
- 和327号v1方案的差异分析

### 3. 代码中怎么引用文档

代码中放关键经验时，同时给出文档引用：

```python
"""
【VMS-28验证结果2026-08-10】成功——7个Level、23个非局部trace。
step_2_grid_vein()选方式A。详见329号§8.3。
"""
```

格式：`【<经验摘要>】<关键发现>。详见<文档编号>§<章节>。`

### 4. 哪些代码位置放经验

| 代码位置 | 放什么经验 | 当前状态 |
|---|---|---|
| pipes.py的docstring | POC验证结果、方式选择原因、FCA立场声明 | 已做 |
| prompts.py的notes字段 | 版本演进原因、验证状态、FCA术语映射 | 已做 |
| types.py的docstring | 数据结构的设计原因、FCA对应、自我审计要求 | 已做 |
| principles.py的docstring | 原则的来源和演进 | 待检查 |
| reflection.py的docstring | 反思原则的来源和演进 | 待检查 |
| references.py的docstring | 文档索引的来源 | 待检查 |

### 5. 和文档的关系

| 载体 | 性质 | 放什么 |
|---|---|---|
| 代码（docstring/notes） | 离开发者最近——always-on | 关键经验摘要+文档引用 |
| 研发过程文档（第六代系统研发过程文档/） | 完整记录——按需读 | 完整分析、对比表格、subagent产出、审计报告 |
| 技术说明书（第六代系统技术说明书/） | 沉淀和整合——按需读 | 经过确认的系统规格 |

三者互补——代码是"摘要+索引"，文档是"完整记录"，技术说明书是"最终规格"。

## 为什么代码也要记录研发经验

1. **代码是always-on的**——开发者每次看代码都能看到这些经验，不需要额外去读文档
2. **文档可能被忽略**——开发者不一定会读研发过程文档，但一定会读代码
3. **代码中的注释是"离开发者最近的知识"**——开发者在写代码、改代码时，旁边的注释就是最直接的知识来源
4. **研发经验影响实现决策**——为什么step_2_grid_vein()选方式A、为什么Parser AI需要自我审计报告——这些经验直接影响代码怎么写，应该和代码在一起
