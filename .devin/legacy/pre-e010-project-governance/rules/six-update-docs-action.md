# "更新文档"动作定义——system系统研发语境

**触发条件**：用户在system系统研发过程中说"更新文档"时。本rule定义"更新文档"这个短语在system系统研发语境下的完整动作清单。

## 核心约束

**"更新文档"在system系统研发中不是一个简单动作，而是一个需要全面检查的流程。** 用户说"更新文档"时，必须按以下清单逐项检查，确认哪些需要更新，然后执行。不允许只更新一部分就停下。

## "更新文档"的完整动作清单

### 第1层：三件套同步检查（.py / .ref / .ai-check）

对本次修改涉及的每个`.py`文件，检查三件套是否同步：

| 检查项 | 怎么检查 | 何时需要更新 |
|---|---|---|
| `.py`代码变更了吗 | 对比git diff | 如果变了→进入下面所有检查 |
| `.ref`还准确吗 | 代码引用的文档路径是否仍然存在、章节编号是否仍然正确 | 代码职责变了→.ref可能需要加新文档；文档路径变了→.ref需要更新路径 |
| `.ai-check`还准确吗 | 检查项目是否仍然覆盖了代码的所有关键行为 | 代码新增了检查点→.ai-check的"代码能检查的"节可能需要加项；代码新增了行为→.ai-check的"AI需要检查的"节可能需要加项 |

**规则**：改了`.py`必须检查`.ref`和`.ai-check`。改了`.ref`必须检查`.ai-check`（参考文档变了，检查标准可能也要变）。三个文件必须同步。

### 第2层：系统设计文档同步

检查本次代码变更是否影响了系统设计文档，需要更新哪些：

| 设计文档 | 何时需要更新 |
|---|---|
| `第六代系统技术说明书/07-工程规格/01-系统架构总图.md` | 架构变了（新增组件/数据流变了/部署方式变了）；新增了rule（§6/§7/§8等节） |
| `第六代系统技术说明书/06-五代继承/02-第六代的独特贡献.md` | 系统创新变了（4并发方案/三层验证体系/AI优势元素等） |
| `第六代系统技术说明书/01-基础概念/02-trace-tell-hint三步链路.md` | 基础概念变了（trace/tell/hint的定义或关系变了） |
| `第六代系统技术说明书/README.md` | 系统物理实现方向变了（两个入口的定义/会话与启动目录结构变了） |
| `第六代系统提示词积累目录/...` | 提示词版本变了（新增V10/修改了V9/验证状态变了） |

**怎么检查**：看本次代码变更涉及哪些设计概念，然后检查对应的设计文档是否还和代码一致。

### 第3层：AGENTS.md同步

检查AGENTS.md中的以下节是否需要更新：

| AGENTS.md节 | 何时需要更新 |
|---|---|
| rule索引表 | 新增了rule / 修改了rule的触发条件 / 修改了rule文件路径 |
| 六代研发核心方向 | 研发方向变了（新增了方向/完成了某个方向） |
| TODO节 | 完成了某个TODO / 发现了新TODO |
| 认知资产表 | 新增了认知资产（新文档/新代码/新rule） |

### 第4层：six/架构描述代码同步

检查`six/`目录下的架构描述代码是否需要更新：

| six/文件 | 何时需要更新 |
|---|---|
| `six/pipes.py` | Pipe函数的docstring（POC验证结果/4并发方案/运行时闭环反馈等） |
| `six/prompts.py` | 提示词版本登记（新增了版本/验证状态变了） |
| `six/types.py` | 数据结构定义（和system/schema.py同步） |
| `six/loops.py` | 调用关系（Pipe之间的衔接） |
| `six/references.py` | 映射关系（POC编号/核心问题/提示词版本等） |

### 第5层：TODO.md同步

检查`system/TODO.md`是否需要更新：

| 检查项 | 何时需要更新 |
|---|---|
| 完成了某个TODO | 标记为完成，记录完成方式 |
| 发现了新TODO | 新增TODO条目，标注来源/问题/影响/选项/建议 |
| TODO的优先级变了 | 调整优先级（如从"中"升为"高"） |

### 第6层：rule文件同步

检查`.devin/rules/`下的rule文件是否需要更新：

| rule | 何时需要更新 |
|---|---|
| `six-trace-preservation.md` | 痕迹保留的目录结构变了 / 新增了需要保留的痕迹类型 |
| `six-ai-agent-launch.md` | AI Agent启动流程变了 / tmux session命名规范变了 |
| `six-dual-check-mechanism.md` | 检查机制变了 / .ai-check文件格式变了 |
| `six-mechanization-reference.md` | 机械化过程描述+程序验证的流程变了 / V版本验证结果变了 |
| `system-ref-sync.md` | 三件套同步规则变了 |
| 其他six-*.md | 和本次代码变更相关的rule |

## "更新文档"的执行流程

```
用户说"更新文档"
  ↓
第1步：识别本次代码变更涉及的文件
  → git diff 看改了哪些.py文件
  ↓
第2步：第1层——三件套同步检查
  → 对每个改了的.py文件，检查同名.ref和.ai-check是否需要更新
  → 更新不同步的.ref和.ai-check
  ↓
第3步：第2-6层——逐层检查
  → 第2层：系统设计文档——本次变更影响了哪些设计概念？
  → 第3层：AGENTS.md——rule索引表/核心方向/TODO/认知资产表需要更新吗？
  → 第4层：six/架构描述代码——pipes.py/prompts.py/types.py等需要更新吗？
  → 第5层：TODO.md——完成了某个TODO或发现了新TODO吗？
  → 第6层：rule文件——和本次变更相关的rule需要更新吗？
  ↓
第4步：执行所有需要的更新
  → 不允许只更新一部分就停下
  → 如果某一层检查后确认不需要更新，跳过该层（但必须检查过）
  ↓
第5步：commit
  → 把所有更新一起commit
  → commit message说明更新了哪些文档、为什么更新
```

## 快速判断表——哪些变更需要更新哪些文档

| 变更类型 | .ref | .ai-check | 设计文档 | AGENTS.md | six/ | TODO.md | rule |
|---|---|---|---|---|---|---|---|
| 新增.py文件 | ✅新建 | ✅新建 | 可能 | ✅认知资产 | 可能 | 可能 | 可能 |
| 修改.py实现逻辑 | 检查 | ✅ | 可能 | 可能 | 可能 | 可能 | 可能 |

| 新增提示词版本 | ✅ | 可能 | ✅ | 可能 | ✅prompts.py | 可能 | 可能 |
| 新增rule | 可能 | 可能 | ✅ | ✅索引表 | 可能 | 可能 | ✅新建 |

## 注意事项

1. **"更新文档"不等于"更新所有文档"**——是"检查所有文档，更新需要更新的"。如果某一层检查后确认不需要更新，跳过该层。
2. **不允许漏检**——即使你认为某层不需要更新，也必须检查过再跳过，不能直接跳过。
3. **commit要包含所有更新**——如果多个文档需要更新，一起commit，不要分多次commit。
4. **如果用户只说了"更新文档"没有其他上下文**——按本rule的完整清单检查，不要问"你要更新哪些文档"——本rule已经定义了完整清单。
