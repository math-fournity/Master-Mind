## 1. 目标与边界

### 1.1 目标

实现从阶段1（A/B实验·串行单AI·注入提示让旧AI继续）到阶段2（串行多AI·AI自然终止后启动新AI给脉络）的跃迁。

**阶段2的核心区别**：
- 阶段1：1个AI，thinking完成→注入提示→同一AI继续thinking（需要让AI停下）
- 阶段2：AI跑完（或崩溃）后→系统整理脉络→在终点节点检索方向→启动**新AI**给它脉络+方向→新AI继续探索（不需要让AI停下）

### 1.2 边界

**做**：
- ArangoDB树存储（tree_nodes/tree_edges/problems/ai_instances 4个集合）
- 从AI trajectory提取树节点（封装DevinCliParserProvider）
- 脉络构造（从根到当前节点的路径→给新AI的输入文本）
- AI终止检测（改造stall_detector语义）
- 串行多AI实验编排（AI终止→整理→检索→启动新AI的循环）
- 一次端到端实验验证

**不做**（留给阶段3）：
- 并发AI管理（ai_manager.py）
- 实时树整理（AI运行中就提取节点）——阶段2是AI终止后才提取
- 停机判定的形式化验证（solution_verifier.py）——阶段2用人工检查
- 树生长引擎主循环（tree_engine.py）——阶段2用编排脚本替代

### 1.3 与阶段1的复用关系

| 阶段1能力 | 阶段2中的角色 | 改造 |
|---|---|---|
| solver_harness.py | 启动每个AI实例 | 无需改造，每个AI一次launch |
| mitm_proto_capture.py | 采集每个AI的thinking | 无需改造（workdir_mapping已支持） |
| DevinCliParserProvider | 从trajectory提取节点处境 | 无需改造 |
| RetrievalPipeline | 在终点节点检索方向 | 无需改造 |
| ConstrainedPolicy | 选择探索方向 | 无需改造 |
| trajectory_watcher.py | 监控sessions.db获取trajectory | 无需改造 |
| stall_detector.py | ~~检测卡住触发注入~~ → 检测AI终止 | 改造语义 |
| hint_injector.py | ~~注入提示~~ → 废弃 | 不使用 |

### 2.2 数据流（单次循环）

```
1. 启动AI-1（solver-harness launch，给problem.txt）
2. AI-1运行（mitmproxy截获thinking + sessions.db记录trajectory）
3. 检测AI-1终止（termination_detector检测tmux session结束/Response truncated/崩溃）
4. AI-1终止后：
   a. 读取AI-1的thinking_readable.txt + sessions.db trajectory
   b. node_extractor从trajectory提取节点 → 写入tree_store
   c. 在AI-1的终点节点上跑RetrievalPipeline + ConstrainedPolicy → 选出方向Q
   d. path_constructor从根到终点节点构造脉络文本
   e. 脉络文本 + 方向Q → 写入AI-2的problem.txt
5. 启动AI-2（solver-harness launch，给含脉络的problem.txt）
6. 重复2-5，直到找到解答或达到最大AI数
```

### 2.3 与267号主循环的对应

267号§7.1的主循环是阶段3（并发）的设计。阶段2是其串行退化：

| 267号主循环步骤 | 阶段2实现 |
|---|---|
| 1. 采集所有running AI的trajectory | 只采集当前唯一的AI |
| 2. 整理树：从trajectory提取新节点 | AI终止后批量提取（非实时） |
| 3. 检查停机 | 人工检查（阶段2不做自动验证） |
| 4. 检查AI终止→在终点节点做检索 | termination_detector + retrieval |
| 5. 分配新AI | 串行启动1个新AI |
| 6. 实时检索（growing节点） | 不做（阶段2只在终止后检索） |

## 3. 模块设计

### 3.1 tree_store.py

**职责**：ArangoDB树存储，管理tree_nodes/tree_edges/problems/ai_instances 4个集合的CRUD。

**ArangoDB集合**（267号§6.1）：

| 集合 | 类型 | 说明 |
|---|---|---|
| `tree_nodes` | document | 节点=数学处境（六元组+path_from_root） |
| `tree_edges` | edge | 边=提示Q（_from父节点→_to子节点） |
| `problems` | document | 题目（每题一棵树） |
| `ai_instances` | document | 推理AI实例注册 |

**接口设计**：

```python
class TreeStore:
    def __init__(self, db_name=None, host=None, username=None, password=None, in_memory=False)
    
    # problems
    def create_problem(self, problem_id: str, problem_text: str) -> str  # 返回root_node_key
    def get_problem(self, problem_id: str) -> Optional[dict]
    def update_problem_status(self, problem_id: str, status: str)
    
    # tree_nodes
    def add_node(self, problem_id: str, node: TreeNode) -> str  # 返回node_key
    def get_node(self, node_key: str) -> Optional[TreeNode]
    def get_nodes_by_problem(self, problem_id: str) -> List[TreeNode]
    def get_growing_nodes(self, problem_id: str) -> List[TreeNode]
    def update_node_status(self, node_key: str, status: str, **extra_fields)
    
    # tree_edges
    def add_edge(self, problem_id: str, edge: TreeEdge) -> str  # 返回edge_key
    def get_edges_by_problem(self, problem_id: str) -> List[TreeEdge]
    def get_child_edges(self, node_key: str) -> List[TreeEdge]
    
    # ai_instances
    def register_ai(self, ai: AIInstance) -> str  # 返回ai_key
    def get_ai(self, ai_key: str) -> Optional[AIInstance]
    def update_ai_status(self, ai_key: str, status: str, end_reason: str = "", nodes_contributed: List[str] = None)
    
    # 路径查询
    def get_path_from_root(self, node_key: str) -> List[str]  # 返回node_key列表
```

**数据类**：

```python
@dataclass
class TreeNode:
    problem_id: str
    node_type: str          # root/internal/leaf_success/leaf_deadend/leaf_truncated
    situation: dict         # 六元组 V_t/F_t/O_t/U_t/T_t/S_t
    situation_text: str     # 从thinking提取的自然语言描述
    depth: int
    parent_edge_key: Optional[str]
    path_from_root: List[str]  # node_key序列
    created_by_ai: str      # ai_instance_id
    created_at: float
    trajectory_segment: dict    # thinking片段+tool_calls
    status: str             # growing/completed/deadend/truncated
    retrieval_done: bool
    directions_identified: List[str]  # 方向Q的ID列表

@dataclass
class TreeEdge:
    problem_id: str
    _from: str              # 父节点 tree_nodes/xxx
    _to: str                # 子节点 tree_nodes/yyy
    hint_q: str             # 提示Q内容
    hint_q_id: str          # Pattern ID（如有）
    hint_level: float
    ai_instance_id: str
    edge_status: str        # growing/completed/deadend/truncated

@dataclass
class AIInstance:
    problem_id: str
    entry_node_key: str     # 进入树的节点
    entry_edge_key: Optional[str]
    path_text: str          # 脉络文本
    hint_q: str             # 引导方向Q
    tmux_session: str
    devin_session_id: str
    status: str             # running/completed/crashed/truncated
    started_at: float
    ended_at: float
    end_reason: str         # token_limit/crash/solution_found/manual_stop
    trajectory_dir: str
    nodes_contributed: List[str]
```

**实现要点**：
- 连接方式复用`rule_store.py`的模式：`from arango import ArangoClient`，环境变量`ARANGO_DB=grove_math`
- `in_memory=True`模式供单元测试用
- `path_from_root`冗余存储——脉络构造时直接读取，无需递归AQL查询
- 首次使用时自动创建集合（`ensure_collections()`）

### 3.2 node_extractor.py

**职责**：从AI的trajectory中提取树节点。封装DevinCliParserProvider + 六元组提取。

**接口设计**：

```python
class NodeExtractor:
    def __init__(self, math_parser: MathParser = None, tree_store: TreeStore = None)
    
    def extract_nodes_from_trajectory(
        self,
        ai_instance_id: str,
        problem_id: str,
        trajectory: str,        # thinking_readable.txt内容
        entry_node_key: str,    # AI从哪个节点开始
        entry_edge: TreeEdge,   # AI沿哪条边进入
    ) -> List[str]  # 返回创建的node_key列表
```

**工作流程**：
1. 把trajectory按轮次分割（每个thinking round对应一个节点）
2. 对每个轮次调用`DevinCliParserProvider`解析→`ParseResult`（语义事件+六元组）
3. 每个ParseResult创建一个`TreeNode`：
   - `situation` = 六元组
   - `situation_text` = 从thinking提取的自然语言描述
   - `trajectory_segment` = 本轮次的thinking片段+tool_calls
   - `path_from_root` = 父节点的path_from_root + 本节点key
   - `created_by_ai` = ai_instance_id
4. 通过`tree_store.add_node()`写入ArangoDB
5. 返回创建的node_key列表

**关键设计决策**：
- **按轮次分割**：一个AI的trajectory可能有多轮thinking（如A/B实验中A组有6.7轮平均），每轮对应一个节点
- **轮次边界检测**：复用TrajectoryWatcher的Round边界检测逻辑（user消息=边界）
- **降级处理**：如果parser解析失败（parse_confidence < 0.5），仍创建节点但situation为空，situation_text用thinking原文前2000字符

### 3.3 path_constructor.py

**职责**：从根到当前节点的路径，构造给新AI的输入文本（脉络）。

**接口设计**：

```python
class PathConstructor:
    def __init__(self, tree_store: TreeStore)
    
    def construct_path_text(
        self,
        node_key: str,          # 当前节点（脉络终点）
        direction_q: str,       # 给新AI的引导方向Q
    ) -> str                    # 脉络文本
```

**脉络文本格式**（267号§7.2）：

```
你正在解答以下数学题：
[题目原文]

之前已经进行了以下探索：

[节点0] 初始处境：题目给出的条件和目标
  → 提示Q1：[Q1内容]
[节点1] 处境：[从thinking中提取的数学处境描述]
  已证明：[已确立的结论]
  当前表示：[当前的数学表示]
  → 提示Q2：[Q2内容]
[节点2] 处境：[...]
  ...
[节点n] 当前处境：[当前节点的数学处境描述]
  已证明：[到目前为止已确立的结论]
  当前表示：[当前的数学表示]
  卡在：[当前卡点]

请理解验证以上路径后，继续探索以下方向：
[方向Q的内容]

继续推理，给出完整的推理过程。
```

**实现要点**：
- 从`tree_store.get_path_from_root(node_key)`获取路径
- 遍历路径中每个节点，从`tree_store.get_node()`获取situation_text
- 边的hint_q从`tree_store.get_child_edges()`获取
- 根节点的situation_text用problem_text替代
- 如果节点situation_text为空（parser降级），用trajectory_segment的thinking前500字符替代

### 3.4 termination_detector.py（从stall_detector改造）

**职责**：检测推理AI是否自然终止。不是检测"卡住"，而是检测"结束了"。

**与stall_detector的区别**：

| stall_detector（阶段1） | termination_detector（阶段2） |
|---|---|
| 检测AI卡住→触发提示注入 | 检测AI终止→触发节点提取+检索+启动新AI |
| 语义检测"我不知道"等关键词 | 检测tmux session结束/Response truncated |
| 超时30秒无新节点 | 超时可配置（默认120秒，给AI更多时间） |
| 返回StallEvent | 返回TerminationEvent（含终止原因） |

**接口设计**：

```python
@dataclass
class TerminationEvent:
    detected_at: float
    reason: str          # "session_ended"/"response_truncated"/"timeout"/"crash"
    tmux_session: str
    details: str = ""    # 额外信息

class TerminationDetector:
    def __init__(self, timeout: float = 120.0)
    
    def check_terminated(self, tmux_session: str, exp_id: str) -> Optional[TerminationEvent]
```

**终止检测逻辑**：
1. **session_ended**：`tmux has-session`返回false→AI进程已退出
2. **response_truncated**：pane最后8行含"Response truncated"→AI token用尽
3. **timeout**：thinking_readable.txt超过timeout秒无增长→可能卡死
4. **crash**：pane含"Connection failed"/"Error"→进程崩溃

**优先级**：session_ended > crash > response_truncated > timeout

### 3.5 串行多AI编排脚本（scripts/serial_multi_ai.py）

**职责**：编排阶段2的完整流程——启动AI→等终止→提取节点→检索方向→构造脉络→启动新AI。

**接口设计**：

```python
def run_serial_multi_ai(
    problem_id: str,
    problem_text: str,
    max_ai_count: int = 5,
    max_time_per_ai: int = 600,
    model: str = "glm-5-2",
):
    """
    串行多AI树生长实验。
    
    流程：
    1. 在tree_store中创建problem + root_node
    2. 启动AI-1（给problem.txt，不给脉络）
```

## 7. 关键设计决策

### 7.1 为什么阶段2不做实时树整理

267号主循环步骤2是"实时从trajectory提取新节点"。但阶段2选择AI终止后批量提取，原因：
1. 实时提取需要并发监控AI的trajectory，增加复杂度
2. 阶段2是串行的，AI终止后系统有空闲时间做批量提取
3. 批量提取的parser调用可以更从容（DevinCliParserProvider需要25-200秒）
4. 实时提取留给阶段3（并发时必须实时）

### 7.2 为什么阶段2不做自动停机判定

267号§7.5的停机判定需要SymPy/形式化验证。阶段2选择人工检查，原因：
1. 自动验证证明正确性是独立难题（solution_verifier.py是阶段3的任务）
2. 阶段2的目的是验证"脉络注入+串行多AI"机制本身，不是验证自动停机
3. 人工检查3个AI的输出是可行的

### 7.3 为什么用problem.txt传递脉络而非tmux send-keys

阶段1用tmux send-keys注入提示到运行中的AI。阶段2改为写入problem.txt给新AI，原因：
1. 新AI是全新启动的devin cli实例，没有运行中的tmux session可注入
2. problem.txt是新AI启动时读取的第一个文件，自然成为脉络载体
3. 避免了阶段1的tmux send-keys时序问题（排队/Enter/状态检测）

### 7.4 为什么termination_detector是独立模块而非改造stall_detector

虽然termination_detector从stall_detector改造，但做成独立模块，原因：
1. 语义完全不同——stall_detector是"检测卡住触发注入"，termination_detector是"检测终止触发检索分配"
2. 共存需要——阶段2的编排脚本可能同时需要stall_detector（检测AI中途卡住）和termination_detector（检测AI终止）
3. 避免破坏现有代码——stall_detector被RealtimePipeline使用，改造它会影响阶段1的代码

## 8. 风险与应对

| 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|
| DevinCliParserProvider解析新AI的trajectory失败 | 中 | 节点situation为空 | 降级处理：用thinking原文替代situation_text |
| 新AI不理解脉络文本格式 | 中 | 新AI忽略脉络直接重做 | 脉络文本格式迭代优化 |
