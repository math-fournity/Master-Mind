## 0. 为什么记录本文档

306号定义了"我们到底想要什么"——分层的带标记的思维拓扑。但306号§8-§11暴露了一系列规范定义问题（粒度/拓扑化/段结构/脉络边界），以及Lean formalization的局限（排斥探索性思维）。

用户在本轮提出了一个统一解决这些问题的构想：要求推理AI必须用有限原语表达推理过程。这个构想把四个规范问题统一成一个——原语集的定义。本文档完整记录用户的提问和AI的回复。

## 1. 用户的提问（完整记录）

> 我有一个模糊的想法，就是要求推理AI，必须把自己的探索过程全部表达为比如Lean（如果它真的可以），我不知道Lean是不是就出现了函数调用？还是说表达成Python？但是我们必须提供一些"原语"，有限的原语。也就是说，推理AI表达自己的推理过程，必须使用这些原语进行表达。如果原语不够，那么可以增加原语，原语是放在数据库的一张表中可查的，这张表可以增长，但是增长之前要求AI必须确认它在增加一个不存在的原语，而且增加的是原语，是可以泛化和复用的。如果这个理想的想法是对的，那么很多问题是不是都解决了。比如什么思维的拓扑，分层的，那不就是函数调用的分层结构吗？

## 2. AI的回复（完整记录）

### 2.1 这个想法非常深刻——它把四个问题统一成了一个

#### 用户的洞察

如果推理AI必须用有限原语表达推理过程，那么：

**思维的拓扑 = 函数调用图**
- 每个原语调用是一个节点
- 调用关系是边
- 拓扑自动生成，不需要辅助AI提取

**分层 = 调用层次结构**
- 高层原语调用低层原语（`try_modular_analysis`内部调用`compute_mod`、`check_divisibility`）
- 不同Level = 不同调用深度
- 分层自动存在，不需要额外定义

**节点类型 = 原语类型**
- 原语集就是节点类型集
- 不需要T图的11+12种类型——原语就是类型

**粒度 = 原语粒度**
- 每个原语调用是一个节点
- 粒度由原语粒度自然定义

**四个规范全部坍缩成一个：原语集的定义。**

#### 305号的例子用原语重写

```
try_modular_analysis(n, 3) → inconclusive
try_modular_analysis(n, 5) → partial_exclude(n ∤ 5)
try_modular_analysis(n, 7) → complex
try_modular_analysis(n, 11) → complex
-- AI卡住
```

辅助AI看到这段，不需要做拓扑化——原语调用序列本身就是拓扑。"模分析无尽追逐"这个非局部tell，现在表现为**连续4次调用`try_modular_analysis`且返回值从inconclusive→partial→complex**。这个模式可以直接用形式化规则匹配：

```
pattern chase: consecutive_calls(same_primitive, count≥3, diminishing_returns)
```

**段结构规范也变成了原语调用模式匹配**——不需要辅助AI理解"追逐"的语义，只需要匹配"连续调用同一原语且收益递减"的形式化模式。

#### 原语集的增长机制

用户说的增长机制很关键：

**1. 原语放在数据库表中可查**——原语集是显式的、可查询的、不是隐含在AI的thinking里的

**2. AI可以增加原语，但必须确认：**
- 这个原语不存在（不能重复造）
- 这个原语是可泛化和复用的（不能造只适用于一个题目的原语）

**3. 这就是287号"去特化"的自然实现**——原语本身就是去特化的产物。Level 0的题目特化tell不能成为原语（不可泛化），Level 1的可泛化tell才能成为原语。原语集的增长过程就是tell去特化的过程。

#### 这和女娲T图的关系

T图的11种节点类型+12种边类型可以成为**初始原语集**：

节点类型→原语：
- `observe(context)` — 观察到
- `claim(statement)` — 声称
- `represent(expr, form)` — 表示
- `set_subgoal(goal)` — 设子目标
- `test(conjecture)` — 测试
- `detect_contradiction(stmt1, stmt2)` — 发现矛盾
- `backtrack_to(node)` — 回溯
- `resolve(method)` — 解决

边类型→调用关系：
- `infer(premises, conclusion)` — 推断
- `recall(knowledge)` — 回忆
- `transform(expr1, expr2)` — 变换
- `decompose(problem, parts)` — 分解
- `compare(obj1, obj2)` — 比较
- `analogize(source, target)` — 类比

**T图是初始原语集，原语集可以增长——这解决了T图"可能不够覆盖"的问题（306号§9.5）。** 不够覆盖时不是修改T图，是增加新原语。

### 2.2 但有几个问题需要想清楚

#### 1. 探索性思维能不能用原语表达？

305号的模分析追逐是探索性的，但用原语表达没问题——`try_modular_analysis(n, m)`就是一个原语，探索性体现在AI选择调用哪个原语、用什么参数。探索性不是"不能formalize"，是"选择哪个方向的formalize"——选择是AI的，formalize是原语的。

**但有些探索性思维可能真的不能formalize**——"我觉得这个方向有戏"这种直觉。这需要一个escape hatch原语：`free_thinking(text)`，AI用这个原语表达还不能formalize的思考。`free_thinking`的内容是自然语言，辅助AI需要处理它——但`free_thinking`的出现本身是一个信号（AI在这里遇到了原语不能覆盖的思维）。

#### 2. 原语会不会过度增长？

用户说的约束很重要——"必须确认增加的是不存在的、可泛化和复用的原语"。但"可泛化和复用"的判断标准是什么？如果一个原语只被用过一次，它是不是不应该被加入？

可能的机制：新原语先进入"候选原语"表，被调用N次以上才升级为"正式原语"。这保证了原语的可复用性是经验验证的，不是AI声称的。

#### 3. 原语的参数化程度

`try_modular_analysis(n, 3)`和`try_modular_analysis(n, 5)`是同一个原语的不同调用——参数化让原语集保持小。但如果参数太自由，又回到了自然语言的问题。需要定义原语的参数类型——参数也应该是结构化的。

#### 4. 非形式部分（目的/意图）仍然没解决

原语调用捕捉了"做了什么"，没捕捉"为什么"。`try_modular_analysis(n, 3)`可能是追逐策略的一步，也可能是关键验证——原语调用本身不区分。目的/意图仍然需要Pipe 2。

但有一个改进——原语调用序列让Pipe 2的工作量大幅减少。Pipe 2不需要从自然语言中提取结构，只需要在已经结构化的原语序列上判断意图。

### 2.3 总结：这个想法解决了什么

| 问题 | 原语表达解决了吗 |
|---|---|
| 粒度规范 | ✓ 原语粒度自然定义 |
| 节点/边类型规范 | ✓ 原语集就是类型集 |
| 脉络边界规范 | ✓ 调用序列边界自然定义 |
| 段结构规范 | ✓ 原语调用模式可直接匹配 |
| 分层 | ✓ 调用层次结构自动存在 |
| 去特化 | ✓ 原语增长机制自然实现去特化 |
| 非形式部分（目的/意图） | ✗ 仍需Pipe 2，但工作量大幅减少 |
| 原语不能覆盖的思维 | 部分——`free_thinking`作为escape hatch |

**核心洞察：原语表达把"思维的拓扑化"从辅助AI的post-hoc分析变成了推理AI的in-process表达。** 辅助AI不需要从自然语言thinking中提取拓扑——推理AI直接给出了结构化的原语调用序列，拓扑是免费的。

## 3. 原语化框架下的精确对应——点=函数，边=调用关系，看法=代码重构

**触发**：用户说"AI数学思维原语化的好处是，思维的拓扑搞定了，点是什么？就是函数。边是什么，就是函数调用关系。不同Level的看法，就成了代码重构。"

### 3.1 三个对应

**点 = 函数**

每个原语是一个函数。原语调用是一个节点。不需要辅助AI判断"这里是一个点"——函数调用天然是点。

**边 = 函数调用关系**

`try_modular_analysis`内部调用`compute_mod`和`check_divisibility`——这是调用关系，就是边。不需要T图的12种边类型——调用关系天然是边，而且边的类型由被调用函数的类型决定。

**不同Level的看法 = 代码重构**

这是最深刻的洞察。

**最细看法** = 展开所有函数调用：
```
try_modular_analysis(n,3)
  └─ compute_mod(n^4+4^n, 3)
  └─ check_divisibility(result)
  └─ evaluate_conclusion(...)
try_modular_analysis(n,5)
  └─ compute_mod(n^4+4^n, 5)
  └─ ...
```

**中间看法** = 把连续的`try_modular_analysis`调用inline成一个更高层函数：
```
chase_modular_analysis(n, [3,5,7,11])
  └─ try_modular_analysis(n,3) → inconclusive
  └─ try_modular_analysis(n,5) → partial_exclude
  └─ try_modular_analysis(n,7) → complex
  └─ try_modular_analysis(n,11) → complex
```

**最粗看法** = 把整个证明inline成一个函数：
```
prove_fermat_like_theorem()
```

**代码重构就是看法切换。** 把几个函数调用合并成一个高层函数（extract method / inline）= 从最细看法到中间看法。把高层函数展开成底层调用=从中间看法到最细看法。

### 3.2 这意味着什么

**1. 看法空间搜索 = 代码重构空间搜索**

303号§13说的"看法空间有2^(n-1)种划分"——在原语化框架下，这就是"n个函数调用有几种重构方式"。代码重构是一个被深入研究的问题（refactoring catalog、design patterns、abstract interpretation），有成熟的算法和工具。

**2. 非局部tell = 重构后才显现的模式**

305号的"模分析无尽追逐"——在最细看法下是4个独立的`try_modular_analysis`调用，看不出追逐。重构成`chase_modular_analysis(n, [3,5,7,11])`后，"追逐"模式显现了——一个函数接收一个列表参数，列表长度≥3，返回值递减。

**非局部tell就是只有在某个重构层级下才显现的调用模式。** 这和303号§13说的"非局部tell只在更粗看法下出现"完全一致——只不过现在"更粗看法"有了精确的工程含义：代码重构。

**3. 概念树 = 重构模式目录**

287号的"大概念→小概念→概念树"——在原语化框架下，概念就是重构模式。大概念是粗粒度重构（把整段证明合成一个函数），小概念是细粒度重构（把几步合成一个函数）。概念树就是重构模式的层次目录。

289号的"拓扑相同Pipe 1给同分，需要小概念分辨"——两个tell在最细看法下调用序列相同，但重构成不同高层函数后显现不同模式。这就是"需要下降到子概念才能区分"——下降到更细的重构层级。

**4. Pipe 0/1/2的精确含义**

| Pipe | 原语化框架下的含义 |
|---|---|
| Pipe 0 | 生成函数调用图（推理AI直接给出，不需要辅助AI提取） |
| Pipe 1 | 在调用图上做模式匹配——匹配重构模式（大概念过滤） |
| Pipe 2 | 在匹配后的候选上判断意图/目的（为什么这样重构） |

**Pipe 0几乎消失了**——推理AI直接给出函数调用图，辅助AI不需要做拓扑化提取。Pipe 1变成了重构模式匹配——这是形式化的、可自动化的。Pipe 2仍然需要AI理解意图。

### 3.3 和FCA的精确对应

| FCA | 原语化框架 |
|---|---|
| 对象集G | 所有函数调用（节点） |
| 属性集M | 所有重构模式（概念） |
| 关系I | 一段调用序列能否被重构为某个模式 |
| 概念(A,B) | 一类调用序列(A)共有的重构模式(B) |
| 上层概念（粗粒度） | 大重构——很多调用序列都能被重构为这个模式 |
| 下层概念（细粒度） | 小重构——少数调用序列才能被重构为这个模式 |
| Hasse图的边 | 重构细化路径——从大重构到小重构 |
| 闭包算子 | "一段调用序列能被重构为哪些模式"的闭包 |

**FCA的概念格 = 重构模式的格。** 这比306号§4说的"FCA是对象-属性分层，我们要的是思维拓扑粒度分层"更精确——原语化框架下，两者是同一个东西。

### 3.4 一个新的问题——重构规则需要形式化

**代码重构需要"重构规则"——什么情况下可以把几个函数调用合并成一个高层函数？**

在软件工程里，重构规则是人工判断的（"这几个函数在做同一件事，可以extract method"）。在原语化框架下，重构规则需要形式化——否则又回到了辅助AI做post-hoc分析的问题。

可能的形式化规则：
- **连续调用同一原语** → 合并成`chase_X`模式
- **调用A后调用B且A的输出是B的输入** → 合并成`pipeline_A_B`模式
- **调用A失败后调用B** → 合并成`fallback_A_B`模式

这些重构规则就是段结构规范的形式化定义——306号§9.3说"段结构规范待定义"，在原语化框架下，段结构规范=重构规则集。

## 4. 脱水+原语化——探索性思维担心的消解

**触发**：用户说"脱水后，推理AI对题目的思维过程，原语化（规范化）似乎不是一件特别难的事情。你之前的一个担心是比如AI说'这个想法很妙'，这句话根本不在脱水版里。"

### 4.1 脱水是什么

推理AI的原始thinking里混杂着：
- "这个想法很妙"（元认知/情绪）
- "让我想想..."（犹豫）
- "我记得好像有个公式..."（模糊回忆）
- "啊哈！这就是Sophie Germain恒等式！"（直觉跳跃）
- 大量的自然语言连接词、语气词、自我对话

**脱水**就是把这些去掉，只留下：
- 做了什么操作
- 推导了什么结论
- 测试了什么conjecture
- 发现了什么矛盾

脱水后的思维是"干货"——是操作序列，不是思维的全过程。

### 4.2 脱水后原语化容易

脱水后的内容天然接近原语调用：
- "假设素数有限p1,...,pn" → `assume(finite_primes)`
- "构造N=p1·...·pn+1" → `construct(N, product_plus_one)`
- "分析N的素因子q" → `analyze_prime_factor(N)`
- "q不能等于任何pi" → `exclude(q, known_primes)`
- "矛盾" → `detect_contradiction`

每一步都是明确的操作，原语化就是给每个操作匹配一个原语。

### 4.3 "这个想法很妙"不在脱水版里

§2.2的担心是——探索性思维中的直觉/情绪/元认知（"这个想法很妙"、"我觉得这个方向有戏"）不能用原语表达。

但**这些本来就不在脱水版里。** 脱水的目的就是去掉这些，只留操作。如果"这个想法很妙"不构成一个操作，它就不应该在脱水版里出现，自然也不需要原语化。

### 4.4 脱水会不会丢掉非局部tell需要的信息？

305号的"模分析无尽追逐"——脱水后是：
```
try_modular_analysis(n,3) → inconclusive
try_modular_analysis(n,5) → partial_exclude
try_modular_analysis(n,7) → complex
try_modular_analysis(n,11) → complex
```

这个序列保留了"追逐"模式需要的信息（连续4次调用同一原语+返回值递减）。脱水没有丢掉这个非局部tell。

但如果AI的thinking里有"我发现每次换一个模，问题就变得更复杂，这条路可能走不通"——这是AI自己对追逐模式的元认知。脱水后这句话消失了。**这句话本身不是非局部tell（非局部tell是"追逐"模式），但它是AI对非局部tell的自我意识。**

**丢掉这句话有问题吗？**

可能没有——因为辅助AI的工作是从操作序列中识别非局部tell，不是从AI的自我意识中读非局部tell。AI说"我发现这条路走不通"和辅助AI从操作序列中识别出"追逐模式"，结果是相同的。辅助AI不需要AI的自我意识，辅助AI自己做识别。

但也可能有——如果AI的自我意识比操作序列更早出现（AI在第2次试模时就意识到追逐了，但操作序列要到第4次才显现模式），那丢掉自我意识会延迟非局部tell的识别。

### 4.5 脱水+原语化是配套的

**脱水+原语化是配套的。** 脱水把自然语言thinking变成操作序列，原语化把操作序列变成函数调用。两步合起来，把"从自然语言提取拓扑"变成"从操作序列直接读拓扑"。

**§2.2的担心（探索性思维不能原语化）在脱水框架下大部分消失了**——因为脱水后探索性思维的操作部分（试了什么方向、用了什么参数、得到什么结果）是可原语化的，只有非操作部分（直觉/情绪/元认知）被脱水去掉了，而那些非操作部分本来也不是tell识别需要的。

### 4.6 脱水规则的边界

**唯一需要关注的是**：脱水规则需要保证不丢掉非局部tell需要的信息。具体来说，脱水需要保留操作序列的结构（连续性、参数、返回值），可以去掉元认知和情绪。这定义了脱水规则的边界——**保留操作，去掉非操作。**

| 内容类型 | 脱水保留吗 | 原因 |
|---|---|---|
| 操作（做了什么） | ✓ 保留 | 原语化的输入 |
| 推导（得到什么结论） | ✓ 保留 | 原语的返回值 |
| 测试（验证了什么） | ✓ 保留 | 原语的调用 |
| 矛盾/失败 | ✓ 保留 | 原语的返回值 |
| 连续性/参数/返回值 | ✓ 保留 | 非局部tell识别需要 |
| 元认知（"这条路走不通"） | ✗ 去掉 | 辅助AI从操作序列自己识别 |
| 情绪（"这个想法很妙"） | ✗ 去掉 | 不是操作 |
| 犹豫（"让我想想"） | ✗ 去掉 | 不是操作 |
| 直觉跳跃（"啊哈！"） | ✗ 去掉 | 不是操作（但跳跃的结果——选了哪个方向——是操作，保留） |

## 5. 代码化的边界——只解决它能解决的那部分过滤问题

**触发**：用户说"思维的代码化，不是为了全面地记录一切思维的信息，是为了规范化的思维图谱化服务的，而思维的拓扑是为了加速检索——过滤用的，所以并不是代码化解决一切问题，它只解决它能解决的那部分过滤问题。"

### 5.1 代码化解决什么

代码化（脱水+原语化）解决的是**它能解决的那部分过滤问题**——具体来说：

**Pipe 1能自动化的部分**：
- 调用序列的结构匹配（连续调用同一原语→chase模式）
- 调用关系的拓扑匹配（A调用B vs A并行B vs A失败后B）
- 返回值模式匹配（递减→追逐，交替→振荡）

这些是形式化的、可自动化的过滤——代码化让这些过滤变得精确和高效。

### 5.2 代码化不解决什么

**Pipe 2仍然需要的部分**：
- "为什么"连续调用try_modular_analysis——是追逐策略还是系统性验证？同样的调用序列，目的可能不同。
- hint的生成——tell识别出"追逐"后，hint是"转向代数因式分解"还是"换一个更大的模"还是"放弃模分析用其他数论工具"？这需要理解题目和数学知识，不是调用序列能给出的。

**代码化不解决hint生成**——代码化帮助tell识别（过滤），不帮助hint生成（方向选择）。hint生成仍然需要辅助AI的数学理解能力。

### 5.3 §3.2的修正

§3.2说"Pipe 0几乎消失了"——这容易给人一种"代码化解决了一切"的错觉。实际上Pipe 0的**拓扑生成**部分确实几乎消失了（推理AI直接给调用图），但Pipe 0的**拓扑分析**（在调用图上识别什么模式有意义）没有消失——这部分和Pipe 1的过滤、Pipe 2的意图判断是交织的。

更准确的说法是：

| 阶段 | 代码化前 | 代码化后 |
|---|---|---|
| 拓扑生成 | 辅助AI从自然语言提取（难） | 推理AI直接给调用图（免费） |
| 结构过滤 | 辅助AI在自然语言上做模式匹配（难且不可靠） | Pipe 1在调用图上做形式化匹配（精确且自动化） |
| 意图判断 | Pipe 2从自然语言理解意图 | Pipe 2在调用图上判断意图（输入更干净但判断仍需AI） |
| hint生成 | 辅助AI完全靠理解 | **不变——仍然靠辅助AI的数学理解** |

**代码化让前两步变便宜了，后两步没有变——只是输入变干净了。**

### 5.4 目的的清晰重申

**思维代码化不是为了全面记录思维，是为了规范化的思维图谱化。**
**思维图谱化不是为了图谱本身，是为了加速检索——过滤。**
**过滤不是为了过滤掉一切，是为了缩小Pipe 2的范围。**

代码化只解决它能解决的那部分过滤问题——结构过滤。意图判断和hint生成仍然需要AI。代码化的价值是让AI只处理小范围内的意图判断，而不是在大范围内做everything。

## 6. 完整案例——连续调用try_modular_analysis的九步链路

**触发**：用户说"连续调用try_modular_analysis这个案例，你详细跟我说说"

### 6.1 第一步：推理AI的原始thinking

推理AI拿到题目"求所有正整数n使n⁴+4^n是素数"，开始思考。原始thinking大概是这样的：

```
好，我需要找所有正整数n使得n⁴+4^n是素数。

先试几个小值看看。n=1，1+4=5，是素数。n=2，16+16=32=2⁵，不是素数。
嗯，n=2就不是了。那n偶数的时候，n⁴是偶数，4^n也是偶数，和是偶数>2，
肯定不是素数。所以我只需要考虑n奇数≥3的情况。

好，n奇数≥3。我想用模分析来排除。先试模3。
n⁴ mod 3：如果n不整除3，n²≡1 mod 3（Fermat小定理），所以n⁴≡1。
4^n mod 3：4≡1 mod 3，所以4^n≡1。
和≡1+1=2 mod 3。不是0，所以模3不能排除任何n。

嗯，模3不行。试模5。
n⁴ mod 5：如果n不整除5，n⁴≡1 mod 5（Fermat小定理）。
4^n mod 5：4≡-1 mod 5，n奇数时4^n≡(-1)^n≡-1≡4。
和≡1+4=5≡0 mod 5。所以n不整除5时，n⁴+4^n是5的倍数！
如果这个数>5就不是素数。n≥3时不整除5的奇数，n⁴+4^n≥3⁴+4³=81+64=145>5，
所以不是素数。太好了，排除了n不整除5的奇数。

但是n整除5的奇数呢？n=5,15,25,...
n整除5时n⁴≡0 mod 5，4^n≡4 mod 5，和≡4 mod 5。模5不能排除。
嗯，麻烦了。这些n=5k的奇数需要新的模来排除。

试模7。4^n mod 7：4¹=4, 4²=16≡2, 4³=8≡1，周期3。
n⁴ mod 7：n不整除7时n⁶≡1，n⁴≡n⁻²。这个要看n mod 7。
n mod 7可以是1,2,3,4,5,6，n⁴ mod 7分别是1,2,4,2,4,1。
4^n mod 7要看n mod 3（因为周期3）。
但n=5k的奇数，n mod 3可以是0,1,2...
组合太多了。让我算几个：
n=5: n⁴=625, 625 mod 7=625-89*7=625-623=2。4⁵ mod 7: 5 mod 3=2, 4²≡2。和=4 mod 7。不是0。
n=15: 这个数太大了，计算很烦...
n=25: 更大...

我觉得这条路越来越复杂了。每次排除一部分，但留下新的子情况，
需要新的模来排除。模7的周期和模5不一样，组合情况更多。
也许模11？模13？每个新模都有新的周期结构...

我卡住了。模分析对n=5k的奇数情况越来越复杂，
不知道这条路能不能走通。
```

### 6.2 第二步：脱水

脱水去掉元认知/情绪/犹豫/直觉跳跃，只留操作/推导/测试/矛盾：

```
n=1: n⁴+4^n=5, 素数 ✓
n=2: n⁴+4^n=32=2⁵, 不是素数
n偶数: n⁴+4^n偶数>2, 不是素数
→ 只需考虑n奇数≥3

模3分析:
  n⁴ mod 3 = 1 (n∤3)
  4^n mod 3 = 1
  和 mod 3 = 2
  → 模3不能排除

模5分析:
  n⁴ mod 5 = 1 (n∤5)
  4^n mod 5 = 4 (n奇数)
  和 mod 5 = 0 (n∤5)
  → 排除n∤5的奇数
  但n|5时和 mod 5 = 4, 模5不能排除n=5k奇数

模7分析:
  4^n mod 7周期3
  n⁴ mod 7 ∈ {1,2,4} (n∤7)
  n=5: 和 mod 7 = 4, 不能排除
  n=15,25: 计算复杂
  → 模7对n=5k奇数越来越复杂

模11/模13: 每个新模有新周期结构
→ 卡住: 模分析对n=5k奇数越来越复杂
```

### 6.3 第三步：原语化

把脱水后的操作序列变成原语调用：

```python
# 阶段1：小值测试+偶数排除
test_small_values(n=1) → prime(5)
test_small_values(n=2) → composite(32)
analyze_parity(n_even) → even_greater_than_2
conclude(only_odd_n_ge_3)

# 阶段2：模分析追逐
try_modular_analysis(n, mod=3) → inconclusive
try_modular_analysis(n, mod=5) → partial_exclude(n_not_div_5)
try_modular_analysis(n, mod=7) → complex
try_modular_analysis(n, mod=11) → complex    # AI想到但没完整执行
try_modular_analysis(n, mod=13) → complex    # AI想到但没完整执行

# 阶段3：卡住
stall(mod_analysis_increasingly_complex_for_n=5k)
```

### 6.4 第四步：调用图

原语调用序列构成一个调用图：

```
test_small_values(1) ──→ prime(5)
test_small_values(2) ──→ composite(32)
analyze_parity(even) ──→ even>2
conclude(only_odd≥3)
    │
    ▼
try_modular_analysis(n,3) ──→ inconclusive
    │
    ▼
try_modular_analysis(n,5) ──→ partial_exclude(n∤5)
    │                         但n|5留下
    ▼
try_modular_analysis(n,7) ──→ complex
    │
    ▼
try_modular_analysis(n,11) ──→ complex
    │
    ▼
try_modular_analysis(n,13) ──→ complex
    │
    ▼
stall(increasingly_complex)
```

**这就是思维拓扑。** 点=原语调用，边=调用顺序。不需要辅助AI从自然语言提取——原语调用序列直接给出。

### 6.5 第五步：重构——在不同看法下看这段调用

**最细看法**（展开每个try_modular_analysis的内部）：

```
try_modular_analysis(n,3)
  ├─ compute_mod(n⁴, 3) → 1
  ├─ compute_mod(4^n, 3) → 1
  ├─ add(1, 1) → 2
  └─ evaluate(2 ≠ 0) → inconclusive

try_modular_analysis(n,5)
  ├─ compute_mod(n⁴, 5) → 1
  ├─ compute_mod(4^n, 5) → 4
  ├─ add(1, 4) → 0
  ├─ evaluate(0 = 0) → exclude
  └─ check_residual(n|5) → not_excluded

try_modular_analysis(n,7)
  ├─ compute_mod(n⁴, 7) → {1,2,4}
  ├─ compute_mod(4^n, 7) → period_3
  ├─ combine(...) → multiple_cases
  └─ evaluate(complexity) → complex
...
```

最细看法下，每次`try_modular_analysis`都是几个子操作的组合，看不出"追逐"——只看到一堆计算。

**中间看法**（把连续的try_modular_analysis合并成一个高层函数）：

```
chase_modular_analysis(n, [3, 5, 7, 11, 13])
  ├─ try_modular_analysis(n,3) → inconclusive
  ├─ try_modular_analysis(n,5) → partial_exclude(n∤5)
  ├─ try_modular_analysis(n,7) → complex
  ├─ try_modular_analysis(n,11) → complex
  └─ try_modular_analysis(n,13) → complex
```

中间看法下，"追逐"模式显现了——一个函数接收一个模列表[3,5,7,11,13]，连续尝试，返回值从inconclusive→partial→complex→complex→complex。

**最粗看法**（整个证明是一个函数）：

```
attempt_proof(n⁴+4^n_prime) → stalled
```

最粗看法下，只看到"尝试证明失败了"，看不到怎么失败的。

### 6.6 第六步：非局部tell的识别

**在最细看法下**——看不到"追逐"。每次try_modular_analysis都是独立的计算，返回inconclusive/complex只是单个调用的结果。

**在中间看法下**——"追逐"模式显现。形式化匹配规则：

```
pattern chase:
  consecutive_calls(same_primitive, count≥3)
  AND return_values show(diminishing_returns)
  AND last_call → complex OR stall
```

匹配结果：
- same_primitive = try_modular_analysis ✓
- count = 5 ≥ 3 ✓
- return_values = [inconclusive, partial, complex, complex, complex] → diminishing ✓
- last → stall ✓

**tell识别：模分析无尽追逐**

这个tell是**非局部**的——它不是任何一个单独的try_modular_analysis调用的属性，是5个调用构成的段的结构特征。单看try_modular_analysis(n,7)→complex，看不到"追逐"；看5个连续调用+返回值递减，才看到"追逐"。

**这正是"非局部tell=重构后才显现的模式"**——最细看法下不显现，中间看法（重构为chase_modular_analysis）下显现。

### 6.7 第七步：Pipe 1的形式化过滤

Pipe 1在调用图上做模式匹配。假设概念树中有这些重构模式：

| 重构模式 | 匹配条件 | 对应的tell |
|---|---|---|
| chase_X | 连续调用同一原语≥3次+返回值递减 | 无尽追逐 |
| pipeline_A_B | A的输出是B的输入 | 线性推导 |
| fallback_A_B | A失败后调用B | 回退切换 |
| converge_AB | A和B独立尝试后汇合 | 分治验证 |

Pipe 1对调用图做匹配：
- chase_X模式 → 匹配✓（try_modular_analysis连续5次+递减）
- pipeline_A_B → 不匹配
- fallback_A_B → 不匹配（没有A失败后换B，都是同一个A换参数）
- converge_AB → 不匹配

**Pipe 1过滤结果：候选tell = {chase_X}**

Pipe 1把可能的tell从"所有tell"缩小到"chase_X"——这是形式化过滤，不需要AI理解数学，只需要模式匹配。

### 6.8 第八步：Pipe 2的意图判断

Pipe 1给出了候选tell"chase_X"（模分析无尽追逐），但Pipe 1不知道：
- 这个追逐是"无效追逐"（应该放弃模分析）还是"渐进逼近"（继续试更多模可能成功）？
- hint应该是什么？"转向代数因式分解"还是"试更大的模"还是"用中国剩余定理组合模分析结果"？

**Pipe 2需要AI判断意图**：

Pipe 2看到：
- 调用序列：try_modular_analysis连续5次
- 返回值：inconclusive→partial→complex→complex→complex
- 题目：n⁴+4^n素数性

Pipe 2的判断：
- 模5部分成功（排除了n∤5），但留下了n=5k子情况
- n=5k子情况的模分析越来越复杂（模7已经complex）
- 模分析的本质问题是：每次排除一部分，留下新的子情况，需要新的模——这是递归式的追逐
- **判断：这是无效追逐，不是渐进逼近**——因为每次新模的周期结构和之前的模不共享，不能组合使用

**hint生成**：应转向代数因式分解

Pipe 2为什么给出这个hint？因为Pipe 2有数学知识——它知道n⁴+4^n在n奇数时可以写成x⁴+4y⁴的形式，可以用Sophie Germain恒等式因式分解。这个知识不在调用图里，不在重构模式里，在Pipe 2的数学理解里。

### 6.9 第九步：完整链路

```
原始thinking（含元认知/情绪/犹豫）
    │
    ▼ 脱水
操作序列（只留操作/推导/测试/矛盾）
    │
    ▼ 原语化
原语调用序列（test_small_values/try_modular_analysis/stall...）
    │
    ▼ 调用图自动生成
思维拓扑（点=原语调用，边=调用顺序）← 免费，不需要辅助AI提取
    │
    ▼ 重构（看法切换）
中间看法：chase_modular_analysis(n, [3,5,7,11,13])
    │
    ▼ Pipe 1：形式化模式匹配
匹配chase_X模式 → 候选tell = {模分析无尽追逐}
    │
    ▼ Pipe 2：AI判断意图
判断：无效追逐（非渐进逼近）→ hint = "应转向代数因式分解"
    │
    ▼ 新推理AI收到hint
新AI走代数因式分解路线 → 成功
```

### 6.10 这个案例展示的分工

| 步骤 | 谁做的 | 代码化帮助了吗 |
|---|---|---|
| 脱水 | 辅助AI/规则 | 前提——脱水后才能原语化 |
| 原语化 | 辅助AI/规则 | ✓ 原语集让原语化有规范 |
| 调用图生成 | 自动 | ✓ 免费——推理AI直接给 |
| 重构 | Pipe 1/规则 | ✓ 重构规则形式化 |
| 模式匹配（chase_X） | Pipe 1 | ✓ 形式化过滤 |
| 意图判断（无效追逐vs渐进逼近） | Pipe 2 | ✗ 需要AI理解 |
| hint生成（转向代数因式分解） | Pipe 2 | ✗ 需要数学知识 |

**代码化解决了前5步（脱水到模式匹配），后2步（意图判断和hint生成）仍然需要AI。** 这就是§5说的"代码化只解决它能解决的那部分过滤问题"——它解决了结构过滤，没解决意图判断和方向选择。
