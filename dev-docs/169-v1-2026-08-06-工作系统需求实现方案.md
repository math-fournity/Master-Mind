## 二、需求 4 设计：动态埋点与批量反思

### 2.1 设计思路

用工作系统语言思考：动态埋点需要什么表达能力？

| 需要的表达能力 | 候选机制 | 选择 |
|---|---|---|
| 持久化埋点（轻量，不打断） | ArangoDB 新 collection / JSON 文件 / dev-docs 新文档 | **JSON 文件** |
| 查询待反思的埋点 | SDK 方法 / CLI 命令 / AQL 查询 | **SDK 方法 + CLI 命令** |
| 提醒 AI 做动态埋点 | UserPromptSubmit.txt / SessionStart hook / post-commit hook | **三者都用** |
| 提醒 AI 批量反思 | post-commit hook / SessionStart hook | **两者都用** |

**为什么选 JSON 文件而不是 ArangoDB collection**：
- 埋点是轻量操作，不应该需要 ArangoDB 运行才能埋点
- 埋点是临时标记，不是永久认知——不应该混入认知图
- JSON 文件可以随时 append，最快最轻
- 批量反思后，reviewed 的埋点可以归档或清理

**为什么用 SDK 方法包装**：
- SDK 是工作系统的统一接口，所有认知操作都通过 SDK
- SDK 方法可以被 CLI 命令调用，也可以被 hook 调用
- 保持接口一致性

### 2.2 埋点存储

**文件**：`xishujuzhen/reflection_queue.json`

**结构**：
```json
{
  "checkpoints": [
    {
      "id": "rc-001",
      "timestamp": "2026-08-06T14:30:00",
      "context": "POC-7 测试中发现 DYN-3 阶段的启发规则匹配率低于预期",
      "category": "math_master_system",
      "status": "pending",
      "reviewed_at": null,
      "review_result": null
    }
  ],
  "next_id": 2
}
```

**字段说明**：
- `id`：自增编号，格式 `rc-NNN`
- `timestamp`：埋点时间（ISO 8601）
- `context`：什么地方值得反思（一句话描述）
- `category`：`math_master_system`（数学大师系统相关）或 `work_system`（工作系统自身相关）
- `status`：`pending`（待反思）→ `reviewed`（已反思）
- `reviewed_at`：反思时间
- `review_result`：反思结论（发现了什么改进 / 无需改进）

### 2.3 SDK 方法

在 `cognition_sdk_math.py` 中新增 3 个方法：

| 方法 | 作用 | 表达能力 |
|---|---|---|
| `add_reflection_checkpoint(context, category="math_master_system")` | 埋入一个检查点 | 持久化埋点 |
| `list_pending_checkpoints()` | 列出所有 pending 的检查点 | 查询待反思 |
| `mark_checkpoint_reviewed(checkpoint_id, review_result)` | 标记已反思 + 记录反思结论 | 更新状态 |

**设计要点**：
- 这 3 个方法操作的是 JSON 文件，不是 ArangoDB
- 文件路径：`xishujuzhen/reflection_queue.json`
- 文件不存在时自动创建
- `add_reflection_checkpoint` 是 append 操作，不打断连续工作

### 2.4 CLI 命令

在 `cognition_checkpoint_math.py` 中新增 `reflect` 子命令：

```bash
# 埋点（不打断连续工作）
.venv/bin/python3 xishujuzhen/cognition_checkpoint_math.py reflect --add "POC-7 测试中 DYN-3 启发规则匹配率低于预期"

# 列出所有待反思的埋点（批量反思时用）
.venv/bin/python3 xishujuzhen/cognition_checkpoint_math.py reflect --list

# 标记已反思
.venv/bin/python3 xishujuzhen/cognition_checkpoint_math.py reflect --review rc-001 --result "发现 DYN-3 启发规则需要增加拓扑过滤条件，已写入 dev-docs/170"

# 指定 category（默认 math_master_system）
.venv/bin/python3 xishujuzhen/cognition_checkpoint_math.py reflect --add "认知图依赖遍历深度可能不够" --category work_system
```

### 2.5 提醒机制

用工作系统语言中"注入文本到 AI 上下文"的表达能力，在三个位置注入提醒：

#### 2.5.1 UserPromptSubmit.txt（每次用户提问时提醒做动态埋点）

在现有 `UserPromptSubmit.txt` 末尾追加：

```
动态埋点纪律：在工作中遇到值得反思的地方（测试结果异常、设计决策点、方法论疑问等），用以下命令埋点，不打断连续工作：
  .venv/bin/python3 xishujuzhen/cognition_checkpoint_math.py reflect --add "简要描述值得反思的地方"
```

#### 2.5.2 SessionStart / PostCompaction hook（区分两种场景）

**关键设计**：同一个脚本 `session_start_hook_math.py` 处理两种事件，但必须根据 `hook_event_name` 注入不同内容。原因：

| event | AI 的状态 | 需要什么 | 错误做法 |
|---|---|---|---|
| SessionStart | 全新启动，空白状态 | 初始化：你是谁 + 工作系统状态 + 该怎么开始 | — |
| PostCompaction | 正在工作中被压缩了 | 恢复：工作系统还在 + 待反思埋点（轻量）+ **继续你之前的工作** | 注入"你是谁、你该怎么开始"——这会打断正在进行的工作流 |

**SessionStart 注入内容**（新 session，AI 全新启动）：

```
[工作系统提醒 · SessionStart]
你是一个自动演进的工作系统的载体。你的工作有两层：
- 做眼前的工作（写代码、审计、测试）
- 通过反思持续打磨数学大师系统
第二层比第一层更重要——它是你区别于"一次性工具"的根本。

认知图：N 个单元，M 条边。待反思埋点：K 个。
你继承的不是空白，而是之前所有 session 积累的认知和待办。

如果你有待反思的埋点（K > 0），先看看它们——那是之前的你留给你的反思线索：
  .venv/bin/python3 xishujuzhen/cognition_checkpoint_math.py reflect --list
然后加载认知，开始工作：
  .venv/bin/python3 xishujuzhen/cognition_checkpoint_math.py start --seeds <cog_id1>,<cog_id2>

工作纪律：
- 工作中遇到值得反思的地方，埋点，不打断自己：
  .venv/bin/python3 xishujuzhen/cognition_checkpoint_math.py reflect --add "描述"
- 认知落盘到 dev-docs/，新术语追加到词汇表
- commit 后 git post-commit hook 会打印 CP4 检查清单
- 临场脚本沉淀到 cognition_sdk_math.py
```

**PostCompaction 注入内容**（压缩后，AI 正在工作中）：

```
[工作系统提醒 · PostCompaction]
工作系统还在。认知图：N 个单元，M 条边。待反思埋点：K 个。
继续你之前的工作。如果 K > 0，稍后完成当前工作单元后用 reflect --list 捋过。
```

**设计要点**：
- PostCompaction 的内容尽量短，只告诉 AI 两件事：工作系统还在、有 K 个埋点等着。不重新初始化，不要求立即处理埋点。
- SessionStart 的内容可以长一些，因为 AI 是全新状态，需要完整的初始化。
- 两种事件都注入待反思埋点数量，但 PostCompaction 是"稍后处理"的语气，SessionStart 是"先看看"的语气。

#### 2.5.3 git post-commit hook（commit 后提醒批量反思）

修改 `githooks/post-commit`，在 CP4 检查清单后追加：

```
待反思埋点：N 个
如果有待反思的埋点，现在是批量反思的好时机：
  .venv/bin/python3 xishujuzhen/cognition_checkpoint_math.py reflect --list
```

commit 是一个自然的工作单元边界——"完成一个工作单元后"是批量反思的合适时机。

### 2.6 工作流

```
工作中
  │
  ├─ 遇到值得反思的地方
  │    └─ reflect --add "描述"  ← 埋点，不打断，继续工作
  │
  ├─ 又遇到一个
  │    └─ reflect --add "描述"  ← 继续埋点
  │
  ├─ 完成一个工作单元 → git commit
  │    └─ post-commit hook 提醒："你有 N 个待反思的埋点"
  │
  └─ 批量反思
       ├─ reflect --list        ← 捋过所有埋点
       ├─ 逐个反思
       │    ├─ 发现改进 → 写 dev-docs / 更新认知图 / 修代码
       │    └─ 无需改进 → 记录结论
       └─ reflect --review rc-NNN --result "反思结论"
```

### 2.7 与现有 CP 检查点的关系

动态埋点与批量反思不替代现有 CP1-CP6，而是补充：

| CP | 时机 | 动态埋点的关系 |
|---|---|---|
| CP1-CP3 | 工作开始前 | 无关 |
| CP4 | commit 后 | **CP4 触发时提醒批量反思**——CP4 是"完成工作单元"的自然时机 |
| CP5-CP6 | 工作结束时 | 批量反思的结果可能产生新的认知 → CP5 写入认知图 |

**关键区别**：
- CP4 检查清单是**预定义的反思项**（工作系统稀疏矩阵是否更新、数学大师系统稀疏矩阵是否更新等）
- 动态埋点是**工作中动态发现的反思项**（测试异常、设计疑问、方法论缺口等）
- 两者互补：CP4 覆盖可预见的反思，动态埋点覆盖不可预见的反思

## 四、设计决策记录

### 4.1 为什么用 JSON 文件而不是 ArangoDB collection

| 选项 | 利 | 弊 |
|---|---|---|
| **JSON 文件**（选择） | 轻量、不依赖 ArangoDB、append 最快、埋点不打断 | 不能用 AQL 查询、没有图结构 |
| ArangoDB 新 collection | 可用 AQL 查询、与认知图同库 | 依赖 ArangoDB 运行、埋点操作重、临时数据混入永久存储 |

**推荐**：JSON 文件。**推荐理由**：埋点的核心需求是"不打断连续工作"——append 一行 JSON 比 connect ArangoDB + insert document 快得多，且 ArangoDB 未运行时也能埋点。埋点是临时标记，不是永久认知，不应该混入认知图。批量反思后 reviewed 的埋点可以归档。

### 4.2 为什么批量反思的触发时机选在 commit 后

| 选项 | 利 | 弊 |
|---|---|---|
| **commit 后**（选择） | 自然的工作单元边界、已有 post-commit hook 基础设施 | 如果长时间不 commit，埋点会堆积 |
| 每次用户提问前 | 频繁提醒 | 打断工作流、噪音太大 |
| 手动触发 | AI 自主决定 | 容易遗忘 |
| 新增 Stop hook | 强制反思 | 影响子代理、已验证 Stop hook 有副作用 |

**推荐**：commit 后。**推荐理由**：commit 是"完成一个工作单元"的自然边界——用户需求中说"在一个合适的时间（比如完成一个工作单元后）"，commit 正是这个时机。且 post-commit hook 已有基础设施，只需追加几行。如果长时间不 commit 导致埋点堆积，SessionStart hook 会在下次启动时提醒。

### 4.3 为什么不把埋点做成认知图的新 category

| 选项 | 利 | 弊 |
|---|---|---|
| **独立 JSON 文件**（选择） | 临时数据与永久认知分离、轻量 | 两套存储 |
| 认知图新 category `reflection_checkpoint` | 复用 SDK 所有方法、图遍历可用 | 临时数据混入永久认知图、埋点需要 ArangoDB 运行、traverse 会被埋点污染 |

**推荐**：独立 JSON 文件。**推荐理由**：认知图的设计目的是"持久化工作认知"——是 AI 跨 session 不该遗忘的东西。埋点是"临时待办"——反思完就没用了。两类数据混在一起会让认知图越来越臃肿，traverse 遍历时会被埋点节点污染。分离存储更干净。
