# 76 · xishujuzhen 闭环审计-纠正流程优化方案

## 一、问题发现

### 当前流程的缺陷（开环审计）

POC-7的交叉审计发现了3处瑕疵，但流程到此就结束了——审计报告变成了"事后验尸"而不是"过程纠偏"：

```
JSON → 解读AI → 大师提示词 → 交叉审计 → [发现瑕疵，记录，结束]
                                    ↓
                              B组分析 → 审计 → [发现问题，记录，结束]
                                    ↓
                              评分（带着已知瑕疵评分）
```

**具体问题**：
1. 解读AI不知道自己被发现了瑕疵，无法修正
2. B组分析用的还是有瑕疵的大师提示词——瑕疵向下游传播
3. B组审计发现问题后同样不反馈，B组不知道哪里需要修正
4. 评分时带着已知瑕疵评——忠实度98.8%被记录为"事实"，而不是被纠正为100%

### 用户的洞察

> 审计的目的之一是发现问题，之二是引导纠正问题。发现问题、纠正问题是一个循环，直至完美才能结束。

**核心原则**：审计不是终点，是循环的起点。审计→反馈→修正→再审→...→无瑕疵→结束。

## 二、优化方案：闭环审计-纠正循环

### 优化后流程

```
阶段1：解读+交叉审计闭环
  JSON → 解读AI → 大师提示词v1
                    ↓
              交叉审计v1 → 瑕疵数=0？
                    ↓ 否
              反馈瑕疵清单 → 解读AI修正 → 大师提示词v2
                                              ↓
                                        交叉审计v2 → 瑕疵数=0？
                                                      ↓ 否
                                                    反馈 → 修正 → ... → 瑕疵数=0
                                                                    ↓ 是
                                                              大师提示词（最终版）

阶段2：B组分析+审计闭环
  大师提示词（最终版）+ JSON → B组分析 → 分析结果v1
                                        ↓
                                  执行审计v1 → 问题数=0？
                                        ↓ 否
                                  反馈问题清单 → B组修正 → 分析结果v2
                                                          ↓
                                                    执行审计v2 → 问题数=0？
                                                                  ↓ 否
                                                                反馈 → 修正 → ... → 问题数=0
                                                                                ↓ 是
                                                                          分析结果（最终版）

阶段3：A组分析（并行，无审计闭环——A组无审计要求）

阶段4：评分（用最终版评分，瑕疵已归零）
```

### 关键设计点

#### 1. 循环终止条件

- **硬终止**：瑕疵数=0（或问题数=0）
- **软终止**：达到最大循环次数（防止无限循环）
  - 阶段1（解读闭环）：最大3次
  - 阶段2（B组分析闭环）：最大3次
- **降级终止**：如果3次后仍有瑕疵，记录残余瑕疵数，降级为开环模式继续

#### 2. 反馈格式

每次反馈给AI的瑕疵清单必须结构化：

```markdown
## 审计反馈（第N轮）

### 瑕疵1
- 位置：第六章标题
- 问题：标题写"静态→动态2条"，实际应为"4条"
- 修正建议：将标题改为"静态→动态4条"

### 瑕疵2
- 位置：限0_吉凶判断段落
- 问题：KC嵌入遗漏"童限不主事，仅定根基"
- 修正建议：在限0吉凶判断中补充"但童限不主事，仅定根基"

### 瑕疵3
- 位置：命官关系判断段落
- 问题：称"三条跨宫边"但列举了四条
- 修正建议：将"三条"改为"四条"
```

#### 3. 审计严格程度一致性

每轮审计的标准必须一致——不能因为循环次数多了就放松标准。交叉审计的检查清单固定：
- 节点覆盖率（71/71）
- 边覆盖率（106/106）
- 跨宫边覆盖率（10/10）
- 螺旋环路覆盖率（2/2，圈数正确）
- KC嵌入率（24/24）
- KC完全忠实率（24/24）

#### 4. 循环次数记录

每次循环的审计结果都要记录，形成审计轨迹：

```markdown
## 审计轨迹

| 轮次 | 瑕疵数 | 瑕疵摘要 | 修正后瑕疵数 |
|---|---|---|---|
| 1 | 3 | 标题计数错误+KC遗漏+跨宫边计数错误 | - |
| 2 | 0 | - | 0 |
```

#### 5. 评分调整

闭环流程下，评分维度需要调整：

**维度5（转译忠实性）调整**：
- 旧：记录交叉审计的忠实度（如98.8%）
- 新：记录闭环后的最终忠实度（应为100%或接近100%）+ 闭环效率（几轮达到无瑕疵）

**新增维度7：闭环效率（满分1.0，加入总分变为14分制）**：
- 1轮达到无瑕疵：1.0
- 2轮达到无瑕疵：0.8
- 3轮达到无瑕疵：0.6
- 3轮后仍有瑕疵：0.4

## 三、实施计划

### POC-8中的闭环审计实施

POC-8将首次实施闭环审计-纠正循环。具体执行方式：

#### 阶段1：解读+交叉审计闭环

```python
# 伪代码
prompt_v1 = interpret_ai(json)
audit_v1 = cross_audit_ai(prompt_v1, json)

round = 1
while audit_v1.flaws > 0 and round <= 3:
    feedback = format_feedback(audit_v1.flaws)
    prompt_v2 = interpret_ai_revise(prompt_v1, feedback)
    audit_v2 = cross_audit_ai(prompt_v2, json)
    prompt_v1 = prompt_v2
    audit_v1 = audit_v2
    round += 1

final_prompt = prompt_v1
```

**实施方式**：
1. 第1轮：解读AI生成大师提示词（同POC-7）
2. 第1轮审计：交叉审计AI审计（同POC-7）
3. 如果有瑕疵：将瑕疵清单反馈给解读AI（新subagent调用，输入=原提示词+瑕疵清单）
4. 第2轮审计：交叉审计AI再审修正版
5. 循环直到无瑕疵或达到3次上限

#### 阶段2：B组分析+审计闭环

```python
# 伪代码
analysis_v1 = b_group_ai(final_prompt, json)
audit_v1 = execution_audit_ai(analysis_v1, json)

round = 1
while audit_v1.issues > 0 and round <= 3:
    feedback = format_feedback(audit_v1.issues)
    analysis_v2 = b_group_ai_revise(analysis_v1, feedback)
    audit_v2 = execution_audit_ai(analysis_v2, json)
    analysis_v1 = analysis_v2
    audit_v1 = audit_v2
    round += 1

```

**实施方式**：
1. 第1轮：B组分析AI生成分析结果（同POC-7）
2. 第1轮审计：执行审计AI审计（同POC-7）
3. 如果有问题：将问题清单反馈给B组分析AI（新subagent调用，输入=原分析+问题清单）
4. 第2轮审计：执行审计AI再审修正版
5. 循环直到无问题或达到3次上限

### Subagent调用方式

闭环流程需要多次subagent调用。每次修正调用是一个新的subagent（或resume之前的subagent）：

**方案A：每次修正用新subagent**
- 优点：简单，每次调用独立
- 缺点：新subagent不知道之前的上下文，需要把完整提示词+瑕疵清单都传过去

**方案B：resume之前的subagent**
- 优点：subagent有之前的上下文，只需传瑕疵清单
- 缺点：subagent可能因为之前的上下文而产生路径依赖

**推荐方案A**：每次修正用新subagent，输入=完整原版+瑕疵清单。这样每次修正都是独立的，避免路径依赖。

### 对评分的影响

| 维度 | POC-7（开环） | POC-8（闭环） |
|---|---|---|
| 转译忠实性 | 98.8%（3处瑕疵） | **100%**（瑕疵已纠正） |
| 可审计性 | 1.7/2.0（审计报告截断） | **2.0/2.0**（审计完整+闭环） |
| 闭环效率 | N/A | **新增维度** |

### 对边际增益的影响

闭环流程会增加B组的执行成本（多次subagent调用），但会提高B组的输出质量（瑕疵归零）。预期：
- B组总分会提高（忠实度从98.8%到100%）
- A组总分不变（A组无审计闭环）
- 边际增益会略增

### 对实验验证的影响

闭环流程使得B组的输出质量有**过程保证**——不是"一次性生成然后审计"，而是"生成→审计→修正→再审→直到无瑕疵"。这更接近实际工程中的质量控制流程。

## 五、风险与缓解

### 风险1：无限循环

**风险**：如果审计AI和修正AI陷入"修了又错、错了又修"的循环，可能无法收敛。
**缓解**：最大循环次数3次。3次后仍有瑕疵则降级为开环模式，记录残余瑕疵。

### 风险2：修正引入新瑕疵

**风险**：修正AI在修正旧瑕疵时可能引入新瑕疵（如改了标题但改错了内容）。
**缓解**：每轮审计都是全量审计（不只检查上次瑕疵是否修正，而是重新检查所有维度）。

### 风险3：subagent输出截断

**风险**：POC-7中B组审计报告因子代理输出截断未完整生成。闭环流程中多次subagent调用可能加剧这一问题。
**缓解**：
1. 将B组分析结果和审计报告分两次subagent调用生成
2. 修正调用只输出修正部分（diff格式），不重复输出未修正部分

### 风险4：成本增加

**风险**：闭环流程需要多次subagent调用，成本增加。
**缓解**：
1. 大多数情况下1-2轮就能达到无瑕疵（POC-7只有3处轻微瑕疵，1轮修正应该就能解决）
2. 最大3次上限控制成本
3. 修正调用只传瑕疵清单+原版，不传完整JSON，减少输入成本
