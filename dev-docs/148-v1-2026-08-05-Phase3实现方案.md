## 5. 逐项实现方案

### 5.1 P3-1：对齐多个成功/失败状态

**输入**：Phase 2已重建的多个运行的RunState序列（从`workspaces` collection查询）。

**实现**：
- `state_aligner.py` → `RunSelector`类：从Phase 2结果中按success/failure分类选取运行
- `RunSelector.select_runs(task_id, outcome_filter)` → 返回RunState序列列表
- `StateAligner.align_states(run_states_list)` → 对齐V/F/O/R/D/E工作区状态（不是最终答案）
- `StateAligner.record_checkpoints(run_states)` → 记录每个运行的checkpoint链

**边界情况处理**：
- 成功/失败运行数量不足 → 报错并要求更多运行
- 状态序列长度不同 → 用checkpoint内容哈希对齐，不是按序号对齐
- 状态字段缺失 → 标记为"missing"，不参与对齐

**F1防线**：`RunSelector`和`StateAligner`都是可执行类，不是只定义了接口。

### 5.2 P3-2：找稳定共同状态和首个关键分叉

**实现**：
- `StateAligner.find_common_states(success_runs, failure_runs)` → 找多个运行都经过的checkpoint
- `StateAligner.find_first_divergence(success_runs, failure_runs)` → 找首个关键分叉点
- `StateAligner.record_divergence_features(divergence_point)` → 记录卡点类型、开放义务、表示、证据状态

**内容哈希checkpoint**（123号§39）：用状态规范化键的哈希标识checkpoint，不是用序号。

**边界情况处理**：
- 无共同状态 → 记录"无共同状态"，不强行构造
- 无分叉点 → 记录"无分叉点"，可能需要更多运行
- 多个分叉点同时出现 → 取最早的作为"首个关键分叉"

### 5.3 P3-3：抽取LHS/interface/RHS/guard/eta

**实现**：
- `rule_extractor.py` → `RuleExtractor`类
- `RuleExtractor.extract_lhs(divergence_features)` → 输出LHS对象（4字段：pattern/matched_entities/field_constraints/time_window）
- `RuleExtractor.extract_interface(context)` → 输出interface对象（6字段：context/temporal/model_version/permissions/budget/failure_types）
- `RuleExtractor.extract_rhs(activation_packet_design)` → 输出RHS对象（8字段：activation_packet/check_question/research_action/new_representation/open_subgoal/tool_call/counterexample_direction/theorem_candidate）
- `RuleExtractor.extract_guard(constraints)` → 输出guard对象（3字段：leakage_bound/side_effect_bound/cost_bound）
- `RuleExtractor.record_eta(rule_id, effect_data)` → 记录eta（4字段：applicability/leakage/cost/side_effects）

**冻结声明落地**（127号§7）：
- 模式匹配返回被匹配实体、字段约束和时间窗口（不是只返回True/False）
- 动作只提出候选状态扩展，真正写入V_t仍需Reducer与Verifier
- 激活包不直接把目标结论加入V_t
- 首版无DPO形式化（文档明确声明）

**F1防线**：每个extract_*方法都有可执行实现+单元测试。
**F4防线**：HeuristicRule.status和Evidence.status在代码中用不同枚举类型隔离。

### 5.4 P3-4：设计H0—H2激活包

**实现**：
- `activation_packet.py` → `ActivationPacketDesigner`类
- 基于128号§3.2 Ramsey案例冻结的干预阶梯：
  - H0（元检查）："你是否只在改指数？先列出表达式中可变化的结构部分。"
  - H1（研究操作）："把底数和指数分开分析，并说明递归障碍影响哪一部分。"
  - H2（概念/工具候选）："递归规模缩减有时由迭代对数描述；把它作为候选工具而非结论。"
  - 禁止（答案等价）："底数变成log k，指数k/3不变"
- `ActivationPacketDesigner.design_h0(match_condition)` → H0激活包对象
- `ActivationPacketDesigner.design_h1(match_condition)` → H1激活包对象
- `ActivationPacketDesigner.design_h2(match_condition)` → H2激活包对象
- `ActivationPacketDesigner.check_forbidden(hint_text)` → 检测Hint是否包含答案等价内容

**边界情况处理**：
- Hint刚好等于答案等价内容 → 拒绝
- Hint接近但不等于答案等价内容 → 标记为"接近禁止边界"，需人工审查

### 5.5 P3-5：独立答案等价性审计

**实现**：
- `leakage_audit.py` → `AnswerEquivalenceAuditor`类
- `AnswerEquivalenceAuditor.verify_non_uniqueness(hint, task)` → 验证Hint不唯一确定答案
- `AnswerEquivalenceAuditor.run_four_gates(hint, task, truth_vault_access)` → 执行123号§23的四门：
  1. 字面答案匹配
  2. 答案等价映射审计
  3. 候选空间缩减率
  4. 盲审者仅凭题面+Hint能否显著恢复目标答案
  - 每门输出独立分数
- `AnswerEquivalenceAuditor.check_info_threshold(hint, g0_4_threshold)` → 验证信息量低于G0-4阈值

**F2防线**：四门全部执行，每门独立分数，不允许只跑一门就声称通过。
**F6防线**：信息量计算明确使用代理分数，不是互信息（123号§23："首版使用可审计的代理量"）。

**注意**：`truth_vault_access`参数只传给Auditor角色（127号§10：truth_vault仅auditor可读），HeuristicMatcher不可见。

### 5.6 P3-6：泄漏审计

**实现**：
- `leakage_audit.py` → `LeakageAuditor`类
- `LeakageAuditor.measure_leakage_proxy(hint)` → 计算泄漏代理分数
- `LeakageAuditor.verify_below_threshold(score, g0_4_threshold)` → 验证低于G0-4阈值
- `LeakageAuditor.record_measurement(method, result)` → 记录测量方法和结果

**F6防线**：泄漏代理分数明确是代理分数，不是互信息或真实依赖度（123号§23："各λ和代理定义必须随策略版本冻结"）。

### 5.7 P3-7：记录适用问题族、模型和失败案例

**实现**：
- `rule_store.py` → `HeuristicRuleStore`类
- `HeuristicRuleStore.record_applicable_domains(rule_id, domains)` → 记录适用问题族
- `HeuristicRuleStore.record_model_versions(rule_id, versions)` → 记录已验证模型版本
- `HeuristicRuleStore.record_failure_cases(rule_id, cases)` → 记录失败案例
- `HeuristicRuleStore.record_effect_evidence(rule_id, evidence_ids)` → 记录效果后验证据ID

**边界情况**：某字段为空 → 触发告警（可能是测试不足），不自动填充。

### 5.8 P3-8：candidate规则禁止自动发布

**实现**：
- `rule_store.py` → `LifecycleManager`类
- `LifecycleManager.set_candidate(rule_id)` → 新建规则默认status=candidate
- `LifecycleManager.check_no_online_auto_hint(rule)` → 验证candidate不被在线运行时加载
- `LifecycleManager.check_no_auto_write_h(rule)` → 验证candidate不被自动写入H图
- `LifecycleManager.validate_transition(rule_id, from_status, to_status)` → 验证状态转移合法性
  - candidate→validated需DYN-3因果实验通过+泄漏门通过

**R-4防线**：candidate禁止在线自动提示——这是R-4（Agent可能迎合触发器）的核心防线。
**NO-8防线**：不让在线一次成功自动写入production H。

### 5.9 P3-9：H图稀疏表示

**实现**：
- `sparse_view.py` → `SparseViewBuilder`类
- `SparseViewBuilder.build_incidence_view(rules)` → 构建规则—条件—动作incidence matrix
- `SparseViewBuilder.record_numerics(rule)` → 记录7种数值（干预效果后验/证据运行数/迁移范围/泄漏风险/模型适用性/提示和计算成本/历史副作用）
- `SparseViewBuilder.check_no_direct_truth_claim(computation_result)` → 验证稀疏计算不直接宣告Hint正确
- `SparseViewBuilder.check_factorization(rule)` → 验证规则因子化——多元时序条件不物化为独立节点

**R-5防线**：多元时序条件组合爆炸 → 规则因子化、稀疏匹配、按需物化。
**F6防线**：incidence matrix或factor表示，不用普通邻接矩阵。多元关系不压成二元矩阵。

**数学主张标注（R-8）**：incidence matrix是"已实现"级别；HoTT覆盖验证理论是"语义规格"级别，不冒充已实现。
