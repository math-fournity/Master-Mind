## 一、用户需求（逐字记录）

> 其实，我们的数学大师系统，需要我可以全程监控，而且它自己可以全程记录，也就是说，我们运行起来一个测试之后，最后可以审计整个测试的结果，包括tmux中的devin的某个实例的运行全程的所有操作，或许这个可以通过tmux的自动log来实现或者devin cli自己就提供这种全程的trajectory的审计。另外就是整个系统的工作过程的细节，代码运行的细节，都应该可以翻查、审计，这样我们才可以分析，数学大师在工作的时候，它的思路到底是怎么走的，我们的系统到底是一步步如何引导它的，最终如果没有达到预期，我们的系统应该如何优化？是吸收更多的数据到稀疏矩阵中？还是说我们的系统的工作机制存在应该被优化的点？

### 需求拆解

| # | 需求 | 说明 |
|---|---|---|
| R1 | 全程监控 | 用户可以实时观察数学大师系统的运行过程 |
| R2 | 全程记录 | 系统自己记录整个运行过程，不需要用户一直盯着 |
| R3 | 事后审计 | 测试结束后可以回溯审计整个运行过程 |
| R4 | devin实例操作记录 | tmux中devin实例的运行全程所有操作都要可翻查 |
| R5 | 系统工作过程细节 | 系统每一步做了什么、为什么这么做，都要可翻查 |
| R6 | 代码运行细节 | 代码执行的具体细节（输入、输出、中间状态）可翻查 |
| R7 | 思路分析 | 分析数学大师工作时的思路走向 |
| R8 | 引导分析 | 分析系统是如何一步步引导数学大师的 |
| R9 | 优化决策 | 未达预期时，判断是"吸收更多数据到稀疏矩阵"还是"优化工作机制" |

## 二、AI理解

### 2.1 核心问题

当前数学大师系统有一个**可观测性缺口**：

- **系统内部有事件记录**（RawEvent/SemanticEvent存储在ArangoDB），但这是系统自己记录自己的内部状态变化，不是从外部审计整个运行过程。
- **devin cli实例的运行过程没有完整记录**——tmux session中的操作只存在于终端scrollback buffer里，session结束后就消失了。
- **代码执行细节没有结构化记录**——Python代码的输入、输出、异常、中间变量状态都只在stdout/stderr中，没有结构化存储。
- **系统引导数学大师的过程没有可回放的轨迹**——系统每一步给了什么提示、数学大师怎么回应、系统下一步又给了什么，这个交互轨迹没有完整记录。

这个缺口的后果是：**我们无法回答"数学大师是怎么工作的"这个核心问题**。如果一次测试没有达到预期，我们无法回溯分析是数学大师的能力问题、还是系统的引导问题、还是数据不足的问题。

### 2.2 三个层次的全程记录

我认为全程记录需要覆盖三个层次：

#### 层次1：devin cli实例的运行轨迹（外部层）

这是用户最关心的——tmux中devin实例从启动到结束的所有操作。

**记录内容**：
- devin cli的每一次工具调用（exec/edit/read/write等）
- devin cli的每一条输出（思考过程、回复、错误）
- devin cli与用户的每一次交互
- 时间戳——每个操作的精确时间

**实现方式**（两种，不互斥）：
1. **tmux自动log**：tmux的`pipe-pane`命令可以把pane的所有输出实时写入文件。这是最简单的方式，不需要devin cli自己支持。
2. **devin cli的trajectory导出**：如果devin cli自己支持导出session trajectory（类似Codex的rollout JSONL），这是更结构化的方式。

**我的判断**：两种方式应该同时使用——tmux pipe-pane作为兜底（保证不丢任何输出），devin cli trajectory导出作为结构化分析入口（如果devin cli支持的话）。

#### 层次2：系统代码执行的结构化记录（中间层）

这是系统内部代码运行的可观测性。

**记录内容**：
- 每个Phase的12步运行时每一步的输入和输出
- StateReducer的状态重建结果（从什么状态到什么状态）
- HeuristicMatcher的匹配结果（匹配了哪些规则、生成了什么候选激活包）
- Retriever的检索结果（检索了什么、返回了什么、过滤了什么）
- ContextCompiler的编译结果（编译了什么上下文、5项记录是什么）
- Controller的决策结果（选择了什么动作、为什么）
- Verifier的验证结果（验证了什么、结果是什么）
- Budget的消耗情况（每一步消耗了多少token/计算/工具调用）

**实现方式**：
- 系统已有的事件记录（RawEvent/SemanticEvent）是基础，但需要补充结构化的执行日志
- 可以用Python的logging模块+结构化JSON输出，每一步的关键操作都记录到ArangoDB或文件
- 关键是：日志要结构化，不能只是文本，要能被程序查询和分析

#### 层次3：数学大师的思路轨迹（内部层）

这是最深层也是最有价值的——数学大师在系统引导下的思路走向。

**记录内容**：
- 数学大师每一步的思考内容（从devin cli的输出中提取）
- 数学大师每一步选择了什么方向、为什么
- 数学大师遇到卡点时的反应（是停下来思考、还是换方向、还是请求帮助）
- 系统给了什么提示、数学大师如何回应提示
- 数学大师的"顿悟时刻"（如果有的话）——什么时候从不知道怎么做变成了知道怎么做

**实现方式**：
- 这一层不能完全自动化——需要从devin cli的输出中提取和标注
- 可以用事件捕获器（EventCapture）的语义抽取功能，从devin cli输出中抽取语义事件
- 但语义抽取只是第一步——真正的思路分析需要人工或AI辅助标注

### 2.3 审计维度

事后审计时，需要能回答以下问题：

| 审计维度 | 问题 | 数据来源 |
|---|---|---|
| 时间线 | 系统从启动到结束经历了哪些步骤？每步多长时间？ | 层次1+2 |
| 决策链 | 系统每一步为什么做这个决策？有没有更好的选择？ | 层次2 |
| 引导链 | 系统给了数学大师哪些提示？每个提示的效果是什么？ | 层次2+3 |
| 思路链 | 数学大师的思路是怎么演化的？有没有走弯路？ | 层次3 |
| 卡点分析 | 数学大师在哪些地方卡住了？卡了多久？系统怎么帮助的？ | 层次2+3 |
| 预算消耗 | 预算是怎么消耗的？哪一步消耗最多？是否值得？ | 层次2 |
| 效果归因 | 最终结果好或不好，归因于什么？ | 层次1+2+3 |
| 优化方向 | 下次应该改进什么？数据？机制？提示策略？ | 综合分析 |

### 2.4 优化决策框架

用户提出的核心问题："最终如果没有达到预期，我们的系统应该如何优化？是吸收更多的数据到稀疏矩阵中？还是说我们的系统的工作机制存在应该被优化的点？"

我认为这需要一个**优化决策框架**，根据审计结果判断优化方向：

| 审计发现 | 优化方向 | 具体行动 |
|---|---|---|
| 数学大师不知道某个数学工具/定理 | **数据问题**——稀疏矩阵缺数据 | 吸收更多数学知识到K投影 |
| 数学大师知道工具但没想到用 | **机制问题**——HeuristicMatcher没匹配到规则 | 优化规则LHS条件或新增规则 |
| 系统给了提示但数学大师没理解 | **提示问题**——提示内容或形式不对 | 优化Hint级别或提示内容 |
| 系统给了提示但提示方向错误 | **机制问题**——StateReducer状态估计错误 | 优化状态重建逻辑或卡点检测 |
| 数学大师思路正确但执行出错 | **能力问题**——数学大师自身能力不足 | 换更强的模型或提供更多工具支持 |
| 预算耗尽但任务未完成 | **预算问题**——预算分配不合理 | 优化预算分配策略 |
| 系统循环但无进展 | **停止条件问题**——没及时停止 | 优化停止条件检测 |

这个框架不是穷尽的，但给出了从审计发现到优化行动的映射逻辑。

### 2.5 与现有系统的关系

当前系统已有的可观测性组件：

| 组件 | 位置 | 记录什么 | 缺什么 |
|---|---|---|---|
| RawEvent | events/store.py | 原始事件（工具调用、文本输出等） | 只有系统内部事件，没有devin cli实例操作 |
| SemanticEvent | events/store.py | 语义事件（从原始事件抽取） | 语义抽取覆盖度52%（176号审计） |
| manifest | manifest.py | 运行元数据（Q_0哈希、模型版本、预算） | 只有静态元数据，没有动态执行轨迹 |
| checkpoint | events/store.py | 状态快照（内容寻址） | 有checkpoint但无continuation轨迹分析 |
| leakage_audit | heuristics/leakage_audit.py | 泄漏审计 | 只审计泄漏，不审计引导效果 |

**缺口**：现有组件记录的是"系统内部发生了什么"，不记录"devin cli实例做了什么"和"数学大师怎么思考的"。

### 2.6 我的建议

这个方案的核心是**三层全程记录 + 事后审计分析**：

1. **层次1（devin cli实例轨迹）**：用tmux pipe-pane自动log + devin cli trajectory导出（如果支持）
2. **层次2（系统代码执行）**：在12步运行时的每一步添加结构化执行日志
3. **层次3（数学大师思路）**：从devin cli输出中抽取语义事件 + 人工/AI辅助标注
4. **审计工具**：一个可以回放整个运行过程的审计dashboard（可以是CLI工具或Web界面）
5. **优化决策框架**：从审计发现到优化行动的映射表

**优先级建议**：
- 先做层次1（tmux pipe-pane）——最简单、最基础、立刻可用
- 再做层次2（结构化执行日志）——需要改代码但价值高
- 最后做层次3（思路轨迹分析）——需要AI辅助标注，最复杂

## 五、调查结果（2026-08-06）

### 5.1 devin cli的session记录机制——远超预期

调查发现devin cli有**完整的session记录系统**，远超178号v0中的预期。三个数据源：

#### 数据源1：`sessions.db`（SQLite，9GB）

位置：`~/.local/share/devin/cli/sessions.db`

表结构：
| 表名 | 记录数 | 内容 |
|---|---|---|
| `sessions` | — | 每个session的元数据（id、工作目录、模型、创建时间、标题） |
| `message_nodes` | **807,294** | 完整对话消息树（system/user/assistant消息，含parent_node_id构成消息森林） |
| `tool_call_state` | **22,658** | 每次工具调用的完整JSON（工具名、参数、输出结果） |
| `prompt_history` | — | 用户输入历史 |
| `rendered_commits` | — | 渲染的提交记录 |

**关键发现**：`message_nodes`表的`chat_message`字段是完整JSON，包含：
- `role`：system/user/assistant
- `content`：消息文本内容
- `tool_calls`：assistant的工具调用数组（工具名、参数、ID）
- `thinking`：**AI的思考过程**（thinking字段包含AI的内部推理文本！）
- `metadata`：token数、请求ID、性能指标（ttft_ms、total_time_ms、input/output_tokens）

**这意味着**：devin cli已经记录了AI的完整思考过程（thinking）、工具调用（tool_calls）和性能指标（metadata）。这是层次1和层次3的核心数据源——**不需要额外开发，只需要查询接口**。

#### 数据源2：`transcripts/`目录（JSON，100个文件）

位置：`~/.local/share/devin/cli/transcripts/`

格式：ATIF-v1.7 schema的JSON文件，每个session一个文件。

结构：
```json
{
  "schema_version": "ATIF-v1.7",
  "session_id": "pastoral-patch",
  "agent": {"name": "devin", "version": "3000.3.27", "model_name": "Claude Sonnet 5"},
  "steps": [
    {"step_id": 1, "timestamp": "...", "source": "system", "message": "..."},
    {"step_id": 9, "source": "user", "message": "..."},
    {"step_id": 11, "source": "agent", "message": "...", "extra": {"generation_model": "glm-5-2", "telemetry": {...}}
  ],
  "final_metrics": {"total_prompt_tokens": 38477, "total_completion_tokens": 177, "total_steps": 11}
}
```

**用途**：transcript是session的精简版导出——只有消息文本，没有tool_calls和thinking的详细结构。适合快速浏览session内容。

#### 数据源3：`--export`选项

devin cli启动时可以加`--export <PATH>`选项，每turn自动导出conversation到文件。这是实时导出，不需要事后查询sessions.db。

#### 数据源4：`logs/`目录（10,949个.gz文件）

位置：`~/.local/share/devin/cli/logs/`

每个devin cli进程一个log文件，包含启动、认证、工具调用等日志。这是调试级别的日志，不适合审计但可以补充。

### 5.2 tmux pipe-pane——简单可靠的兜底

`tmux pipe-pane`命令可以把pane的所有输出实时管道到一个shell命令：

```bash
# 开始记录pane输出到文件
tmux pipe-pane -o -t <session:window.pane> 'cat >> ~/logs/tmux_<session>_<pane>.log'

# 停止记录
tmux pipe-pane -t <session:window.pane>
```

- `-O`：pane输出管道到命令（默认）
- `-I`：命令输出写入pane
- `-o`：只在没有现有pipe时才开启（可toggle）

**特点**：
- 记录的是纯文本（含ANSI转义序列），需要清洗才能结构化分析
- 不区分用户输入和AI输出——所有终端输出混在一起
- 但作为兜底非常可靠——即使devin cli的session记录出问题，tmux log也在

**我的判断**：tmux pipe-pane作为兜底使用，主分析入口用sessions.db。

### 5.3 现有系统的事件记录能力gap分析

| 审计需求 | devin cli sessions.db | 系统RawEvent/SemanticEvent | gap |
|---|---|---|---|
| AI的思考过程 | ✅ `thinking`字段 | ❌ | 需要从sessions.db提取 |
| AI的工具调用 | ✅ `tool_calls`字段 | ❌ | 需要从sessions.db提取 |
| 工具调用结果 | ✅ `tool_call_state`表 | ❌ | 需要从sessions.db提取 |
| 系统内部状态变化 | ❌ | ✅ RawEvent | 需要从ArangoDB查询 |
| 语义事件（卡点/分支/回溯） | ❌ | ✅ SemanticEvent | 需要从ArangoDB查询 |
| 系统给AI的提示 | ❌（只在user消息中） | ✅ HINT_INJECTION事件 | 需要交叉关联 |
| AI对提示的回应 | ✅ assistant消息 | ✅ SemanticEvent | 需要交叉关联 |
| 预算消耗 | ❌ | ✅ Budget字段 | 需要从ArangoDB查询 |
| 性能指标 | ✅ `metadata`字段 | ❌ | 需要从sessions.db提取 |

**核心gap**：devin cli的session记录和系统的ArangoDB事件记录是**两个独立的数据源，没有关联键**。要实现完整审计，需要：
1. 在system prompt中注入`run_id`，使devin cli的session与系统的run关联
2. 在EventCapture中记录devin cli的`session_id`，使系统事件与devin cli session关联
3. 建立一个审计查询工具，能同时从sessions.db和ArangoDB查询并关联

### 5.4 调查结论

| 178号v0的问题 | 调查答案 |
|---|---|
| devin cli是否支持trajectory导出？ | **是**——sessions.db有完整的trajectory（thinking+tool_calls+结果），transcripts/有精简版，--export有实时导出 |
| tmux pipe-pane的输出格式？ | 纯文本含ANSI转义序列，需清洗，作为兜底 |
| 结构化执行日志存哪里？ | **不需要新建**——sessions.db已有完整记录，只需查询接口 |
| 审计dashboard是CLI还是Web？ | 先做CLI（查询sessions.db+ArangoDB），后续可加Web |
| 思路轨迹标注是人工还是AI辅助？ | sessions.db的`thinking`字段已自动记录AI思考过程，不需要额外标注 |
| 与现有事件系统的集成？ | 需要建立run_id↔session_id关联键 |
| 审计分析的自动化程度？ | 时间线/决策链/预算消耗可自动化；思路链/效果归因需AI辅助 |
| 优化决策框架的验证？ | 可以用sessions.db中的历史session回测 |

**最大的发现**：**devin cli已经记录了我们需要的几乎所有数据**——AI的思考过程（thinking）、工具调用（tool_calls）、工具结果（tool_call_state）、性能指标（metadata）。我们不需要从零建设全程记录系统，只需要：
1. 建立sessions.db和ArangoDB之间的关联键
2. 建一个审计查询工具
3. 建一个审计分析框架

这把方案复杂度从"建设三层全程记录系统"降低到"建设一个查询关联工具"。

## 六、修订后的方案架构（v0.5）

### 6.1 数据流

```
devin cli实例运行
    ├─ sessions.db自动记录（thinking + tool_calls + 结果 + metadata）
    ├─ transcripts/自动导出（精简版）
    └─ --export实时导出（可选）

系统12步运行时
    └─ ArangoDB自动记录（RawEvent + SemanticEvent + Budget + Checkpoint）

关联键
    ├─ system prompt注入run_id → devin cli session与系统run关联
```
