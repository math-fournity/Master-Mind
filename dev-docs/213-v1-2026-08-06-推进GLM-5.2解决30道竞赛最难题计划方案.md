## 1. 问题陈述

### 1.1 目标

推进GLM-5.2解决30道2024-2026年世界级竞赛最难题（IMO/USAMO/Putnam/AIME/HMMT等各竞赛最后2-3道大题），这些题在两轮裸跑测试中正确率0%。

### 1.2 当前状态

- **第一轮测试**（43题，含7道做出来）：正确率18.9%
- **第二轮重测**（30道做不出来的题，全新session隔离）：0/30做出来
- **25/30有解答**（23道有数值答案，2道有sample_solution），5道无解答

### 1.3 失败模式分析（关键发现）

| 失败模式 | 数量 | 根因 |
|---|---|---|
| **题目文本被截断** | **~15题** | **devin -p的prompt过长，题目在中间被截断，AI说"题目被截断了"** |
| **输出token超限** | 4题 | "model hit max output token limit"，AI在写证明时被截断 |

**核心发现：最大的失败原因不是AI数学能力不足，而是测试基础设施bug——题目文本通过devin -p传递时被截断。**

### 1.3b Phase 1b验证结果（2026-08-06）

修复截断问题后（题目从parquet重新提取完整文本+通过文件传递），重测30道题：

| 状态 | 数量 | 说明 |
|---|---|---|
| stuck | 21 | AI看到完整题目但仍做不出来 |
| error | 5 | API连接问题/token超限 |
| no_answer_format | 3 | 有思路但没给出boxed答案 |
| wrong_answer | 1 | 答案错误 |
| **correct/solved** | **0** | **0/25（排除error后）** |

**结论：修复截断后，30道题仍然0道做出来。这确认了这些题是GLM-5.2的真实能力边界，不是基础设施问题。需要进入Phase 3的提示干预。**

## 2. 根因分析

### 2.1 题目截断问题

`devin -p`命令行参数有长度限制。当prompt包含完整LaTeX题目（有些题目500-900字符）加上指令模板时，总prompt可能超过命令行参数长度限制，导致题目在中间被截断。

**证据**：
- BRUMO 2025 #29回复："题目文本被截断了"
- IMO 2025 #4回复："题目文本被截断了——你的消息在On the nth turn之后就中断了"
- HMMT Nov 2025 #29回复："题目在第二个条件处被截断了"
- USAMO 2026 #4回复："题目被截断了"
- 10道"stuck_short"题中至少8道是截断问题

### 2.2 输出token超限问题

4道题的error是"model hit max output token limit"——AI在写长证明时输出被截断。这不是能力问题，是输出长度限制问题。

### 2.3 真正的数学能力不足

排除截断和token超限后，真正因为数学能力不足而失败的约8题。这些题AI看到了完整题面，尝试了但做不出来。

## 3. 解决方案

### Phase 1：修复测试基础设施（预计立即完成）

#### 3.1 修复题目截断

**方案**：把题目写入文件，让devin cli读文件而不是通过命令行参数传题。

```python
# 把题目写入work_dir下的problem.txt
problem_file = os.path.join(work_dir, "problem.txt")
with open(problem_file, "w") as f:
    f.write(prompt)

# devin cli的prompt改为"请读取problem.txt中的题目并解答"
cmd = ["devin", "-p", f"请读取当前目录下的problem.txt文件，解答其中的数学题。禁止搜索网络。", ...]
```

**注意**：每道题运行前清理problem.txt，运行后清理，确保不泄漏到下一题。

#### 3.2 修复输出token超限

**方案**：增加`--max-tokens`参数或分段输出。查devin cli是否支持设置max output tokens。

#### 3.3 重新测试30道题

用修复后的基础设施重新测试30道题，获得真实的失败模式。

### Phase 2：分析真实失败（预计Phase 1完成后立即进行）

#### 3.4 分类真实失败

排除截断和token超限后，对真正做不出来的题按失败类型分类：

- **Type A：不知道切入点** — AI说"我不知道"或给出极短回复
- **Type B：切入点错误** — AI尝试了某个方向但方向不对
- **Type C：切入正确但中途卡住** — AI知道该用什么方法但执行不下去
- **Type C：计算错误** — 方法对但计算出错

#### 3.5 建立题目-知识映射

对每道真实失败的题，分析：
1. 这道题需要什么数学知识（定理/技巧/公式）
2. 这些知识在依赖图K中是否存在
3. AI缺的是知识还是策略

### Phase 3：设计干预策略

#### 3.6 三级提示策略

基于项目已有的HINT_REGISTRY和203-A.0提示分级：

| 级别 | 类型 | 内容 | 示例 |
|---|---|---|---|
| L1 | knowledge | 给具体数学事实/定理 | "考虑用Vieta跳跃" |
| L2 | strategy | 给解题方向/方法选择 | "从小情形开始验证" |
| L3 | meta | 给元提示 | "请给出更详细的分析" |

#### 3.7 干预实验设计

对每道真实失败的题：
1. **Turn 1（solo）**：裸跑，不给提示
2. **Turn 2（L3 meta）**：如果Turn 1卡住，给meta提示"请继续深入分析"
3. **Turn 3（L2 strategy）**：如果Turn 2仍卡住，给策略提示
4. **Turn 4（L1 knowledge）**：如果Turn 3仍卡住，给具体知识提示

记录每道题在第几个turn被突破，以及什么级别的提示最有效。

### Phase 4：执行干预实验

#### 3.8 批量干预测试

用修复后的测试脚本+提示注入，对真实失败的题执行多turn干预实验。

**技术方案**：
- 修改`matharena_batch_test.py`支持多turn模式
- Turn 1：写problem.txt → devin -p "读problem.txt解题"
- Turn 2-N：写hint.txt → devin -p "读hint.txt，这是对你上一轮解答的提示，请继续"
- 每个turn都是全新session（遵守session隔离铁律），但把上一轮的解答摘要写入hint.txt

#### 3.9 对照实验

- **对照组**：裸跑（无提示）
- **实验组A**：只给L3 meta提示
- **实验组B**：给L2 strategy提示
- **实验组C**：给L1 knowledge提示
- **实验组D**：给完整解答的关键步骤提示

### Phase 5：分析与归因

#### 3.10 统计干预效果

| 指标 | 说明 |
|---|---|
| 裸跑正确率 | Phase 1修复后的真实裸跑正确率 |
| L3提示后正确率 | 只给meta提示的正确率 |
| L2提示后正确率 | 给策略提示的正确率 |
| L1提示后正确率 | 给知识提示的正确率 |
| 完全引导正确率 | 给关键步骤提示的正确率 |

#### 3.11 归因分析

对每道题：
- 如果L1 knowledge提示能突破 → AI缺的是知识，依赖图K需要补充
- 如果L2 strategy提示能突破但L1不能 → AI缺的是策略，启发规则H需要补充
- 如果L3 meta提示就能突破 → AI缺的是坚持，不是知识或策略
- 如果所有提示都不能突破 → 题目本身超出GLM-5.2能力边界

## 6. 风险与应对

| 风险 | 应对 |
|---|---|
| 修复截断后发现AI仍然做不出来 | 说明确实是能力问题，Phase 3的提示干预是必要的 |
| 提示干预效果不明显 | 说明GLM-5.2在这些题上可能需要更强的模型或更多turn的引导 |

| 题目-知识映射工作量太大 | 优先处理8道真实失败的题，不处理截断和token超限的题 |
