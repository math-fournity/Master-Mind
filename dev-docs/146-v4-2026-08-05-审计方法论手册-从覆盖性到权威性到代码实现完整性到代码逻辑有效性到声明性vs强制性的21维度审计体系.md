## 0. 本手册是什么、给谁读、怎么用

### 0.1 是什么

本手册是数学大师项目建设过程中，从 Phase 0 到 Phase 4 的多轮审计里沉淀出来的**审计方法论**。它不是某一次审计的报告，而是从多次审计中提炼出的**可复用的"把事做好、做对"的元经验**：

- 断层有哪些类型（F1—F15）
- 实现到什么程度才算"实现了"（D1—D4）
- 审计要查哪些维度（21个维度）
- 审计按什么流程做（三文件交叉审计 + 代码实现审计 + 声明性vs强制性审计）
- 权威以谁为准（127号Schema冻结文档是法律）
- 本项目踩过哪些具体的坑（领域教训清单）

**v2核心突破**：v1的14维度全部是"文档vs文档"审计——查Check List是否覆盖来源文档、Check List措辞是否精确、Check List是否与127号一致、Check List是否回溯了跨章节定义和母本细节。但这条链有一个结构性缺口：**它假设了"Check List正确→代码实现正确"**。153号Phase 4审计证明这个假设不成立——Check List可以完全正确（通过维度1-14所有审计），但代码实现仍然可以没有实现Check List要求的方法、丢失了母本中被两次概括的细节、有参数传递bug。v2新增3个"文档vs代码"审计维度（维度15/16/17），补全了这个结构性缺口。

**v3核心突破**：v2的维度15有一个结构性盲区——**它只查"方法是否存在"，不查"方法逻辑是否真正有效"和"方法是否完整实现了来源要求的所有来源"**。158号Phase 5审计证明这个盲区导致第一轮审计过于乐观（找到6项F9+1项F10后评估"优秀"），第二轮深入审视代码逻辑后又发现7项深层次遗漏（含1个高危空检查bug——`token_cost>0 or token_cost==0`永远为True，和1个高危K投影来源缺失——123号§24要求3个来源但代码只从1个获取）。v3新增3个审计维度（维度18/19/20），从"方法存在性检查"升级为"方法逻辑有效性+方法完整性+来源逐字要求检查"。同时新增"审计者乐观偏差"教训——审计者倾向于"找到第一批问题就停止"，需要"强制深入"机制。

**v4核心突破**：v3的维度18检查恒真/恒假（如`x>0 or x==0`），但161号Phase 6审计发现一种v3完全无法覆盖的新型断层——**声明性实现而非强制性实现**。声明性实现的返回值不是恒真的（确实返回了True），方法逻辑也不是空操作（确实执行了检查），但**True背后没有实际强制机制**。典型实例：`lambdas_frozen: True`声明已冻结，但没有`freeze()`方法、没有`bump_version()`机制、修改λ时不抛异常；`capability_token_verified: True`声明已验证，但没有`CapabilityToken`类、没有`PermissionError`运行时强制。这种断层比F12（恒真/恒假）更危险——F12的恒真/恒假容易被发现（条件永远为True/False很可疑），但声明性实现的返回值是"正确的"（确实返回了True），审计者看到`frozen=True`会认为"已冻结"，但实际上只是声明。161号Phase 6审计发现10项问题中6项是声明性实现或条件限定词丢失（如G0-5检查"≥3"但漏了"未参与设计"限定词，R-14检查"数量>1"而非"不同模型版本>1"）。v4新增F15断层类型（声明性实现）、维度21（声明性vs强制性审计）、教训15，扩展F12定义（新增"检查了错误的条件"和"只检查了条件的一部分"两种变体）和维度19定义（新增"一个条件的多个限定词"检查），强化维度20预检精度（不只检查"是否覆盖"，还检查"限定词是否完整"）。同时发现147号SOP缺少"实现后审计触发"阶段——Phase 6实现后只运行了集成测试，没有执行维度15-20的实现后审计。

### 0.2 给谁读

- **每个 Phase 实现前的 AI**：读第 8 章"实现前自检协议"，知道动手前要做什么
- **每个 Phase 实现后的审计者**：读第 9 章"实现后审计协议"，按 21 维度逐项审计
- **新 session / 压缩后的 AI**：读第 1 章演进史，理解这套方法为什么是今天这个样子，不要重新踩 F1—F15
- **Check List 编写者**：读第 3 章 D1—D4 和第 4 章 21 维度，按规范编写

### 0.3 怎么用

1. **实现前**：打开本手册第 8 章 + 对应 Phase 的 Check List + 127号Schema冻结文档，三者并读
2. **实现中**：每完成一个"实现X"类项，按 D1—D4 自评深度，用四元勾选 `[D1]/[D2]/[D3]/[D4]/[ ]`
3. **实现后**：按第 9 章 21 维度逐项审计，重点跑维度 11（可实现性）、维度 12（权威性逐字核对）、维度 15（Check List→代码实现完整性）、维度 16（代码层面母本回溯）、维度 17（代码参数正确性）、维度 18（方法逻辑有效性）、维度 19（方法完整性）、维度 20（来源逐字要求检查）、维度 21（声明性vs强制性）
4. **发现新断层**：追加到第 2 章，分配 F7、F8……编号，记录发现于/修正于

**v2新增的关键步骤**：实现后审计必须包含维度15/16/17——这是"文档vs代码"审计，不是"文档vs文档"审计。v1的14维度全部通过不等于代码实现正确。

**v3新增的关键步骤**：实现后审计必须包含维度18/19/20——这是"代码逻辑深度"审计。v2的维度15/16/17只查"方法是否存在"，不查"方法逻辑是否有效"和"方法是否完整"。维度15/16/17全部通过不等于方法逻辑有效且完整。

**v4新增的关键步骤**：实现后审计必须包含维度21——这是"声明性vs强制性"审计。v3的维度18检查恒真/恒假，但声明性实现的返回值不是恒真的（确实返回了True），只是True背后没有强制机制。维度18全部通过不等于返回值有实际强制机制。同时，维度19/20预检必须检查"限定词是否完整"——不只检查"是否覆盖"，还要检查来源要求中的形容词/限定词是否在Check List中保留。

### 核心逻辑：六层审计递进

```
覆盖性审计（138号，维度1-10）
  └─ 查"Check List 是否提到了来源文档的每个要求"
  └─ 盲区：Check List 说"实现X"，但"实现"标准不明确 → F1/F2

可实现性审计（142号，维度11）
  └─ 查"Check List 措辞是否精确到能区分'定义'和'实现'"
  └─ 盲区：假设 Check List 本身的描述正确 → F4/F5/F6

权威性逐字核对（145号，维度12）
  └─ 查"实现的枚举/字段/状态是否与127号Schema冻结文档逐字一致"
  └─ Check List 是导航，127号是法律
  └─ 盲区：只核对127号不核对123号跨章节定义，只读本Phase章节不读跨章节依赖 → F7

跨章节依赖扫描（149号，维度13）
  └─ 查"Phase X实现中用到的每个概念，是否回溯到123号中该概念的定义章节"
  └─ 不只读"本Phase对应章节"，要扫描全文中所有被当前Phase引用的概念的定义章节
  └─ 盲区：123号概括了系统探讨.md母本中的实现细节 → F8

母本回溯审计（149号，维度14）
  └─ 查"实现是否回溯了系统探讨.md中被123号概括掉的母本细节"
  └─ 系统探讨.md不是"辅助文件（按需）"，是必读母本
  └─ 盲区：以上14维度全部是"文档vs文档"审计，假设了"Check List正确→代码实现正确" → F9/F10
```

**v2新增的"文档vs代码"审计层**：

```
Check List→代码实现完整性审计（153号，维度15）
  └─ 查"代码是否实现了Check List要求的具体方法/逻辑/边界情况"
  └─ 不只查"有对应的类/函数"，要查"代码是否实现了Check List要求的方法"（F9）
  └─ 盲区：代码参数传递bug → F11（维度17）

代码层面母本回溯审计（153号，维度16）
  └─ 查"代码是否实现了系统探讨.md母本中被两次概括丢失的细节"
  └─ Check List概括了123号，123号概括了母本，到代码层面母本细节完全丢失（F10）
  └─ 不只查"Check List是否覆盖了母本"（维度14），更查"代码是否实现了母本细节"

代码参数正确性审计（153号，维度17）
  └─ 查"代码中每个函数调用的参数是否正确传递"
  └─ 特别检查参数是否传了正确的变量而不是类名/类型名
```

**v3新增的"代码逻辑深度"审计层**：

```
方法逻辑有效性审计（158号，维度18）
  └─ 查"方法内部的逻辑是否真正有效（不是恒真/恒假/空操作）"
  └─ 特别检查`or`连接的条件——`x>0 or x==0`是恒真的
  └─ 盲区：方法存在且不是恒真/恒假，但返回值只是声明，没有强制机制 → F15（维度21）

方法完整性审计（158号，维度19）
  └─ 查"方法是否完整实现了来源要求的所有来源/所有字段/所有子要求"
  └─ v4扩展：还查"一个条件的多个限定词"是否全部实现（如"≥3 AND 未参与设计"）
  └─ 盲区：条件限定词丢失（检查了"≥3"但漏了"未参与设计"） → F12扩展（维度18扩展）

来源逐字要求检查（158号，维度20）
  └─ 查"plan/123号的逐字要求（不只是Check List概括的）是否在代码中实现"
  └─ v4强化：不只检查"是否覆盖"，还检查"限定词是否完整"
  └─ 盲区：概念覆盖了但限定词丢失（"3个问题族"覆盖了但"未参与设计"丢失） → F15变体（维度21）
```

**v4新增的"声明性vs强制性"审计层**：

```
声明性vs强制性审计（161号，维度21）
  └─ 查"返回True/False的验证方法是否有实际强制机制支撑"
  └─ 特别检查：返回frozen=True的方法是否有实际冻结机制（修改时抛异常）
  └─ 特别检查：返回verified=True的方法是否有运行时权限检查（PermissionError）
  └─ 特别检查：返回defense=True的方法是否由实际防御逻辑支撑（不只是数量检查）
  └─ 关键原则：True/False返回值不等于强制机制——必须检查返回值背后是否有运行时强制逻辑
```

**这条链的教训**：每一层审计都建立在前一层的假设上，而每一个假设都会被下一轮实现打破。145号说"127号是法律"是对的，但149号发现"只读127号+本Phase章节"不够。149号说"系统探讨.md是必读母本"是对的，但153号发现"Check List正确不等于代码实现正确"。**v1的14维度解决了"文档层面"的所有已知断层，v2的3个新维度解决了"文档→代码"层面的断层。** 158号发现v2的维度15只查"方法是否存在"不查"方法逻辑是否有效"，v3的3个新维度解决了"代码逻辑深度"层面的断层。161号发现v3的维度18只查"恒真/恒假"不查"声明性vs强制性"，v4的1个新维度解决了"声明性vs强制性"层面的断层。本手册不是终点——未来 Phase 7+ 实现后，可能还会暴露 F16+，届时追加到第 2 章。

### 2.2 每种断层的详解

#### F1：定义了=实现了

**定义**：Check List 要求"实现 X"，但实际只"定义了 X 的类型/schema/枚举"就勾选。

**典型实例**（140号，Phase 1）：
- P1-2.2 要求"实现事件捕获器（hook 到 Devin CLI 的 tool 调用、subagent 输出、文件写入等）"，实际只有 EventFactory（创建事件的辅助方法）。"建一个渔网"变成了"建一个能手工往里放鱼的容器"。
- P1-4.3 要求"实现语义抽取器（从原始事件中识别命题、义务、表示、证据和拒绝分支）"，实际只有 SemanticEvent 类型定义。"建一个翻译器"变成了"只建了目标语言的字典"。

**为什么前一层没防住**：138号覆盖性审计只查"Check List 是否提到了 X"，不查"实现的标准是什么"。

**检测方法**：维度11——每个"实现X"项必须标注 D1-D4 预期深度，勾选时明确当前深度。

#### F2：验证了=完整了

**定义**：Check List 要求"验证 X"，但实际只"写了验证函数"就勾选，不考虑验证是否覆盖所有边界情况。

**典型实例**（140号，Phase 1）：
- P1-3.5 要求"验证事件因果图是 DAG（不形成环）"，实现用 DFS 检测环——但 123号§17 明确"不存自环"，DFS 环检测不等于自环检测。验证函数写了，但边界情况（自环）没覆盖。

**为什么前一层没防住**：同 F1，覆盖性审计不查"验证覆盖了哪些边界"。

**检测方法**：维度11——每个"验证X"项必须附边界情况清单。

#### F3：Check List 覆盖盲区

**定义**：Check List 本身遗漏了来源文档中的某些要求。

**典型实例**（140号，Phase 1）：
- 123号§17 明确"数据库只存其无环的直接前驱边，不存自环"，但 131号 P1-3.5 只说"不形成环"，遗漏了"不存自环"这个更强的约束。
- 123号§44 明确把"事件捕获完整度"列为 Phase 1 核心指标，但 131号 Check List 完全没有这项。
- 123号§39 明确要求"同一 checkpoint 多 continuation"的实验设计，131号提到了但没要求实际验证。

**检测方法**：维度11 的 F3 检查——逐项对照来源文档（123号/系统探讨.md/plan）的每一行，确认 Check List 没有遗漏。

#### F4：概念混淆

**定义**：两个不同概念在实现者脑中合并为一个，导致代码中用了错误的枚举/字段/类型。

**典型实例**（144号，Phase 2，A-1）：
- 123号§14 定义了 9 种 TaskType（prove/refute/construct/compute/classify/optimize/conjecture/explain/value）
- 127号§4 定义了 10 种 ObligationType（prove/refute/construct/compute/search/compare/evaluate/interface/verification/value）
- 实现时把 TaskType 的值（classify/optimize/conjecture/explain）混入了 ObligationType

**为什么 140/142 没防住**：140/142 关注"实现深度"（D1-D4），不是"概念正确性"。D2 深度等级要求"有可执行的函数/方法"——实现了，但实现的是错误的概念。

**检测方法**：维度12——核对实现中的每个枚举/类型，确认它对应的是 127 号中的哪个 schema 定义，而非凭"名称相似"假设。

#### F5：权威定义偏差

**定义**：Check List 正确描述了要求，实现也确实"实现"了（不是只定义），但实现的枚举值/字段名/状态值与 Schema 冻结文档（127号）的权威定义不一致。

**典型实例**（144号，Phase 2）：
- EvidenceStatus 用了 `pending/verified/contradicted/withdrawn`，127号§6 权威定义是 `pending/active/superseded/retracted`
- StallType 用了自创的 7 类，123号§38 权威定义是 `necessary_exploration/semantic_repetition/unresolved_contradiction/tool_blocked/representation_unsuitable/strategy_exhaustion/budget_depletion`
- ObligationStatus 用了 `released`，127号§4 权威定义是 `discharged`

**为什么 140/142 没防住**：140/142 假设了一个前提——Check List 本身的描述是正确的。实际上 Check List 可能抄错了，再怎么加深度等级和边界情况，也是在一个错误的描述上加精度。

**检测方法**：维度12——实现时不能只看 Check List，必须同时打开 127号 Schema 冻结文档逐字核对。**Check List 是导航，127号是法律。**

#### F6：方法近似

**定义**：Check List 要求用特定方法（如 Krippendorff α），实现用了近似方法（如 Jaccard 相似度）替代，且未声明近似。

**典型实例**（144号，Phase 2，A-9）：
- 132号 P2-6.2 要求"字段级 Krippendorff α"
- 实现用了 Jaccard 相似度近似 α，没有声明是近似

**为什么 140/142 没防住**：140/142 关注"是否实现了"，不是"实现的方法是否与要求的方法一致"。

**检测方法**：维度12——对每个要求特定方法的 Check List 项，核对实现是否使用了要求的方法，如使用近似方法必须明确声明。

#### F7：跨章节依赖遗漏

**定义**：Phase X 的实现使用了 Phase Y 或 §Z 中定义的概念，但实现时只读了 Phase X 对应章节，没读概念的定义章节，导致实现不完整。Check List 做了概括（如"设计H0—H2激活包"），但概括丢失了定义章节中的细节（如9个完整动作、7个checkpoint字段、3个依赖代理）。

**典型实例**（149号，Phase 3）：
- Phase 3 用了 checkpoint（定义在 §39 DYN-3 / Phase 4 章节），但 147号SOP 只要求读"本Phase对应章节"，checkpoint 的7个字段（Q_0/事件前缀/模型/工具/权限/预算/版本哈希）全部遗漏。
- Phase 3 用了控制器动作集合（定义在 §485-497 / §21-28 控制器设计章节），但只读 §48 Phase 3 章节，动作集合从9个缩水到5个。
- Phase 3 用了 Agent 依赖代理（定义在 §530 / §23 最小提示章节），但只读 §48，依赖代理完全缺失。
- Phase 3 用了 visibility label（定义在 §607 / §28 角色可见性章节），但 147号SOP 只要求读 127号角色定义，不要求读 123号§28 的"落实为 visibility label + 能力令牌"实现形式要求。

**为什么 F1-F6 没防住**：
- F3 检查的是"Check List 是否遗漏来源文档要求"——但 Check List 说"设计H0—H2激活包"不算遗漏（它概括了），问题是概括丢失了 §485-497 的9个动作细节。F3 查 Check List 遗漏，不查"实现是否回溯了123号原文中被Check List概括掉的细节"。
- 维度12 只核对 127号 Schema 冻结文档——但这4项偏差是 123号定义的（不是127号），维度12 不覆盖 123号的定义。
- 147号SOP 阶段1 只要求读"本Phase对应的DYN章节"——Phase 3 对应 §48，但 checkpoint 定义在 §39（DYN-3/Phase 4），动作集合定义在 §485-497（§21-28），依赖代理定义在 §530（§23），visibility label 定义在 §607（§28）。这些跨章节依赖全部被跳过。

**检测方法**：维度13——跨章节依赖扫描。对 Phase X 实现中用到的每个概念，回溯到 123号中该概念的定义章节，核对实现是否完整覆盖了定义中的所有字段/枚举/子要求。不只读"本Phase对应章节"，要扫描全文中所有被当前Phase引用的概念的定义章节。

**系统性遗漏模式**（150号 Phase 4-7预防性审计发现）：

F7不是随机遗漏，而是**系统性遗漏**——某些跨章节依赖会在所有用到它们的Phase中被重复遗漏。150号审计了Phase 3-7共5个Phase的Check List，发现以下系统性遗漏模式：

| 跨章节依赖 | 定义章节 | 遗漏的Phase | 系统性？ |
|---|---|---|---|
| checkpoint 7字段 | 123号§847 | Phase 3/4/6（3个） | **是**——凡是用checkpoint的Phase都遗漏 |
| visibility label | 123号§607 | Phase 3/4/5/6（4个） | **是**——凡是有角色隔离的Phase都遗漏 |
| a_t=W^T*p_t公式 | 系统探讨.md§10.4 | Phase 3/5（2个） | **半系统性**——凡是涉及H投影的Phase都遗漏 |
| 动作集合9个 | 123号§485-497 | Phase 3（1个） | 否——Phase 6已正确列出9种 |
| Agent依赖代理3种 | 123号§530 | Phase 3（1个） | 否——Phase 4/6已正确列出3种 |

**系统性遗漏的根因**：Check List编写时只读"本Phase对应章节"，而某些概念（如checkpoint、visibility label）的定义章节不在任何Phase的"对应章节"内——它们是全局性概念，被多个Phase使用但定义在非Phase章节（§847在§39 DYN-3，§607在§28角色可见性）。

**系统性遗漏的检测策略**：在实现前自检协议中，不只扫描"本Phase用到的概念"，还要预先建立**跨章节依赖清单**——列出所有被多个Phase使用的全局性概念及其定义章节，确保每个Phase的Check List都覆盖了它们。当前已知的系统性遗漏概念：
1. checkpoint 7字段（123号§847）——被Phase 3/4/6使用
2. visibility label + 能力令牌（123号§607）——被Phase 3/4/5/6使用
3. a_t=W^T*p_t公式（系统探讨.md§10.4）——被Phase 3/5使用

未来可能新增其他系统性遗漏概念，届时追加到此清单。

#### F8：母本继承损失

**定义**：123号是系统探讨.md的严格化版本，但严格化过程中概括了母本中的部分实现细节（如公式、算法、数据结构）。实现时只读123号不读母本，导致被概括掉的细节未被实现。

**典型实例**（149号，Phase 3）：
- 系统探讨.md §10.4（第1943-1967行）定义了完整的 `a_t = W_{C,F,τ}^T * p_t` 稀疏计算公式，包含7种数值权重的具体组合方式。
- 123号 §25（第554-562行）只概括为"H首版使用规则—条件—动作incidence/factor视图"——公式本身未被123号逐字继承，7种数值权重被概括为"H中的数值可包含"列表。
- 实现时只读123号§25，不读系统探讨.md§10.4，导致稀疏计算公式完全缺失，incidence matrix 只存了0/1权重而非7种数值组合权重。

**为什么 F1-F7 没防住**：
- 147号SOP 阶段1 把系统探讨.md列为"辅助文件（按需）"，不是必读文件。实现前预检不读母本。
- 146号第5章的三文件交叉审计虽然是标准流程，但只在"实现后审计协议"（第9章）中被引用。实现前预检不引用第5章。
- F3 检查的是"Check List 是否遗漏"——但 Check List 说"H图incidence/factor稀疏视图"不算遗漏（它概括了123号§25），问题是123号§25本身已经概括损失了系统探讨.md§10.4的公式。F3 查的是Check List vs 123号，不查 123号 vs 系统探讨.md 的继承损失。

**检测方法**：维度14——母本回溯审计。对 Phase X 实现中用到的每个设计概念，回溯到系统探讨.md母本中该概念的原始定义，检查123号是否完全继承了母本中的实现细节。若123号概括了母本细节（如把公式概括为"incidence/factor视图"），实现必须回溯母本获取丢失的细节。

#### F9：Check List→代码实现完整性断层

**定义**：Check List正确描述了要求（通过了维度1-14所有文档层面审计），但代码实现没有完整实现Check List要求的方法/逻辑/边界情况。代码"有对应的类/函数"，但没有实现Check List要求的具体方法。

**典型实例**（153号，Phase 4）：
- Check List P4-5.2说"分层或配对统计"（123号§39要求），代码只做了简单配对（mean(t)-mean(c)），没有实现分层统计（按checkpoint分层，层内估计ATE，加权汇总）。有`estimate_ate()`函数，但没有实现Check List要求的"分层"方法。
- Check List提了"答案泄漏代理四门"（123号§23），代码的`audit_leakage()`只记录一个分数，没有实现四门检测逻辑（字面匹配/等价映射/候选空间缩减/盲审恢复）。有`audit_leakage()`方法，但没有实现Check List要求的"四门"。
- 127号§10.7要求Auditor接收9类输入（冻结manifest/处理分配/所有实际Hint/提示前后事件状态/输出/ground truth/工具证据/哈希/隔离记录），代码的`Auditor`类没有`receive_inputs()`方法。有`Auditor`类，但没有实现127号要求的输入输出契约。

**为什么 F1-F8 没防住**：
- F1-F8 全部是"文档vs文档"断层——查Check List vs 来源文档、Check List vs 127号、Check List vs 123号跨章节、Check List vs 系统探讨.md母本。没有一个维度查"代码 vs Check List"。
- 维度11查Check List措辞是否精确到能区分"定义"和"实现"——但即使Check List措辞精确，代码仍然可以只实现简化版。
- 维度12查枚举/字段名是否与127号一致——但不查"代码是否实现了127号要求的输入输出契约"。
- 150号用维度13/14预防性审计了Check List，修正了F7/F8——但只修正了Check List，没有审计代码实现是否真的实现了修正后的Check List要求。

**检测方法**：维度15——Check List→代码实现完整性审计。对Check List中每个"实现X"项，打开代码文件，核对代码是否实现了X要求的具体方法/逻辑/边界情况。特别检查：Check List要求特定方法时（如"分层或配对统计"），代码是否实现了该方法；Check List要求特定数量时（如"四门"），代码是否实现了全部；Check List要求边界情况处理时，代码是否处理了。

#### F10：母本细节在代码层面的二次丢失

**定义**：系统探讨.md母本中的实现细节，被123号概括一次（F8检测这一层），再被Check List概括第二次，到代码层面完全丢失。F8检测的是"123号 vs 母本"的第一次概括损失，F10检测的是"代码 vs Check List vs 123号 vs 母本"的第二次概括损失。

**典型实例**（153号，Phase 4）：
- 系统探讨.md§15.4定义了gaming检测（"Agent可能输出停滞词以触发更多帮助。需要工具证据和结构进展，而不是只相信自报"），123号在风险列表中概括提及（§57"Hint让Agent形成帮助依赖"），Check List P4-8概括为"记录负效应和无效规则"，到代码层面gaming检测完全缺失。母本中的检测机制（停滞词+工具证据+结构进展的三元判定）被两次概括完全丢失。
- 系统探讨.md§13定义了反应式救援模式（五条具体理由：先观察自然失败/因果归因清楚/泄漏干扰低/可能浪费预算/DYN-0-3即可实验），123号概括为"因果归因较清楚，泄漏和干扰较低"，Check List没有单独提及反应式救援模式，到代码层面完全缺失。母本中的模式声明（Phase 4必须采用反应式救援，不能使用主动式导航）被两次概括丢失。
- 系统探讨.md§14定义了POC-C六维度（越过卡点率/正确率/新有效边/提示成本/泄漏风险/副作用），Check List没有单独提及这六个维度，到代码层面完全缺失。

**为什么 F8 没防住**：
- F8检测的是"123号 vs 系统探讨.md"的概括损失——但123号可能继承了母本细节（在风险列表中提及gaming），Check List进一步概括时丢失了（P4-8只说"记录负效应"），代码实现时只读Check List不读123号和母本，细节就完全丢失了。
- 150号用维度14审计了Check List层面的F8——但审计精度不够。P4-8"记录负效应"在Check List层面看起来覆盖了系统探讨.md§15.4的gaming检测，因为"负效应"可以包含gaming。但实际上gaming检测是一个具体的检测机制（停滞词+工具证据+结构进展的三元判定），不是笼统的"负效应记录"。150号的审计精度停留在"概念覆盖"层面，没有深入到"实现机制覆盖"层面。
- 维度14查"Check List是否覆盖了母本"——但不查"代码是否实现了母本细节"。即使Check List覆盖了（150号审计通过），代码仍然可以不实现。

**检测方法**：维度16——代码层面母本回溯审计。对Check List中每个概括性条目（如"记录负效应"、"测帮助量曲线"），回溯到系统探讨.md母本中该概念的原始定义，检查代码是否实现了母本中的所有细节（检测机制、标注要求、模式声明），不只是Check List概括后的版本。特别检查母本中的具体检测机制——这些最容易被两次概括丢失。

**F10的两个层面（154号发现）**：
- **Check List层面的前置表现**：Check List概括了123号，123号概括了母本，Check List层面已经丢失了母本细节。维度16预检（第8章步骤10）能在Check List层面发现并修正这个前置表现——在Check List中显式列出母本细节。
- **代码层面的最终表现**：即使Check List修正了（显式列出了母本细节），代码实现时仍然可能不实现母本细节。维度16（第9章9.7）检测这个最终表现——打开代码文件核对代码是否实现了母本细节。
- **154号证明**：维度16预检可以在Check List层面执行（154号对Phase 5/6/7 Check List做了维度16预检，修正了5处F10风险），在实现前修正Check List中丢失的母本细节，避免实现时母本细节完全丢失。

#### F11：代码参数传递bug

**定义**：代码中的参数传递错误——参数值传了错误的变量（如传了类名/类型名而不是实际值），或参数的语义与函数签名不一致。这不是文档问题，是纯粹的代码bug，需要代码审查才能发现。

**典型实例**（153号，Phase 4）：
- `migration_tester.py:161`：`hint_level=best_original.ate.__class__.__name__`——传的是`float`（Python类型名），而不是实际的处理组名称（如"h1"）。`__class__.__name__`返回的是`float`，不是hint level名称。正确应该是`best_original_group`（处理组的key名称）。

**为什么 F1-F10 没防住**：
- F1-F10 全部是文档层面或文档→代码层面的断层——不查代码内部的参数传递正确性。
- 维度15查"代码是否实现了Check List要求的方法"——但不查"代码内部的参数传递是否正确"。方法可以实现，但参数传错导致结果错误。
- 这种bug只能通过代码审查或运行时测试发现——文档审计无法覆盖。

**检测方法**：维度17——代码参数正确性审计。对代码中每个函数调用的参数，核对参数值是否正确传递（类型、值、语义）。特别检查：参数是否传了正确的变量（而不是类名/类型名）；参数的语义是否与函数签名一致；边界情况参数是否被正确处理。**最有效的检测方法是运行集成测试**——参数传错通常会导致测试失败或结果异常。

#### F12：方法存在但逻辑无效

**定义**：方法/函数存在（通过维度15"方法存在性检查"），但其内部逻辑实际上没有执行有效检查或没有产生有效结果。方法签名正确，方法体存在，但逻辑是空操作或恒真判断。

**典型实例**（158号，Phase 5）：
- `ContextSegment.check_has_5_records()`方法存在，但内部逻辑是`token_cost > 0 or token_cost == 0`——这个条件**永远为True**（任何数要么>0要么≤0），实际上没有检查任何东西。同样`pruning_record != "" or pruning_record == ""`也永远为True。整个方法是一个空检查——方法存在但逻辑无效。
- 这个bug特别危险，因为它看起来像是在检查5项记录（方法名、参数、返回值类型都正确），但实际上没有过滤任何东西。如果只查"方法是否存在"（维度15），这个bug无法被发现。

**为什么 F9 没防住**：
- F9（维度15）查"代码是否实现了Check List要求的方法"——check_has_5_records()方法存在，维度15通过。
- 维度15定义说了"核对代码是否实现了X要求的具体方法/逻辑"，但"逻辑"这个词太笼统，实际执行时审计者只检查了"方法是否存在"，没有检查"方法的条件判断是否真正过滤"。
- 这种bug需要逐行审视方法体的逻辑才能发现——不是"有对应的类/函数"的问题，是"函数内部的逻辑是否真正有效"的问题。

**检测方法**：维度18——方法逻辑有效性审计。对代码中每个验证/检查类方法，逐行审视方法体的逻辑，确认：
1. 条件判断是否真正过滤（不是恒真/恒假）
2. 返回值是否真正反映检查结果（不是总是True/总是False）
3. 循环是否真正遍历（不是空循环/单次循环）
4. 特别检查`or`连接的条件——`x > 0 or x == 0`是恒真的，`x != "" or x == ""`也是恒真的

**F12与F9的区别**：F9是"方法不存在"，F12是"方法存在但逻辑无效"。F9检查"有对应的类/函数"，F12检查"函数内部的逻辑是否真正有效"。

**v4扩展（161号）**：F12不只包括恒真/恒假/空操作，还包括以下两种变体：

- **(b) 检查了错误的条件**：方法存在且不是恒真/恒假，但检查的条件与来源要求的条件不同。典型实例（161号，Phase 6）：R-14防线要求"不被单一模型版本绑架"——需要检查"不同模型版本数>1"，但代码检查的是"效果记录数>1"。如果2条效果记录都来自同一模型版本，`len(effects) > 1`为True但仍然是被绑架。方法存在、条件不是恒真的、返回值类型正确，但检查了错误的条件。

- **(c) 只检查了条件的一部分**：方法存在且不是恒真/恒假，但来源要求的一个条件有多个限定词，代码只检查了其中部分限定词。典型实例（161号，Phase 6）：G0-5要求"≥3个**未参与设计**的问题族"——有两个限定词"≥3"和"未参与设计"，代码只检查了"≥3"（`applicable_domains >= 3`），漏了"未参与设计"。方法存在、条件不是恒真的、返回值类型正确，但只检查了条件的一部分。

**F12三种变体的共同特征**：方法存在、方法体不是空操作、返回值不是恒真/恒假——但方法逻辑实际上没有执行来源要求的有效检查。维度18必须检查全部三种变体，不只是(a)恒真/恒假。

#### F13：方法存在但不完整——来源要求多来源/多字段但代码只实现部分

**定义**：方法/函数存在（通过维度15"方法存在性检查"），但没有完整实现来源要求的所有来源、所有字段或所有子要求。来源（123号/系统探讨.md/plan）明确要求多个来源或多个字段，但代码只实现了部分。

**典型实例**（158号，Phase 5）：
- 123号§24明确K投影从3个来源查询："从数学语义、证明义务和表示运输中查询'可以调用什么'"。但代码的`query_k()`只从1个来源（dg_adapter）获取——缺少"证明义务"和"表示运输"2个来源。方法存在，但不完整。
- 123号§29明确温层包含"失败模式"，但WarmEntry没有failure_mode字段。数据结构存在，但字段不完整。
- 123号§29明确热层包含"单个激活包"，但HotEntry没有activation_pack字段。数据结构存在，但字段不完整。

**为什么 F9/F7 没防住**：
- F9（维度15）查"代码是否实现了Check List要求的方法"——query_k()方法存在，维度15通过。但维度15没有检查"方法是否完整实现了来源要求的所有来源"。
- F7（维度13）查"概念定义章节"——但维度13被理解为"查概念定义是否存在"，不是"逐字段核对数据结构实现"。123号§29定义了温层/热层的具体字段，但维度13没有明确要求"对定义了具体数据结构字段的章节，逐字段检查实现"。

**检测方法**：维度19——方法完整性审计。对代码中每个方法/数据结构，核对来源（123号/系统探讨.md/plan）是否要求了多个来源/多个字段/多个子要求，确认代码是否全部实现。特别检查：
1. 来源明确列出多个来源时（如"从A、B、C中查询"），代码是否实现了全部来源
2. 来源明确定义了数据结构字段时（如"温层包含X、Y、Z"），代码的数据结构是否包含全部字段
3. 来源明确要求多个子功能时（如"4种派生状态"），代码是否实现了全部子功能

**F13与F9的区别**：F9是"方法不存在"，F13是"方法存在但只实现了部分来源/部分字段"。F9检查"有对应的类/函数"，F13检查"类/函数是否完整实现了来源要求的所有部分"。

#### F14：plan/123号逐字要求未被Check List概括，维度15只查Check List不查plan/123号逐字要求

**定义**：plan或123号中有Check List没有概括到的具体行号要求（如plan第197行、第199行、第248行；123号§24、§25、§28、§31、§57）。维度15只查"Check List要求"，不查"plan/123号逐字要求"，导致这些要求在代码层面缺失。

**典型实例**（158号，Phase 5）：
- plan第197行明确要求"微包不预载未来路线"，但Check List没有概括这条要求，代码的MicroPack没有check_no_preload_future_route()方法。
- plan第199行明确要求"请求按需展开本身也成为事件"，但Check List没有概括这条要求，代码的ContextCompiler没有request_expansion()方法。
- plan第248行明确要求"从内容寻址checkpoint继续"，但Check List没有概括这条要求，代码的ContextCompiler没有set_checkpoint()方法。
- 123号§25明确要求"稀疏计算不能越过原始证据与发布状态直接宣告某Hint正确"，但Check List没有概括这条要求，代码的SparseActivation没有check_not_overriding_evidence()方法。
- 123号§31明确要求"派生认识状态至少区分4种"，但Check List没有概括这条要求，代码的Verifier没有compute_derived_epistemic_state()方法。

**为什么 F9/F7 没防住**：
- F9（维度15）定义是"对Check List中每个'实现X'项"——只查Check List要求，不查plan/123号逐字要求。plan和123号有Check List没有概括到的具体行号要求，维度15完全不覆盖。
- F7（维度13）查"概念定义章节"——但plan的具体行号要求不是"概念定义"，是"实现要求"。维度13不覆盖plan的行号要求。
- 三文件交叉审计（第5章）虽然在审计流程中读了三文件，但审计时只把三文件用于"横向对照"，没有逐行检查"plan第X行的要求是否在代码中实现"。

**检测方法**：维度20——来源逐字要求检查。在三文件交叉审计中，不只做"横向对照"，还要逐行检查plan和123号的每个具体要求（不只是Check List概括的要求）是否在代码中实现。特别检查：
1. plan的每个具体行号要求（如"第197行要求X"）是否在代码中实现
2. 123号的每个§X要求（不只是Check List概括的）是否在代码中实现
3. 系统探讨.md的每个具体机制描述是否在代码中实现
4. Check List概括时可能丢失的plan/123号具体要求

**F14与F9的区别**：F9是"Check List要求了但代码没实现"，F14是"plan/123号要求了但Check List没概括，维度15只查Check List所以没覆盖"。F9检查"Check List→代码"，F14检查"plan/123号→代码"（绕过Check List）。

#### F15：声明性实现而非强制性实现

**定义**：方法/字段存在，返回值类型正确，不是恒真/恒假（确实执行了检查逻辑），但返回值只是声明性的——返回True/False但没有任何实际强制机制。声明性实现看起来像是在检查（方法名、参数、返回值类型都正确），但实际上只是一个布尔声明，不是运行时强制。

**典型实例**（161号，Phase 6）：

- **λ冻结声明性实现**：`verify_p6_9_1_compliance()`返回`"lambdas_frozen": True`——声明已冻结，但`PolicyPiConfig`没有`frozen`字段、没有`freeze()`方法、没有`bump_version()`机制、修改λ时不抛异常。`True`只是一个硬编码的声明，不是由实际冻结机制支撑的返回值。

- **CapabilityToken声明性实现**：`verify_8_role_contracts()`返回`"capability_token_verified": True`——声明已验证，但没有`CapabilityToken`类、没有`PermissionError`运行时强制、没有`enforce_role_access()`方法。`True`只是一个硬编码的声明，不是由实际权限检查机制支撑的返回值。

- **R-14防线声明性实现**：`get_layered_effects()`返回`"r14_defense": len(effects) > 1`——声明R-14防线，但检查的是"效果记录数>1"而非"不同模型版本数>1"。如果2条效果记录都来自同一模型版本，`r14_defense`为True但仍然是被单一模型版本绑架。返回值不是恒真的（确实取决于效果记录数），但检查的条件是错误的。

**为什么 F12 没防住**：

- F12(a)检查恒真/恒假——声明性实现的返回值不是恒真的（`frozen=True`确实返回了True，不是`x > 0 or x == 0`那种恒真）
- F12(b)检查错误的条件——R-14的`len(effects) > 1`属于F12(b)，但λ冻结和CapabilityToken不属于F12(b)（它们没有"检查了错误的条件"，它们根本没有检查条件，只是硬编码返回True）
- F12(c)检查条件的一部分——G0-5的`applicable_domains >= 3`属于F12(c)，但λ冻结和CapabilityToken不属于F12(c)（它们没有"只检查了条件的一部分"，它们根本没有检查条件）
- **声明性实现比F12更危险**：F12的恒真/恒假容易被发现（条件永远为True/False很可疑），但声明性实现的返回值是"正确的"（确实返回了True），审计者看到`frozen=True`会认为"已冻结"，看到`verified=True`会认为"已验证"——但实际上只是声明

**为什么 F13 没防住**：

- F13检查"多来源/多字段只实现部分"——声明性实现不是"只实现了部分"（它看起来完整实现了：方法存在、返回值正确、字段齐全），只是返回值是声明性的而非强制性的

**检测方法**：维度21——声明性vs强制性审计。对代码中每个返回True/False的验证/合规/防线方法，检查返回值是否由实际强制机制支撑。特别检查：
1. 返回`frozen=True`的方法是否有实际冻结机制（修改时抛异常、有`freeze()`方法、有`bump_version()`机制）
2. 返回`verified=True`的方法是否有运行时权限检查（`PermissionError`、`enforce_role_access()`方法）
3. 返回`defense=True`的方法是否由实际防御逻辑支撑（不只是数量检查，而是检查正确的条件）
4. 返回`compliant=True`的方法是否有实际合规检查（不只是声明，而是由具体检查逻辑支撑）

**关键原则**：True/False返回值不等于强制机制——必须检查返回值背后是否有运行时强制逻辑。声明性实现是最危险的断层类型，因为它看起来像是在检查，但实际上只是声明。

**F15与F12的区别**：F12是"方法逻辑无效"（恒真/恒假/错误条件/部分条件），F15是"方法返回值没有强制机制支撑"（True只是声明，不是由实际机制返回的）。F12检查"方法内部的逻辑是否有效"，F15检查"方法的返回值是否有强制机制支撑"。一个方法可以同时通过F12（逻辑不是恒真的）但不通过F15（返回True但没有强制机制）。

### 2.3 断层类型的根本规律

**F1/F2/F3 是"措辞精度"问题**：Check List 说得不够清楚，实现者按最宽松标准勾选。修正方向是 D1-D4 + 边界情况清单。

**F4/F5/F6 是"权威来源"问题**：Check List 本身可能错，实现者可能混淆概念，方法可能被偷换。修正方向是把权威来源从 Check List 切换到 127号原文。

**F7/F8 是"审计范围"问题**：不是措辞不精确，也不是权威来源错误，而是审计/预检的范围设计有结构性缺口——只读本Phase章节不读跨章节依赖（F7），只读123号不读母本（F8）。修正方向是扩大审计范围：跨章节依赖扫描 + 母本回溯。

**F9/F10/F11 是"文档→代码"问题**：不是文档层面的问题，而是文档正确但代码实现没有对应上。Check List正确但代码没有实现Check List要求的方法（F9），母本细节被两次概括在代码层面丢失（F10），代码参数传递bug（F11）。修正方向是新增"文档vs代码"审计层：Check List→代码实现完整性审计 + 代码层面母本回溯 + 代码参数正确性审计。

**F12/F13/F14 是"代码逻辑深度"问题**：不是"方法不存在"（F9已覆盖），而是方法存在但逻辑无效（F12）、方法存在但不完整（F13）、plan/123号逐字要求未被Check List概括导致维度15不覆盖（F14）。修正方向是从"方法存在性检查"升级为"方法逻辑有效性+方法完整性+来源逐字要求检查"。

**F15 是"声明性vs强制性"问题**：不是"方法逻辑无效"（F12已覆盖恒真/恒假/错误条件/部分条件），而是方法返回值没有强制机制支撑——True只是声明，不是由实际机制返回的。修正方向是从"方法逻辑有效性检查"升级为"声明性vs强制性审计"——检查返回值背后是否有运行时强制逻辑。

**六类问题不能互相替代**：把 Check List 措辞改得再精确（解决 F1-F3），如果 Check List 本身抄错了 127 号（F5），实现还是错的。逐字核对 127 号（解决 F4-F6），如果 Check List 漏了 123 号的某条要求（F3），实现还是会缺。即使 F1-F6 全部通过，如果实现只读本Phase章节不读跨章节依赖（F7）或只读123号不读母本（F8），实现还是会缺细节。**即使 F1-F8 全部通过（文档层面全部正确），如果代码没有实现Check List要求的方法（F9）、母本细节在代码层面丢失（F10）、代码参数传错（F11），实现仍然是错的。即使 F9/F10/F11 全部通过（方法存在+母本细节实现+参数正确），如果方法逻辑无效（F12）、方法不完整（F13）、plan/123号逐字要求未被覆盖（F14），实现仍然是不完整的。即使 F12/F13/F14 全部通过（方法逻辑有效+方法完整+来源逐字要求覆盖），如果方法返回值只是声明而非强制（F15），实现仍然是声明性的而非强制性的。**

**v1 vs v2 vs v3 vs v4 的根本区别**：v1的14维度解决了"文档层面"的所有已知断层（F1-F8），v2的3个新维度解决了"文档→代码"层面的断层（F9-F11），v3的3个新维度解决了"代码逻辑深度"层面的断层（F12-F14），v4的1个新维度解决了"声明性vs强制性"层面的断层（F15）。v2假设"方法存在=方法有效+方法完整"，v3打破了这个假设。v3假设"方法逻辑有效=返回值有强制机制"，v4打破了这个假设。

## 5. 三文件交叉审计标准流程

### 5.1 三个母本

| 母本 | 角色 |
|---|---|
| `plan-dad3347dc4d8e542.md`（建设计划） | 执行视图基准 |
| `系统探讨.md`（123号母本） | 第一性原理基准 |

**冲突裁决原则**：三份文件冲突时，以 123 号 v1 为最高权威（它是当前最高架构与建设基线），其次系统探讨.md，最后 plan。冲突裁决记录必须写入审计报告。

### 5.2 并行 subagent 方法（138号首创）

用 3 个并行 subagent，分别完整捋过三个母本的每一行：

```
subagent A → 完整读 plan，逐行提取"plan 要求了什么"
subagent B → 完整读 系统探讨.md，逐行提取"系统探讨要求了什么"
subagent C → 完整读 123号v1，逐行提取"123号要求了什么"
```

然后汇总三个 subagent 的提取结果，做横向对照。这样能避免单个审计者只盯一份文档导致的盲区。

### 5.3 审计步骤

1. **三母本并行提取**：3 subagent 分别逐行提取要求
2. **横向对照**：三份提取结果对照，识别冲突和遗漏
3. **逐项对照实现**：把对照后的要求清单逐项对照实现代码
4. **断层分类**：把发现的遗漏按 F1-F15 分类
5. **修正**：以 127 号为权威修正实现，以 123 号为权威修正 Check List
6. **集成测试**：运行修正后的测试，确认出口门通过
7. **审计报告**：写审计报告，记录发现/修正/教训
8. **来源逐字要求检查（维度20，158号v3新增，161号v4强化）**：不只做"横向对照"，还要逐行检查plan和123号的每个具体要求（不只是Check List概括的要求）是否在代码中实现。特别检查plan的每个具体行号要求、123号的每个§X要求、Check List概括时可能丢失的plan/123号具体要求。**v4强化**：不只检查"是否覆盖"，还检查"限定词是否完整"——§X要求中的形容词/限定词是否在Check List中保留，§X要求中的条件是否被Check List概括为更宽松的条件
9. **声明性vs强制性审计（维度21，161号v4新增）**：对代码中每个返回True/False的验证/合规/防线方法，检查返回值是否由实际强制机制支撑。特别检查：返回frozen=True的方法是否有实际冻结机制；返回verified=True的方法是否有运行时权限检查；返回defense=True的方法是否由实际防御逻辑支撑；返回compliant=True的方法是否有实际合规检查。关键原则：True/False返回值不等于强制机制——必须检查返回值背后是否有运行时强制逻辑

### 5.4 强制深入机制（158号v3新增）

**问题**：审计者倾向于"找到第一批问题就停止"——158号Phase 5第一轮审计找到6项F9+1项F10后就评估"优秀"，第二轮深入审视代码逻辑后又发现7项深层次遗漏。

**强制深入机制**：在审计流程中，找到第一批问题后**不允许停止**——必须继续做维度18（方法逻辑有效性）、维度19（方法完整性）、维度20（来源逐字要求检查）和维度21（声明性vs强制性）审计。具体要求：
1. 找到第一批F9/F10/F11后，必须继续做维度18/19/20/21
2. 维度18/19/20/21完成后，才能写审计报告
3. 审计报告必须记录"维度18/19/20/21已执行"，不能只记录"维度15/16/17已执行"
4. 如果维度18/19/20/21发现了新问题，必须修正后重新运行全部测试

**v4强化**：维度21（声明性vs强制性）特别容易被忽略——审计者看到`frozen=True`、`verified=True`、`defense=True`会本能认为"已冻结/已验证/有防线"，但实际上可能只是声明。维度21要求审计者追问"True背后有什么强制机制？"——如果没有`freeze()`方法、没有`PermissionError`、没有实际防御逻辑，True就是声明性的。

| Representation 字段 | 127号§5 | 12个字段：rep_id/source_form/target_form/map_type/domain/preconditions/forward_transport/backward_transport/preserved_invariants/lost_information/soundness_obligation/evidence |
| HeuristicRule 字段 | 127号§7 | LHS/interface/RHS/guard/status/effect_evidence/applicable_domains/model_versions/failure_cases/eta |

### 核对规则

1. **127号是法律，Check List 是导航**：发现偏差时以 127 号为准
2. **逐字核对**：不只是核对"名称相似"，要核对每个字符
3. **区分概念**：TaskType 和 ObligationType 是不同概念，不能因为名称相似就合并
4. **方法一致性**：Check List 要求特定方法时，实现必须用该方法，近似必须声明
5. **角色完整性**：Check List 列出的所有角色必须全部实现，不能跳过

## 7. 领域教训清单（本项目特定的坑）

这些是 144号 Phase 2 审计发现的具体教训，未来 Phase 实现时容易重犯。

### 教训1：TaskType ≠ ObligationType

- 123号§14 定义了 9 种**任务类型**（用于 Q_0 的 κ 字段）
- 127号§4 定义了 10 种**义务类型**（用于 O_t 中义务的 type 字段）

- Phase 2 原实现把 TaskType 的值（classify/optimize/conjecture/explain）混入了 ObligationType

### 教训2：Schema 冻结文档是权威

- 127号是 Schema 冻结文档，其定义是权威的
- Check List 中的描述应与 127号一致，如有偏差以 127号为准
- 实现代码必须严格按 127号的字段名、枚举值和冻结声明
- **Check List 是导航，127号是法律**

### 教训3：角色隔离不是可选项

- 132号 P2-ROLE-1/2/3 定义了 3 个角色，Phase 2 原实现只有 StateReducer

### 教训4：方法近似必须声明

- Check List 要求特定方法（如 Krippendorff α）时，不能用近似方法（如 Jaccard）静默替代
- 如必须近似，必须明确声明"此处用 X 近似 Y，理由是……"

### 教训5：枚举权威值速查（最常抄错的几个）

### 教训6：Check List 概括不等于定义完整（149号 Phase 3 审计发现）

- Check List 说"设计H0—H2激活包"——这是概括，不是完整定义
- 123号§485-497定义了9个完整动作（continue_observing/ask_diagnostic_question/request_tool_check/retrieve_minimal_interface/inject_hint_0/inject_hint_1/inject_hint_2/abstain/stop_or_escalate）

- 同理：Check List 说"独立答案等价性和泄漏审计"——但123号§530还定义了"Agent依赖代理至少包括3个"，Check List 概括时丢了

### 教训7：系统探讨.md不是辅助文件，是必读母本（149号 Phase 3 审计发现）

- 123号是系统探讨.md的严格化版本，但严格化过程会概括掉实现细节
- 系统探讨.md§10.4的`a_t=W^T*p_t`公式被123号§25概括为"incidence/factor视图"，公式丢失
- 147号SOP阶段1把系统探讨.md列为"辅助文件（按需）"——这是错的，应该是必读文件
- **实现前必须回溯母本**：对Phase X用到的每个设计概念，回溯系统探讨.md母本，检查123号是否完全继承了母本细节

### 教训8：F7的系统性遗漏模式（150号 Phase 4-7预防性审计发现）

- F7不是随机遗漏，而是**系统性遗漏**——某些跨章节依赖会在所有用到它们的Phase中被重复遗漏
- 已知的系统性遗漏概念：checkpoint 7字段（§847，被Phase 3/4/6遗漏）、visibility label（§607，被Phase 3/4/5/6遗漏）、a_t=W^T*p_t公式（§10.4，被Phase 3/5遗漏）
- **根因**：这些概念是全局性概念，被多个Phase使用但定义在非Phase章节（§847在§39 DYN-3，§607在§28角色可见性）
- **检测策略**：实现前预先建立**跨章节依赖清单**——列出所有被多个Phase使用的全局性概念及其定义章节，确保每个Phase的Check List都覆盖了它们
- **预防性审计的价值**：150号在Phase 4-7实现前修正Check List，避免了149号Phase 3那样实现后才发现偏差的循环

### 教训9：Check List正确不等于代码实现正确（153号 Phase 4审计发现）

- v1的14维度全部是"文档vs文档"审计——查Check List vs 来源文档、Check List vs 127号、Check List vs 123号跨章节、Check List vs 系统探讨.md母本
- 但这条链有一个结构性缺口：**它假设了"Check List正确→代码实现正确"**
- 153号证明这个假设不成立——Check List可以完全正确（通过维度1-14所有审计），但代码实现仍然可以：
  - 没有实现Check List要求的方法（只实现了简化版）——如Check List说"分层或配对统计"，代码只做简单配对
  - 没有实现Check List要求的数量——如Check List说"四门"，代码只记录一个分数
  - 没有实现127号要求的输入输出契约——如127号要求9类输入，代码没有实现输入验证
- **Check List是导航的导航，127号是法律，123号是架构母本，系统探讨.md是设计母本——但代码必须实现这些文档要求的具体方法，不只是"有对应的类/函数"**
- **检测策略**：实现后必须做维度15——Check List→代码实现完整性审计。打开代码文件，核对代码是否实现了Check List要求的具体方法/逻辑/边界情况

### 教训10：母本细节会被两次概括在代码层面丢失（153号 Phase 4审计发现）

- F8检测的是"123号 vs 系统探讨.md"的第一次概括损失
- 但即使123号继承了母本细节，Check List可能再次概括丢失，代码实现时只读Check List不读123号和母本，细节就完全丢失了——这是第二次概括损失
- 典型实例：系统探讨.md§15.4的gaming检测（停滞词+工具证据+结构进展的三元判定）→ 123号§57概括为"Hint让Agent形成帮助依赖" → Check List P4-8概括为"记录负效应" → 代码层面gaming检测完全缺失
- **150号审计了Check List层面的F8，但审计精度不够**——P4-8"记录负效应"在概念覆盖层面看起来覆盖了gaming检测，但实际上gaming检测是一个具体的检测机制，不是笼统的"负效应记录"。150号的审计精度停留在"概念覆盖"层面，没有深入到"实现机制覆盖"层面
- **检测策略**：实现后必须做维度16——代码层面母本回溯审计。对Check List中每个概括性条目，回溯到系统探讨.md母本，检查代码是否实现了母本中的具体检测机制、标注要求、模式声明

### 教训11：代码参数传递bug需要代码审查发现（153号 Phase 4审计发现）

- 代码中的参数传递错误——参数值传了错误的变量（如传了类名/类型名而不是实际值），或参数的语义与函数签名不一致
- 典型实例：`migration_tester.py:161`的`hint_level=best_original.ate.__class__.__name__`——传的是`float`（Python类型名），而不是实际的处理组名称
- **这种bug不是文档问题，是纯粹的代码bug，文档审计无法覆盖**
- **检测策略**：实现后必须做维度17——代码参数正确性审计。对代码中每个函数调用的参数，核对参数值是否正确传递。**最有效的检测方法是运行集成测试**——参数传错通常会导致测试失败或结果异常。但有些参数bug不会导致测试失败（如传了类型名但测试不检查具体值），需要代码审查才能发现

### 教训12：方法存在不等于方法有效（158号 Phase 5审计发现）

- v2的维度15只查"方法是否存在"，不查"方法逻辑是否真正有效"
- 158号Phase 5审计发现`check_has_5_records()`方法存在，但内部逻辑是`token_cost > 0 or token_cost == 0`——**永远为True**，实际上没有检查任何东西
- 这个bug特别危险，因为它看起来像是在检查5项记录（方法名、参数、返回值类型都正确），但实际上没有过滤任何东西
- **v2假设"方法存在=方法有效"，158号证明这个假设不成立**
- **检测策略**：实现后必须做维度18——方法逻辑有效性审计。对代码中每个验证/检查类方法，逐行审视方法体的逻辑，确认条件判断是否真正过滤（不是恒真/恒假）。特别检查`or`连接的条件——`x > 0 or x == 0`是恒真的

### 教训13：方法存在不等于方法完整（158号 Phase 5审计发现）

- v2的维度15只查"方法是否实现了Check List要求"，不查"方法是否完整实现了来源要求的所有来源/所有字段"
- 158号Phase 5审计发现`query_k()`方法存在，但只从1个来源（dg_adapter）获取——123号§24明确要求3个来源（数学语义+证明义务+表示运输），缺少2个来源
- 同样：123号§29明确温层包含"失败模式"，但WarmEntry没有failure_mode字段；热层包含"单个激活包"，但HotEntry没有activation_pack字段
- **v2假设"方法存在=方法完整"，158号证明这个假设不成立**
- **检测策略**：实现后必须做维度19——方法完整性审计。对代码中每个方法/数据结构，核对来源是否要求了多个来源/多个字段/多个子要求，确认代码是否全部实现

### 教训14：审计者乐观偏差——找到第一批问题就停止（158号 Phase 5审计发现）

- 158号Phase 5第一轮审计找到6项F9+1项F10后，评估"优秀"并准备结束
- 用户质疑后第二轮深入审视代码逻辑，又发现7项深层次遗漏（含1个高危空检查bug+1个高危K投影来源缺失）
- **审计者倾向于"找到第一批问题就停止"——这是一种乐观偏差**
- **根因**：审计流程没有"强制深入"机制——找到第一批问题后没有要求继续做维度18/19/20
- **检测策略**：在审计流程中加入"强制深入"机制——找到第一批F9/F10/F11后，必须继续做维度18/19/20/21，全部完成后才能写审计报告。审计报告必须记录"维度18/19/20/21已执行"
- **这个教训本身也是v2的一个盲区**：v2关注的是"代码实现vs文档要求"的断层，没有关注"审计者自身的行为偏差"。v3新增"强制深入"机制，补全了这个盲区

### 教训15：声明性实现是最危险的断层（161号 Phase 6审计发现）

- 161号Phase 6审计发现`lambdas_frozen: True`声明已冻结，但没有`freeze()`方法、没有`bump_version()`机制、修改λ时不抛异常——True只是一个硬编码的声明
- 同样`capability_token_verified: True`声明已验证，但没有`CapabilityToken`类、没有`PermissionError`运行时强制——True只是一个硬编码的声明
- **声明性实现比F12（恒真/恒假）更危险**：F12的恒真/恒假容易被发现（条件永远为True/False很可疑），但声明性实现的返回值是"正确的"（确实返回了True），审计者看到`frozen=True`会认为"已冻结"，看到`verified=True`会认为"已验证"——但实际上只是声明
- **v3假设"返回True=已实现"，161号证明这个假设不成立**——True可以只是声明，不是由实际强制机制支撑的
- **检测策略**：实现后必须做维度21——声明性vs强制性审计。对每个返回True/False的验证方法，检查True背后是否有实际强制机制。特别检查：返回frozen=True的方法是否有`freeze()`方法；返回verified=True的方法是否有`PermissionError`；返回defense=True的方法是否检查了正确的条件（不只是数量检查）
- **这个教训本身也是v3的一个盲区**：v3关注的是"方法逻辑是否有效"（恒真/恒假/错误条件/部分条件），没有关注"方法返回值是否有强制机制支撑"。v4新增维度21，补全了这个盲区
- **同时发现维度19/20预检精度不足**：159号对Phase 6 Check List做了维度19/20预检，但预检停留在"概念覆盖"层面，没有深入到"限定词覆盖"层面。§44说"跨3个**未参与设计**的问题族"，Check List说"跨3个问题族"——预检认为"已覆盖"（都提到了"3个问题族"），但"未参与设计"限定词被丢失。这和教训10中描述的问题完全一样——150号审计P4-8"记录负效应"时，审计精度停留在"概念覆盖"层面，没有深入到"实现机制覆盖"层面。维度19/20预检重复了同样的错误。v4强化维度20预检精度：不只检查"是否覆盖"，还检查"限定词是否完整"

7. **跨章节依赖扫描（维度13，149号新增，150号强化）**：列出 Phase X 实现中将用到的每个概念（如 checkpoint、动作集合、依赖代理、visibility label），回溯到 123号中每个概念的定义章节（不限于本Phase章节），提取定义中的所有字段/枚举/子要求。不只读"本Phase对应的DYN章节"，要扫描全文中所有被当前Phase引用的概念的定义章节。**额外步骤（150号强化）**：对照本手册F7详解中的"系统性遗漏模式"清单，确认本Phase的Check List已覆盖所有已知的系统性遗漏概念（checkpoint 7字段/visibility label/a_t=W^T*p_t公式）。若发现新的系统性遗漏概念，追加到F7详解的清单中。
8. **母本回溯审计（维度14，149号新增）**：对 Phase X 实现中用到的每个设计概念（如稀疏计算公式、激活包结构、角色可见性机制），回溯到系统探讨.md母本中该概念的原始定义，检查123号是否完全继承了母本中的实现细节。若123号概括了母本细节（如把公式概括为"incidence/factor视图"），必须回溯母本获取丢失的细节。系统探讨.md不是"辅助文件（按需）"，是必读文件。
9. **Check List→代码实现完整性预检（维度15预检，153号v2新增，154号强化）**：**在Check List层面做预检**——检查Check List中每个"实现X"项是否精确描述了要求的具体方法/逻辑（不只是"有对应的类/函数"的概括）。不够精确的项在Check List中补充具体方法描述。特别检查：Check List要求特定方法时（如"分层或配对统计"），Check List是否明确了该方法的具体逻辑而不只是概括性描述；Check List要求特定数量时（如"四门"），Check List是否列出了全部而不只是概括；Check List要求边界情况处理时，Check List是否列出了具体边界情况。**154号证明：维度15预检可以在Check List层面执行，在实现前修正不够精确的描述，避免实现时只做简化版（F9预防）。**
10. **代码层面母本回溯预检（维度16预检，153号v2新增，154号强化）**：**在Check List层面做预检**——对Check List中每个概括性条目（如"记录负效应"、"测帮助量曲线"），回溯系统探讨.md母本，检查Check List是否已经丢失了母本中的具体细节（检测机制、标注要求、模式声明）。如果Check List概括性条目已经丢失了母本细节，在Check List中显式列出母本细节。**154号证明：F10有两个层面——Check List层面的前置表现（Check List概括已经丢失母本细节）和代码层面的最终表现（代码不实现母本细节）。维度16预检能在Check List层面发现并修正前置表现，避免实现时母本细节完全丢失（F10预防）。** 关键原则：母本细节会被两次概括（123号概括一次，Check List概括第二次）——维度16预检在Check List层面补回第二次概括丢失的细节。
11. **代码参数正确性预检（维度17，153号v2新增）**：实现时对每个函数调用的参数，核对参数值是否正确传递（类型、值、语义）。特别检查：参数是否传了正确的变量而不是类名/类型名（如`__class__.__name__`返回的是类型名而不是实际值）；参数的语义是否与函数签名一致。**关键原则：代码参数传递bug不是文档问题，文档审计无法覆盖——实现时必须做代码审查，实现后必须运行集成测试。维度17无法在Check List层面预检，只能在实现后通过代码审查和集成测试发现。**
12. **方法完整性预检（维度19预检，159号v3.1新增）**：**在Check List层面做预检**——检查Check List中每个"实现X"项是否明确列出了来源要求的所有来源/所有字段/所有子要求。不够完整的项在Check List中补充完整列表。特别检查：来源明确列出多个来源时（如"从A、B、C中查询"），Check List是否列出了全部来源；来源明确定义了数据结构字段时（如"温层包含X、Y、Z"），Check List是否列出了全部字段；来源明确要求多个子功能时（如"8个角色的最小输入/输出契约"），Check List是否逐项列出了全部子功能。**159号证明：维度19预检可以在Check List层面执行，在实现前修正不完整的描述，避免实现时只实现部分来源/部分字段/部分子功能（F13预防）。**
13. **来源逐字要求检查预检（维度20预检，159号v3.1新增，161号v4强化）**：**在Check List层面做预检**——用并行subagent逐行扫描plan和123号中本Phase相关章节，提取每个具体行号/§X要求，逐项对照Check List是否覆盖。未覆盖的要求在Check List中显式列出。特别检查：plan的每个具体行号要求（如"第912行要求X"）是否在Check List中被覆盖；123号的每个§X要求（不只是Check List概括的）是否在Check List中被覆盖；Check List概括时可能丢失的plan/123号具体要求。**159号证明：维度20预检可以在Check List层面执行，在实现前修正未被Check List概括的plan/123号逐字要求（F14预防）。159号用2个并行subagent分别扫描plan和123号，Phase 6发现8项F14风险，Phase 7发现5项F14风险，共13项F14风险全部在Check List层面修正。** **v4强化（161号）**：维度20预检不只检查"是否覆盖"，还检查"限定词是否完整"——§X要求中的形容词/限定词是否在Check List中保留，§X要求中的条件是否被Check List概括为更宽松的条件。典型实例：§44说"跨3个**未参与设计**的问题族"，Check List说"跨3个问题族"——v3预检认为"已覆盖"（都提到了"3个问题族"），但"未参与设计"限定词被丢失。v4预检要求逐字对照§X的每个限定词，不只检查概念覆盖，还检查限定词覆盖。
14. **声明性vs强制性预检（维度21预检，161号v4新增）**：**在Check List层面做预检**——检查Check List中每个"验证X"或"实现X的强制机制"类项是否明确描述了强制机制（不只是"返回True/False"）。不够明确的项在Check List中补充强制机制描述。特别检查：Check List要求"冻结X"时是否明确了冻结机制（如"修改时抛异常"、"有freeze()方法"、"有bump_version()机制"）；Check List要求"验证X"时是否明确了运行时强制（如"PermissionError"、"enforce_role_access()方法"）；Check List要求"防线X"时是否明确了防御逻辑（不只是"返回defense=True"，而是"检查正确的条件"）。**关键原则**：维度21预检可以在Check List层面部分执行——检查Check List是否描述了强制机制。但维度21的完整审计只能在实现后执行——检查代码是否真的实现了强制机制。Check List描述了强制机制不等于代码实现了强制机制。

## 9. 实现后审计协议

每个 Phase 实现后，必须按 21 维度逐项审计：

### 9.1 维度1-10：横向一致性审计（138号方法）

用 3 并行 subagent 分别捋三个母本，汇总后横向对照，逐项检查 DYN阶梯/12步/角色/schema/出口门/代码模块/预注册门/贯穿案例/数据迁移/五项变化 是否覆盖。

### 9.2 维度11：可实现性审计

- 每个"实现X"项是否标注了 D1-D4 预期深度
- 每个"验证X"项是否附了边界情况清单
- 每个"覆盖X"项是否明确了覆盖标准
- Check List 是否遗漏了来源文档（123号/系统探讨.md/plan）的某条要求（F3）

### 9.3 维度12：权威性逐字核对

- 对实现中的每个枚举，核对 127号原文（F5）
- 对实现中的每个字段名，核对 127号原文（F5）
- 对实现中的每个状态值，核对 127号原文（F5）
- 对实现中的每个角色名，核对 127号§8（F4）
- 对实现中使用的方法，核对是否与 Check List 要求的方法一致（F6）
- 区分易混概念（如 TaskType vs ObligationType）（F4）

### 9.4 跨章节依赖扫描（维度13，149号新增）

- 列出 Phase X 实现中用到的每个概念（如 checkpoint、动作集合、依赖代理、visibility label）
- 对每个概念，回溯到 123号中该概念的定义章节（不限于本Phase章节）
- 核对实现是否完整覆盖了定义中的所有字段/枚举/子要求
- 特别注意 Check List 概括了但 123号原文有更多细节的条目（如 Check List 说"设计H0—H2激活包"，123号§485-497定义了9个完整动作）
- 特别注意 Phase X 用了 Phase Y 定义的概念（如 Phase 3 用了 Phase 4/DYN-3 定义的 checkpoint）

### 9.5 母本回溯审计（维度14，149号新增）

- 对 Phase X 实现中用到的每个设计概念，回溯到系统探讨.md母本中该概念的原始定义
- 检查123号是否完全继承了母本中的实现细节
- 若123号概括了母本细节（如把公式概括为"incidence/factor视图"），核对实现是否回溯了母本获取丢失的细节
- 特别注意母本中的公式、算法、数据结构——这些最容易被严格化过程概括掉

### 9.6 Check List→代码实现完整性审计（维度15，153号v2新增）

- 对Check List中每个"实现X"项，打开代码文件，核对代码是否实现了X要求的具体方法/逻辑
- 特别检查Check List要求特定方法时（如"分层或配对统计"），代码是否实现了该方法而不只是简化版
- 特别检查Check List要求特定数量时（如"四门"），代码是否实现了全部而不只是一个
- 特别检查Check List要求边界情况处理时，代码是否处理了
- 特别检查127号要求的输入输出契约（如Auditor接收9类输入），代码是否实现了
- **关键原则**：有对应的类/函数不等于实现了Check List要求的方法——必须打开代码看具体实现逻辑

### 9.7 代码层面母本回溯审计（维度16，153号v2新增）

- 对Check List中每个概括性条目（如"记录负效应"、"测帮助量曲线"），回溯到系统探讨.md母本中该概念的原始定义
- 检查代码是否实现了母本中的所有细节（检测机制、标注要求、模式声明），不只是Check List概括后的版本
- 特别检查母本中的具体检测机制——这些最容易被两次概括丢失
- 特别检查母本中的模式声明（如"Phase 4必须采用反应式救援模式"）——这些声明在Check List中可能完全缺失
- **关键原则**：维度14查"Check List是否覆盖了母本"——维度16更查"代码是否实现了母本细节"。即使Check List覆盖了，代码仍然可以不实现

### 9.8 代码参数正确性审计（维度17，153号v2新增）

- 对代码中每个函数调用的参数，核对参数值是否正确传递（类型、值、语义）
- 特别检查参数是否传了正确的变量而不是类名/类型名（如`__class__.__name__`返回的是类型名而不是实际值）
- 特别检查参数的语义是否与函数签名一致
- **最有效的检测方法是运行集成测试**——参数传错通常会导致测试失败或结果异常
- 但有些参数bug不会导致测试失败（如传了类型名但测试不检查具体值），需要代码审查才能发现
- **推荐方法**：用subagent读取全部实现代码，逐个函数检查参数传递正确性

### 9.9 方法逻辑有效性审计（维度18，158号v3新增，161号v4扩展）

- 对代码中每个验证/检查类方法，逐行审视方法体的逻辑
- 确认条件判断是否真正过滤（不是恒真/恒假）——特别检查`or`连接的条件
- 确认返回值是否真正反映检查结果（不是总是True/总是False）
- 确认循环是否真正遍历（不是空循环/单次循环）
- **典型bug模式(a)**：`x > 0 or x == 0`（恒真）、`x != "" or x == ""`（恒真）、`if condition: return True; else: return True`（恒True）
- **v4新增典型bug模式(b)**：检查了错误的条件——如R-14检查"效果记录数>1"而非"不同模型版本数>1"
- **v4新增典型bug模式(c)**：只检查了条件的一部分——如G0-5检查"≥3"但漏了"未参与设计"限定词
- **推荐方法**：用subagent读取全部验证/检查类方法，逐行审视方法体逻辑，检查全部三种变体

### 9.10 方法完整性审计（维度19，158号v3新增，161号v4扩展）

- 对代码中每个方法/数据结构，核对来源是否要求了多个来源/多个字段/多个子要求
- 特别检查：来源明确列出多个来源时（如"从A、B、C中查询"），代码是否实现了全部来源
- 特别检查：来源明确定义了数据结构字段时（如"温层包含X、Y、Z"），代码的数据结构是否包含全部字段
- 特别检查：来源明确要求多个子功能时（如"4种派生状态"），代码是否实现了全部子功能
- **v4新增**：特别检查来源要求一个条件的多个限定词时（如"≥3个**未参与设计**的问题族"），代码是否实现了全部限定词——不只检查"≥3"，还检查"未参与设计"
- **推荐方法**：用subagent读取123号§29等定义了具体数据结构字段的章节，逐字段核对实现。同时用subagent扫描§X要求中的形容词/限定词，逐限定词核对代码是否实现

### 9.11 来源逐字要求检查（维度20，158号v3新增，161号v4强化）

- 在三文件交叉审计中，不只做"横向对照"，还要逐行检查plan和123号的每个具体要求
- 特别检查plan的每个具体行号要求（如"第197行要求X"）是否在代码中实现
- 特别检查123号的每个§X要求（不只是Check List概括的）是否在代码中实现
- 特别检查系统探讨.md的每个具体机制描述是否在代码中实现
- **v4强化**：不只检查"是否覆盖"，还检查"限定词是否完整"——§X要求中的形容词/限定词是否在代码中保留，§X要求中的条件是否被代码概括为更宽松的条件。典型实例：§44说"跨3个**未参与设计**的问题族"，代码检查`applicable_domains >= 3`——覆盖了"3个问题族"但丢失了"未参与设计"限定词
- **推荐方法**：用subagent逐行扫描plan和123号，提取每个具体要求，逐项对照代码。同时用subagent扫描§X要求中的形容词/限定词，逐限定词核对代码是否实现

### 9.12 审计收口

- 所有发现按 F1-F15 分类
- 修正后运行集成测试，确认出口门通过
- **强制深入检查（158号v3新增，161号v4强化）**：确认维度18/19/20/21已全部执行，不能只记录"维度15/16/17已执行"
- 写审计报告，记录发现/修正/教训
- 若发现新断层类型（F16+），追加到本手册第 2 章

### 9.13 声明性vs强制性审计（维度21，161号v4新增）

- 对代码中每个返回True/False的验证/合规/防线方法，检查返回值是否由实际强制机制支撑
- 特别检查：返回`frozen=True`的方法是否有实际冻结机制（修改时抛异常、有`freeze()`方法、有`bump_version()`机制）
- 特别检查：返回`verified=True`的方法是否有运行时权限检查（`PermissionError`、`enforce_role_access()`方法）
- 特别检查：返回`defense=True`的方法是否由实际防御逻辑支撑（不只是数量检查，而是检查正确的条件）
- 特别检查：返回`compliant=True`的方法是否有实际合规检查（不只是声明，而是由具体检查逻辑支撑）
- **关键原则**：True/False返回值不等于强制机制——必须检查返回值背后是否有运行时强制逻辑
- **典型bug模式**：`"lambdas_frozen": True`（硬编码声明，没有`freeze()`方法）、`"capability_token_verified": True`（硬编码声明，没有`PermissionError`强制）、`"r14_defense": len(effects) > 1`（检查了错误的条件，不是不同模型版本数而是效果记录数）
- **推荐方法**：用subagent读取全部返回True/False的验证/合规/防线方法，对每个方法追问"True背后有什么强制机制？"——如果没有`freeze()`方法、没有`PermissionError`、没有实际防御逻辑，True就是声明性的

## 11. 给未来 session 的话

如果你是一个新 session 或压缩后的 AI，接到一个 Phase 的实现或审计任务：

1. **先读本手册第 1 章演进史**——理解这套方法为什么是今天这个样子
2. **再读第 8 章或第 9 章**——按协议执行
3. **不要跳过维度12**——140/142 跳过了它，144号就暴露了 F4/F5/F6
4. **不要假设 Check List 正确**——145号证明 Check List 本身会抄错
5. **不要假设"实现了=完整了"**——140号证明这是 F1/F2 断层的根源
6. **不要假设"Check List正确→代码实现正确"**——153号证明这是 F9/F10/F11 断层的根源。v1的14维度全部是"文档vs文档"审计，v2新增的维度15/16/17是"文档vs代码"审计，两者缺一不可
7. **不要假设"方法存在=方法有效+方法完整"**——158号证明这是 F12/F13/F14 断层的根源。v2的维度15只查"方法是否存在"，v3新增的维度18/19/20查"方法逻辑是否有效"+"方法是否完整"+"plan/123号逐字要求是否实现"
8. **不要假设"返回True=有强制机制"**——161号证明这是 F15 断层的根源。v3的维度18检查恒真/恒假，但声明性实现的返回值不是恒真的（确实返回了True），只是True背后没有强制机制。v4新增的维度21查"返回值是否有强制机制支撑"
9. **实现后必须做维度15/16/17/18/19/20/21**——打开代码文件，核对代码是否实现了Check List要求的具体方法（维度15）、母本中的检测机制和模式声明（维度16）、参数传递正确性（维度17）、方法逻辑有效性（维度18）、方法完整性（维度19）、plan/123号逐字要求（维度20）、声明性vs强制性（维度21）。运行集成测试是维度17最有效的检测方法
10. **不要找到第一批问题就停止**——158号证明审计者有"乐观偏差"，第一轮找到6项后评估"优秀"，第二轮深入又发现7项。必须做完全部21维度才能写审计报告
11. **维度21特别容易被忽略**——审计者看到`frozen=True`、`verified=True`、`defense=True`会本能认为"已冻结/已验证/有防线"，但实际上可能只是声明。维度21要求审计者追问"True背后有什么强制机制？"
12. **维度19/20预检不只检查"是否覆盖"，还检查"限定词是否完整"**——§44说"跨3个**未参与设计**的问题族"，Check List说"跨3个问题族"——v3预检认为"已覆盖"，但"未参与设计"限定词被丢失。v4预检要求逐字对照§X的每个限定词
13. **发现新断层时，追加到本手册**——这是持续维护的活文档，不是一次性快照

本手册的存在意义：**让未来 Phase 的实现和审计不必从 129—161号重新拼经验，而是从一份完整手册开始。**
