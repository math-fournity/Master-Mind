## 一、核心问题

01工作线验证了"检索机制能选出正确的Q"（253号A7→Q8），但这是**离线、单次、用预生成数据**的验证。

04工作线要验证的是：**选出Q后，AI是否真的能突破卡点**——这需要**在线、实时、用真实Solver**。

两者性质不同：
- 01是"组件验证"——各模块是否能独立工作
- 04是"系统集成验证"——各模块串起来能否在真实环境中工作

## 二、系统架构

### 2.1 实时闭环数据流

```
solver-harness启动Solver
  ↓
Solver输出（MITM token级 + sessions.db step级）
  ↓
trajectory适配器（从trajectory数据提取每轮agent_output文本）
  ↓
MathParser.parse() → ParseResult（语义事件 + 六元组）
  ↓
StallDetector.detect() → 卡点检测
  ↓ （检测到卡点时触发）
RetrievalPipeline.retrieve() → List[MatchedRule]
  ↓
ConstrainedPolicy.select() → SelectionResult（选中的提示规则）
  ↓
提示注入（tmux send-keys到Solver session）
  ↓
Solver继续推理（收到提示后）
  ↓ （循环）
```

### 2.2 与solver-harness的集成

solver-harness的数据产物：
- `mitm/trajectory.jsonl`：token级（thinking + tool_calls），stop后decode-all生成
- `sessions_db/trajectory.jsonl`：step级（db monitor实时轮询）
- `tmux/tmux_pipe.log`：pipe-pane兜底（实时）
- `exports/conversation.json`：devin cli --export（每轮自动导出）

**实时管线用哪个数据源？**

| 数据源 | 延迟 | 完整性 | 适合实时管线？ |
|---|---|---|---|
| `sessions_db/trajectory.jsonl` | ~3秒（db monitor轮询间隔） | step级（每轮完整输出） | ✅ 最适合——每轮一个完整node，延迟可控 |
| `tmux/tmux_pipe.log` | 实时（pipe-pane） | 纯文本terminal输出 | ⚠️ 可做兜底，但格式不结构化 |
| `mitm/trajectory.jsonl` | stop后才生成 | token级 | ❌ 不适合实时（事后批量解码） |
| `exports/conversation.json` | 每轮自动导出 | 结构化JSON | ⚠️ 可用但需要文件监听 |

**决策**：实时管线用`sessions_db/trajectory.jsonl`作为主数据源，`tmux/tmux_pipe.log`作为兜底。

### 2.3 与01工作线模块的集成

01工作线的4个核心模块：

| 模块 | 入口函数 | 输入 | 输出 | 实时集成点 |
|---|---|---|---|---|
| MathParser | `parse(ParseRequest) → ParseResult` | agent_output文本 | 语义事件+六元组 | 每轮trajectory node → ParseRequest |
| StallDetector | `detect(progress_history, budget, obligations) → List[StallDetection]` | 历史状态+预算+义务 | 卡点列表 | 每轮ParseResult后检测 |
| RetrievalPipeline | `retrieve(ParseResult, hgraph) → List[MatchedRule]` | ParseResult | 匹配规则 | 检测到卡点时触发 |
| ConstrainedPolicy | `select(List[MatchedRule], SixTuple) → SelectionResult` | 匹配规则+六元组 | 选中规则 | 检索后立即选择 |

## 三、组件设计

### 3.1 TrajectoryAdapter（新增）

**位置**：`xishujuzhen/research_runtime/runtime/trajectory_adapter.py`

**职责**：从solver-harness的sessions_db/trajectory.jsonl中提取每轮agent_output，构造ParseRequest。

**接口**：
```python
class TrajectoryAdapter:
    def __init__(self, trajectory_jsonl_path: str, problem_text: str)
    def poll_new_turns(self) -> List[ParseRequest]
    # 返回自上次调用以来新增的turn的ParseRequest列表
```

**数据流**：
1. 读取sessions_db/trajectory.jsonl的新增行（增量读取，记录上次读到的位置）
2. 每行是一个step级node（含role, content, thinking, tool_calls）
3. 把assistant角色的content+thinking拼接为agent_output
4. 构造ParseRequest（agent_output, round_index, problem_text, history, current_six_tuple）

### 3.2 RealtimePipeline（新增）

**位置**：`xishujuzhen/research_runtime/runtime/realtime_pipeline.py`

**职责**：编排实时闭环——trajectory适配器 → parser → stall检测 → retrieval → policy → 提示注入。

**接口**：
```python
class RealtimePipeline:
    def __init__(
        self,
        exp_id: str,
        problem_text: str,
        hgraph: HeuristicRuleGraph,
        parser: MathParser,
        stall_detector: StallDetector,
        retrieval: RetrievalPipeline,
        policy: ConstrainedPolicy,
    )
    def run(self, max_rounds: int = 20, timeout: int = 600) -> RealtimeResult
    # 持续轮询trajectory，解析，检测卡点，检索，注入提示
```

**循环逻辑**：
```python
while not done and round < max_rounds and time < timeout:
    # 1. 轮询新turn
    new_requests = adapter.poll_new_turns()
    if not new_requests:
        sleep(3)  # 等db monitor轮询
        continue

    # 2. 解析每个新turn
    for request in new_requests:
        parse_result = parser.parse(request)
        six_tuple = parse_result.six_tuple
        progress_history.append(six_tuple_to_progress(six_tuple))

    # 3. 卡点检测
    detections = stall_detector.detect(progress_history, budget, obligations)

    # 4. 如果卡点，检索+选择
    if detections and not all(d.type == NECESSARY_EXPLORATION for d in detections):
        matched = retrieval.retrieve(parse_result, hgraph)
        selection = policy.select(matched, six_tuple)

        # 5. 注入提示
        if selection.selected_rule and not selection.is_abstain:
            inject_hint(exp_id, selection.selected_rule.hint_text)
            round += 1  # 提示注入算一轮
```

### 3.3 HintInjector（新增）

**位置**：`xishujuzhen/research_runtime/runtime/hint_injector.py`

**职责**：把选中的提示通过tmux send-keys注入到Solver session。

**接口**：
```python
class HintInjector:
    def __init__(self, exp_id: str)
    def inject(self, hint_text: str) -> bool
    # 通过tmux send-keys两步把提示发送到harness-<exp-id> session
```

**实现**（基于6.1验证结果）：
```python
def inject(self, hint_text: str) -> bool:
    # devin cli交互模式支持运行时输入，但需要两步send-keys
    # 步骤1：排队消息
    subprocess.run([
        "tmux", "send-keys", "-t", f"harness-{self.exp_id}",
        hint_text, "Enter"
    ])
    # 步骤2：发送排队消息（在空输入行按Enter）
    subprocess.run([
        "tmux", "send-keys", "-t", f"harness-{self.exp_id}",
        "Enter"
    ])
    return True
```

**前提条件**：solver-harness的launch命令需要改为交互模式（不带`-p`，用`--`分隔prompt），否则devin cli在单轮模式下不接受运行时输入。

## 四、关键技术问题

### 4.1 devin cli是否支持运行时输入？

**问题**：solver-harness用`devin -p`启动，这是单轮模式。如果devin cli在单轮模式下不接受运行时输入，提示注入无法用tmux send-keys。

**调查方案**：
1. 用solver-harness启动一个实验
2. 等Solver输出一段后，用`tmux send-keys -t harness-xxx "test" Enter`尝试输入
3. 观察devin cli是否接受输入

**如果devin cli不支持运行时输入**：
- 方案A：改用交互模式启动（`devin`不带`-p`），通过send-keys发送初始prompt和后续提示
- 方案B：每轮提示用新launch启动（exp-id带轮次后缀），但这样不是真正的"实时注入"

### 4.2 sessions.db轮询延迟

**问题**：db monitor每3秒轮询一次sessions.db，意味着trajectory数据有3秒延迟。

**影响**：如果Solver在3秒内完成一轮并进入卡点，实时管线需要等3秒才能看到这轮的输出。

**缓解**：3秒延迟对于数学解题场景可接受（AI一轮思考通常10-60秒）。如果需要更低延迟，可以缩短轮询间隔到1秒。

### 4.3 Parser的LLM调用延迟

**问题**：MathParser用LLM解析agent_output，每次parse()需要一次LLM调用（~2-5秒）。

**影响**：实时管线每轮需要等parser完成才能做卡点检测，总延迟 = db轮询延迟 + parser延迟 = 5-8秒。

**缓解**：可接受。如果需要更低延迟，可以用mock parser（正则匹配）做快速预筛，只在疑似卡点时才用LLM parser。

### 5.1 实验题目选择

从01工作线的3个验证案例中选1-2道，或选MathArena竞赛题中GLM-5.2做不出来的题（30道stuck题中的代表）。

- 有标准答案可验证

### 5.2 A/B对照

| 组别 | 条件 | 预期 |
|---|---|---|
| A组（实验组） | 实时检索+提示注入 | AI在卡点时收到提示，突破卡点 |
| B组（对照组） | Solver裸跑，无提示 | AI卡住不动，无法突破 |

**每组跑3次**（排除偶然性），记录：
- 成功率：是否做出正确答案
- 突破卡点：A组在收到提示后是否真的突破了卡点（trajectory中有新进展）
- 效率：从开始到完成的时间
- 提示质量：提示是否引导AI自己思考（而非替AI做题）

### 5.3 评估指标

| 指标 | A组预期 | B组预期 | 判定 |

### 6.1 调查devin cli运行时输入支持（P0前置）✅

**为什么做**：提示注入机制依赖devin cli接受运行时输入。如果不支持，需要改方案。

**调查结果**：devin cli交互模式（不带`-p`）**支持运行时输入**。

**验证过程**：
1. 用`devin --model glm-5-2 --export <path> -- 'prompt'`启动交互模式（注意：prompt需要用`--`分隔）
2. Solver开始思考后，用`tmux send-keys -t <session> "hint text" Enter`排队消息
3. devin cli显示`❭ Press Enter to send queued message`
4. 再用`tmux send-keys -t <session> Enter`发送排队消息
5. devin cli中断当前思考（"Canceled. What should Devin do?"），处理新输入

**结论**：提示注入用tmux send-keys两步实现：
```bash
# 步骤1：排队消息
tmux send-keys -t harness-<exp-id> "提示文本" Enter
# 步骤2：发送排队消息
tmux send-keys -t harness-<exp-id> Enter
```

**对solver-harness的影响**：solver-harness当前用`devin -p`（单轮模式），需要改为交互模式（不带`-p`，用`--`分隔prompt）才能支持运行时提示注入。

## 七、与现有OnlineOrchestrator的关系

OnlineOrchestrator（`runtime/orchestrator.py`）已有12步循环骨架，但步骤3-9都是占位实现（返回简单StepResult）。

RealtimePipeline不直接修改OnlineOrchestrator，而是作为独立的实时管线运行。原因：
1. OnlineOrchestrator的12步是概念框架，不是执行框架
2. RealtimePipeline需要与solver-harness的trajectory数据集成，这是OnlineOrchestrator没有的
3. 未来可以把RealtimePipeline的逻辑回填到OnlineOrchestrator的步骤4-9中
