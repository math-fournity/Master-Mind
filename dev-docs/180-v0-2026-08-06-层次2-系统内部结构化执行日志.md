## 一、层次2的目标

记录系统12步运行时每一步的输入、输出和中间状态，使测试结束后可以完整回溯系统内部的工作过程。

**对应需求**（178号）：
- R5 系统工作过程细节——系统每一步做了什么、为什么这么做
- R6 代码运行细节——代码执行的具体细节（输入、输出、中间状态）

---

## 二、现有系统能力分析

### 2.1 已有的可观测性组件

| 组件 | 位置 | 记录什么 | 缺什么 |
|---|---|---|---|
| RawEvent | events/store.py | 原始事件（工具调用、文本输出等） | 只有系统内部事件，没有执行细节 |
| SemanticEvent | events/store.py | 语义事件（从原始事件抽取） | 语义抽取覆盖度52%（176号审计） |
| manifest | manifest.py | 运行元数据（Q_0哈希、模型版本、预算） | 只有静态元数据，没有动态执行轨迹 |
| checkpoint | events/store.py | 状态快照（内容寻址） | 有checkpoint但无continuation轨迹分析 |
| leakage_audit | heuristics/leakage_audit.py | 泄漏审计 | 只审计泄漏，不审计引导效果 |

### 2.2 gap

现有组件记录的是"系统内部发生了什么事件"，不记录"每个模块执行时的输入/输出/中间状态"。

具体gap：
- StateReducer：记录了状态变化事件，但不记录重建过程的中间步骤
- HeuristicMatcher：记录了匹配结果事件，但不记录每个规则的匹配尝试
- Retriever：记录了检索结果事件，但不记录检索查询和过滤过程
- ContextCompiler：记录了编译结果事件，但不记录每段的5项记录详情
- Controller：记录了决策事件，但不记录决策的推理过程
- Verifier：记录了验证结果事件，但不记录验证的具体检查项

## 三、方案设计

### 3.1 结构化执行日志的schema

每个模块的每次执行记录一条`ExecutionLog`：

```json
{
  "log_id": "exec_<run_id>_<step>_<module>_<seq>",
  "run_id": "run_20260806_001",
  "session_id": "devin_session_id",
  "step": 4,
  "module": "StateReducer",
  "timestamp": "2026-08-06T09:01:55.903Z",
  "input": {
    "raw_events": [...],
    "previous_state": {...}
  },
  "output": {
    "new_state": {...},
    "state_changes": [...]
  },
  "intermediate": {
    "extraction_steps": [...],
    "failed_extractions": [...]
  },
  "duration_ms": 1234,
  "budget_consumed": {"tokens": 0, "compute": 0, "tool_calls": 0},
  "status": "success" | "partial" | "failed",
  "error": null | "error message"
}
```

### 3.2 各模块的记录内容

| 模块 | 输入 | 输出 | 中间状态 |
|---|---|---|---|
| EventCapture | devin cli输出文本 | RawEvent列表 | 语义抽取的每一步尝试 |
| StateReducer | RawEvent列表 + 前一状态 | 新状态 + 状态变化 | 重建过程的中间步骤 |
| StallDetector | 状态 + 进度历史 | 卡点检测结果 | 每个卡点类型的检测尝试 |
| HeuristicMatcher | 状态 + 规则库 | 匹配结果 + 候选激活包 | 每条规则的匹配尝试 |
| Retriever | 激活包 + 查询 | 检索结果 | 检索查询 + 过滤过程 |
| ContextCompiler | 检索结果 + 义务 | 上下文段列表 | 每段的5项记录 |
| Controller | 状态 + 候选动作 | 决策 | 决策推理过程 |
| Verifier | 验证对象 + 标准 | 验证结果 | 每个检查项的结果 |
| Budget | 预算配置 | 消耗报告 | 每步的预算消耗 |

### 3.3 存储方式

**方案**：每个run一个JSON文件 + ArangoDB collection。

| 存储位置 | 用途 | 格式 |
|---|---|---|
| `runs/${RUN_ID}/system_events.json` | 文件备份，运行中可读 | JSON Lines（每行一条ExecutionLog） |
| ArangoDB `execution_logs` collection | 结构化查询 | 文档数据库 |

**写入逻辑**：
```python
def log_execution(run_id, step, module, input, output, intermediate, budget, status):
    log_entry = {
        "log_id": f"exec_{run_id}_{step}_{module}_{seq}",
        "run_id": run_id,
        "session_id": get_session_id(),
        "step": step,
        "module": module,
        "timestamp": datetime.utcnow().isoformat(),
        "input": input,
        "output": output,
        "intermediate": intermediate,
        "budget_consumed": budget,
        "status": status,
    }
    # 写文件（实时可读）
    with open(f"runs/{run_id}/system_events.json", "a") as f:
        f.write(json.dumps(log_entry, ensure_ascii=False) + "\n")
    # 写ArangoDB（结构化查询）
    db.collection("execution_logs").insert(log_entry)
```

### 3.4 与现有事件系统的关系

**不是替代，是补充**：

| 系统 | 记录什么 | 粒度 |
|---|---|---|
| RawEvent/SemanticEvent（现有） | 系统发生了什么事件 | 事件级 |
| ExecutionLog（新增） | 每个模块执行时的输入/输出/中间状态 | 执行级 |

RawEvent/SemanticEvent是"什么发生了"，ExecutionLog是"怎么发生的"。

**关联键**：ExecutionLog的`run_id`和`session_id`与RawEvent/SemanticEvent的`run_id`一致。
