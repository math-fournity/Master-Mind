# 77 · xishujuzhen POC-8 验证方案：闭环审计标准流程化

## 一、POC-8定位

POC-7的闭环验证已经证明了闭环审计的有效性（3轮修正从98.8%提升到100%）。POC-8的目标是**将闭环审计作为标准流程从头实施**，并与开环模式做对照实验，量化闭环的边际增益。

### 与POC-7的关系

| 维度 | POC-7 | POC-8 |
|---|---|---|
| 闭环实施方式 | 事后补救（开环完成后追加闭环） | **从头实施（第1轮就闭环）** |
| 对照实验 | 无（只有闭环前后对比） | **开环组 vs 闭环组对照** |
| 验证目标 | 闭环是否有效 | **闭环作为标准流程的边际增益** |

## 二、实验设计

### 三组对照

| 组别 | 流程 | 审计方式 | 目的 |
|---|---|---|---|
| **A组** | 直接分析（无依赖图） | 无审计 | 基线 |
| **B开环组** | JSON→解读→交叉审计（1轮）→分析→执行审计（1轮） | 开环（1轮审计） | 对照开环模式 |
| **B闭环组** | JSON→解读→交叉审计闭环→分析→执行审计闭环 | 闭环（多轮直到无瑕疵） | 验证闭环标准流程 |

### 核心假设

1. **闭环组忠实度>开环组**：闭环组的转译忠实度应高于开环组（预计100% vs ~95%）
2. **闭环组发现瑕疵数>开环组**：闭环组累计发现的瑕疵数应多于开环组（因为多轮审计更严格）
3. **闭环组修正瑕疵数>开环组**：闭环组修正的瑕疵数应多于开环组（开环组不修正）
4. **闭环效率≤3轮**：闭环组在3轮修正内达到无瑕疵
5. **闭环组总分>开环组**：闭环组的6维度总分应高于开环组

### 场景选择

**复用POC-7的12限全量场景**（71节点106边10跨宫边2螺旋环路），不重新设计场景。原因：
1. POC-7已有完整的开环结果作为对照
2. POC-7的3处瑕疵+3处预存瑕疵+2处传播瑕疵已经充分暴露了问题
3. 重新设计场景会增加变量，不利于隔离闭环效应

### 执行方式

#### A组（基线）
- 复用POC-7的A组结果（`poc7_output_a.md`），不重新执行
- A组无审计要求，结果不变

#### B开环组（对照）
- 复用POC-7的B组开环结果（`poc7_output_b_interpretation.md` v1 + `poc7_output_b_result.md`）
- 开环组的交叉审计只做1轮（`poc7_output_b_cross_audit.md`），不修正
- 开环组的执行审计只做1轮，不修正

#### B闭环组（验证目标）
- **从头实施闭环流程**：
  1. 第1轮解读AI生成大师提示词（新subagent，不是复用v1）
  2. 第1轮交叉审计→如有瑕疵→反馈→修正→第2轮交叉审计→...→无瑕疵
  3. 第1轮B组分析→第1轮执行审计→如有问题→反馈→修正→第2轮执行审计→...→无问题
- 记录每轮审计的瑕疵数变化

**关键设计**：B闭环组的第1轮解读AI是全新调用，不是复用v1。这样B闭环组和B开环组的起点相同（同样的JSON输入），区别只在于流程（开环vs闭环）。

## 六、风险与缓解

### 风险1：B闭环组第1轮解读与v1不同

**风险**：B闭环组的第1轮解读AI是全新调用，可能生成与v1不同的大师提示词，导致瑕疵分布不同。
**缓解**：这是预期行为——闭环流程的验证就是要在全新调用上验证，不是在v1上修补。瑕疵分布不同不影响闭环有效性的验证。

### 风险2：闭环效率可能超过3轮

**风险**：如果B闭环组的第1轮解读瑕疵比v1多，可能需要超过3轮修正。
**缓解**：最大3轮上限。3轮后仍有瑕疵则降级为开环模式，记录残余瑕疵。

### 风险3：subagent输出截断

**风险**：POC-7中B组审计报告因子代理输出截断未完整生成。
**缓解**：B闭环组的分析结果和审计报告分两次subagent调用生成。
