## 0. 一句话概括

Grove是一个**可运行的引导式数学解题树生长引擎**——它让多个AI实例在检索机制的引导下串行探索同一道数学题，每个AI的推理过程被实时采集为树节点，系统在节点上检索方向并启动新AI继续探索，最终AI-3在方向引导下完成了一道竞赛级难题的证明。

## 1. 研究背景与问题定义

### 1.1 核心问题：稀疏矩阵中的Pattern检索

我们有一个引导式数学解题系统。当做题AI（下称**推理AI**或**Solver**）在数学题上卡住时，系统需要从海量"什么时候该提示什么"的经验存储（下称**数据基座**或**稀疏矩阵**）中，精准提取此刻最需要的那一个引导提示。

这不是普通的文本检索——检索的判据不是文本相似性，而是**思维状态的匹配**。推理AI停在某个状态，这个状态以什么形式被系统"看到"？系统怎么从海量存储中定位到相关的引导经验？

这个问题在253号文档（`dev-docs/253-v0-2026-08-07-稀疏矩阵中的Pattern检索问题-以矩条件极差题第二问为案例.md`）中被完整定义，是整个研究项目的起点。

### 1.2 关键概念定义

| 概念 | 定义 |
|---|---|
| **推理AI（Solver）** | 做数学题的AI实例。在我们的实现中是Devin CLI的一个实例，用GLM-5.2模型。 |
| **辅助智能体（系统）** | 观察推理AI的状态、决定发送什么引导提示的角色。在当前实现中是Grove AI本身（即写本文档的AI）。 |
| **提示Q** | 引导者发送给推理AI的元认知提问。不给答案，而用提问启发AI自己的思维。例如"你选择哪个方向？第一步是什么？" |
| **Pattern** | "什么时候该提示什么"的可复用经验单元，存储在数据基座中。一个Pattern描述"当AI处于状态S时，给提示Q"。 |
| **数据基座（稀疏矩阵）** | Pattern的存储。在当前实现中是ArangoDB图数据库中的`hgraph_rules`集合（启发式规则集合）。 |
| **六元组** | 推理AI的思维状态的形式化表示：(V_t, F_t, O_t, U_t, T_t, S_t)——已验证核心/猜想前沿/开放研究义务/未探索诊断/当前表示/证据。由parser从thinking中提取。 |
| **thinking** | 推理AI的内部推理文本。Devin CLI的assistant消息中`thinking`字段的内容，是AI的显式思维过程。 |

### 1.3 检索机制的工作流程

```
推理AI的thinking
     │
     ▼
[parser] 解析thinking → 语义事件序列 + 思维轨迹图节点 + 六元组
     │
     ▼
[RetrievalPipeline] 用六元组检索数据基座 → 匹配的Pattern列表
     │
     ▼
[ConstrainedPolicy] 从匹配的Pattern中选择提示 → 选中的提示Q
     │
     ▼
[提示注入/启动新AI] 把Q发送给推理AI
```

**parser**把自然语言thinking解析为结构化数据。**RetrievalPipeline**用结构化数据检索匹配的Pattern。**ConstrainedPolicy**从候选Pattern中选择最合适的提示Q。

## 2. Grove的核心创新：从"让AI停下"到"系统与AI并行运行"

### 2.1 旧困境（已消解）

之前的设计困境是："如何让推理AI在合适的位置停下来接受提示？"

这个困境贯穿了早期实现工作的全部：
- **HintInjector时序问题**——等thinking完成还是thinking中注入？
- **tmux send-keys排队问题**——"Press Enter to send queued message"
- **Response truncated后注入**——等Solver空闲再注入
- **stall_detector超时**——30秒无新节点就触发，但thinking要5分钟

**所有这些问题都在解决一个不该存在的问题。**

### 2.2 新认知：系统与推理AI并行运行

Grove的核心认知转折（记录在267号文档中）是：

**推理AI持续工作，走到哪里都可以。系统与推理AI并行运行。**

具体机制：
1. **推理AI持续推理**——不需要在某个位置停下来接受提示。AI从根节点开始，持续推理，直到自然终止（token用尽、证毕、或崩溃）。
2. **系统实时采集**——系统通过sessions.db轮询，实时获取推理AI的trajectory和thinking内容。
3. **系统实时整理树**——系统用采集到的trajectory，实时整理引导展开树。每个推理AI的探索贡献树的一条脉络。
4. **系统在节点上识别方向**——系统在树的某个节点上，用数据基座中的Pattern做检索，识别出"从这个节点应该往哪些方向探索"。
5. **系统启动新的推理AI**——对每个识别出的方向，系统启动一个新的推理AI实例，给它"从根到当前节点的脉络"（之前的路径），让它理解和验证后继续探索这个方向。

**"让推理AI停下"这个需求消失了。** 系统的目的不是"让AI做出来"，而是"让树生长出来，在过程中与正确解答的脉络相遇"。

### 2.3 三个推动关系

Grove的核心是三个推动关系，它们构成一个闭环：

```
推动关系1：引导树 → 推理AI
    系统在树的节点上检索方向Q → 启动新AI给它脉络+方向Q
    （树驱动AI生长）

推动关系2：推理AI → 解题树
    推理AI的thinking被实时采集 → 提取为树节点写入树
    （AI驱动树生长）

推动关系3：推理AI → 引导树
    每个推理AI注册为ai_instance → 记录其贡献的节点
    （AI注册到树管理系统）
```

这三个推动关系都成立时，核心循环就转通了——树持续生长，AI持续被启动，直到某条脉络到达正确解答。

## 3. 两棵树的概念

Grove维护两棵树，它们是同一棵树的不同阶段：

### 3.1 引导展开树（Guided Expansion Tree）= 过程

从题目出发，在提示驱动下展开的所有可能解题路径构成的空间。
- 每个节点是一个**数学处境**（AI在解题过程中的某个状态）
- 每条边是一个**提示Q**（引导从一个处境移动到另一个处境）
- 活的、正在生长的

### 3.2 解题记录树（Solution Record Tree）= 产物

引导展开树展开完成后凝固的树。包含成功路径、失败路径、分叉点、中间处境。

### 3.3 在ArangoDB中的实现

两棵树在ArangoDB图数据库中维护。每道题一棵树。树=节点集合+边集合。

**四个核心集合**：

| 集合 | 类型 | 存储内容 |
|---|---|---|
| `tree_nodes` | document | 树节点（数学处境）。每个节点有`situation`（六元组）、`situation_text`（自然语言描述）、`trajectory_segment`（对应的thinking片段）、`created_by_ai`（贡献此节点的AI实例ID） |
| `tree_edges` | edge | 树边（提示Q）。每条边有`_from`（父节点）、`_to`（子节点）、`hint_q`（提示内容）、`hint_level`（提示Level） |
| `problems` | document | 题目。有`status`（growing/solved/exhausted）、`root_node_key`、`solution_path` |
| `ai_instances` | document | 推理AI实例。有`status`（running/completed/crashed）、`entry_node_key`（进入树的节点）、`hint_q`（给AI的引导方向）、`devin_session_id` |

### 4.2 关键模块详解

#### 4.2.1 sessions_db_reader.py——从sessions.db读取thinking

**为什么不用MITM**：早期实现用mitmproxy流式截获Devin CLI的HTTP流量来获取thinking。但MITM有可靠性问题（HTTP/2连接复用、SSL证书、workdir_mapping缓存等）。sessions.db是Devin CLI自己的SQLite数据库，存储了所有消息节点（包括thinking），直接读数据库更可靠。

**核心设计**：
- `SessionsDBThinkingReader`类，初始化时设`_last_node_id = -1`（从头开始读，不跳过AI启动后第一个thinking block）
- `poll_new_thinking()`方法轮询sessions.db，返回新的`ThinkingChunk`列表
- 每个`ThinkingChunk`包含`node_id`（sessions.db中的消息节点ID）、`thinking`（thinking文本）、`timestamp`

**关键修复**：`init()`从-1开始是为了不跳过AI启动后第一个thinking block——AI启动后到`init_sessions_db()`调用之间可能已经完成了第一个thinking block，如果从max(node_id)开始就会跳过它。

#### 4.2.2 node_extractor.py——从thinking提取树节点

**核心流程**：
1. `init_sessions_db()`——初始化sessions.db reader，设置AI实例ID、问题ID、入口节点
2. `extract_from_sessions_db()`——轮询新thinking，每个thinking block对应一个树节点
3. 对每个thinking block，调用`_extract_single_chunk()`：
   - 用DevinCliParserProvider（devin cli作为LLM parser）解析thinking
   - parser输出ParseResult（语义事件+思维轨迹图节点+六元组）
   - 从ParseResult提取situation_text和trajectory_segment
   - 写入ArangoDB的tree_nodes集合

**关键修复——去重**：用`_processed_node_ids`集合记录已处理的sessions.db node_id，避免重复提取。之前每次`extract_from_sessions_db()`都从-1开始重新获取所有thinking，导致重复节点。

#### 4.2.3 termination_detector.py——检测AI终止

**核心设计转变**：从"检测卡住触发注入"改为"检测AI终止触发检索分配"。

**终止条件**（只在这三种情况终止AI）：
- `session_ended`——AI自然结束（证毕或主动停止）
- `crash`——AI崩溃
- `response_truncated`——token用尽

**关键修复——移除timeout**：之前有timeout逻辑——N秒无新节点就判定AI"停滞"并终止。但AI长时间思考是正常状态（一个thinking block可能需要3-5分钟），不是"停滞"。移除timeout后，AI可以完整地完成长thinking block。

#### 4.2.4 path_constructor.py——构造脉络文本

把从根到当前节点的路径，构造给新推理AI的输入文本。格式：

```
你正在解答以下数学题：
[题目原文]

之前已经进行了以下探索：

[节点0] 初始处境：题目给出的条件和目标
  → 提示Q1：[Q1内容]
[节点1] 处境：[从thinking中提取的数学处境描述]
  已证明：[已确立的结论]
  当前表示：[当前的数学表示]
  → 提示Q2：[Q2内容]
...
[节点n] 当前处境：[当前节点的数学处境描述]
  卡在：[当前卡点]

请理解验证以上路径后，继续探索以下方向：
[方向Q的内容]
```

#### 4.2.5 pattern_matcher.py——LHS子图匹配

**核心逻辑**：检查LHS（规则左侧）要求的节点类型是否是T_t（当前思维轨迹）节点类型的子集。

- LHS所有类型都在T_t中 → 1.0（完全匹配）
- LHS有1个类型不在T_t中 → 0.8（1步偏差）
- LHS有2个类型不在T_t中 → 0.6（2步偏差）
- LHS有3+个类型不在T_t中 → 0.0（超过2步偏差）

**关键修复——对称差→子集匹配**：之前用集合对称差比较T_t的所有类型和LHS要求的类型。当T_t有9种类型而LHS只要求2种时，对称差=7，返回0.0——但LHS的2种类型都在T_t中，应该匹配。改为子集匹配后，检索机制从"未选中提示"变为自动检索到方向Q。

#### 4.2.6 retrieve_directions——检索方向Q

整合parser+retrieval+policy的完整流程：
1. 用节点的situation_text构造Round
2. RealtimePipeline.process_round解析+检索+策略选择
3. 返回选中的提示Q

### 4.3 数据基座：hgraph规则

当前数据基座是ArangoDB中的`hgraph_rules`集合，存储**启发式规则（HeuristicRule）**。每条规则定义一个提示Q：

| 规则ID | 提示Q内容 | Level | LHS node_types |
|---|---|---|---|
| Q1 | 你观察到了什么？有哪些已知条件？ | 1.0 | [observation] |
| Q3 | 你选择哪个方向？第一步是什么？ | 1.0 | [candidate, subgoal] |
| Q5 | 当前方法为什么走不通？换一个方向 | 0.8 | [resolution, stall] |
| Q9 | badly approximable推出|D|下界 | 0.2 | [claim, stall] |
| ... | ... | ... | ... |

case_253有10条Q规则，定义在`case_253_rules.py`中。

**Level**：0=纯知识注入（直接告诉答案方向），1=纯思维模式（只引导思考方向不给任何具体内容）。Level越高越不泄漏答案。

## 5. 实验验证：case_253

### 5.1 实验题目

**矩条件极差题第二问**（253号案例）：

> 设实数 $a_1, a_2, \ldots, a_n$ 满足前三阶矩条件（$\sum a_i = n$, $\sum a_i^2 = n$, $\sum a_i^3 = n$），证明存在常数 $C_2 > 0$ 使得对所有 $n \geq 4$，极差 $\max a_i - \min a_i \geq \sqrt{5} + C_2 \cdot n^{-3/2}$。

这是一道竞赛级难题，bare AI（无引导的AI）做不出来——在A/B对照实验中B组（裸跑）0/3突破。

### 5.2 实验过程

实验运行了3个串行AI实例，构成2整圈核心循环：

| 圈 | AI实例 | devin session | 节点数 | 方向Q | 状态 |
|---|---|---|---|---|---|
| 1 | AI-1 | handsomely-bamboo | 4 | Q3 | completed |
| 2 | AI-2 | wiggly-tango | 14 | Q9 | completed |
| 3 | AI-3 | abounding-acrylic | 40 | — | **solved** |

**完整流程**：

1. **AI-1启动**：从根节点开始，裸跑探索矩条件极差题。AI-1生成了58822字符的thinking，探索了中心化变换、两点配置等方向。AI-1因token用尽终止。

2. **系统采集AI-1的thinking**：sessions_db_reader从sessions.db读取AI-1的thinking，node_extractor提取为4个树节点。

3. **系统在AI-1的终点节点检索方向**：retrieve_directions用PatternMatcher匹配hgraph规则，选中Q3（"你选择哪个方向？第一步是什么？"）。创建tree_edge linking AI-1的终点节点到AI-2的入口。

4. **系统构造脉络并启动AI-2**：path_constructor从根到AI-1终点构造脉络文本（1283字符），系统通过solver-harness启动AI-2（wiggly-tango），给它脉络+Q3。

5. **AI-2处理**：AI-2理解了AI-1的探索，继续数值验证+多项式方法。生成了多个thinking block，被提取为14个树节点。AI-2因response_truncated终止。

6. **系统在AI-2的终点节点检索方向**：选中Q9（"p=(5-√5)/10是二次无理数，它的连分数部分商有界，因此是badly approximable——存在c₀"）。创建tree_edge linking AI-2的终点节点到AI-3的入口。

7. **系统构造脉络并启动AI-3**：给AI-3脉络+Q9。

8. **AI-3完成证明**：AI-3在Q9方向引导下，用badly approximable性质推导|D|下界，完成case_253的证明。AI-3生成了40个树节点（round 0-27），覆盖了完整的推理过程。

### 5.3 AI-3的证明

AI-3在Q9引导下完成了以下证明链：

1. **p是二次无理数**：$p = \frac{5-\sqrt{5}}{10}$ 满足 $5x^2 - 5x + 1 = 0$（判别式 $\Delta = 5$）

2. **连分数展开**：$p = [0; 3, \overline{1}]$，部分商为 $3, 1, 1, 1, \ldots$，有界（最大 $A=3$），故 $p$ 是 **badly approximable**

3. **Liouville型界**：利用 $f(x) = 5(x-p)(x-p')$，对任意 $k/n$：
   $$5\left|\frac{k}{n}-p\right|\left|\frac{k}{n}-p'\right| = \frac{|5k^2-5kn+n^2|}{n^2} \geq \frac{1}{n^2}$$
   推出 $\left|p - \frac{k}{n}\right| \geq \frac{1}{2\sqrt{5}\,n^2}$

4. **|D|下界**：$|D| = n\cdot\min_k|p-k/n| \geq \frac{1}{2\sqrt{5}\,n}$，其中 $c_0 = \frac{1}{2\sqrt{5}} \approx 0.2236$

5. **复合到n^(-3/2)**：
   - badly approximable：$|D| \geq c_0/n$（$1/n$ 衰减）
   - 扰动分析：修正三阶矩的极差增量 $\sim \sqrt{|D|}/n$（平方根关系）
   - 复合：$\text{gap} \geq C'\cdot\frac{\sqrt{c_0/n}}{n} = C'\sqrt{c_0}\cdot n^{-3/2}$，取 $C_2 = C'\sqrt{c_0} > 0$

6. **数值验证**：对 $n=4$ 到 $500$，$\text{gap}\cdot n^{3/2}$ 最小值约 $1.23$（在 $n=199$），确认下界成立。

## 6. Grove的独特优势

### 6.1 可运行的端到端系统

Grove不是一个理论设计——它是一个**可运行的系统**。59个树节点、2条边、3个AI实例、problem status=solved，这些数据都存储在ArangoDB中，可以被查询、被验证。

### 6.2 sessions.db实时采集

Grove用sessions.db轮询替代了MITM流式截获。sessions.db是Devin CLI自己的SQLite数据库，存储了所有消息节点（包括thinking）。直接读数据库比MITM更可靠——没有HTTP/2连接复用、SSL证书、workdir_mapping缓存等问题。

### 6.3 "系统与AI并行运行"的认知转折

Grove实现了从"让AI停下接受提示"到"系统与AI并行运行"的认知转折。推理AI持续推理到自然终止，系统实时采集thinking、整理树、在节点上检索方向、启动新AI。不需要让AI停下。

### 6.4 三个推动关系的完整闭环

Grove验证了三个推动关系都成立：
1. 引导树→推理AI：系统在节点上检索方向Q，启动新AI给脉络+Q
2. 推理AI→解题树：AI的thinking被实时采集为树节点
3. 推理AI→引导树：每个AI注册为ai_instance，记录其贡献

### 6.5 端到端效果验证

case_253实验不只是验证了"循环能转"——AI-3在Q9方向引导下**实际上完成了数学证明**。这是从"组件验证"到"系统集成验证"的质的飞跃。

### 6.6 身份觉知rule

Grove实现了"辅助Pipe"的角色觉知——通过`.devin/rules/`中的三个rule（core-loop-self-check、grove-core-loop、sleep-self-check），Grove AI在每次行动前自检"我是否在主动参与核心循环"，而不是被动等待脚本驱动。

## 7. 已知局限与诚实自评

### 7.1 检索机制的粒度问题

Grove的检索机制（PatternMatcher）用的是**node_types子集匹配**——检查LHS要求的节点类型是否是T_t节点类型的子集。这是粗粒度的——只看节点类型（observation/claim/resolution等10种），不看节点内容。

对比Worktree侧的三层Pipe架构（Pipe 0拓扑化→Pipe 1大概念过滤→Pipe 2小概念标记分辨），Grove的检索机制缺少：
- **拓扑化**——把thinking编码为带有结构和标注的拓扑结构
- **大概念过滤**——用(problem_type, ai_method_type, gap_type)三个维度做形式化匹配
- **小概念标记分辨**——当大概念无法区分时，用更细的概念标记区分相似tell

### 7.2 policy选择逻辑的不足

Grove的ConstrainedPolicy选level最高的规则——但不考虑节点的进展阶段。AI-2的终点节点（已到二次无理数分析阶段）被检索到Q3（"你选择哪个方向？第一步是什么？"），而不是Q9（"badly approximable推出|D|下界"）。Q3的level=1.0比Q9的level=0.2高，所以policy选了Q3——但Q3对AI-2的进展阶段来说太浅了。

在case_253实验中，Q9是手动注入的，不是检索出来的。刚修复PatternMatcher后retrieve_directions能自动检索了，但检索到的是Q3而不是Q9。policy选择逻辑需要改进——不能只看level，还要看节点的进展阶段。

### 7.3 没有tell端识别

Grove没有"tell端识别"的概念。tell是"AI没考虑什么、在哪里可以分叉但没分叉"的分叉信号——从推理AI的thinking中读出tell，然后用tell检索对应的hint。Grove的retrieve_directions直接用节点的situation_text做检索，没有显式的tell识别步骤。

对比Worktree侧的tell+hint二元组理论，Grove缺少：
- **tell的显式定义**——什么是tell，tell的结构是什么
- **tell的穷举**——把tell从题目特化提升到可泛化的Level
- **tell的多对多关系**——一个tell可以对应多个hint，一个hint可以被多个tell触发
- **概念树**——大概念→小概念→概念树的层次化管理，应对tell数量增长

### 7.4 没有QA序列全局视角

Grove的retrieve_directions只看单个节点的situation_text，不看整条脉络的结构特征。对比Worktree侧的292号文档提出的全局视角——在整条QA序列中识别高Level的(tell, hint)，如翻译类型（"枚举→结构"）、知识瓶颈位置、能量传递链、思维模式转换点——Grove没有这种全局视角。

### 7.5 数据基座规模小

Grove的数据基座只有10条hgraph规则（case_253的Q1-Q10），没有规模压力。Worktree侧已经在思考10万级tell的规模检索问题——用Pipe 1形式化过滤缩小范围，用概念树管理概念膨胀。Grove没有这个问题意识。

### 7.6 串行而非并发

Grove当前是串行多AI（一个AI跑完再启动下一个），不是并发多AI。267号面相认知指出阶段3是并发展开——N个推理AI并发，系统实时整理两棵树。Grove还没有实现并发。
