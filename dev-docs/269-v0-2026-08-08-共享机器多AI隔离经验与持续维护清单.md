## 0. 本文档的定位

本文档记录在一台共享机器上，两个AI并发工作时如何做资源隔离的完整经验。它不是一次性迁移记录，而是**持续维护的隔离检查清单**——未来新增任何共享资源使用时，都应回查本文档确认是否需要隔离。

**关联元组**：
- Rule：`.devin/rules/isolation-awareness.md`（always-on触发）
- Skill：`.devin/skills/isolation-audit/SKILL.md`（按需加载的隔离审计工作流）

---

## 1. 问题背景

两个AI在同一台机器上工作：
- **上游AI**：在 `/data/master-mind/` 工作
- **Grove AI**：在 `/data/master-mind-glm5.2-grove/` 工作（从上游clone而来）

如果共享资源不做隔离，两个AI的数据会互相覆盖、互相污染。**最危险的冲突是隐性的**——不会报错，但数据悄悄被破坏。

---

## 2. 隔离层次模型

隔离不是一次性操作，而是多层防御。每层独立失效不影响其他层。

### 层次1：文件系统隔离（最外层）

**原理**：两个AI的代码仓库物理分离，互不写入对方的目录。

**Grove实施**：
- Grove repo：`/data/master-mind-glm5.2-grove/`（D盘HDD）
- 上游 repo：`/data/master-mind/`（D盘HDD，不同目录）
- 旧worktree：`~/master-mind-glm5.2-worktree/`（内置SSD，已废弃）

**关键教训**：clone时必须确认新路径和上游路径**完全不同**，不能只改一个后缀。旧worktree路径 `master-mind-glm5.2-worktree` 和上游 `master-mind` 差异够大，但名字里带 `master-mind` 容易在文档中混淆。

### 层次2：数据库隔离（最关键）

**原理**：两个AI共享同一个ArangoDB实例（`localhost:8529`），通过不同的database name隔离数据。

**Grove实施**：
- Grove数据库：`grove_math`
- 上游数据库：`xishujuzhen_math`

**关键教训**：数据库名必须**完全不同前缀**。之前用 `xishujuzhen_math_glm52`（只比上游 `xishujuzhen_math` 多一个 `_glm52` 后缀），一旦 `source .env` 忘了，代码 fallback 到默认值 `xishujuzhen_math` 就直接写到了上游数据库。改成 `grove_math` 后，前缀完全不同，不可能混淆。

**防御机制**：
1. `.env` 文件设置 `ARANGO_DB=grove_math`
2. 代码用 `os.environ.get("ARANGO_DB", "xishujuzhen_math")`——默认值是上游库名，忘了source .env会fallback到上游（读不冲突，写会冲突）
3. `init_research_runtime_db.py` 有 assert 检查：`assert os.environ.get("ARANGO_DB") == "grove_math"`
4. **未来应改为**：默认值设为一个不存在的库名（如 `DATABASE_NOT_SET`），忘了source .env直接连接失败，而不是静默写到上游

### 层次3：工作目录隔离（Solver/Parser/trajectory）

**原理**：两个AI启动的子进程（Solver、Parser）和产生的数据（trajectory、exports）在不同目录下，不互相覆盖。

**Grove实施**：
| 用途 | Grove路径 | 旧路径（已废弃） |
|---|---|---|
| Solver工作目录 | `/data/grove-agents-dir/` | `/data/math-agent-glm5.2-tmux-agents-dir/` |
| Trajectory存储 | `/data/grove-agents-trajectory/` | `/data/math-agent-glm5.2-tmux-agents-trajectory/` |
| Parser工作目录 | `/data/grove-parser-{1,2,3}/` | `/data/math-agent-glm5.2-parser-{1,2,3}/` |

**关键教训**：旧路径名里带 `glm5.2`，如果上游AI也是GLM-5.2模型，或者上游开始用类似的harness架构，目录名会撞。新路径用 `grove-` 前缀，和上游的 `math-agent-{1,2}` 模式完全不同。

**数据迁移策略**：复制（rsync）而非移动（mv），旧目录保留给正在运行的实验进程。运行中的实验进程的命令行参数里硬编码了旧路径，移动会导致它们的 `--export` 路径失效。等运行中的实验结束后，旧目录可以删除。

### 层次4：进程级隔离（tmux sessions）

**原理**：tmux session名不撞，两个AI的实验进程互不干扰。

**Grove实施**：tmux session命名用 `harness-<exp-id>`，exp-id用 `<dev-docs编号>-<实验名>` 模式（如 `harness-ab-253-A1`、`harness-vms-poc0-baseline-01`）。

**风险**：如果两个AI用了相同的exp-id，tmux session会撞名。但目前上游AI不用harness模式，不存在实际冲突。

### 层次5：网络端口隔离

**原理**：两个AI起的服务用不同端口。

**Grove实施**：
- ArangoDB：共享 `localhost:8529`（通过DB name隔离，不需要端口隔离）
- mitmproxy：共享 `localhost:18889`（launchd系统服务，通过workdir_mapping区分实验）

**风险**：mitmproxy的 `workdir_mapping` 有10秒缓存，如果两个AI在同一秒启动Solver，mapping可能匹配到对方的实验。但实际操作中极不可能发生。

### 层次6：无法隔离的共享资源

**sessions.db**（`~/.local/share/devin/cli/sessions.db`）：Devin CLI的全局session存储，两个AI的所有session都在同一个9GB的SQLite文件里。无法隔离——这是Devin CLI的设计决定的。但实际风险低：所有查询通过session_id过滤，不会读到对方的session。

**Python环境**：Grove用独立 `.venv/`，上游用自己的环境。已隔离。

## 3. 隔离检查清单（新增共享资源时必查）

当Grove AI开始使用一个新的共享资源时，必须过这个清单：

### 3.1 数据库类
- [ ] 是否用了独立的数据库名？（不能只比上游多一个后缀）
- [ ] 数据库名的前缀是否和上游完全不同？
- [ ] `.env` 是否配置了正确的环境变量？
- [ ] 代码的默认值是否安全？（默认值不应是上游的库名——应该是"未设置"标记或一个不存在的库名）
- [ ] 是否有assert检查防止忘source .env？

### 3.2 文件系统类
- [ ] 新目录路径是否和上游的目录路径完全不同前缀？
- [ ] 目录名里是否包含模型名（如 `glm5.2`）？如果上游可能用同一模型，去掉模型名
- [ ] 代码中的路径常量是否已更新？
- [ ] 文档中的路径引用是否已更新？
- [ ] 正在运行的进程是否依赖旧路径？（如果是，复制而非移动）

### 3.3 进程类
- [ ] tmux session命名是否可能和上游撞？
- [ ] 启动的服务端口是否和上游冲突？（起服务前 `lsof -i :<port>` 检查）
- [ ] launchd系统服务是否共享？（如mitmproxy）共享的话是否有区分机制？

### 3.4 全局配置类
- [ ] `~/.mitmproxy/` 中的addon副本是否已同步更新？
- [ ] `~/.config/devin/` 中的全局配置是否需要项目级覆盖？
- [ ] 环境变量是否可能泄漏到上游的进程？（如通过 `.env` source）

## 4. 隔离审计方法

### 4.1 快速检查（每次启动新实验前）

```bash
# 1. 确认数据库
echo $ARANGO_DB  # 应输出 grove_math

# 2. 确认工作目录
ls /data/grove-agents-dir/  # 应存在

# 3. 确认没有写入禁止路径
# 检查最近的git操作只在grove repo内
```

### 4.2 深度审计（定期或新增共享资源时）

执行 `.devin/skills/isolation-audit/SKILL.md` 中的完整审计流程。

## 6. 未来需要关注的隔离风险

### 6.1 上游AI开始用harness模式
如果上游AI也开始用solver-harness启动Solver，tmux session命名和trajectory目录可能冲突。届时需要：
- 上游用 `math-agent-agents-dir/`，Grove用 `grove-agents-dir/`（已隔离）
- 或在exp-id中加入AI标识前缀（如 `grove-ab-253-A1` vs `upstream-poc-1`）

### 6.2 上游AI开始用ArangoDB的新集合
如果上游AI在 `xishujuzhen_math` 中新增集合，Grove的 `grove_math` 不受影响（已隔离）。

### 6.3 Devin CLI升级
Devin CLI升级可能改变sessions.db的schema或位置。升级后需确认trajectory_watcher和thinking_extractor仍能正常工作。

### 6.4 新增第三方服务
如果Grove要起新的HTTP服务、消息队列等，必须检查端口是否和上游冲突。

## 7. 隔离的元认知

**隔离不是一次性工程，而是持续 vigilance。**

每次Grove AI做以下事情时，都应触发隔离意识：
1. 使用一个新的共享资源（新数据库、新目录、新端口）
2. 修改一个路径常量
3. 创建一个新的子进程工作目录
4. 引入一个新的第三方依赖

**隔离失败的最常见模式不是"忘了隔离"，而是"以为已经隔离了但隔离不够强"**——如数据库名只差一个后缀、目录名包含共享的模型名。

**隔离的黄金法则**：两个AI的任何资源标识（库名、目录名、session名、端口）都应**完全不同前缀**，不能只靠后缀区分。
