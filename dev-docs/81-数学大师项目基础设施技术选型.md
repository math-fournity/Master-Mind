# 81-数学大师项目基础设施技术选型

## 背景

本文档是对 79 号文档（星学项目技术选型：ArangoDB）在数学领域的更新。

79 号文档的核心选型是 **ArangoDB**（多模型：图+文档+键值，Apache 2.0），用于存储依赖图、展开图、知识内容、审计报告。该选型在星学领域经过 POC1-8 验证，证明可行。

迁移到数学领域后，需要重新审视：哪些选型仍然适用？哪些需要更新？哪些是数学领域特有的新增组件？

## 一、星学 vs 数学：基础设施需求差异

| 维度 | 星学 | 数学 | 对选型的影响 |
|---|---|---|---|
| 知识来源 | 古籍（有限、封闭、可版本化） | 数学文献（开放、持续增长）+ MathLib（已有形式化依赖图） | 需要文献管道 |
| 依赖图规模 | POC-8 达 71 节点 106 边；预估终态数千~数万节点 | MathLib 本身已有 30 万声明 840 万边；数学知识体系远大于星学 | ArangoDB 仍够用，但数据导入策略不同 |
| 计算底座 | qizheng（星历计算，Python） | SageMath + SymPy + Lean 4（符号计算+形式化证明） | **新增计算工具层** |
| 形式化验证 | 规则库可求值但不形式化 | Lean 4/MathLib 提供形式化证明验证 | **新增证明助手** |
| 已有依赖图 | 需要从零构建 | MathLib 已有 840 万条依赖边（可参考/导入） | **重大利好，改变建设路径** |
| 跨领域映射 | 跨宫（同体系内，命宫→官禄） | 跨数学领域（不同体系间的结构同构，代数↔拓扑↔几何） | 依赖图的新边类型 |
| 知识增长速度 | 古籍固定，吸收是有限任务 | arXiv 每日新增，数学知识持续增长 | 需要持续更新管道 |

## 二、79 号文档选型的适用性判断

### 仍然适用的部分

| 选型 | 理由 |
|---|---|
| **ArangoDB 主数据库** | 多模型（图+文档+键值+向量）对数学同样适用。数学依赖图、知识内容、审计报告、分析结果都可以用一个数据库处理。Apache 2.0 不变。向量索引对数学文献检索更有用 |
| **AQL 统一查询** | 图遍历（依赖路径）+ 文档查询（知识内容）+ 集合差集（拓扑覆盖验证）的需求不变 |
| **拓扑覆盖验证代码化** | 78 号文档的拓扑覆盖方法论与领域无关，数学版同样适用 |
| **SciPy 稀疏矩阵** | 邻接矩阵运算、传递闭包、可达性矩阵的需求不变 |
| **Python 3.14 栈** | 不变 |

### 需要更新的部分

| 原选型 | 更新内容 | 原因 |
|---|---|---|
| 数据规模预估 | 从"数千~数万节点"上调到"数万~数十万节点" | MathLib 本身 30 万声明；数学知识体系远大于星学 |
| 数据导入策略 | 新增"从 MathLib 导入初始依赖图"路径 | 星学是 from scratch；数学可以站在 MathLib 肩膀上 |
| Collections 设计 | 新增数学特有的集合（见下文） | 数学文献、形式化证明、研究案例是星学没有的数据类型 |

### 需要新增的部分

数学领域相比星学，需要三个新的基础设施组件：

1. **形式化证明助手**（Lean 4 + MathLib）——星学没有对应物
2. **符号计算引擎**（SageMath）——对应星学的 qizheng，但复杂度高得多
3. **数学文献管道**（arXiv 接入）——星学的古籍是封闭的，数学文献是开放的

## 三、新增基础设施组件选型

### 3.1 形式化证明助手：Lean 4 + MathLib

**选型**：Lean 4 + MathLib4

**关键事实**（2026-08 搜索确认）：
- MathLib4：190 万行代码，308,129 个声明，8,436,366 条依赖边，7,563 个模块
- 许可证：Apache 2.0
- 覆盖领域：代数、分析、拓扑、几何、数论、范畴论、组合学等
- 已有网络结构分析论文（arXiv:2604.24797），提取了多层依赖图
- 社区活跃，Lean Community 维护

**对项目的三重价值**：

1. **现成的依赖图数据源**：MathLib 的 840 万条依赖边本身就是形式化数学知识的依赖图。可以从中提取：
   - 定理→引理的依赖关系（知识依赖边）
   - 理论模块之间的依赖（领域依赖边）
   - 声明的作用域利用统计（稀疏性证据——开发者中位数仅使用 1.6% 的导入范围）

2. **证明验证器**：AI 提出的证明可以用 Lean 4 验证正确性。这是星学没有的能力——星学的规则只能求值真假，不能验证证明过程。

3. **形式化数学知识库**：MathLib 覆盖了大学到研究生级数学，是 `math-notes/` 知识系统的重要参考来源。

**集成方式**：
```
MathLib (.lean 源码)
  ↓ lean-graph-extractor（待建工具）
  ↓ 提取 declaration 依赖为 JSON
  ↓
ArangoDB (dg_nodes + dg_edges)
  ↓
xishujuzhen 依赖图导航
  ↓ 提示
AI
  ↓ 提出证明
  ↓
Lean 4 验证器 → 验证结果
```

**风险**：
- MathLib 的依赖图是"形式化证明的依赖"，不是"数学思维的依赖"——前者是逻辑前置（A的证明需要B），后者是思维路径（解决这类问题适合用这个工具）。二者有重叠但不相同。不能直接把 MathLib 依赖图等同于 xishujuzhen 依赖图，需要加工和补充。
- MathLib 的 840 万边中包含编译器/工具基础设施的边，不全是数学依赖。网络分析论文指出需要区分"显式边"和"编译器合成边"。

**备选**：Coq（LGPL，社区版）、Isabelle（BSD）。但 MathLib 的规模和社区活跃度远超 Coq/Isabelle 的数学库，且 Apache 2.0 许可证最友好。

### 3.2 符号计算引擎：SageMath

**选型**：SageMath（主）+ SymPy（轻量补充）

**关键事实**（2026-08 搜索确认）：
- SageMath：整合 90+ 开源数学包（NumPy, SciPy, Maxima, SymPy, GAP, FLINT, PARI/GP, Singular, Polymake, R, NetworkX...）
- 许可证：GPL+（作为服务调用不传染）
- 研究级数学计算的标准工具，数论/组合/群论/代数几何领域广泛使用
- 已有 LLM+SageMath 研究先例（arXiv:2607.06820，SageMath-Augmented LLM Agents）
- 部署：本地安装或 CoCalc 云端

**对项目的价值**：
- 对应星学中的 `qizheng/`——提供精确计算原料
- AI 需要验证猜想时，调用 SageMath 做符号计算/数值实验
- SageMath 整合了 GAP（群论）、PARI/GP（数论）、Singular（代数几何）等专业工具，覆盖面远超 SymPy

**三层验证器阶梯**（借鉴 SPL 论文 arXiv:2607.07727）：

| 层级 | 工具 | 验证能力 | 适用场景 |
|---|---|---|---|
| L1 代数验证 | SymPy | 基本代数化简、等式检验 | 快速验证代数恒等式 |
| L2 数学验证 | SageMath | 研究级符号计算、数值实验 | 验证猜想、寻找反例 |
| L3 形式化证明 | Lean 4 | 完整证明的形式化验证 | 验证证明过程正确性 |

AI 提出一个数学断言后，可以按需选择验证层级：快速检验用 SymPy，研究级验证用 SageMath，完整证明用 Lean 4。

**集成方式**：
```
AI 提出数学断言
  ↓
xishujuzhen 判断需要哪个层级的验证
  ↓
L1: SymPy（进程内调用，毫秒级）
L2: SageMath（Jupyter kernel 或 Sage CLI，秒级）
L3: Lean 4（lean --check，秒~分钟级）
  ↓
验证结果回传 AI
```

**与 qizheng 的对应关系**：

| 星学 qizheng | 数学 SageMath |
|---|---|
| 星历计算（行星黄经） | 符号计算（代数运算） |
| 宫位推算 | 数值实验（猜想验证） |
| 大限起算 | 群论/数论计算 |
| 矫正求解 | 反例搜索 |
| 不做命理判断 | 不做数学判断 |
| 提供数值原料 | 提供计算原料 |

### 3.3 数学文献管道：arXiv HTML 接入

**选型**：arXiv OAI-PMH（元数据）+ arXiv HTML Papers（全文）+ ArangoDB 向量索引

**关键事实**（2026-08 搜索确认）：
- arXiv 支持 OAI-PMH 协议批量元数据收割，每日更新
- 数学是 arXiv 主要分类之一（math.* 子分类）
- **arXiv 自 2023 年起官方提供 HTML 版本**（arXiv HTML Papers），每篇新提交的 TeX/LaTeX 论文自动生成
- HTML 版本使用 **LaTeXML** 转换，携带 **MathML**（不是图片公式），数学结构对机器直接可读
- 历史语料库通过 **ar5iv.org** 提供 HTML 版本（约 75% 的历史论文已转换，25% 转换失败）
- 元数据包含：标题、作者、摘要、arXiv 分类、MSC 分类、DOI

**为什么用 HTML 而不是 PDF**：

| 维度 | PDF | HTML + MathML |
|---|---|---|
| 公式表示 | 图片/矢量图形，需 OCR | MathML 标记，机器直接可读 |
| 结构解析 | 需要版面分析，易出错 | 标准 DOM 解析（BeautifulSoup/lxml） |
| 定理/证明提取 | 极难，需 NLP+版面理解 | 可按 HTML 语义结构提取（section/theorem/proof） |
| 引用关系 | 需解析参考文献页 | 超链接直接可提取 |
| 跨论文链接 | 无 | 引用可解析为 arXiv ID 间的边 |
| 存储 | 大（几 MB/篇） | 小（几十 KB~几百 KB/篇） |
| 可访问性 | 差（arXiv 的初衷就是改善这个） | 好（W3C 标准） |

**核心优势**：HTML+MathML 暴露了数学结构——定理陈述、证明步骤、公式层级都可以用 DOM 解析器程序化提取，不需要公式 OCR 或版面分析。这对构建依赖图至关重要：可以从论文 HTML 中直接提取"这个定理依赖哪个引理""这个证明用了什么方法"，而不需要理解 PDF 的视觉版面。

**对项目的价值**：
- 星学的古籍是封闭的（星平会海+星学大成，两本书），可以"冻结边界"
- 数学的文献是开放的，arXiv 每日新增——需要一个持续更新管道
- 新论文可能包含新的数学知识、新的依赖关系、新的跨领域映射
- HTML 版本的 MathML 结构让自动化提取成为可能，这是 PDF 路径做不到的
- 向量索引（ArangoDB 原生支持）可以用于语义检索相关论文

**集成方式**：
```
arXiv OAI-PMH（每日收割新论文元数据）
  ↓
ArangoDB papers 集合（标题/摘要/分类/作者/DOI）
  ↓
ArangoDB 向量索引（摘要 embedding）
  ↓
AI 研究时语义检索相关论文
  ↓
按需获取全文：arXiv HTML 版本（https://arxiv.org/html/<id>）
  ↓
DOM 解析（BeautifulSoup/lxml）+ MathML 提取
  ↓
提取定理陈述、证明结构、引用关系 → 更新依赖图
```

**ar5iv 备用路径**：对于历史论文（2023 年前提交，不在 HTML Papers 实时管道中），通过 ar5iv.org 获取 HTML 版本。约 75% 覆盖率，未覆盖的 25% 回退到 PDF+OCR（低优先级，按需处理）。

**与星学的关键差异**：
- 星学：知识来源是古籍 → 人工吸收 → study-notes（封闭任务，可完成）
- 数学：知识来源是 arXiv HTML + MathLib + 教材 → 持续管道 → math-notes（开放任务，持续增长）

这意味着数学版的知识系统不能预设"某个版本可以冻结边界"——数学知识是持续增长的。但每个版本仍然可以冻结当前的研究边界（"本版本覆盖到哪些领域、哪些定理"），只是边界会持续扩展。

## 七、成本与风险

### 新增成本

| 组件 | 磁盘 | 内存 | 复杂度 |
|---|---|---|---|
| ArangoDB | ~1GB（当前规模） | ~512MB | 低（Docker） |
| Lean 4 + MathLib | ~5-10GB（完整构建） | ~4GB（编译时） | 中（构建时间长） |
| SageMath | ~1-2GB | ~512MB | 低（包管理器安装） |
| arXiv 元数据 | ~100MB（纯元数据） | 低 | 低（OAI-PMH） |

### 关键风险

| 风险 | 缓解 |
|---|---|
| MathLib 依赖图 ≠ 思维依赖图 | 明确区分"证明依赖"和"思维依赖"；MathLib 是参考数据源，不是 xishujuzhen 依赖图本身 |
| Lean 4 学习曲线陡 | 前期可以只用 MathLib 的依赖图数据，不写新形式化证明；后期逐步引入 |
| SageMath GPL 许可证 | 作为外部服务调用（子进程或 Jupyter kernel），不链接进项目代码，不传染 |
| arXiv 数据量持续增长 | 只存元数据和 embedding，不存全文 HTML；全文按需从 arXiv HTML 版本获取 |
| ar5iv 历史覆盖不全（约 75%） | 未覆盖的 25% 回退到 PDF+OCR，低优先级按需处理；新论文全部有官方 HTML 版本 |
| 数学知识体系过于庞大 | 从一个领域切入（如代数拓扑），逐步扩展；不要试图一次性覆盖全部数学 |
