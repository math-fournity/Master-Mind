>
> 话题关键词：数学大师、系统边界、知识架构、依赖图、上下文编译、研究运行、数学验证、认知演化

## 为什么记录

项目已经积累了从 80 号到 121 号的大量方案、POC、知识资产、图数据库和工作系统代码。但这些成果分布在不同文档和不同技术支线里：

- 80、81 号讨论数学大师的能力和技术选型；
- 82、83、107 号讨论题库与 L1/L2/L3 三层提取；
- 86、88、99、100 号讨论七步骤工作流、经典计算展开与认知反哺；
- 109、110、112 号讨论全知识宇宙、大规模访问和 arXiv 冷存储；
- 89—104 号建设的是管理 AI 工作过程的认知图系统；
- 84—121 号持续运行不同 POC，但近期又发现答案泄漏、单次实验和审计证据不足等问题。

现在的问题不是“有没有组件”，而是：这些组件是否共同构成了一套边界清楚、数据一致、能够端到端做数学研究的系统？

本调查从最大的框架开始，不试图一次解决所有细节。它先回答五个问题：

1. 数学大师系统究竟是什么，不是什么？
2. 完整系统应该由哪些平面、层和闭环组成？
3. 当前已经实现了什么，哪些仍停留在方案或 POC？
4. 现有架构最危险的断层和概念混用在哪里？
5. 下一轮应该按什么顺序继续梳理？

---

## 摘要

### 一句话结论

**当前项目已经拥有较强的知识收集能力、图数据库原型、POC方法和工作认知控制面，但尚未形成完整的数学研究运行系统。真正缺失的核心是：一条稳定的“问题理解 → 数学知识召回 → 依赖子图构造 → 上下文编译 → AI研究 → 数学工具验证 → 结果审计 → 认知回写”端到端主链。**

### 最重要的五个发现

1. **架构碎片已经很多，但中心链路没有闭合。** 七步骤脚本只有步骤1—3真正执行；步骤4—7只是打印“待AI执行”。数据库中的 `prompts`、`analyses`、`audits`、`uf_nodes`、`uf_edges` 目前全部为0。
2. **知识资产不等于可工作的数学知识。** ArangoDB已有239472篇arXiv元数据，但全部仍是L4索引级；1719个数学图节点中只有18个独立KC记录，1683个节点没有内嵌KC。系统大部分时候只知道“有这个名字”，不知道可供研究使用的完整内容。
3. **依赖图已经发生模式分裂。** 早期POC边使用 `from_node_id/to_node_id/edge_type`，题库边使用 `_from/_to/type`。1431/1483条边没有 `edge_type` 和命名端点。当前拓扑覆盖只有节点99.4%、边79.0%，验证失败。
4. **大规模召回与上下文编译仍是纸面架构。** 110号提出的层次索引、embedding、语义检索、token预算子图提取、按需查询协议均没有对应实现文件。当前 `cognition_sdk_math.py` 的图遍历主要服务工作认知图，不是325000节点数学图的在线研究召回器。
5. **工作系统比数学大师目标系统更成熟。** CP1—CP6、认知版本链、Hook、回归验证和文档纪律已经可用；但这套控制面不能代替数学知识建模、在线召回、研究执行和数学真值验证。

## 一、先确定系统边界

### 1.1 数学大师系统是什么

数学大师系统不是一个单独模型，也不是一张巨大的知识图。它应当是一个围绕 AI 研究者建立的**数学研究认知操作系统**：

- 保存可追溯的数学知识；
- 显式记录“什么时候该想到什么”的依赖与调用关系；
- 面对具体问题，只激活相关子图；
- 把子图编译成 AI 能稳定使用的研究上下文；
- 让 AI 执行判断、猜想、证明和跨领域类比；
- 调用符号、数值和形式化工具检验关键步骤；
- 保存结果、失败和新发现，并更新知识与依赖图。

它的核心价值仍然是项目最初的信念：

> 系统不替 AI 判断，而是工程化“知道此刻该判断什么”。

证据：`dev-docs/80-数学大师项目启动认知基础.md:13-43,47-100`；`AGENTS.md:23-109`。

### 1.2 数学大师系统不是什么

它不是：

1. **数学资料仓库**：收集60万条材料不等于会做研究；
2. **普通RAG**：只找相似文档，没有给出思维依赖和工具路径；
3. **自动定理证明器**：Lean等工具负责验证，不负责研究方向与品味；
4. **专家规则系统**：系统不把数学判断写成固定if/then规则；
5. **POC集合**：一系列对照实验只能验证局部假设，不能代替产品运行架构；
6. **工作认知图**：管理AI怎么工作，与管理数学知识是两套不同职责；
7. **星学MOIRA运行时**：星学资产是方法论来源，不是数学大师系统本体。

### 1.3 最终使用者应该看到什么

从使用者视角，完整系统至少应支持以下入口：

- “帮我探索这个数学问题可能从哪里切入”；
- “给出候选猜想，并说明应做哪些数值、反例或极端检验”；
- “组织一条可验证的证明路线”；
- “告诉我这个问题与哪些领域存在结构对应”；
- “在研究中按需展开某个概念、定理、方法或论文”；
- “标出哪些步骤已证明、哪些只是猜测、哪些被工具验证”；
- “把这次研究产生的新知识、新边和失败案例吸收回系统”。

当前项目主要验证了前四项的局部POC，尚没有稳定的统一入口和完整研究会话生命周期。

## 二、完整架构的最高层：三个平面

为了避免继续把所有东西塞进“依赖图”一个词里，整个系统应先分成三个平面。

### 2.1 知识平面

**人话解释**：这是数学大师“知道什么”的部分。

它负责：

- 原始文献、教材、题目、证明、数学家工作和开放问题的存档；
- 定义、定理、方法、反例、研究案例、意识和范式的规范化；
- 依赖边、工具适用边、跨领域映射边和证据来源；
- 版本、出处、可信度、适用条件和冲突关系。

它不负责执行一轮具体研究。

### 2.2 研究运行平面

**人话解释**：这是数学大师“面对这个问题，现在怎么工作”的部分。

它负责：

- 理解和结构化用户问题；
- 从知识平面定位种子；
- 提取当前问题的依赖子图；
- 把子图和知识内容编译成上下文；
- 让 AI 在上下文中提出猜想、组织证明、调用工具；
- 保存本轮研究状态、分支、证据、结论和未决点。

### 2.3 控制平面

**人话解释**：这是“如何保证前两个平面长期不失控”的部分。

它负责：

- 认知图、CP1—CP6、AGENTS、dev-docs和版本链；
- POC设计、盲评、答案泄漏审计和回归验证；
- 数据模式迁移、图版本、证据归档和质量门；
- AI执行者、审计者和工具之间的职责分离。

当前89—104号工作系统主要属于控制平面。它很重要，但它不能代替知识平面和研究运行平面。

### 2.4 三个平面的关系

```text
┌──────────────────────── 控制平面 ────────────────────────┐
│ 版本 / 审计 / POC / CP1-CP6 / 文档 / 回归 / 权限 / 证据 │
│                                                         │
│  ┌────────────── 知识平面 ──────────────┐               │
│  │ 原始证据 → 规范知识 → 数学依赖图     │               │
│  │ 定理/方法/反例/意识/范式/研究案例     │               │
│  └─────────────────┬───────────────────┘               │
│                    │ 召回相关知识与子图                  │
│  ┌─────────────────▼───────────────────┐               │
│  │            研究运行平面              │               │
│  │ 问题理解 → 子图提取 → 上下文编译     │               │
│  │ → AI研究 → 工具验证 → 结果与新认知   │               │
│  └─────────────────┬───────────────────┘               │
│                    └───── 回写知识平面 ──────────────────│
└─────────────────────────────────────────────────────────┘
```

## 三、知识平面：从材料到可工作的数学认知

知识平面不是一层，而是四层。

### 3.1 K0：证据资产层

**它是什么**：不改写原始事实的材料库。

包括：

- arXiv元数据和全文；
- 教材、专著、数学家全集、习题集；
- 竞赛题、数学杂志问题栏；
- MathLib、Coq、Mizar等形式化库；
- OEIS、DLMF、nLab等数据库；
- 历史证明、失败路线和研究过程记录。

109号把来源扩展为十三类，估计60万条目、325000个知识节点。这个范围是知识宇宙地图，不是当前实现规模。证据：`dev-docs/109-数学大师全知识宇宙-穷尽式知识地图v3.md:796-830`。

**当前状态**：

- arXiv元数据239472篇已入库；
- 1305篇有本地全文；
- 题库有60道题、159个解法；
- 其他十二类来源大多仍是目录规划或少量文件；
- `math-notes/` 尚不存在。

### 3.2 K1：规范数学知识层

**它是什么**：把材料中的数学内容变成可以查询、比较和验证的规范对象。

至少包括：

| 对象 | 必需字段 |
|---|---|
| 定义 | 对象类型、输入、输出、等价定义、适用域、来源 |
| 定理/引理 | 前提、结论、量词、依赖、证明状态、来源 |
| 证明 | 目标、策略、步骤、使用定理、验证状态 |
| 方法/工具 | 适用条件、输出、失败条件、案例 |
| 反例 | 反驳命题、最小反例、适用边界、来源 |
| 开放问题 | 已知结果、未决部分、失败路线、更新时间 |
| 研究案例 | 问题、关键转折、调用工具、判断依据、结果 |
| 数学意识 | 何时触发、做什么检查、适用边界、实证案例 |
| 范式 | 连接哪些领域、改变哪些边、证据和反例 |

81号曾设计 `theorems/proofs/counterexamples/research_cases/cross_domain_maps` 等集合，但当前数据库中这些集合并不存在。证据：`dev-docs/81-数学大师项目基础设施技术选型.md:233-267`。

### 3.3 K2：数学依赖图层

**它是什么**：不是保存长篇知识，而是保存知识对象之间“该如何一起被激活”的关系。

建议区分以下关系家族：

1. **逻辑依赖**：`requires / proves / refutes / generalizes / specializes`；
2. **解法路径**：`next_step / transforms_to / reduces_to`；
3. **工具关系**：`uses / verified_by / computes_with`；
4. **意识调用**：`invokes_awareness`；
5. **跨领域关系**：`analogous_to / equivalent_view / dual_to / transfers_to`；
6. **证据关系**：`supported_by / extracted_from`；
7. **版本关系**：`supersedes / refines / contradicts`。

每条边至少需要：

- 统一类型；
- 合法起点和终点类型；
- 来源或实证；
- 置信度/审核状态；
- 适用上下文；
- 创建版本；
- 失效条件。

当前图把POC证明边、题库解法边、跨领域边和指向认知图的意识调用边混在一个 `dg_edges` 集合里，但端点和字段模式并不统一，这是后文的核心问题。

### 3.4 K3：可供提示使用的知识内容层

**它是什么**：当某个图节点被激活时，真正交给AI阅读的内容。

图节点名称只是索引；AI还需要：

- 定义或定理正文；
- 为什么与当前问题有关；
- 适用条件；
- 常见陷阱；
- 可调用工具；
- 证据定位；
- 内容分辨率版本。

现有 `kcs` collection承担这个角色，但当前只有18条；1719个 `dg_nodes` 中1683个没有内嵌KC。这意味着当前大图主要是一张“名称和关系图”，不是完整的可读知识系统。

## 四、研究运行平面：真正应该闭合的在线主链

### 4.1 R0：问题接入与任务建模

系统首先要把用户问题转换为结构化研究任务：

- 数学对象是什么；
- 前提、结论和量词是什么；
- 是求证、反驳、构造、猜想、分类、估计还是研究导航；
- 涉及哪些领域和表示方式；
- 哪些信息已知、哪些不确定；
- 成功条件和允许使用的工具是什么。

当前种子推荐表只覆盖五类通用意识种子，主要服务工作认知图。它不是完整的数学问题解析器。

### 4.2 R1：数学种子定位

系统应从问题中找到最初的数学节点。完整机制可包含：

1. 领域/主题索引定位；
2. 符号、定义和定理精确匹配；
3. 数学语义检索；
4. 已知问题/研究案例匹配；
5. 数学意识种子补充。

110号设计了“层次索引 → embedding语义检索 → 图遍历”的三级机制，但对应的七个工具文件目前都不存在。证据：`dev-docs/110-大规模依赖图可操作性方案-三层访问架构.md:141-168,435-472`。

### 4.3 R2：依赖子图提取

从种子开始，系统需要提取一张受预算控制的子图，而不是加载整个数据库。

子图提取至少要考虑：

- 图遍历深度；
- 依赖边优先级；
- 证据质量；
- 节点分辨率；
- 螺旋环路完整保留；
- 跨领域边保留；
- token预算；
- 可回溯的剪枝理由。

110号把它描述为冷存储、热工作集和温查询三层访问架构。当前冷存储部分存在，热工作集和按需温查询仍未成为完整运行组件。证据：`dev-docs/110-大规模依赖图可操作性方案-三层访问架构.md:69-167,480-497`；`dev-docs/112-arXiv论文导入ArangoDB与节点映射规则方案.md:180-188`。

### 4.4 R3：上下文编译器

**上下文编译器**是本调查提出的核心架构名称：它把“机器可查询的数学子图”变成“AI此刻能可靠使用的研究上下文”。

它不是普通prompt模板。它必须完成：

1. 决定节点展开顺序；
2. 决定每个节点使用哪种内容分辨率；
3. 把边翻译成明确的思考关系；
4. 保留分叉、汇聚和反馈环；
5. 标注事实、猜测、意识、工具和警告；
6. 记录每段文字来自哪个节点和证据；
7. 在token预算内删减，但保留删减清单；
8. 生成可审计的“上下文包”。

现有 `topo_generator.py` 实现了L0结构复制、L1类型推断和L2章节推荐，是上下文编译器的**结构骨架生成器**，不是完整上下文编译器。`uf_nodes`、`uf_edges` 和 `prompts` 为空，说明完整文字展开尚未进入主运行链。

### 4.5 R4：AI研究执行器

AI研究执行器负责真正的数学判断：

- 沿多个候选路径探索；
- 提出猜想和子目标；
- 组织证明；
- 主动请求展开更多知识；
- 记录失败分支；
- 区分已知事实、推导结果和猜测；
- 决定何时调用数值、符号或形式化工具。

项目原则“系统不做判断，AI做判断”在这里落地。

当前没有统一的研究会话对象、分支状态、查询协议或执行器。主要运行方式仍是把材料交给独立Agent完成一次回答。

### 4.6 R5：数学工具验证器

81号提出三层验证器阶梯：

- 快速符号/数值检查；
- SageMath等更强计算；
- Lean 4等形式化证明。

本机已能找到 `lean`、`lake` 和 `sage`，但项目 `.venv` 中没有SymPy、NumPy、SciPy，`xishujuzhen/*.py` 也没有把Lean/Sage/SymPy接入研究运行链的代码。

完整工具层应输出统一的验证记录：

- 验证了哪个命题；
- 使用什么工具和版本；
- 输入是什么；
- 输出是什么；
- 是证明、反例、数值支持还是仅语法检查；
- 能否复现；
- 失败意味着什么。

### 4.7 R6：结果、证据和研究状态

最终输出不应只是一段Markdown答案。应形成一次**研究运行记录**：

```text
research_run
├── problem_model
├── selected_seeds
├── extracted_subgraph
├── compiled_context
├── reasoning_branches
├── tool_calls_and_evidence
├── claims
│   ├── proven
│   ├── computationally_verified
│   ├── conjectured
│   └── unresolved
├── final_output
└── audit_report
```

当前数据库已经预留 `prompts/analyses/audits`，但三者均为空，说明这个运行对象还没有真正实现。

## 五、控制平面：保证系统不会边长边坏

### 5.1 C0：工作认知图

当前项目有两套图：

| 图 | 管什么 | 当前规模 | 主要代码 |
|---|---|---:|---|
| 数学依赖图 | 数学知识、解法、意识调用、跨领域关系 | 1719节点、1483边 | `dg_nodes/dg_edges`, `topo_generator.py`, `topology_verifier.py` |
| 工作认知图 | AI如何维护项目、执行流程和跨Session恢复 | 163单元、45边、178版本 | `cognition_*_math.py`, Hook, AGENTS |

工作认知图是控制面，不应成为数学知识本体。

意识节点可以在两边有对应记录，但必须明确：

- 工作认知图中的意识节点：告诉执行AI“工作前要加载什么思维”；
- 数学依赖图中的意识节点：表示某类数学问题会调用这种意识；
- 两者需要稳定ID映射和同步规则，不应直接靠重复手工维护。

### 5.2 C1：质量与证据门

至少需要四种不同验证，不能混为一谈：

| 验证 | 回答的问题 | 当前状态 |
|---|---|---|
| 模式验证 | 数据字段和端点是否合法 | 不完整，存在两套边模式 |
| 拓扑覆盖 | 展开图是否覆盖原图节点和边 | 工具已实现，但当前全图验证失败 |
| 语义忠实 | 提示是否忠实表达KC和边语义 | 主要依赖人工/AI审计，主集合为空 |
| 数学正确 | 定理、推导和结论是否正确 | 尚未接入统一工具链 |

TopologyVerifier只能证明“复制没有漏点漏边”，不能证明节点内容正确、依赖边合理或数学结论为真。

### 5.3 C2：POC与评估

POC的职责是验证架构假设，而不是代替架构：

- 依赖图提示是否产生增量；
- L2/L3是否可迁移；
- 上下文编译是否优于裸JSON；
- 召回子图是否命中关键节点；
- 工具验证是否减少错误；
- 结果是否可重复。

121号已经把答案泄漏审计、重复A/B运行和完整过程证据纳入POC方法。这个标准应扩展到所有后续架构POC。

### 5.4 C3：版本、快照和迁移

系统至少需要区分：

1. **规范生产图**：经过审核、供真实研究使用；
2. **实验图快照**：某个POC固定使用的输入；
3. **候选图**：新提取但未审核的节点和边；
4. **展开图**：某次研究运行生成的上下文结构；
5. **历史版本**：可回放、可比较、可回滚。

当前POC脚本和题库数据直接写入同一 `dg_nodes/dg_edges`。`import_math_graph_to_arangodb.py:14-18` 甚至会清空四个核心集合后重新导入POC-2图。这说明生产数据、实验快照和导入工具的边界尚未建立。

### 5.5 C4：项目文档和跨Session记忆

这一部分当前最成熟：

- `AGENTS.md` 保存项目定位、索引、TODO和跨Session认知；
- `dev-docs/` 保存方案、实验和调查；
- CP1—CP6加载与回写认知；
- post-commit Hook提醒检查依赖、术语、SDK和文档；
- 认知图版本链保存方法论演化。

但要注意：文档里写“已设计”不等于代码“已实现”，代码“能运行一次”也不等于成为稳定架构组件。

## 六、三条必须闭合的系统循环

### 6.1 离线知识生产循环

```text
材料进入
→ 原文存档与许可/来源记录
→ 数学对象和命题解析
→ K1规范知识对象
→ L1具体路径提取
→ L2意识抽象
→ L3范式候选
→ 数学与来源审计
→ 候选图
→ 人工/高质量AI审核
→ 生产图
→ 回归验证
```

当前状态：原文存档、题库三层提取和部分图导入存在；规范对象、审核门、候选/生产分区和数学工具验证没有闭合。

### 6.2 在线数学研究循环

```text
问题输入
→ 问题建模
→ 数学种子定位
→ 依赖子图提取
→ 上下文编译
→ AI多分支研究
→ 按需查询与工具验证
→ 结论分级
→ 结果审计与输出
```

当前状态：主要以人工选择依赖图和独立Agent回答的POC形式存在，尚未形成统一运行时。

### 6.3 研究后认知演化循环

```text
研究结果/失败/卡点
→ 提取新知识、新边、新反例或边界
→ 证据与质量审计
→ 更新候选图和版本
→ 跑已有POC回归
→ 合格后发布到生产图
```

当前状态：工作认知图的版本链已经可用；数学依赖图的节点版本、边版本、发布流程和回滚机制仍不完整。

## 十、当前架构的十六个结构性问题

### P0-1：没有闭合的产品主链

问题、召回、上下文编译、AI执行、工具验证和结果回写没有由一个运行时统一管理。现在是“人工拼装POC”，不是系统运行。

### P0-2：数学图没有规范模式

早期POC和题库使用两种边字段；节点也同时存在中文类型、英文类型、缺domain、缺source和缺KC。没有模式版本、迁移器和发布门。

直接后果：TopologyVerifier当前失败，TopoGenerator对1431条题库边生成空命名端点。

### P0-3：图节点与知识内容脱节

1719节点只有18条独立KC。节点数量增长快于可读、可验证知识内容，图正在趋向“标签网络”。

### P0-4：上下文编译器缺失

`topo_generator`只保证结构复制。谁选择节点内容、处理分辨率、编译边语义、管理token、记录裁剪和生成可审计prompt，目前没有完整组件。

### P0-5：七步骤只有前三步工程化

`seven_step_pipeline.py:112-165` 的步骤4—7只打印待办。系统不能自动生成 `unfold_full`、prompt、分析和审计记录。

### P0-6：数学验证工具与AI研究脱节

Lean/Sage存在于机器环境，但没有统一适配器、命题输入格式、验证证据格式和失败解释。

### P1-1：知识宇宙与可用知识被混为一谈

239K论文入库很有价值，但它们只是索引资产。把“论文数量”或“节点数量”当作大师能力，会掩盖激活、规范化、依赖建模和验证的缺失。

### P1-2：多个“三层/L1-L3”发生命名碰撞

当前至少有四套互不相同的L层：

| 名称 | 实际含义 |
|---|---|
| 三层验证器 | SymPy → SageMath → Lean |
| 三层提取 | L1具体路径 → L2意识 → L3范式 |
| 论文映射级别 | L1定理 → L2方法 → L3意识 → L4索引 |
| TopoGenerator层 | L0骨架 → L1类型 → L2章节 → L3语义 |

此外还有三图 `G/G'_topo/G'_full` 和冷/热/温三层。跨Session时极易误解，必须命名空间化。

### P1-3：多套“工作流”没有统一版本

- 86号七步骤：导入、规划、验证、转译、KC审计、分析、覆盖审计；
- 99/100号升级：步骤2改为经典计算+AI语义细化；
- 110号又给出“步骤0—5”的大规模访问版；
- 工作系统另有CP1—CP6。

需要统一命名为不同协议，不能都叫“七步骤工作流”。

### P1-4：数学图和工作图边界被穿透

`dg_edges` 的 `invokes` 边有260条直接指向 `cognition_units`，但ArangoDB `dependency_graph` 的edge definition只允许 `dg_nodes → dg_nodes`。代码通过直接写edge collection绕过图定义，说明“双重身份”尚未形成明确的跨图协议。

### P1-5：POC数据与生产图没有隔离

题库、POC-2、POC-4/5等数据累计在同一图里；旧导入脚本还会清空核心集合。缺少实验快照、候选图、生产图和迁移版本。

### P1-6：结构覆盖容易被误称为数学验证

96号已经诚实指出：当前所谓HoTT/拓扑覆盖实际是集合差集，不是HoTT证明。结构100%覆盖也不能证明语义正确。证据：`dev-docs/96-诚实评估与未来-数学项目工作系统.md:123-158`。

### P1-7：L2/L3提取质量没有稳定审核器

POC-3中L3审计只有1/2通过，而且C组材料直接给了组合↔拓扑映射。说明“范式提取”本身可能制造看似深刻但不可靠的边。证据：`dev-docs/106-大师-POC-3验证结果.md:55-68,105-114,140-150`。

### P1-8：旧星学运行时仍在项目控制路径中

本轮 `tools/moira_runtime.py capsule` 返回 `REVIEW_REQUIRED`，其硬锚点仍声明“MOIRA是七政四余排盘、矫正星盘项目”。`ai-runtime/protocol/agent-anchors.json:6-10` 也保留该定义。

这套旧运行时不是数学大师控制面，应当隔离、迁移或显式标记为星学遗留，避免它向数学任务发出错误治理指令。

### P2-1：单点数据库与硬编码配置

ArangoDB是单点依赖，多个脚本硬编码连接信息。缺少环境配置、备份/恢复、迁移和只读审计账户。

### P2-2：来源、许可和证据等级没有统一模型

109号覆盖大量书籍和数据库，但不同来源的许可、可复制范围、引用定位和可信度不同。当前 `source` 多为一个字符串，不能支撑大规模审计。

## 十一、纠偏后的总体架构原则

### 原则1：先建主链，再继续扩大节点规模

在产品主链闭合前，继续从1719扩到325000节点只会放大模式和质量问题。

### 原则2：原始材料、规范知识、依赖图和运行产物必须分层

- 原始材料保留证据；
- 规范知识承担数学语义；
- 依赖图承担激活关系；
- 运行产物属于某次研究，不直接污染生产知识。

### 原则3：生产图、候选图和实验快照必须分开

任何POC都使用冻结快照；任何新提取先进入候选区；只有通过模式、来源、语义和回归门才发布到生产图。

### 原则4：上下文编译器是核心产品组件

依赖图本身不是提示词。子图如何在token预算内变成可追溯、可操作的上下文，是系统真正把“经典计算”连接到AI判断的桥。

### 原则5：结构正确、语义忠实、数学正确是三件事

三者必须分别验证，不允许用100%节点覆盖代替数学正确性。

### 原则6：AI创造候选，工具和证据决定可信等级

AI可以提出新边、新猜想和新范式，但不能直接把它们发布成已证知识。

### 原则7：失败和反例必须成为一等资产

真正的研究系统不只吸收成功证明，还要保存：

- 无效路线；
- 错误猜想；
- 反例；
- 失败工具调用；
- 提示泄漏；
- 适用边界。

### 原则8：工作系统服务数学系统，而不是取代数学系统

控制面做到100/100，不等于数学大师已经具备100分研究能力。

## 十二、建议的架构主干

完整系统可以收敛到以下八个正式组件，而不是继续按文档编号自然生长：

| 组件 | 核心职责 | 当前承接物 |
|---|---|---|
| 1. Evidence Registry | 原始来源、许可、定位、哈希、版本 | `knowledge/`, `arxiv_papers` |
| 2. Math Knowledge Core | 定义/定理/证明/方法/反例/问题的规范对象 | 目前缺失，部分散在problems/solutions/kcs |
| 3. Math Dependency Graph | 知识激活关系、意识调用、跨领域映射 | `dg_nodes/dg_edges/loops` |
| 4. Retrieval & Subgraph Engine | 问题解析、种子选择、召回、剪枝、按需展开 | 110号方案，未实现 |
| 5. Context Compiler | 子图→可审计研究上下文 | `topo_generator`只是骨架 |
| 6. Research Runtime | AI分支研究、状态、工具调用、结果分级 | 目前靠人工Agent编排 |
| 7. Verification & Audit | 模式、拓扑、语义、数学、实验验证 | 多个局部工具，未统一 |
| 8. Governance & Evolution | 版本、发布、POC、认知图、文档、回归 | 当前最成熟 |

### 组件之间的正式主链

```text
Evidence Registry
      ↓ 提取与审核
Math Knowledge Core
      ↓ 建边与版本发布
Math Dependency Graph
      ↑                     用户问题
      └──── Retrieval & Subgraph Engine
                            ↓
                     Context Compiler
                            ↓
                     Research Runtime
                      ↙           ↘
       Verification & Audit       研究输出
                      ↘           ↙
                    Governance & Evolution
                            ↓
                 回写候选知识与候选边
```

## 十三、下一阶段如何继续梳理

这次只完成大框架。后续不应直接开工重写全部代码，而应按架构依赖顺序逐层调查。

### 调查A：统一词汇和系统边界

目标：解决L1/L2/L3、三层、七步骤、两套图等命名冲突。

产物：架构词汇表、系统上下文图、组件责任矩阵。

### 调查B：规范数学知识与图模式

目标：定义唯一的节点、边、证据、版本、状态和端点规则。

重点：

- POC旧模式和题库模式如何迁移；
- `invokes_awareness`跨图关系如何合法建模；
- 生产图、候选图、实验快照如何分离；
- 模式迁移和回滚怎么做。

### 调查C：最小端到端研究主链

目标：不追求大规模，先用一个小而真实的问题闭合：

```text
问题建模 → 子图召回 → 上下文编译 → AI研究
→ 至少一次工具验证 → 结果分级 → 审计 → 回写候选认知
```

这是整个系统是否成立的最关键架构POC。

### 调查D：数学真值与证据架构

目标：统一SymPy/Sage/Lean、数值实验、文献证据和人工审核的结果格式。

### 调查E：大规模召回和token预算

只有在规范模式和小链闭合后，再实现110号的层次索引、语义检索、子图剪枝和按需查询。

### 调查F：长期评估体系

从单题单次POC升级为：

- 能力维度矩阵；
- 多问题、多领域、多次运行；
- 冻结输入和完整过程证据；
- 错误类型和失败率；
- 版本间回归；
- 成本与上下文预算。

## 十四、本轮不做的决定

为了避免“大框架调查”再次变成一次性总设计，本轮暂不决定：

1. 规范知识最终使用ArangoDB、文件还是双写；
2. 数学embedding模型选型；
3. 研究运行时使用单Agent、多Agent还是混合编排；
4. Lean、Sage和SymPy的具体适配API；
5. 325000节点是否仍是合理终态规模；
6. 是否保留HoTT命名；
7. 旧MOIRA运行时如何迁移。

这些都需要在后续专项调查中用证据决定。

## 十五、结论 / 决策

1. **数学大师系统必须被定义为三平面、八组件、三闭环的数学研究认知操作系统，而不是知识库或依赖图的同义词。**
2. **当前最成熟的是控制平面，最薄弱的是规范数学知识、在线召回、上下文编译、研究运行和数学真值验证。**
3. **当前数学图不是健康的统一生产图：模式分裂、KC稀疏、拓扑验证失败、POC与题库混存。**
4. **在修复模式和闭合最小端到端研究链之前，不应把扩大知识节点规模作为主优先级。**
5. **下一份专项文档应优先调查“统一词汇与规范图模式”，随后用一个小问题闭合最小研究主链。**
6. 本文档是架构调查v1，不是最终架构冻结。后续调查应沿用122号编号形成v2/v3，逐步把假设变成经过验证的架构决策。
