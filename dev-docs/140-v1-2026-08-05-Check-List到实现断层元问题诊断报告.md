## 3. 这一次是什么问题——131号Check List与实现的逐项断层分析

### 3.1 断层类型分类

### 3.3 关键发现

**断层最严重的两项是P1-2.2和P1-4.3**：

- **P1-2.2**明确要求"实现事件捕获器"，但实际只有EventFactory（创建事件的辅助方法）。EventFactory是"创建事件的工具"，不是"从Solver输出中捕获事件的捕获器"。这就像Check List要求"建一个渔网"，实际建了"一个能手工往里放鱼的容器"。

- **P1-4.3**明确要求"实现语义抽取器（从原始事件中识别...）"，但实际只有SemanticEvent类型定义。这就像Check List要求"建一个翻译器"，实际只建了"目标语言的字典"。

**Check List覆盖盲区（F3）三项**：

- 123号§17明确说"数据库只存其无环的直接前驱边，不存自环"，但131号P1-3.5只说"不形成环"，遗漏了"不存自环"这个更强的约束。
- 123号§44明确把"事件捕获完整度"列为Phase 1核心指标，但131号Check List完全没有这项。
- 123号§39明确要求"同一checkpoint多continuation"的实验设计，131号P1-5.COMP3和P1-6.1虽然提到了，但没有要求实际验证。

## 4. 为什么审计过了还是出现了问题

### 4.1 138号审计做了什么

138号审计的10个横向审计维度：

1. DYN-0—7阶梯覆盖
2. 12步运行时覆盖
3. 角色隔离启用顺序
4. 8类schema覆盖
5. 入口门/出口门链条
6. 代码模块创建顺序
7. 预注册门G0-1—G0-6覆盖
8. 贯穿案例覆盖
9. 数据迁移原则覆盖
10. 五项变化覆盖

### 4.2 138号审计的盲区

138号审计的10个维度全部是**跨Phase横向一致性**维度——检查Phase之间是否对齐、是否覆盖了来源文档的要求。但它**没有检查"Check List项的措辞是否足够精确到能区分'定义'和'实现'"**。

具体来说，138号审计回答了这些问题：
- "DYN-0—7是否全部映射到对应Phase？" → 是
- "12步是否全部覆盖？" → 是
- "8类schema是否全部定义？" → 是

但138号审计**没有回答**这些问题：
- "P1-2.2说'实现事件捕获器'，Check List是否明确了'实现'的标准——是'有捕获类'还是'有捕获类+实际hook到Solver输出'？"
- "P1-4.3说'实现语义抽取器'，Check List是否明确了'实现'的标准——是'有抽取方法'还是'有从原始事件自动识别语义类型的完整逻辑'？"
- "P1-3.5说'不形成环'，是否覆盖了123号§17的'不存自环'这个更强的约束？"

### 4.3 根本原因

**138号审计是"覆盖性审计"，不是"可实现性审计"。**

- **覆盖性审计**：检查Check List是否提到了来源文档中的每个要求 → 138号做了
- **可实现性审计**：检查Check List的措辞是否足够精确，使得实现者能区分"定义"和"实现" → 138号没做

这导致了一个系统性盲区：**Check List可以说"实现X"，但只要X在Check List中被提到，覆盖性审计就会判为"通过"，即使Check List没有明确"实现"的标准是什么。**

## 6. 根本原因分析

### 6.1 Check List措辞的系统性缺陷

当前Check List的措辞存在一个系统性缺陷：**"实现X"这个动词没有被精确定义。**

在当前Check List中，"实现X"可能被理解为：
- 理解A："定义X的类型/schema/枚举" → 最弱
- 理解B："定义X的类型 + 写了处理X的逻辑" → 中等
- 理解C："定义X的类型 + 写了处理X的逻辑 + 有测试覆盖X的全部边界情况" → 最强

131号Check List的P1-2.2和P1-4.3在实现时被按理解A勾选了，但123号§46和§28的要求实际上是理解C。

### 6.2 审计方法的系统性缺陷

138号审计是"覆盖性审计"——检查Check List是否提到了来源文档的每个要求。但它不是"可实现性审计"——不检查Check List的措辞是否足够精确到能区分"定义"和"实现"。

这导致了一个悖论：**Check List可以通过覆盖性审计，但在实现时仍然出问题。**

### 6.3 勾选标准的系统性缺陷

当前Check List的勾选标准是二元的：`[x]`或`[ ]`。但"实现X"不是一个二元状态——它是一个从"定义了"到"完整实现了+测试了"的连续谱。

用二元勾选覆盖连续谱，必然导致"定义了就勾选"的倾向，因为勾选者倾向于选择最宽松的满足标准。

## 7. 修正方案

### 7.1 Check List措辞修正——引入"实现深度等级"

在每个"实现X"类Check List项中，明确标注实现深度等级：

| 等级 | 定义 | 勾选标准 |
|---|---|---|
| **D1：定义** | 定义X的类型/schema/枚举 | 类型定义存在且有文档 |
| **D2：逻辑** | 定义X的类型 + 写了处理X的逻辑 | 有可执行的函数/方法 |
| **D3：测试** | D2 + 有测试覆盖X的全部边界情况 | 测试通过且覆盖边界情况 |
| **D4：集成** | D3 + X与上下游组件集成验证 | 集成测试通过 |

示例修正：

**修正前**（131号P1-2.2）：
```
- [x] P1-2.2：实现事件捕获器（hook到Devin CLI的tool调用、subagent输出、文件写入等）
```

**修正后**：
```
- [x] P1-2.2：实现事件捕获器（hook到Devin CLI的tool调用、subagent输出、文件写入等）
  - 实现深度：D2（有可执行的EventCapture类，10种捕获方法）
  - 注：D4（hook到Devin CLI）在Phase 6在线运行时完成
```

### 7.2 审计方法修正——新增"可实现性审计"维度

在138号式的交叉审计中，新增第11个审计维度：

**维度11：可实现性审计**——检查每个"实现X"类Check List项的措辞是否足够精确到能区分"定义"和"实现"。

具体检查：
1. 每个"实现X"项是否标注了实现深度等级（D1/D2/D3/D4）
2. 每个"验证X"项是否明确了验证的边界情况清单
3. 每个"覆盖X"项是否明确了"覆盖"的标准——是"定义了枚举"还是"有处理逻辑"

### 7.3 勾选标准修正——从二元改为四元

将Check List的勾选从`[x]/[ ]`改为`[D1]/[D2]/[D3]/[D4]/[ ]`，强制勾选者明确实现深度。

### 7.4 对132—137号的预防性修正

在Phase 2—7实现前，对132—137号Check List做以下预防性修正：

1. 对每个"实现X"项，标注预期的实现深度等级
2. 对每个"验证X"项，明确验证的边界情况清单
3. 对每个"覆盖X"项，明确"覆盖"的标准

## 9. 结论

### 9.1 这一次的问题

Phase 1实现出现6项遗漏的根本原因是：

1. **Check List措辞不精确**："实现X"没有被精确定义，导致"定义了=实现了"的断层（F1）
2. **审计方法是覆盖性的而非可实现性的**：138号审计检查了"Check List是否提到了X"，但没检查"Check List是否精确到能区分'定义'和'实现'"（F2）
3. **Check List本身有覆盖盲区**：131号遗漏了123号§17自环、§44完整度度量、§39多continuation（F3）

### 9.2 其他Phase的范型问题

**其他Phase普遍存在同样的范型问题**。Phase 2/4/5/6/7的F1风险均为高（6—7项），需要在实现前做预防性修正。

### 9.3 根本修正

根本修正不是"再审计一遍"，而是**改变Check List的措辞规范和审计方法**：

1. 引入"实现深度等级"（D1—D4）
2. 新增"可实现性审计"维度
3. 将勾选从二元改为四元

只有这样才能从"反复审计但实现仍然出问题"的循环中跳出来。
