## 0. 为什么需要这份方案

244号重构把26个文件分成了三层（primitives / concepts / criteria），但有一个东西被从所有文件中删掉了却没有安顿好——**面相**。用户正确地判断：面相是特别重要的概念，不能就这么消失了。

## 1. 面相独立目录

### 1.1 面相是什么

面相（Facet）= 看系统和看设计过程的切分维度。它不是原语（不能执行/放置），不是概念框架（不是观察视角），不是性质标准（不检查任何东西）——它是**元分类**，决定我们用什么角度来切分系统理解和设计过程。

241号定义了两类共5个面相：

**系统面相**（看系统是什么）：

| 面相 | 名称 | 核心判断 | 来源 |
|---|---|---|---|
| 面相1 | 两种计算 | 系统 = 经典计算 + AI计算 | 239号核心 |
| 面相2 | 语料双路径 | 语料→训练路径 + 语料→抽取路径 | 231号核心 |
| 面相3 | Pipeline网络 | AI是Pipeline网络中的Pipe，有不同角色 | 241号新增，修正238和239 |

**设计过程面相**（看原语从哪来）：

| 面相 | 名称 | 核心判断 | 来源 |
|---|---|---|---|
| 面相A | 实践涌现 | 原语从实验和迭代中涌现，带着实验证据 | 238时期 |
| 面相B | 知识选取 | 原语从人类知识海洋中选取，有数学正当性 | 239时期 |

### 1.2 为什么面相需要独立目录

面相在241号方案中是"原语的来源字段"——每个原语标一个面相标签。244号重构删掉了这个字段，因为面相不是原语的属性，是**原语之上的分类维度**。

把面相独立出来的价值：

1. **面相本身会演化**——面相3是241号新增的，修正了面相1和面相2的局限。未来可能有面相4。面相的演化需要被记录。
2. **面相之间的关系是理念层的**——面相3修正面相1的"AI计算黑箱"问题，面相A和面相B互补。这些关系不属于任何原语，属于面相层。
3. **面相指导分类**——一个新的设计想法出现时，先问"它属于哪个面相？"这决定了它被放在哪里、用什么格式记录。
4. **面相覆盖度是健康指标**——如果所有原语都集中在面相A（实践涌现），说明项目缺乏理论深化；如果都集中在面相B（知识选取），说明项目缺乏实验验证。

### 1.3 目录结构

```
facets/
  README.md              # 面相说明 + 索引
  system-facet-1.md      # 面相1：两种计算
  system-facet-2.md      # 面相2：语料双路径
  system-facet-3.md      # 面相3：Pipeline网络
  process-facet-A.md     # 面相A：实践涌现
  process-facet-B.md     # 面相B：知识选取
```

### 1.4 面相文件格式

```markdown
# 面相名（中英文）

## 定义
这个面相在切分什么维度。

## 核心判断
这个面相下，对系统/设计过程的核心判断是什么。

## 来源
哪个文档/哪个时期提出的。

## 贡献
这个面相正确识别了什么。

## 局限
这个面相看不到什么——被后续面相修正的部分。

## 包含的设计元素
这个面相下有哪些原语/概念/标准（引用primitives/concepts/criteria中的文件）。

## 被修正 by
被哪个后续面相修正了什么（如果有）。

## 开放问题
这个面相还有什么没想清楚的。
```

### 1.5 面相与三层目录的关系

面相是**第四层**，但不是和前三层平行的层——它是**横切前三层的分类维度**：

```
              面相1   面相2   面相3   面相A   面相B
primitives/    ×      ×      ×      ×      ×
concepts/      ×      ×      ×      ×      ×
criteria/      ×      ×      ×      ×      ×
```

每个设计元素（原语/概念/标准）可以属于一个或多个面相。例如：
- `continuous-questioning`（操作原语）属于面相A（实践涌现）+ 面相3（它是模式识别引擎Pipe的输出协议）
- `formalization-boundary`（概念）属于面相B（知识选取）+ 面相1（它是两种计算分工的分界线）
- `pipe`（结构原语）属于面相3（Pipeline网络）

**关系记录方式**：面相文件中的"包含的设计元素"字段列出属于它的元素；元素文件不记录面相（保持文件简洁），通过面相文件的反向引用建立关系。

## 2. 设计元素管理元组群

### 2.1 管理对象

需要管理的东西（4类）：

| 管理对象 | 目录 | 数量 | 更新频率 |
|---|---|---|---|
| 原语 | primitives/ | 16 | 随实验更新验证状态 |
| 概念框架 | concepts/ | 7 | 随理念突破更新 |
| 性质标准与隐喻 | criteria/ | 3 | 最稳定，偶尔新增 |
| 面相 | facets/ | 5 | 随系统理解深化演化 |

### 2.2 管理操作（需要元组覆盖的场景）

识别出4个需要元组管理的操作场景：

**场景1：新增设计元素**
- 触发：实验中涌现新操作/新结构，或讨论中产生新概念/新面相
- 做什么：判断分类（原语/概念/标准/面相）→ 判断面相归属 → 创建文件 → 更新索引
- 频率：中等（每次有理念突破或新实验时）

**场景2：实验后验证状态更新**
- 触发：跑完一个实验（guided_004, bare_q2等）
- 做什么：识别实验测试了哪些原语 → 更新验证状态 → 更新使用经验/架构位置 → 更新面相的"包含的设计元素" → commit
- 频率：高（每次实验后）

**场景3：面相演化**
- 触发：对系统结构有了新的理解，需要新面相或修正旧面相
- 做什么：创建/修改面相文件 → 评估对现有设计元素的影响 → 更新面相的"包含的设计元素" → commit
- 频率：低（理念突破时）

**场景4：定期审查**
- 触发：用户要求审查，或达到某个里程碑
- 做什么：检查验证状态分布 → 识别长期untested的原语 → 识别应该被操作化的概念 → 检查面相覆盖度 → 输出审查报告
- 频率：低（按需）

### 2.3 元组设计

4个场景 → 4个元组（Rule + Skill）。不是元组群（它们是独立触发的，不是一条工作流的分段），而是4个独立元组。

#### 元组1：design-element-creation（新增设计元素）

**Rule**（always-on，放 `.devin/rules/`）：
```
当实验或讨论中产生一个新的设计想法（操作/结构/概念/标准/面相）时，
加载 design-element-creation skill。
判断标准：这个想法是否值得记录为设计元素？
- 如果只是一次性的实验参数，不值得
- 如果是可复用的设计决策或可积累的理解，值得
```

**Skill**（`.devin/skills/design-element-creation/SKILL.md`）：
- 分类决策树：可执行？可验证？构造性？→ 原语（操作/结构）/ 概念 / 标准 / 面相
- 面相归属判断：属于哪个系统面相？哪个设计过程面相？
- 文件创建：按对应模板创建文件
- 索引更新：更新对应目录的 README.md
- 面相更新：在 facets/ 对应面相文件的"包含的设计元素"中添加引用
- commit

#### 元组2：experiment-status-update（实验后验证状态更新）

**Rule**：
```
当一个实验run完成并产出结果后，加载 experiment-status-update skill。
触发条件：runs/ 目录下新增了实验结果，或用户要求更新验证状态。
```

**Skill**：
- 识别实验测试了哪些原语（从run的problem.txt、solutions.json、引导者决策中提取）
- 对每个受影响的原语，判断验证状态变化：
  - untested → tested / tested_negative / partial
  - partial → tested / tested_negative
  - tested → 保持或细化
- 更新原语文件的验证状态section
- 更新使用经验/架构位置section
- 更新 primitives/README.md 的验证状态分布统计
- 如果实验结果影响面相理解，更新 facets/ 对应文件
- commit

#### 元组3：facet-evolution（面相演化）

**Rule**：
```
当对系统结构有了新的理解，需要新增面相或修正现有面相时，加载 facet-evolution skill。
判断标准：这个新理解是否改变了我们切分系统/设计过程的维度？
- 如果只是新增了一个原语/概念，不改变维度 → 不触发，走元组1
- 如果改变了"我们用什么角度看系统" → 触发
```

**Skill**：
- 记录新面相/面相修正（按面相文件格式）
- 评估对现有设计元素的影响：哪些元素应该归入新面相？
- 更新受影响面相的"包含的设计元素"
- 更新 facets/README.md 索引
- 如果面相修正了旧面相，更新旧面相的"被修正by"字段
- commit

#### 元组4：design-element-review（定期审查）

**Rule**：
```
当用户要求审查设计元素目录，或达到项目里程碑时，加载 design-element-review skill。
```

**Skill**：
- 验证状态分布统计（按层、按面相）
- 识别长期untested的原语——它们是否应该被优先测试？
- 识别应该被操作化的概念——是否有概念已经具备了变成原语的条件？
- 检查面相覆盖度——是否有面相没有设计元素？是否有设计元素没有面相归属？
- 检查跨层引用完整性——所有"约束于"引用是否指向存在的文件？
- 输出审查报告到 dev-docs/
- 不自动修改文件，只输出报告和建议

### 2.4 为什么是4个独立元组而不是元组群

元组群适用于**一条长工作流的分段**（如 guided-math-solving 的5个Skill是一条引导解题流程的5个阶段）。这4个元组不是一条流程的分段——它们是**独立触发的管理操作**：

- 新增元素时不一定在实验后
- 实验后不一定有面相演化
- 审查不依赖前三个操作的执行

所以它们是4个独立元组，每个有自己的触发条件和完整的工作流，不依赖其他元组的产出。

### 2.5 元组之间的关系

虽然独立，但它们有交叉：

```
元组1（新增）──创建元素时──→ 可能需要更新面相 → 触发元组3的判断
元组2（实验更新）──实验结果改变理解──→ 可能触发新面相 → 触发元组3
元组4（审查）──发现遗漏──→ 建议触发元组1或元组2
```

这些交叉通过Rule的触发条件自然处理——元组1创建元素时如果发现需要新面相，元组3的Rule会触发。不需要显式编排。

## 5. 决策结论（讨论后确认）

5个问题的讨论结论：

| 问题 | 决策 | 理由 |
|---|---|---|
| 1. 目录位置 | **根目录**，和 primitives/concepts/criteria 平级 | 面相横切前三层，放任何一个下面会暗示从属关系；四层平级结构最清晰 |
| 2. 命名 | **编号命名** `facet-1.md` / `facet-A.md`（系统面相用数字，过程面相用字母） | 面相内容会演化，编号稳定；README写对应关系 |
| 3. 元组数量 | **4个独立元组，按优先级渐进建设**：先建元组2（experiment-status-update），再建元组1，元组3/4延后 | 4个场景独立触发不合并；按使用频率排序建设，不为未出现的需求提前建工具 |
| 4. 执行时机 | **先执行面相目录，元组渐进建设**（先建元组2） | 面相目录是确定工作，执行风险低；元组是工具，实际使用中再建 |
| 5. 关系记录 | **正向引用**——元素文件"来源"字段加一行面相归属，面相文件不列元素清单 | 高频操作（新增元素时记面相）应低成本（写一行）；低频操作（覆盖度统计）可高成本（扫描文件） |

**对方案正文的修正**（基于问题5的决策变更）：
- §1.5"面相与三层目录的关系"中的关系记录方式从反向引用改为正向引用
- §1.4面相文件格式中删除"包含的设计元素"字段
- §2.3元组3 Skill中删除"更新受影响面相的包含的设计元素"步骤
- 元素文件（primitives/concepts/criteria中的所有文件）的"来源"字段加回一行面相归属
