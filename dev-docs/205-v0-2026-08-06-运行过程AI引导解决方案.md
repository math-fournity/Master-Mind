## 一、问题回顾

202号文档诊断了当前系统在运行过程中的AI缺位：

1. **步骤7诊断全部经典计算**：StallDetector用关键词+阈值检测7种卡点，不理解Solver思路内容
2. **步骤8匹配全部经典计算**：HeuristicMatcher按stall_type字符串匹配规则
3. **步骤9动作选择全部经典计算**：PolicyPi用if-else阈值（0.7/0.3硬编码）
4. **步骤10提示编译全部经典计算**：GuidedLoop的5条提示全部硬编码
5. **无AI引导者角色**：8角色中无人做智能分析和

## 二、能不能解决？

**能解决，但有一个核心张力需要先回答：**

### 2.1 核心张力——AI引导者 vs 200号作弊问题

这里有一个与200号的直接矛盾：**如果我们在步骤10引入AI编译提示，AI会不会变成"更高级的递答案"？**

200号说：经典计算的硬编码提示有作弊成分（给了具体数学知识）。
202号说：经典计算的提示太"死"，需要AI给出"活"的判断。

**解决这个张力的关键是203号的泄漏审计**：无论提示是经典计算生成的还是AI生成的，都必须经过四门泄漏审计。AI引导者的输出不豁免审计。

**结论**：能解决，但AI引导者必须与203号的泄漏审计同时实施——AI生成的提示也要过四门审计。

### 2.2 各环节的解决难度

| 环节 | 能否解决 | 难度 | 原因 |
|---|---|---|---|
| 步骤7诊断引入AI | **能** | 中 | 需要调用AI分析Solver response内容 |
| 步骤8匹配引入AI | **能** | 中 | 需要调用AI从候选规则中选择 |
| 步骤9动作选择引入AI | **能** | 低 | 需要调用AI从合法动作中选择 |
| 步骤10提示编译引入AI | **能** | 中高 | 需要调用AI生成针对性提示+过泄漏审计 |
| 多轮智能规划 | **部分能** | 高 | 需要AI维护"已探索区域"的全局视图 |
| 全自动AI引导 | **部分能** | 很高 | AI调用成本+延迟+质量不稳定 |

**关键判断**：步骤7-10引入AI是工程问题——调用AI分析+选择+生成。多轮智能规划是设计问题——需要定义"已探索区域"的表示和"下一步最优方向"的算法。全自动AI引导不现实——成本和延迟是硬约束。

## 三、能在多大程度上解决？

### 3.1 步骤7-10引入AI（解决程度：75%）

**已有基础**：
- `controller_belief.py`已定义9种动作和信念估计
- `stall_detector.py`已定义7种卡点类型
- `matcher.py`已定义规则匹配框架
- `guided_loop.py`已定义提示生成框架
- DevinCliAdapter已能调用AI（devin cli）

**需要做的**：
1. 在步骤7中，当经典计算给出不确定结果时，调用AI分析Solver response
2. 在步骤8中，当候选规则>1时，调用AI从候选中选择
3. 在步骤9中，当多个动作都合法时，调用AI选择最有价值的
4. 在步骤10中，调用AI生成针对性提示（+过泄漏审计）

**解决程度**：75%——调用AI是工程问题。剩余25%是：
- AI分析质量不稳定（可能给出错误判断）
- AI调用成本和延迟（每步都调用太贵）
- AI生成的提示需要过泄漏审计（与203号耦合）

### 3.2 多轮智能规划（解决程度：60%）

**已有基础**：
- GuidedLoop已能多轮运行
- 状态归约已记录历史进展

**需要做的**：
1. 定义"已探索区域"的表示——Solver已经探索了哪些知识节点/方法/方向
2. 定义"未探索区域"的表示——稀疏矩阵中哪些区域Solver还没去过
3. 定义"桥梁节点"——连接已探索和未探索区域的节点
4. AI根据已探索/未探索/桥梁节点，规划下一步引导方向

**解决程度**：60%——"已探索区域"可以从状态归约中提取，但"桥梁节点"和"最优方向"需要AI判断。剩余40%是：
- 稀疏矩阵数据量巨大时的效率问题
- AI规划的全局视图维护成本
- 多轮规划的一致性（AI可能在不同轮给出矛盾的方向）

### 3.3 全自动AI引导（解决程度：40%）

**需要做的**：
1. 每步都调用AI分析+选择+生成
2. AI调用的成本控制（token预算）
3. AI调用的延迟控制（超时fallback）
4. AI分析质量监控

**解决程度**：40%——全自动在技术上可行，但成本和延迟是硬约束。更现实的方案是"按需调用"——只在经典计算不确定时调用AI。

## 四、是否需要连续POC验证？

**需要。每个环节都需要POC验证：**

| 环节 | POC类型 | 验证内容 | 预期轮次 |
|---|---|---|---|
| 步骤7 AI诊断 | 对比测试 | AI诊断 vs 经典计算诊断的准确性 | 3-5轮 |
| 步骤10 AI编译 | 对比测试 | AI编译提示 vs 硬编码提示的有效率 | 3-5轮 |
| 泄漏审计拦截 | 安全验证 | AI生成的提示能否被四门审计拦截 | 2-3轮 |
| 多轮智能规划 | 端到端测试 | 多轮AI引导的完成率 vs 多轮经典计算引导 | 5-10轮 |
| 成本/延迟 | 性能测试 | AI调用的token消耗和延迟 | 持续监控 |

**步骤A1**：定义AI诊断的调用时机

```python
# 在stall_detector.detect()之后

if len(detections) > 1 and max_confidence_diff(detections) < 0.2:
```

**步骤A2**：设计AI诊断的prompt

```

{detections}

请分析：
1. Solver是真的卡住了，还是在做合理的策略转换？
2. 如果卡住了，真实原因是什么？（从7种卡点类型中选择，或提出新类型）
```

### 5.2 Phase 205-B：步骤10 AI编译+泄漏审计（3-5轮POC）

**步骤B1**：定义AI编译的调用时机

```python
# 在_generate_hint()中
```

**步骤B2**：设计AI编译的prompt

```

稀疏矩阵K维度的相关上下文：{k_dimension_context}
经典计算生成的提示骨架：{classic_hint}

请生成一条针对性提示，要求：
1. 不包含答案或答案的等价表述（会经过泄漏审计）
2. 针对Solver的具体思路内容，不是通用提示
3. 优先给策略（解题方向），其次给元提示（继续/更详细），最后才给知识
4. 如果Solver的思路方向是对的，只给"继续"的元提示
5. 如果Solver的思路方向不对，给策略提示引导换方向
```

**步骤B3**：POC验证——用5个已有run，对比AI编译提示和硬编码提示的有效率

## 六、与203号的耦合关系

205号的步骤B（AI编译提示）必须与203号的泄漏审计同时实施：

```
AI编译提示 → 203号四门审计 → 通过则发送 / 不通过则降级
```

**不能只做205不做203**——那样AI生成的提示没有泄漏审计，可能比硬编码提示更危险（AI更"聪明"，泄漏方式可能更隐蔽）。

**实施顺序**：203-A（提示分级+泄漏审计）→ 205-A（AI诊断）→ 205-B（AI编译+泄漏审计）→ 205-C（多轮规划）
