1. 对每个术数概念，找到原文的**完整定义段落**（不是目录条目）

## 四、第三层：历史命例验证方案（案例）

### 4.1 为什么案例是最硬的验证

数据表考据（第二层）验证的是"我们的数据对不对"。案例验证验证的是"**我们的整个系统能不能复现古人的论命结果**"——这是端到端测试。

如果古人说"此人丙戌时生，命坐卯宫，火躔翼宿"，我们可以：
1. 用丙戌时的干支反推出生日期
2. 用我们的软件排盘
3. 检查命宫是否在卯宫
4. 检查火星是否在翼宿
5. 如果一致 → 系统正确 + 古人可靠
6. 如果不一致 → 系统有误 或 古人有误 或 我们对古人的理解有误

### 4.2 已知历史命例来源

| 来源 | 命例数量 | 含出生数据 | 可用性 | 获取状态 |

| 《果老星宗》郑氏星案 | 40例 | 含四柱干支 + 星图 | **极高** | 网上有部分（d5168.com 等） |

### 4.3 郑氏星案的特殊价值

郑氏星案是元代星命家郑希诚的 40 个真实推命案例，每个案例含：
- **四柱干支**（年月日时）→ 可反推出生时间
- **星图**（七政四余躔度）→ 可对比我们的排盘结果
- **郑氏断语**（命理判断）→ 可对比我们的分析输出

这是**千年前的端到端测试用例**。

### 4.4 案例验证的挑战

| 挑战 | 说明 | 应对 |
|---|---|---|
| 历法转换 | 郑氏星案用元代历法（授时历），我们用现代UT反推 | 需要确认干支→UT的转换在元代是否正确 |
| 时空差异 | 元代的二十八宿位置与现在不同（岁差） | 需要第四层时空重建 |
| 星图精度 | 郑氏星图只画到整度，无小数 | 容差设为 ±1° |
| 出生地点 | 郑氏案例未明确出生地经纬度 | 假设为中原地区（如洛阳/开封，lon≈113°, lat≈34.5°） |
| 四柱→公历 | 干支纪日需要精确转换 | 用 Swiss Ephemeris 的 `julday` 反推 |

```
对每个历史命例：
1. 提取四柱干支（年月日时）
2. 确定出生地点（默认中原地区，如有线索则用具体地点）

   a. 命宫地支 → 与星图标注的命宫一致？

   c. 化曜 → 与星图标注的化曜一致？
   d. 神煞 → 与星图标注的神煞一致？
   e. 大限 → 与断语中的限路推演一致？
6. 记录验证结果
7. 如不一致 → 分析原因（历法？岁差？数据？算法？）
```

## 五、第四层：历史星空重建方案（时空）

### 5.1 为什么时空重建是必要的

**古本上的星象描述，只有回到那个时代的星空才能正确理解。**

千年以来，星空发生了以下变化：

| 变化 | 速率 | 千年累积 | 对七政四余的影响 |
|---|---|---|---|
| **岁差（春分点西移）** | ~50.3角秒/年 | ~14° | 二十八宿起点移动，古书"角宿在某度"指的是那个时代的度数 |
| **恒星自行** | 角宿一约0.05角秒/年 | ~0.8° | 二十八宿距星位置微移 |
| **黄赤交角变化** | ~0.47角秒/年 | ~0.8° | 黄道与赤道夹角变化，影响宫位边界 |
| **历法变更** | 不连续 | 多次变更 | 唐用大衍历，宋用纪元历，元用授时历，明用大统历，清用时宪历 |

### 5.2 关键发现：清代历狱与四余定义变更

从《清史稿》搜索结果发现一个重大历史事件：

> "康熙三年十二月...二十八宿次序，湯若望將觜、參二宿改易前後；又將四餘刪去紫炁，俱不合。"

> "康熙十七年...是年更定羅睺、計都名目，又增入紫炁為四餘。"

这意味着：
- **清初曾短暂删除紫炁**（汤若望认为紫炁"无用"）
- **康熙十七年又恢复紫炁**为四余之一
- **觜宿和参宿的顺序曾被改易**（乾隆十九年才改回觜前参后）
- **罗睺计都的名目曾被更定**

**对本项目的影响**：
- 我们的系统用 `true_node`（真交点）计算罗睺，但古法可能用 `mean_node`（平交点）
- 紫炁（紫气）的天文定义在不同时代可能不同
- 二十八宿的顺序在不同时代可能不同（觜参前后）

### 5.3 Swiss Ephemeris 的历史星空能力

我们已有的 Swiss Ephemeris 可以计算**任意历史时刻**的行星位置：

```python
import swisseph as swe
# 计算元代某日期的行星位置
jd = swe.julday(1330, 5, 15, 3.5)  # 元至顺元年
positions = swe.calc_ut(jd, swe.SUN)  # 太阳黄经
```

这意味着我们可以：
1. 取古书中的命例日期
2. 计算那个日期的实际星空
3. 与古书描述对比
4. 验证古书的可靠性 + 我们的理解是否正确

### 5.4 二十八宿宿度的历史变迁

从《清史稿》天文志发现：

> "宿度，乾隆十八年以前，用康熙壬子年表，十九年以後，用乾隆甲子年表"

这意味着二十八宿宿度表在不同时代是不同的：
- **明·授时历**宿度表（郭守敬测定）→ 《星学大成》用此
- **清·康熙壬子**宿度表 → 清初用此
- **清·乾隆甲子**宿度表 → 清中后期用此
- **现代**宿度表 → 我们现在用此

**我们的 `constants.json → lunar_mansions → width_yellow` 用的是哪个时代的宿度？需要确认。**

### 5.5 时空重建 SOP

```
对每个需要历史验证的术数概念：

1. 确定概念的历史时代：
   - 《星学大成》→ 明·嘉靖(1563) → 用授时历宿度
   - 《果老星宗》→ 宋元 → 用纪元历/授时历宿度
   - 郑氏星案 → 元·至顺(1330) → 用授时历宿度

2. 获取该时代的历法参数：
   - 二十八宿宿度表（该时代版本）
   - 岁差校正值（该时代 vs 现代）
   - 历法转换规则（该时代的节气定义）

3. 用 Swiss Ephemeris 计算该时代的实际星空：
   - 行星黄经（已含岁差，但需确认参考系）
   - 二十八宿边界（该时代版本 + 岁差校准）

4. 对比古本描述 vs 计算结果

5. 如不一致 → 分析原因：
   - 古本用赤道坐标 vs 我们用黄道坐标？
   - 古本宿度表 vs 我们宿度表不同？
   - 岁差校准有误？
   - 古本本身有误？
```

## 九、搜索预置审查：每个 TODO 该不该先搜索

### 9.0 为什么要做这个审查

A3 十干化曜错误的教训：**Phase 2 从 Java 源码提取数据表时没有搜索原文对照，导致庚辛壬癸四干化曜全部错位，错误存活了整个 Phase 1-12**。

如果当时有"搜索预置"机制——提取数据表前必须搜索原文核对——这个错误在 Phase 2 就会被发现，不会拖到 Phase 20 审计。

本节对**全部 TODO（已完成的 + 未完成的）**逐一审查搜索预置需求，分三级：

| 标记 | 含义 | 何时搜索 |
|---|---|---|
| 🔍 **先搜索** | 必须先搜索外部信息源（原文/参考数据/API文档）才能动手。不搜索 = 必然幻觉或用错数据 | 动手前 |
| 🔄 **边做边搜索** | 主体是工程任务，但过程中有特定细节需要核对原文/参考。不搜索 = 可能出错但不必然 | 过程中按需 |
| ⚙️ **不需要搜索** | 纯工程任务，需求已在代码库或 TODO 描述中定义清楚。搜索 = 浪费时间 | 不需要 |

### 9.4 搜索预置操作规范

对标记为 🔍 **先搜索** 的 TODO，执行前必须完成以下步骤：

```
1. 搜索阶段（动手前）：
   a. 用 web_search 搜索相关原文/参考数据/API 文档
   b. 用 webfetch 抓取完整内容
   c. 记录搜索结果到考据记录文件
   d. 确认搜索结果足以支撑实现

2. 实现阶段：
   a. 基于搜索结果设计/实现
   b. 实现过程中如遇到搜索结果未覆盖的问题，回到步骤 1

3. 验证阶段：
   a. 实现结果与搜索结果对照
   b. 记录一致性判定
```

对标记为 🔄 **边做边搜索** 的 TODO，在遇到以下情况时触发搜索：

- 需要确认某个具体数值/定义/关系
- 实现结果与预期不符，需要查找原因
- 遇到搜索结果未覆盖的边界情况

对标记为 ⚙️ **不需要搜索** 的 TODO，直接实现。
