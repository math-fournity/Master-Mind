## 2. 审计方法

### 2.1 22 维度审计法

严格按 146号v4.2 的 22 个维度逐项审计。关键维度包括：

- **维度 14**：实现→母本覆盖（是否每个代码/文档项都能在母本中找到来源）
- **维度 15**：Check List→实现完整性
- **维度 16**：实现→Check List 完整性
- **维度 17**：方法完整性
- **维度 18**：来源引用正确性
- **维度 19**：方法完整性（多来源/多字段）
- **维度 20**：plan/123号 逐字要求
- **维度 21**：声明性 vs 强制性（是否真正强制，不是只返回 True）
- **维度 22**：母本逐字要求检查（F16 断层类型）

### 2.2 三文件交叉审计

对重要对象，同时加载三份母本：
1. `plan-dad3347dc4d8e542.md`
2. `系统探讨.md`
3. `123-v1-2026-08-05-数学大师系统全景复盘与第一性原理重构计划.md`

按母本原文逐条核对 Master 的工作产物。

### 2.3 代码静态审计

- 检查 Python 代码是否按 Check List 实现
- 检查 ArangoDB 连接是否已环境变量化
- 检查是否缺少异常处理、日志、测试
- 检查函数签名和文档字符串是否与母本对齐

### 2.4 测试审计

- 检查 test_phase1.py 到 test_phase7.py 是否覆盖关键检查点
- 检查测试是否通过（如果 ArangoDB 已启动则实际运行）
- 检查测试是否有假 PASS（通过但不真实）

## 4. 审计产出格式

每份审计报告必须包含：

1. **审计对象**：文件名/模块/Check List
2. **审计依据**：146号v4.2 的哪些维度、母本的哪些章节
3. **审计方法**：人工/自动/半自动
4. **发现问题**：按 F1-F16 断层类型分类
5. **改进意见**：每条意见必须可执行、可验证
6. **优先级**：P0（必须立即改）/P1（建议改）/P2（可选）
7. **责任方**：Master 执行 / Supervisor 监督

---

## 5. 改进意见的"可交付"标准

按用户需求，改进意见要写到"能放心交给低级别 AI 进行改进的实现"的程度：

- 明确指出**哪一行/哪一段/哪个函数**需要改
- 给出**修改后的代码片段或伪代码**（如果是代码问题）
- 给出**修改后的文档原文**（如果是文档问题）
- 说明**为什么需要这样改**（引用母本出处）
- 说明**改了之后如何验证**（测试、审计、对比）

   - 改进意见是否可执行
4. Supervisor 反馈到 `Supervisor/dev-docs/`
5. Master 根据反馈修正审计报告或直接执行改进
