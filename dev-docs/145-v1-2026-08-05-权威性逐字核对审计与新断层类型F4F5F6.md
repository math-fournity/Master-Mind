## 2. 新断层类型定义

### F4：概念混淆

**定义**：两个不同概念在实现者脑中合并为一个，导致代码中用了错误的枚举/字段/类型。

**典型实例**（144号A-1）：
- 123号§14定义了9种TaskType（prove/refute/construct/compute/classify/optimize/conjecture/explain/value）
- 127号§4定义了10种ObligationType（prove/refute/construct/compute/search/compare/evaluate/interface/verification/value）
- 实现时把TaskType的值（classify/optimize/conjecture/explain）混入了ObligationType

**为什么140/142没防住**：140/142关注的是"实现深度"（D1-D4），不是"概念正确性"。D2深度等级要求"有可执行的函数/方法"——实现了，但实现的是错误的概念。

**检测方法**：核对实现中的每个枚举/类型，确认它对应的是127号中的哪个schema定义，而非凭"名称相似"假设。

### F5：权威定义偏差

**定义**：Check List正确地描述了要求，实现也确实"实现"了（不是只定义），但实现的枚举值/字段名/状态值与Schema冻结文档（127号）的权威定义不一致。

**典型实例**（144号A-2/A-3/A-10）：
- EvidenceStatus用了`pending/verified/contradicted/withdrawn`，127号§6权威定义是`pending/active/superseded/retracted`
- StallType用了自创的7类，123号§38权威定义是`necessary_exploration/semantic_repetition/...`
- ObligationStatus用了`released`，127号§4权威定义是`discharged`

**为什么140/142没防住**：140/142假设了一个前提——Check List本身的描述是正确的。实际上Check List可能抄错了，再怎么加深度等级和边界情况，也是在一个错误的描述上加精度。

**检测方法**：实现时不能只看Check List，必须同时打开127号Schema冻结文档逐字核对。Check List是导航，127号是法律。

### F6：方法近似

**定义**：Check List要求用特定方法（如Krippendorff α），实现用了近似方法（如Jaccard相似度）替代，且未声明近似。

**典型实例**（144号A-9）：
- 132号P2-6.2要求"字段级Krippendorff α"
- 实现用了Jaccard相似度近似α，没有声明是近似

**为什么140/142没防住**：140/142关注的是"是否实现了"，不是"实现的方法是否与要求的方法一致"。

**检测方法**：对每个要求特定方法的Check List项，核对实现是否使用了要求的方法，如使用近似方法必须明确声明。

## 3. 第12审计维度：权威性逐字核对

### 3.1 维度定义

在138号式的交叉审计中，新增第12个审计维度：

**维度12：权威性逐字核对**——对每个枚举值、字段名、状态值，逐字核对127号Schema冻结文档原文，而不是核对Check List的描述。

### 3.2 核对清单

实现完成后、勾选Check List前，必须完成以下核对：

| 核对项 | 权威来源 | 核对内容 |
|---|---|---|
| TaskType枚举 | 127号§1 | 9种值是否一致 |
| ObligationType枚举 | 127号§4 | 10种值是否一致（注意：与TaskType不同） |
| ObligationStatus枚举 | 127号§4 | open/discharged/suspended/failed |
| EvidenceKind枚举 | 127号§6 | 6种值是否一致 |
| EvidenceStatus枚举 | 127号§6 | pending/active/superseded/retracted |
| EvidencePolarity枚举 | 127号§6 | support/refute |
| 派生认识状态 | 127号§6 | no_decisive/support_only/refute_only/mixed |
| 验证等级（Verifier输出） | 127号§6 | proven/formally_verified/computationally_supported/numerically_tested/contradicted/unknown |
| map_type枚举 | 127号§5 | equivalence/encoding/reduction/relaxation/duality/functor_candidate |
| HeuristicRule lifecycle_status | 127号§9 | candidate/validated/published/retired |
| 角色枚举 | 127号§8 | solver/event_capture/state_reducer/retriever/heuristic_matcher/verifier/auditor/orchestrator |
| Obligation字段 | 127号§4 | 9个字段：obligation_id/type/status/task_id/parent_obligation/description/evidence_refs/evidence_gate/sub_obligations |
| Evidence字段 | 127号§6 | 12个字段：evidence_id/claim_id/kind/polarity/status/scope/assumptions/artifact_hash/source_event/verifier/verifier_version/confidence/conflicts |
| Representation字段 | 127号§5 | 12个字段：rep_id/source_form/target_form/map_type/domain/preconditions/forward_transport/backward_transport/preserved_invariants/lost_information/soundness_obligation/evidence |
| HeuristicRule字段 | 127号§7 | LHS/interface/RHS/guard/status/effect_evidence/applicable_domains/model_versions/failure_cases/eta |

### 3.3 核对规则

1. **127号是法律，Check List是导航**：发现偏差时以127号为准
2. **逐字核对**：不只是核对"名称相似"，要核对每个字符
3. **区分概念**：TaskType和ObligationType是不同概念，不能因为名称相似就合并
4. **方法一致性**：Check List要求特定方法时，实现必须用该方法，近似必须声明
5. **角色完整性**：Check List列出的所有角色必须全部实现，不能跳过

## 7. 执行纪律

### 7.1 实现时的核对流程

每个Phase实现时，必须遵循以下流程：

1. **读Check List**：理解要求
2. **读127号原文**：核对Check List中提到的每个枚举/字段/状态
3. **发现偏差时**：以127号为准，修正Check List或实现
4. **实现完成后**：逐字核对实现代码与127号的一致性
5. **勾选Check List前**：完成第12维度核对

### 7.2 审计时的核对流程

每个Phase实现后的审计，必须包含第12维度：

1. 对实现中的每个枚举，核对127号原文
2. 对实现中的每个字段名，核对127号原文
3. 对实现中的每个状态值，核对127号原文
4. 对实现中的每个角色名，核对127号§8
5. 对实现中使用的方法，核对是否与Check List要求的方法一致

## 8. 结论

### 8.1 根本教训

140号解决了"措辞精度"问题，142号解决了"可实现性"问题，但两者都假设了一个前提——Check List本身的描述是正确的。144号暴露了这个假设的错误：Check List本身可能抄错，实现者可能混淆概念，方法可能被近似替代。

### 8.2 根本修正

**实现时不能只看Check List，必须同时打开127号Schema冻结文档逐字核对。Check List是导航，127号是法律。**

这不是"再审计一遍"，而是改变审计的权威来源——从"核对Check List"改为"核对127号原文"。

### 8.3 后续Phase的防护

Phase 3-7实现时，必须：
1. 同时打开127号和对应Check List
2. 发现偏差时以127号为准
3. 完成第12维度核对后才能勾选Check List
