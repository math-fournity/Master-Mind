## 2. 已完成的工作（按时间顺序）

### 2.1 实时解析管线实现（§2.3-2.5）

**为什么做**：01工作线的parser是离线的——解析预先生成的A_i文本。效果验证需要在线实时解析——Solver每输出一段，立即解析为ParseResult，检索Pattern，选择提示，注入到Solver。

**实现的模块**（`xishujuzhen/research_runtime/realtime/`）：

| 文件 | 职责 |
|---|---|
| `trajectory_watcher.py` | 监控sessions.db，从Devin CLI trajectory提取Round（一个Round = Solver一轮完整输出） |
| `stall_detector.py` | 卡点检测（语义检测"我不知道"等关键词 + 超时检测N秒无新节点） |
| `pipeline.py` | RealtimePipeline整合watcher + stall_detector + MathParser + RetrievalPipeline + ConstrainedPolicy |
| `hint_injector.py` | 通过tmux send-keys注入提示到Solver session |
| `devin_cli_parser.py` | DevinCliParserProvider——用devin cli作为parser的LLM provider |
| `test_realtime.py` | mock测试——用253号A7数据验证完整流程 |
| `test_devin_cli_parser.py` | parser单元测试 |
| `test_realtime_devin_cli.py` | 完整管线测试（devin cli parser + retrieval + policy） |

**关键验证**：mock测试选中Q8与离线test_e2e_253结果一致——实时管线正确复现了离线检索流程。

### 2.2 DevinCliParserProvider实现

**为什么做**：本地没有可用的LLM API端点（无OpenAI兼容API key）。解决方案：用devin cli本身作为parser的LLM——`devin -p`发送解析prompt，捕获JSON输出。

**关键设计决策**：
- parser的devin cli在独立工作目录运行（`/data/math-agent-glm5.2-parser-1/`），不复用Solver工作目录
- parser的devin cli用`-p`单轮模式（不需要交互）
- parser的devin cli不需要MITM（不采集trajectory）
- parser的devin cli用`--permission-mode dangerous`（需要exec权限做SymPy验证）
- JSON提取容错：支持纯JSON、markdown代码块、花括号提取等多种格式

**性能**：25-41秒/次解析（单次JSON解析成功），202秒（第一次JSON失败+重试成功）。parse_confidence=0.82-0.88。

### 2.3 mitmproxy流式thinking截获（02工作线产出，04工作线依赖）

**为什么做**：sessions.db只在响应完成后才有assistant消息。thinking期间（5+分钟）没有新节点，无法实时获取Solver的推理过程。mitmproxy通过代理截获HTTP响应流，实现token级实时thinking截获。

**实现**：
- `xishujuzhen/mitm_thinking_intercept/mitm_proto_capture.py`——mitmproxy addon，截获GetChatMessage的protobuf响应流
- mitmproxy作为launchd系统服务运行（端口18889，开机自启动，两AI共享不冲突）
- `--no-http2`标志——强制HTTP/1.1，修复多轮交互的Connection failed问题
- `NODE_EXTRA_CA_CERTS`环境变量——修复Node.js的SSL验证问题（Node.js不能读macOS Keychain）
- 四路落盘：`thinking_live.txt`（token chunks）+ `thinking_readable.txt`（人可阅读连续文本）+ `thinking_raw.bin`（原始protobuf）+ `content.txt`（final output）

**数据路径**：`/data/math-agent-glm5.2-tmux-agents-trajectory/<exp_id>/mitm/thinking_readable.txt`

### 2.4 第二轮Connection Failed问题诊断与修复（266号文档）

**问题**：Solver第一轮thinking正常完成，但第二轮thinking开始后立即"Connection failed"。最初怀疑是API限速（UI显示"0% remaining"），但实际是mitmproxy的HTTP/2连接多路复用在流式响应后变得不稳定。

**修复**：mitmproxy启动命令加`--no-http2`标志，强制HTTP/1.1。修复后多轮交互正常。

### 3.1 核心转变

**旧困境（已消解）**："如何让推理AI在合适的位置停下来接受提示？"——HintInjector时序、tmux send-keys排队、Response truncated后注入——所有这些问题都在解决一个不该存在的问题。

**新认知**：推理AI不需要停下。系统与推理AI并行运行。

### 3.2 未来系统的工作方式

1. **推理AI持续推理**——不需要停下来接受提示。从根节点（或某个脉络的起点）开始，持续推理，直到自然终止（token用尽、证毕、或崩溃）
2. **系统实时采集**——通过mitmproxy流式截获、sessions.db轮询，实时获取推理AI的trajectory和thinking内容
3. **系统实时整理两棵树**——引导展开树（=解题记录树的生长态）。每个推理AI的探索贡献树的一条脉络
4. **系统在节点上识别方向**——用数据基座中的Pattern做检索/模式识别，识别出"从这个节点应该往哪些方向探索"
5. **系统启动新的推理AI**——对每个识别出的方向，启动一个新的推理AI实例，给它"从根到当前节点的脉络"，让它理解和验证后继续探索
6. **并发**——多个推理AI可以并发（如5个额度）。某个脉络尽头有3条路→启动3个AI各探索一条→剩余2个额度用于实时整理3个AI的trajectory发现新可分配节点
7. **停机条件**——与正确解答的脉络相遇时停机

### 3.3 两棵树概念（引用自另一个AI的256号论文原语化版）

来自`原语化AI数学工程系统设计/05-两棵树/`（不修改另一个AI的文件，只引用理解）：

- **引导展开树（Guided Expansion Tree）** = 过程——从题目出发，在提示驱动下展开的所有可能解题路径构成的空间。每个节点是一个数学处境，每条边是一个提示Q。活的、正在生长的。
- **解题记录树（Solution Record Tree）** = 产物——引导展开树展开完成后凝固的树。包含成功路径、失败路径、分叉点、中间处境。
- **它们是同一棵树的不同阶段。**
- **系统本质**：在不知道答案的情况下，通过引导展开机制，让AI生长出一棵尽可能完整的解题记录树。

## 5. 技术细节

### 5.1 mitmproxy配置

- **端口**：18889（launchd系统服务，开机自启动）
- **关键标志**：`--no-http2`（强制HTTP/1.1，修复多轮Connection failed）
- **CA证书**：`NODE_EXTRA_CA_CERTS`环境变量指向mitmproxy CA证书（修复Node.js SSL验证）
- **workdir_mapping缓存**：10秒（原60秒，减至10秒避免新实验匹配失败）
- **四路落盘**：thinking_live.txt + thinking_readable.txt + thinking_raw.bin + content.txt
- **启动/停止**：`xishujuzhen/solver_harness/solver_harness.py mitm start/stop`

### 5.2 solver-harness

- **启动Solver**：`.venv/bin/python3 xishujuzhen/solver_harness/solver_harness.py launch --exp-id <exp_id> --model glm-5-2 --interactive`
- **停止Solver**：`.venv/bin/python3 xishujuzhen/solver_harness/solver_harness.py stop --exp-id <exp_id> --no-decode`
- **tmux session命名**：`harness-<exp_id>`
- **Solver工作目录**：`/data/math-agent-glm5.2-tmux-agents-dir/<exp_id>/`
- **trajectory目录**：`/data/math-agent-glm5.2-tmux-agents-trajectory/<exp_id>/`
- **⚠️ 硬约束**：所有场景启动Solver必须通过solver-harness（AGENTS.md硬约束6），禁止手动tmux/exec后台/nohup

### 5.3 A/B实验脚本

- **运行A组**：`PYTHONUNBUFFERED=1 .venv/bin/python3 scripts/ab_experiment.py --group A --exp-id ab-253-A<N> --max-time 1200`
- **运行B组**：`PYTHONUNBUFFERED=1 .venv/bin/python3 scripts/ab_experiment.py --group B --exp-id ab-253-B<N> --max-time 900`
- **PYTHONUNBUFFERED=1**：必须加，否则stdout被缓冲看不到实时输出
- **A组流程**（`run_group_a`）：
  1. launch_solver启动Solver
  2. 构建pipeline组件（hgraph + DevinCliParserProvider + MathParser + RetrievalPipeline + ConstrainedPolicy + BudgetManager）
  3. 手动控制时序的监控循环：
     - `is_solver_thinking()`：检查tmux pane最后8行是否包含"Thinking"
     - `is_solver_idle()`：检查tmux pane最后8行是否包含"Response truncated"等空闲标志
     - thinking中 → 等待（每15秒检查thinking_readable.txt增长）
     - idle且未注入 → 读取thinking_readable.txt → 构造Round → pipeline.process_round → 选中Q则inject_hint_via_tmux
     - idle且已注入 → 等待Solver开始新一轮thinking
     - thinking中且已注入 → 重置injected_for_this_round标志
  4. 自动停止Solver

### 5.4 DevinCliParserProvider

- **工作目录**：`/data/math-agent-glm5.2-parser-1/`（独立于Solver工作目录）
- **调用方式**：`devin -p <prompt> --model glm-5-2 --respect-workspace-trust false --permission-mode dangerous`
- **超时**：180秒（`timeout=180`）
- **重试**：`max_retries=1`（第一次JSON解析失败后重试一次）
- **降级**：两次都失败返回_fallback_response（最小有效JSON，parse_confidence=0.3）
- **性能**：25-41秒（单次成功）/ 202秒（第一次失败+重试成功）

### 5.5 数据库

- **ArangoDB**：`localhost:8529`，数据库名`xishujuzhen_math_glm52`（通过.env设置ARANGO_DB）
- **Devin CLI sessions.db**：`~/.local/share/devin/cli/sessions.db`（SQLite，含sessions/message_nodes/tool_call_state表）
- **⚠️ 数据库隔离**：本repo用`xishujuzhen_math_glm52`，禁止写入上游的`xishujuzhen_math`
