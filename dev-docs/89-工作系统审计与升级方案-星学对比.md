# 89-工作系统审计与升级方案·星学对比

> **文档定位**：这不是数学大师系统（数学内容）的文档，而是"AI 作为工作者如何组织自己的工作"的元层面文档。审计星学项目已完成的工作系统升级，判断数学项目是否需要同样的升级，并编制方案。
>
> **触发原因**：在与数学项目分别后，星学项目完成了自己的工作系统升级——**把"稀疏矩阵/依赖图/拓扑验证/ArangoDB"这套基座（原本是用来打造星学大师目标系统的）安装到了工作系统自身上**。因为 AI 积累的文档和工作思路也太多了，需要同样的基座来管理自己的工作认知。
>
> **第一次审计的纠正**：我第一次审计时只看到了 master_controller + factory + auditor 那套编排层，误以为那就是工作系统升级的全部。实际上，那套编排层是更早的架构，真正的"基座安装到工作系统自身"的升级是 `xishujuzhen/` 目录下的 `cognition_*.py` 系列——把 AI 自己的工作认知建模为 ArangoDB 中的图结构。

### 1.2 核心机制

#### Capsule 机制（moira_runtime.py）

每次 session start 或 user prompt submit 时，hook 调用 `moira_runtime.py hook <event>`，生成一个 capsule 注入到 AI 上下文中。Capsule 包含：
- 协议审计结果（PASS/FAIL, remainder）
- 任务状态计数（queued/leased/in_progress/completed/failed）
- Worker 状态计数
- 非线性状态（当前阶段、迭代次数、维度覆盖、最低覆盖维度、发现数、未知概念数）
- 停止策略（STOP_ALLOWED / CONTINUE_REQUIRED / REVIEW_REQUIRED）
- 活跃锚点
- 角色命令简报
- 下一步必需动作

**核心价值**：AI 不需要依赖记忆来恢复上下文——capsule 从文件系统实时生成，是"机器派生的控制上下文"，比记忆和终端印象更强。

#### Stop Gate 机制

当 AI 尝试停止时，hook 检查：
- 协议审计是否 PASS
- 是否有 failed/blocked/error 任务
- 是否有 queued/leased/in_progress 任务
- 是否有 busy worker

如果有任何未完成的工作，hook 返回 `block`，阻止 AI 停止。

#### Master-Worker-Auditor 三角色分离

| 角色 | 职责 | Skill |
|---|---|---|
| Master | 协调非线性研究循环，不把项目简化为线性任务列表 | moira-orchestrator |
| Worker | 吸收一个有界经验包，报告形式系统如何演化 | moira-worker |
| Auditor | 审计 Worker 输出是否通过语义和 SOP 门控 | moira-auditor |

#### PathListGate 机制

在处理任何古籍正文前，必须先构建或验证该书的 `full_path_tree.json`（完整路径树），包含稳定 path ID、源文件、行号范围、可验证 hash。没有路径列表，不允许 Worker 处理正文。

#### 自我迭代机制（self_iteration.py）

- 从吸收过程中发现新任务
- 动态调整吸收策略
- 非线性多维度吸收
- 知识图谱构建（算子/集合/命题/关系/概念/发现）

#### 质量门控（quality_gate.py）

- 检查审计记录是否完整
- 检查一致性判定是否有依据
- 检查修正建议是否可执行

### 1.3 星学项目未完成的部分

### 2.3 当前工作模式的痛点

从 POC-1 和 POC-2 的执行经验中提取：

| 痛点 | 表现 | 影响 |
|---|---|---|
| **Session 中断后无法恢复** | POC-2 执行到步骤6时如果 session 中断，无法从 checkpoint 恢复 | 必须从头开始 |
| **Background subagent 写文件失败** | POC-2 中 A组和B'组的 background subagent 无法写入 /Volumes 路径 | 必须用前台 subagent 或主 Agent 代写 |
| **POC 执行全靠主 Agent 手动编排** | 每个步骤都是主 Agent 手动启动 subagent、等待、收集结果 | 效率低，不可复用 |
| **没有 capsule 注入** | 每次 session start 都是白纸，需要读 AGENTS.md 恢复上下文 | 恢复效率低 |
| **没有质量门控** | 评分后没有自动验证审计记录完整性 | 审计记录可能不完整 |
| **没有自我迭代** | 不会从 POC 结果中发现新任务 | 新 POC 必须手动设计 |
| **没有 stop gate** | AI 可能过早停止 | 工作可能遗漏 |

## 三、判断：是否有必要升级

### 3.1 结论：**有必要升级，但不是简单复制，而是针对数学项目特点的重新设计**

### 3.2 理由

**支持升级的理由**：

1. **数学项目的 POC 验证循环已经是多步骤、多角色的非线性工作流**——七步骤工作流（依赖图导入→G'_topo生成→拓扑验证→转译→KC审计→分析→分析覆盖审计）本质上就是 Master-Worker-Auditor 三角色分离的实例。但目前全靠主 Agent 手动编排，没有自动化。

2. **Session 中断风险**——POC-2 执行了 10 个阶段，如果 session 在阶段5中断，无法从 checkpoint 恢复。随着 POC 规模增长（三层提取 POC、跨领域映射 POC），这个风险会越来越大。

3. **Background subagent 写文件问题**——这是一个系统性问题，需要系统性的解决方案（如 checkpoint 机制 + 文件写入重试 + 主 Agent 代写回退）。

4. **Capsule 注入的价值**——数学项目的 capsule 可以包含：当前 POC 进度、ArangoDB 状态、拓扑覆盖验证结果、KC 审计结果。这比读 AGENTS.md 更高效。

5. **自我迭代的潜力**——数学项目可以从 POC 结果中发现新的数学意识节点（如 POC-1 发现了"数值检验意识"的重要性），自动生成新 POC 任务。

**不支持简单复制的理由**：

1. **数学项目的工作模式与星学项目不同**——星学项目是"非线性吸收"（从古籍中吸收知识），数学项目是"POC 验证"（设计实验→执行→评分→落盘）。直接复制星学的 Master-Worker-Auditor 架构不适合。

2. **数学项目已有独特资产**——七步骤工作流 + ArangoDB + 拓扑覆盖验证是数学项目的独特资产，星学项目没有。升级方案应该集成这些资产，而不是用星学的 JSON 文件方式替代。

3. **数学项目的 Worker 角色不同**——星学的 Worker 是"吸收古籍文本"，数学的 Worker 是"做数学证明"。需要不同的思维力模板。

4. **数学项目可以用 ArangoDB 作为状态存储**——星学项目用 JSON 文件（tasks.json, master_state.json 等），数学项目可以用 ArangoDB 图数据库存储任务队列和状态，这更强大。

### 3.3 "更高的升级"的可能性

| 升级方向 | 星学项目 | 数学项目可以做到的更高版本 |
|---|---|---|
| 状态存储 | JSON 文件 | ArangoDB 图数据库（已有） |
| 质量门控 | 审计记录完整性 | 拓扑覆盖验证（TopologyVerifier，已有） |
| 知识图谱 | JSON 文件（knowledge_graph.json） | ArangoDB 图数据库（dg_nodes + dg_edges + kcs） |
| 自我迭代 | 从吸收中发现新任务 | 从 POC 结果中发现新数学意识节点，自动构建依赖图 |
| Worker 思维力 | 形式化思维+定量化+开放性+全息+时代性 | 不变量思维+局部-全局+逼近论+极端检验+数值检验（已有） |
| 计算验证 | 无 | Lean 4 / SageMath（未来） |

## 六、核心审计：cognition 系统（基座安装到工作系统自身）

> **本节是第二次审计的核心内容**。第一次审计只看到了编排层（master_controller + factory + auditor），遗漏了真正的升级——`xishujuzhen/cognition_*.py` 系列。

### 6.1 什么是"基座安装到工作系统自身"

星学项目有两套系统：

| 系统 | 内容 | 基座 |
|---|---|---|
| **目标系统**（星学大师） | 星学知识系统（study-notes/、古籍考据、推命步骤） | 稀疏矩阵/依赖图/拓扑验证/ArangoDB |
| **工作系统**（AI 自己的工作方式） | AI 自己的工作认知（文档积累、工作思路、方法论演进） | **原来没有基座** → 升级后安装了同样的基座 |

升级的核心洞察：**AI 积累的工作文档和工作思路太多了，和星学知识一样需要图结构管理**。所以把目标系统的基座（稀疏矩阵/依赖图/拓扑验证/ArangoDB）安装到工作系统自身上。

### 6.2 cognition 系统的架构

| 组件 | 文件 | 功能 |
|---|---|---|
| **认知单元图** | `cognition_units.json` → ArangoDB `cognition_units` + `cog_edges` + `cog_versions` | 64个认知单元，100条边。认知单元 = AI 自己的工作认知（不是星学知识） |
| **认知验证器** | `cognition_verifier.py` | 图遍历引擎：从种子认知单元出发，沿 depends_on 边遍历，找到所有前置认知。验证 AI 在 session 中加载的认知是否覆盖任务所需 |
| **认知 SDK** | `cognition_sdk.py` | 封装 ArangoDB 操作：查询、审计（版本链/图遍历完整性/覆盖率/约束保留）、修复、POC 回归评分 |
| **认知检查点** | `cognition_checkpoint.py` | CP1-CP6 工作流：种子选择→认知加载→缺口检查→认知捕获→认知图更新→任务-认知映射 |
| **认知审计** | `cognition_audit.py` | 参数化审计 CLI：一键全量审计或单项审计 |
| **认知导入** | `cognition_import.py` | 将认知单元 JSON 导入 ArangoDB |

### 6.3 认知单元是什么

认知单元**不是星学知识**，而是 **AI 对自己工作过程中积累的认知的建模**。例如：

| cog_id | title | category | 说明 |
|---|---|---|---|
| `chart_engine` | 排盘引擎建设 | core | AI 对排盘引擎建设工作的认知 |
| `rules_library` | 格局规则库 | core | AI 对格局规则库建设工作的认知 |
| `formal_system` | 七政四余形式化体系 | core | AI 对形式化体系建设的认知 |
| `spiral_cognition` | 星学意识与螺旋上升的稀疏矩阵 | core | AI 对螺旋上升认知方法的认知 |
| `agents_management` | AGENTS.md管理系统 | core | AI 对 AGENTS.md 管理工作的认知 |
| `poc_methodology` | POC验证方法论 | core | AI 对 POC 验证方法的认知 |

每个认知单元有：
- `cog_id`：唯一标识
- `title`：标题
- `category`：分类（core/process/support）
- `key_cognition`：核心认知摘要
- `source_docs`：载体文档列表（如 ["85"]，指向 dev-docs/85）
- `current_version`：当前版本
- `version_chain`：版本链（认知的演化历史）

### 6.4 CP1-CP6 工作流

| 检查点 | 时机 | 内容 |
|---|---|---|
| CP1 | 工作开始前 | 种子选择：确定本次任务需要哪些种子认知单元 |
| CP2 | 工作开始前 | 认知加载：AQL 图遍历，从种子出发沿 depends_on 边找到所有前置认知 |
| CP3 | 工作开始前 | 缺口检查：验证已加载的认知是否覆盖任务所需，发现遗漏的认知单元 |
| CP4 | 工作结束时 | 认知捕获：检查本次工作是否产生新的工作意识（新方法论/新依赖/新版本/新术语/临场脚本） |
| CP5 | 工作结束时 | 认知图更新：新版本/新边写入 ArangoDB |
| CP6 | 工作结束时 | 任务-认知映射：记录"这个任务用了哪些种子认知单元"，形成经验学习 |

### 6.5 Devin CLI 集成（三 hook）

| Hook | 文件 | 触发时机 | 功能 |
|---|---|---|---|
| SessionStart | `session_start_hook.py` | session 开始 / 上下文压缩后 | 注入工作系统提醒：认知图统计、工作纪律（CP1-CP6）、Stop hook 会强制 CP4 |
| UserPromptSubmit | `prompt_hook.py` | 用户每次提问 | 设置 `work_pending=1`，让 Stop hook 知道本轮工作需要 CP4 检查 |
| Stop | `stop_hook.py` | AI 尝试结束 | 第一次 stop：block + 注入 CP4 检查清单（从 SDK 查稀疏矩阵动态获取）；第二次 stop：检查 git clean |

**Stop hook 的核心设计**：CP4 检查清单不是硬编码的，而是从 ArangoDB 稀疏矩阵动态查询的（`sdk.get_stop_checklist('stop_hook')`）。"未来加新纪律只需在 ArangoDB 加一条边，此方法不用改"——这是基座安装到工作系统的典型体现。

### 6.6 与编排层（master_controller + factory + auditor）的关系

| 层 | 功能 | 与 cognition 系统的关系 |
|---|---|---|
| 编排层（L3） | Master-Worker-Auditor 任务编排 | 更早的架构，管的是"谁做什么任务" |
| cognition 系统 | AI 工作认知的图结构管理 | 新升级，管的是"AI 做工作时需要哪些前置认知" |

两层是互补的：编排层管任务分配，cognition 系统管认知覆盖。但 cognition 系统是更底层的基座——它管的是 AI 工作的前提条件（认知是否充分），而不是任务执行本身。

### 6.8 "更高的升级"的可能性

数学项目在以下维度可以超越星学项目：

| 维度 | 星学项目 | 数学项目可以做到的更高版本 |
|---|---|---|
| 认知覆盖验证 | AQL 集合差集（文字确定性） | **TopologyVerifier 拓扑覆盖验证**（数学确定性，已有） |
| 认知图与目标系统的关系 | 两套图独立（cognition_units 和 dependency_graph 无关） | **两套图共享同一个 ArangoDB 实例**，认知图的节点可以引用数学依赖图的节点 |
| 认知单元的版本链 | 手动维护 | 可以用 POC 评分结果**自动更新版本链**（POC 通过 = 新版本确认） |
| 认知单元的意识节点 | 无（星学的意识节点在 study-notes/星学意识/，不在 cognition_units 中） | **数学项目的意识节点（不变量思维/局部-全局/逼近论/极端检验/数值检验）可以直接作为认知单元**，与数学大师的依赖图共享 |
| 自我迭代 | 从古籍吸收中发现新任务 | **从 POC 评分结果中发现新数学意识节点**，自动构建依赖图 |
