## 1 · 新系统是步骤化的吗？

### 诊断

**表面上是，实质上不彻底。**

当前 study-notes/01-20 的编号暗示了步骤序列，17-流程总图也画了01→13的线性流程。但：

| 编号段 | 定位 | 是否真步骤 | 问题 |
|---|---|---|---|
| 01-13 | 命盘+推限 | ✅ 是步骤 | 有顺序依赖，但未声明依赖关系 |
| 14-16 | 附录（参考表） | ❌ 不是步骤 | 是"被步骤引用的数据表"，不是流程节点 |
| 17 | 流程总图 | ❌ 不是步骤 | 是01-13的元描述，不是流程节点 |
| 18-20 | 专题（女命/凶死/琴堂） | ⚠️ 模糊 | 是"特定场景下的判读子流程"，不是独立步骤 |

**核心问题**：14-20被编入了与01-13相同的编号序列，但它们的性质完全不同。一个真正的步骤化系统，应该区分"流程步骤"和"参考资源"。

### 更新建议

将 study-notes/ 重新分层：

```
study-notes/
├── 流程步骤/（DAG节点，有依赖关系）     ← 原01-13
│   ├── 01-历法基础.md
│   ├── ...
│   └── 13-综合判读.md
├── 参考资源/（被步骤引用的数据表/附录）  ← 原14-17
│   ├── 14-星曜性情详表.md
│   ├── 15-二十八宿五行禽名表.md
│   ├── 16-地支五行与宫主对照.md
│   └── 17-流程总图与待确认事项.md
├── 专题判读/（特定场景的子流程）         ← 原18-20 + 未来扩展
│   ├── 18-女命专论.md
│   ├── 19-凶死与疾病断法.md
│   └── 20-琴堂断法歌诀.md
└── 外部系统/（老系统吸收追踪）           ← 已有
```

**或者**：保持扁平编号，但在每个文件的元数据中声明类型（`类型: 步骤/参考/专题`），并在 README.md 中区分。

## 2 · 新系统是DAG吗？

### 诊断

**不是。当前是线性链表，不是DAG。**

17-流程总图画的是：01→02→03→...→13，纯线性序列。

但实际的七政四余分析流程不是纯线性的：

```
01-历法基础 ──→ 02-星历计算 ──→ 03-宫位系统 ──→ 04-安命安身
                       │                                │
                       ├──→ 05-四柱八字（可并行）  ←─────┘
                       │
                       └──→ 06-化曜（可并行）
                                │
                                ├──→ 07-神煞
                                ├──→ 08-状态判断
                                └──→ 09-格局分析 ←── 04（命主星影响格局判断）
                                          │
                                          ▼
                                    10-限运系统 ←── 04（命宫起限）
                                          │
                                          ▼
                                    11-推限分析 ←── 08（状态影响限运判断）
                                          │
                                          ▼
                                    12-流年推演
                                          │
                                          ▼
                                    13-综合判读 ←── 09+10+11+12（汇聚）
```

真正的DAG有分支（并行步骤）和合并（多入度节点）。当前01-13的线性编号掩盖了这些依赖关系。

### 更新建议

1. **声明依赖关系**：每个步骤文件头部增加 `前置: [02, 04]` / `后继: [06, 07, 08]` 元数据
2. **允许并行步骤**：05-四柱八字和06-化曜可以并行，不必强制顺序
3. **合并节点**：13-综合判读是汇聚节点，依赖09/10/11/12多个步骤的输出
4. **流程图更新**：17-流程总图应改为DAG图（有分支和合并），不是线性链表

## 5 · 吸收时，一条外部内容可能要进入新系统的多个位置吗？

### 诊断

**是的，但当前Check List的多指向标注不够系统化。**

实际检查发现，Check List中已有一些多指向标注（用 `+` 连接），例如：

```
- [x] `星曜躔度歌/角/木-天贵` → study-notes/09-格局分析（引用吸收：示例）+ study-notes/02-星历计算（引用吸收：典型格式）
```

这说明一条躔度规则同时被02（星历计算，作为典型格式示例）和09（格局分析，作为格局规则）吸收。但这种情况是手动发现的，不是系统化检查的。

**典型的一对多场景**：
- "论四时"（二十四要法）→ 01-历法基础（节气概念）+ 05-四柱八字（月令）+ 08-状态判断（令星强弱）
- "度主切于宫主"（论十二宫所守）→ 04-安命安身（度主定义）+ 09-格局分析（格局判断时度主优先）+ 13-综合判读（综合判断原则）
- "煞能为煞"（步天警句）→ 07-神煞（煞星定义）+ 08-状态判断（煞星状态）+ 11-推限分析（限内遇煞）

### 更新建议

1. **Check List标注格式扩展**：允许 `→ study-notes/NN + study-notes/MM + study-notes/KK` 多指向
2. **反向核对脚本升级**：反向核对时，一条引用路径应能匹配多个Check List条目
3. **吸收时主动检查多指向**：吸收一条外部内容时，主动问"这条内容是否影响其他步骤？"
4. **建立"跨步骤概念索引"**：某些核心概念（如"度主"、"令星"、"恩用仇难"）横跨多个步骤，应有独立索引

### 7.2 印度占星学（Jyotisha）的特殊价值

七政四余与印度占星学（Jyotisha）有深厚的同源性。两者都源于巴比伦-希腊天文占星传统，经印度传入中国后与本土术数融合。具体对应关系：

| 七政四余 | 印度占星（Jyotisha） | 对应关系 |
|---|---|---|
| 七政（日/月/木/火/土/金/水） | Navagraha（Surya/Chandra/Guru/Mangala/Shani/Shukra/Budha） | 一一对应 |
| 四余（炁/孛/罗/计） | Rahu/Ketu（+其他暗星） | 部分对应（罗睺/计都直接同名） |
| 二十八宿 | Nakshatra（27宿） | 同源，28宿vs27宿差异 |
| 十二宫 | Rasi（12星座） | 同源 |
| 洞微大限 | Vimshottari Dasha（120年大运） | 可能同源，需深入研究 |
| 庙旺平陷 | dignity（exaltation/debilitation/own sign等） | 概念对应 |
| 格局 | Yoga（行星组合） | 概念对应 |

**吸收策略**：不是把印度占星全盘搬入，而是：
1. 对照确认七政四余中模糊的概念（如四余定义、大限起源）
2. 补充七政四余中缺失的概念（如印度占星的分宫图Bhava对应不等宫位制）
3. 交叉验证共有概念（如庙旺表是否一致）

### 7.3 星盘多圈层设计

**核心思想**：星盘不是单一圈层，而是多层叠加。不同体系（七政四余/印度占星/西占）可以共存在同一张星盘上，通过圈层标识区分。

```
星盘 = {
  "圈层": {
    "L1-七政四余-整宫制": {
      "宫位制": "整宫制",
      "十二宫": [...],
      "星曜": [...],
      "神煞": [...]
    },
    "L2-七政四余-不等宫位制": {
      "宫位制": "Placidus/Koch",
      "十二宫": [...],
      "星曜": [...]
    },
    "L3-印度占星-Nakshatra": {
      "二十七宿": [...],
      "Navagraha": [...],
      "Dasha": [...]
    },
    "L4-西占-黄道十二宫": {
      "星座": [...],
      "行星": [...],
      "Aspects": [...]
    }
  },
  "圈层标识": "L1-七政四余-整宫制"  ← 当前批命时看的圈层
}
```

**设计原则**：
1. **每个圈层有唯一标识名**：如 `L1-七政四余-整宫制`、`L3-印度占星-Nakshatra`
2. **批命时声明看哪个圈层**：可以看一个，也可以同时看多个（跨体系对照）
3. **等宫位和不等宫位可共存**：放在不同圈层，不冲突
4. **圈层间可对照**：同一颗木星在L1（整宫制）可能在寅宫，在L2（不等宫位制）可能在卯宫，两个都显示，批命时说明看哪个

**对新系统的影响**：
- study-notes/03-宫位系统 需要扩展，容纳多宫位制
- study-notes/02-星历计算 需要扩展，容纳不同体系的星历（如印度占星的Nakshatra划分）
- qizheng/chart.py 的 `build_chart()` 输出需要增加"圈层"维度
- 这不是推翻现有系统，而是在现有系统上增加圈层维度

## 8 · 外部系统文献的获取与还原

### 8.1 问题

有些外部系统的文献我们本地没有原文，或者有的是MinerU VLM OCR识别的结果，存在错讹风险。

### 8.2 获取策略

**策略A：网络搜索获取**
- 算准网（suanzhun.net）已有《星平会海》全文，其他典籍也可能有
- 识典古籍（shidian.gujian.com.cn）有部分古籍
- 中国哲学书电子化计划（ctext.org）有部分古籍
- 维基文库有部分古籍

**策略B：AI知识还原**
- AI可以背诵某本书的目录大纲
- 然后细化背诵每一部分（XPATH对应）的内容
- 这样可以"还原"出原书的结构化内容
- 准确性需要交叉验证（多个AI模型比对，或与已有原文比对）

**策略C：MinerU OCR结果校正**
- 用户提供的MinerU VLM OCR结果作为初稿
- 通过网络搜索/AI知识交叉校正
- 标记置信度（高/中/低），低置信度内容待人工确认

**策略D：从已有典籍交叉推断**
- 如果《星平会海》和《果老星宗》都引用了某段内容，可以交叉确认
- 如果多个典籍对同一概念有不同表述，记录差异

### 8.3 文献还原的工作流

```
1. 确定目标典籍
2. 检查本地是否已有原文
   ├── 有 → 直接使用
```

## 11 · 总结

老方案（56）建立了正确的框架，但执行过程中发现了8个需要迭代的问题：

1. **步骤化不彻底**：14-20不是真步骤，需要分层
2. **不是DAG**：当前是线性链表，需要声明依赖关系
3. **反查有缺口**：14-16无标注，01-13有大量无标注行
4. **吸收远未完成**：只做了《星平会海》一部，且自身吸收率36%
5. **多指向不够系统化**：一条内容可能影响多个步骤，需系统化标注
6. **步骤框架需要迭代**：吸收过程中发现需要新增/拆分/调整步骤
7. **需要吸收更多外部系统**：印度占星学/果老星宗/星学大成等，星盘多圈层设计
8. **文献获取需要多策略**：网络搜索/AI知识还原/MinerU校正/交叉推断

**核心认知**：新系统的建设不是一次性工程，而是持续迭代的过程。步骤框架会变，外部系统会扩展，反查覆盖率会提升。关键是建立"允许迭代"的机制，而不是追求一次性完美。
