## 1. 修正目标

从源头消除140号诊断发现的三种系统性断层模式：
- F1"定义了=实现了"：Check List说"实现X"但只定义了类型就勾选
- F2"验证了=完整了"：写了验证函数但不覆盖边界情况就勾选
- F3"Check List覆盖盲区"：Check List本身遗漏来源文档要求

## 2. 修正方法

### 2.1 引入实现深度等级D1—D4

| 等级 | 定义 | 勾选标准 |
|---|---|---|
| D1：定义 | 定义X的类型/schema/枚举 | 类型定义存在且有文档 |
| D2：逻辑 | 定义X的类型 + 写了处理X的可执行逻辑 | 有可执行的函数/方法 |
| D3：测试 | D2 + 有测试覆盖X的全部边界情况 | 测试通过且覆盖边界情况清单 |
| D4：集成 | D3 + X与上下游组件集成验证 | 集成测试通过 |

### 2.2 三条措辞规则

1. 每个"实现X"类Check List项，标注预期深度等级（D1/D2/D3/D4）
2. 每个"验证X"类Check List项，附边界情况清单
3. 每个"覆盖X"类Check List项，明确覆盖标准

### 2.3 勾选格式从二元改为四元

从`[x]/[ ]`改为`[D1]/[D2]/[D3]/[D4]/[ ]`，强制勾选者明确实现深度。

### 2.4 F3检查

对132号做F3检查——重新对照123号§47/§37/§38/§15-16/§31/§22/§18/§23，检查是否遗漏任何要求。

## 4. 修正前后对比示例

### 4.1 F1修正示例（P2-2.3）

**修正前**：
```
- [ ] P2-2.3：实现工作区读写接口
```

**修正后**：
```
- [ ] P2-2.3：实现工作区读写接口 [预期D2]
  - 深度标准：有可执行的WorkspaceStore类，支持create/read/update_workspace
  - 边界情况：空工作区、字段缺失、并发写入、W_t不可直接修改（只能通过Reducer派生）
```

修正前"实现工作区读写接口"可能被误解为"定义了Workspace dataclass就勾选"。修正后明确预期D2深度（有可执行的WorkspaceStore类）和边界情况，消除了F1断层。

### 4.2 F2修正示例（P2-3.3）

**修正前**：
```
- [ ] P2-3.3：验证义务图是DAG（无环，环路在状态商空间处理）
```

**修正后**：
```
- [ ] P2-3.3：验证义务图是DAG（无环，环路在状态商空间处理） [预期D3]
  - 边界情况：自环、双向往返环、多节点环、SCC（强连通分量——不自动释放，产生待审计的SCC）
```

修正前"验证DAG"可能被误解为"写了DFS环检测就勾选"。修正后明确边界情况（包括自环——Phase 1的F3遗漏就是自环），消除了F2断层。

### 4.3 F3修正示例（P2-9.3新增）

**修正前**：无对应项（123号§18的规范化键定义在132号中遗漏）

**修正后**：
```
- [ ] P2-9.3：定义状态等价关系`~_{α,κ}`和规范化键（123号§18，F3修正补充） [预期D2]
  - 状态等价不是万能关系，而是由任务类型κ和抽象级别α参数化的`~_{α,κ}`
  - 首版规范化键至少包括：开放义务的类型化同构类、当前表示ID、已验证核心中的目标相关命题ID、活动分支和证据门状态
  - 规范化键忽略：措辞、变量改名和事件时间
  - 只有规范化键一致，才记为`W_i ~_{α,κ} W_j`
  - 深度标准：有可执行的规范化键计算函数和等价关系判定函数
  - 边界情况：规范化键部分一致、不同抽象级别α下的等价判定、不同任务类型κ下的等价判定
```

## 5. 修正效果

### 5.1 F1风险消除

修正前：132—137号共约40个"实现X"类项存在F1风险（可能被误解为"定义了就勾选"）。

修正后：每个"实现X"类项都标注了预期深度等级（D1/D2/D3/D4），明确"实现"的标准。实现者必须达到标注的深度等级才能勾选。

### 5.2 F2风险消除

修正前：132—137号共约20个"验证X"类项存在F2风险（可能被误解为"写了验证函数就勾选"）。

修正后：每个"验证X"类项都附了边界情况清单，明确验证需要覆盖哪些边界。验证者必须覆盖全部边界情况才能勾选。

### 5.3 F3风险消除

修正前：132号遗漏了123号§18的3项要求（状态等价参数化/规范化键定义/规范化键一致性判定）。

修正后：新增P2-9.3和P2-9.COMP3，覆盖了§18的3项遗漏要求。

### 5.4 审计方法升级

修正前：138号审计是"覆盖性审计"（检查Check List是否提到X），不检查措辞是否能区分"定义"和"实现"。

修正后：新增第11维度"可实现性审计"，在实现前检查措辞是否精确到能区分"定义"和"实现"。

## 6. 后续工作

Phase 2实现时，按D1-D4深度等级逐项验收。每项实现完成后，对照标注的预期深度等级和边界情况清单验证：
- 预期D1：检查类型定义是否存在
- 预期D2：检查可执行逻辑是否存在
- 预期D3：检查测试是否覆盖全部边界情况
- 预期D4：检查集成测试是否通过

1. 每个项的实现深度是否达到标注的预期等级？
2. 每个项的边界情况是否全部覆盖？
3. 每个项的覆盖标准是否满足？

### 6.3 131号Check List的回溯标注

131号（Phase 1 Check List）已完成实现，可以回溯标注D1-D4深度等级，验证Phase 1实现是否达到预期深度。此项工作优先级低，可在Phase 2实现前补充。

## 7. 结论

本次预防性修正从源头消除了140号诊断发现的三种系统性断层模式：
- F1通过引入D1-D4深度等级消除
- F2通过附边界情况清单消除
- F3通过F3检查发现并补充遗漏项消除

132—137号Check List共386项D1-D4标注、346处边界情况、38处覆盖标准，使每个Check List项的"实现"标准从模糊变为精确。

新增的第11维度"可实现性审计"使审计方法从"覆盖性审计"升级为"覆盖性审计+可实现性审计"，在实现前拦截措辞不精确的Check List。

这样下一个Phase实现后审计时，有明确的深度等级作为验收标准，不会再出现"定义了就勾选"的断层。
