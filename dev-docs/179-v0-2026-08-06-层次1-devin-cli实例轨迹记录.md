## 二、数据源调查结果

### 2.1 `--export`选项——层次1的首选实现

devin cli启动时加`--export <PATH>`选项，**每turn自动导出**完整conversation到指定文件。

**实测确认**（2026-08-06）：
```bash
devin --export /path/to/conversation.json -p "回复一个hello"
# → 文件conversation.json被创建，48KB
# → 内容是ATIF-v1.7格式JSON
# → 包含完整steps数组（system/user/agent消息 + timestamp + telemetry）
# → 每turn结束后自动更新
```

**导出格式**（ATIF-v1.7 JSON）：
```json

  "session_id": "tidy-tamarind",
  "agent": {
```

**关键特性**：

- 精简版：含消息文本，**不含**`thinking`字段和`tool_calls`详情

### 2.2 `sessions.db`——深度审计入口

位置：`~/.local/share/devin/cli/sessions.db`（SQLite，9GB）

| 表名 | 记录数 | 内容 |
|---|---|---|
| `sessions` | — | session元数据（id、工作目录、模型、创建时间、标题） |
| `message_nodes` | **807,294** | 完整对话消息树（含parent_node_id构成消息森林） |
| `tool_call_state` | **22,658** | 每次工具调用的完整JSON |
| `prompt_history` | — | 用户输入历史 |

**`message_nodes`表的`chat_message`字段**是完整JSON：

**`tool_call_state`表**包含工具调用的完整输入和输出：
- `tool_call_json`：工具调用的初始JSON（工具名、参数、title、kind）
- `tool_call_update_json`：工具调用的结果JSON（输出内容、状态）

**关键发现**：`thinking`字段记录了AI的内部推理过程——这是层次3（思路轨迹）的核心数据源，但也使sessions.db成为层次1的深度审计入口。

### 2.3 `transcripts/`目录——自动备份

位置：`~/.local/share/devin/cli/transcripts/`（100个JSON文件，ATIF-v1.7格式）

每个session一个文件，自动生成，格式与`--export`导出的一致。作为自动备份使用，不需要额外配置。

### 2.4 tmux pipe-pane——兜底

`tmux pipe-pane`命令把pane的所有输出实时管道到shell命令：

```bash
# 开始记录
tmux pipe-pane -o -t <session:window.pane> 'cat >> /path/to/runs/${RUN_ID}/tmux.log'

# 停止记录
tmux pipe-pane -t <session:window.pane>
```

- `-O`：pane输出管道到命令（默认）
- `-o`：只在没有现有pipe时才开启（可toggle）

**特点**：
- 纯文本（含ANSI转义序列），需清洗才能结构化分析
- 不区分用户输入和AI输出——所有终端输出混在一起
- 但作为兜底非常可靠——即使`--export`和sessions.db出问题，tmux log也在

### 2.5 数据源对比

| 对比项 | `--export` | sessions.db | tmux pipe-pane |
|---|---|---|---|
| 实时性 | ✅ 每turn导出 | ❌ 需事后查询 | ✅ 实时 |
| 结构化 | ✅ ATIF JSON | ✅ SQLite表 | ❌ 纯文本+ANSI |
| 路径可控 | ✅ 任意路径 | ❌ 固定位置 | ✅ 任意路径 |
| 含thinking | ❌ 精简版无 | ✅ 完整 | ❌ 无 |
| 含tool_calls详情 | ❌ 精简版无 | ✅ 完整 | ❌ 只有终端输出 |
| 含工具输出 | ❌ | ✅ tool_call_state | ✅ 终端输出 |
| 运行中可读 | ✅ 文件可直接读 | ⚠️ SQLite并发读 | ✅ 文件可直接读 |
| 配置复杂度 | 极低（一个参数） | 零（自动） | 低（tmux命令） |

## 三、方案设计

### 3.1 三层数据采集策略

```
启动devin cli实例时：
    devin --export runs/${RUN_ID}/conversation.json -- "数学问题..."

同时（在tmux中启动时）：
    tmux pipe-pane -o -t <pane> 'cat >> runs/${RUN_ID}/tmux.log'

自动（devin cli自己记录）：
    sessions.db ← message_nodes + tool_call_state（无需配置）
    transcripts/ ← 自动备份（无需配置）
```

**三个数据源的分工**：
| 数据源 | 角色 | 用途 |
|---|---|---|
| `--export` conversation.json | **实时监控** | 运行中可读，每turn更新，适合实时观察 |
| sessions.db | **深度审计** | 事后查询thinking + tool_calls + 工具输出 + 性能指标 |
| tmux pipe-pane | **兜底** | 纯文本终端输出，只在其他两个出问题时才需要 |

### 3.2 run_id关联

**关联方式**：`--export`路径包含`run_id`，使导出文件天然与系统run关联。

```bash
# 启动数学大师测试run
RUN_ID="run_20260806_001"
mkdir -p runs/${RUN_ID}

# devin cli导出路径包含run_id
devin --export runs/${RUN_ID}/conversation.json -- "数学问题..."

# tmux log也放在同一目录
tmux pipe-pane -o -t <pane> "cat >> runs/${RUN_ID}/tmux.log"

# 系统的ArangoDB事件也记录run_id（层次2负责）
# → EventCapture记录session_id，使系统事件与devin cli session关联
```

**run目录结构**：
```
runs/
  run_20260806_001/
    conversation.json    ← --export导出（ATIF-v1.7）
    tmux.log             ← tmux pipe-pane兜底
    system_events.json   ← 层次2的系统执行日志（待179/180定义）
    audit_report.md      ← 层次2的审计报告（待182定义）
```

### 3.3 从sessions.db提取深度数据

`--export`的conversation.json是精简版（无thinking/tool_calls详情）。深度审计需要从sessions.db提取。

**提取逻辑**（伪代码）：
```python
import sqlite3, json

def extract_session_trajectory(session_id: str):
    """从sessions.db提取完整session轨迹"""
    conn = sqlite3.connect("~/.local/share/devin/cli/sessions.db")

    # 1. session元数据
    session = conn.execute(
        "SELECT id, working_directory, model, created_at, title FROM sessions WHERE id = ?",
        (session_id,)
    ).fetchone()

    # 2. 消息树（含thinking + tool_calls）
    messages = conn.execute(
        "SELECT node_id, parent_node_id, chat_message, created_at FROM message_nodes WHERE session_id = ? ORDER BY node_id",
        (session_id,)
    ).fetchall()

    # 3. 工具调用状态（含输出结果）
    tool_calls = conn.execute(
        "SELECT tool_call_id, tool_call_json, tool_call_update_json FROM tool_call_state WHERE session_id = ?",
        (session_id,)
    ).fetchall()

    # 4. 组装完整轨迹
    trajectory = {
        "session": session,
        "messages": [json.loads(m[2]) for m in messages],
        "tool_calls": [{"id": tc[0], "call": json.loads(tc[1]), "result": json.loads(tc[2]) if tc[2] else None} for tc in tool_calls],
    }
    return trajectory
```

**session_id的获取**：从`--export`的conversation.json中读取`session_id`字段。

### 6.3 发现的问题

1. **`tee`不是`pipe-pane`**：本次用`tee`记录tmux输出，只捕获了AI的最终输出文本（4.6KB），没有捕获终端的全部操作过程。下次应该用`tmux pipe-pane`替代`tee`。
2. **message_nodes有重复**：node 31/32、35/36内容完全相同——可能是devin cli的内部重试或缓存机制。审计工具需要去重。
3. **tool_call_state的update content为空**：tool_call_update_json的content数组为空，工具结果实际在message_nodes的role=tool消息中。审计工具应该从message_nodes提取tool结果，而非tool_call_state。
4. **timestamp精度不够**：所有node的created_at都是同一秒（05:23:11），无法区分消息间的精确时间顺序。需要用node_id排序而非timestamp。
5. **system消息重复**：node 0-30中有大量重复的system消息（同样的content出现4次），可能是devin cli的context窗口管理机制。审计工具应该只显示唯一的system消息。
