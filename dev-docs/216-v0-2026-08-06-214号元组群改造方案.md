## 1. 为什么要改造

214号文档目前是一个~1000行的单一文档，包含8个章节+8.14节。问题：

1. **混合了理论和操作**——路线B、Level连续谱是always-on认知；DFS执行、回溯、数据持久化是操作流程。混在一起，AI每次都要读全部，但大部分内容只在特定阶段需要。

2. **操作流程太长**——如果做成单一Skill，从预演到引导执行到回溯到持久化，可能跨越压缩边界。Skill后续内容丢失，AI不知道下一步该做什么。

3. **没有区分"每次必须知道"和"特定场景需要"**——违反元组核心原理。

## 3. 元组群设计

### 3.1 元组群名称

`guided-math-solving`（引导式数学解题）

### 3.2 规则（always-on，放在`.devin/rules/guided-math-solving.md`）

规则包含：
1. 路线B决策（一句话+指向214号文档）
2. Level连续谱定义（一段+指向214号文档）
3. 最小知识传递目标（公式+一句话）
4. DFS树结构定义（一段）
5. 回溯铁律（新session不原地回溯）
6. 节点同一性（路径同一性为主+判断适用性）
7. **元组群目录**（5个Skill的有序列表+何时加载+阶段间传递）

### 3.3 Skill拆分

| Skill | 名称 | 覆盖的214章节 | 做什么 | 产出 |
|---|---|---|---|---|
| Skill 1 | `guided-rehearsal` | 第3-6章+第4章4.4 | 给定题目，生成模拟QA序列和极致提示集合 | `rehearsal.md` |
| Skill 2 | `guided-session-launch` | 第8章工程部分+solver-tmux-launch | 准备work_dir、problem.txt、启动tmux+devin+--export | session信息 |
| Skill 3 | `guided-interaction` | 第5-6章+第8章8.4-8.6 | 连续发问框架执行，从L1到L5，包括提示注入 | dfs_tree.json更新 |
| Skill 4 | `guided-backtrack` | 第8章8.9-8.12 | 新session+重放Q序列+在岔口换方向 | dfs_tree.json更新+新session |
| Skill 5 | `guided-data-persist` | 第8章8.13-8.14 | 记录到dfs_tree.json+ArangoDB+文件系统 | ArangoDB记录+文件系统归档 |

### 3.4 元组群目录（在规则中）

```
## 元组群：guided-math-solving（引导式数学解题）

**触发条件**：需要用最小知识传递引导AI做数学题时

**整体目标**：通过连续启发式提问，以最大Level SUM引导AI完成解题

**Skill目录**（按执行顺序）：
1. Skill guided-rehearsal：预演——给定题目，生成模拟QA序列和极致提示集合
   - 产出落盘到 runs/<run_id>/rehearsal.md
2. Skill guided-session-launch：启动session——准备work_dir+problem.txt+tmux+devin+--export
   - 产出：session_id, export_path, work_dir
3. Skill guided-interaction：交互引导——连续发问框架执行（核心Skill）
   - 读取 rehearsal.md 获取候选提示
   - 产出：dfs_tree.json 持续更新
   - 执行过程中可能调用 Skill 4 和 Skill 5
4. Skill guided-backtrack：回溯——新session+重放Q序列+在岔口换方向
   - 读取 dfs_tree.json 获取回溯点和Q序列
   - 产出：新session + dfs_tree.json更新
   - 回溯后回到 Skill 3 继续引导
5. Skill guided-data-persist：数据持久化——记录到ArangoDB+文件系统归档
   - 读取 dfs_tree.json + export文件
   - 产出：ArangoDB完整记录 + 文件系统归档
   - 在 Skill 3 每轮交互后调用，也在实验结束时调用

**阶段间传递**：
- 1→2：rehearsal.md（模拟QA+极致提示集合）
- 2→3：session信息（session_id, export_path, work_dir）
- 3↔4：dfs_tree.json（当前树状态+回溯点）
- 3↔5：dfs_tree.json + export文件 → ArangoDB

**何时进入下一阶段**：
- 1完成（rehearsal.md落盘）→ 加载2
- 2完成（session启动）→ 加载3
- 3执行中遇到死路 → 加载4 → 4完成后回到3
- 3每轮交互后 → 调用5持久化
- 3完成（AI给出正确解答或确认无法推进）→ 调用5做最终持久化
```

### 3.5 为什么这样拆分

**Skill 1（预演）独立**：预演是一个完整的思考过程——读题、拆解步骤、生成提示集合。它的产出（rehearsal.md）是后续引导的参考。预演不需要tmux/session，纯思考+落盘。

**Skill 2（启动session）独立**：这是一个工程操作——清理work_dir、写problem.txt、启动tmux+devin+--export。操作明确、时间短、不会跨越压缩边界。

**Skill 3（交互引导）是核心**：连续发问框架的执行。这是最长的Skill——从L1观察到L5推进，可能多轮交互。但它每轮交互都是独立的（发Q→等A→判断状态→决定下一步），每轮之间通过dfs_tree.json传递状态，不依赖Session上下文传递。即使压缩了，AI读dfs_tree.json就能恢复当前状态。

**Skill 4（回溯）独立**：回溯是一个明确的操作——启动新session、重放Q序列、在岔口换方向。操作明确，不依赖当前Session的上下文（依赖dfs_tree.json）。

**Skill 5（数据持久化）独立**：记录到ArangoDB+文件系统归档。操作明确，可以在任何时间点调用。

### 3.6 Skill 3如何避免压缩问题

Skill 3是最长的，可能跨越压缩边界。解决方案：

1. **Skill 3本身只包含框架**——六层渐进发问的框架、提示注入的规则、状态判断的标准。这些内容短（<2000字），压缩后仍可见。

2. **具体提示文本在rehearsal.md中**——Skill 3读取rehearsal.md获取候选提示，不把所有提示放在Skill中。

3. **每轮交互的状态在dfs_tree.json中**——AI读dfs_tree.json就知道当前在哪个节点、哪些候选已试过、Level SUM是多少。不依赖Session上下文。

4. **每轮交互后调用Skill 5持久化**——即使Session压缩了，数据已经落盘。
