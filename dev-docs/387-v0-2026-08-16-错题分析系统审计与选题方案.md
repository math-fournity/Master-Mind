## 一、核心理念

### 1.1 审计不是重做一遍

**审计 ≠ 重做分析。** 这是本方案的核心约束。

- **重做分析** = 对每道题重新读原题+标准解答+AI thinking，重新判断d1/d2——成本极高，且本质上是在质疑分析AI的能力，等于否定整个系统
- **审计** = 检查结果集的质量属性——不重新分析任何一道题，不读原题，不读thinking，只检查结果集本身的内部一致性、完备性、可操作性、分布合理性

**类比**：财务审计不是重新做账，而是检查账目的内部一致性、凭证完备性、异常项。同理，分析结果审计不是重新分析，而是检查结果的内部一致性、字段完备性、异常项。

### 1.2 分阶段处理，每个阶段都是devin cli Pipe

**三个Pipe，各自有提示词，各自用devin cli执行，不用关键词匹配。**

| Pipe | 输入 | 做什么 | 不做什么 | 提示词文件 |
|---|---|---|---|---|
| **Pipe 1：分析Pipe**（现有） | 原题+标准解答+AI thinking | 判定d1/d2，产出d1_exp/d2_exp | 不考虑选题 | `templates/analysis_agents_md.md`（现有） |
| **Pipe 2：审计Pipe**（新增） | Pipe 1的分析结果（d1/d2/d1_exp/d2_exp等全部字段） | 检查结果集质量属性（完备性/一致性/可操作性） | 不读原题，不读thinking，不重新判定d1/d2 | `templates/audit_agents_md.md`（新增） |
| **Pipe 3：选题Pipe**（新增） | Pipe 2审计通过的结果 + Mid-Hint选题标准 | 判定每道题是否适合Mid-Hint，按批次分组 | 不读原题，不读thinking，不重新判定d1/d2 | `templates/selection_agents_md.md`（新增） |

**关键区别**：
- 三个Pipe都不读原题、不读thinking——Pipe 2和Pipe 3只读Pipe 1的分析结果文本
- 三个Pipe都用devin cli+提示词——不用关键词匹配
- Pipe 3的提示词包含完整的Mid-Hint选题理念（局部-全局切换、7种卡点类型、3个批次）
- 各Pipe解耦，各自可独立迭代——Pipe 1的分析结果是通用资产，不只服务于Mid-Hint

**并发约束**：系统整体并发最多5个。一个Pipe算1个并发。三个Pipe串行执行（不并行），每个Pipe内部并发5个devin cli实例。

### 1.3 为什么不把选题理念融合到Pipe 1

因为Pipe 1的分析结果是**通用资产**——不只服务于Mid-Hint。如果Pipe 1的提示词中写死了Mid-Hint选题理念，分析结果就被Mid-Hint绑定了，将来如果有其他选题标准（如其他TellCore实验），就需要重新分析。

分阶段处理的好处是：**Pipe 1做客观分析，Pipe 2做质量审计，Pipe 3做选题判定——各Pipe解耦，各自可独立迭代。**

### 1.4 选题理念来自哪里

选题理念来自eight-system的Mid-Hint预注册文档（`eight-system/runs/midhint/preregistration.md`）§1.9和`full_analysis.py`的判定逻辑。

**原始选题理念是二元判定**（preregistration.md §1.9原文）：

> bare失败有两种原因，只有第一种适合测试：
> - **方向出错**：AI的thinking中走了错误方向，没有使用目标TellCore机制（局部-全局切换）→ **适合**
> - **token不够**：AI的thinking中已经在正确方向上（使用了局部-全局切换），但token用尽 → **不适合**

**判定方法**（§1.9原文）：
> 如果AI的thinking中完全没有出现目标方向的关键词（如mod p/二次剩余/p-adic），说明AI方向出错了；如果AI的thinking中出现了目标方向但没完成proof，说明AI方向对了但token不够。

**这是二元判定：要么AI走了局部-全局切换方向（不管走多远），要么没走。没有中间地带。**

### PARTIAL_PROGRESS不纳入选题

Pipe 1的提示词中定义了PARTIAL_PROGRESS（"AI识别了一些关键想法但missed关键转折点"），这是错题分析系统自己加的中间地带，**不在原始选题理念中**。

从Mid-Hint选题角度看，这个中间地带不存在：
- 如果AI的thinking中出现了局部-全局切换方向的关键词（mod p/二次剩余/p-adic），说明AI走了这个方向——更接近TOKEN_LIMIT
- 如果AI的thinking中完全没有出现这些关键词，说明AI没走这个方向——DIRECTION_ERROR
- "识别了一些关键想法但missed关键转折点"——如果这些"关键想法"是局部-全局切换方向的，那就是TOKEN_LIMIT；如果不是，那就是DIRECTION_ERROR

**Pipe 3选题时**：
- d1=DIRECTION_ERROR → 适合（AI没走局部-全局切换方向）
- d1=TOKEN_LIMIT → 不适合（AI走了局部-全局切换方向但token不够）
- d1=CONNECTION_ERROR → 不适合（技术失败）
- d1=PARTIAL_PROGRESS → **不纳入选题**（原始选题理念中没有这个类别）

### 选题的三个条件

**选出"标准解答需要局部-全局表示切换，但AI没有走这个方向"的题。**

三个条件缺一不可：
1. **标准解答的关键转折点用了局部-全局切换**（mod p/p-adic/QR/CRT/LTE/有限域）——这是TellCore v0的机制
2. **AI没有走局部-全局切换的方向**——AI走了别的方向（d1=DIRECTION_ERROR）
3. **AI的失败是数学失败，不是技术失败**——排除CONNECTION_ERROR

这个理念完整地写入Pipe 3的提示词中，不写入Pipe 1的提示词中。

## 三、Pipe 2：审计Pipe

### 3.1 定位

**审计Pipe检查Pipe 1分析结果的质量属性，不重新分析。**

审计Pipe的devin cli实例收到的输入是：Pipe 1的分析结果文本（d1/d2/d1_exp/d2_exp/ai_direction_summary/standard_solution_key_technique/confidence）。审计AI不读原题、不读thinking、不读标准解答——只读Pipe 1的分析结果，检查其质量属性。

### 3.2 审计检查项

审计AI对每条分析结果检查以下5类质量属性：

**A类：字段完备性**
- A1：d1非空且合法（∈ {DIRECTION_ERROR, TOKEN_LIMIT, CONNECTION_ERROR, PARTIAL_PROGRESS}）
- A2：d1_exp非空且长度≥50 chars
- A3：d2非空且合法（d1=DE/PP时；d2∈10种合法类型）
- A4：d2_exp非空且长度≥50 chars
- A5：ai_direction_summary非空
- A6：standard_solution_key_technique非空

**B类：内容完整性**
- B1：d1_exp/d2_exp中不含XML标签泄漏（`</dimension`或`<dimension`）
- B2：d1_exp/d2_exp中不含模板占位符泄漏（"1-3 sentences"/"ONE_OF:"）
- B3：d1_exp/d2_exp不过短（≥50 chars）

**C类：内部一致性**
- C1：d1/d2逻辑一致（d1=CONNECTION_ERROR时d2可为null；d1=DE/PP/TL时d2应有值）
- C2：d1_exp与d1判定一致（d1_exp描述的失败类型与d1标签匹配）
- C3：d2_exp与d2分类一致（d2_exp描述的技巧与d2标签匹配）

**D类：可操作性**
- D1：d1_exp可操作（长度≥100 chars且含至少一个动词——identified/missed/explored/used/went）
- D2：d2_exp可操作（长度≥100 chars且含至少一个数学术语）
- D3：ai_direction_summary可操作（描述了AI具体走了什么方向）
- D4：standard_solution_key_technique可操作（描述了标准解答的具体技巧）

**E类：重复检测**
- E1：同一problem_id是否有多条结果（审计AI标记，由脚本去重）

### 3.3 审计状态判定

| 审计状态 | 判定规则 | 是否进入选题池 |
|---|---|---|
| **通过** | A1-A6全通过 + B1-B3全通过 + C1-C3全通过 | ✅ 进入 |
| **通过-可选题** | 通过 + d1=DIRECTION_ERROR + D1-D4全通过 | ✅ 优先选题 |
| **不通过-解析失败** | A1不通过（d1=null或非法） | ❌ 不进入 |
| **不通过-不完整** | A2-A6任一不通过 | ❌ 不进入 |
| **不通过-内容损坏** | B1-B2不通过（XML泄漏/占位符泄漏） | 修复后重新审计 |
| **不通过-不一致** | C1-C3不通过 | ❌ 不进入（分析结果不可信） |
| **不通过-不可操作** | D1-D4不通过但A-C通过 | 标记为"通过但不可选题" |

## 四、Pipe 3：选题Pipe

### 4.1 定位

**选题Pipe从审计通过的结果中，按Mid-Hint选题标准判定每道题是否适合Mid-Hint，并按批次分组。**

选题Pipe的devin cli实例收到的输入是：Pipe 1的分析结果文本 + Pipe 2的审计状态。选题AI不读原题、不读thinking、不读标准解答——只读分析结果文本和审计状态，基于Mid-Hint选题理念做选题判定。

### 4.2 选题理念（写入Pipe 3提示词）

**核心命题**（来自Mid-Hint预注册§1.1）：
> 非特化Hint在半路注入场景下，能否在正交题面上有效启发AI把正确解题方向推理出来。

**TellCore v0定义**（来自`src/tellcores/local_global_switch.yaml`）：
> 当问题在当前表示下陷入困境时，尝试切换到局部表示（Z/pZ或Q_p），在局部表示下寻找隐藏的代数结构，将局部发现提升为全局结论。

**选题标准**：
1. **d1=DIRECTION_ERROR**——AI走了错误方向（不是token不够，不是技术失败）
2. **d2属于局部-全局切换类型**——标准解答用了局部-全局切换：
   - mod_p_grouping / mod_p_non_obvious / multi_step_mod_p（mod p取模）
   - quadratic_residue_euler（二次剩余+Euler准则）
   - p_adic_valuation（p-adic赋值）
   - lte_lemma（LTE提升）
   - crt（CRT多模数组合）
   - finite_field_structure（有限域结构）
   - permutation_polynomial（有限域上的置换多项式）
3. **d2=other的处理**——选题AI读d2_exp和standard_solution_key_technique的**语义**（不是关键词匹配），判断标准解答是否涉及局部-全局切换。如果涉及，判定属于哪个子类型。

**排除标准**：
- d1=TOKEN_LIMIT——AI方向对了，Hint无用武之地
- d1=CONNECTION_ERROR——技术失败
- d1=PARTIAL_PROGRESS——不纳入选题（原始选题理念中没有这个类别，见§1.4）
- d2=other且标准解答不涉及局部-全局切换——TellCore v0的direction对这道题没有指导价值

### 4.3 选题批次分组

| 批次 | d2类型 | Mid-Hint需求 | 现有题数 | 预估（含d2=other再分类） |
|---|---|---|---|---|
| 批次1（低难度） | mod_p_grouping | 4+ | 28 | 28+ |
| 批次2（中难度） | mod_p_non_obvious + p_adic_valuation + multi_step_mod_p | 3+ | 13 | 13+ |
| 批次3（高难度） | quadratic_residue_euler + crt + lte_lemma | 4+ | 15 | 15+（d2=other中135题含LTE） |
| 可扩展 | finite_field_structure + permutation_polynomial | — | 14 | — |

### 4.4 选题Pipe的提示词设计

`templates/selection_agents_md.md`（新增）：

```
# Selection Task

You are a problem selection assistant for the Mid-Hint experiment.
You will decide whether a problem is suitable for the Mid-Hint experiment.

**CRITICAL CONSTRAINTS:**
- Do NOT use any tools. Do NOT write files. Do NOT execute commands.
- All information you need is in your prompt above.
- Output your selection decision directly in your response.
- End with: ### SELECTION COMPLETE

## Mid-Hint Experiment Background

The Mid-Hint experiment tests whether a non-specific hint ("switch to local
representation: Z/pZ or Q_p, find hidden algebraic structure, lift to global
conclusion"), injected mid-trajectory, can correct an AI's wrong direction.

## Selection Criteria

A problem is SUITABLE for Mid-Hint if ALL three conditions hold:
1. d1=DIRECTION_ERROR — the AI went in a wrong direction
2. The standard solution uses local-global representation switching
   (mod p / p-adic / QR+Euler / LTE / CRT / finite field structure)
3. The AI did NOT attempt this local-global switching direction

A problem is NOT SUITABLE if:
- d1=TOKEN_LIMIT (AI was on the right track, hint has no value)
- d1=CONNECTION_ERROR (technical failure)
- d1=PARTIAL_PROGRESS — NOT suitable (this category does not exist in the
  original selection criteria; if the AI touched the local-global switching
  direction at all, it's TOKEN_LIMIT; if not, it's DIRECTION_ERROR)
- The standard solution does NOT use local-global switching (TellCore v0's
  direction has no guiding value for this problem)

## d2=other Handling

If d2=other, read d2_exp and standard_solution_key_technique CAREFULLY
(semantic understanding, not keyword matching). Determine:
- Does the standard solution use local-global representation switching?
- If yes, which subtype (mod_p_grouping / mod_p_non_obvious / ... / lte_lemma)?
- If no, the problem is NOT suitable for Mid-Hint

## Batch Assignment

If suitable, assign to a batch:
- Batch 1 (low difficulty): mod_p_grouping
- Batch 2 (medium): mod_p_non_obvious, p_adic_valuation, multi_step_mod_p
- Batch 3 (high): quadratic_residue_euler, crt, lte_lemma
- Extended: finite_field_structure, permutation_polynomial

## Output Format

<selection>
  <problem_id>{pid}</problem_id>
  <suitable>YES/NO</suitable>
```

## 六、关键设计决策

### 6.1 为什么三个Pipe都用devin cli

**因为判断需要语义理解，关键词匹配不够准确。**

- Pipe 2审计的C2/C3检查（d1_exp与d1判定是否一致、d2_exp与d2分类是否一致）需要语义理解——关键词匹配无法判断"d1_exp描述的失败类型是否与d1标签匹配"
- Pipe 3选题的d2=other处理需要语义理解——判断"d2_exp和standard_solution_key_technique描述的技巧是否涉及局部-全局切换"不是关键词匹配能准确做的

**devin cli的成本**：每题一个devin cli实例，并发5，1982条审计约需6-8小时（按Pipe 1的经验，每题5分钟以内，并发5）。选题只对审计通过的题（预估1500条左右），约需5-6小时。三个Pipe串行执行，总成本约15-20小时——分阶段运行，可接受。

### 6.2 为什么审计不是重做分析

**审计检查的是结果集的质量属性，不检查每道题的判定是否正确。**

- 重做分析要回答："这道题的d1应该是DIRECTION_ERROR还是TOKEN_LIMIT？"——需要读原题+标准解答+thinking
- 审计要回答："这条结果的字段是否完备？内容是否完整？d1_exp与d1标签是否一致？"——只需要检查结果集本身

**审计能发现的问题**：
- 字段缺失/不完整 → 系统性bug
- XML标签泄漏 → parse_xml bug
- d1/d2不一致 → 模板指令不清晰
- d2_exp与d2标签不匹配 → 分析AI分类错误
- 重复题 → 去重逻辑缺失

**审计不能发现的问题**（也不应该试图发现）：
- d1判定是否准确（需要读thinking——这是重做分析）
- d2分类是否准确（需要读标准解答——这是重做分析）

### 6.3 为什么d2=other的再分类在Pipe 3做

**因为再分类需要Mid-Hint选题理念的语义判断。**

d2=other的960条中，哪些涉及局部-全局切换？这个问题不是纯客观的——它取决于"局部-全局切换"的定义，而"局部-全局切换"的定义来自TellCore v0。Pipe 1的分析AI不知道TellCore v0，所以它把无法归入10种类型的题都分到other。Pipe 3的选题AI知道TellCore v0，所以它能从d2_exp和standard_solution_key_technique的语义中判断是否涉及局部-全局切换。

**再分类不改变Pipe 1的分析结果**——Pipe 3的选题AI只输出选题判定（suitable/batch/d2_reclassified），不修改analysis_results集合中的d2字段。如果需要修改d2字段，是后续工作。

### 6.4 选题时的人工确认范围

**Pipe 3产出选题清单后，对被选中的题（预估30-50道）做人工确认。** 读d1_exp/d2_exp判断是否真的适合Mid-Hint。这是30-50题的人工确认，不是1982题的人工确认。

## 七、与现有工作的关系

### 7.1 与Pipe 1（10轮打磨）的关系

10轮打磨验证了Pipe 1的**形式质量**（XML格式、占位符、d1/d2一致等）。Pipe 2审计是**全量内容质量**的规范化检查。打磨是迭代改进过程，审计是一次性全量验证。

### 7.2 与full_analysis.py的关系

full_analysis.py用关键词匹配做判定（标准解答含TellCore关键词 + thinking不含 → DIRECTION_ERROR），覆盖6181题，产出236道候选题。Pipe 1用devin cli做判定，覆盖1982题，产出1071道DIRECTION_ERROR。Pipe 3选题用devin cli做判定，从Pipe 1的结果中按Mid-Hint标准选题。

**full_analysis.py的236道候选题与Pipe 1的1982条结果的关系**：两者是独立的两套数据。full_analysis.py的关键词匹配是粗粒度的，Pipe 1的devin cli分析是细粒度的。Pipe 3选题时，可以对照full_analysis.py的236道候选题——如果Pipe 3选出的题与full_analysis.py的候选题重叠度高，说明两套方法互相验证。

### 7.3 与Mid-Hint预注册的关系

Pipe 3产出选题清单，作为Mid-Hint实验的输入。Mid-Hint预注册中的11道预判题作为**基准对照**——如果Pipe 3对这11道题的选题判定与预判一致，说明Pipe 3可信。

### 7.4 与eight-system的关系

本方案完成eight-system非特化研究的中断点（选题阶段），使研究可以继续推进到Mid-Hint实验执行（正交出题→bare跑→脉络提取→Hint注入→对照实验）。

## 八、已确认的设计决策

1. **重复题去重规则**：在Pipe 2启动前用脚本自动去重（`audit_collector.py`中）。规则：confidence=high > 字段完整性（7个字段非空数最多的）> 最新时间。被淘汰的结果标记为"重复-已去重"但不删除。去重是确定性规则，不需要语义判断，用脚本做不用devin cli。

2. **d2=other再分类后不修改analysis_results**：Pipe 3只输出选题判定（suitable/batch/d2_reclassified），不修改Pipe 1的d2字段。Pipe 3的d2再分类结果放在selection_results集合中，作为Pipe 3自己的产出。Pipe 1的分析结果保持原样，不被Pipe 3修改。如果将来需要更新d2字段，是单独的工作。

3. **PARTIAL_PROGRESS不纳入选题**：原始选题理念是二元判定（方向出错 vs token不够），PARTIAL_PROGRESS是Pipe 1自己加的中间地带，不在原始选题理念中。Pipe 3选题时d1=PARTIAL_PROGRESS → 不纳入。

4. **并发永远是5个**：系统整体并发最多5个，一个Pipe算1个。三个Pipe串行执行，每个Pipe内部并发5。

## 九、Pipe 3分类逻辑审查（2026-08-17追加）

> **背景**：Pipe 3选题系统实现并单例测试通过后，对其分类逻辑做完备性和合理性审查。

### 9.1 审查结论

| 维度 | 评价 | 说明 |
|---|---|---|
| 子类型完备性 | 基本OK | 9种子类型覆盖Z/pZ和Q_p范围内的主要技术，other类别兜底 |
| PARTIAL_PROGRESS处理 | 合理 | 二元判定逻辑成立（见§1.4），PARTIAL_PROGRESS不纳入选题是正确的设计 |
| 批次难度分配 | 缺乏依据 | 分级是先验硬编码，应基于实验数据经验性验证 |
| 判断信号充分性 | **核心局限** | Pipe 3的准确性 ≤ Pipe 1描述质量 × Pipe 3自身判断准确性 |

### 9.2 子类型完备性

9种子类型（mod_p_grouping / mod_p_non_obvious / multi_step_mod_p / quadratic_residue_euler / p_adic_valuation / lte_lemma / crt / finite_field_structure / permutation_polynomial）覆盖了TellCore v0 hint范围内（Z/pZ和Q_p）的主要技术。

**边缘情况**：
- Hensel引理：可归入p_adic_valuation（都是Q_p相关）
- mod p^k直接分析：可归入multi_step_mod_p
- other类别仍然存在作为兜底

**结论**：完备性基本OK，不需要修改。

### 9.3 PARTIAL_PROGRESS处理——撤回质疑

我最初质疑"PARTIAL_PROGRESS一刀切会漏题"，但审查§1.4后**撤回此质疑**。

§1.4的论证是正确的：**原始选题理念是二元判定**——要么AI走了局部-全局切换方向（不管走多远），要么没走。PARTIAL_PROGRESS是Pipe 1自己加的中间地带，但从Mid-Hint选题角度看：
- 如果AI的thinking中出现了局部-全局切换方向的关键词 → TOKEN_LIMIT（方向对了）
- 如果AI的thinking中完全没有这些关键词 → DIRECTION_ERROR（方向错了）
- "识别了一些关键想法但missed关键转折点"——如果这些想法是局部-全局切换方向的，那就是TOKEN_LIMIT；如果不是，那就是DIRECTION_ERROR

**二元判定逻辑成立，PARTIAL_PROGRESS不纳入选题是正确的设计。**

### 9.4 批次难度分配——需经验验证

当前批次分配（mod_p_grouping=低，quadratic_residue_euler=高，等）是先验硬编码，缺乏依据。

**建议**：不修改当前分配，但在Pipe 3产出后，统计各批次的实际通过率/失败模式，用实验数据验证或修正难度分级。这是后续迭代工作，不阻塞当前Pipe 3运行。

### 9.5 判断信号充分性——核心局限

**这是Pipe 3最根本的局限**。选题AI只看到两个文本字段：
- `d2_explanation`：Pipe 1分析AI对标准解答关键技术的描述
- `standard_solution_key_technique`：Pipe 1分析AI对标准解答技术的描述

选题AI**不看到原题、不看到标准解答、不看到AI的thinking**。它的判断完全依赖Pipe 1分析AI的描述质量。

**二阶误差问题**：Pipe 3的准确性 ≤ Pipe 1的准确性 × Pipe 3自身的判断准确性。

**风险**：
- Pipe 1描述不清楚 → Pipe 3无法准确判断
- Pipe 1描述错误（如把crt题标成other，描述也写歪）→ Pipe 3跟着错
- Pipe 1漏掉关键技术信息 → Pipe 3判NOT SUITABLE，但其实应该SUITABLE

**缓解措施**：
1. Pipe 2审计已经过滤了Pipe 1中字段不完整/内容损坏/不一致的结果——Pipe 3只处理PASS_SELECTABLE的结果，质量有保证
2. 51个已有明确d2子类型的题不需要Pipe 3——这些题的d2分类是Pipe 1直接给出的，Pipe 3只用于667个d2=other的再分类
3. 如果Pipe 3的再分类结果与人工判断差异大，可以考虑给Pipe 3补充原题信息（但这会增加prompt体积和API成本）

**结论**：判断信号充分性是已知局限，但通过Pipe 2审计前置过滤 + 51个已分类题不需要Pipe 3，风险可控。如果后续验证发现Pipe 3准确性不足，再考虑补充信号。
