## 一、核心理念

### 1.1 审计不是重做一遍

**审计 ≠ 重做分析。** 这是本方案的核心约束。

- **重做分析** = 对每道题重新读原题+标准解答+AI thinking，重新判断d1/d2——成本极高，且本质上是在质疑分析AI的能力，等于否定整个系统
- **审计** = 用系统化的、可批量执行的检查规则，验证分析结果作为整体的质量——不重新分析任何一道题，不读原题，不读thinking，只检查结果集本身的内部一致性、完备性、可操作性、分布合理性

**类比**：财务审计不是重新做账，而是检查账目的内部一致性、凭证完备性、异常项。同理，分析结果审计不是重新分析，而是检查结果的内部一致性、字段完备性、异常项。

### 1.2 全量审计，不是抽样

**1982条结果全部审计。** 理由：

1. **审计是自动化的**——检查规则都是可脚本化的，1982条用脚本几秒跑完，不存在"成本太高"的问题
2. **抽样会漏掉系统性问题**——比如XML标签泄漏144条（7%），如果抽样24题可能完全漏掉
3. **选题需要全量基础**——选题要从全量结果中选，不能从抽样中选

### 1.3 审计必须规范化

**审计不是随意抽查，而是有明确标准、可执行脚本、可复现的规范化流程。** 规范化要求：

1. **明确的审计标准**——每个检查项有精确的通过/不通过判定规则
2. **可执行的审计脚本**——全量检查用脚本自动执行，不依赖人工逐题判断
3. **可复现的审计结果**——同样的输入+同样的脚本=同样的审计结论
4. **审计报告有固定格式**——每条结果有明确的审计状态（通过/不通过/需人工复查）

### 1.4 选题是审计的延续

**选题不是独立于审计的工作，而是审计的延续。** 审计产出"哪些分析结果可信"，选题从可信结果中按Mid-Hint标准筛选。如果审计发现某条结果不可信，这条结果不进入选题池。

**选题本身也是审计**——选题时检查"d2分类是否覆盖了Mid-Hint需要的卡点类型"，这本身就是对分析系统完备性的审计。

## 三、审计规范

### 3.1 审计检查项（全量自动化）

**A类：字段完备性检查**

| 检查ID | 检查项 | 判定规则 | 不通过时的处理 |
|---|---|---|---|
| A1 | d1非空 | dimension1_verdict != null且 != '' | 标记为"解析失败"，不进入选题池 |
| A2 | d1_exp非空 | dimension1_explanation != null且长度>0 | 标记为"不完整" |
| A3 | d2非空（d1=DE/PP时） | d1∈{DIRECTION_ERROR, PARTIAL_PROGRESS} → d2 != null且 != '' | 标记为"d1/d2不一致" |
| A4 | d2_exp非空 | dimension2_explanation != null且长度>0 | 标记为"不完整" |
| A5 | ai_direction_summary非空 | ai_direction_summary != null且长度>0 | 标记为"不完整" |
| A6 | standard_solution_key_technique非空 | standard_solution_key_technique != null且长度>0 | 标记为"不完整" |

**B类：取值合法性检查**

| 检查ID | 检查项 | 判定规则 | 不通过时的处理 |
|---|---|---|---|
| B1 | d1合法值 | d1 ∈ {DIRECTION_ERROR, TOKEN_LIMIT, CONNECTION_ERROR, PARTIAL_PROGRESS} | 标记为"无效d1值" |
| B2 | d2合法值 | d2 ∈ {mod_p_grouping, mod_p_non_obvious, quadratic_residue_euler, lte_lemma, p_adic_valuation, multi_step_mod_p, crt, permutation_polynomial, finite_field_structure, other} | 标记为"无效d2值" |

**C类：内容完整性检查**

| 检查ID | 检查项 | 判定规则 | 不通过时的处理 |
|---|---|---|---|
| C1 | XML标签泄漏 | d1_exp/d2_exp中不含`</dimension`或`<dimension` | 标记为"XML泄漏"，用parse_xml修复 |
| C2 | 模板占位符泄漏 | d1_exp/d2_exp中不含"1-3 sentences"/"ONE_OF:"/"Your 1-3 sentence" | 标记为"占位符泄漏" |
| C3 | d1_exp过短 | d1_exp长度 >= 50 chars | 标记为"过短" |
| C4 | d2_exp过短 | d2_exp长度 >= 50 chars | 标记为"过短" |

**D类：一致性检查**

| 检查ID | 检查项 | 判定规则 | 不通过时的处理 |
|---|---|---|---|
| D1 | d1/d2逻辑一致 | d1=CONNECTION_ERROR时d2可为null；d1=DE/PP/TL时d2应有值 | 标记为"逻辑不一致" |
| D2 | 重复题去重 | 同一problem_id有多条结果时，保留confidence=high且字段最完整的最新一条 | 标记被淘汰的为"重复-已去重" |

**E类：可操作性检查（用于选题）**

| 检查ID | 检查项 | 判定规则 | 不通过时的处理 |
|---|---|---|---|
| E1 | d1_exp可操作性 | d1_exp长度 >= 100 chars且含至少一个动词（identified/missed/explored/used/went...） | 标记为"不可操作" |
| E2 | d2_exp可操作性 | d2_exp长度 >= 100 chars且含至少一个数学术语 | 标记为"不可操作" |
| E3 | d2=other再分类 | d2=other但d2_exp/standard_solution_key_technique中含明确d2类型关键词（mod p/LTE/CRT/p-adic/quadratic residue/finite field） | 标记为"建议再分类"+建议d2类型 |

### 3.2 审计状态判定

每条结果经过A-E类检查后，得到一个审计状态：

| 审计状态 | 判定规则 | 是否进入选题池 |
|---|---|---|
| **通过** | A1-A6全通过 + B1-B2全通过 + C1-C4全通过 + D1通过 | ✅ 进入 |
| **通过-可选题** | 通过 + d1=DIRECTION_ERROR + E1-E2通过 | ✅ 优先选题 |
| **通过-需再分类** | 通过 + d2=other + E3触发 | ✅ 进入（再分类后） |
| **修复后通过** | C1/D2不通过但可自动修复 | 修复后进入 |
| **不通过-解析失败** | A1不通过（d1=null） | ❌ 不进入 |
| **不通过-不完整** | A2-A6任一不通过 | ❌ 不进入 |
| **不通过-无效值** | B1/B2不通过 | ❌ 不进入 |

### 3.3 审计产出

1. **`audit_results`集合**（ArangoDB）——每条analysis_result对应一条审计记录：
   ```
   {
     analysis_result_key: "...",
     problem_id: "...",
     audit_status: "通过" / "修复后通过" / "不通过-...",
     check_results: {A1: "pass", A2: "pass", ..., E3: "suggest_reclassify:mod_p_grouping"},
     issues_found: ["XML泄漏", "d2=other建议再分类"],
     fix_applied: ["XML泄漏已修复"]  # 如果自动修复了
   }
   ```

2. **`audit_summary.md`**——审计汇总报告：
   - 总检查数 / 通过数 / 不通过数 / 修复后通过数
   - 各检查项的通过率
   - 主要问题分布
   - 选题池大小（通过+可选题+需再分类）

## 四、选题规范

### 4.1 选题标准

**从审计通过的结果中选题，不直接从analysis_results选题。**

**维度1：d1筛选**
- **首选**：d1=DIRECTION_ERROR（方向出错，Hint有纠正价值）
- **备选**：d1=PARTIAL_PROGRESS（部分正确但missed关键转折——需E1-E2可操作性检查通过）
- **排除**：d1=TOKEN_LIMIT / CONNECTION_ERROR / None

**维度2：d2筛选（按Mid-Hint批次分组）**

| 批次 | d2类型 | Mid-Hint需求 | 现有题数 | 再分类后预估 |
|---|---|---|---|---|
| 批次1（低难度） | mod_p_grouping | 4+ | 28 | 28+（d2=other中923题含modular，部分可再分类） |
| 批次2（中难度） | mod_p_non_obvious + p_adic_valuation + multi_step_mod_p | 3+ | 3+2+8=13 | 13+（d2=other中86题含p-adic） |
| 批次3（高难度） | quadratic_residue_euler + crt + lte_lemma | 4+ | 4+11+0=15 | 15+（d2=other中135题含LTE，135题含quadratic） |
| 可扩展 | finite_field_structure | — | 13 | — |

**LTE lemma缺口**：现有0条d2=lte_lemma，但d2=other中有135题含"LTE"关键词。E3检查会把这些题标记为"建议再分类:lte_lemma"，审计后自动补充到批次3。

### 4.2 d2=other再分类规则

**不是重新分析，而是基于已有d2_exp和standard_solution_key_technique文本做关键词分类。** 规则：

| 优先级 | 关键词模式 | 建议d2 | 说明 |
|---|---|---|---|
| 1 | "LTE" / "lifting the exponent" | lte_lemma | 明确提到LTE |
| 2 | "quadratic residue" / "Legendre" / "Euler's criterion" | quadratic_residue_euler | 明确提到QR |
| 3 | "Chinese remainder" / "CRT" | crt | 明确提到CRT |
| 4 | "p-adic" / "v_p" / "valuation" | p_adic_valuation | 明确提到p-adic |
| 5 | "finite field" / "F_p" / "Z/pZ" / "GF(" | finite_field_structure | 明确提到有限域 |
| 6 | "mod p" / "modular arithmetic" / "mod " + 数字 | mod_p_grouping或mod_p_non_obvious | 需进一步判断p是否显然 |
| 7 | 以上都不匹配 | other | 保持原分类 |

**注意**：再分类是**建议**，不是最终判定。再分类后的题在选题时需要人工确认（但不是全量人工确认——只确认被选中的题）。

### 4.3 选题产出

1. **`selection_results`集合**（ArangoDB）——选题清单：
   ```
   {
     problem_id: "...",
     selected_batch: "批次1" / "批次2" / "批次3" / "可扩展",
     d1: "DIRECTION_ERROR",
     d2: "mod_p_grouping",
     d2_reclassified: false,  // 是否经过再分类
     selection_reason: "d1=DE, d2=mod_p_grouping, 审计通过",

     d1_exp: "...",  // 从analysis_result复制

     ai_direction_summary: "...",
     standard_solution_key_technique: "..."
   }
   ```

2. **`selection_summary.md`**——选题汇总：
   - 各批次题数
   - d2分布
   - 再分类统计
   - 与Mid-Hint预注册11道预判题的对照

## 六、关键设计决策

### 6.1 为什么全量审计可行

**因为审计是自动化的。** A-E类检查全部可以用脚本执行，1982条几秒跑完。成本不在"审计全量"上，而在"写审计脚本"上——写一次脚本，跑全量是零成本。

### 6.2 为什么审计不是重做分析

**审计检查的是结果集的质量属性，不检查每道题的判定是否正确。**

- 重做分析要回答："这道题的d1应该是DIRECTION_ERROR还是TOKEN_LIMIT？"——需要读原题+标准解答+thinking
- 审计要回答："这条结果的字段是否完备？取值是否合法？内容是否完整？是否有XML泄漏？d2分类是否与d2_exp内容一致？"——只需要检查结果集本身

**审计能发现的问题**：
- 字段缺失/不完整 → 系统性bug（如解析失败）
- XML标签泄漏 → parse_xml bug
- d1/d2不一致 → 模板指令不清晰
- d2=other但含明确关键词 → 分析AI分类不够细致
- 重复题 → 去重逻辑缺失

**审计不能发现的问题**（也不应该试图发现）：
- d1判定是否准确（需要读thinking才能判断——这是重做分析）
- d2分类是否准确（需要读标准解答才能判断——这是重做分析）

**对于"判定准确性"的验证**：用交叉验证——与已有的`analyze_failure.py`预判结果对照。如果错题分析系统对1631/1843等题的分析结果与`analyze_failure.py`的预判一致，说明系统判定准确。这不是全量验证，而是基准验证。

### 6.3 d2=other再分类不是重做分析

**再分类基于已有文本做关键词匹配，不重新分析。** 分析AI已经写了d2_exp和standard_solution_key_technique——这些文本中包含了标准解答的关键技巧描述。再分类只是从这些已有文本中提取关键词，判断是否应该归入更具体的d2类型。

**再分类不改变d2_exp的内容**——只改变d2分类标签。如果关键词匹配不到，保持other。

### 6.4 选题时的人工确认范围

**不是全量人工确认，只确认被选中的题。** 审计+选题后，可能有30-50道题进入Mid-Hint选题清单。对这些题做人工确认——读d1_exp/d2_exp判断是否真的适合Mid-Hint。这是30-50题的人工确认，不是1982题的人工确认。

## 七、与现有工作的关系

### 7.1 与10轮打磨的关系

10轮打磨验证了**形式质量**（XML格式、占位符、d1/d2一致等）。本方案的审计是**全量形式质量+内容完备性+可操作性**的规范化检查。打磨是迭代改进过程，审计是一次性全量验证。

### 7.2 与Mid-Hint预注册的关系

本方案产出选题清单，作为Mid-Hint实验的输入。Mid-Hint预注册中的11道预判题作为**基准对照**——如果错题分析系统对这11道题的分析结果与预判一致，说明系统可信。

### 7.3 与eight-system的关系

本方案完成eight-system非特化研究的中断点（选题阶段），使研究可以继续推进到Mid-Hint实验执行。
