> **状态**：DRAFT（待用户确认）

## 一、问题定义

### 1.1 我们中断在哪里

eight-system非特化研究的中断点在Mid-Hint实验的选题阶段。具体状态：

1. **已完成**：Mid-Hint实验预注册文档（`eight-system/runs/midhint/preregistration.md`），定义了选题标准（维度1：方向出错vs token不够；维度2：7种卡点类型）
2. **已完成**：11道DIRECTION_ERROR题的预判（1631/1843/1709/1962等），用`analyze_failure.py`脚本验证
3. **已完成**：错题分析系统建设+10轮打磨（50题次），产出1982条分析结果
4. **未完成**：从1982条分析结果中系统性地选题——把分析结果转化为可执行的Mid-Hint实验选题清单

### 1.2 选题为什么是审计

**选题过程本身就是对错题分析系统前半部分工作的审计。** 原因：

1. **选题要验证分析结果的准确性**——选题时需要抽查"这道题真的是DIRECTION_ERROR吗？d2分类准确吗？"如果分析结果不准确，选题就会选错题
2. **选题要验证分析结果的完备性**——选题需要d2分类覆盖Mid-Hint的7种卡点类型。如果某些卡点类型没有足够的题，说明分析系统的d2分类有盲区
3. **选题要验证分析结果的可操作性**——选题时需要从分析结果中提取"这道题的卡点是什么、标准解答的关键技巧是什么、AI走错了什么方向"——这些信息必须足够具体，能指导正交出题和Hint设计

**如果选题工作进行不下去，说明分析系统的产出质量不够——选题工作暴露了分析系统的问题。**

### 1.3 本方案的目标

把错题分析系统从"产出分析结果"延伸到"产出选题清单"，并在选题过程中审计分析质量。具体产出：

1. **选题清单**：按Mid-Hint卡点类型分组的题目列表，每道题附带选题理由（d1/d2/d1_exp/d2_exp）
2. **审计报告**：对分析结果的准确性/完备性/可操作性的审计结论
3. **系统架构补充**：在错题分析系统中增加"选题器"和"审计器"两个组件

## 三、方案设计

### 3.1 系统架构补充

在错题分析系统中增加两个组件：

```
现有架构：
data_collector → analysis_launcher → result_collector → aggregator
                                                        ↓
                                                   analysis_results集合

补充架构：
                                                        ↓
                                              analysis_results集合
                                                        ↓
                                            ┌─────────────────────┐
                                            │   审计器 (auditor)   │ ← 抽查分析质量
                                            └─────────────────────┘
                                                        ↓
                                            ┌─────────────────────┐
                                            │   选题器 (selector)  │ ← 按选题标准筛选
                                            └─────────────────────┘
                                                        ↓
                                              selection_results集合
                                              （选题清单+选题理由）
```

**审计器（auditor）**：
- 输入：analysis_results中的抽样题目
- 操作：对照原题+标准解答+AI thinking，验证d1/d2/d1_exp/d2_exp的准确性
- 输出：audit_report（每道题的审计结论：通过/不通过/审计理由）

**选题器（selector）**：
- 输入：analysis_results + audit_report + Mid-Hint选题标准
- 操作：按d1（DIRECTION_ERROR/PARTIAL_PROGRESS）+ d2（卡点类型）筛选，排除审计不通过的题
- 输出：selection_results（选题清单，按Mid-Hint批次分组）

### 3.2 审计器设计

**审计目标**：验证分析结果的准确性、完备性、可操作性。

**审计方法**：抽样深度验证（不是全量验证——1982条太多，抽样即可）。

**抽样策略**：
1. **分层抽样**：按d2分类分层，每层抽2-3题（覆盖所有d2类型）
2. **重点抽样**：Mid-Hint选题标准涉及的d2类型（mod_p_grouping/mod_p_non_obvious/quadratic_residue_euler/p_adic_valuation/multi_step_mod_p/crt）每层抽3题
3. **边界抽样**：d1=PARTIAL_PROGRESS的题抽3题（验证PARTIAL_PROGRESS是否也适合Mid-Hint）

**审计检查项**（每道题）：

| 检查项 | 通过标准 | 不通过时的处理 |
|---|---|---|
| d1准确性 | 对照AI thinking，d1判定正确 | 记录误判，分析AI为什么判错 |
| d2准确性 | 对照标准解答，d2分类正确 | 记录误分类，分析AI为什么分错 |
| d1_exp可操作性 | d1_exp足够具体，能指导Hint设计 | 记录"不可操作"，需要重新分析 |
| d2_exp可操作性 | d2_exp准确描述了标准解答的关键技巧 | 记录"不可操作"，需要重新分析 |
| 选题适用性 | 这道题真的适合Mid-Hint实验吗 | 记录"不适合"，给出理由 |

**审计产出**：
- `audit_report.json`：每道题的审计结论
- `audit_summary.md`：审计汇总（通过率、常见问题、建议）

### 3.3 选题器设计

**选题标准**（从Mid-Hint预注册文档继承）：

**维度1：d1筛选**
- **首选**：d1=DIRECTION_ERROR（方向出错，Hint有纠正价值）
- **备选**：d1=PARTIAL_PROGRESS（部分正确但missed关键转折——需审计判断是否适合）
- **排除**：d1=TOKEN_LIMIT（方向对了，Hint无用武之地）
- **排除**：d1=CONNECTION_ERROR（技术失败，非数学失败）

**维度2：d2筛选（按Mid-Hint批次分组）**

| 批次 | d2类型 | 需求题数 | 现有题数 | 缺口 |
|---|---|---|---|---|
| 批次1（低难度） | mod_p_grouping | 4+ | 28 | 无（充足） |
| 批次2（中难度） | mod_p_non_obvious + p_adic_valuation + multi_step_mod_p | 3+ | 3+2+8=13 | 无（充足） |
| 批次3（高难度） | quadratic_residue_euler + crt | 4+ | 4+11=15 | 无（充足） |
| **缺口** | **lte_lemma** | **2+** | **0** | **需要补充** |

**LTE lemma缺口处理**：
- 方案A：在960条d2=other中搜索LTE lemma相关题（grep "LTE"/"Lifting The Exponent"/"lifting the exponent"）
- 方案B：在full-analysis-v2的queued但未分析的2554题中，优先分析标准解答含LTE lemma的题
- 方案C：放弃LTE lemma卡点类型，用其他卡点类型替代
- **推荐方案A**——先在现有结果中搜索，成本最低

**选题产出**：
- `selection_results.json`：按批次分组的选题清单
- 每道题附带：problem_id / d1 / d2 / d1_exp / d2_exp / ai_direction_summary / standard_solution_key_technique / audit_status
- `selection_summary.md`：选题汇总（各批次题数、选题理由、审计结论）

### 3.4 d2=other的处理

960条DIRECTION_ERROR + d2=other是最大的未分类池。处理策略：

1. **不全部重新分析**——960条太多，成本高
2. **按Mid-Hint适用性筛选**——d2=other的题中，哪些涉及局部-全局切换（TellCore v0的机制）？
3. **筛选方法**：在d2_exp中搜索关键词（mod / p-adic / valuation / 局部 / residue / CRT / 有限域 / 同余）
4. **筛选出的题**：重新分析或人工分类，判断是否适合Mid-Hint
5. **未筛选出的题**：不涉及局部-全局切换，不适合Mid-Hint，排除

## 五、关键设计决策

### 5.1 为什么审计在选题之前

**审计是选题的前提**——如果分析结果不准确，选题就会选错题。先审计验证质量，再基于审计通过的结果选题。

**但审计不是全量的**——1982条全量审计成本太高。用分层抽样24题，如果通过率>80%，认为整体质量可信，可以选题。如果通过率<80%，需要分析常见问题并修正后再选题。

### 5.2 为什么不直接用Mid-Hint预注册中的11道题

Mid-Hint预注册中已有11道DIRECTION_ERROR题的预判（1631/1843/1678/2095/2111/2843/2040/1964/1929/2024/2921）。这些题是用`analyze_failure.py`脚本逐题分析的，不是用错题分析系统批量分析的。

**不直接用的原因**：
1. **审计需求**——用户要求审计错题分析系统的产出，11道预判题不在错题分析系统的1982条结果中（或只有部分在）
2. **扩展需求**——错题分析系统有1982条结果，可能发现比11道预判题更好的选题
3. **一致性需求**——所有选题应该来自同一个数据源（错题分析系统），而不是混合数据源

**但11道预判题作为基准**——如果错题分析系统对这11道题的分析结果与`analyze_failure.py`的预判一致，说明系统可信。如果不一致，需要调查原因。

### 5.3 PARTIAL_PROGRESS是否适合Mid-Hint

Mid-Hint预注册只选了DIRECTION_ERROR的题。但PARTIAL_PROGRESS的152题中，有些可能是"AI识别了正确框架但missed关键转折点"——这种题也适合Mid-Hint（Hint引导AI发现关键转折点）。

**处理方式**：在审计阶段抽3题PARTIAL_PROGRESS，判断是否适合Mid-Hint。如果适合，在选题阶段纳入。

## 七、与现有工作的关系

### 7.1 与错题分析系统10轮打磨的关系

10轮打磨验证了分析系统的**形式质量**（XML格式正确、无占位符泄漏、d1/d2一致等）。本方案的审计验证**内容质量**（d1/d2判定是否准确、d1_exp/d2_exp是否可操作）。形式质量+内容质量=完整质量保证。

### 7.2 与Mid-Hint预注册的关系

本方案产出选题清单，作为Mid-Hint实验的输入。Mid-Hint实验的后续步骤（正交出题、Phase A/B/C）不变。

### 7.3 与eight-system非特化研究的关系

本方案完成eight-system非特化研究的中断点（选题阶段），使研究可以继续推进到Mid-Hint实验执行。
