# 110-大规模依赖图可操作性方案——三层访问架构

> **文档定位**：109号方案v3估计~325000节点。大师（AI）只有20万token上下文。本文档解决"325000节点如何放进20万token"的可操作性问题。
>
> **核心结论**：这不仅是可以解决的，而且方法论本身已经包含了答案——稀疏矩阵的本质就是"在具体研究点上只有一小部分被激活"。需要做的是把这个隐含原理显式化为一套工程架构。

## 一、问题陈述

### 1.1 看似矛盾

| 维度 | 数量 |
|---|---|
| 依赖图总节点 | ~325000 |
| AI上下文窗口 | ~200000 token |
| 每个节点平均token | ~200（含定义、依赖、属性） |
| 朴素全量装入 | 325000 × 200 = 6500万token → **不可能** |

### 1.2 其实不是矛盾

这个"矛盾"基于一个错误假设：**大师需要同时看到所有节点**。

但方法论的核心信念已经否定了这个假设：

> **稀疏性：总知识量很大，但在每个具体研究点上，只有一小部分被激活。大师的功力不在于知道多少，而在于知道在什么时候激活什么。**

> **关键约束：依赖图的大小必须被控制在一个合理范围内。不是把整个三维稀疏矩阵一次性呈现给AI，而是提取当前上下文相关的子图。**

325000节点是"大师脑中的总知识量"，不是"大师同时激活的知识量"。一个人类数学大师脑中可能有等价于几十万节点的数学知识，但他解决一个具体问题时，同时激活的可能只有几百个概念——这和20万token的上下文窗口在同一个数量级。

**真正的问题不是"如何装下325000节点"，而是"如何在325000节点中找到该激活的那几百个"。**

## 二、Token预算分析

### 2.1 20万token的分配

| 用途 | Token预算 | 占比 |
|---|---|---|
| 系统指令+方法论提示 | ~10K | 5% |
| 问题陈述 | ~5K | 2.5% |
| **依赖图子图（核心）** | **~80K** | **40%** |
| 数学意识（L2/L3思维模式） | ~15K | 7.5% |
| 计算工具输出（SymPy/SageMath） | ~10K | 5% |
| **AI推理空间（输出）** | **~80K** | **40%** |

**依赖图子图预算：~80K token**

### 2.2 80K token能装多少节点

| 节点详细度 | 每节点token | 80K预算可装节点数 |
|---|---|---|
| 全细节（定义+证明概要+依赖+交叉引用） | ~300 | ~270 |
| 中细节（陈述+关键依赖） | ~100 | ~800 |
| 轻量（名称+一句话描述+领域） | ~30 | ~2700 |
| 极简（ID+公式） | ~10 | ~8000 |

**结论**：80K token可以装270-800个全/中细节节点，或2700-8000个轻量/极简节点。这远超POC验证所需——POC-2用18节点就实现了显著增益，POC-7用71节点实现100%覆盖。

### 2.3 与人类大师的类比

| 维度 | 人类大师 | AI大师（20万token） |
|---|---|---|
| 总知识量 | ~几十万概念 | 325000节点（ArangoDB） |
| 同时激活 | ~几百概念（工作记忆） | ~270-800节点（80K token子图） |
| 查阅能力 | 知道去哪本书查 | ArangoDB AQL查询 |
| 查阅速度 | 分钟级（翻书） | 秒级（数据库查询） |

AI大师的"同时激活"容量与人类大师在同一个数量级，甚至更大。**20万token不是限制，是足够的。**

## 三、三层访问架构

### 3.1 核心架构

```
┌─────────────────────────────────────────────────────────────┐
│                    ArangoDB (325000节点)                      │
│                    冷存储层 (Cold Layer)                      │
│  全部节点+边+原文。永久存储，永不全部装入上下文。              │
└──────────────────┬──────────────────────────────────────────┘
                   │
         ┌─────────┴─────────┐
         │  种子选择 + 子图提取  │
         │  (经典计算，秒级)     │
         └─────────┬─────────┘
                   │
┌──────────────────┴──────────────────────────────────────────┐
│                 子图 (200-800节点)                            │
│                 热工作集 (Hot Layer)                          │
│  当前问题相关的依赖子图。装入上下文，AI直接推理。              │
│  Token预算：~80K                                              │
└──────────────────┬──────────────────────────────────────────┘
                   │
                   │ AI推理中需要更多信息时
                   ↓
┌──────────────────────────────────────────────────────────────┐
│              按需查询 (On-Demand Query)                       │
│              温查询层 (Warm Layer)                            │
│  AI说"展开节点X" → ArangoDB查询 → 返回X的邻居/依赖/原文       │
│  每次查询返回~10-50节点，追加到热工作集。                      │
└──────────────────────────────────────────────────────────────┘
```

### 3.2 三层详解

#### 冷存储层 (Cold Layer) — ArangoDB

| 属性 | 值 |
|---|---|
| 存储内容 | 全部325000节点 + 全部边 + 原文 |
| 存储位置 | ArangoDB (dg_nodes/dg_edges/knowledge_docs) |
| 访问方式 | AQL图遍历查询 |
| 是否在上下文中 | **否**，永远不全部装入 |
| 角色 | 大师的"书架"——所有知识都在这里，但不会同时全部打开 |

#### 热工作集 (Hot Layer) — 上下文中的子图

| 属性 | 值 |
|---|---|
| 存储内容 | 当前问题相关的200-800节点子图 |
| 存储位置 | AI上下文窗口（~80K token） |
| 生成方式 | 种子选择 → 图遍历 → 剪枝 → 装入 |
| 角色 | 大师的"工作台"——当前正在思考的内容 |

#### 温查询层 (Warm Layer) — 按需展开

| 属性 | 值 |
|---|---|
| 存储内容 | ArangoDB中的任意节点/子图 |
| 访问方式 | AI在推理中发起查询："展开节点X" / "查询X的依赖" |
| 返回量 | 每次查询~10-50节点，追加到热工作集 |
| 角色 | 大师的"翻书"——思考中发现需要更多信息，去书架查 |

### 3.3 与人类大师的对应

| 人类大师 | AI大师 |
|---|---|
| 脑中总知识（记忆） | ArangoDB 325000节点（冷存储） |
| 工作记忆（同时思考的概念） | 热工作集 200-800节点（上下文子图） |
| "我去翻一下那本书" | 温查询："展开节点X" |
| "我记得这个概念在哪个领域" | 层次索引（见下文） |

## 四、种子选择——如何找到该激活的节点

这是325000节点可操作性的**关键环节**。当前系统（1697节点）可以用随机选题+全遍历，但325000节点不行。需要精确的种子选择。

### 4.1 三级种子选择机制

```
数学问题输入
    ↓
┌─ 第一级：层次索引定位 ──────────────────────┐
│  3层主题树（~20K token，可常驻上下文）         │
│  领域 → 子领域 → 主题                          │
│  输出：问题所属的2-5个主题                      │

│  （预计算节点embedding，存储在ArangoDB）       │
```

### 4.3 语义检索（第二级）

**预计算**：
- 对325000个节点，每个节点计算一个embedding向量（使用text-embedding模型）
- 存储在ArangoDB中（新增字段`embedding`）

**运行时**：
- 问题输入 → 计算问题embedding
- ArangoDB AQL + cosine similarity → 返回top-20最近节点
- 这20个节点就是种子

**为什么需要语义检索**：
- 层次索引只定位到"主题"级别（~100-300节点），不够精确
- 语义检索直接定位到"最相关的具体节点"
- 两者互补：层次索引给领域上下文，语义检索给精确种子

### 4.4 图遍历扩展（第三级）

**已有能力**：`cognition_sdk_math.py`的`traverse(seeds, max_depth=7)`已经实现了图遍历。

**需要升级**：
- 深度控制：默认max_depth=3（不是7），避免爆炸
- 宽度剪枝：每个节点只保留top-K个最相关的邻居
- Token预算剪枝：遍历过程中累计token，达到70K时停止
- 螺旋环路优先：如果遍历路径经过螺旋环路节点，优先保留（方法论要求）
- 跨领域边优先：跨领域映射边是高价值连接，优先保留

```python
# 伪代码
def extract_subgraph(seeds, token_budget=80000):
    subgraph = {}
    frontier = seeds
    total_tokens = 0
    
    for depth in range(max_depth):
        next_frontier = []
        for node in frontier:
            neighbors = query_neighbors(node)
            # 剪枝：只保留top-K最相关邻居
            neighbors = prune(neighbors, k=10, 
                             prefer_spiral=True, 
                             prefer_cross_domain=True)
            for n in neighbors:
                if n.id not in subgraph:
                    node_tokens = estimate_tokens(n)
                    if total_tokens + node_tokens > token_budget:
                        return subgraph  # 预算用完
                    subgraph[n.id] = n
                    total_tokens += node_tokens
                    next_frontier.append(n)
        frontier = next_frontier
        if not frontier:
            break
    
    return subgraph
```

## 五、多分辨率节点存储

### 5.1 问题

不是所有325000节点都需要同等细节。一个OEIS序列节点（A000045: Fibonacci）和一个核心定理节点（Hilbert零点定理）需要的描述量完全不同。

### 5.2 四级分辨率

| 级别 | 适用节点 | 内容 | 每节点token | 估计节点数 |
|---|---|---|---|---|
| **R1: 全细节** | 核心定理、重要猜想、关键方法 | 定义+陈述+证明概要+依赖+交叉引用+L2/L3思维模式 | ~300 | ~5000 |
| **R2: 中细节** | 标准定理、常见方法 | 陈述+关键依赖+领域标签 | ~100 | ~20000 |
| **R3: 轻量** | 概念、OEIS序列、Wikipedia条目 | 名称+一句话描述+领域 | ~30 | ~200000 |
| **R4: 极简** | OEIS序列（大部分）、历史人物 | ID+公式/名称 | ~10 | ~100000 |

### 5.3 动态升级

节点默认以最低必要分辨率存储。当图遍历到达某节点时，按需升级：

```
图遍历到达节点X（R3轻量）
    ↓
AI判断需要更多细节
    ↓
"展开节点X" → ArangoDB查询X的R2或R1版本
    ↓
替换上下文中X的R3版本为R2/R1版本
```

**类比**：人类大师看到"椭圆曲线"这个词（R3），如果当前问题需要，他会回忆起Weierstrass方程、群律、Mordell定理等细节（R1）。不需要时，"椭圆曲线"这个词就够了（R3）。

## 六、渐进式展开协议

### 6.1 AI的查询能力

AI在推理过程中，可以发起以下查询：

| 查询 | 含义 | 返回 |
|---|---|---|
| `expand(X)` | 展开节点X的细节 | X的R2/R1版本 |
| `dependencies(X)` | 查询X依赖什么 | X的依赖邻居（~10-20节点） |
| `dependents(X)` | 查询什么依赖X | X的被依赖邻居（~10-20节点） |
| `cross_domain(X)` | 查询X的跨领域连接 | X的跨领域边连接的节点 |
| `path(X, Y)` | 查询X到Y的依赖路径 | X到Y的最短路径上的节点 |
| `loop(X)` | 查询X参与的螺旋环路 | 环路上的所有节点 |
| `siblings(X)` | 查询与X同主题的节点 | 同主题的其他节点 |
| `search("关键词")` | 语义搜索 | top-10匹配节点 |

### 6.2 查询协议格式

AI在推理中输出特殊标记来发起查询：

```
[QUERY: expand(node_Hilbert_Nullstellensatz)]
```

系统拦截这个标记，执行ArangoDB查询，将结果追加到上下文，AI继续推理。

### 6.3 Token预算管理

每次查询返回的内容消耗token预算。系统跟踪当前token使用量：

```
[CONTEXT BUDGET: 80000 tokens total, 45000 used, 35000 remaining]
```

AI看到剩余预算后，自行判断是否值得发起查询。

## 七、粒度拆分→小图分析→大图综合

### 7.1 当子图仍然太大时

即使有剪枝，某些问题可能需要>800节点的子图。此时启动"粒度拆分"（方法论已有此概念）：

```
800+节点的大子图
    ↓
拆分为3-5个小子图（每个~200节点）
    ↓
对每个小子图独立分析（各消耗~80K token上下文）
    ↓
综合各小图分析结果（消耗~40K token上下文）
```

### 7.2 拆分策略

| 策略 | 适用场景 |
|---|---|
| 按领域拆分 | 跨领域问题——每个领域一个子图 |
| 按依赖深度拆分 | 深依赖链——L1层一个子图，L2层一个子图 |
| 按证明阶段拆分 | 证明构造——每个引理/阶段一个子图 |
| 按螺旋环路拆分 | 多环路问题——每个环路一个子图 |

## 十二、诚实面对

1. **embedding质量是关键风险**：语义检索的质量取决于embedding模型对数学概念的理解。通用embedding模型可能对"概形"和"层"这样的数学概念区分不够。可能需要用数学语料微调的embedding模型。

2. **层次索引需要持续维护**：随着知识吸收，新的节点需要归入主题树。这可能需要AI辅助分类。

3. **剪枝可能丢失重要节点**：token预算剪枝是贪心的，可能剪掉看似不相关但实际重要的节点。缓解策略：保留螺旋环路节点和跨领域边节点（这些是方法论认为高价值的）。

4. **多分辨率增加了复杂度**：同一节点有R1/R2/R3/R4四个版本，需要保持一致性。R1更新时R2/R3/R4需要同步。

5. **查询协议需要AI配合**：AI需要学会在推理中主动发起expand/query。这需要在提示词中训练AI使用这个协议。

6. **325000节点是远期目标**：当前只有1697节点。三层访问架构在1697节点时不需要embedding检索（全遍历即可），但随着节点增长，逐步启用各层能力。建议：
   - <5000节点：全遍历，不需要种子选择
   - 5000-50000节点：层次索引+图遍历，不需要embedding
   - 50000-325000节点：完整三层架构（层次索引+embedding+图遍历+剪枝）

7. **这个架构本身需要POC验证**：理论上可行，但种子选择准确性、子图提取质量、token预算可控性都需要实验验证。建议在节点数达到~5000时做第一次POC。
