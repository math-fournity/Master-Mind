## 0. 一句话概括

258号检索机制设计文档的第一层（状态感知）依赖三个原语——event-sourcing、thinking-trajectory-graph、dynamic-workspace——它们都需要从工作智能体的自然语言推理输出中解析出结构化语义表示。但这个解析器没有对应的原语覆盖，是整个检索机制的瓶颈。本文档给出这个解析器的完整攻关方案：输入输出规格、LLM+SymPy混合解析策略、用253号案例A1-A10的具体走通设计、工程实现方案、是否成为新原语的分析、以及验证方案。

## 1. 问题定义

### 1.1 缺口的精确描述

258号§3.2步骤①-③描述了第一层状态感知的三个原语：

- **event-sourcing**（步骤①）：把工作智能体的推理输出解析为不可变事件，标注14种语义类型
- **thinking-trajectory-graph**（步骤②）：从语义事件流构建思维图T_t，节点有10种类型
- **dynamic-workspace**（步骤③）：从事件流归约六元组状态(V_t/F_t/O_t/R_t/E_t/U_t)

三个原语都处于untested状态，原因相同——**事件捕获器（解析器）未实现**。258号§7.2明确标注：

> "event-sourcing、thinking-trajectory-graph、dynamic-workspace三个原语都依赖'从工作智能体的自然语言推理输出中解析出结构化表示'。但这个解析器本身没有对应的原语——它是一个工程实现问题，不是系统设计原语。"

### 1.2 问题的具体化

以253号案例A7为例。A7的输出是：

```
A7：导出稳定性方程：
- 由Σxᵢ=0 → A_r+A_s=-D ... (1)
- 由Σq(xᵢ)=0 → -√5·A_r+√5·A_s+B_r+B_s=0 ... (2)
- 由Σxᵢq(xᵢ)=0 → 5D = 3√5(B_r-B_s) + 2C ... (3)

其中D=Σζᵢ=kr+(n-k)s=√5(pn-k)，p=(5-√5)/10。
```

系统需要从中识别出：

| 需要识别的内容 | 对应的结构化表示 | 供给哪个原语 |
|---|---|---|
| 语义事件类型："导出恒等式" | SemanticEvent(type=RESOLUTION, ...) | event-sourcing |
| 语义事件类型："引入新变量" | SemanticEvent(type=REPRESENTATION, ...) | event-sourcing |
| 数学对象：稳定性方程(3) | T_t节点(type=resolution, content="5D=3√5(B_r-B_s)+2C") | thinking-trajectory-graph |
| 数学对象：量D=√5(pn-k) | T_t节点(type=claim, content="D=√5(pn-k)") | thinking-trajectory-graph |
| 结构特征：D取决于整数k和n的关系 | 六元组U_t条目："D的量级取决于整数关系" | dynamic-workspace |
| 思维状态：停在这里，有稳定性方程但不知道下一步 | 六元组F_t={稳定性方程}, O_t={估计D下界} | dynamic-workspace |

### 1.3 为什么现有实现不够

当前代码库中已有一个`SemanticExtractor`（`xishujuzhen/research_runtime/events/extractor.py`），但它的工作方式是**类型映射**——从`RawEventType`枚举值映射到`SemanticEventType`枚举值。例如：

```python
RawEventType.TOOL_CALL → SemanticEventType.TEST
RawEventType.CLAIM_MADE → SemanticEventType.CLAIM
```

这个映射基于**事件的结构化类型标签**（由devin cli的tool调用hook捕获），而不是基于**文本内容的语义理解**。当工作智能体输出一段自然语言推理文本时，这段文本被捕获为`RawEventType.TEXT_OUTPUT`，然后统一映射为`SemanticEventType.OBSERVATION`——所有文本输出都变成"观察"，无法区分"导出恒等式""引入新变量""得到中间结果"等更细粒度的语义类型。

**缺口的核心**：需要一个从**自然语言+数学公式的混合文本**到**结构化语义事件序列**的内容级解析器，而不只是类型级的映射器。

### 1.4 影响范围

258号§3.3明确指出：

> "第一层的核心缺口：从自然语言推理输出到结构化表示的解析准确率。event-sourcing、thinking-trajectory-graph、dynamic-workspace三个原语都依赖这个解析，但都处于untested状态。这是整个检索机制的瓶颈环节。"

如果解析不准确：
- T_t不准确 → activation-score的特征向量p_t不准确 → 第二层粗筛遗漏或引入噪声
- 六元组不准确 → constrained-policy的进展估计不准确 → 第三层决策偏移
- 卡点类型不准确 → 检索触发条件错误 → 在不该检索时检索，或该检索时没检索

**结论**：解析器是检索机制的入口瓶颈，必须优先攻关。

## 2. 解析器输入输出规格

### 2.1 输入规格

解析器的输入是一个`ParseRequest`对象：

```python
@dataclass
class ParseRequest:
    # 必需字段
    agent_output: str           # 工作智能体本轮的自然语言推理输出（如A7的文本）
    round_index: int            # 当前轮次（如A7对应第7轮）
    problem_text: str           # 题目原文

    # 累积context（可选但强烈推荐）
    history: List[TurnRecord]   # 完整QA历史 [(Q1,A1), (Q2,A2), ...]
    current_six_tuple: Optional[SixTuple]  # 上一轮解析后的六元组状态（用于增量解析）

    # 元信息
    run_id: str                 # 运行ID
    model_version: str          # 工作智能体的模型版本
    timestamp: str              # 时间戳
```

其中`TurnRecord`是单轮QA的记录：

```python
@dataclass
class TurnRecord:
    q_text: str                 # 引导者发送的提示
    a_text: str                 # 工作智能体的回复
    q_level: float              # 提示的Level值
    q_non_specificity: float    # 提示的非特定性程度
    parsed_events: List[SemanticEvent]  # 该轮已解析的语义事件（历史解析结果）
```

### 2.2 输出规格

解析器的输出是一个`ParseResult`对象：

```python
@dataclass
class ParseResult:
    # 核心输出1：语义事件序列（供给event-sourcing）
    semantic_events: List[SemanticEvent]

    # 核心输出2：思维轨迹图节点和边（供给thinking-trajectory-graph）
    trajectory_nodes: List[TrajectoryNode]
    trajectory_edges: List[TrajectoryEdge]

    # 核心输出3：六元组状态（供给dynamic-workspace）
    six_tuple: SixTuple

    # 解析质量信息
    parse_confidence: float             # 整体解析置信度（0-1）
    per_event_confidence: List[float]   # 每个事件的解析置信度
    sympy_verified: List[bool]          # 每个事件是否经过SymPy验证
    parse_warnings: List[str]           # 解析过程中的警告信息
```

### 2.3 各输出组件的详细格式

#### 2.3.1 语义事件（SemanticEvent）

14种语义事件类型（来自`models/event.py`的`SemanticEventType`枚举）：

| 类型 | 含义 | 在数学推理中的典型场景 |
|---|---|---|
| OBSERVATION | 从题面或证据中注意到的事实 | "注意到结论是渐近精细下界" |
| CLAIM | 当前认为成立的命题 | "D≠0因为p是无理数" |
| REPRESENTATION | 当前采用的表示 | "设R=√5+δ，做紧性归约" |
| SUBGOAL | 需要解决的子问题 | "需要估计D的下界" |
| CANDIDATE | 候选答案或方法 | "可能用柯西不等式" |
| TEST | 正在尝试的思维动作 | "做数值实验观察δ量级" |
| TOOL_RESULT | 工具返回 | SymPy计算结果 |
| CONTRADICTION | 发现冲突 | "候选与已知上界不相容" |
| STALL | 停滞或重复 | "有稳定性方程但不知道下一步" |
| BACKTRACK | 回退 | "放弃这个方向" |
| RESOLUTION | 已解决的局部结论 | "得到稳定性方程5D=3√5(B_r-B_s)+2C" |
| HINT_INJECTION | 提示注入 | 系统发出的Q（非工作智能体产出） |
| STATE_REDUCTION | 状态归约 | 系统内部事件（非工作智能体产出） |
| VERIFICATION | 验证结果 | "SymPy验证恒等式成立" |

每个`SemanticEvent`的格式：

```python
@dataclass
class SemanticEvent:
    event_id: str               # 唯一ID
    type: SemanticEventType     # 14种之一
    timestamp: str              # 时间戳
    round_index: int            # 第几轮QA

    # 语义内容
    description: str            # 自然语言描述（如"导出稳定性方程(3)"）
    math_objects: List[MathObject]  # 涉及的数学对象
    raw_text_span: str          # 原文中对应的文本片段

    # 关联信息
    depends_on: List[str]       # 依赖的前序事件ID
    confidence: float           # 解析置信度（0-1）
    sympy_verified: bool        # 是否经过SymPy验证
    source: str                 # 解析来源（"llm" / "sympy" / "hybrid"）
```

其中`MathObject`是数学对象的统一表示：

```python
@dataclass
class MathObject:
    name: str                   # 名称（如"稳定性方程"）
    latex: str                  # LaTeX表示（如"5D = 3\\sqrt{5}(B_r - B_s) + 2C"）
    sympy_expr: Optional[str]   # SymPy可解析的表达式（如"5*D - 3*sqrt(5)*(B_r - B_s) - 2*C"）
    object_type: str            # 类型：equation/variable/inequality/identity/definition
    variables: List[str]        # 涉及的变量列表（如["D", "B_r", "B_s", "C"]）
    properties: Dict[str, str]  # 结构特征（如{"depends_on_integers": "k,n"}）
```

#### 2.3.2 思维轨迹图节点和边

10种节点类型（来自122-v2§3.2）：

| 节点类型 | 含义 | 在数学推理中的典型场景 |
|---|---|---|
| observation | 从题面或证据中注意到的事实 | "结论是渐近精细下界问题" |
| claim | 当前认为成立的命题 | "D≠0" |
| representation | 当前采用的表示 | "投影到根：ζᵢ∈{r,s}" |
| subgoal | 需要解决的子问题 | "估计D的下界" |
| candidate | 候选答案或方法 | "柯西不等式" |
| operation | 正在尝试的思维动作 | "组合三个矩条件" |
| tool_result | 工具返回 | SymPy验证结果 |
| contradiction | 发现冲突 | "D=0需要k/n=p但p是无理数" |
| stall | 停滞或重复 | "不知道下一步" |
| resolution | 已解决的局部结论 | "稳定性方程5D=..." |

每个`TrajectoryNode`的格式：

```python
@dataclass
class TrajectoryNode:
    node_id: str                # 唯一ID
    type: str                   # 10种之一
    round_index: int            # 第几轮QA产生
    content: str                # 节点内容描述
    math_objects: List[MathObject]  # 关联的数学对象
    is_frontier: bool           # 是否是当前前沿节点（工作智能体停在这里）
    confidence: float           # 解析置信度
```

边类型（来自122-v2§3.2的13种边）：

```python
@dataclass
class TrajectoryEdge:
    source_id: str              # 源节点ID
    target_id: str              # 目标节点ID
    edge_type: str              # 13种之一：notice/infer/recall/transform/
                                # decompose/compare/test/reject/backtrack/
                                # generalize/analogize/ask_for_hint/activate
    description: str            # 边的描述
```

#### 2.3.3 六元组状态（SixTuple）

```python
@dataclass
class SixTuple:
    V_t: List[VerifiedProp]     # 已验证核心：已通过验证的命题
    F_t: List[Conjecture]       # 猜想前沿：正在探索但未验证的命题
    O_t: List[Obligation]       # 开放义务：待解决子目标
    R_t: List[Representation]   # 表示状态：当前使用的表示形式
    E_t: List[Evidence]         # 证据：已积累的证据
    U_t: List[UnsolvedProblem]  # 未解决问题：已识别但未解决的问题

@dataclass
class VerifiedProp:
    statement: str              # 命题内容
    math_objects: List[MathObject]
    verified_by: str            # 验证方式（"logic"/"sympy"/"given"）
    verified_at_round: int

@dataclass
class Conjecture:
    statement: str              # 猜想内容
    math_objects: List[MathObject]
    status: str                 # "exploring"/"promising"/"weak"

@dataclass
class Obligation:
    description: str            # 义务描述（如"估计D的下界"）
    obligation_type: str        # prove/refute/construct/compute/compare/evaluate
    status: str                 # open/in_progress/solved/denied
    depends_on: List[str]       # 依赖的其他义务

@dataclass
class Representation:
    name: str                   # 表示名称（如"投影到根"）
    description: str            # 表示描述
    introduced_at_round: int

@dataclass
class Evidence:
    kind: str                   # literature/numerical/symbolic/formal_proof/counterexample/human_audit
    content: str                # 证据内容
    supports: str               # 支持哪个命题

@dataclass
class UnsolvedProblem:
    description: str            # 问题描述（如"D的量级问题"）
    severity: str               # "blocking"/"minor"/"potential"
    identified_at_round: int
```

## 3. 解析策略

### 3.1 LLM粗解析

#### 3.1.1 为什么用LLM做粗解析

工作智能体的输出是自然语言+数学公式的混合文本，具有以下特征：
- **格式不统一**：数学公式可能用LaTeX（`$\sqrt{5}$`）、Unicode（`√5`）、或纯文本（`sqrt(5)`）
- **语义隐含在上下文中**：A7的"导出稳定性方程"这个语义事件类型不在文本中显式标注，需要从内容推断
- **需要领域知识**：识别"这是一个稳定性方程"需要理解数学含义

LLM擅长从非结构化文本中提取结构化信息，适合做粗解析。

#### 3.1.2 LLM解析的Prompt设计

**系统提示词（System Prompt）**：

```
你是一个数学推理过程的结构化解析器。你的任务是从工作智能体（做题AI）的自然语言推理输出中，解析出结构化的语义事件序列。

你需要识别14种语义事件类型：
1. OBSERVATION - 从题面或证据中注意到的事实
2. CLAIM - 当前认为成立的命题
3. REPRESENTATION - 引入新表示、新变量、新记号
4. SUBGOAL - 需要解决的子问题
5. CANDIDATE - 候选答案或方法
6. TEST - 正在尝试的思维动作（如数值实验、极端检验）
7. TOOL_RESULT - 工具返回结果
8. CONTRADICTION - 发现冲突
9. STALL - 停滞或重复
10. BACKTRACK - 回退或放弃方向
11. RESOLUTION - 已解决的局部结论（如导出恒等式、得到中间结果）
12. HINT_INJECTION - 系统提示注入（非工作智能体产出，通常忽略）
13. STATE_REDUCTION - 状态归约（系统内部事件，通常忽略）
14. VERIFICATION - 验证结果

你需要识别10种思维轨迹图节点类型：
observation, claim, representation, subgoal, candidate, operation, tool_result, contradiction, stall, resolution

你需要归约六元组状态：
- V_t（已验证核心）：已被逻辑确认的数学事实
- F_t（猜想前沿）：正在探索但未验证的命题
- O_t（开放义务）：待解决子目标
- R_t（表示状态）：当前使用的表示形式
- E_t（证据）：已积累的证据
- U_t（未解决问题）：已识别但未解决的问题

对于每个数学对象，提取：
- name: 名称
- latex: LaTeX表示
- sympy_expr: SymPy可解析的表达式（用Python语法，如 5*D - 3*sqrt(5)*(B_r - B_s) - 2*C）
- object_type: equation/variable/inequality/identity/definition
- variables: 涉及的变量列表
- properties: 结构特征（如 {"depends_on_integers": "k,n"}）
```

#### 3.1.3 LLM输出的后处理

LLM输出的JSON需要经过以下后处理：

1. **JSON校验**：解析JSON，校验字段完整性。解析失败则回退到错误处理流程（§5.3）。
2. **类型校验**：检查`type`字段是否在14种语义事件类型和10种节点类型的枚举值中。不在枚举中的做模糊匹配（如"derive"→"RESOLUTION"）。
3. **ID分配**：为每个事件和节点分配唯一ID（`event_{run_id}_{round}_{seq}`）。
4. **依赖关系校验**：检查`depends_on`引用的event_id是否存在。
5. **数学对象去重**：跨事件的相同数学对象合并（如A7中方程(1)(2)(3)都涉及D，D只创建一次）。

#### 3.1.4 LLM的选择和配置

- **模型选择**：使用与工作智能体相同或更强的LLM。如果工作智能体是GLM-5.2，解析器可以用GLM-5.2或更强的模型。理由：解析需要理解数学语义，模型能力不足会导致解析质量差。
- **温度**：0.0-0.1。解析是确定性任务，不需要创造性。
- **输出格式**：JSON mode（如果模型支持），否则用`json.loads`解析。

### 3.2 SymPy精确验证

#### 3.2.1 为什么需要SymPy验证

LLM粗解析的输出中，数学对象部分（`MathObject`）是最容易出错的：
- LaTeX表达式可能有语法错误
- SymPy表达式可能与原文不一致（LLM可能"幻觉"出错误的公式）
- 变量列表可能遗漏或多出

SymPy是符号计算库，可以：
1. **验证表达式等价性**：检查LLM提取的SymPy表达式是否与LaTeX表达式一致
2. **验证恒等式**：检查声称的恒等式是否成立
3. **提取变量**：从SymPy表达式中自动提取变量列表
4. **简化表达式**：将表达式规范化，便于后续比较

#### 3.2.2 SymPy验证的具体内容

对LLM输出的每个`MathObject`，SymPy验证以下内容：

| 验证项 | 方法 | 通过条件 | 失败处理 |
|---|---|---|---|
| 表达式可解析性 | `sympify(expr)` 不抛异常 | 无异常 | 标记`sympy_verified=False`，保留LLM输出 |
| LaTeX-SymPy一致性 | 用`sympy.latex(sympified_expr)`与LLM的LaTeX比较 | 规范化后一致 | 标记不一致，以SymPy为准修正LaTeX |
| 变量列表完整性 | `expr.free_symbols` 与LLM的`variables`比较 | 集合相等 | 以SymPy提取的为准 |
| 恒等式验证（如适用） | `simplify(lhs - rhs) == 0` | 等于0 | 标记为"未验证恒等式"，不删除 |
| 结构特征验证（如适用） | 检查`properties`中声称的结构特征 | SymPy能确认 | 无法确认则标记为"LLM声称，SymPy未确认" |

#### 3.2.3 SymPy验证的代码框架

```python
import sympy as sp

def verify_math_object(math_obj: MathObject) -> MathObject:
    """对单个数学对象做SymPy验证，返回修正后的对象"""
    if math_obj.sympy_expr is None:
        # 无SymPy表达式，尝试从LaTeX解析
        try:
            expr = parse_latex_to_sympy(math_obj.latex)
            math_obj.sympy_expr = str(expr)
        except Exception:
            math_obj.sympy_verified = False
            return math_obj

    try:
        # 验证表达式可解析性
        expr = sp.sympify(math_obj.sympy_expr)

        # 提取变量列表
        actual_vars = {str(s) for s in expr.free_symbols}
        claimed_vars = set(math_obj.variables)
        if actual_vars != claimed_vars:
            math_obj.variables = list(actual_vars)
            # 记录警告

        # 如果是equation类型，验证恒等式
        if math_obj.object_type == "identity":
            if isinstance(expr, sp.Eq):
                diff = sp.simplify(expr.lhs - expr.rhs)
                if diff == 0:
                    math_obj.properties["verified_identity"] = "true"
                else:
                    math_obj.properties["verified_identity"] = "false"

        math_obj.sympy_verified = True
    except Exception as e:
        math_obj.sympy_verified = False
        math_obj.properties["sympy_error"] = str(e)

    return math_obj
```

#### 3.2.4 SymPy验证的局限

SymPy验证不能覆盖所有情况：

1. **自然语言中的数学公式格式不统一**：A7中的`√5·A_r`需要先转换为`sqrt(5)*A_r`才能被SymPy解析。这个转换本身需要LLM或正则完成。
2. **某些数学概念无法用SymPy表达**：如"badly approximable"是数论概念，SymPy没有对应函数。这类结构特征只能靠LLM识别。
3. **上下文依赖的语义**：如"D取决于整数k和n的关系"——这个结构特征需要理解D=√5(pn-k)中p是无理数、k和n是整数，SymPy可以验证D的表达式，但"取决于整数关系"这个语义判断需要LLM。
4. **定义性引入**：如"p=(5-√5)/10"是定义，不是恒等式，SymPy验证的是表达式可解析性，不是"这个定义是否合理"。

**结论**：SymPy验证是LLM粗解析的补充，不是替代。SymPy验证数学表达式的正确性，LLM负责语义理解。

#### 3.3.2 协同的具体流程

**LLM先，SymPy后**——不是SymPy先LLM兜底。理由：

1. 自然语言文本的语义理解是SymPy无法做的——SymPy只能处理已经结构化的数学表达式，不能从"由Σxᵢq(xᵢ)=0 → 5D = 3√5(B_r-B_s) + 2C"这段文本中识别出"这是一个恒等式"。
2. LLM先做粗解析，把自然语言转为结构化JSON，SymPy再验证JSON中的数学表达式部分。
3. 如果SymPy验证失败（表达式不可解析或恒等式不成立），不回退到LLM重新解析——而是标记为"LLM声称但SymPy未验证"，保留LLM输出但降低置信度。

**例外**：如果LLM输出的JSON本身解析失败（格式错误），则回退到LLM重新生成（最多重试2次）。

#### 3.3.3 置信度计算

最终的解析置信度综合LLM自评和SymPy验证结果：

```
parse_confidence = llm_confidence * sympy_factor

其中：
- llm_confidence：LLM在JSON中自评的置信度（0-1）
- sympy_factor：
  - 所有math_objects都通过SymPy验证：1.0
  - 部分通过：0.8
  - 全部未通过但有math_objects：0.5
  - 无math_objects（纯文本推理）：1.0（不涉及SymPy验证）
```

#### 4.3.2 需要SymPy验证的部分

| 内容 | 为什么需要SymPy | 验证内容 |

#### 4.3.3 难点（LLM和SymPy都难以可靠处理）

**难点1：结构特征的识别**

A7中"D取决于整数k和n的关系"这个结构特征是Q8检索的关键——Q8的触发条件包含"量D取决于整数关系"。但这个特征需要理解：
- D=√5(pn-k)中p是无理数
- k和n是整数
- 因此D≠0但|D|的下界取决于有理逼近

LLM可能识别出"D与k和n有关"，但"取决于整数关系"这个精确的语义需要更深理解。SymPy无法验证这个语义——它可以验证D的表达式，但不能判断"取决于整数关系"这个结构特征。

**应对方案**：在LLM prompt中明确要求识别"数学对象中哪些变量是整数、哪些是无理数"，并标注"整数变量之间的依赖关系"作为结构特征。这给LLM更具体的指引，提高识别准确率。

**难点2：隐含的卡点识别**

A7本身没有显式说"我卡住了"——它只是输出了稳定性方程就停了。卡点是隐含的：工作智能体有稳定性方程但不知道下一步。这需要从"输出到此为止"这个行为推断，而不是从文本内容推断。

**应对方案**：卡点检测不只看文本内容，还看"输出是否结束"和"是否有新的subgoal或candidate"。如果前沿节点是resolution类型但没有后续的subgoal或candidate节点，判定为"有中间结果但不知道下一步方向"的卡点。

**难点3：跨轮次的增量解析**

A7的解析依赖于A1-A6的累积context。例如，识别"稳定性方程"需要知道A6引入了投影到根的表示。如果每轮独立解析，可能丢失上下文。但如果把所有历史都塞进LLM prompt，token会超限。

**应对方案**：增量解析策略——每轮解析时传入上一轮的六元组状态（而非完整历史文本），六元组是累积context的压缩表示。LLM在上一轮六元组的基础上做增量更新。这控制了token用量，同时保留了必要的上下文。

**难点4：数学公式的格式不统一**

A7中的公式用Unicode符号（√5、Σ、ᵢ），不是标准LaTeX。LLM需要先理解Unicode数学符号，再转为LaTeX/SymPy格式。不同工作智能体可能用不同格式——有的用LaTeX，有的用Unicode，有的用纯文本。

**应对方案**：在LLM prompt中给出格式转换的示例（如"√5 → sqrt(5), Σ → sum, ᵢ → _i"），让LLM做格式归一化。SymPy验证时如果解析失败，尝试用正则做预处理（如`√(\d+)` → `sqrt(\1)`）。

**难点5：A8的知识瓶颈识别**

A8中工作智能体"尝试各种估计但有困难——这是知识瓶颈"。识别"知识瓶颈"（而非"思维瓶颈"）需要理解：工作智能体不是不知道该做什么，而是缺乏必要的数学知识（badly approximable性质）。这个区分对检索至关重要——知识瓶颈需要知识注入（Level→0），思维瓶颈需要元认知提示（Level→1）。

**应对方案**：在LLM prompt中要求区分两类卡点：
- "思维瓶颈"：工作智能体知道方向但不知道怎么做 → STALL类型
- "知识瓶颈"：工作智能体尝试了但缺乏必要知识 → STALL类型 + U_t中标注"knowledge_gap"

### 5.3 错误处理

| 错误类型 | 处理方式 | 用户可见信息 |
|---|---|---|
| LLM输出JSON解析失败 | 重试LLM（最多2次），仍失败则降级为纯OBSERVATION事件 | warning: "LLM输出格式错误，降级为纯观察事件" |
| LLM输出的事件类型不在14种枚举中 | 模糊匹配最接近的类型，匹配失败则默认为OBSERVATION | warning: "未知事件类型'{x}'，映射为OBSERVATION" |
| SymPy验证失败（表达式不可解析） | 保留LLM输出的LaTeX，标记sympy_verified=False，降低置信度 | warning: "SymPy无法解析表达式'{x}'" |
| SymPy验证失败（恒等式不成立） | 保留表达式但标记properties.verified_identity="false" | warning: "恒等式验证失败：{lhs} ≠ {rhs}" |
| 一致性检查失败（事件与六元组矛盾） | 以事件为准修正六元组，记录warning | warning: "六元组{field}与事件不一致，已修正" |
| LLM调用超时或API错误 | 降级为纯OBSERVATION事件，标记parse_confidence=0.3 | warning: "LLM调用失败，降级处理" |
| 增量解析中上一轮六元组缺失 | 退化为非增量解析（不传入previous_six_tuple） | warning: "无上一轮六元组，执行非增量解析" |

**核心原则**：解析失败不阻塞流程。即使解析质量差，也要输出一个可用的ParseResult（哪怕只有纯OBSERVATION事件和空六元组），让后续环节能继续运行。解析质量通过置信度标记，低置信度的结果在后续activation-score中权重降低。

### 5.4 增量解析

#### 5.4.1 策略选择：逐轮增量解析

**选择**：工作智能体每完成一轮输出后，对该轮输出做增量解析（而非等所有轮完成后批量解析）。

**理由**：
1. 检索机制需要在每轮结束后做状态感知和Pattern提取——如果等所有轮完成再解析，检索机制无法在中间环节工作。
2. 逐轮增量解析控制了每次解析的输入规模——只解析当前轮的输出+上一轮的六元组状态，而非全部历史文本。
3. 与258号检索流程的架构一致——258号的流程是"每轮输出→状态感知→Pattern提取→决策→发送Q→下一轮输出"的循环。

#### 5.4.2 增量解析的具体机制

```
第1轮：ParseRequest(agent_output=A1, history=[], previous_six_tuple=None)
  → 非增量解析 → ParseResult_1 → six_tuple_1

第2轮：ParseRequest(agent_output=A2, history=[Q1,A1], previous_six_tuple=six_tuple_1)
  → 增量解析：LLM在six_tuple_1基础上更新 → ParseResult_2 → six_tuple_2

...

第7轮：ParseRequest(agent_output=A7, history=[Q1-Q6,A1-A6], previous_six_tuple=six_tuple_6)
  → 增量解析：LLM在six_tuple_6基础上更新 → ParseResult_7 → six_tuple_7
```

**history_summary的构建**：不传入完整历史文本，而是传入简要摘要：

```python
def build_history_summary(history: List[TurnRecord], max_rounds: int = 3) -> str:
    """只传入最近3轮的Q和A的摘要，控制token用量"""
    recent = history[-max_rounds:]
    lines = []
    for turn in recent:
        lines.append(f"Q{turn.round_index}(L{turn.q_level}): {turn.q_text[:100]}...")
        lines.append(f"A{turn.round_index}: {turn.a_text[:200]}...")
    return "\n".join(lines)
```

**六元组的增量更新**：LLM在prompt中收到上一轮的六元组JSON，被要求输出**更新后**的完整六元组（而非增量diff）。这简化了LLM的任务——不需要理解增量格式，只需要输出当前完整状态。代价是输出token较多，但六元组通常不超过几百个token。

#### 5.4.3 增量解析的风险和缓解

| 风险 | 缓解措施 |
|---|---|
| 六元组累积误差——每轮增量更新可能引入小误差，多轮后误差累积 | 每5轮做一次全量解析（传入完整历史），与增量解析结果对比，如果差异大则用全量结果覆盖 |
| 早期轮次的信息在增量更新中丢失（LLM可能遗忘V_t中的早期条目） | 在prompt中强调"V_t只增不减，不要删除已有条目" |
| token用量随轮次增长（history_summary增长） | 限制history_summary为最近3轮，更早的历史通过六元组压缩表示 |

## 6. 是否成为新原语

### 6.1 分析

258号§7.2缺口1的原文说：

> "这个解析器本身没有对应的原语——它是一个工程实现问题，不是系统设计原语。"

这个判断需要重新审视。解析器的性质可以从原语三判据（可执行性 + 可验证性 + 构造性）来分析：

| 判据 | 分析 | 满足？ |
|---|---|---|
| **可执行性** | 解析器有明确的输入（自然语言文本+context）和输出（结构化语义事件+节点+六元组），可以执行 | ✓ |
| **可验证性** | 解析准确率可以用人工标注的gold standard对比测量（§7验证方案），有明确的验证方法 | ✓ |
| **构造性** | 解析器构造了event-sourcing、thinking-trajectory-graph、dynamic-workspace三个原语的共享基础设施——没有解析器，这三个原语无法工作 | ✓ |

三判据都满足，解析器**可以**成为新原语。

### 6.2 但它更应该是什么

然而，解析器的本质是**从一种表示到另一种表示的转换器**——从自然语言表示到结构化语义表示。这与event-sourcing（事件溯源的架构模式）、thinking-trajectory-graph（思维图的数据结构）、dynamic-workspace（六元组的状态模型）不同——后者是"系统应该用什么结构来表示状态"的设计原语，而解析器是"如何从原始数据产生这些结构"的工程实现。

类比：数据库的schema设计是设计原语（定义数据应该怎么组织），而ETL管线是工程实现（把原始数据转换为schema规定的格式）。解析器更接近ETL管线。

### 6.3 建议

**建议：不作为独立原语，但作为event-sourcing原语的实现规格补充。**

具体做法：

1. **在`primitives/structural/event-sourcing.md`中补充"事件捕获器规格"章节**，明确：
   - 事件捕获器的输入输出规格（本文档§2）
   - LLM+SymPy混合解析策略（本文档§3）
   - 14种语义事件类型的解析规则（什么文本模式对应什么事件类型）
   - 验证方法（本文档§7）

2. **event-sourcing的验证状态从untested升级为partial**——当解析器原型实现并用253号案例验证后，event-sourcing的"事件捕获器未实现"这个open problem得到部分解决。

3. **在event-sourcing的开放问题中更新**：
   - 原："14种语义事件类型是否完备？事件流增长后如何做快照压缩？"
   - 新："14种语义事件类型是否完备？（260号攻关方案中用253号案例验证）LLM+SymPy混合解析的准确率是否达到可用水平？（260号验证方案）事件流增长后如何做快照压缩？"

**理由**：
- 解析器是event-sourcing的实现核心——event-sourcing的定义是"从研究过程中抽取语义事件"，解析器就是做这个抽取的组件。
- 把解析器规格写入event-sourcing原语文件，使该原语从"设计完成但未实现"升级为"设计完成且有实现规格"。
- 不创建独立原语避免了原语数量膨胀——解析器不是一个可以独立于event-sourcing存在的组件，它就是event-sourcing的实现。

**替代方案（如果后续验证发现解析器有独立的设计问题）**：如果253号案例验证发现解析器的设计问题超出了event-sourcing的范围（例如，解析器需要自己独立的验证体系、有自己的组合关系），则升级为独立原语`nl-to-semantic-parser`，放在`primitives/operational/`下（因为它是可执行的操作，不是可放置的结构）。

| 标注项 | 内容 | 格式 |
|---|---|---|
| 语义事件序列 | A_i中包含哪些语义事件，每个事件的类型、描述、数学对象 | List[SemanticEvent] |
| 思维轨迹图节点 | A_i产生了哪些T_t节点，每个节点的类型、内容、是否前沿 | List[TrajectoryNode] |
| 六元组状态 | A_i之后的完整六元组 | SixTuple |
| 卡点类型 | A_i之后工作智能体是否卡住，卡点类型是什么 | Enum |

**步骤2：标注一致性检查**

由2名标注者独立标注，计算Cohen's Kappa系数。Kappa < 0.7的标注项需要讨论统一。

**步骤3：生成Gold Standard JSON**

将人工标注结果转为与ParseResult相同的JSON格式，作为对比基准。

### 7.4 评估方法

对A1-A10的每个A_i，运行解析器，得到ParseResult_i。将ParseResult_i与Gold_Standard_i对比：

#### 7.4.1 事件级评估

| 指标 | 定义 | 计算方式 |
|---|---|---|
| 事件类型准确率 | 每个事件类型分类是否正确 | 对每个事件，类型匹配gold standard的类型计为正确 |
| 事件数量准确率 | 解析出的事件数量是否与gold standard一致 | abs(解析数量 - gold数量) / gold数量 |
| 事件-文本对齐率 | raw_text_span是否正确指向原文 | 人工判断每个事件的raw_text_span是否覆盖了正确的文本片段 |

**事件对齐方法**：解析器和gold standard的事件可能数量不同、顺序不同。用最优匹配（Hungarian算法）做事件对齐——以事件描述的语义相似度为代价，找最优配对。

#### 7.4.2 数学对象级评估

| 指标 | 定义 | 计算方式 |
|---|---|---|
| 数学对象提取率 | gold standard中的数学对象被正确提取的比例 | 正确提取数 / gold中的对象数 |
| SymPy验证通过率 | 提取的数学表达式通过SymPy验证的比例 | 通过验证数 / 有sympy_expr的对象数 |
| 变量列表准确率 | 提取的变量列表与gold standard一致的比例 | 变量集合一致的对象数 / 总对象数 |

#### 7.4.3 六元组级评估

| 指标 | 定义 | 计算方式 |
|---|---|---|
| V_t准确率 | V_t中的条目与gold standard一致 | 正确条目数 / gold中V_t条目数 |
| F_t准确率 | 同上 | 同上 |
| O_t准确率 | 同上 | 同上 |
| R_t准确率 | 同上 | 同上 |
| U_t准确率 | 同上 | 同上 |
| 六元组综合准确率 | 6个字段准确率的加权平均 | (V×0.25 + F×0.20 + O×0.20 + R×0.15 + E×0.05 + U×0.15) |

**权重理由**：V_t和F_t是检索的核心输入（决定activation-score的特征），权重最高。O_t和U_t决定卡点检测和进展估计，权重次高。R_t影响表示匹配，权重中等。E_t在本案例中通常为空（没有外部工具调用），权重最低。

#### 7.4.4 前沿节点和卡点评估

| 指标 | 定义 | 计算方式 |
|---|---|---|
| 前沿节点识别率 | 正确识别当前前沿节点的轮数 / 总轮数 | 逐轮对比 |
| 卡点类型识别率 | 正确识别卡点类型的轮数 / 有卡点的轮数 | 逐轮对比 |

### 7.6 验证通过标准

| 指标 | 最低可接受值 | 目标值 |
|---|---|---|
| 事件类型准确率 | 70% | 80% |
| 数学对象提取率 | 80% | 90% |
| SymPy验证通过率 | 75% | 85% |
| 六元组综合准确率 | 65% | 75% |
| 前沿节点识别率 | 80% | 90% |
| 卡点类型识别率 | 70% | 80% |

**最低可接受值的理由**：低于这些值意味着解析器的输出不可靠，会导致后续检索机制（activation-score、pattern-matching）的输入质量太差，检索结果不可信。如果验证结果低于最低可接受值，需要改进解析策略（如改进prompt、增加few-shot示例、换更强的LLM）后重新验证。

### 7.7 验证的局限

1. **单案例验证**：253号案例只有10轮QA，验证结果的统计显著性有限。通过验证不代表在所有数学推理场景都有效。后续需要用更多案例（其他题目的QA序列）扩展验证。
2. **人工标注的主观性**：Gold Standard由人工标注，标注者对"什么是一个语义事件""某个事件是什么类型"的判断可能有主观差异。通过2人独立标注+Kappa系数检查缓解。
3. **A_i是预演输出，非真实输出**：253号的A1-A10是"预期A"（预演中工作智能体应该输出的内容），不是真实运行中工作智能体的实际输出。真实输出的格式可能更不规范（有错别字、格式混乱、中途改主意等）。后续需要用真实运行的输出做验证。
