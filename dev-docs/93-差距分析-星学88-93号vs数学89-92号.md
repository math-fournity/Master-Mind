## 二、星学有而数学缺失的（6项）

### 缺失1：设计哲学文档（对应星学88号）

**星学88号做了什么**：
- 从"AI上下文有限 vs 认知积累无限"的核心矛盾出发
- 分析了3种朴素方案的失败（全塞AGENTS.md/线性列表/让AI自己搜索）
- 记录了用户的直觉性画面（稀疏矩阵→螺旋环路）
- 提炼了7个设计决策，每个都有"解决的问题"和"数学基础"
- 明确了适用范围和不适用范围

**数学89-92号缺失什么**：
- 没有从核心矛盾出发的设计哲学
- 没有分析朴素方案的失败
- 没有记录用户的直觉性画面（虽然89号提到了"用户的愿景"，但没有作为设计哲学的起点）
- 没有提炼设计决策（91号有"超越星学三点"但不是设计决策级别的）
- 没有明确适用范围

**影响**：数学项目的方案缺少"为什么这样做"的论证。其他AI看到91号方案知道"做什么"，但不知道"为什么这样做"。

### 缺失2：POC验证体系（对应星学91号）

**星学91号做了什么**：
- POC1-9的完整演进时间线（10代验证）
- 评分维度体系（D1-D5，5维度满分100）
- 边际增益计算方法
- Ground truth标注方法
- POC-9的5个核心假设（H1-H5）及验证结果
- POC-R1回归评分（修复前88.6→修复后99.6）
- 6条关键发现（交叉审计比自审严格/闭环比开环有效/文字随机匹配是根本问题/meta/normal分离/碰巧100%vs数学确定100%/边际增益随复杂度增长）
- 3档复用指南（最小/标准/回归）
- 7条验证体系设计原则

**数学89-92号缺失什么**：
- **完全没有POC验证体系的设计**
- 91号方案的Check List中阶段6"与七步骤工作流集成"只是说"在POC执行前用cognition_checkpoint加载认知"，但没有设计如何验证工作系统本身的有效性
- 数学项目有POC-1和POC-2，但那些是验证"依赖图提示对数学证明的有效性"，不是验证"工作系统对AI工作的有效性"
- 没有D1-D5评分维度
- 没有假设检验设计
- 没有回归验证设计

**影响**：数学项目的工作系统建好后，无法证明它有效。星学项目用POC-R1证明了"认知图系统使AI的认知覆盖率从22.2%提升到100%"——数学项目没有类似的证据。

### 缺失3：Hook强制纪律的演进记录和subagent防护（对应星学92号）

**星学92号做了什么**：
- 完整记录了v1（Stop hook+flag文件）的废弃过程和根本原因（影响subagent）
- v2（git post-commit hook）的设计理由
- 三层维护机制的详细说明（以术语维护和SDK沉淀为例）
- subagent防护的天然方案（subagent不commit）
- 已废弃文件的清单

**数学91号缺失什么**：
- 91号方案的"三Hook设计"直接照搬了星学**已废弃的v1**（Stop hook + prompt_hook + session_start_hook）
- **没有提到星学92号文档中v1废弃的教训**
- 91号的stop_hook_math.py设计用了`stop_hook_active`和`work_pending` flag——这正是星学v1的方案，星学已经实测发现它影响subagent
- 91号的hooks.v1.json包含UserPromptSubmit hook（prompt_hook_math.py）——星学92号明确说这个hook已废弃
- 没有三层维护机制的设计
- 没有subagent防护的设计

**影响**：数学项目如果按91号方案实现，会重蹈星学v1的覆辙——Stop hook影响subagent。这是**最严重的缺失**。

### 缺失4：诚实评估（对应星学93号）

**星学93号做了什么**：
- 两套系统（认知图系统 vs xishujuzhen系统）的愿景达成度对比
- 6条已知局限（种子选择依赖AI/覆盖验证是朴素集合论/没有螺旋环路/Hook强制力降级/ArangoDB单点依赖/认知图维护依赖人工）
- HoTT标签的诚实定位（哪些是已实现的，哪些是愿景标签而非实现）
- 未来演进方向（短期/中期/长期）
- 给其他AI的最终建议（可复用/需调整/需警惕）

**数学89-92号缺失什么**：
- 90号文档有"诚实面对的不确定性"（5条），但这是关于经典计算展开的，不是关于工作系统整体的
- 91号方案没有诚实评估——没有说"这个方案有哪些已知局限"
- 92号方案有"诚实面对的不确定性"（4条），但只关于topo_generator
- 没有HoTT标签的诚实定位（数学项目用了"拓扑覆盖验证"这个词，但没有说这是朴素集合论还是真正的拓扑覆盖）
- 没有给其他AI的建议

**影响**：数学项目的方案看起来"什么都能做"，但没有诚实面对"什么做不到"。其他AI复用时可能盲目相信方案的有效性。

### 缺失5：认知图架构的数学形式化（对应星学89号）

**星学89号做了什么**：
- 认知图的形式化定义：`G_repo = (V, E, L, T, φ)`，5个组分的数学定义
- 图遍历的数学表达：`traverse(S, max_depth) = {v | ∃ path from s to v, s ∈ S, length(path) ≤ max_depth}`
- 覆盖验证的数学表达：`task_cogs - loaded_cogs = gaps`
- 版本链的数学结构：`版本链(v) = [version_1, version_2, ..., version_n]`
- 当前规模指标（67个认知单元/141条边/3.2%稀疏度/3.3:1压缩比）

**数学91号缺失什么**：
- 有认知单元设计（~30个）和依赖边设计（~30条），但没有数学形式化
- 没有图遍历的数学表达
- 没有覆盖验证的数学表达
- 没有规模指标（稀疏度/压缩比）

**影响**：数学项目的方案是工程级的（"建什么collection、写什么脚本"），但不是数学级的。如果其他AI要理解方案的数学结构，需要自己推导。

### 缺失6：其他AI如何复用的指南（对应星学90/91/92/93号都有）

**星学每篇文档都有**：

- 91号：最小验证/标准验证/回归验证 + 验证体系设计原则7条
- 92号：最小强制/标准强制 + 关键实现细节6条 + 如果必须用Stop hook的建议
- 93号：可直接复用/需调整/需警惕 三类建议

**数学89-92号缺失什么**：
- 91号方案有Check List但没有"其他AI如何复用"的指南
- 92号方案有Check List但没有复用指南
- 没有"最小实现/完整实现/增强实现"的分档
- 没有"需警惕"的清单

**影响**：数学项目的方案是"给自己看的"，不是"给其他AI看的"。如果其他AI要复用，不知道从哪里开始、哪些是必须的、哪些是可选的。

## 三、数学有而星学缺失的（3项）

### 数学有1：经典计算展开G'_topo的方案（92号）

**星学缺失什么**：
- 星学的G'_topo由meta AI生成（步骤2），没有经典计算展开的方案
- 星学93号"未来演进方向"中提到"AI辅助认知图维护"，但没有提到"经典计算展开G'_topo"
- 这是数学项目独有的愿景（用户提出）

**星学为什么没有**：
- 星学的G'_topo生成已经通过POC-9验证（meta AI生成，1次通过100%覆盖），没有动力做经典计算展开
- 数学项目的独特性在于"经典计算负责展开"的愿景——这需要数学项目自己探索

**价值**：这是数学项目对工作系统升级的**独有贡献**。如果实现成功，可以反哺星学项目。

### 数学有2：两套图共享ArangoDB的设计（91号）

**星学缺失什么**：
- 星学的认知图系统（cognition_units）和xishujuzhen系统（dg_nodes）是**独立的**——89号文档明确说"认知图系统是xishujuzhen系统的简化版"，两者没有共享数据库
- 星学的认知图在`xishujuzhen`数据库，xishujuzhen系统的三层图也在`xishujuzhen`数据库——但两套图的节点没有交叉引用

**数学91号做了什么**：
- 认知单元和数学依赖图节点共享`xishujuzhen_math`数据库
- 意识节点（不变量思维/局部-全局/逼近论/极端检验/数值检验）**同时存在于cognition_units和dg_nodes**
- cognition_sdk可以交叉引用dg_nodes

**价值**：这是数学项目对工作系统设计的**超越点**。星学的两套图是分离的，数学项目的两套图是共享的。

### 数学有3：意识节点作为认知单元的设计（91号）

**星学缺失什么**：
- 星学的意识节点（五行生克/阴阳昼夜/庙旺平陷等）在`study-notes/星学意识/`目录，**不在cognition_units中**
- 星学的cognition_units是工作认知（排盘引擎/格局规则库/形式化体系等），不是意识节点

**数学91号做了什么**：
- 数学项目的意识节点（不变量思维/局部-全局/逼近论/极端检验/数值检验）直接作为cognition_units
- 意识节点同时是工作认知单元和数学依赖图节点

**价值**：数学项目的意识节点有双重身份——它们既是AI的工作认知（做数学证明时需要的思维方式），又是数学依赖图的节点（证明步骤的calls目标）。这是数学项目独有的设计。

## 五、最严重的缺失：数学91号重蹈星学已废弃的v1覆辙

这是本次调查最重要的发现：

**星学92号明确记录**：
- v1用Stop hook + flag文件（work_pending）+ session_id防护
- 实测发现Stop hook影响subagent——subagent启动后被block，长时间不返回
- session_id防护方案不可靠
- **v1已废弃**，改为v2（git post-commit hook）

**数学91号方案**：
- 5.3节设计了`stop_hook_math.py`，用`stop_hook_active`和`work_pending` flag
- 5.2节设计了`prompt_hook_math.py`，设置`work_pending=1`
- 5.4节的hooks.v1.json包含UserPromptSubmit hook
- **这正是星学已废弃的v1方案**

**根本原因**：我编制91号方案时，只读了星学的`stop_hook.py`代码（v1的代码还保留着），没有读星学92号文档（明确记录了v1废弃的过程）。星学92号文档说"stop_hook.py保留（代码参考）"，我误以为它还在用。
