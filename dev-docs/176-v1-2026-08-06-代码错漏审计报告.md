## 二、P0发现详述

### 2.1 F-176-1：dataclass未设frozen=True

**问题**：`models/`模块的7个核心数据类都使用`@dataclass`但未设置`frozen=True`：
- `models/event.py:110` RawEvent
- `models/event.py:151` SemanticEvent
- `models/task.py:32` Task
- `models/workspace.py:18` Workspace
- `models/workspace.py:112` Budget
- `models/workspace.py:139` ModelConfig
- `models/workspace.py:158` RunState

**违反的约束**：
- 127号§1：Task schema冻结声明"Q_0在运行时保持冻结"
- 127号§2：Workspace schema冻结声明"W_t只能由版本化Reducer派生，不能被直接修改"
- 127号§3：Event schema冻结声明"原始事件append-only，不允许修改或删除"

**影响**：任何代码都可以直接修改`task.goal = "新目标"`或`raw_event.payload = {}`，绕过所有冻结约束。虽然`state_reducer/q0.py`有`verify_q0_frozen()`做哈希检查，但这只是事后检测，不是事前阻止。

**改进意见**：
1. 将7个核心数据类改为`@dataclass(frozen=True)`（或至少Task/RawEvent/SemanticEvent）
2. 对于需要更新status的字段（如Evidence.status），使用`dataclasses.replace()`创建新实例而非直接修改
3. 添加单元测试验证不可变性：尝试修改字段时应抛出`FrozenInstanceError`

### 2.2 F-176-2：candidate规则禁止自动发布无运行时拦截

**问题**：`heuristics/rule_store.py:294-333`的`check_no_online_auto_hint`和`check_no_auto_write_h`方法只返回字典`{"passed": True/False, ...}`，没有实际拦截逻辑。没有任何代码在candidate规则尝试在线提示或写入H图时抛出异常或阻止操作。

**违反的约束**：
- 123号§48：candidate规则禁止自动发布
- R-4风险防线：Agent迎合触发器
- 133号P3-8：candidate规则禁止自动发布

**影响**：如果未来在线运行时错误地加载了candidate规则，没有任何代码级机制会阻止它。当前的`check_no_online_auto_hint`只是个报告函数，不是强制执行函数。

**改进意见**：
1. 在`heuristics/matcher.py`的`match()`方法中添加强制检查：如果规则的`lifecycle_status != "published"`，抛出`RuleNotPublishedError`
2. 在`runtime/published_loader.py`中添加强制检查：加载规则时验证`lifecycle_status == "published"`（当前已有此检查，但需要确保它是唯一入口）
3. 添加集成测试：尝试用candidate规则做在线提示时应抛出异常

### 2.3 F-176-3：角色隔离验证方法未在业务逻辑中调用

**问题**：
- `heuristics/matcher.py:411-425`的`check_visibility_label`和`check_capability_token`方法存在但未被调用
- `matcher.py:141-185`的`match()`方法内部未调用任何验证方法
- `auditor/capability_tokens.py:142-167`的`verify_access`方法只在测试中调用
- `auditor/visibility_labels.py:120-125`的`check_access`只在测试中调用

**违反的约束**：
- 123号§607：角色边界落实为collection/visibility label/能力令牌
- 127号§10.6：CapabilityToken强制机制

**影响**：角色隔离是声明性的（定义了约束）而非强制性的（运行时未检查）。任何代码都可以绕过角色隔离直接访问collection。

**改进意见**：
1. 在`matcher.py`的`match()`方法入口处调用`check_visibility_label()`和`check_capability_token()`
2. 在`experiments/experiment_runner.py`的`run_experiment()`入口处调用`verify_access()`
3. 在所有ArangoDB访问层添加CapabilityToken验证

### 2.4 F-176-4：dg_adapter浅拷贝

**问题**：`retrieval/dg_adapter.py:65-66`使用`list(dg_nodes)`和`list(dg_edges)`复制列表，但这是浅拷贝——内部字典对象仍可被外部修改。

```python
self.dg_nodes = list(dg_nodes)  # 浅拷贝
self.dg_edges = list(dg_edges)  # 浅拷贝
```

`check_readonly`方法（101-108行）只检查列表长度，不检查内容是否被修改。

**违反的约束**：
- NO-10约束：不原地清空或迁移旧dg_*集合
- 123号§55：数据迁移原则
- 135号P5-8.2：验证adapter不修改dg_*数据（只读）

**影响**：外部代码可以通过原始引用修改`dg_nodes[0]["label"] = "modified"`，adapter内部的数据也会被修改，违反只读约束。

**改进意见**：
1. 使用深拷贝：`self.dg_nodes = copy.deepcopy(dg_nodes)`
2. 或使用不可变视图：将字典转为`MappingProxyType`或frozen dataclass
3. `check_readonly`应比较内容哈希而非长度

### 2.5 F-176-5：context_compiler/verification模块多处无异常处理

**问题**：
- `context_compiler/context_compiler.py:102-148` `compile()`方法无try-catch
- `context_compiler/minimality_audit.py:77-106` `audit()`方法无try-catch
- `verification/stall_detector.py:280-312` `StallAnnotationStore`的3个数据库操作方法无try-catch

**影响**：输入格式错误或数据库连接失败时，这些方法会直接崩溃，没有优雅降级或错误恢复。

**改进意见**：
1. 在`compile()`和`audit()`中添加输入格式验证和try-catch
2. 在`StallAnnotationStore`中添加ArangoDB连接异常处理
3. 定义明确的异常类型（如`CompilationError`、`AuditError`）

## 三、P1发现详述

### 3.1 F-176-6：manifest冻结检查只在开始时执行一次

**问题**：`experiments/experiment_runner.py:137-138`的manifest冻结检查只在`run_experiment()`开始时执行一次，后续无运行时保护。

**影响**：manifest可能在实验运行中被修改，违反G0-6约束。

**改进意见**：在每次读取manifest字段时验证`manifest.frozen == True`，或使用`@dataclass(frozen=True)`。

### 3.2 F-176-7：leakage_audit._filter_candidates逻辑矛盾

**问题**：`heuristics/leakage_audit.py:250-253`的条件判断矛盾——第250行排除某些候选，但第253行又保留它们。

**影响**：泄漏审计的过滤逻辑可能不正确，导致泄漏分数计算错误。

**改进意见**：审查250-253行的条件逻辑，明确排除和保留的条件。

### 3.3 F-176-8：dependency.verify_p6_3_compliance返回硬编码True

**问题**：`runtime/dependency.py:203`的`verify_p6_3_compliance()`方法返回硬编码`True`，未实际验证。

**影响**：P6-3合规检查（帮助依赖不超过预注册阈值）未实际执行，可能违反R-11风险停止条件。

**改进意见**：实现实际的依赖代理阈值验证逻辑。

### 3.4 F-176-9：representation_map.find_chain未检测环路

**问题**：`representation/representation_map.py:164-178`的`find_chain()`方法未检测环路，可能导致无限循环。

**改进意见**：添加访问集合`visited`，检测到已访问节点时停止。

### 3.5 F-176-10：stall_detector/verifier核心功能缺测试

**问题**：
- `verification/stall_detector.py`无独立测试
- `verification/verifier.py`的`verify()`方法无测试
- `policy/constraint_optimizer.py`无测试文件

**影响**：卡点检测（DYN-2核心）和验证路由（P5-6核心）无测试覆盖，无法确认逻辑正确性。

**改进意见**：为stall_detector、verifier、constraint_optimizer添加独立测试文件。

### 3.6 F-176-11：evidence/obligation的update_status允许更新

**问题**：
- `state_reducer/evidence.py:156-163` `update_status()`允许更新status
- `state_reducer/obligation.py:179-191` `update_obligation_status()`允许更新status

**分析**：这两个方法本身是合理的——Evidence的status从pending→active→superseded→retracted是合法的状态转移。但127号§3说"原始事件append-only"，而Evidence/Obligation不是原始事件，它们的status更新是合法的。

**判定**：这个发现需要更细致的分析。Evidence和Obligation的status更新是合法的状态转移，不是违反append-only。但需要确保状态转移方向正确（如不能从retracted回到active）。

**改进意见**：在`update_status()`中添加状态转移方向验证，确保只允许合法的状态转移。

## 七、对用户三个担心的回答（补充）

### 担心3：Phase具体实现是否错漏百出？

**回答**：**是的，存在多个P0级错漏**。最严重的5个P0问题：
1. 7个核心dataclass未设frozen=True——冻结约束是声明性的不是强制性的
2. candidate规则禁止自动发布无运行时拦截——R-4核心防线只是报告函数
3. 角色隔离验证方法未在业务逻辑中调用——只在测试中调用
4. dg_adapter浅拷贝——外部可修改内部数据
5. context_compiler/verification多处无异常处理——输入错误会崩溃

**但**：代码的逻辑架构是正确的——DAG验证、来源追溯链、5项记录、义务超边存储等核心逻辑都有完整实现。问题主要集中在"声明性vs强制性"——约束定义了但未在运行时强制执行。

**改进路径**：5个P0问题都有明确的修复方案（见§五），修复工作量估计在1-2天内。修复后代码的强制机制将显著增强。
