# 96-诚实评估与未来·数学项目工作系统

> **文档定位**：诚实评估数学项目工作系统的愿景达成度，指出已知局限和未来演进方向。对应星学93号文档。
>
> **依据**：93号差距分析 + 91/92号方案 + 94号POC验证体系 + 95号设计哲学

## 一、愿景达成度对比

数学项目有两套图驱动的系统：

1. **认知图系统**（工作系统）：管理AI自己的工作认知（~30个认知单元）
2. **数学依赖图系统**（目标系统）：管理数学证明的依赖结构（dg_nodes/dg_edges/loops）

### 1.1 对比表

| 维度 | 认知图系统（工作系统） | 数学依赖图系统（目标系统） |
|---|---|---|
| 节点 | ~30个认知单元 | 18个证明节点（POC-2） |
| 边 | ~30条 | 25条 |
| 图结构 | 单层 | 三层（G/G'_topo/G'_full） |
| 图展开 | BFS图遍历（AQL） | BFS图遍历 + **经典计算展开骨架**（92号方案） |
| 覆盖验证 | 集合差集（found vs ground_truth） | AQL集合差集 + TopologyVerifier |
| 螺旋环路 | 无（当前） | 有：2个环路（POC-2） |
| 知识内容 | key_cognition字段（摘要） | kcs集合（POC-2有） |
| 验证结果 | **待验证**（94号POC-R1-Math设计完成，未执行） | POC-2: 1次通过100%覆盖 |

### 1.2 数学依赖图系统做到了什么

**拓扑覆盖验证**：TopologyVerifier从星学零修改复用，POC-2中1次通过100%覆盖（18/18节点，25/25边，2/2环路）。这是确定性代码验证。

**螺旋环路**：POC-2的依赖图有2个螺旋环路（极端检验↔数值检验意识，局部-全局↔逼近论），环路圈数在G'_topo中保持。

**七步骤工作流**：依赖图导入→G'_topo生成→拓扑验证→转译→KC审计→分析→分析覆盖审计。POC-2验证了全流程。

### 1.3 认知图系统（工作系统）做到了什么

**方案设计完成**：91号方案完成了认知单元设计（~30个）、ArangoDB collections设计、核心脚本设计、Hook设计（v2方案，吸取星学教训）、Check List。

**未实现**：方案还是纸面的，代码未编写，ArangoDB collections未创建，认知单元未导入，Hook未部署。

### 1.4 经典计算展开做到了什么

**方案设计完成**：92号方案完成了L0骨架展开算法（Kahn拓扑排序）、L1类型推断、L2 section划分推荐、验证方案设计。

**未实现**：topo_generator.py未编写，未用POC-2依赖图测试。

## 二、已知局限

### 2.1 认知图系统是星学的简化版

**问题**：数学项目的认知图系统（91号方案）是星学认知图系统的简化版。它用了图遍历和集合差集，但没有三层图结构、没有螺旋环路检测、没有拓扑骨架展开。

**与星学93号文档的诚实定位一致**：星学也承认其认知图系统是xishujuzhen系统的简化版。数学项目继承了同样的局限。

**未来方向**：引入三层图结构到认知图系统（中期目标）。

### 2.2 种子选择依赖AI概率判断

**问题**：CP1（种子选择）由AI自己决定选哪些认知单元作为种子。AI可能选错种子——漏选重要前置认知，或选了无关的种子。

**与星学93号文档的已知局限一致**：星学也有同样的局限。

**当前缓解**：AGENTS.md中列出所有core认知单元，AI可以参考；CP3缺口检查提醒AI"图遍历可能遗漏与种子无依赖边但任务相关的认知单元"。

**未解决**：没有确定性算法自动选择种子。

### 2.3 覆盖验证是朴素集合论

**问题**：认知图系统的覆盖验证是Python set操作`task_ids - loaded_set`。这只是检查"哪些认知单元没被加载"，不检查"加载的认知单元之间的依赖关系是否被正确使用"。

**与星学93号文档的诚实定位一致**：星学也承认其覆盖验证是朴素集合论，不是HoTT级别的拓扑覆盖验证。

**数学项目的优势**：数学依赖图系统有TopologyVerifier做拓扑覆盖验证（四层验证：节点+边+跨宫边+环路）。但认知图系统没有。

**未来方向**：在认知图系统中引入边覆盖验证和环路检测（短期目标）。

### 2.4 Hook强制力降级

**问题**：v2用git post-commit hook替代了v1的Stop hook。强制力从"硬block"降级为"提示"。AI看到CP4检查清单后可以"看完就忽略"。

**与星学93号文档的已知局限一致**：星学也有同样的局限。

**当前缓解**：三层维护机制（CP4提示+AGENTS.md约束+认知图依赖）提供多重提醒。

**未解决**：没有硬block机制。

### 2.5 ArangoDB是单点依赖

**问题**：整个工作系统依赖ArangoDB运行。ArangoDB未运行时，所有Hook脚本graceful降级，认知图操作不可用。

**与星学93号文档的已知局限一致**。

**未来方向**：考虑SQLite作为fallback。

### 2.6 经典计算展开的section划分质量不确定

**问题**：92号方案的L2 section划分用启发式规则（每5个一段+意识单独成章），这是粗糙的近似。meta AI的section划分更符合数学证明的逻辑结构。

**数学项目独有局限**（星学没有这个问题，因为星学的G'_topo由meta AI生成）。

**当前缓解**：L2是推荐，AI可以在L3阶段调整section边界。

**未解决**：经典计算的section划分质量需要POC-3-Math验证（94号方案）。

### 2.7 两套图共享的一致性风险

**问题**：意识节点在cognition_units和dg_nodes中都有记录，如果一处更新另一处没更新，会导致内容不一致。

**数学项目独有局限**（星学的两套图是独立的，没有这个问题）。

**当前缓解**：POC-4-Math验证一致性（94号方案）。

**未解决**：没有自动同步机制。未来可以探索触发器或应用层同步。

### 2.8 工作系统未实现

**问题**：91号方案是纸面方案，代码未编写，ArangoDB collections未创建，认知单元未导入，Hook未部署。

**这是最根本的局限**——方案设计再好，不实现就没有价值。

**未来方向**：按91号方案的Check List逐步实现。

## 三、HoTT标签的诚实定位

### 3.1 哪些是已实现的

- **图遍历**：BFS图遍历（AQL）——已在POC-2中实现，确定性
- **集合差集覆盖验证**：Python set操作——已在POC-2中实现，确定性
- **拓扑覆盖验证**（数学依赖图）：TopologyVerifier的AQL集合差集——已在POC-2中实现，确定性
- **螺旋环路检测**（数学依赖图）：图论算法——已在POC-2中实现
- **版本链**：时序图——91号方案设计完成，未实现

### 3.2 哪些是愿景标签而非实现

- **HoTT（同伦类型论）**：用作概念框架理解问题，但没有用HoTT的任何数学工具做实际验证。覆盖验证用的是朴素集合论，不是HoTT的covering map。
- **拓扑学**：用了"拓扑覆盖"这个词，但实际验证是集合差集，不是拓扑学意义上的覆盖映射。
- **稀疏矩阵**：用了"稀疏矩阵"这个概念，但实际存储是图数据库，不是矩阵。稀疏度只是描述性指标。

### 3.3 数学项目比星学更接近HoTT的地方

数学项目的数学依赖图系统比星学的xishujuzhen系统更接近HoTT，因为：

- **数学对象本身就是拓扑结构**：数学证明的依赖链天然是拓扑结构（86号文档论述）
- **螺旋环路有数学含义**：极端检验↔数值检验意识的螺旋环路对应数学意识迭代，不是人工标注的
- **经典计算展开是拓扑同构**：92号方案的L0骨架展开从G直接拷贝节点集和边集，这是拓扑同构

**但仍然不是HoTT**：覆盖验证仍然是集合差集，不是HoTT的covering map。

### 3.4 诚实结论

数学项目工作系统的**工程实现**是扎实的（POC-2已验证数学依赖图系统的有效性）。

数学项目工作系统的**数学标签**是愿景性的——HoTT/拓扑学是理解问题的概念框架，不是已实现的数学工具。

**其他AI复用时的建议**：
- 工程实现可以直接复用（图遍历+集合差集+版本链+Hook+TopologyVerifier）
- 数学标签可以保留作为愿景，但不要声称已经实现了HoTT级别的验证
- 经典计算展开G'_topo是数学项目的独有贡献，可以反哺星学项目

## 四、未来演进方向

### 4.1 短期（可立即实现）

1. **实现91号方案**：编写代码，创建ArangoDB collections，导入认知单元，部署Hook
2. **实现92号方案**：编写topo_generator.py，用POC-2依赖图测试
3. **执行POC-R1-Math**：验证工作系统有效性（94号方案）
4. **执行POC-3-Math**：验证经典计算展开有效性（94号方案）
5. **边覆盖验证**：在认知图系统中引入边覆盖验证

### 4.2 中期（需要一定开发量）

6. **三层图结构**：在认知图系统中引入三层图结构（G/G'_topo/G'_full）
7. **种子推荐**：根据任务描述自动推荐种子认知单元
8. **SQLite fallback**：小规模认知图用SQLite+JSON模拟图遍历
9. **两套图自动同步**：意识节点的cognition_units和dg_nodes记录自动同步

### 4.3 长期（需要研究）

10. **真正的HoTT验证**：用HoTT的数学工具做覆盖验证
11. **螺旋环路自动识别**：自动区分平面环路和螺旋环路
12. **认知图自动演化**：从POC评分结果中自动发现新数学意识节点，自动构建依赖图
13. **计算验证集成**：Lean 4 / SageMath作为数学证明的计算验证层

## 五、给其他AI的最终建议

### 5.1 可以直接复用的

- **设计哲学**（95号文档）：10个设计决策（7个从星学继承+3个数学独有）
- **认知图架构**（91号方案）：认知单元/版本链/边类型/ArangoDB schema
- **Hook设计**（91号方案v2）：git post-commit hook + 三层维护机制（**不要用Stop hook**）
- **POC验证方法论**（94号方案）：D1-D6评分+H1-H8假设检验+回归验证
- **经典计算展开**（92号方案）：topo_generator.py的L0+L1+L2算法

### 5.2 需要根据项目情况调整的

- **认知单元数量和分类**：根据项目规模调整core/process/support的比例
- **边类型**：根据项目需要增减边类型
- **Hook触发时机**：如果项目不用git，需要找其他触发机制
- **检查清单内容**：根据项目纪律调整stop_hook的depends_on边
- **经典计算展开的section划分规则**：根据领域特点调整L2的启发式规则

### 5.3 需要警惕的

- **不要用Stop hook做block**：会影响subagent（星学92号文档实测证实，数学91号方案v2吸取了教训）
- **不要硬编码检查清单**：从认知图动态查询，未来加新纪律只需加一条边
- **不要把文档当节点**：节点是认知单元，不是文档
- **不要忽略版本链**：认知会迭代，需要版本链处理演化
- **不要声称实现了HoTT**：覆盖验证是朴素集合论，不是HoTT
- **不要跳过POC验证**：工作系统的有效性需要实证证明（94号方案）
- **不要把两套图混在一起**：集合名隔离，图遍历隔离，意识节点双重身份需要一致性验证
- **不要期望经典计算展开替代AI全部工作**：L3语义标注仍需要AI
