## 一、问题

178-182号定义了"审计什么维度"（时间线、决策链、思路链等8个维度），但没有定义**每个模块审什么、什么算好、什么算不好**。

审计标准不是一份文档能搞定的——每个模块功能不同，审什么完全不同。需要按模块建立审计元组：
- **Rule**（always-on）：触发审计的条件
- **Skill**（on-demand）：审计的工作流
- **审计文档**（dev-docs/）：审计的具体内容、标准、经验，维护在skill之外

## 三、审计元组设计

每个模块的审计是一个元组：

```
Rule（always-on）→ 触发条件
  ↓
Skill（on-demand）→ 审计工作流
  ↓
审计文档（dev-docs/）→ 具体标准、经验、案例
```

### 3.1 Rule的职责

Rule负责"什么时候审"：
- 每次run结束后审
- 每次模块代码变更后审
- 每次认知图变更后审
- 定期回归审计

### 3.2 Skill的职责

Skill负责"怎么审"：
- 从哪里取数据（sessions.db / ArangoDB / run目录）
- 检查哪些项
- 如何判定通过/不通过
- 如何输出审计报告

### 3.3 审计文档的职责

审计文档负责"审什么、标准是什么、经验在哪"：
- 该模块的功能定义
- 审计检查项清单（逐项）
- 每项的通过/不通过标准
- 历史审计中发现的问题和修复经验
- 边界情况和已知限制
