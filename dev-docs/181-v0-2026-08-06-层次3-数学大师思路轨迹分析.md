## 二、数据源

### 2.1 sessions.db的`thinking`字段——核心数据源

**重大发现**：devin cli的sessions.db中，`message_nodes`表的`chat_message`JSON包含`thinking`字段，记录了AI的内部推理过程。

```json
{
  "role": "assistant",
  "content": "",
  "tool_calls": [{"id": "...", "name": "exec", "arguments": {"command": "..."}}],
  "thinking": {
    "thinking": "用户问的是：用户需求.md中对未来工作有很多期许...\n\n我需要：\n1. 读取用户需求.md\n2. 了解期许内容\n3. 查看现有方案文档\n4. 对比分析\n\n先并行读取用户需求.md和列出dev-docs目录。",
    "signature": ""
  }
}
```

**这意味着**：数学大师的思考过程已经被devin cli自动记录——不需要额外开发记录机制，只需要分析工具。

### 2.2 层次1的conversation.json

`--export`导出的conversation.json是精简版（无thinking），但包含完整的消息流——可以看到数学大师每一步说了什么、做了什么。

### 2.3 层次2的ExecutionLog

系统内部的ExecutionLog记录了每一步系统给了什么提示、做了什么决策——这是"引导链"的数据源。

## 三、思路轨迹的构成

数学大师的完整思路轨迹由以下部分构成：

| 组成部分 | 数据来源 | 说明 |
|---|---|---|
| 思考过程 | sessions.db `thinking`字段 | AI每一步的内部推理 |
| 行为选择 | sessions.db `tool_calls`字段 | AI每一步选择了什么工具、什么参数 |
| 输出文本 | conversation.json / sessions.db `content` | AI每一步对外说了什么 |
| 系统引导 | 层次2 ExecutionLog | 系统每一步给了什么提示 |
| 引导回应 | 交叉关联thinking+ExecutionLog | AI如何回应系统的提示 |
| 卡点反应 | SemanticEvent + thinking | AI遇到卡点时的反应（停/换/求助） |
| 顿悟时刻 | thinking文本分析 | AI从不知道到知道的转变点 |

## 四、方案设计

### 4.1 思路轨迹提取

从sessions.db提取thinking + tool_calls + content，按时间排序，构成思路轨迹：

```python
def extract_thinking_trajectory(session_id: str):
    """从sessions.db提取数学大师的思路轨迹"""
    conn = sqlite3.connect("~/.local/share/devin/cli/sessions.db")

    messages = conn.execute(
        "SELECT node_id, chat_message, created_at FROM message_nodes "
        "WHERE session_id = ? AND chat_message LIKE '%\"role\":\"assistant\"%' "
        "ORDER BY node_id",
        (session_id,)
    ).fetchall()

    trajectory = []
    for node_id, chat_message, created_at in messages:
        msg = json.loads(chat_message)
        trajectory.append({
            "step": node_id,
            "timestamp": created_at,
            "thinking": msg.get("thinking", {}).get("thinking", ""),
            "action": msg.get("tool_calls", []),
            "output": msg.get("content", ""),
            "metadata": msg.get("metadata", {}),
        })
    return trajectory
```

### 4.2 引导-回应关联分析

将层次2的ExecutionLog（系统引导）与层次3的思路轨迹（AI回应）按时间戳关联：

```
时间线：
  t1: 系统StateReducer检测到卡点 → ExecutionLog记录
  t2: 系统HeuristicMatcher匹配规则 → ExecutionLog记录
  t3: 系统ContextCompiler编译提示 → ExecutionLog记录
  t4: 系统发送提示给devin cli → user消息
  t5: devin cli的AI读到提示 → thinking字段记录推理
  t6: devin cli的AI选择行动 → tool_calls记录
  t7: devin cli的AI输出回应 → content记录
  t8: 系统EventCapture捕获AI输出 → RawEvent记录
  t9: 系统StateReducer重建状态 → ExecutionLog记录
  → 循环
```

**关联键**：时间戳 + run_id + session_id。

### 4.3 思路分析维度

| 分析维度 | 问题 | 方法 |
|---|---|---|
| 方向选择 | AI每一步选择了什么方向？ | 从thinking文本提取关键词 |
| 方向理由 | AI为什么选这个方向？ | 从thinking文本提取推理链 |
| 卡点反应 | AI遇到卡点时怎么反应？ | 关联SemanticEvent + thinking |
| 提示效果 | 系统提示后AI的思路变化？ | 对比提示前后的thinking文本 |
| 弯路检测 | AI有没有走弯路？ | 分析thinking中的自我纠正信号 |
| 顿悟时刻 | AI什么时候从不知道到知道？ | 分析thinking中的认知转变信号 |

### 4.4 自动化程度

| 分析任务 | 自动化程度 | 方法 |
|---|---|---|
| 思路轨迹提取 | ✅ 全自动 | 从sessions.db查询 |
| 引导-回应关联 | ✅ 全自动 | 按时间戳关联 |
| 方向选择提取 | ⚠️ 半自动 | 关键词匹配 + AI辅助标注 |
| 卡点反应分析 | ⚠️ 半自动 | SemanticEvent + AI辅助 |
| 提示效果分析 | ⚠️ 半自动 | 文本对比 + AI辅助 |
| 弯路检测 | ❌ 需AI辅助 | 需理解thinking的语义 |
| 顿悟时刻识别 | ❌ 需AI辅助 | 需理解thinking的语义 |

**AI辅助标注的方式**：用另一个AI（如本Master AI）读thinking文本，标注思路分析维度。这比人工标注快，但需要验证标注质量。
