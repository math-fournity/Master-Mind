## 1 · 我的理解

### 1.1 这是一种 AI 使用范式

我们当前在 study-notes/ 上做的工作，本质上是在建设一个 **全新的、AI 原生的七政四余知识系统**。这个新系统不是任何一本典籍的电子版，也不是多本典籍的简单合并，而是一个 **重新组织的、有结构的、可被 AI 和经典计算高效遍历使用的** 知识载体。

与之相对，《星平会海》、《果老星宗》、《星学大成》、《天步真原》等典籍，都是相对于我们这个新系统的 **老系统**——它们是参考文献，是原料来源，不是产物本身。

### 1.2 新系统的结构特征

新系统（study-notes/）的结构必须满足：

1. **树状 DAG**：内容按编号组织成树/有向无环图，不是扁平大杂烩
2. **数字编号的步骤**：每个文件是一个"步骤"，有编号顺序（01-历法基础→02-星历计算→...→20-琴堂断法歌诀）
3. **DFS 可遍历**：经典计算和 AI 计算可以按编号顺序做全遍历，不漏不重
4. **步骤视角入库**：所有内容（包括产物、前置准备）都放在"步骤"视角下入库，带步骤编号
   - 例：历算是步骤（01-历法基础），历算的产物（节气表/月将表）也放在 01 步骤视角下入库
   - 例：格局判断是步骤（09-格局分析），格局判断的产物（格局清单/判读规则）也放在 09 步骤视角下入库

**关键约束**：study-notes 不是结构乱的大杂烩。任何时候入库新内容，都要先回答"这属于哪个步骤？步骤编号是什么？"

### 1.3 老系统的角色

老系统（典籍）是原料，不是产物。它们的内容被 **选择性地吸收** 进新系统。但吸收必须是 **双向可追溯** 的：

| 方向 | 含义 | 当前状态 |
|---|---|---|
| 新系统 → 老系统 | study-notes 中的每条内容，都能反查到它来自老系统的哪个 XPATH | **已实现**（`[文献:星平会海/卷二/二十四要法/论四时]` 这种标注） |
| 老系统 → 新系统 | 老系统的每条内容，都能查到它是否已被吸收进新系统、被吸收到哪个步骤 | **缺失**（这正是本次要补的） |

### 1.4 当前漏的事

我们当前只保证了"新→老"方向的反查（通过 `[文献:...]` XPATH 标注），但没有保证"老→新"方向的全面追踪。也就是说：

- 我们无法回答"《星平会海》卷一星曜躔度歌的 308 条规则，有多少已经被吸收进 study-notes？哪些还没被吸收？"
- 我们无法回答"《星平会海》卷二入门四十四看法的 44 条，每条分别被吸收到了 study-notes 的哪个步骤？"

这就意味着老系统的内容可能被 **遗漏**，而我们无法发现。

### 1.5 解决方案：老系统 Schema = Check List XPATH List

为每个老系统（每本典籍）建立一份完整的 Schema，以 **XPATH 列表** 的形式记录。每条 XPATH 作为一个 **Check List Item**，可标记是否已被吸收、被吸收到哪个步骤。

**Schema 粒度**：灵活把握，不强制统一。原则是"一条 XPATH 对应一个可独立吸收的知识单元"。
- 好的粒度示例：`星曜躔度歌/角度星耀/木躔角宿`（一条躔度规则）
- 好的粒度示例：`入门四十四看法/一宫主`（一条看法）
- 好的粒度示例：`二十四要法/论四时`（一条要法）
- 太粗的粒度：`卷一`（一整卷，无法追踪单条吸收状态）
- 太细的粒度：`星曜躔度歌/角度星曜/木躔角宿/诗句第一句`（比知识单元还小）

### 2.4 与现有 schema.json / full_path_tree.json 的关系

dev-docs/原典/星平会海/ 下已有两个 JSON 文件：
- `schema.json`（3875行）：机器可读的结构化索引，含每条规则的 id/star/name/text
- `full_path_tree.json`（6608行）：带行号定位的完整路径树，含 hash

**关系**：
- 现有 JSON 是 **机器可读的结构化索引**，是 Schema 的数据源
- 新方案 Markdown Check List 是 **人机皆可读的吸收追踪表**，是从 JSON 派生的
- 生成方式：可写脚本从 schema.json / full_path_tree.json 自动生成 Markdown Check List 骨架，然后人工/ AI 标注吸收状态
- JSON 不废弃，作为权威数据源；Markdown Check List 作为追踪视图

### 2.5 XPATH 命名规范

为保持与现有 `[文献:星平会海/卷二/二十四要法/论四时]` 标注的一致性，外部系统 Schema 文件中的 XPATH 采用 **相对路径**（不含"星平会海/"前缀，因为已在目录名中）：

## 4 · 关键设计决策（需用户确认）

### 4.1 Schema 文件放在 study-notes/外部系统/ 还是 dev-docs/原典/？

**推荐**：放在 `study-notes/外部系统/《星平会海》/`。

**理由**：
- study-notes/ 是新系统的载体，外部系统 Schema 是新系统的"吸收追踪表"，逻辑上属于新系统的配套
- dev-docs/原典/ 放的是老系统的原始内容（txt 全文）和机器可读索引（JSON），是"原料仓库"
- Check List 是"吸收进度视图"，是新系统视角的产物，放 study-notes/ 更合理
- 与 study-notes/01-20 同级，方便对照

### 4.2 Check List 粒度策略

**推荐**：按内容类型分级。

| 内容类型 | 粒度 | 理由 |
|---|---|---|
| 躔度歌（308条） | 条级（每星每宿一条） | 每条是独立规则，需独立追踪 |
| 照宫歌（132条） | 条级（每星每宫一条） | 同上 |
| 交会歌（~60条） | 条级（每对星一条） | 同上 |
| 入门四十四看法（44条） | 看法级（每条看法一条） | 每条是独立概念 |
| 二十四要法（24条） | 要法级（每条要法一条） | 同上 |
| 步天警句 | 句级（每句警句一条） | 每句是独立断法 |
| 琴堂总诀（36条） | 条级（每条歌诀一条） | 同上 |
| 女命警诀/总诀 | 条级 | 同上 |
| 碎金总诀（40条） | 条级 | 同上 |
| 卷三论十二宫 | 宫级（每宫一条） | 每宫是独立论断单元 |
| 卷四-十各种格局 | 格级（每种格局一条） | 每种格局是独立规则 |

### 4.3 已吸收标记格式

**推荐**：`- [x] XPATH → study-notes/NN-步骤名（吸收方式）`

**吸收方式分类**：
- `（全文吸收）`：整条内容被吸收
- `（要点吸收）`：只吸收了要点
- `（引用吸收）`：作为典籍依据引用
- `（归纳吸收）`：被归纳进某个总结表

### 4.4 是否为每本典籍都建 Schema？

**推荐**：是。但优先级：
1. 《星平会海》（当前主要来源，优先）
2. 《果老星宗》（后续引入时建）
3. 《星学大成》（后续引入时建）
4. 其他典籍（按需建）

## 6 · 与现有 AGENTS.md 出处标注规则的关系

AGENTS.md 中已有的出处标注规则（`[文献:典籍名/卷/篇目/小节]` + `[内知]`）是 **新→老方向** 的反查机制，本次新增的 Check List XPATH List 是 **老→新方向** 的追踪机制。两者互补，共同构成完整的双向可追溯体系。

```
新系统 study-notes/01-20          老系统 study-notes/外部系统/《星平会海》/
┌─────────────────┐              ┌──────────────────────┐
│ 09-格局分析.md   │              │ 卷一/001-星曜躔度歌.md │

│  卷一/星曜躔度歌/│              │   → study-notes/09   │
│  角/木-天贵]     │  ◀─老→新──  │ - [ ] 角/气-天异      │
└─────────────────┘              └──────────────────────┘
        ↑                                ↑
    反查标注                         Check List 追踪
    （已实现）                       （本次新增）
```

## 7 · 总结

这个范式的核心是：**把 AI 建设的知识系统当成一个有结构的全新系统，把典籍当成原料仓库，用双向 XPATH 机制保证吸收的完整性和可追溯性。**

- 新系统是树状 DAG，数字编号步骤，DFS 可遍历
- 老系统是参考文献，每本典籍建一份 Check List XPATH List
- 新→老：`[文献:...]` 标注（已实现）
- 老→新：Check List 吸收状态追踪（本次新增）
- Schema 粒度灵活，按内容类型分级
- study-notes 中的内容一定是"步骤"视角，带步骤编号，不是大杂烩
