# 64-xishujuzhen POC 验证方案

## 1. 验证命题

### 1.1 从 63 号文档核心信念到可验证命题

63 号文档的核心信念是：

> 完美的提示词，是可以通过经典计算产生的。

这个信念是宏大的，POC 不能一次性验证它的全部。POC 验证的是一个更谦虚的、可证伪的命题：

> **在星学的命宫分析场景中，AI 在 xishujuzhen 依赖图提示下的分析质量，在结构化评分的多个维度上，显著优于直接读 study-notes 时的分析质量。**

如果这个命题成立，说明依赖图提示确实能帮助 AI 做出更好的分析——核心信念在最小范围内得到支持，可以扩展到更大范围继续验证。

如果这个命题不成立，有两种可能：
- 依赖图提示的方向是对的，但 POC 的实现有问题（提示格式不对、粒度不对、依赖图不完整）→ 调整后重试
- 依赖图提示的方向本身有问题 → 核心信念受到挑战，需要重新审视

### 1.2 POC 不验证什么

- 不验证 xishujuzhen 能否扩展到全系统（那是后续工作）
- 不验证依赖图能否自动构建（POC 的依赖图是手动构建的）
- 不验证系统能否处理矫正、流年等复杂场景
- 不验证"综述博士角色可工程化"这个宏大命题（那是 63 号文档深层含义层面的，POC 只验证最小命题）

## 2. 验证方法：对照实验

### 2.1 实验设计

同一张简化星盘，同一分析任务（命宫分析），两种条件：

| 条件 | AI 拿到什么 | 对应什么场景 |
|---|---|---|
| **A 组（对照组）** | study-notes 中命宫相关内容的 Markdown 文本 | 模拟当前工作方式：AI 直接读知识文档分析 |
| **B 组（实验组）** | xishujuzhen 生成的依赖图提示 JSON | 模拟 xishujuzhen 工作方式：AI 拿到依赖图提示后分析 |

两组使用同一个 AI（同一个模型、同一个 session 或平行 session），分析同一张盘的同一个任务。

### 2.2 可比性保证

- 两组的星盘数据完全相同（同一份简化盘数值）
- 两组的分析任务表述完全相同（"分析此命的命宫"）
- 两组的 AI 指令除了输入材料不同外，其余完全相同
- A 组拿到的 study-notes 内容是真实的命宫相关知识
- B 组拿到的依赖图提示中的知识指向同一批 study-notes 内容，但以依赖图结构呈现

### 2.3 评判方式

结构化评分，定义 5 个维度，每个维度 1-5 分。评分者盲评（不知道哪个是 A 组哪个是 B 组）。

### 3.5 环路

依赖图中有一个环路：`五行生克 → 阴阳昼夜 → 五行生克`。

这个环路在 POC 中是**螺旋环路**——第一次五行生克在"命主星木在寅"上下文中被调用，第二次五行生克在"昼生木旺"上下文中被调用。上下文不同，是螺旋上升，不是平面循环。

### 3.6 依赖图可视化

```
命宫分析
  ├──depends_on──→ 命主星判断
  │                   ├──calls──→ 庙旺平陷
  │                   │              └──calls──→ 五行生克 ←──┐
  │                   └──calls──→ 五行生克                    │
  └──calls──→ 庙旺平陷                                    阴阳昼夜
                                                                └──calls──→ 五行生克（螺旋）
```

## 4. 依赖图构建

### 4.1 图的数据结构（networkx DiGraph）

```python
import networkx as nx

graph = nx.DiGraph()

# 节点（带元数据）
graph.add_node("命宫分析", type="step", context="命宫")
graph.add_node("命主星判断", type="substep", context="命宫/命主木星")
graph.add_node("庙旺平陷", type="意识", context="命宫/星曜庙旺")
graph.add_node("五行生克", type="意识", context="命宫/五行关系")
graph.add_node("阴阳昼夜", type="意识", context="命宫/昼生")

# 边（带依赖类型）
graph.add_edge("命宫分析", "命主星判断", type="depends_on")
graph.add_edge("命宫分析", "庙旺平陷", type="calls")
graph.add_edge("命主星判断", "庙旺平陷", type="calls")
graph.add_edge("命主星判断", "五行生克", type="calls")
graph.add_edge("庙旺平陷", "五行生克", type="calls")
graph.add_edge("五行生克", "阴阳昼夜", type="calls")
graph.add_edge("阴阳昼夜", "五行生克", type="calls")
```

### 4.2 环检测与分类

```python
def classify_cycles(graph):
    """检测环路并分类为平面环路或螺旋环路"""
    sccs = list(nx.strongly_connected_components(graph))
    cycles = []
    for scc in sccs:
        if len(scc) > 1:  # 多节点 SCC = 有环
            contexts = {graph.nodes[n]['context'] for n in scc}
            if len(contexts) == 1:
                cycles.append({
                    'type': 'planar',
                    'nodes': list(scc),
                    'context': contexts.pop(),
                    'note': '平面环路：同一上下文中的循环，应停止追溯'
                })
            else:
                cycles.append({
                    'type': 'spiral',
                    'nodes': list(scc),
                    'contexts': list(contexts),
                    'note': '螺旋环路：跨上下文的深化，应继续追溯'
                })
    return cycles
```

对于 POC 的图，SCC 检测会发现 `{五行生克, 阴阳昼夜}` 构成一个 SCC（互相可达）。它们的上下文分别是"命宫/五行关系"和"命宫/昼生"——不同上下文，分类为螺旋环路。

## 6. 对照实验执行方案

### 6.1 执行步骤

1. **准备星盘数据**：手动构造上述简化盘，写成一份星盘摘要文本
2. **准备 A 组材料**：从 study-notes 中提取命宫相关内容，拼成一份 Markdown 文档
3. **准备 B 组材料**：运行 POC 脚本生成依赖图提示 JSON
4. **执行 A 组分析**：给 AI 星盘摘要 + study-notes Markdown，要求分析命宫
5. **执行 B 组分析**：给 AI 星盘摘要 + 依赖图提示 JSON，要求分析命宫
6. **收集两组输出**：保存两次分析的完整输出
7. **盲评打分**：评分者不知道哪个是 A 哪个是 B，对两个输出按 5 个维度打分

### 6.2 AI 指令模板

两组的 AI 指令除了输入材料外完全相同：

```
你是一位七政四余星学分析师。请分析以下命盘的命宫。

[星盘摘要]

[输入材料：A组为study-notes内容 / B组为依赖图提示JSON]

请给出完整的命宫分析，包括：
- 命主星判断
- 命宫星曜配置吉凶
- 命宫整体格局判断
```

## 7. 评判标准

### 7.1 评分维度（5 维，每维 1-5 分）

| 维度 | 1 分 | 3 分 | 5 分 | 权重 |
|---|---|---|---|---|
| **完整性** | 遗漏多个该考虑的方面 | 覆盖主要方面但有遗漏 | 覆盖全部该考虑的方面（命主星、庙旺、五行、昼夜、星曜配置、格局） | 0.25 |
| **准确性** | 命理判断有明显错误 | 判断基本正确但有瑕疵 | 命理判断全部正确 | 0.25 |
| **深度** | 停留在表面描述 | 涉及部分底层意识 | 深入到五行生克、阴阳昼夜等底层意识，且有逻辑递进 | 0.20 |
| **逻辑性** | 判断之间缺乏逻辑联系 | 有部分逻辑链但不完整 | 判断之间有清晰的逻辑依赖链，能看出"因为A所以B" | 0.15 |
| **结构感** | 平铺直叙，无结构 | 有一定组织但不够清晰 | 分析结构清晰，能看出知识间的依赖关系和层次 | 0.15 |

### 7.2 综合评分

综合评分 = Σ（维度得分 × 权重），满分 5 分。

### 7.3 "显著优于"的定义

- B 组综合评分比 A 组高 **0.5 分以上**（满分 5 分的 10%），且
- B 组在**至少 3 个维度**上不低于 A 组，且
- B 组在**至少 2 个维度**上比 A 组高 1 分以上

同时满足这三个条件，判定为"显著优于"。

## 8. 成功/失败定义

### 8.1 成功（信念得到支持）

B 组显著优于 A 组。

含义：依赖图提示确实能帮助 AI 做出更好的命宫分析。核心信念在最小范围内得到支持。

后续行动：扩展 POC 范围——增加知识节点和意识、增加分析任务（官禄宫、格局、大限）、引入真实星盘（调用 qizheng）。

### 8.2 部分成功

B 组在部分维度优于 A 组，但不满足"显著优于"的全部条件。

含义：依赖图提示方向可能是对的，但实现需要调整。可能的问题：
- 提示格式不够好 → 调整 JSON 结构
- 依赖图不完整 → 补充缺失的依赖边
- 知识指针不准确 → 修正 study-notes 指向
- 评分标准不合理 → 重新审视评判维度

后续行动：诊断问题，调整后重新执行 POC。

### 8.3 失败（信念受到挑战）

B 组不优于 A 组，甚至低于 A 组。

含义：依赖图提示没有帮助，甚至干扰了 AI 的分析。核心信念在最小范围内受到挑战。

可能的原因分析：
- 依赖图提示对 AI 来说不如直接读 Markdown 直观 → 提示格式问题
- 命宫分析太简单，依赖图的优势体现不出来 → 场景选择问题
- 依赖图的结构化呈现不如自然语言文档对 AI 有效 → 更深层的问题

后续行动：认真分析失败原因。如果是实现问题，调整后重试。如果是方向问题，回到 63 号文档重新审视核心信念。

## 9. 后续路径

### 9.1 如果 POC 成功

扩展路径（按优先级）：

1. **增加知识节点**：从 5 个扩展到 15-20 个，覆盖命宫+官禄+格局
2. **增加意识**：从 2 个扩展到 5-6 个（加入恩用仇难、虚实）
3. **增加分析任务**：从命宫分析扩展到双宫分析（命宫+官禄），验证螺旋环路
4. **引入真实星盘**：用 qizheng 排真实盘，验证依赖图提示在真实数据下的效果
5. **引入矫正流程**：验证依赖图在矫正迭代中的环路检测
6. **全系统扩展**：覆盖 study-notes 全部知识 + qizheng 全部计算

每一步扩展都重复对照实验，确保依赖图提示的优势在更大范围内仍然成立。

### 9.2 如果 POC 失败

不直接放弃核心信念，先诊断：

1. 是提示格式问题吗？→ 尝试不同格式（自然语言描述依赖 vs JSON vs 混合格式）
2. 是场景太简单吗？→ 换更复杂的场景重试
3. 是依赖图不完整吗？→ 补充依赖边后重试
4. 是 AI 看不懂依赖图吗？→ 改进提示中对依赖图的解释

如果以上调整后仍然失败，回到 63 号文档的"核心悖论"章节，重新审视"直觉的内容可形式化"这个假设是否成立。

## 10. POC 的诚实声明

这份 POC 方案有以下局限，必须诚实面对：

1. **简化盘不是真实盘**：手动设定的数值可能过于"理想"，真实星盘的复杂性可能让依赖图提示的优势更不明显。但 POC 的目的是验证机制，不是验证真实场景——真实场景留给后续扩展。

2. **命宫分析可能太简单**：如果命宫分析的依赖链太短，依赖图提示的优势可能体现不出来。但命宫分析是星学分析的基础入口，如果连基础入口都体现不出优势，更复杂的场景更不可能。

3. **评分者主观性**：结构化评分仍然依赖评分者的判断。为降低主观性，评分应盲评，且最好有多个评分者。

4. **单次实验的统计效力不足**：一次 POC 的结果不能确证或否证核心信念。POC 的目的是给出第一个证据，不是最终判决。无论结果如何，都需要多次实验、多场景验证。

5. **依赖图是手动构建的**：POC 不验证依赖图能否自动构建。自动构建是后续工作。POC 验证的是"给定一个手动构建的依赖图，它生成的提示是否有用"。
