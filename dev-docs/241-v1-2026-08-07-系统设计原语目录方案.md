## 0. 为什么记录这份文档

238（引导式提问框架）和239（形式化边界推进系统）的对比分析（240号）暴露了一个结构性问题：**项目在20多份文档的迭代中产生了大量设计原语，但这些原语散落在各文档中，没有统一的目录。** 每个原语只在它出现的文档里有上下文，跨文档的关系靠人脑记忆维护。

后果是具体的：239写完之后，如果要建系统，需要从20份文档里重新提取所有原语，判断哪些是tested的、哪些是untested的、哪些互相替代、哪些互相组合。这个提取工作现在做一次，以后每做一次实验都要更新。

本方案提出：**建立一套原语目录，每个文件名是一个原语名，文件内容是我们对这个原语的思考和使用经验。** 每个原语带着它的证据状态，一眼能看出哪些是坚实的、哪些是悬空的。

但在提出目录结构之前，需要先记录产生这个想法的理念层思考——因为原语目录不只是工程方便，它源于对"AI数学工程系统是什么"的三个面相（Facet）的重新理解。

## 1. 理念层：AI数学工程系统的三个面相

### 1.1 面相1：两种计算

```
AI数学工程系统 = 经典计算 + AI计算
```

这是239号的核心。经典计算处理边界以内（可形式化、可检查、可审计），AI计算处理边界以外（感知、模式识别、直觉、类比）。两者互补，闭环推进边界。

**这个面相的贡献**：它正确识别了两种根本不同的计算能力，以及它们的分工。

**这个面相的局限**：它把"AI计算"看成一个黑箱——只说它"处理边界以外"，没说它内部怎么工作、有哪些不同的角色、这些角色怎么协作。guided_001的"提问激活"效应（AI在被问问题时能做出不被问时做不出来的东西）在这个面相里没有位置——因为"问问题"既不是经典计算，也不是"AI计算"的自发能力，它是两个AI之间的交互。

### 1.2 面相2：数学语料的两条路径

```
数学语料 →
  路径1：进入AI模型训练 → 黑盒模式匹配引擎、约束求解器
  路径2：进入数据基座 → 白盒可执行数学记忆、证书系统
```

这是231号的核心。同一批数学语料应该被处理成两种不同的东西：训练路径产生AI的能力，抽取路径产生系统的知识基座。

**这个面相的贡献**：它正确识别了数学知识的两种成分（可形式化的进入数据基座，不可形式化的进入AI训练），以及双重知识生产的必要性。

**这个面相的局限**：它描述的是"语料怎么变成系统能力"，不是"系统怎么工作"。它是材料论，不是运行论。系统运行时，AI在做什么、经典计算在做什么、它们怎么交互——这个面相不回答。

### 1.3 面相3：Pipeline网络中的Pipe（本次新增）

#### 1.3.1 从238到239的一个被跳过的问题

238有两个角色：引导者（问问题）+ 做题AI（解题）。
239有一个角色：AI直接感知+经典计算验证。引导者消失了。

238的引导者被去掉的原因是218的非特定性危机——引导者通过选择性引用AI选的方向，隐含地确认了正确路径。239的解决方案是去掉引导者，让AI自己感知"不自然"。

但这里有一个被跳过的问题：**guided_001证明的"提问激活"效应去哪了？**

30道做不出来的题（裸跑0/25），在被问4轮元认知问题后，做出来了。这个效应不能用"AI自己感知"解释——因为裸跑时AI也在感知，但没有被问问题，所以没有激活。239用"AI直接感知"替换了"提问激活"，而不是整合它。

#### 1.3.2 关键洞察：引导者做的也是数学工作

回到238的引导者角色。引导者在做什么？
- 判断当前状态的不自然
- 识别该往哪个方向走
- 评估哪个表示更清晰
- 决定该问什么问题

**这些本身就是数学工作。** 一个数学家指导另一个数学家时，指导者做的不是"传递答案"，而是用自己的数学品味判断方向、识别结构、提出启发。这是数学工作的一部分——而且是高Level的数学工作（元认知层面）。

所以问题不是"引导者是否在泄露答案"，而是"引导者的数学工作能不能被一个不知道答案的AI来完成"。如果能，引导者就是Pipeline里的一个合法Pipe，不是外部的全知角色。

#### 1.3.3 面相3的表述

```
在未来的AI数学工程系统中，AI无论是Worker、Assistant还是
其他某个Pipeline阶段的角色，本质上都是Pipeline网络中的一个Pipe。

在那个Pipe中，它可能是这样一些角色：
1. 数学推理引擎——执行具体的数学推导、计算、证明步骤
2. 模式识别引擎——识别当前处境的不自然、判断该用哪类思维拓扑
3. 多约束求解引擎——在多个约束下搜索满足条件的解或反例

还会有其他角色，但细化出角色名有助于我们的工作——
因为细化出的角色名就是有含义的名词，
这些名词会成为我们思考整个Pipeline网络的原语。
```

#### 1.3.4 面相3如何同时修正238和239

**对238的修正**：引导者不是外部的全知角色，它是Pipeline里的一个Pipe（模式识别引擎）。非特定性危机的框架变了——问题不再是"引导者是否在泄露答案"，而是"这个Pipe的输入输出是否依赖于它不应该知道的信息"。一个Pipe只应该看到它的上游Pipe传来的东西——如果它需要知道答案才能工作，那它不是合法的Pipe。

**对239的修正**：去掉引导者不是解决方案。guided_001的"提问激活"效应表明，AI之间的交互（一个AI问另一个AI问题）能激活后者做出单独做不到的事情。239的闭环架构应该包含这种交互，而不是让AI孤立地感知。Pipe之间的连接不只是数据传递，还有认知激活——一个Pipe发给另一个Pipe的不只是"这是当前处境"，还有"你该往哪看"，而后者改变的是下游Pipe的认知状态，不只是它的输入数据。

#### 1.3.5 面相3的开放问题

面相3提出了一个238和239都没回答的问题：**Pipe之间的"认知激活"到底是什么？它和"数据传递"有什么区别？**

guided_001的数据表明它是一个真实的empirical phenomenon——同样的AI模型，同样的数学知识，有没有被问问题，结果不同。但它的机制不清楚。是提问改变了AI的注意力分配？是提问降低了任务粒度？是提问激活了AI的某种元认知模式？还是以上全部？

这个问题暂时不解决，但需要有一个原语来捕捉它（见§3的`cognitive-activation`原语）。

## 2. 理念层：系统设计过程的面相

原语目录的想法不只来自对系统的面相理解，也来自对**系统设计过程本身**的面相理解。

### 2.1 面相A：实践涌现的原语

```
我们在系统设计过程中探索最终的系统架构，
但一次次的迭代也给我们留下了不同的系统设计原语。
找到系统架构的过程，也是找到所有系统设计原语的过程——
因为它们并不是一开始就在我们脑海中的，
而是随着系统设计实践不断涌现的。
我们要积累这些系统设计的原语。
```

238时期涌现的原语：连续发问、安全第一步、DFS引导、Level连续谱、最小知识传递、非特定性、隐含筛选、回溯铁律。

这些原语不是从理论推导出来的，而是从guided_001的实验和218的危机中**涌现**的。它们是实践产物，带着实验证据。

### 2.2 面相B：从人类知识海洋中选取的原语

```
广阔的人类知识海洋中包含着无数可以用于系统设计的原语。
所以我们的系统设计过程，不但在发现面相A中叙述的、
我们自己创造的原语，更是在已有的人类知识海洋中
挑选出来可以被用于系统设计的原语。
```

239时期选取的原语：形式化边界（来自数学哲学/逻辑学）、范畴（来自范畴论）、偏序（来自序理论）、交换图（来自范畴论）、Galois connection（来自序理论）、Grothendieck topology（来自代数几何）、上同调（来自同调代数）、语义场（来自物理学隐喻）、证书（来自计算复杂性/形式化验证）。

这些原语是从人类知识中借用的，它们有数学/哲学的正当性，但在本系统中的操作化状态各不相同——有些已经被操作化（执行契约、证书系统），有些只是候选（Σ是范畴、V-R是伴随-like），有些只是隐喻（语义场、能量）。

### 2.3 两类原语的关系

面相A的原语（实践涌现）和面相B的原语（知识选取）不是对立的，而是互补的：

- **实践涌现的原语**有实验证据，但可能缺乏数学精确性——"连续发问"是一个empirical有效的操作，但它没有形式化定义。
- **知识选取的原语**有数学精确性，但可能缺乏实验验证——"Σ是范畴"是一个精确的数学陈述，但它从未在实验中被检查过。

原语目录的价值在于：**把两类原语放在同一个目录里，每个带着它的来源和验证状态，让设计者一眼看到哪些是坚实的、哪些是悬空的、哪些需要被测试。**

## 3. 原语目录的设计

### 3.1 目录位置

**决策**：`primitives/`（项目根目录下的独立目录）

**理由**：
- 原语目录是living reference，不是时间序列文档——它不属于`dev-docs/`（dev-docs是时间序列的工作记录）
- 原语目录和认知图是不同的东西——认知图是ArangoDB中的稀疏矩阵，原语目录是文件系统中的markdown文件——所以不放在`xishujuzhen/`下
- 独立目录最清晰，增加一个顶层目录的代价可接受

### 3.2 目录结构

```
primitives/
  README.md                    # 目录说明 + 原语索引（按验证状态分组）
  _template.md                 # 原语文件模板

  continuous-questioning.md    # 连续发问
```

### 3.3 每个原语文件的结构

```markdown
# 原语名（中英文）

## 定义
一句话说清楚这个原语是什么。

## 来源
- 面相：A（实践涌现）还是 B（人类知识选取）还是 A+B（两者都有）
- 出处：哪个文档/哪个实验/什么领域

## 验证状态
[tested / tested_negative / untested / borrowed_unoperationalized]
具体说明：在什么实验中验证了什么，或者为什么未验证。

## 使用经验
在什么场景下用过，效果如何，有什么注意事项。

## 关系
- 替代了：___
- 组合了：___ + ___
- 细化了：___
- 被细化 by：___
- 与___ tension：___

## 开放问题
这个原语还有什么没想清楚的。
```

### 3.4 验证状态的四个等级

这是原语目录的核心纪律，防止它变成另一个239——一堆有道理但没测试的漂亮概念。

| 状态 | 含义 | 例子 |
|---|---|---|
| `tested` | 在实验中被用过且有效 | 连续发问（guided_001验证） |
| `tested_negative` | 在实验中被用过且无效 | （暂无，但未来会有） |
| `untested` | 提出但从未测试 | DFS引导（提出但guided_001没用到回溯） |
| `borrowed_unoperationalized` | 从人类知识借用但未操作化 | Σ是范畴（数学概念清晰但系统中未实现） |

**关键纪律**：每个原语文件必须标注验证状态。浏览目录时，一眼看出哪些是坚实的、哪些是悬空的。这防止"有道理的概念"和"被验证的概念"混在一起，让人误以为它们有同等的正当性。

### 3.5 关系字段的意义

原语不是孤立的。它们之间有替代、组合、细化、tension关系。这些关系目前散落在20份文档中，靠人脑记忆维护。原语目录把它们显式化。

几个关键关系的例子：
- `non-specificity` 与 `implicit-filtering` tension：非特定性是目标，隐含筛选是违反它的危机
- `continuous-questioning` 组合了 `safe-first-step`：连续发问框架的第一步就是安全第一步
- `pipe` 细化了 `two-computations`：面相3把"AI计算"细化成多个Pipe角色
- `cognitive-activation` 与 `formalization-boundary` tension：238的提问激活效应在239的形式化边界框架里没有位置
- `life-death-condition` 组合了 `borrowed_unoperationalized`：生死条件是借用原语操作化的一种方式

## 5. 原语目录与现有系统的关系

### 5.1 与认知图（ArangoDB）的关系

认知图是ArangoDB中的稀疏矩阵（35个认知单元，51条边），记录的是项目级的认知依赖关系。原语目录是文件系统中的markdown文件，记录的是系统设计原语的定义、来源、验证状态、关系。

**它们是不同的东西**：
- 认知图：项目认知管理（工作系统的一部分）
- 原语目录：系统设计参考（设计决策的积累）

**它们有交叉**：某些认知单元可能对应某些原语（如`glossary`词汇表对应原语目录的术语层面）。但原语目录不是认知图的替代，也不是认知图的一部分。

### 5.2 与dev-docs的关系

dev-docs是时间序列的工作记录——每份文档记录某个时间点的思考、方案、分析。原语目录是living reference——每个文件持续更新，反映当前对这个原语的理解。

**关系**：dev-docs是原语的来源之一。原语文件在"来源"字段引用它出处的dev-docs。dev-docs不变（版本化保留），原语文件持续更新。

### 5.3 与239号技术说明书的关系

239是一份1224行的技术说明书，试图结构化地呈现整个系统。原语目录是239的**分解**——把239里的每个概念拆成独立文件，每个带着验证状态。

**原语目录不是239的替代**。239提供了概念之间的关系和整体架构，原语目录提供了每个概念的独立深度和验证状态。两者互补：239是地图，原语目录是每个地点的详细卡片。

## 7. 开放问题

### 7.1 cognitive-activation的机制

guided_001证明提问激活是真实效应，但机制不清楚。是注意力分配？任务粒度降低？元认知模式激活？还是全部？这个问题的答案会影响Pipe之间的连接设计——如果认知激活只是"降低任务粒度"，那Pipe连接可以简化成"数据传递+粒度控制"；如果它是更深层的"元认知模式激活"，那Pipe连接需要专门的设计。

### 7.2 Pipe角色的完备性

面相3提出了三个角色（数学推理引擎、模式识别引擎、多约束求解引擎）。这是完备的吗？会不会还有：
- 猜想生成引擎（提出新猜想）
- 反例搜索引擎（专门找反例）
- 表示变换引擎（专门做换基/对偶化）
- 证书验证引擎（专门检查证书）

这些是不是上面三个角色的子角色？还是独立角色？需要在实际跑Pipeline时观察。

### 7.3 原语目录会不会变成另一个239

239的问题是一堆有道理但没测试的漂亮概念。原语目录如果只写不验证，也会变成同样的东西。验证状态标注是防御机制，但它依赖诚实标注——如果借用原语被标成"tested"，防御就失效了。

**纪律**：`borrowed_unoperationalized`和`untested`必须严格标注。一个原语只有在**实际实验中被用过且有效**时才能标`tested`。从人类知识借用但未操作化的，必须标`borrowed_unoperationalized`。提出但未测试的，必须标`untested`。

## 附录：本方案与240号的关系

240号分析了238和239的对比——238有empirical core（提问激活）但非特定性危机未修复，239有深层结构（形式化边界）但未测试且丢了提问激活。
