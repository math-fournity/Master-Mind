## 0. 摘要

用户给出 `用户需求.md` 时，明确了两个互相关联但层次不同的需求：

1. **短期/具体需求**：让本 AI 审计低级别 AI 对 123 号/系统探讨/146/147 的理解和 Phase 拆分/Check List 实现，给出详细改进意见。
2. **长期/架构需求**：设计一个**可自动演进的多层次 Agent 工作系统**，用 tmux 模式让 Supervisor Agent 持续监控 Master Agent，使其不断反思并迭代大师数学系统。

这两层需求共同指向同一个目标：**制造一个能持续自我迭代的数学大师系统**，而不是一次性的工程交付。

## 2. 显式需求拆解

### 需求 A：审计与改进意见

| 子需求 | 具体内容 |
|---|---|
| A1 | 分多个文件给出详细审计和改进意见 |
| A2 | 必须读取 146号 和 147号 **最新版全文** |
| A3 | 146号 是参考标准——改进意见要写到什么程度，才能放心交给低级别 AI 实现？ |
| A4 | 147号 是流程引导——理解低级别 AI 在短上下文中如何按 SOP 迭代实现复杂工程 |

**审计对象**：低级别 AI 生成的 Check List 文件（130-137号）和具体实现（Phase 0-6 runtime/、Phase 7 representation/）。

**审计目标**：
- 找出对 123 号/系统探讨/plan 的理解偏差
- 找出实现设计不够高级、不够充分的地方
- 找出具体实现中的错漏
- 给出可执行的改进意见，让低级别 AI 能照着改

### 需求 B：多层次监控 Agent 架构

| 子需求 | 具体内容 |
|---|---|
| B1 | 有效使用 tmux 中启动 Agent 的模式 |
| B2 | 不只是启动 subagent 做任务，而是把被监控的 Agent 放在 tmux 中 |
| B3 | 每增加一个监控层级，就启动一个 tmux |
| B4 | Master Agent 在 tmux 中工作，Supervisor Agent 监督和监控它 |
| B5 | Supervisor 检查 Master 是否在每个检查点都进行了充分反思 |
| B6 | 交付一个可自动演进的多层次工作系统 |
| B7 | 在 D 盘建立 Supervisor Agent 专用目录和 AGENTS.md |

**核心概念**：
- **Master Agent**：直接执行数学大师系统工作的 AI（类似当前的工作 AI）
- **Supervisor Agent**：更高维度的监督者，监控 Master Agent 的工作质量、流程合规、反思充分性
- **层次关系**：Supervisor > Master；未来可能再加更高层的 Meta-Supervisor

## 3. 隐式需求

### 3.1 工作系统本身的持续迭代

用户提到：
> "这个系统需要测试，需要迭代，需要在测试中精细化地监控。"  
> "或者说，其实，这个系统永远工作在这种模式中。"

这意味着：
- 大师数学系统不是一次性的项目，而是**持续运行、持续测试、持续审计**的活的系统
- 测试不是一次性的，而是常态化的
- 监控和反思也不是一次性的，而是贯穿整个生命周期

### 3.2 反思力的工程化

用户提到：
> "反思，这是作为Master Agent来说非常重要的工作。"  
> "大师数学系统，应该是持续迭代的。"

这意味着：
- 需要为 Master Agent 设计**反思触发点**和**反思清单**
- 需要把反思的结果转化为可执行的工作项
- 需要验证反思是否真的带来了系统改进

### 3.3 AGENTS.md 的权限分层

用户提到：
> "AGENTS.md 其实很特殊，它既能被 Supervisor Agent 看到，又能被 Master Agent 看到，其实是不对的。"

这意味着：
- AGENTS.md 混合了**工作指导**（Master 需要）和**监督指导**（Supervisor 需要）
- 未来需要拆分：
  - Master Agent 看到的内容：怎么做、当前任务、技术约束
  - Supervisor Agent 看到的内容：监督标准、检查点、反思框架、Master 的不足之处

## 4. 与本 repo（glm5.2 worktree）的关系

### 4.1 本 repo 能直接做的

**需求 A 的部分**可以在本 repo 内完成：
1. 读取 146号v4.2 和 147号v1.4.1 全文
2. 对上游 AI 已完成的工作进行审计
3. 产出审计报告（按 146号 的 22 维度审计方法论）
4. 给出改进意见文档

但注意：
- 上游 AI 已经停摆，它不会立即实现这些改进意见
- 这些改进意见可能最终被另一个 AI 使用

### 4.2 本 repo 与 Supervisor 架构的关系

需求 B 要求：
- 在 D 盘建立 Supervisor Agent 的专用目录和 AGENTS.md
- 这个目录不能是本 repo（本 repo 在内置 SSD）

**本 repo 的角色**：Master Agent 的工作目录。本 repo 当前的 setup（独立 venv、独立 ArangoDB 数据库、绝对路径 hooks）正是为了让 Master Agent 有一个干净的、可隔离的工作环境。

**Supervisor 目录**：需要在 `/data/` 下新建，比如 `/data/master-mind-supervisor/` 或类似路径。Supervisor 可以从那里启动 Devin，并监督和监控 Master Agent 的工作。

### 4.3 不能在本 repo 做的

- **在 D 盘建立 Supervisor 目录**：本 repo 在 `~/...`（内置 SSD），不在 D 盘
- **直接操作 Supervisor Agent**：那是另一个工作目录，需要在那里启动另一个 Devin 实例
- **让 Supervisor 看到 Master 的工作过程**：需要 tmux + 某种信息传递机制设计
