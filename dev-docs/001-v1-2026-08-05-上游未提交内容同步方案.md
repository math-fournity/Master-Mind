## 3. 同步方案

### 方案 A（推荐）· 等上游 commit 后 git fetch + rebase

**做法**：不做任何手动同步。等上游 AI commit 后，`git fetch origin && git rebase origin/main`，git 原生方式拿到全部内容。

**利**：
- 零冲突风险，git 原生处理
- representation/ 代码、146/147 修改、163-166 文档一次性完整拿到
- 不产生重复 commit，历史干净
- AGENTS.md 的 +4行会由 git 自动合并到下游项目部分（我们的隔离章节在顶部，不冲突）

**弊**：
- 依赖上游 AI 的 commit 时机，不可控
- 在此期间本 repo 的方法论基线停在 v4.1（21维度），缺 F16/维度22

**rebase 后需要做的事**：
- 检查 representation/ 代码是否仍无 ArangoDB 依赖（上游可能在 commit 前又改了）
- 如果上游在 representation/ 里新增了 ArangoDB 连接，需要补做环境变量化
- 验证本 repo 的环境变量化改动（25+25个文件）没有和上游改动冲突——预期不冲突，因为上游改的是 representation/（新文件）和 dev-docs（文档），我们改的是已有 .py 的连接参数

### 方案 B · 现在手动同步（不 commit，只作参考）

**做法**：把上游未提交内容复制到本 repo，但不 commit，放在 working tree 里作为参考。等上游 commit 后，`git checkout .` 丢弃手动复制的内容，再 `git fetch + rebase`。

**利**：
- 现在就能读到 Phase 7 代码和 v4.2 方法论文档
- 不产生 commit，不污染历史

**弊**：
- 复杂操作多，容易出错
- 146/147 的修改需要手动 patch 应用（不是简单复制）
- AGENTS.md 的 +4行需要手动插入到正确位置
- 未来 rebase 前必须记得 `git checkout .` 清理，否则冲突
- representation/ 代码作为 untracked 文件存在，可能干扰 git status

**具体步骤**（如果选 B）：
1. 复制 `representation/` 24个.py 到本 repo（无 ArangoDB 依赖，直接复制）
2. 复制 `dev-docs/163-166` 到本 repo（无路径依赖，直接复制）
3. 生成上游 146/147 的 patch：`cd /data/master-mind && git diff -- dev-docs/146-*.md > /tmp/146.patch && git diff -- dev-docs/147-*.md > /tmp/147.patch`
4. 在本 repo 应用 patch：`git apply /tmp/146.patch && git apply /tmp/147.patch`
5. AGENTS.md 手动加 163-166 索引条目（参考上游 diff 的 +4行，插入到下游项目部分的索引表中）
6. **不 commit**
7. 验证：`python3 -m py_compile xishujuzhen/research_runtime/representation/*.py`
8. 未来上游 commit 后：`git checkout . && git clean -fd xishujuzhen/research_runtime/representation/ && git fetch origin && git rebase origin/main`

### 方案 C · 现在手动同步并 commit

**做法**：同方案 B，但 commit 到 glm5.2 分支。

**利**：
- 现在就能读到，且 commit 后有记录
- 本 repo 的方法论基线立即升级到 v4.2

**弊**：
- **最大风险**：未来上游 commit 后 rebase，这批文件会严重冲突（146/147/AGENTS.md/163-166 都会冲突），冲突解决成本高
- 产生"重复 commit"——上游 AI commit 后，同样的内容在两个分支各有一份
- 违反"显式同步"原则，制造历史混乱

**不推荐方案 C**。

## 4. 推荐与理由

**推荐方案 A**（等上游 commit 后 git fetch + rebase）。

**理由**：
1. **风险最低**：git 原生 rebase 自动处理文件合并，不产生冲突（除非上游改了我们环境变量化过的文件，但可能性低——上游改的是 representation/ 新文件和 dev-docs 文档）。
2. **历史最干净**：不产生重复 commit，本 repo 的 glm5.2 分支只有自己的隔离工作 commit + 上游 commit 的 rebase。
3. **AGENTS.md 自动合并**：我们的隔离章节在文件顶部，上游的 +4行在下游项目部分，rebase 时 git 能自动合并（不同位置）。
4. **representation/ 无需额外处理**：已确认无 ArangoDB 依赖，rebase 过来即可用。
5. **唯一代价是等待**：但上游 AI 迟早会 commit，且 `用户需求.md`（22:23创建）是给它的下一步需求，它现在应该正在做新工作，commit 旧工作是其收尾的必经步骤。

**如果急需现在就读 Phase 7 代码/文档做参考**：用方案 B 的步骤 1-2（只复制 representation/ 和 163-166，不碰 146/147/AGENTS.md），不 commit，读完即可丢弃。这是方案 A 的轻量补充，风险可控。
