## 二、实际能做什么（v0.1.0 真实上限）

`seven.py` 真正能跑的命令：

- `preflight`——只读检查（D 盘、README、数据根、DB 名、Harness、目录隔离、工具策略）
- `init-epoch`——冻结 Epoch 元数据（源码树哈希、卷/README 指纹、路径、输入空位）
- `dry-run`——幂等提交演练（同内容返回 `ALREADY_COMMITTED`，异内容抛 `ContentConflictError`）
- `validate-epoch` / `status`——完整性验证
- `wp1-db-contract-report`——离线 DB 契约测试（不连真实 DB）
- `capabilities`——列出能力状态
- 几个 stdout-only 辅助命令（`build-work-package-plan`、`verify-normative-review-record`、`build-implementation-completion-bundle`、`build-audit-input-pack`、`validate-audit-input-pack`、`audit-input-pack-report`、`db1l-logical-site-report`、`db1l-verify-logical-site-report`）

**不能做**：连真实数据库、写数据库、启动 Solver、调用任何远程模型、QuestionRelease、P2–P9 任何科学管线、任何 Evidence 生产。所有 adapter（Solver / Devin 认知 / Codex 认知）都是 `FakeHarnessAdapter` / `FakeModelRoleAdapter` 这种确定性 stub。

## 三、复杂度来源分析

### A. 合理的需求复杂度（约 30–40%）

这部分来自科学方法本身的内在要求，删掉就会破坏实验有效性：

1. **因果实验骨架**——预注册、随机化、对照 arm、盲化、三审、contrast 级 EvidenceRecord。这是"证明 Tell 对 Solver 有增益"这个因果主张的硬要求，不是装饰。
2. **多系统边界隔离**——只读消费题海的冻结 bundle、不写回 `math:*`、不 import `system.*`。这是不污染两个生产系统的合理边界。
3. **答案隔离**——Solver / Selector / Renderer / Process Auditor 永久不可见答案。实验有效性的硬约束。
4. **人工 Gate 不可绕过**——模型不能自己签发 Gate。防止 AI 自我批准。
5. **append-only + 版本化**——题面变化必须新版本并使旧核验失效。科学可重现性要求。

### B. 过度设计产生的复杂度（约 60–70%）

这部分有明显的"治理递归"特征——为了约束自己不越界，就为每一步加 Gate；为防 Gate 被绕过，加验证器；为防验证器被绕过，加授权链……在没有实际运行反馈的情况下无限展开：

#### B1. 561 个错误码，32% 是死代码

一个只能做 preflight 的系统定义了 561 个错误码，182 个从未被引用，48 个被引用但未定义。这是"先枚举所有可能的错误"而不是"从实际故障中提取错误码"。

定位：`seven-system/src/seven_system/contracts/errors.py`

#### B2. 638 条 MUST 条款，全部 PENDING

把所有 Markdown 中的 MUST 逐条枚举成 19,688 行的 JSON 索引，意图是可追溯性。但在还没有实现任何实际功能时就做这件事，是本末倒置——给一个空壳写 638 条规范。

定位：`seven-system/docs/implementation/normative-requirement-index.v1.json`

#### B3. 25 个工作包的完整 DAG，只实现了 1 个

设计了从 DOC0 到 OP1 的完整 25 个工作包依赖图，但 2 天内只有 GV0 到了 `IMPLEMENTED_PENDING_EVIDENCE`，其余 `NOT_STARTED`。这是"先设计完整体系再实现"的典型模式。

定位：`seven-system/docs/implementation/03-work-package-dag.md`

#### B4. 3 层授权链（EEA → LiveRunPermit → AuthorizationConsumptionReceipt）

为防止 AI 自我授权而设计。但系统还没有任何 live 能力时，这三层链是纯理论构造。

定位：`seven-system/docs/implementation/04-object-and-schema-catalog.md` 第 24–32 行

#### B5. 文档量 ≈ 代码量的 47%（不算测试）

5,283 行 Markdown + 26,283 行 JSON vs 66,291 行代码。对一个只能做 preflight 的系统，这个比例过高。

#### B6. 为未实现的能力写 Schema

19 个 wire contract schemas + docs/implementation 下 20+ 个 schema，很多对应的能力是 `NOT_IMPLEMENTED`。先定合同再实现是好的意图，但在没有需求验证的情况下过早固化接口形状。

#### B7. "非主张"（nonclaims）文化

几乎每个文档和代码块都有大量"不主张 X"的声明。意图是防止过度声称，但密度过高导致信噪比下降。

## 四、根本矛盾

这个系统试图用**"实现完整治理体系"**的方式来保证**"不过度声称"**。但"不过度声称"只需要诚实——不需要 561 个错误码、638 条规范、25 个工作包的 DAG。

设计者（从 commit 模式看是 AI）陷入了**治理递归**：

```
为了确保每一步不越界
  → 为每一步设计 Gate
    → 为防 Gate 被绕过设计验证器
      → 为防验证器被绕过设计授权链
        → 为防授权链被绕过设计原子预留
          → ...无限展开
```

这种递归在没有实际运行反馈的情况下无限展开，结果是 2 天写了 66K 行代码但只能做 preflight。

---

## 五、判断

**过度设计占主导（约 60–70%），需求复杂度占 30–40%。**

合理的需求复杂度是：因果实验骨架、多系统边界、答案隔离、人工 Gate、append-only。这些删掉会破坏实验有效性。

过度设计的核心问题是**没有 MVP**。系统试图在 2 天内同时做"科学严谨"和"工程完整"，结果科学严谨的部分被工程治理部分淹没——90% 精力在治理结构上，10% 在实际功能上。

## 六、更合理的路径建议

先实现一条最小的端到端路径：

```
一道题 → 一次 bare → 一次 guided → 一次 contrast → 一条 EvidenceRecord
```

在真实运行中发现需要哪些 Gate 和隔离，而不是预先设计 25 个工作包的 DAG 和 561 个错误码。规范和治理结构应该从真实运行的经验中沉淀出来，不是在空壳上预先铸造。

具体来说：

1. **先跑通一条真实实验**——用现有的 `solver_harness` 跑一道 bare 题、一道 guided 题，手动对比结果。这一步不需要任何 Gate、授权链或 Schema。
2. **从真实失败中提取约束**——跑通后发现"Solver 偷看了答案" → 才需要答案隔离；发现"AI 自己签了 Gate" → 才需要人工 Gate 验签；发现"重跑结果不一致" → 才需要 append-only。
3. **治理结构跟随实验规模增长**——做 1 道题不需要 25 个工作包；做 10 道题不需要 638 条规范；做 100 道题可能才需要部分授权链。治理结构的规模应该与实验规模匹配，不是预先最大化。
