## 一、背景与现状

### 1.1 已完成

审计标准体系已建立并通过回测验证：
- 13份审计标准文档（183-195号），覆盖8子系统40+模块
- 审计Rule+Skill元组（audit-trigger + audit-module）
- 5个历史run回测验证（196号）——标准有效，3个缺陷已修订

### 1.2 当前差距

| 差距 | 说明 | 影响 |
|---|---|---|
| 审计是手动的 | 目前审计靠AI按文档逐项检查，没有自动化脚本 | 每次审计耗时，且可能遗漏 |
| 待细化项未落实 | 12份文档共约60项"待细化"——阈值、具体值、边界情况未确认 | 标准有空洞，执行时缺乏依据 |
| 回测只覆盖P0 | 只回测了184/194/195（P0），P1/P2/P3未回测 | P1-P3标准未经验证 |
| 缺少复杂run | 现有5个run都是简单证明题，1turn完成，没有多turn+hint的复杂场景 | 引导效果度量无法计算 |

## 二、目标

把审计从"AI按文档手动检查"升级为"脚本自动提取数据+按检查项判定+输出结构化报告"，同时落实标准中的待细化项。

### 2.1 分阶段目标

| 阶段 | 目标 | 交付物 |
|---|---|---|
| Phase A | 审计脚本框架 | 能从ArangoDB/sessions.db/run目录提取数据并输出结构化报告的Python脚本 |
| Phase B | P0审计自动化 | 184（循环）+195（数学正确性）+194（Solver连接）的检查项全部脚本化 |
| Phase C | 待细化项落实 | 12份文档的约60项待细化逐个确认，补入标准 |
| Phase D | P1-P3审计自动化 | 185-193的检查项脚本化 |
| Phase E | 复杂run生成与回测 | 用需要多turn+hint的复杂问题生成新run，回测全部标准 |

## 三、Phase A · 审计脚本框架

### 3.1 目标

写一个Python审计框架，能：
1. 从3个数据源提取数据（ArangoDB / sessions.db / run目录）
2. 按检查项定义执行判定
3. 输出结构化审计报告（JSON + Markdown）

### 3.2 设计

```
xishujuzhen/audit/
├── __init__.py
├── framework.py          # 审计框架核心
├── data_sources.py       # 数据源接口（ArangoDB/sessions.db/run目录）
├── check_items.py        # 检查项基类和判定逻辑
├── report.py             # 报告生成器
├── standards/            # 按模块分的审计标准实现
│   ├── __init__.py
│   ├── std_184_loop.py       # 184号：12步循环与引导循环
│   ├── std_185_controller.py # 185号：控制器与策略
│   ├── std_186_budget.py     # 186号：预算
│   ├── std_187_events.py     # 187号：事件系统
│   ├── std_188_reducer.py    # 188号：状态归约
```

### 3.3 核心接口

```python
# 检查项基类
@dataclass(frozen=True)
class CheckResult:
    item_id: str          # 检查项ID
    name: str             # 检查项名称
    verdict: str          # "通过" / "有缺陷" / "失败" / "N/A"
    detail: str           # 具体说明
    evidence: dict        # 支撑证据（数据值/查询结果）

# 审计器基类
class StandardAuditor:
    standard_id: str      # 如"184"
    standard_name: str    # 如"12步循环与引导循环"
    
    def audit(self, data: AuditData) -> List[CheckResult]:
        """按检查项逐项执行审计"""
        ...
    
    def generate_report(self, results: List[CheckResult]) -> AuditReport:
        """生成审计报告"""
        ...
```

### 3.4 命令行接口

```bash
# 审计单个run
.venv/bin/python3 -m xishujuzhen.audit.cli audit --run-id run_20260806_guided_004 --standards 184,194,195

# 审计全部标准
.venv/bin/python3 -m xishujuzhen.audit.cli audit --run-id run_20260806_guided_004 --standards all

# 输出报告
.venv/bin/python3 -m xishujuzhen.audit.cli report --run-id run_20260806_guided_004 --format markdown
```

## 四、Phase B · P0审计自动化

### 4.1 目标

把184/194/195号的检查项全部脚本化。

### 4.2 184号检查项脚本化

| 检查项 | 数据源 | 判定逻辑 |
|---|---|---|
| solo explore先于guided | run目录/guided_loop_result.json | turn_history[0].is_hint == False |
| hint只在卡点后给 | run目录/guided_loop_result.json | solo阶段hints_used == 0 |
| hint数量不超过预算 | run目录/guided_loop_result.json | n_hints <= max_hints |
| turn数量不超过预算 | run目录/guided_loop_result.json | n_turns <= max_turns |
| 完成判定合理 | run目录/guided_loop_result.json | completed=True时response含完成信号且不以[ERROR开头 |
| 卡点检测准确 | run目录/guided_loop_result.json | stall_detected时response含数学卡点信号；含工作系统关键词时标记非数学卡点 |
| hint内容相关 | run目录/guided_loop_result.json | hint的stall_reason与response卡点信号一致 |

### 4.3 194号检查项脚本化

| 检查项 | 数据源 | 判定逻辑 |
|---|---|---|
| devin cli调用成功 | run目录/guided_loop_result.json | response不以[ERROR开头 |
| session_id获取 | run目录/guided_loop_result.json | session_id != "" |
| export文件生成 | run目录/turn_*_conversation.json | 文件存在且大小>0 |
| 工作目录正确 | sessions.db/sessions表 | working_directory含/data/math-agent-glm5.2- |
| 无web_search | sessions.db/tool_call_state表 | 无web_search记录 |
| 无工作系统劫持 | run目录/guided_loop_result.json | response不含"认知种子"/"CP1-CP3"/"七步骤" |

### 4.4 195号检查项脚本化

| 检查项 | 数据源 | 判定逻辑 |
|---|---|---|
| 数据来源纯净性 | sessions.db/tool_call_state表 | 无web_search |
| 逻辑链完整性 | run目录/guided_loop_result.json | 需要AI辅助（无法纯脚本判定） |
| 小情形验证 | Python/SymPy计算 | 对猜想类任务自动计算小情形 |
| 结论正确性 | Python/SymPy计算 | 对计算类任务自动验证 |

**注意**：195号的证明类检查项（逻辑链完整性/前提正确性/无循环论证）无法纯脚本判定，需要AI辅助。脚本只做能自动化的部分（小情形验证/计算验证/数据来源检查），AI辅助部分留给audit-module Skill。

## 七、Phase E · 复杂run生成与回测

### 7.1 目标

现有5个run都是简单证明题（1turn完成，0-1 hints）。需要生成复杂问题的run来：
1. 回测引导效果度量（solo成功率/hint有效率/干预时机）
2. 回测卡点检测（7种卡点类型）
3. 回测gaming检测
4. 回测预算控制

### 7.2 复杂问题设计

| 问题 | 预期行为 | 测试什么 |
|---|---|---|
| Ramsey R_k(C_4)下界猜测 | 猜想类，可能需要hint | 猜想类审计 + hint效果 |
| 构造性证明（如Ramsey图构造） | 计算类，可能卡在构造 | 计算类审计 + 卡点检测 |
| 需要跨领域类比的证明 | 可能卡在表示变换 | 表示映射审计 + 卡点检测 |
| 故意给一个错误猜想 | 应该被验证为contradicted | 验证子系统审计 |
| 故意给一个gaming输出 | 应该被gaming_detector检测 | gaming检测审计 |

## 八、依赖关系与执行顺序

```
Phase A（框架）
  ├── Phase B（P0自动化）——依赖A
  │     └── Phase E（复杂run回测）——依赖B + D
  ├── Phase C（待细化落实）——不依赖A，可并行
  │     └── Phase D（P1-P3自动化）——依赖A + C
  └── Phase D（P1-P3自动化）——依赖A + C
```

**推荐执行顺序**：
1. Phase A + Phase C 并行（A写框架，C落实待细化项）
2. Phase B（P0自动化，验证框架可用性）
3. Phase D（P1-P3自动化）
4. Phase E（复杂run回测，最终验证）

## 九、风险与缓解

| 风险 | 说明 | 缓解 |
|---|---|---|
| 195号证明类检查无法纯脚本化 | 逻辑链完整性/无循环论证需要AI判断 | 脚本只做可自动化部分，AI辅助部分留给Skill |
| 待细化项落实后发现标准需要大改 | 阈值或列表与实际不符 | 先做C再做D，避免D基于错误标准 |
| 复杂run生成失败 | Solver可能无法处理复杂问题 | 先用中等难度问题测试，逐步加难 |
| ArangoDB数据不完整 | 某些模块可能没有写入ArangoDB | 先检查ArangoDB中实际有哪些数据 |
| sessions.db schema变化 | devin cli更新可能改变schema | 审计脚本做schema兼容检查 |
