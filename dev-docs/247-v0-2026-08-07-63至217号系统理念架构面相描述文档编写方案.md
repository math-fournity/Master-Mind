## 1. 内容标准——最终文档应该写成什么样

### 1.1 参照系：238和239号文档的写法

238号和239号文档的共同特征：
- **不是摘要**，是**复原**——让一个没读过原始文档的人，读完这一份就能完整理解那套系统的全貌
- 有**背景与起点**（这套方案是从哪里冒出来的）
- 有**核心观念/柱子/奠基性观念**的逐个阐述
- 有**架构设计**的结构化呈现
- 有**演化路径**（从什么到什么的变迁）
- 有**实验验证**的记录
- 有**暴露的问题/危机**

### 1.2 本文档的内容标准

最终文档（暂定编号248号）应该包含以下部分：

**第一部分：理念层**
- 系统的深层本质（一句话定义 + 精确含义）
- 核心信念（完美提示词可以通过经典计算产生）
- 奠基性观念的逐个阐述（从63号的稀疏矩阵想法开始，到后续演化出的观念）
- 核心隐喻的演化（稀疏矩阵→依赖图→提示生成器→数学大师→...）

**第二部分：架构设计**
- 系统的组件结构（xishujuzhen系统、依赖图、ArangoDB、POC验证体系、数学大师系统组件等）
- 组件之间的关系
- 数据流与控制流
- 技术选型与理由

**第三部分：面相**
- 系统从不同角度看到的样子（作为提示生成器、作为大师形式化、作为依赖图导航、作为POC验证系统、作为数学大师系统等）
- 面相之间的关系与演化

**第四部分：演化与问题**
- 理念的演化路径（从星学到数学，从稀疏矩阵到依赖图到引导式解题）
- 实验验证的关键结果
- 暴露的问题（提示作弊、AI缺位等）——这些问题如何导向了238号系统

**第五部分：与238/239号的关系**
- 这套系统如何过渡到了238号系统（引导式数学解题）
- 这套系统如何过渡到了239号系统（AI数学工程）

### 1.3 写作风格

- 人话（遵守全局规范§3）
- 不是文档清单，是**叙事性复原**
- 每个观念都要说清楚"为什么"——不只是"是什么"
- 引用具体文档编号和关键内容片段作为证据

## 2. 执行方案——Multi-Pass文档筛选

### 2.1 为什么需要筛选

63-217号共157个文档，不是所有文档都和"理念·架构·面相"有关。大量文档是：
- POC验证结果（只有测试数据）
- CheckList（实现追踪）
- 审计报告（代码质量检查）
- Phase实现方案（工程细节）
- 数据丢失记录（运维事件）

这些文档对理解系统的理念、架构、面相没有直接贡献。需要筛选出真正相关的文档。

### 2.2 为什么用Multi-Pass

一次性给subagent太多文档，它无法有效处理。Multi-Pass的方法：
- **Pass 1（粗筛）**：每个subagent读一个文档，判断它是否和"理念·架构·面相"有关。产出是一份文档列表。
- **Pass 2（精读）**：对Pass 1筛选出的文档，每个subagent精读一个，提取和"理念·架构·面相"相关的具体信息。

Pass 1后文档数量会大幅减少（预计从157个减少到30-50个），Pass 2的工作量可控。

### 2.3 并发策略

5个subagent并发执行。157个文档，每批5个，需要约32批。但subagent是background的，可以持续运行。

**Pass 1的执行方式**：
- 每批启动5个background subagent，每个读一个文档
- 每个subagent的任务：读文档，判断相关性，返回结构化结果
- 所有批次完成后，汇总结果，形成Pass 2的文档列表

### 2.4 Pass 1：筛选标准

#### 2.4.1 subagent的指令模板

每个subagent收到如下指令：

```
你是一个文档筛选助手。请读取以下文档，判断它是否和"系统的理念、架构设计、面相"有关。

文档路径：{文件路径}

你需要判断这篇文档是否包含以下三类内容中的任何一类：

1. **理念（Philosophy）**：系统的核心信念、设计哲学、根本想法、"为什么"要这样设计。
   例如：为什么用稀疏矩阵、为什么依赖图可以替代大师、什么是"综述博士"、完美提示词可以通过经典计算产生等。

2. **架构设计（Architecture）**：系统的结构设计、组件划分、模块关系、技术选型、数据流。
   例如：xishujuzhen系统的目录结构、依赖图的存储方案、ArangoDB的技术选型、系统组件之间的关系等。

3. **面相（Facets）**：系统从不同角度的理解、系统的维度切分、如何看待这个系统。
   例如：系统作为提示生成器 vs 作为大师形式化 vs 作为依赖图导航、系统的不同视角等。

判断标准：
- **相关**：文档中包含上述三类内容中至少一类的实质性讨论（不是一句话提及，而是有展开论述）
- **不相关**：文档纯粹是POC测试数据、CheckList条目、审计报告、bug记录、实现细节，没有理念/架构/面相层面的讨论

请返回以下结构化结果：
- 文档编号：{编号}
- 文档标题：{标题}
- 是否相关：是/否
- 相关类型（如相关）：理念/架构/面相（可多选）
- 相关内容摘要（如相关）：用2-3句话概括文档中与理念/架构/面相相关的具体内容
- 关键段落定位（如相关）：列出文档中最相关的章节标题或行号范围
```

#### 2.4.2 筛选的边界判断

**明确相关的文档类型**（大概率Pass 1选中）：
- 设计哲学/理念文档（如63号、95号、96号）
- 系统架构调查/设计文档（如122号、123号）
- 技术选型文档（如79号、81号）
- 项目启动/认知基础文档（如80号）
- 下一代工作流设计文档（如78号、83号）
- 问题分析与解决方案中的理念部分（如200-208号中的分析部分）

**明确不相关的文档类型**（大概率Pass 1排除）：
- POC验证结果（只有测试数据，如69号、71号、73号等）
- Phase CheckList（实现追踪，如130-137号）
- Phase实现方案（工程细节，如143号、148号等）
- 审计报告（代码质量检查，如129号、138号等）
- 数据丢失记录（运维事件，如172号）
- 审计标准（如183-195号，这些是238/239系统的前身，但属于审计维度而非系统理念）

**需要subagent判断的灰色地带**：
- POC验证方案：可能包含设计理念（如64号POC方案可能讨论了为什么要这样验证）
- 反哺方案：可能包含系统演化理念（如99号）
- 工作系统升级方案：可能包含架构理念（如91号）

### 2.5 Pass 1的产出

Pass 1完成后，形成一份文档：`dev-docs/247-pass1-result-文档筛选结果.md`，内容包括：

1. **全部157个文档的筛选结果表**：编号、标题、是否相关、相关类型、摘要
2. **Pass 2精读文档列表**：所有被标记为"相关"的文档，按编号排序
3. **按相关类型的分组**：理念类、架构类、面相类（一个文档可能属于多类）

### 2.6 Pass 2：精读与信息提取（后续执行，本方案不展开）

Pass 2对Pass 1筛选出的文档逐个精读，提取和"理念·架构·面相"相关的具体信息。Pass 2的方案在Pass 1完成后另行制定。

### 2.7 最终文档编写（后续执行）

Pass 2完成后，基于提取的信息编写最终文档（暂定248号）。

## 5. 风险与应对

### 5.1 subagent数量过多

157个文档 / 5个并发 = 32批。如果每批需要等待，总时间可能较长。

**应对**：background subagent可以持续运行，不需要每批都等待完成。可以一次性启动多批，然后统一收集结果。

### 5.2 筛选标准不一致

不同subagent对"相关"的判断标准可能不一致。

**应对**：在指令模板中给出明确的判断标准和正反例。Pass 1完成后人工抽查部分结果，对不一致的判断进行修正。

### 5.3 灰色地带文档的误判

部分文档可能既有理念内容又有工程细节，subagent可能误判。

**应对**：宁可多选不漏。Pass 1的筛选标准偏宽松——只要文档中有实质性的理念/架构/面相讨论就选入Pass 2，即使它同时包含大量工程细节。
