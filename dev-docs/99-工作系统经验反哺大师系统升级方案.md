# 99-工作系统经验反哺大师系统升级方案

> **文档定位**：89-98号文档完成了工作系统自身的升级（cognition基座+经典计算展开）。本文档分析工作系统升级中产生的经验和机制如何反哺大师系统（目标系统），形成大师系统的下一代升级方案。
>
> **核心论点**：工作系统升级不是纯粹的元层面工作——它产生的6个机制可以直接增强大师系统的七步骤工作流、数学意识管理、认知演化和质量保障。
>
> **依据**：80-88号文档（大师系统已有成果）+ 89-98号文档（工作系统升级成果）

## 一、两套系统的关系回顾

数学项目有两套图驱动的系统：

| 系统 | 角色 | 节点 | 当前状态 |
|---|---|---|---|
| **大师系统**（目标系统） | 管理数学证明的依赖结构 | dg_nodes（18个证明节点） | POC-1/POC-2验证通过，七步骤工作流可用 |
| **工作系统**（元系统） | 管理AI自己的工作认知 | cognition_units（27个认知单元） | 89-98号方案实现完成，14/16测试通过 |

两套图共享同一个ArangoDB实例（xishujuzhen_math），意识节点有双重身份。

**本文档的核心洞察**：工作系统升级中产生的机制，不只是管工作认知的——它们是通用的图驱动认知管理机制，可以直接应用到大师范系统的数学认知管理上。

## 二、6个反哺点

### 反哺1：经典计算展开替代七步骤工作流的步骤2

#### 工作系统中的经验

92号方案设计了topo_generator.py，实现经典计算展开G'_topo骨架（L0拓扑排序+L1类型推断+L2 section划分）。98号测试报告验证：**1次通过100%覆盖**（18/18节点，25/25边，2/2环路）。

#### 大师范系统当前的状态

POC-2的七步骤工作流中：
- 步骤2：**meta AI生成G'_topo**——AI从零规划section/position/type/connection
- 步骤3：TopologyVerifier验证——如果步骤2遗漏节点或边，需要回退到步骤2重做

**问题**：meta AI生成G'_topo可能遗漏，步骤3的验证是"catch错误"而非"保证正确"。

#### 反哺方案

**步骤2从"meta AI生成"升级为"经典计算生成骨架（L0+L1+L2）+ AI语义细化（L3）"**

| 步骤 | 当前（POC-2） | 升级后 |
|---|---|---|
| 步骤2 | meta AI从零生成G'_topo | **topo_generator.py生成骨架** + AI只做L3（section命名+spiral类型确认） |
| 步骤3 | TopologyVerifier验证（可能回退） | TopologyVerifier验证（**必然1次通过，不需要回退**） |
| AI工作量 | 全部G'_topo规划 | 只有L3语义标注 |

**实现路径**：
1. topo_generator.py已实现并测试通过——直接可用
2. 七步骤工作流的步骤2改为调用`topo_generator.py --mode full --verify`
3. AI只在L3阶段介入：调整section边界、给section命名、确认spiral类型
4. 步骤3变为确认性验证（不是catch性验证）

**价值**：
- 消除步骤2的不确定性——经典计算保证全覆盖
- 减少AI工作量——AI只做语义标注，不做结构规划
- 步骤3不需要回退——L0骨架展开从G直接拷贝节点集和边集

### 反哺2：CP1-CP3加载数学意识作为前置认知

#### 工作系统中的经验

91号方案设计了CP1-CP3工作流入口：
- CP1：种子选择（确定本次任务需要哪些种子认知单元）
- CP2：认知加载（AQL图遍历，从种子出发沿depends_on边找到所有前置认知）
- CP3：缺口检查（验证已加载的认知是否覆盖任务所需）

98号测试验证：从seven_step_workflow出发，depth=7找到26个认知单元，覆盖所有前置依赖。

#### 大师范系统当前的状态

POC-1和POC-2中，AI做数学证明前**没有系统性地加载数学意识**。POC-1的B组提示中包含了"数值检验意识"节点，但这是手动放入提示材料的——AI不知道自己应该调用哪些数学意识。

**POC-1的核心发现**：B组优于A组的根源是B组有"数值检验意识"标注，A组没有。B组正确区分了上界与下界，A组没有。

#### 反哺方案

**用CP1-CP3系统性地加载数学意识作为做数学证明的前置认知**

意识节点双重身份已经实现（cognition_units + dg_nodes）。cognition_units中的意识节点是AI的工作认知——做数学证明时需要的思维方式。

**工作流**：
```
AI接到数学证明任务
  ↓ CP1：种子选择
  选择种子认知单元（如seven_step_workflow + 相关的数学意识）
  ↓ CP2：认知加载（图遍历）
  cognition_checkpoint_math.py start --seeds seven_step_workflow,invariant_thinking
  → 图遍历找到所有前置认知，包括数学意识节点
  ↓ CP3：缺口检查
  验证是否遗漏了任务相关但与种子无依赖边的意识
  ↓ AI在完整的数学意识加载下做证明
```

**关键设计**：种子选择时，不仅选工作流认知单元，还要选**与题目相关的数学意识**作为种子。比如：
- 矩条件极差题 → 种子包含`numerical_check`（数值检验意识）和`extreme_testing`（极端检验）
- 跨领域题 → 种子包含`local_global_thinking`（局部-全局思维）

**实现路径**：
1. 为每类数学问题建立"种子推荐表"——什么类型的题应该选哪些意识作为种子
2. AI接到题目后，先查种子推荐表，再执行CP1-CP3
3. POC验证：对比"有CP1-CP3加载意识"vs"无加载"的证明质量差异

**价值**：
- 把POC-1的发现（意识标注的价值）系统化——不是手动放入提示，而是图遍历自动加载
- AI不再"不知道自己不知道什么"——图遍历会找到AI没想到但任务需要的意识
- 这正是95号设计哲学中"朴素方案3（让AI自己搜索）的失败"的解决方案

### 反哺3：版本链管理数学认知的演化

#### 工作系统中的经验

91号方案设计了cog_versions版本链——每个认知单元有多个版本，current_version指向最新版本。版本链记录了认知的演化历史。

98号测试验证：3个多版本认知单元（math_master_system, poc_methodology, seven_step_workflow）的current_version全部正确指向latest。

#### 大师范系统当前的状态

数学依赖图的节点没有版本链。POC-1的8节点依赖图和POC-2的18节点依赖图是独立的——POC-2不是POC-1的"升级版"，它们是不同的依赖图。

**问题**：数学认知的演化没有被记录。比如"数值检验意识"这个节点，在POC-1中是8节点图的一个节点，在POC-2中是18节点图的一个节点——但两次POC中对这个意识的理解深化了（POC-1发现它能区分上界下界，POC-2发现它是螺旋环路的一部分），这个深化没有版本记录。

#### 反哺方案

**用版本链管理数学意识节点的认知演化**

每个数学意识节点在cognition_units中都有对应记录（双重身份）。给这些认知单元建立版本链：

| 认知单元 | v1 | v2 | v3 |
|---|---|---|---|
| `numerical_check` | POC-1：发现能区分上界下界 | POC-2：发现是螺旋环路的一部分 | POC-3：（待验证）跨题复用增益 |
| `invariant_thinking` | POC-1：矩恒等式在扰动下保持 | POC-2：不变量是稳定性方程的核心 | - |
| `extreme_testing` | POC-1：三点构型数值试探 | POC-2：极端构型是稳定性方程的起点 | - |

**工作流**：
```
每次POC验证完成后（CP4-CP6）
  ↓ CP4：认知捕获
  检查本次POC是否深化了对某个数学意识的理解
  ↓ CP5：认知图更新
  如果深化了 → 给对应认知单元新增版本（v2→v3）
  版本记录包含：POC编号、验证结果、新发现
  ↓ CP6：任务-认知映射
  记录"这个POC用了哪些种子意识，验证了什么"
```

**实现路径**：
1. 每次POC结束后，执行`cognition_checkpoint_math.py end --new_version <cog_id>:<new_version>:<poc_doc>:<summary>`
2. 版本链自动记录"这个意识在哪个POC中被验证过、验证结果如何"
3. 跨session的AI可以通过版本链知道"这个意识到了哪个版本，最新版本的理解是什么"

**价值**：
- 数学认知的演化被显化——不是只留在POC文档中，而是结构化在版本链中
- 跨session的AI可以快速恢复"某个意识当前的理解深度"
- 为三层提取（L1/L2/L3）提供演化追踪——L1是v1，L2是v2，L3是v3

### 反哺4：回归验证保障大师系统的持续质量

#### 工作系统中的经验

94号方案设计了POC回归验证——D1覆盖率+D3版本链+D4图遍历完整性+D2约束保留+D5流程可执行性，满分100。

98号测试验证：基线100/100，故意删除版本记录后D3下降到19/20，恢复后回到100/100。回归验证能检测到人为制造的问题。

#### 大师范系统当前的状态

大师系统的POC验证是一次性的——做完POC-1就做POC-2，没有回归验证。如果POC-3的依赖图变更影响了POC-1/POC-2的已有功能，不会被发现。

**问题**：随着POC数量增长，依赖图越来越复杂，早期POC验证过的功能可能被后续变更破坏。

#### 反哺方案

**每次大师系统的依赖图变更后，跑回归验证**

```bash
# 依赖图变更后（如新增意识节点、新增依赖边）
.venv/bin/python3 xishujuzhen/cognition_audit_math.py poc-regression \
    --seeds seven_step_workflow,invariant_thinking \
    --ground-truth seven_step_workflow,invariant_thinking,topology_coverage,...
```

**回归验证覆盖的内容**：
- D1：图遍历是否仍然覆盖所有ground truth认知单元
- D3：版本链是否仍然正确（current_version=latest）
- D4：图遍历完整性（depth=7 vs depth=9是否一致）
- 拓扑覆盖验证：TopologyVerifier是否仍然1次通过100%覆盖

**实现路径**：
1. 为每个POC建立ground truth（该POC验证时图遍历应该找到的认知单元集合）
2. 依赖图变更后，对所有POC的ground truth跑回归验证
3. 如果某个POC的回归验证得分下降，定位是哪个变更导致的

**价值**：
- 大师系统的质量有了持续保障——不是"做完了就不管了"
- 依赖图变更的影响可以被检测——新增意识节点不会悄悄破坏已有功能
- 这正是89号文档中"质量门控"的数学项目实现——用TopologyVerifier+回归验证替代星学的文字审计

### 反哺5：从POC结果中自动发现新数学意识节点

#### 工作系统中的经验

89号文档第六节提到"自我迭代"的可能性：从POC评分结果中自动发现新数学意识节点，自动构建依赖图。

这是工作系统"自我迭代"能力对大师系统的反哺——工作系统可以从自己的工作中发现新认知，大师系统也可以从POC结果中发现新数学意识。

#### 大师范系统当前的状态

POC-1中发现了"数值检验意识"的重要性——B组因为有这个意识标注而正确区分了上界与下界。但这个发现是**人工的**——AI和用户分析了POC结果后，手动在依赖图中标注了这个意识。

**问题**：如果POC数量增长，人工分析每个POC结果来发现新意识，效率太低。

#### 反哺方案

**设计"意识发现"机制——从POC评分结果的增量来源中自动发现新数学意识**

**工作流**：
```
POC验证完成，评分结果显示B组在某个维度显著优于A组
  ↓ 分析增量来源
  B组优于A组的根源是什么？
  ↓ 如果增量来自一个尚未被显式标注的数学意识
  在B组的提示材料中找到这个隐含的意识
  ↓ 自动创建新意识节点
  在dg_nodes中创建新意识节点（type=意识）
  在cognition_units中创建对应认知单元（双重身份）
  在cog_versions中创建v1版本记录（来源=本次POC）
  ↓ 下次POC验证这个新意识的价值
  下次POC的种子选择中包含这个新意识
  如果POC结果确认它有价值 → 版本链升级到v2
  如果POC结果确认它无价值 → 标记为deprecated
```

**实现路径**：
1. POC评分结果结构化——评分时不仅打分，还要标注"B组优于A组的增量来源是什么"
2. 增量来源分析——如果增量来源是一个隐含的数学意识（不是已有意识节点的调用），标记为"候选新意识"
3. 自动创建——在ArangoDB中创建新意识节点和对应认知单元
4. 下次POC验证——种子选择中包含候选新意识，验证其价值

**价值**：
- 数学意识的发现从"人工"升级为"半自动"
- 依赖图的构建从"手动设计"升级为"从POC结果中生长"
- 这正是80号文档"关键的诚实面对"中说的"依赖图的构建阶段需要综述博士参与"的工程化——用POC结果驱动意识发现，而不是依赖人工数学功力

**诚实面对**：
- 自动发现的"候选新意识"需要人工确认——AI可能发现假阳性
- 这个机制目前是设计，未实现——需要先积累足够多的POC结果才有分析价值
- 短期内仍然是"AI辅助发现+人工确认"，长期才可能做到全自动

### 反哺6：三层提取（L1/L2/L3）用版本链管理演化

#### 工作系统中的经验

91号方案的版本链设计——认知单元的版本从v1到v2到v3，记录演化历史。

#### 大师范系统当前的状态

83号文档设计了三层提取：L1解题思路→L2数学思维（弥漫性）→L3范式思维（改变图结构）。但三层提取的版本演化没有机制管理——L1/L2/L3是不同层次的东西，不是同一个认知的版本迭代。

**问题**：三层提取的结果如何结构化存储？L2是从L1抽象出来的，L3是从多个L2综合出来的——这个"抽象"和"综合"的过程没有被记录。

#### 反哺方案

**用版本链管理三层提取的演化——L1是v1，L2是v2，L3是v3**

| 层次 | 版本 | 内容 | 来源 |
|---|---|---|---|
| L1解题思路 | v1 | 具体步骤序列（"第一步作辅助线，第二步用相似比..."） | 直接记录 |
| L2数学思维 | v2 | 从L1抽象出的思维模式（"寻找不变量"） | AI二次分析 |
| L3范式思维 | v3 | 从多个L2综合出的范式（"矩阵=模等价"） | AI三次分析 |

**工作流**：
```
题库中一道题的解法
  ↓ L1提取（直接记录）
  cognition_units中创建认知单元，版本v1，key_cognition=具体步骤
  ↓ L2提取（AI二次分析）
  给同一认知单元新增版本v2，key_cognition=抽象出的思维模式
  ↓ L3提取（AI三次分析，综合多个L2）
  给同一认知单元新增版本v3，key_cognition=范式级思维
  ↓ 版本链记录了从具体到抽象的完整演化
```

**实现路径**：
1. 题库结构化时，每道题的解法创建一个认知单元
2. L1提取后，版本v1记录具体步骤
3. L2提取后，版本v2记录思维模式，current_version更新为v2
4. L3提取后，版本v3记录范式思维，current_version更新为v3
5. 跨题复用时，AI通过版本链知道"这个认知已经到了L3级别，可以跨领域复用"

**价值**：
- 三层提取的演化被结构化记录——不是只留在83号文档的方案中，而是每道题的提取都有版本链
- 跨题复用时，AI通过current_version知道"这个认知是L1/L2/L3哪个级别"——L1只在类似题中复用，L3可以跨领域复用
- 为83号文档的POC验证（三层提取跨题复用增益）提供结构化基础——可以对比"用L1提示"vs"用L2提示"vs"用L3提示"的证明质量差异

## 四、实现优先级

## 六、诚实面对

### 6.1 反哺不是替代，是增强

工作系统的经验反哺大师系统，不是用工作系统替代大师系统。两套系统仍然各司其职：
- 工作系统管AI的工作认知（怎么做工作）
- 大师系统管数学证明的依赖结构（怎么解数学题）

反哺的是**机制**——工作系统中验证过的机制（图遍历/版本链/回归验证/经典计算展开）可以应用到大师范系统的数学认知管理上。

### 6.2 反哺2的种子推荐表是新的不确定性

反哺2引入了"种子推荐表"——什么类型的题应该选哪些意识作为种子。这个表本身需要人工设计，是新的不确定性来源。

**缓解**：种子推荐表可以随POC验证迭代——某个种子推荐如果POC验证无效，就调整推荐。长期可以通过反哺5的自动发现机制来补充种子推荐表。

### 6.3 反哺5目前是设计，未实现

反哺5（自动发现新数学意识）是最有价值的反哺点，但也是最难实现的。需要：
- 足够多的POC结果才有分析价值
- POC评分结果需要结构化（标注增量来源）
- "候选新意识"的自动创建需要人工确认

短期内仍然是"AI辅助发现+人工确认"，长期才可能做到全自动。

### 6.4 反哺6需要题库建设配合

反哺6（三层提取用版本链管理）需要题库结构化配合——82号文档设计的题库结构化格式需要先实现。如果题库没有结构化，三层提取的版本链管理就没有数据基础。

## 七、与星学项目的关系

| 反哺点 | 星学项目是否有对应 | 说明 |
|---|---|---|

## 八、总结

工作系统升级（89-98号）不只是元层面的工作——它产生的6个机制可以直接增强大师系统：

1. **经典计算展开替代步骤2**——消除七步骤工作流的不确定性
2. **CP1-CP3加载数学意识**——系统化POC-1的发现（意识标注的价值）
3. **版本链管理数学认知演化**——结构化记录数学意识的深化过程
4. **回归验证保障持续质量**——依赖图变更后检测对已有功能的影响
5. **自动发现新数学意识**——从POC结果中生长依赖图
6. **三层提取用版本链管理**——L1/L2/L3的演化被结构化记录

**核心理念**：工作系统和大师系统共享同一套图驱动认知管理机制。工作系统是这些机制的第一个用户（管AI自己的工作认知），大师系统是第二个用户（管数学证明的依赖结构）。机制是通用的，应用场景是不同的。

**下一步**：按P0→P1→P2→P3的优先级逐步实现。P0（反哺1）可以立即执行——topo_generator.py已实现并测试通过，只需集成到七步骤工作流。P1（反哺2+反哺3）可以在POC-3执行时同时验证。
