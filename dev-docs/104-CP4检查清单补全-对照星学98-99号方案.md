# 104-CP4检查清单补全-对照星学98/99号方案

> **文档定位**：对照星学项目98号（CP4动态查询技术说明书）和99号（CP4补全两个稀疏矩阵更新纪律），补全数学项目的CP4检查清单。

## 一、问题

### 1.1 对照星学发现的缺失

星学项目CP4检查清单5项（都是**纪律**）：
1. 技术说明书同步纪律（doc_sync_discipline）
2. 星学大师系统稀疏矩阵更新纪律（star_master_matrix_update）
3. 工作系统稀疏矩阵更新纪律（work_matrix_update）
4. SDK维护纪律（sdk_maintenance）
5. 工作系统词汇表（glossary）

数学项目CP4检查清单当前5项，但只有2项是纪律，3项是认知资产（不是纪律）：
1. sdk_maintenance ✅ 纪律
2. glossary ✅ 纪律
3. arangodb_infra ❌ 基础设施描述，不是纪律
4. work_system_upgrade ❌ 升级方案，不是纪律
5. agents_management ❌ 管理认知，不是纪律

### 1.2 缺失的3项纪律

1. **技术说明书同步纪律**（doc_sync_discipline）——修改机制实现时对应说明书要同步。数学项目102号文档就是犯了这个错误（内联技术说明后没有同步机制），103号才补上依赖入图。
2. **工作系统稀疏矩阵更新纪律**（work_matrix_update）——本次工作产生了什么新的认知单元或依赖关系。
3. **数学大师系统稀疏矩阵更新纪律**（math_master_matrix_update）——本次工作是否发现了新的数学知识依赖关系。

### 1.3 103号文档的"检查依赖"触发词

103号文档（其实是AGENTS.md第6条工作系统纪律）加了"检查依赖"触发词——用户说"检查依赖"时AI回顾两个稀疏矩阵的更新需求。但这又只写在AGENTS.md的Markdown里，没入稀疏矩阵。应该作为CP4检查清单的一部分存在。

## 四、设计要点

### 4.1 为什么纪律必须是认知单元+依赖边，不能是AGENTS.md里的文字

星学98号文档的核心设计：**纪律是认知，不是代码（也不是Markdown文字）**。把纪律存为认知单元的好处：
- 纪律有版本链（可以追踪纪律的演变历史）
- 纪律有source_docs（可以反查纪律出自哪个文档）
- 纪律可以被图遍历发现（从stop_hook出发可以遍历到所有纪律）
- 纪律可以被审计（检查是否有纪律认知单元缺少depends_on边）
- 加新纪律=加一条边，不用改任何代码/AGENTS.md

### 4.2 为什么清理arangodb_infra等3个错误依赖

CP4检查清单的每一项应该是"回顾什么"的纪律，不是"是什么"的认知资产。
- arangodb_infra是"ArangoDB基础设施是什么"——这是认知资产，不是纪律
- work_system_upgrade是"工作系统升级方案是什么"——这是认知资产，不是纪律
- agents_management是"AGENTS.md管理是什么"——这是认知资产，不是纪律

它们应该保留在认知图中（可以被图遍历发现），但不应该出现在CP4检查清单中（不是"每次工作结束要回顾什么"）。
