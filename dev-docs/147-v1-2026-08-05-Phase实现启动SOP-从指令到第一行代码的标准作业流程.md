## 0. 本SOP是什么、怎么触发、做什么不做什么

### 0.1 是什么

本SOP是**从接到"实现Phase X"指令到动手写第一行代码**的完整前置流程。它不是审计手册（那是146号的职责），不是Check List（那是130—137号的职责），不是实现方案（那是如143号的职责），而是**把这三者串起来的工程工作流**——确保动手前认知到位、前置到位、预检到位、环境到位。

### 0.2 怎么触发

用户说以下任一语句时，AI必须执行本SOP：

- "请你遵照147号文档中的SOP，开始实现Phase X"
- "按147号SOP启动Phase X实现"
- "启动Phase X，走147号流程"

执行时，AI应明确宣告："我现在遵照147号SOP启动Phase X实现，当前进入阶段N：……"

### 0.3 做什么

10个阶段的前置检查和准备：
- 认知加载 → 三文件并读 → 前置Phase验收 → Check List预检 → 权威性预核对 → 断层预扫 → 全局项核对 → 角色隔离确认 → 方案先行 → 环境确认 → 启动声明

### 0.4 不做什么

- **不写实现代码**：SOP完成前不动手写任何实现代码
- **不做审计**：审计是146号第9章的事，在Phase实现后才做
- **不跳步**：10个阶段必须顺序执行，每阶段有明确出口条件
- **不假设"上次说通过了"**：前置Phase验收必须看测试证据

### 0.5 与146号的关系

| 文档 | 视角 | 覆盖范围 |
|---|---|---|
| 146号 | 审计方法论 | F1-F6断层类型学、D1-D4深度等级、12审计维度、实现前自检（第8章）、实现后审计（第9章） |
| 147号（本文件） | 工程工作流 | 从指令到第一行代码的10阶段前置流程，其中阶段3/4/5引用146号第8章作为子流程 |

**不重复原则**：147号阶段3（可实现性预检）、阶段4（权威性预核对）、阶段5（断层预扫）直接引用146号第8章的步骤，不在此重抄。147号补充的是146号第8章没有的：认知加载、前置Phase验收、全局项核对、角色隔离确认、方案先行、环境确认、启动声明。

## 4. 阶段2：前置Phase验收核对

### 4.1 为什么要这一步

139号审计证明：Phase 1实现出现6项遗漏，其中部分是因为前置Phase的"通过"只是"说通过了"，没有看测试证据。前置Phase的EXIT门必须**有测试证据**地通过，不能凭声明。

### 4.2 步骤

1. **确认前置Phase是哪个**：
   - Phase 1的前置是Phase 0
   - Phase 2的前置是Phase 1
   - …以此类推

2. **找前置Phase的EXIT门测试证据**：
   - 读前置Phase的Check List中的EXIT门定义
   - 找到对应的测试文件（如`test_phase1.py`、`test_phase2.py`）
   - **实际运行测试**，确认EXIT门通过
   - 如果测试文件不存在或测试失败，**停止SOP**，报告阻塞

3. **检查前置Phase的遗留问题**：
   - 读前置Phase的审计报告（如139号对Phase 1、144号对Phase 2）
   - 确认审计发现的遗漏已修正
   - 如有未修正的遗漏，记录但不阻塞（除非遗漏影响本Phase）

4. **检查前置Phase的代码模块是否就位**：
   - 确认前置Phase新增的代码模块存在且可导入

### 4.3 出口条件

- 前置Phase的EXIT门测试已实际运行并通过
- 前置Phase的遗留问题已记录
- 前置Phase的代码模块已确认就位

### 4.4 阻塞处理

如果前置Phase的EXIT门测试失败：
- **停止SOP**
- 报告："Phase X的前置Phase Y的EXIT门测试失败，需先修复Phase Y"
- 不进入下一阶段

| 对齐检查 | `.venv/bin/python3 xishujuzhen/alignment_check.py` | 通过 |

### 11.2 git clean纪律

> 来自全局AGENTS.md的"改前清干净+改后立即commit"纪律。

- 改文件前：检查目标文件/目录是否处于git clean状态，记录`before_status_baseline`，明确本轮`intended_delta`
- 改文件后：完成一个逻辑工作单元，立即commit，记录`after_status_baseline`，核验`after - before == intended_delta`

### 11.3 出口条件

- 所有检查项通过
- `before_status_baseline`已记录

## 13. SOP执行中的阻塞处理

### 13.1 阻塞类型

| 阻塞类型 | 典型场景 | 处理 |
|---|---|---|
| 前置Phase未通过 | 阶段2发现前置Phase EXIT门测试失败 | 停止SOP，报告"需先修复Phase Y" |
| G0门未冻结 | 阶段6发现本Phase前的G0门未冻结 | 停止SOP，报告"需先冻结G0-X" |
| Check List与127号严重偏差 | 阶段4发现大量枚举不一致 | 停止SOP，报告"Check List需大修" |
| 环境异常 | 阶段9发现ArangoDB连不上 | 停止SOP，报告"环境异常" |
| 未决问题阻塞 | 阶段6发现UQ-X未解决且影响本Phase | 停止SOP，报告"需先解决UQ-X" |

### 13.2 阻塞处理原则

- **不跳步**：阻塞时不绕过，不"先做别的"
- **报告清晰**：说明阻塞在哪一步、什么原因、需要什么才能解除
- **记录阻塞**：把阻塞记录到工作日志或dev-docs中
