## 一、核心问题

**检索机制（实时解析+检索+策略选择+提示注入）是否真的能帮助AI突破卡点？**

这不是"检索机制能选出正确的Q"（01工作线已验证），而是"选出Q后注入给AI，AI是否真的比没有Q时做得更好"。

A/B对照是唯一能回答这个问题的实验设计：
- A组（实验组）：有检索系统——实时解析Solver的trajectory，检测卡点时检索提示并注入
- B组（对照组）：无检索系统——Solver裸跑，无任何提示

只有A组显著优于B组，才能证明检索机制的价值。

## 二、实验题目选择

### 2.1 选择标准

A/B对照的题目必须满足：
1. **AI裸跑时stuck**——不是做错，是卡住不动（输出<200字符就说"我不知道"）
2. **有标准答案**——能客观判定A/B组谁做对了
3. **H图中有对应规则**——检索机制需要H图中的启发规则才能选出提示

### 2.2 题目集

**主实验**：253号案例题目（极差渐近精细下界问题）

选择理由：
- 已有完整的H图（Q1-Q10共10条规则）
- 01工作线已验证A7→Q8的检索正确性
- DevinCliParserProvider已在此题上验证（parse_confidence=0.88）
- 题目是证明题，有明确的对错判定标准

**补充实验**（如时间允许）：从MathArena stuck题中选2-3道数值题

候选（从20道stuck题中选）：
- AIME 2025 I #14（answer=735，resp_len=176，有一定输出但没做对）
- HMMT Nov 2025 #29（answer=3√5/7，resp_len=429，输出较长但卡住）
- BRUMO 2025 #28（answer=-2431/50，resp_len=284，输出较长但卡住）

**注意**：补充实验需要先为这些题构建H图（253号H图是专为极差问题构建的，不通用）。如果构建H图成本太高，先只做253号案例。

### 2.3 题目传递方式

用solver-harness的`--problem-file`传递题目文件，`--interactive`模式启动（支持运行时提示注入）。

## 三、实验设计

### 3.1 A/B对照变量

| 变量 | A组（实验组） | B组（对照组） |
|---|---|---|
| Solver | GLM-5.2 via devin cli | GLM-5.2 via devin cli |
| 启动方式 | solver-harness --interactive | solver-harness --interactive |
| MITM采集 | ✅ | ✅ |
| RealtimePipeline | ✅ 运行 | ❌ 不运行 |
| 提示注入 | ✅ 检测到卡点时注入 | ❌ 不注入任何提示 |
| Parser | DevinCliParserProvider | 无（B组不解析） |
| H图 | 253号H图（Q1-Q10） | 无 |

**唯一差异**：A组有RealtimePipeline运行（实时解析+检索+提示注入），B组没有。

### 3.2 重复次数

每组跑**3次**，排除偶然性。

- A组3次：`ab-test-a-253-run1`, `ab-test-a-253-run2`, `ab-test-a-253-run3`
- B组3次：`ab-test-b-253-run1`, `ab-test-b-253-run2`, `ab-test-b-253-run3`

### 3.3 实验参数

| 参数 | 值 | 说明 |
|---|---|---|
| model | glm-5-2 | 固定模型 |
| max_time | 600秒（10分钟） | 每次实验最大时间 |
| max_rounds | 10 | A组最大提示注入轮次 |
| hint_budget | 10 | A组最大提示注入次数 |
| poll_interval | 3秒 | trajectory轮询间隔 |
| stall_check_interval | 3轮 | 每3轮检测一次卡点 |
| parser_timeout | 180秒 | DevinCliParserProvider超时 |

### 3.4 执行顺序

**先跑B组（对照组），再跑A组（实验组）**。

原因：B组是裸跑，结果可预测（大概率stuck）。先跑B组确认"AI确实做不出来"，再跑A组看"检索系统是否能帮AI突破"。

## 四、评估指标

### 4.1 主要指标

| 指标 | 判定方法 | A组预期 | B组预期 |
|---|---|---|---|
| **成功率** | 证明是否正确（人工判定或SymPy验证） | >0% | 0% |
| **突破率** | 收到提示后trajectory中有新进展（新节点/新六元组元素） | >60% | N/A |
| **进展深度** | 六元组中V_t（已验证事实）的数量 | 中-高 | 低 |

### 4.2 次要指标

| 指标 | 判定方法 | 说明 |
|---|---|---|
| **效率** | 从开始到完成（或超时）的时间 | A组可能更慢（有解析开销），但更有进展 |
| **提示质量** | 提示是否引导AI自己思考（非替AI做题） | 检查提示文本是否包含答案 |
| **提示针对性** | 选中的Q是否对应AI当前的卡点 | 人工对比卡点类型和Q的内容 |
| **解析质量** | parse_confidence和SymPy验证通过率 | DevinCliParserProvider的解析效果 |

### 4.3 判定标准

**实验成功的标准**：
- A组至少1次做出正确证明（或显著进展），B组0次 → 检索机制有效
- A组和B组都stuck → 检索机制无效（或提示质量不够）
- A组和B组都做对 → 题目太简单，需要换更难的题

**突破率的判定**：
- 突破 = 收到提示后，AI的trajectory中新增了resolution节点或V_t元素
- 未突破 = 收到提示后，AI继续stuck或重复已有内容

## 五、实施流程

### 5.1 B组（对照组）实验

对每次run（run1, run2, run3）：

1. `solver_harness.py mitm start`（如果未启动）
2. `solver_harness.py launch --exp-id ab-test-b-253-run<N> --problem-file <253号题目文件> --model glm-5-2 --interactive`
3. 等待10分钟（或Solver自然结束）
4. `solver_harness.py stop --exp-id ab-test-b-253-run<N>`（自动decode-all）
5. 记录结果：是否做出证明、trajectory内容、耗时

**B组不启动RealtimePipeline**——Solver完全裸跑。

### 5.2 A组（实验组）实验

对每次run（run1, run2, run3）：

1. `solver_harness.py mitm start`（如果未启动）
2. `solver_harness.py launch --exp-id ab-test-a-253-run<N> --problem-file <253号题目文件> --model glm-5-2 --interactive`
3. 启动RealtimePipeline（用e2e_realtime_test.py --skip-launch）：
   - DevinCliParserProvider作为parser LLM
   - 253号H图
   - hint_budget=10
   - max_time=600
4. Pipeline自动运行：轮询trajectory → 解析 → 卡点检测 → 检索 → 选择 → 注入
5. 等待Pipeline结束（max_time=600秒或max_rounds=10）
6. `solver_harness.py stop --exp-id ab-test-a-253-run<N>`（自动decode-all）
7. 记录结果：是否做出证明、trajectory内容、提示注入次数、选中的Q、耗时

### 5.3 结果分析

实验完成后：
1. 收集A/B组的trajectory.jsonl和realtime_result.json
2. 对比A/B组的：
   - 最终证明是否正确
   - trajectory中的节点数量和类型分布
   - 六元组的最终状态（V_t/F_t/O_t/U_t）
   - 耗时
3. 对A组额外分析：
   - 每次提示注入后AI的trajectory变化（是否突破卡点）
   - 选中的Q是否对应AI当前的卡点
   - 提示文本是否包含答案（提示质量检查）
4. 落实验报告到dev-docs

## 八、风险和缓解

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| B组Solver意外做对（题目太简单） | 低 | 高（实验无效） | 先跑B组确认stuck，如做对则换更难的题 |
| A组Parser延迟过高导致提示注入太少 | 中 | 中 | max_time=600秒允许10轮，每轮解析~30秒，足够 |
| A组提示注入后Solver不响应 | 低 | 高 | 6.1已验证send-keys有效，6.5已验证注入成功 |
| A组每次都选中同一个Q（如Q1） | 中 | 中 | DevinCliParserProvider已能解析resolution事件（选中Q4），比降级模式好 |
| 实验耗时过长（6次×10分钟=60分钟+解析开销） | 中 | 低 | 可并行跑（不同exp-id，不同工作目录） |
| SymPy验证在解析中失败导致六元组不准 | 低 | 低 | parser有降级机制，parse_confidence会反映质量 |
