## 1. 两棵树（概念引用）

来自`原语化AI数学工程系统设计/05-两棵树/`：

- **引导展开树（Guided Expansion Tree）** = 过程——从题目出发，在提示驱动下展开的所有可能解题路径构成的空间。每个节点是一个数学处境，每条边是一个提示Q。活的、正在生长的。
- **解题记录树（Solution Record Tree）** = 产物——引导展开树展开完成后凝固的树。包含成功路径、失败路径、分叉点、中间处境。
- **它们是同一棵树的不同阶段。**

**系统的本质**：在不知道答案的情况下，通过引导展开机制，让AI生长出一棵尽可能完整的解题记录树。

## 2. 用户注入的核心认知：系统与推理AI并行运行

### 2.1 旧困境（已消解）

之前的设计困境是："如何让推理AI在合适的位置停下来接受提示？"

这个困境贯穿了04工作线的全部实现工作：
- HintInjector时序问题——等thinking完成还是thinking中注入？
- tmux send-keys排队问题——"Press Enter to send queued message"
- Response truncated后注入——等Solver空闲再注入
- stall_detector超时——30秒无新节点就触发，但thinking要5分钟

**所有这些问题都在解决一个不该存在的问题。**

### 2.2 新认知：推理AI不需要停下

**推理AI持续工作，走到哪里都可以。系统与推理AI并行运行。**

具体机制：

1. **推理AI持续推理**——不需要在某个位置停下来接受提示。AI从根节点（或某个脉络的起点）开始，持续推理，直到自然终止（token用尽、证毕、或崩溃）。

2. **系统实时采集**——系统通过mitmproxy流式截获、sessions.db轮询等手段，实时获取推理AI的trajectory和thinking内容。这是已经实现的能力（262号、05fef30 commit）。

3. **系统实时整理两棵树**——系统用采集到的trajectory/thinking，实时整理引导展开树（=解题记录树的生长态）。每个推理AI的探索贡献树的一条脉络。

4. **系统在节点上识别方向**——系统在树的某个节点上，用数据基座中的Pattern做检索/模式识别，识别出"从这个节点应该往哪些方向探索"。这些方向来自数据基座的积累。

5. **系统启动新的推理AI**——对每个识别出的方向，系统启动一个新的推理AI实例，给它"从根到当前节点的脉络"（之前的路径），让它理解和验证后继续探索这个方向。

6. **并发**——多个推理AI可以并发。假设有5个并发额度：
   - 某个脉络尽头有3条路 → 启动3个推理AI各探索一条
   - 剩余2个额度 → 系统实时整理3个AI的trajectory，发现新的可分配节点 → 分配剩余2个

7. **停机条件**——与正确解答的脉络相遇时停机。不需要所有分支都探索完。

### 2.3 关键洞察

**"让推理AI停下"这个需求消失了。**

- 推理AI运行到何方都是可以的——数据都会被用来形成两棵树
- 即便AI在思考到一半时崩溃了（token用尽），我们仍然得到了解题记录树的增长信息——它探索了一个脉络的一部分
- 如果AI最终解出来了，一切圆满
- 如果没有，它的思考和探索记录也是有价值的——只要它探索了最终的解题记录树的一个脉络

**系统的目的不是"让AI做出来"，而是"让两棵树生长出来，在过程中与正确解答的脉络相遇"。**

## 3. 对当前实现工作的影响

### 3.1 A/B对照实验的定位

当前A/B实验（265号方案）是未来系统的**简化版本**：
- 只有1个推理AI（不并发）
- 串行展开（thinking完成 → 注入提示 → 下一轮thinking）
- "注入提示让Solver继续"是"启动新推理AI给它脉络"的退化形式

A/B实验验证的是：**检索机制是否能选出正确的方向（提示Q）**。这是未来系统的核心能力之一——系统在节点上识别方向的能力。A/B实验用"注入提示"的方式验证这个能力，未来系统用"启动新推理AI+给脉络"的方式使用这个能力。

### 3.2 已实现能力的复用

| 已实现能力 | 在未来系统中的角色 |
|---|---|
| mitmproxy流式thinking截获 | 系统实时采集推理AI的trajectory |
| DevinCliParserProvider | 系统整理两棵树时的节点状态提取 |
| RetrievalPipeline | 系统在节点上识别探索方向 |
| ConstrainedPolicy | 系统选择"该往哪些方向展开" |
| solver-harness | 启动/管理多个并发推理AI实例 |
| sessions.db trajectory | 解题记录树的数据来源 |

### 3.3 需要新增的能力

| 新能力 | 描述 |
|---|---|
| 脉络构造 | 从根到当前节点的路径，构造给新推理AI的输入（"你之前已经证明了X、Y、Z，现在请继续探索方向W"） |
| 并发推理AI管理 | 同时管理N个推理AI实例，分配额度，收集结果 |
| 实时树整理 | 从多个并发推理AI的trajectory中，实时更新引导展开树 |
| 停机判定 | 检测某条脉络是否到达了正确解答 |
| 失败脉络记录 | 记录走不通的路径（死路叶），供数据基座积累 |

### 3.4 当前HintInjector时序问题的重新定位

之前花大量时间修复的HintInjector时序问题（等thinking完成再注入、tmux send-keys排队、状态检测等），在未来系统中**不再是问题**——因为未来系统不需要让推理AI停下接受提示，而是启动新的推理AI实例。

但这些修复工作不是白费的——它们验证了：
1. mitmproxy流式thinking截获的可靠性
2. tmux pane状态检测的方法
3. DevinCliParserProvider解析thinking内容的能力
4. RetrievalPipeline+ConstrainedPolicy选出提示的能力

这些能力都会在未来系统中复用。

## 4. 从A/B实验到未来系统的演进路径

### 阶段1（当前）：A/B对照实验——串行单AI
- 1个推理AI，串行展开
- thinking完成 → 解析 → 检索 → 选提示 → 注入 → 下一轮thinking
- 验证：检索机制是否能选出正确方向

### 阶段2：脉络注入——串行多AI
- 1个推理AI跑完（或崩溃）后，系统整理其脉络
- 在脉络的终点节点，检索识别方向
- 启动新的推理AI，给它之前的脉络，继续探索
- 仍然是串行，但不需要"让AI停下"——AI自然终止后系统再分配

### 阶段3：并发展开——多AI并发
- N个推理AI并发（比如5个）
- 系统实时采集所有AI的trajectory，整理两棵树
- 在树的节点上识别方向，分配新的推理AI
- 停机：与正确解答脉络相遇

### 阶段4：自我增殖——树→Pattern→树
- 解题记录树完成后，提炼Pattern存入数据基座
- 数据基座的Pattern积累 → 未来树长得更快更准
- 这是256号论文描述的"自我增殖的循环"

## 5. 术语对照

| 当前实现中的术语 | 未来系统中的术语 | 关系 |
|---|---|---|
| Solver（推理AI） | 推理智能体（树的生长点） | 同一概念 |
| 提示Q | 引导展开树的边 | 提示Q驱动从一个处境移动到另一个处境 |
| thinking内容 | 节点的数学处境 | parser从thinking中提取六元组=处境 |
| 检索+策略选择 | 在节点上识别方向 | 系统在节点上决定"该往哪些方向展开" |
| HintInjector注入提示 | 启动新推理AI+给脉络 | 阶段1用注入，阶段2+用启动新AI |
| solver-harness | 并发推理AI管理器 | 阶段1管理1个，阶段3管理N个 |
| A/B实验的B组（裸跑） | 只产出一条路径的弱系统 | 裸跑AI不产出树 |
| A/B实验的A组（有检索） | 长出几条路径的中等系统 | 检索机制驱动树的分叉 |
