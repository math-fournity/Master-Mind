## 1. 两棵树（概念引用）

来自`原语化AI数学工程系统设计/05-两棵树/`：

- **引导展开树（Guided Expansion Tree）** = 过程——从题目出发，在提示驱动下展开的所有可能解题路径构成的空间。每个节点是一个数学处境，每条边是一个提示Q。活的、正在生长的。
- **解题记录树（Solution Record Tree）** = 产物——引导展开树展开完成后凝固的树。包含成功路径、失败路径、分叉点、中间处境。
- **它们是同一棵树的不同阶段。**

**系统的本质**：在不知道答案的情况下，通过引导展开机制，让AI生长出一棵尽可能完整的解题记录树。

## 2. 用户注入的核心认知：系统与推理AI并行运行

### 2.1 旧困境（已消解）

之前的设计困境是："如何让推理AI在合适的位置停下来接受提示？"

这个困境贯穿了04工作线的全部实现工作：
- HintInjector时序问题——等thinking完成还是thinking中注入？
- tmux send-keys排队问题——"Press Enter to send queued message"
- Response truncated后注入——等Solver空闲再注入
- stall_detector超时——30秒无新节点就触发，但thinking要5分钟

**所有这些问题都在解决一个不该存在的问题。**

### 2.2 新认知：推理AI不需要停下

**推理AI持续工作，走到哪里都可以。系统与推理AI并行运行。**

具体机制：

1. **推理AI持续推理**——不需要在某个位置停下来接受提示。AI从根节点（或某个脉络的起点）开始，持续推理，直到自然终止（token用尽、证毕、或崩溃）。

2. **系统实时采集**——系统通过mitmproxy流式截获、sessions.db轮询等手段，实时获取推理AI的trajectory和thinking内容。这是已经实现的能力（262号、05fef30 commit）。

3. **系统实时整理两棵树**——系统用采集到的trajectory/thinking，实时整理引导展开树（=解题记录树的生长态）。每个推理AI的探索贡献树的一条脉络。

4. **系统在节点上识别方向**——系统在树的某个节点上，用数据基座中的Pattern做检索/模式识别，识别出"从这个节点应该往哪些方向探索"。这些方向来自数据基座的积累。

5. **系统启动新的推理AI**——对每个识别出的方向，系统启动一个新的推理AI实例，给它"从根到当前节点的脉络"（之前的路径），让它理解和验证后继续探索这个方向。

6. **并发**——多个推理AI可以并发。假设有5个并发额度：
   - 某个脉络尽头有3条路 → 启动3个推理AI各探索一条
   - 剩余2个额度 → 系统实时整理3个AI的trajectory，发现新的可分配节点 → 分配剩余2个

7. **停机条件**——与正确解答的脉络相遇时停机。不需要所有分支都探索完。

### 2.3 关键洞察

**"让推理AI停下"这个需求消失了。**

- 推理AI运行到何方都是可以的——数据都会被用来形成两棵树
- 即便AI在思考到一半时崩溃了（token用尽），我们仍然得到了解题记录树的增长信息——它探索了一个脉络的一部分
- 如果AI最终解出来了，一切圆满
- 如果没有，它的思考和探索记录也是有价值的——只要它探索了最终的解题记录树的一个脉络

**系统的目的不是"让AI做出来"，而是"让两棵树生长出来，在过程中与正确解答的脉络相遇"。**

## 3. 对当前实现工作的影响

### 3.1 A/B对照实验的定位

当前A/B实验（265号方案）是未来系统的**简化版本**：
- 只有1个推理AI（不并发）
- 串行展开（thinking完成 → 注入提示 → 下一轮thinking）
- "注入提示让Solver继续"是"启动新推理AI给它脉络"的退化形式

A/B实验验证的是：**检索机制是否能选出正确的方向（提示Q）**。这是未来系统的核心能力之一——系统在节点上识别方向的能力。A/B实验用"注入提示"的方式验证这个能力，未来系统用"启动新推理AI+给脉络"的方式使用这个能力。

| 新能力 | 描述 |
|---|---|

之前花大量时间修复的HintInjector时序问题（等thinking完成再注入、tmux send-keys排队、状态检测等），在未来系统中**不再是问题**——因为未来系统不需要让推理AI停下接受提示，而是启动新的推理AI实例。

但这些修复工作不是白费的——它们验证了：
1. mitmproxy流式thinking截获的可靠性
2. tmux pane状态检测的方法
3. DevinCliParserProvider解析thinking内容的能力
4. RetrievalPipeline+ConstrainedPolicy选出提示的能力

这些能力都会在未来系统中复用。

## 4. 从A/B实验到未来系统的演进路径

### 阶段1（当前）：A/B对照实验——串行单AI
- 1个推理AI，串行展开
- thinking完成 → 解析 → 检索 → 选提示 → 注入 → 下一轮thinking
- 验证：检索机制是否能选出正确方向

### 阶段2：脉络注入——串行多AI
- 1个推理AI跑完（或崩溃）后，系统整理其脉络
- 在脉络的终点节点，检索识别方向
- 启动新的推理AI，给它之前的脉络，继续探索
- 仍然是串行，但不需要"让AI停下"——AI自然终止后系统再分配

### 阶段3：并发展开——多AI并发
- N个推理AI并发（比如5个）
- 系统实时采集所有AI的trajectory，整理两棵树
- 在树的节点上识别方向，分配新的推理AI
- 停机：与正确解答脉络相遇

### 阶段4：自我增殖——树→Pattern→树
- 解题记录树完成后，提炼Pattern存入数据基座
- 数据基座的Pattern积累 → 未来树长得更快更准
- 这是256号论文描述的"自我增殖的循环"

## 6. 数据库表设计（ArangoDB图数据库）

两棵树在ArangoDB中维护。每道题一棵树。树=节点集合+边集合。

### 6.1 核心集合

#### `tree_nodes`（树节点集合·document）

每个节点 = 一个数学处境。

| 字段 | 类型 | 说明 |
|---|---|---|
| `_key` | string | 自动生成 |
| `problem_id` | string | 题目ID（哪棵树） |
| `node_type` | string | `root`/`internal`/`leaf_success`/`leaf_deadend`/`leaf_truncated` |
| `situation` | object | 数学处境（六元组：V_t/F_t/O_t/U_t/T_t/S_t） |
| `situation_text` | string | 处境的自然语言描述（从thinking中提取） |
| `depth` | int | 在树中的深度（根=0） |
| `parent_edge_key` | string | 父边的_key（根节点为null） |
| `path_from_root` | string[] | 从根到本节点的路径（节点key序列，冗余存储加速脉络构造） |
| `created_by_ai` | string | 贡献这个节点的推理AI实例ID |
| `created_at` | float | 创建时间戳 |
| `trajectory_segment` | object | 本节点对应的trajectory片段（thinking片段+tool_calls+results） |
| `status` | string | `growing`/`completed`/`deadend`/`truncated` |
| `retrieval_done` | bool | 系统是否已在此节点做过检索 |
| `directions_identified` | string[] | 检索识别出的方向Q的ID列表 |
| `ai_instances_started` | string[] | 从此节点启动的推理AI实例ID列表 |

#### `tree_edges`（树边集合·edge）

每条边 = 一个提示Q（引导从一个处境移动到另一个处境）。

| 字段 | 类型 | 说明 |
|---|---|---|
| `_key` | string | 自动生成 |
| `_from` | string | 父节点ID（`tree_nodes/xxx`） |
| `_to` | string | 子节点ID（`tree_nodes/yyy`） |
| `problem_id` | string | 题目ID |
| `hint_q` | string | 提示Q的内容（引导方向） |
| `hint_q_id` | string | 提示Q在数据基座中的Pattern ID（如有） |

| `ai_instance_id` | string | 沿这条边探索的推理AI实例ID |
| `created_at` | float | 创建时间戳 |
| `edge_status` | string | `growing`/`completed`/`deadend`/`truncated` |

#### `problems`（题目集合·document）

每道题一棵树。

| 字段 | 类型 | 说明 |
|---|---|---|
| `_key` | string | 题目ID |
| `problem_text` | string | 题目原文 |
| `root_node_key` | string | 根节点ID |
| `status` | string | `growing`/`solved`/`exhausted` |
| `solution_path` | string[] | 正确解答脉络的节点key序列（找到时填充） |

| `total_edges` | int | 树的总边数 |
| `ai_instances_used` | int | 使用的推理AI实例总数 |

#### `ai_instances`（推理AI实例集合·document）

每个推理AI实例的注册信息。

| 字段 | 类型 | 说明 |
|---|---|---|
| `_key` | string | AI实例ID（=solver-harness的exp_id） |
| `problem_id` | string | 题目ID |
| `entry_node_key` | string | 进入树的节点（从此节点开始探索） |
| `entry_edge_key` | string | 沿哪条边进入（如从根开始则为null） |
| `脉络文本` | string | 给AI的脉络输入（从根到entry_node的路径文本） |

| `devin_session_id` | string | devin cli session ID |
| `status` | string | `running`/`completed`/`crashed`/`truncated` |
| `started_at` | float | 启动时间 |
| `ended_at` | float | 结束时间 |

### 6.2 数据基座复用现有集合

数据基座（Pattern存储）复用01工作线已建立的集合：

- `patterns`：Pattern集合（"什么时候该提示什么"的经验单元）
- `hgraph_rules`：启发式规则集合（H图的Q规则）
- `cognition_units`：认知单元集合
- `dependency_edges`：依赖图边集合

检索机制（RetrievalPipeline）从这些集合中检索，识别出"从当前节点应该往哪些方向探索"。

### 6.3 图查询

ArangoDB AQL查询示例：

```sql
-- 获取某棵树的所有节点
FOR node IN tree_nodes
  FILTER node.problem_id == @problem_id
  RETURN node

-- 获取某棵树的所有边
FOR edge IN tree_edges
  FILTER edge.problem_id == @problem_id
  RETURN edge

-- 获取从根到某节点的路径（脉络构造）
-- 利用path_from_root冗余字段直接获取，无需递归查询

-- 获取所有status=growing的节点（可分配新AI的节点）
FOR node IN tree_nodes
  FILTER node.problem_id == @problem_id
  FILTER node.status == "growing"
  FILTER node.retrieval_done == true
  FILTER node.directions_identified != []
  RETURN node

-- 获取某棵树的成功路径
FOR node IN tree_nodes
  FILTER node.problem_id == @problem_id
  FILTER node.node_type == "leaf_success"
  RETURN node.path_from_root
```

## 7. 系统工作流程详细设计

### 7.1 主循环（树生长引擎）

```
while problem.status != "solved" and problem.status != "exhausted":
    # 1. 采集：实时采集所有running状态AI的trajectory
    for ai in get_running_ais(problem_id):
        trajectory = collect_trajectory(ai)
        thinking = collect_thinking(ai)  # mitmproxy流式截获

    # 2. 整理树：从trajectory中提取新节点，更新树
    for ai in get_running_ais(problem_id):
        new_nodes = extract_nodes_from_trajectory(ai, trajectory)
        for node in new_nodes:
            add_to_tree(node)
            update_ai_contribution(ai, node)

    # 3. 检查停机：是否有AI找到了正确解答
    for ai in get_running_ais(problem_id):
        if check_solution_found(ai):
            mark_problem_solved(problem_id, ai)
            break

    # 4. 检查AI终止：是否有AI自然终止
    for ai in get_running_ais(problem_id):
        if check_ai_terminated(ai):
            mark_ai_terminated(ai)
            # 在AI的最后一个节点上做检索
            last_node = get_last_node(ai)
            if not last_node.retrieval_done:
                directions = retrieve_directions(last_node)
                last_node.directions_identified = directions
                last_node.retrieval_done = true

    # 5. 分配：在所有可分配节点上启动新AI
    available_slots = MAX_CONCURRENT - count_running_ais()
    if available_slots > 0:
        assignable_nodes = get_assignable_nodes(problem_id)
        for node in assignable_nodes:
            if available_slots <= 0:
                break
            for direction in node.directions_identified:
                if available_slots <= 0:
                    break
                # 构造脉络
                path_text = construct_path_text(node.path_from_root)
                # 启动新AI
                ai = launch_ai(problem_id, node, direction, path_text)
                available_slots -= 1

    # 6. 实时检索：在growing节点上做检索（不等AI终止）
    for node in get_growing_nodes(problem_id):
        if not node.retrieval_done:
            # 节点还在生长中，但已经可以检索了
            directions = retrieve_directions(node)
            if directions:
                node.directions_identified = directions
                node.retrieval_done = true

    sleep(POLL_INTERVAL)  # 短暂等待后继续循环
```

### 7.2 脉络构造（construct_path_text）

把从根到当前节点的路径，构造给新推理AI的输入文本。

```
输入：path_from_root = [node_0, node_1, ..., node_n]
输出：脉络文本

脉络文本格式：
"""
你正在解答以下数学题：
[题目原文]

之前已经进行了以下探索：

[节点0] 初始处境：题目给出的条件和目标
  → 提示Q1：[Q1内容]
[节点1] 处境：[从thinking中提取的数学处境描述]
  已证明：[已确立的结论]
  当前表示：[当前的数学表示]
  → 提示Q2：[Q2内容]
[节点2] 处境：[...]
  ...
[节点n] 当前处境：[当前节点的数学处境描述]
  已证明：[到目前为止已确立的结论]
  当前表示：[当前的数学表示]
  卡在：[当前卡点]

请理解验证以上路径后，继续探索以下方向：
[方向Q的内容]

继续推理，给出完整的推理过程。
"""
```

### 7.3 节点提取（extract_nodes_from_trajectory）

从推理AI的trajectory中提取树节点。

```
输入：ai的trajectory（thinking + tool_calls + results）
输出：新节点列表

流程：
1. 用DevinCliParserProvider解析trajectory → ParseResult（语义事件+六元组）
2. 每个ParseResult对应一个新节点
3. 节点的situation = 六元组（V_t/F_t/O_t/U_t/T_t/S_t）
4. 节点的situation_text = 从thinking中提取的自然语言描述
5. 节点的trajectory_segment = 本节点对应的trajectory片段
6. 节点的created_by_ai = ai实例ID
7. 节点的parent_edge_key = 进入此节点的边
8. 节点的path_from_root = 父节点的path_from_root + 本节点key
```

### 7.4 方向检索（retrieve_directions）

在节点上检索数据基座，识别探索方向。

```
输入：node（当前节点）
输出：directions（方向Q列表）

流程：
1. 从node.situation提取六元组
2. 用RetrievalPipeline检索数据基座中的Pattern
3. 用ConstrainedPolicy选择最相关的N个方向
4. 返回方向Q列表（每个Q是一个引导提示）
```

### 7.5 停机判定（check_solution_found）

检测某条脉络是否到达了正确解答。

```
输入：ai的trajectory
输出：bool（是否找到正确解答）

流程：
1. 检查ai的最终输出是否包含完成标记（"证毕"/"QED"/"证明完毕"）
2. 如果包含，提取证明过程
3. 用SymPy/形式化验证工具验证证明的正确性
4. 如果验证通过，标记为leaf_success，返回true
5. 如果验证不通过，标记为leaf_deadend（看似成功但实际错误），返回false
```

### 7.6 AI终止检测（check_ai_terminated）

检测推理AI是否自然终止。

```
输入：ai实例
输出：bool + 终止原因

终止原因：
- token_limit：Response truncated（token用尽）
- crash：进程崩溃或连接失败
- solution_found：AI自己认为做出来了（需进一步验证）
- manual_stop：系统手动停止（如超时）
```
