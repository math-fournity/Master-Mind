## 1. 实验目标

验证两件事：

1. **实时并行树生长**——推理AI在thinking的同时，系统实时采集thinking、提取节点、整理两棵树。不是"等AI跑完再回填"，是"AI一边工作，系统一边整理树"。
2. **核心循环完整性**——循环的三个推动关系是否都成立。特别是推动关系3（AI终止后在叶节点检索方向Q，启动新AI），在POC-VMS-2第一次运行时没触发。

---

## 2. 实验设计

### 2.1 批量模式（tree_engine.py主循环）

- **题目**：10道虚拟群论题（8阶/12阶群，6种题目类型）
- **AI编排**：每题3个AI（1裸跑+2检索引导），共30个AI
- **并发**：最多2个并发AI
- **数据基座**：8个基础Pattern模板（加载到ArangoDB patterns集合）
- **检索器**：简化版（deterministic字段粗筛，无AI精筛）

### 2.2 手动模式（辅助Pipe亲手执行循环）

- **题目**：VG_067_conjugacy_class_computation（8阶直积群，共轭类计算）
- **AI编排**：单AI模式——每题只跑1个AI，如果token_limit没有其他AI抢先solved
- **辅助Pipe**：Master Agent本人手动调用工具执行循环的每一步
- **目的**：验证推动关系3能触发——AI token_limit后，在叶节点检索方向Q，构造脉络，启动新AI

## 3. 实验结果

### 3.1 批量模式结果

| 指标 | 结果 |
|---|---|
| AI总数 | 30 |
| solution_found | 27 |
| token_limit | 3 |
| solved率 | 10/10 |
| tree_nodes | 267 |
| tree_edges | 237 |
| 树深度 | d0-d11（最深处11层） |

**循环完整性诊断（批量模式）**：

| 推动关系 | 状态 | 说明 |
|---|---|---|
| 1. 引导树→推理AI | ✅ | 20个AI有方向Q，10个裸跑 |
| 2. 推理AI→解题树 | ✅ | 191/201个节点有thinking片段 |
| 3. 推理AI→引导树 | ❌ | 0/47个叶节点retrieval_done，0个动态扩展AI |

**判定：循环只转了半圈。**

推动关系3没触发的原因：3个token_limit的AI终止时，problem已经被其他并发AI solved了，走"already solved, 停机"分支，跳过了叶节点检索。当前虚拟题对GLM-5.2太简单，每道题至少有一个AI能解出来，所以停机条件总是先触发。

### 3.2 手动模式结果

| 指标 | 结果 |
|---|---|
| AI总数 | 2（branch1 + ext1） |
| AI-1（branch1） | token_limit，4个节点 |
| AI-2（ext1） | solution_found，4个节点 |
| solved率 | 1/1 |
| tree_nodes | 9（含根节点） |
| tree_edges | 8 |
| 树深度 | d0-d8（8层） |

**树结构**：

```
d0 [root]              system创建根节点+检索4个方向Q
  ↓
d1 [read_problem]      AI-1读取题目
d2 [conjugacy]         AI-1计算共轭类
d3 [conjugacy]         AI-1计算共轭类
d4 [leaf_truncated]    AI-1想写答案但token_limit终止
  ↓ 推动关系3：叶节点检索4个方向Q → 构造脉络 → 启动AI-2
d5 [read_problem]      AI-2读取题目
d6 [conjugacy]         AI-2计算共轭类
d7 [conjugacy]         AI-2计算共轭类
d8 [leaf_success]      AI-2给出最终答案
  ↓
problem: solved ✅ 停机
```

**循环完整性诊断（手动模式）**：

| 推动关系 | 状态 | 说明 |
|---|---|---|
| 1. 引导树→推理AI | ✅ | 2个AI有方向Q |
| 2. 推理AI→解题树 | ✅ | 8个节点有thinking片段 |
| 3. 推理AI→引导树 | ✅ | 1个叶节点retrieval_done，1个动态扩展AI |

**判定：循环完整转了一圈半。** 从根节点出发，AI-1走到d4 token_limit，叶节点检索启动AI-2，AI-2走到d8 solution_found，problem solved停机。

## 4. 检索准确性评估

| 指标 | 结果 |
|---|---|
| precision | 1.0（检索到的Pattern全部是期望的） |
| recall | 1.0（期望的Pattern全部被检索到） |
| 检索方法 | deterministic字段粗筛（task_type + group_order + group_type） |

**说明**：简化版检索器只用deterministic字段做粗筛，没有AI精筛。在当前8个Pattern的小规模基座下，粗筛已经足够准确。后续POC-VMS-3（1000个Pattern）需要加入AI精筛。

## 5. 关键发现

### 5.1 实时并行树生长可行

AI在thinking的同时，系统从thinking_live.jsonl中增量提取节点写入ArangoDB——树在AI运行过程中实时生长。不是"等AI跑完再回填"。

**技术路径**：mitmproxy流式截获thinking → thinking_live.jsonl（每个chunk一条JSON记录） → 按counter分组提取round → identify_operation识别操作类型 → create_node写入ArangoDB。

### 5.2 推动关系3需要"AI解不出来"的场景

推动关系3的触发条件是AI终止且problem未solved。如果AI解出来了（solution_found），停机条件先触发，跳过叶节点检索。只有AI token_limit（解不出来）且没有其他AI抢先solved时，推动关系3才会执行。

**对后续实验的启示**：要让循环完整转起来，需要要么用更难的题（AI全部token_limit），要么用单AI模式（没有其他AI抢先solved）。

### 5.3 辅助Pipe是AI本人，不是脚本

**最重要的发现。** 批量模式（tree_engine.py主循环）循环只转了半圈——不是代码有bug，是脚本没有判断力，遇到"problem already solved"就走停机分支，跳过了叶节点检索。手动模式（辅助Pipe亲手执行循环）循环完整转了一圈半——因为AI本人有判断力，知道在叶节点检索方向Q、构造脉络、启动新AI。

**结论**：tree_engine.py是辅助Pipe的工具集，不是辅助Pipe的替身。脚本的函数是手脚，认知和判断是AI的。运行实验时，AI切换到辅助Pipe角色，手动调用工具执行循环的每一步。

## 6. 双重角色教训

### 6.1 第一次跑POC-VMS-2时的反模式

启动tree_engine.py → `get_output`干等280秒 → 看结果。这等于把辅助Pipe的角色完全交给了脚本，自己退化成旁观者。

### 6.2 正确模式

手动调用工具执行循环：
1. 创建problem + 根节点 + 检索方向Q
2. 构造脉络 + 启动AI
3. AI在thinking时，读thinking_live.jsonl → 提取节点 → 写入ArangoDB
4. AI终止时，在叶节点检索方向Q → 构造脉络 → 启动新AI
5. 重复3-4直到problem solved或exhausted

**每一步的判断是AI的，脚本的函数只是手脚。**
