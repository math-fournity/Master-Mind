## 一、目标

提供一个CLI审计工具，能从层次1/2/3的数据源中提取完整运行轨迹，按8个维度进行审计分析，并根据审计结果给出优化方向建议。

**对应需求**（178号）：
- R3 事后审计
- R9 优化决策——未达预期时，判断是"吸收更多数据到稀疏矩阵"还是"优化工作机制"

## 二、CLI审计工具设计

### 2.1 工具接口

```bash
# 审计一个run
python audit_run.py --run-id run_20260806_001

# 审计一个devin cli session
python audit_run.py --session-id verbose-sunshine

# 只看时间线
python audit_run.py --run-id run_20260806_001 --dimension timeline

# 只看思路链
python audit_run.py --session-id verbose-sunshine --dimension thinking

# 导出审计报告
python audit_run.py --run-id run_20260806_001 --export-report runs/run_20260806_001/audit_report.md
```

### 2.2 数据源查询

```python
class AuditTool:
    def __init__(self, run_id=None, session_id=None):
        self.run_id = run_id
        self.session_id = session_id

    def load_layer1_data(self):
        """层次1：devin cli实例轨迹"""
        # 1. 读--export的conversation.json
        conv = json.load(open(f"runs/{self.run_id}/conversation.json"))
        # 2. 从sessions.db提取完整轨迹（thinking + tool_calls）
        trajectory = extract_session_trajectory(conv["session_id"])
        return {"conversation": conv, "trajectory": trajectory}

    def load_layer2_data(self):
        """层次2：系统内部执行日志"""
        # 1. 读system_events.json
        logs = [json.loads(line) for line in open(f"runs/{self.run_id}/system_events.json")]
        # 2. 从ArangoDB查询execution_logs collection
        db_logs = query_arango("execution_logs", {"run_id": self.run_id})
        return {"file_logs": logs, "db_logs": db_logs}

    def load_layer3_data(self):
        """层次3：思路轨迹"""
        # 从sessions.db提取thinking轨迹
        thinking_traj = extract_thinking_trajectory(self.session_id)
        return {"thinking_trajectory": thinking_traj}
```

## 三、8个审计维度

| 审计维度 | 问题 | 数据来源 | 自动化程度 |
|---|---|---|---|
| 时间线 | 系统从启动到结束经历了哪些步骤？每步多长时间？ | 层次1+2 | ✅ 全自动 |
| 决策链 | 系统每一步为什么做这个决策？有没有更好的选择？ | 层次2 | ✅ 全自动 |
| 引导链 | 系统给了数学大师哪些提示？每个提示的效果是什么？ | 层次2+3 | ⚠️ 半自动 |
| 思路链 | 数学大师的思路是怎么演化的？有没有走弯路？ | 层次3 | ❌ 需AI辅助 |
| 卡点分析 | 数学大师在哪些地方卡住了？卡了多久？系统怎么帮助的？ | 层次2+3 | ⚠️ 半自动 |
| 预算消耗 | 预算是怎么消耗的？哪一步消耗最多？是否值得？ | 层次2 | ✅ 全自动 |
| 效果归因 | 最终结果好或不好，归因于什么？ | 层次1+2+3 | ❌ 需AI辅助 |
| 优化方向 | 下次应该改进什么？数据？机制？提示策略？ | 综合分析 | ❌ 需AI辅助 |

## 四、优化决策框架

用户的核心问题："最终如果没有达到预期，我们的系统应该如何优化？是吸收更多的数据到稀疏矩阵中？还是说我们的系统的工作机制存在应该被优化的点？"

### 4.1 审计发现→优化方向映射

| 审计发现 | 优化方向 | 具体行动 | 验证方式 |
|---|---|---|---|
| 数学大师不知道某个数学工具/定理 | **数据问题**——稀疏矩阵缺数据 | 吸收更多数学知识到K投影 | 下次run中数学大师是否使用了该工具 |
| 数学大师知道工具但没想到用 | **机制问题**——HeuristicMatcher没匹配到规则 | 优化规则LHS条件或新增规则 | 下次run中规则是否被匹配 |
| 系统给了提示但数学大师没理解 | **提示问题**——提示内容或形式不对 | 优化Hint级别或提示内容 | 下次run中数学大师是否理解了提示 |
| 系统给了提示但提示方向错误 | **机制问题**——StateReducer状态估计错误 | 优化状态重建逻辑或卡点检测 | 下次run中状态估计是否正确 |
| 数学大师思路正确但执行出错 | **能力问题**——数学大师自身能力不足 | 换更强的模型或提供更多工具支持 | 下次run中执行是否正确 |
| 预算耗尽但任务未完成 | **预算问题**——预算分配不合理 | 优化预算分配策略 | 下次run中预算是否够用 |
| 系统循环但无进展 | **停止条件问题**——没及时停止 | 优化停止条件检测 | 下次run中是否及时停止 |

### 4.2 决策流程

```
审计完成
  ↓
效果是否达到预期？
  ├─ 是 → 记录成功模式，无需优化
  └─ 否 → 进入归因分析
        ↓
      归因分析（7种可能）
      ├─ 数据问题 → 吸收更多数据到K投影
      ├─ 机制问题（匹配） → 优化规则LHS
      ├─ 机制问题（状态） → 优化StateReducer
      ├─ 提示问题 → 优化Hint内容/级别
      ├─ 能力问题 → 换模型/加工具
      ├─ 预算问题 → 优化预算分配
      └─ 停止条件问题 → 优化停止检测
        ↓
      记录优化决策
        ↓
      下次run验证优化效果
```

### 4.3 框架的验证

这个框架本身需要验证——用历史session回测：

1. 从sessions.db中找几个已知结果的session
2. 用审计工具分析这些session
3. 看优化建议是否与实际已知的优化方向一致
4. 如果不一致，修正映射表
