## 一、用户需求（逐字记录）

> 其实，我们的数学大师系统，需要我可以全程监控，而且它自己可以全程记录，也就是说，我们运行起来一个测试之后，最后可以审计整个测试的结果，包括tmux中的devin的某个实例的运行全程的所有操作，或许这个可以通过tmux的自动log来实现或者devin cli自己就提供这种全程的trajectory的审计。另外就是整个系统的工作过程的细节，代码运行的细节，都应该可以翻查、审计，这样我们才可以分析，数学大师在工作的时候，它的思路到底是怎么走的，我们的系统到底是一步步如何引导它的，最终如果没有达到预期，我们的系统应该如何优化？是吸收更多的数据到稀疏矩阵中？还是说我们的系统的工作机制存在应该被优化的点？

### 需求拆解

|---|---|---|---|
| R1 | 全程监控 | 用户可以实时观察数学大师系统的运行过程 | 层次1 |
| R2 | 全程记录 | 系统自己记录整个运行过程，不需要用户一直盯着 | 层次1+2 |

## 二、核心问题

当前数学大师系统有一个**可观测性缺口**：

- **系统内部有事件记录**（RawEvent/SemanticEvent存储在ArangoDB），但这是系统自己记录自己的内部状态变化，不是从外部审计整个运行过程。
- **devin cli实例的运行过程没有完整记录**——tmux session中的操作只存在于终端scrollback buffer里，session结束后就消失了。
- **代码执行细节没有结构化记录**——Python代码的输入、输出、异常、中间变量状态都只在stdout/stderr中，没有结构化存储。
- **系统引导数学大师的过程没有可回放的轨迹**——系统每一步给了什么提示、数学大师怎么回应、系统下一步又给了什么，这个交互轨迹没有完整记录。

这个缺口的后果是：**我们无法回答"数学大师是怎么工作的"这个核心问题**。

## 三、三层全程记录架构

### 3.1 架构概览

```
层次1：devin cli实例轨迹（外部层）
  → 记录devin cli从启动到结束的所有操作
  → 详见 179号

层次2：系统内部结构化执行日志（中间层）
  → 记录12步运行时每一步的输入/输出/中间状态
  → 详见 180号

层次3：数学大师思路轨迹（内部层）
  → 分析数学大师在系统引导下的思路走向
  → 详见 181号

审计工具 + 优化决策框架
  → 从3层数据源提取完整轨迹，按8个维度审计，给出优化建议
  → 详见 182号
```

### 3.2 数据流

```
devin cli实例运行
    ├─ --export <run_dir>/conversation.json  ← 层次1首选：实时结构化导出
    ├─ sessions.db自动记录                    ← 深度审计：thinking + tool_calls + 结果
    ├─ transcripts/自动导出                   ← 自动备份
    └─ tmux pipe-pane > <run_dir>/tmux.log   ← 层次1兜底：纯文本终端输出

系统12步运行时
    ├─ ArangoDB自动记录（RawEvent + SemanticEvent + Budget + Checkpoint）
    └─ runs/${RUN_ID}/system_events.json      ← 层次2：结构化执行日志

关联键
    ├─ --export路径包含run_id → 导出文件与系统run关联
    ├─ system prompt注入run_id → devin cli session与系统run关联
    └─ EventCapture记录session_id → 系统事件与devin cli session关联

审计工具
    ├─ 读--export的conversation.json → 实时轨迹（system/user/agent消息流）
    ├─ 查询sessions.db → 深度分析（thinking + tool_calls + 性能指标）
    ├─ 查询ArangoDB → 系统内部状态变化、语义事件、预算消耗
    └─ 交叉关联 → 完整的运行轨迹审计
```

### 3.3 重大发现

**devin cli已经记录了我们需要的几乎所有数据**：
- AI的思考过程（`thinking`字段）
- 工具调用（`tool_calls`字段）
- 工具结果（`tool_call_state`表）
- 性能指标（`metadata`字段）

我们不需要从零建设全程记录系统，只需要：
1. 建立sessions.db和ArangoDB之间的关联键
2. 建一个审计查询工具
3. 建一个审计分析框架

这把方案复杂度从"建设三层全程记录系统"降低到"建设一个查询关联工具"。

## 四、8个审计维度

| 审计维度 | 问题 | 数据来源 | 自动化 |
|---|---|---|---|
| 时间线 | 系统从启动到结束经历了哪些步骤？每步多长时间？ | 层次1+2 | ✅ |
| 决策链 | 系统每一步为什么做这个决策？有没有更好的选择？ | 层次2 | ✅ |
| 引导链 | 系统给了数学大师哪些提示？每个提示的效果是什么？ | 层次2+3 | ⚠️ |
| 思路链 | 数学大师的思路是怎么演化的？有没有走弯路？ | 层次3 | ❌ |
| 卡点分析 | 数学大师在哪些地方卡住了？卡了多久？系统怎么帮助的？ | 层次2+3 | ⚠️ |
| 预算消耗 | 预算是怎么消耗的？哪一步消耗最多？是否值得？ | 层次2 | ✅ |
| 效果归因 | 最终结果好或不好，归因于什么？ | 层次1+2+3 | ❌ |
| 优化方向 | 下次应该改进什么？数据？机制？提示策略？ | 综合分析 | ❌ |

## 五、优化决策框架

| 审计发现 | 优化方向 | 具体行动 |
|---|---|---|
| 数学大师不知道某个数学工具/定理 | **数据问题**——稀疏矩阵缺数据 | 吸收更多数学知识到K投影 |
| 数学大师知道工具但没想到用 | **机制问题**——HeuristicMatcher没匹配到规则 | 优化规则LHS条件或新增规则 |
| 系统给了提示但数学大师没理解 | **提示问题**——提示内容或形式不对 | 优化Hint级别或提示内容 |
| 系统给了提示但提示方向错误 | **机制问题**——StateReducer状态估计错误 | 优化状态重建逻辑或卡点检测 |
| 数学大师思路正确但执行出错 | **能力问题**——数学大师自身能力不足 | 换更强的模型或提供更多工具支持 |
| 预算耗尽但任务未完成 | **预算问题**——预算分配不合理 | 优化预算分配策略 |
| 系统循环但无进展 | **停止条件问题**——没及时停止 | 优化停止条件检测 |
