# 从提取到查询的范式转变与trace-tell-hint统一命名

**文档编号**：309-v0
**日期**：2026-08-09
**触发**：用户在308号（亲眼看vms_test_1的AI推理thinking）之后提出范式转变——"所有的tell都是辅助AI来负责发现的。辅助AI是在查库。想办法把hint查出来。"随后要求完整定义过程中涉及的所有元素，并给出统一命名。
**前置文档**：304号（FCA与工程方案对应）、305号（非局部tell识别价值）、306号（我们到底想要什么）、307号（原语化构想）、308号（亲眼看vms_test_1真实thinking标注）
**性质**：范式转变记录 + 统一命名定义——从"从thinking提取拓扑"转向"辅助AI分析thinking→形成拓扑→查库→得到tell+hint"

---

## 0. 为什么记录本文档

308号证明了Grove AI（作为辅助AI的替身）能够分析真实thinking、识别非局部tell、给出hint。用户据此提出了一个根本性转向：如果辅助AI能做这件事，整个系统架构应该从"提取"范式转向"查询"范式。同时，过程中涉及的元素需要统一命名——和tell、hint一样简单。

本文档完整记录这个范式转变和统一命名方案。

---

## 1. 范式转变

### 1.1 原来的构想（304-307号）

```
推理AI产生thinking
    │
    ▼ Pipe 0：提取
拓扑（从thinking中机械提取，需要四类规范约束）
    │
    ▼ Pipe 1：匹配
候选tell（用拓扑匹配模式，形式化过滤）
    │
    ▼ Pipe 2：判断
tell（AI判断意图，从候选中选定）
    │
    ▼ 生成
hint（AI生成方向提示）
    │
    ▼ 给新推理AI
```

核心动作：**提取**。系统从thinking中提取拓扑，用拓扑匹配模式，AI判断意图，生成hint。tell是从thinking里"提取"出来的，hint是从tell"生成"的。

### 1.2 转向后的构想

```
推理AI产生thinking
    │
    ▼ 辅助AI分析（规范化方法）
trace（局部/非局部，辅助AI的识别结果）
    │
    ▼ 拓扑化（trace转化为查询key）
拓扑
    │
    ▼ 查库（用拓扑做key查询数据基座）
候选tell
    │
    ▼ 精化（概念树帮助下缩小范围）
tell（标准化trace描述）
    │
    ▼ 关联取出
hint（方向提示）
    │
    ▼ 给新推理AI
```

核心动作：**查询**。辅助AI分析thinking产出trace，用trace的拓扑查库，从库里取出标准化tell和关联的hint。tell不是从thinking里"提取"的，是辅助AI"识别"后从库里"查出"的。hint不是从tell"生成"的，是从库里"取出"的。

### 1.3 核心区别

**tell不是从thinking里"提取"出来的，是辅助AI"识别"出来的。hint不是从tell"生成"的，是从库里"查出"来的。**

### 1.4 转向的依据

308号的经验：Grove AI读了vms_test_1的thinking，然后：
1. 识别出"PSLQ闭式追逐"这个非局部tell——这不是从thinking里机械提取的，是**理解了**操作序列后**判断**出来的
2. 建议了hint"停止PSLQ追逐，考虑数值答案或分单元解析计算"——这不是从模式匹配生成的，是**基于数学知识**给出的

**Grove AI能做这件事，辅助AI就能做这件事。** 因为Grove AI就是辅助AI——读了thinking、理解了它、识别出tell、给出hint的AI。304-307号框架的全部复杂性（原语化、脱水、四类规范、Pipe 0/1/2）都是在解决"怎么让提取机械化"的问题。但如果辅助AI是智能的，提取不需要机械化——辅助AI直接分析thinking，就像Grove AI直接分析了vms_test_1的thinking一样。

## 2. 什么变了

### 2.1 306号的四类规范全部变性质

| 306号的规范 | 原来的问题 | 转向后 |
|---|---|---|
| 粒度规范 | 辅助AI提取节点粒度任意，需要约束 | 辅助AI自己判断粒度——就像Grove AI判断"PSLQ追逐"是一个段而不是每个pslq_attempt是一个段 |
| 拓扑化规范 | 需要定义节点/边类型（T图11+12种） | 辅助AI自己形成拓扑——拓扑是它的**分析产物**，不是提取产物 |
| 段结构规范 | 需要定义"追逐/桥接/构造-分析-排除"的模式 | 辅助AI自己识别模式——就像Grove AI识别出"追逐" |
| 脉络边界规范 | 需要定义脉络从哪到哪 | 辅助AI自己判断边界——它读thinking时自然知道哪里是一段 |

### 2.2 307号的原语化和脱水变可选

原语化和脱水的目的是让拓扑提取变机械化。如果辅助AI直接分析thinking，它不需要thinking是原语化的——它能读自然语言thinking，就像Grove AI能读vms_test_1的自然语言thinking。原语化和脱水从"必须"变成"可选的优化"——如果thinking是原语化的，辅助AI的分析更快更准，但不是前提条件。

### 2.3 Pipe 0/1/2的边界模糊了

原来Pipe 0（提取）、Pipe 1（匹配）、Pipe 2（判断）是三个独立阶段。转向后，辅助AI的分析本身就包含了提取+匹配+判断——Grove AI分析vms_test_1时没有分三个Pipe，直接就识别出了tell并给出了hint。三个Pipe融合成辅助AI的一次分析。

## 3. 什么没变

### 3.1 数据库（数据基座）仍然需要——角色变了

原来它是"Pattern库"（存拓扑模式供Pipe 1匹配）。现在它是**tell-hint字典**——存标准化的tell文本和对应的hint。辅助AI查库不是为了匹配拓扑，是为了**找到它识别出的trace对应的标准tell文本和hint**。

### 3.2 概念树仍然需要——角色变了

原来它是"概念格的工程版本"（管理概念膨胀）。现在它是**查询精化工具**——辅助AI用第一轮拓扑查询得到一批候选后，用概念树缩小到具体的标准化tell。

### 3.3 非局部tell的概念仍然成立

辅助AI仍然需要识别跨段模式（追逐/桥接/构造-分析-排除），仍然需要在中间看法下才能看到这些模式。只不过"看法"不是机械的连续划分，是辅助AI自己选择的分析粒度。

## 4. 统一命名——trace / tell / hint

### 4.1 现有叫法的问题

在304-308号文档里，"辅助AI从thinking中识别出来的东西"有多个叫法：

- "非局部tell"（305号）——跨段模式，如"模分析无尽追逐"
- "局部tell"（305号）——单节点特征，如"卡住了"
- "段特征"（304号§8.15）——段作为整体时的特征，如"构造必然逃逸的数"
- "tell"（000号）——"AI走了哪条路、没走哪条路"
- "tell目标内容"（304号§1）——格出来的可能是tell的东西
- "非局部hint"（305号§6.3）——针对整段的方向转换
- "局部hint"（305号§6.3）——针对单点的提示

问题：tell既指"AI识别出的模式"又指"库里存的标准化文本"，两个含义混在一起。而且"局部/非局部"是修饰词不是独立名词，说起来啰嗦。

### 4.2 三个核心名词

**trace** — 辅助AI从推理AI的thinking中识别出的结构化内容

**tell** — 数据库中存储的标准化trace描述

**hint** — 数据库中与tell关联的方向提示

三者构成一条链：**trace → tell → hint**

- 辅助AI分析thinking → 产出**trace**（局部trace或非局部trace）
- 辅助AI用trace查库 → 匹配到**tell**（如果库里存在）
- tell关联的**hint**被取出 → 给新推理AI

### 4.3 trace的定义

**trace** = 辅助AI对推理AI思维过程的结构化识别结果。

它不是thinking原文的摘要，是辅助AI**理解后**产出的结构化描述。比如Grove AI分析vms_test_1时产出的"PSLQ闭式追逐——AI反复尝试不同常数组合和精度，每次失败后换一组再试"——这就是一个trace。

trace分两种：
- **局部trace**：单段/单操作的特征。如"数值积分得0.32516"、"解析推导Area(A)得到arcsin组合"
- **非局部trace**：跨段模式。如"PSLQ闭式追逐"、"模分析无尽追逐"、"构造-分析-排除"

两者都是trace，只是作用范围不同。统一叫trace，用"局部/非局部"作修饰词区分——和原来tell的用法一样，但现在trace是AI侧的产物，tell是库侧的存储。

### 4.4 tell的定义

**tell** = 数据库中存储的标准化trace描述。

tell是trace的标准化版本。辅助AI产出的trace是具体的、和当前题目绑定的（"PSLQ闭式追逐"），库里的tell是去特化的、可泛化的（"闭式猜测追逐——AI反复尝试不同方法猜闭式解，每次失败后换方法再试"）。

一个tell可以匹配多个trace。比如"闭式猜测追逐"这个tell可以匹配"PSLQ闭式追逐"trace，也可以匹配"连分数闭式追逐"trace。

### 4.5 hint的定义

**hint** = 数据库中与tell关联的方向提示。

hint不变——还是305号定义的"方向，不是答案"。但现在hint明确是**库里存的**，不是辅助AI现场生成的。辅助AI查到tell就拿到hint，不需要自己生成。

### 4.6 三者的关系

```
推理AI的thinking
    │
    ▼ 辅助AI分析（规范化方法）
trace（局部/非局部）
    │
    ▼ 查库（用trace的拓扑特征做key）
tell（标准化trace描述）
    │
    ▼ 关联取出
hint（方向提示）
    │
    ▼ 给新推理AI
```

**trace是发现，tell是匹配，hint是取用。**

### 4.7 为什么这样命名好

1. **trace和tell只有一个字母之差，但角色清晰分离**——trace是AI侧的（动态的、具体的），tell是库侧的（静态的、标准化的）。原来tell身兼两职（既是识别结果又是库内容）的混淆消失了。

2. **trace有"踪迹"的含义**——辅助AI在推理AI的思维中追踪，留下的识别结果就是trace。比"tell目标内容"或"段特征"直观得多。

3. **trace→tell→hint是三步链路，每一步的动作不同**——发现（trace）、匹配（tell）、取用（hint）。原来tell→hint是两步，但tell内部混了发现和匹配，实际上是三步硬说成两步。

4. **局部/非局部统一修饰trace**——"局部trace"和"非局部trace"自然对应原来的"局部tell"和"非局部tell"，但不再混淆AI侧和库侧。

## 5. 完整的元素清单

转向后整个过程中涉及的元素：

| 元素 | 定义 | 谁产出 | 存在哪 |
|---|---|---|---|
| **thinking** | 推理AI的推理过程 | 推理AI | session数据 |
| **trace** | 辅助AI对thinking的结构化识别结果（局部/非局部） | 辅助AI | 持久化（作为数据基座增长的种子） |
| **拓扑** | trace的形式化表达，用作查询key | 辅助AI从trace构造 | 不持久化（临时使用） |
| **tell** | 标准化的trace描述 | 预先建设/持续增长 | 数据基座（数据库） |
| **hint** | 与tell关联的方向提示 | 预先建设/持续增长 | 数据基座（数据库） |
| **概念树** | tell的组织结构，供查询精化 | 预先建设/持续增长 | 数据基座（数据库） |
| **脉络** | 给新推理AI的输入（从根到当前节点路径+hint） | 辅助AI构造 | 引导树 |

过程性概念：

| 过程 | 定义 |
|---|---|
| **分析** | 辅助AI读thinking，产出trace |
| **拓扑化** | 辅助AI把trace转化为可查询的形式化表达 |
| **查库** | 辅助AI用拓扑做key查询数据基座，得到候选tell |
| **精化** | 辅助AI在概念树帮助下从候选tell缩小到具体tell |
| **取用** | 从tell关联取出hint |
| **注入** | 把hint构造为脉络，启动新推理AI |

## 6. trace的持久化与数据基座增长

trace持久化——它是数据基座增长的种子。辅助AI识别出的trace，如果库里没有匹配的tell，这个trace就是候选tell，经过确认后可以升级为tell并存入库。

这就是307号说的"原语增长机制"的trace版本——trace增长为tell。

增长机制：
1. 辅助AI产出trace
2. 查库，没有匹配的tell
3. trace标记为"候选tell"
4. 候选tell经过确认（可泛化、可复用）后升级为正式tell
5. 正式tell关联hint后存入数据基座

这个机制和307号§2.2的原语增长机制同构——"必须确认增加的是不存在的、可泛化和复用的"。只不过原语变成了trace→tell。

## 7. 一个待解决的问题

用户说"辅助AI是在查库，想办法把hint查出来"——这里有一个前提：**库里得有标准化的tell文本和对应的hint**。

这意味着数据基座的建设变成了核心工作。数据基座里需要存：
- 标准化的tell文本（"模分析无尽追逐"、"闭式猜测追逐"、"辅助函数+非负性约束"……）
- 每个tell对应的hint（"转向代数因式分解"、"停止猜测考虑数值答案或分单元计算"、"……"）
- tell的拓扑特征（供第一轮查询用）
- tell在概念树中的位置（供第二轮精化用）

**没有这个库，辅助AI能识别trace但查不到tell和hint。** Grove AI在308号给vms_test_1建议的hint是自己用数学知识生成的——如果库里没有"闭式猜测追逐"这个标准tell和它的hint，辅助AI只能自己生成hint，那就不是"查库"了，又回到了"AI生成"。

数据基座的建设是转向后的核心工程工作。

## 8. 另一个待解决的问题——辅助AI分析thinking的"规范化方法"

用户说"按照规范化的方法，把自己识别出来的非局域化内容形成拓扑"——这个"规范化的方法"需要定义。

不是306号的四类提取规范（那是给机械提取的），是给AI分析的规范——告诉辅助AI"你应该怎么分析thinking，应该形成什么样的拓扑作为查询key"。

这个规范可能包括：
- 分析thinking时关注什么（操作序列的结构、操作之间的关系、返回值模式）
- 识别trace时怎么判断"这是一个trace"（操作的累积构成有意义的模式）
- 形成拓扑时用什么形式（trace的结构化表达——操作类型+关系+模式）
- 局部trace和非局部trace的判断标准（单段vs跨段）

这个规范是后续要定义的。
