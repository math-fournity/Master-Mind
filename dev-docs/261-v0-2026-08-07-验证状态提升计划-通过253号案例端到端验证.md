## 2. 验证优先级排序

### 2.1 排序维度

对31个untested原语按以下四个维度排序：

**维度1：在检索机制中的角色**
- 核心14个原语（直接决定检索能否工作）> 支撑原语（提供基础设施）> 不直接服务于检索

**维度2：依赖关系（被多少其他原语依赖）**
- 被依赖越多 → 越优先（因为不验证它，依赖它的原语也无法验证）

**维度3：实现难度**
- 低（逻辑清晰、有现成方案）> 中（需要设计决策但路径明确）> 高（需要攻关或理论突破）

**维度4：验证难度（能否用253号案例直接验证）**
- 低（253号的Q/A直接覆盖）> 中（需要额外构造测试数据）> 高（需要完全不同的场景）

### 2.2 P0：必须先验证（第一层入口+解析器相关）

**P0包含5个原语**——它们是检索机制的入口瓶颈，不验证P0则后续所有环节无法运行：

| 优先级 | 原语 | 排序依据 |
|---|---|---|
| P0-1 | event-sourcing | 检索机制入口①，被4个原语依赖（最多），260号已给完整攻关方案，验证难度中等 |
| P0-2 | thinking-trajectory-graph | 检索机制步骤②，被3个原语依赖，依赖event-sourcing，260号已给T_t构建方案 |
| P0-3 | dynamic-workspace | 检索机制步骤③，被3个原语依赖，依赖event-sourcing，260号已给六元组归约方案 |
| P0-4 | progress-measurement | 检索机制步骤⑤，被constrained-policy依赖，253号A7后进展可直接验证，验证难度低 |
| P0-5 | checkpoint | 支撑原语，被controlled-experiment和reactive-rescue依赖，实现难度低（SHA-256哈希），验证难度低 |

**P0排序理由**：
1. event-sourcing是整个检索机制的数据入口——没有事件流，T_t、六元组、卡点检测都没有输入。260号已经给出了完整的LLM+SymPy混合解析方案，实现路径明确。
2. thinking-trajectory-graph和dynamic-workspace直接依赖event-sourcing的输出，是第一层状态感知的核心组件。
3. progress-measurement虽然被依赖数只有1，但它的验证难度低（253号的10步证明路径提供了明确的进展度量基准），且是constrained-policy的前置条件。
4. checkpoint实现简单（内容哈希+快照存储），是后续实验的基础设施。

### 2.3 P1：核心机制（第二层+第三层核心）

**P1包含9个原语**——它们是检索机制的核心算法环节，依赖P0的输出：

| 优先级 | 原语 | 排序依据 |
|---|---|---|
| P1-1 | heuristic-rule-graph | H图是activation-score和pattern-matching的存储基础，需先初始化Pattern库 |
| P1-2 | activation-score | 检索机制步骤⑥，粗筛机制，依赖heuristic-rule-graph，253号10个Q可做权重标定 |
| P1-3 | pattern-matching | 检索机制步骤⑦，精排机制，依赖T_t和H图，253号Q8的LHS可做匹配验证 |
| P1-4 | constrained-policy | 检索机制步骤⑩，最终决策，知识悖论核心，253号Q8 vs Q9的选择可验证 |
| P1-5 | hint-gradient | 检索机制步骤⑪，降级机制，253号Q9的泄漏可验证降级路径 |
| P1-6 | pattern-lifecycle | H图规则管理，activation-score的前置（需published规则），253号10个Q可初始化生命周期 |
| P1-7 | reactive-rescue | 运行模式，协同constrained-policy，253号A7→Q8是反应式救援的典型场景 |
| P1-8 | budget-management | constrained-policy的约束条件，实现难度低，验证难度低 |
| P1-9 | gain-attribution | 反馈闭环，253号A8的好坏判定可验证增益归因 |

**P1排序理由**：
1. heuristic-rule-graph排在P1最前——H图是第二层检索的存储基础，没有H图，activation-score和pattern-matching都没有数据可操作。253号的10个Q需要作为Pattern初始化到H图中。
2. activation-score和pattern-matching是第二层的核心算法，直接决定Q8能否被检索到。
3. constrained-policy是第三层的核心决策，决定从候选中选出Q8还是其他。
4. hint-gradient是安全阀，253号Q9的泄漏场景可以验证降级机制。
5. pattern-lifecycle、reactive-rescue、budget-management、gain-attribution是支撑机制，在端到端验证中需要运行但不是最关键的算法环节。

## 3. P0实现路径

### 3.1 P0-1：event-sourcing（untested → partial）

**实现什么**：
按260号§5的模块划分实现解析器原型：
- `xishujuzhen/research_runtime/parsing/parser.py`——主入口，协调LLM和SymPy
- `xishujuzhen/research_runtime/parsing/llm_parser.py`——LLM粗解析模块
- `xishujuzhen/research_runtime/parsing/sympy_verifier.py`——SymPy精确验证模块
- `xishujuzhen/research_runtime/parsing/models.py`——ParseRequest/ParseResult等数据结构

核心功能：从工作智能体的自然语言推理输出中，解析出14种语义事件类型的结构化序列。

**用什么测试数据**：
253号案例的A1-A10共10轮输出。重点用A7（稳定性方程推导，包含3个RESOLUTION事件+1个REPRESENTATION事件）作为核心测试用例。辅以A5（STALL事件）、A8（CLAIM+STALL事件）、A9（VERIFICATION+RESOLUTION事件）。

**验证什么（通过标准）**：
按260号§7.6的验证通过标准：
- 事件类型准确率 ≥ 70%（最低可接受值）/ 80%（目标值）
- 数学对象提取率 ≥ 80% / 90%
- SymPy验证通过率 ≥ 75% / 85%
- 六元组综合准确率 ≥ 65% / 75%
- 前沿节点识别率 ≥ 80% / 90%
- 卡点类型识别率 ≥ 70% / 80%

**依赖什么**：
- 无前置原语依赖（event-sourcing是第0层基础设施）
- 需要LLM API（GLM-5.2或更强模型）
- 需要SymPy库
- 需要253号案例的Gold Standard（人工标注A1-A10的语义事件、节点、六元组）

**预期验证状态提升**：untested → partial
- 理由：260号建议将解析器规格写入event-sourcing原语文件，解析器原型实现+253号案例验证后，event-sourcing从"设计完成但事件捕获器未实现"升级为"设计完成+实现规格+原型验证"。但如果准确率未达目标值，仍为partial（部分验证）。

### 3.2 P0-2：thinking-trajectory-graph（untested → partial）

**实现什么**：
从event-sourcing的ParseResult中构建思维轨迹图T_t：
- `xishujuzhen/research_runtime/trajectory/graph_builder.py`——从semantic_events和trajectory_nodes构建T_t
- 图节点10种类型，边13种类型（规格见260号§2.3.2）
- 前沿节点标记（is_frontier）
- 图存储到ArangoDB的trajectory_nodes和trajectory_edges集合

核心功能：把解析器输出的节点和边组装为完整的思维图，标记当前前沿节点。

**用什么测试数据**：
253号案例A1-A10。重点验证A7之后的T_t结构：
- 路径：中心化→q(x)→恒等式→紧性归约→投影到根→稳定性方程（前沿节点）
- 节点类型：observation→claim→representation→resolution→representation→resolution
- 边类型：notice→infer→recall→transform→infer

**验证什么**：
- T_t的节点数量与Gold Standard一致（±1容差）
- 前沿节点正确识别（A7后前沿=稳定性方程resolution节点）
- 路径结构正确（从中心化到稳定性方程的推理链完整）
- 边类型正确（infer/recall/transform等关系正确标注）

**依赖什么**：
- event-sourcing（P0-1，提供ParseResult中的trajectory_nodes和trajectory_edges）
- ArangoDB（存储图结构）

**预期验证状态提升**：untested → partial
- 理由：T_t的构建依赖event-sourcing的解析质量。如果解析器准确率达到70%+，T_t的结构基本正确，但10种节点类型和13种边类型的完备性需要更多案例验证。

### 3.3 P0-3：dynamic-workspace（untested → partial）

**实现什么**：
从event-sourcing的事件流中归约六元组状态：
- `xishujuzhen/research_runtime/workspace/reducer.py`——版本化Reducer，从事件流归约六元组
- 六元组数据结构（SixTuple，见260号§2.3.3）：V_t/F_t/O_t/R_t/E_t/U_t
- 增量更新机制（每轮基于上一轮六元组做增量更新）
- 状态等价检查（规范化键判定）

核心功能：把解析器输出的语义事件归约为当前时刻的完整状态描述。

**用什么测试数据**：
253号案例A1-A10的六元组演化序列。重点验证A7之后的六元组（260号§4.2.2已给出期望输出）：
- V_t：{中心化结果, q(x)定义, 两个恒等式, 紧性归约, 投影结果}（5项）
- F_t：{稳定性方程5D=3√5(B_r-B_s)+2C, D=√5(pn-k)}（2项）
- O_t：{估计D的下界(open), 把D下界传递到δ下界(open)}（2个open义务）
- R_t：{中心化, 紧性归约, 投影到根, 稳定性方程表示}（4项）
- E_t：{}（空）
- U_t：{D的量级问题——D=√5(pn-k)取决于整数k和n的关系(blocking)}（1项）

**验证什么**：
- 六元组综合准确率 ≥ 65%（260号§7.6最低可接受值）
- V_t只增不减（已验证事实不被删除）
- O_t状态正确转移（A7后"从矩条件导出恒等式"标记为solved）
- U_t正确识别blocking问题（D的量级问题）

**依赖什么**：
- event-sourcing（P0-1，提供语义事件序列）
- obligation-hypergraph（partial，提供O_t的AND/OR结构）
- evidence-system（partial，提供E_t的证据管理）

**预期验证状态提升**：untested → partial
- 理由：六元组的V_t/F_t/R_t相对容易归约（从RESOLUTION/REPRESENTATION事件直接映射），但O_t和U_t的自动识别依赖解析器对"开放义务"和"未解决问题"的语义理解，准确率可能不足。

### 3.4 P0-4：progress-measurement（untested → tested）

**实现什么**：
从dynamic-workspace的六元组状态中提取5个可测量分量，计算进展偏序P_κ(S_t)：

### 4.2 P1-2：activation-score（untested → partial）

**实现什么**：
在H图稀疏表示上计算候选激活分数a_t = W^T · p_t：
- `xishujuzhen/research_runtime/activation/score_calculator.py`——激活分数计算模块
- 从T_t提取特征向量p_t（7种数值维度）
- 权重矩阵W（7维 × N规则数）
- 稀疏矩阵乘法，取top-K候选

7种数值维度的初步定义（基于253号标定）：
1. 稳定性方程存在度（T_t中是否有resolution节点包含"稳定性方程"）
2. 整数依赖度（U_t中是否有"取决于整数关系"的条目）
3. 下界需求度（O_t中是否有"估计下界"的open义务）
4. 知识缺口度（U_t中是否有knowledge_gap标注）
5. 推理深度（T_t的路径长度）
6. 表示丰富度（R_t的条目数）
7. 卡点严重度（stall-detection输出的卡点类型严重等级）

**用什么测试数据**：
253号A7之后的T_t特征向量p_t。期望输出：
- Q8的激活分数最高（0.89，258号§6.3预演值）
- Q9的激活分数次高（0.72，因为Q9的LHS也部分匹配A7后的状态）
- Q1-Q7的激活分数低（它们的触发条件是更早的状态，A7后已不匹配）

权重W的标定方法：用253号的10个Q作为标定数据——已知每个Q的触发条件（A_{i-1}之后的状态），反推权重使得Q_i在A_{i-1}之后的激活分数最高。

**验证什么**：
- A7之后Q8的激活分数排在top-3（最低可接受）/ top-1（目标）
- A_i之后Q_{i+1}的激活分数排在top-5（说明排序机制有效）
- 不相关的Q（如A7后Q1的激活分数）排在后面

**依赖什么**：
- heuristic-rule-graph（P1-1，提供H图和规则集）
- pattern-lifecycle（P1-6，规则需为published状态）
- thinking-trajectory-graph（P0-2，提供T_t用于特征提取）

**预期验证状态提升**：untested → partial
- 理由：激活分数公式a_t = W^T · p_t的实现不复杂，但7种数值维度的权重W需要标定。253号的10个Q提供了标定数据，但10个数据点标定7维权重，统计显著性有限。权重标定后Q8能排在前列即为partial，但权重的泛化性（在其他题目上是否有效）需要后续验证。

### 4.3 P1-3：pattern-matching（untested → partial）

**实现什么**：
对activation-score筛出的top-K候选Pattern，逐一做LHS子图匹配+Guard条件检查：
- `xishujuzhen/research_runtime/matching/pattern_matcher.py`——模式匹配模块
- LHS子图匹配：T_t的子图与LHS的图模式做同构检测
- Guard条件检查：额外约束（如"D取决于整数关系"）
- 近似匹配容差：定义图编辑距离阈值（258号缺口3）

近似匹配容差的初步定义：
- 精确匹配：T_t的子图与LHS完全同构 → 匹配分数1.0
- 近似匹配（1步偏差）：T_t比LHS多或少1个节点 → 匹配分数0.8
- 近似匹配（2步偏差）：T_t比LHS多或少2个节点 → 匹配分数0.6
- 超过2步偏差 → 不匹配

**用什么测试数据**：
253号A7之后的T_t与Q8的LHS做匹配。期望：
- Q8的LHS匹配成功（路径匹配+Guard通过），匹配分数≥0.8
- Q9的LHS部分匹配（路径匹配但Guard不通过——A7后还没有"D≠0但下界未知"的状态），匹配分数0.5
- Q1-Q7的LHS不匹配（路径结构差异大），匹配分数<0.3

**验证什么**：
- Q8在A7后的匹配分数最高（被pattern-matching选中）
- Q9在A7后的匹配分数中等（部分匹配，进入候选但不首选）
- 匹配分数的排序与253号QA序列的顺序一致（Q_i在A_{i-1}后匹配分数最高）

**依赖什么**：
- thinking-trajectory-graph（P0-2，提供T_t）
- heuristic-rule-graph（P1-1，提供LHS定义）
- activation-score（P1-2，提供候选集）

**预期验证状态提升**：untested → partial
- 理由：子图匹配算法本身有成熟实现（如VF2算法），但LHS的图模式表示和近似匹配容差是核心难点。253号的10个Q可以标定容差阈值，但图编辑距离的计算复杂度可能较高（NP-hard），需要工程优化。

### 4.4 P1-4：constrained-policy（untested → partial）

**实现什么**：
在进展最大化、泄漏最小化、依赖最小化、成本控制多个约束下选择最优动作：
- `xishujuzhen/research_runtime/policy/constrained_optimizer.py`——多约束决策模块
- 四个约束的计算：
  1. 进展估计：从progress-measurement获取（Q8指向"估计D的下界"，对应O_t中的open义务）
  2. 泄漏估计：从leakage-detection获取（Q8的Level=0.5，非特定性=0.7，四门检查通过）
  3. 依赖估计：从context-compiler的输出中提取（Q8只依赖已有稳定性方程）
  4. 成本估计：1轮交互
- Pareto最优选择：在四个约束下选Pareto最优的动作
- ABSTAIN是合法选择（如果所有候选泄漏风险都太高）

**进展估计的破解方案**（258号缺口4）：
Pattern自带进展标签——在H图中每条规则的RHS中标注"解决O_t中的哪个义务"。constrained-policy只做义务匹配：
- Q8的RHS标注："解决O_t中的'估计D的下界'"
- A7后O_t中有"估计D的下界"(open)
- 匹配成功 → Q8的进展潜力高
- 不需要理解数学内容，只需要做义务ID匹配

**用什么测试数据**：
253号A7之后的候选列表（Q8 + Q9 + 2个部分匹配Pattern）。期望：
- Q8在四个约束下Pareto最优（进展高/泄漏低/依赖低/成本低），被选中
- Q9的泄漏估计高（Level=0.2，非特定性=0.9，包含"badly approximable"关键词），不被首选
- ABSTAIN不被选中（因为Q8的泄漏风险可接受）

**验证什么**：
- 系统在A7后选中Q8（而非Q9或其他Pattern）
- 选择理由可解释（四个约束的值明确给出）
- ABSTAIN机制正确（如果所有候选泄漏都超标，选择不干预）

**依赖什么**：
- progress-measurement（P0-4，提供进展估计）
- leakage-detection（partial，提供泄漏估计）
- budget-management（P1-8，提供成本估计）
- heuristic-rule-graph（P1-1，RHS中标注义务ID）

**预期验证状态提升**：untested → partial
- 理由：多约束优化的框架清晰，Pareto最优选择有成熟算法。但"Pattern自带进展标签"机制需要在H图初始化时人工标注每条规则的RHS义务ID——这是额外的标注工作。253号10个Q的标注完成后可以验证，但进展标签的泛化性（在其他题目上是否有效）需要后续验证。

- 反事实估计："没有Q8，工作智能体是否也会分析D的下界？"

**用什么测试数据**：
253号10轮QA的增益归因：
- Q8的增益：A8分析了D=√5(pn-k)，D≠0但下界未知——这个进展归因给Q8
- Q9的增益：A9使用了badly approximable性质，得到|D|≥c₁/n——这个进展归因给Q9
- Q1-Q7的增益：每轮A_i的进展增量归因给Q_i

**验证什么**：
- 提示链正确记录（Q1→Q2→...→Q10的顺序）
- 增益归因正确（A_i的进展增量归因给Q_i而非Q_{i-1}）
- 反事实估计合理（"没有Q8，工作智能体不太可能自发分析D的下界"——因为D的量级问题在U_t中是blocking）

**依赖什么**：
- controlled-experiment（tested，提供对照框架）
- progress-measurement（P0-4，提供进展度量）
- trajectory-recording（tested，提供轨迹数据）

**预期验证状态提升**：untested → partial
- 理由：增益归因的框架清晰，253号10轮QA可以验证归因逻辑。但反事实估计"没有Q8是否也会达到进展"需要对照实验（去掉Q8重跑），253号是预演数据无法做对照。因此为partial。

## 7. 风险和缓解

### 7.1 解析器准确率不足

**风险**：LLM+SymPy混合解析器的准确率低于最低可接受值（事件类型准确率<70%或六元组综合准确率<65%），导致T_t和六元组质量太差，后续检索环节输入不可靠。

**概率**：中——260号已给出详细的prompt设计和SymPy验证方案，但数学推理文本的语义解析本身是困难任务，首次实现可能达不到目标准确率。

**影响**：高——解析器是整个检索机制的入口瓶颈，准确率不足会导致端到端验证失败。

**缓解措施**：
1. **改进prompt**：增加few-shot示例（用A7的完整解析作为示例），让LLM更准确地理解输出格式
2. **增加SymPy验证覆盖**：对更多数学表达式做SymPy验证，减少LLM幻觉的影响
3. **换更强的LLM**：如果GLM-5.2准确率不足，尝试用更强的模型做解析
4. **降级运行**：即使准确率不足，也运行完整端到端流程，定位哪些环节受影响最大，针对性改进
5. **人工辅助标注**：对解析器输出做人工修正，用修正后的数据运行后续环节，验证后续环节是否工作（隔离解析器问题）

### 7.2 Pattern库为空（冷启动问题）

**风险**：H图初始化时只有253号的10个Q作为Pattern，Pattern库太小，activation-score的权重标定和pattern-matching的容差标定数据不足。

**概率**：高——253号只有10个Q，标定7维权重和匹配容差的统计显著性有限。

**影响**：中——权重和容差可能过拟合到253号案例，在其他题目上泛化性不足。但对253号本身的端到端验证影响较小（因为标定和验证用的是同一组数据）。

**缓解措施**：
1. **明确验证范围**：本次验证只验证253号案例的端到端检索，不验证泛化性。泛化性是后续工作。
2. **留一交叉验证**：用10个Q中的9个标定权重，第10个做验证，轮换10次，评估权重的泛化性。
3. **后续扩展**：验证通过后，用更多案例（其他题目的QA序列）扩展Pattern库，重新标定权重和容差。
4. **权重初始化策略**：如果10个数据点标定7维权重不稳定，先用均匀权重（所有维度等权），再用253号数据微调。

### 7.3 端到端验证失败但单元验证通过

**风险**：P0和P1的每个原语单独验证都通过（单元验证通过），但端到端跑完253号Q8案例时，系统没有选中Q8——某层输出传到下一层时误差累积或接口不匹配。

**概率**：中——多模块集成的经典问题，单元测试通过不代表集成测试通过。

**影响**：高——端到端验证是本次验证的核心目标，失败意味着检索机制的整体设计可能有问题。

**缓解措施**：
1. **逐层定位**：端到端失败时，逐层检查输出——第一层输出是否正确？第二层接收到的第一层输出是否正确？以此类推，定位失败发生在哪一层。
2. **接口契约**：每个模块明确定义输入输出格式（dataclass），单元测试时用真实格式，避免接口不匹配。
3. **中间结果检查点**：每层输出后保存中间结果（到ArangoDB），可以单独检查和重跑某一层。
4. **误差容忍**：如果某层输出有小误差但后续层能容忍（如activation-score排序中Q8排第2而非第1，但pattern-matching仍能选中Q8），端到端仍可能通过。定义各层的误差容忍度。
5. **分层通过标准**：即使端到端未完全通过，如果第一层和第二层各自通过（Q8在候选列表中），只是第三层决策错误（选中了Q9而非Q8），可以定位问题在第三层并针对性改进。

### 7.4 constrained-policy的进展估计需要数学理解

**风险**：258号缺口4指出，constrained-policy需要在"不理解数学内容"的情况下估计每个候选Pattern的进展潜力。如果"Q8指向估计D的下界"这个判断需要数学理解，知识悖论没有被完全破解。

**概率**：中——本文档提出了"Pattern自带进展标签"的破解方案（RHS中标注义务ID，constrained-policy只做义务匹配），但这个方案需要H图初始化时人工标注义务ID。

**影响**：高——如果进展估计需要数学理解，constrained-policy的整个设计理念（形式匹配而非内容理解）就不成立。

**缓解措施**：
1. **义务ID匹配方案**：在H图初始化时，每条规则的RHS标注"解决O_t中的哪个义务"（义务ID）。constrained-policy只做义务ID匹配——A7后O_t中有"估计D的下界"(open)，Q8的RHS标注"解决OBL_估计D下界"，匹配成功。不需要理解数学。
2. **验证义务匹配的充分性**：如果义务ID匹配能正确选中Q8（而非Q9），说明形式匹配方案有效。如果义务ID匹配无法区分Q8和Q9（两者的RHS都指向"估计D下界"），需要增加更细粒度的区分条件。
3. **降级方案**：如果义务ID匹配不足，用Pattern自带的"适用性描述"（自然语言）做辅助判断——但这就引入了内容理解，需要承认知识悖论没有被完全破解。

### 7.5 LLM解析的增量误差累积

**风险**：260号§5.4指出增量解析的策略——每轮基于上一轮六元组做增量更新。10轮增量更新后，六元组的累积误差可能导致A7后的状态与Gold Standard偏差较大。

**概率**：中——每轮增量更新可能引入小误差（如V_t中遗漏早期条目），多轮后误差累积。

**影响**：中——A7后的六元组不准确会影响activation-score的特征提取和constrained-policy的进展估计。

**缓解措施**：
1. **每5轮全量校准**：260号§5.4.3建议每5轮做一次全量解析（传入完整历史），与增量解析结果对比。A5后做一次校准，A10后再做一次。
2. **V_t只增不减约束**：在prompt中强调"V_t只增不减，不要删除已有条目"，防止LLM在增量更新中遗忘早期已验证事实。
3. **A7单独全量解析**：A7是端到端验证的关键轮次，对A7做全量解析（传入A1-A6完整历史而非仅六元组），确保A7后的状态准确。
