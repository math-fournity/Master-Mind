## §1 为什么需要这个操作手册

### 1.1 问题背景

POC方案文档（如415号）定义了"应该怎么做"，执行记录（如POC-2.7-001）记录了"实际怎么做"。随着执行推进，两者会出现差异：

- 方案文档声明用v1方案，执行中发现v1有缺陷改用v2，但方案文档没更新
- 方案文档写了`nohup ... &`启动命令，违反全局AGENTS.md§12 tmux优先铁律
- 执行记录只报告了最终结果，没有记录环境检查/监控纪律/git commit等执行约束的遵守情况
- 执行记录用小样本结论代替全量判定，没有对照§7.1通过标准做正式判定

这些差异如果不审计、不修正，会导致：
1. **未来AI按过时的方案文档执行**——用v1方案、用nohup启动，重复已发现的错误
2. **执行记录不可审计**——无法追溯环境检查是否做过、监控是否执行、产物是否commit
3. **结论的样本量不足就下最终判定**——10题样本的90%成功率被当作919题全量的结论

### 1.2 操作手册的定位

本手册定义的流程不是"重新执行POC"，而是"审计POC方案文档与执行记录之间的一致性，修正发现的差异"。

**审计 ≠ 重做**——不重新跑实验，不重新分析数据，只检查文档之间的内部一致性。

**修正 ≠ 重写**——不重写方案文档或执行记录，只修正发现的差异点（如v1→v2、nohup→tmux、补充缺失的执行约束记录）。

## §2 审计的9个检查项

### 2.1 方案文档检查（3项）

| 检查ID | 检查项 | 检查什么 | 通过标准 |
|---|---|---|---|
| PLAN-001 | tmux优先铁律 | 方案文档中是否有`nohup ... &`用法 | 无nohup（全局AGENTS.md§12） |
| PLAN-002 | method声明与代码一致性 | 方案文档声明的默认method（v1/v2）是否与代码`--method`默认值一致 | 一致 |
| PLAN-003 | 规模估算与method匹配性 | 方案文档声明默认v2时，规模估算章节是否包含v2的估算 | 包含 |

### 2.2 执行记录检查（6项）

| 检查ID | 检查项 | 检查什么 | 通过标准 |
|---|---|---|---|
| REPORT-001 | 环境检查记录 | 是否记录了ArangoDB/D盘/devin cli的环境检查 | 3项全有 |
| REPORT-002 | 监控纪律记录 | 是否记录了tmux session/results.json/proof.md/log的监控 | ≥3项 |
| REPORT-003 | git commit记录 | 是否记录了commit历史（hash+内容+涉及文件） | 有commit历史表 |
| REPORT-004 | 对照通过标准判定 | 是否对照§7.1通过标准做判定，区分样本结论与全量判定 | 引用§7.1 + 区分样本/全量 |
| REPORT-005 | 引用修正后的流程 | 是否引用§10.7修正后的选题流程（Pipe 1在完整thinking上重新分析） | 引用§10.7 + 说明Pipe 1重做 |
| REPORT-006 | 不终止已启动run纪律 | 是否记录了§9.6"不终止已启动的run"纪律 | 有记录 |

### 2.3 检查状态定义

| 状态 | 含义 | 处理 |
|---|---|---|
| PASS | 检查通过 | 无需处理 |
| WARN | 部分通过/信息不完整 | 建议补充 |
| FAIL | 不通过/缺失 | 必须修正 |
| SKIP | 不适用/无法检查 | 跳过 |

## §3 标准操作流程（SOP）

### 步骤1：准备

```bash
# 确认要审计的三个文件存在
ls "Tell分类学研究过程文档/415-v0-2026-08-18-POC-2.7-截断vs思维错误.md"  # 方案文档
ls "POC-2.7/POC-2.7-001-完整进度报告.md"                                   # 执行记录
ls "Tell分类学研究过程文档/poc_assets/poc_2.7/batch_continue_948.py"       # 执行代码

# 检查git状态（记录before_status_baseline）
git status --short "Tell分类学研究过程文档/415-v0-2026-08-18-POC-2.7-截断vs思维错误.md" "POC-2.7/POC-2.7-001-完整进度报告.md"
```

### 步骤2：运行审计脚本

```bash
cd ~/master-mind-glm5.2-worktree

.venv/bin/python3 "POC-2.7/audit_poc_doc_vs_execution.py" \
    --plan "Tell分类学研究过程文档/415-v0-2026-08-18-POC-2.7-截断vs思维错误.md" \
    --report "POC-2.7/POC-2.7-001-完整进度报告.md" \
    --code "Tell分类学研究过程文档/poc_assets/poc_2.7/batch_continue_948.py"
```

脚本输出：
- 终端：每个检查项的PASS/WARN/FAIL/SKAP状态 + 行号定位 + 修正建议
- 退出码：有FAIL=1，只有WARN/PASS=0

### 步骤3：分析审计结果

根据脚本输出的FAIL和WARN项，确定需要修正的内容：

| 审计结果 | 修正动作 |
|---|---|
| PLAN-001 FAIL（有nohup） | 把方案文档中的`nohup ... &`改为`tmux new-session -d -s <name> "..."` |
| PLAN-002 FAIL（method不一致） | 更新方案文档的method声明，或修改代码默认值 |
| PLAN-003 WARN（规模估算缺v2） | 补充v2方案的规模估算 |
| REPORT-001 FAIL/WARN（缺环境检查） | 在执行记录中补充环境检查章节 |
| REPORT-002 FAIL/WARN（缺监控记录） | 在执行记录中补充监控纪律章节 |
| REPORT-003 FAIL/WARN（缺commit记录） | 在执行记录中补充git commit历史表 |
| REPORT-004 FAIL/WARN（缺通过标准判定） | 在执行记录中补充§7.1通过标准对照判定 |
| REPORT-005 FAIL/WARN（缺修正流程引用） | 在执行记录中补充§10.7修正后选题流程引用 |
| REPORT-006 WARN（缺不终止纪律） | 在执行记录中补充§9.6不终止run纪律记录 |

### 步骤4：执行修正

**原则**：
- 只修正审计发现的FAIL和WARN项，不做其他改动
- 方案文档的修正要说明"为什么改"（如"v1→v2因为918/919题原始prompt禁止工具调用"）
- 执行记录的补充如果是事后回溯，要明确标注"事后补充记录"

**修正顺序**：
1. 先修正方案文档（PLAN-xxx项）——因为执行记录的修正可能引用方案文档的新内容
2. 再修正执行记录（REPORT-xxx项）

### 步骤5：验证修正

```bash
# 重新运行审计脚本，确认所有FAIL项已修正
.venv/bin/python3 "POC-2.7/audit_poc_doc_vs_execution.py" \
    --plan "Tell分类学研究过程文档/415-v0-2026-08-18-POC-2.7-截断vs思维错误.md" \
    --report "POC-2.7/POC-2.7-001-完整进度报告.md" \
    --code "Tell分类学研究过程文档/poc_assets/poc_2.7/batch_continue_948.py"
```

**验证标准**：
- 所有FAIL项变为PASS或WARN（WARN可接受，FAIL不可接受）
- 退出码为0

### 步骤6：commit

```bash
# 只add修正过的文件（禁止git add -A）
git add "Tell分类学研究过程文档/415-v0-2026-08-18-POC-2.7-截断vs思维错误.md" \
        "POC-2.7/POC-2.7-001-完整进度报告.md"

# commit（说明修正了哪些审计项）
git commit -m "$(cat <<'EOF'
415号方案文档+POC-2.7-001修正：v2默认方案+tmux启动+执行约束记录

[修正的审计项列表]

Generated with [Devin](https://devin.ai)

Co-Authored-By: Devin <158243242+devin-ai-integration[bot]@users.noreply.github.com>
EOF
)"

# 验证git clean状态
git status --short "Tell分类学研究过程文档/415-v0-2026-08-18-POC-2.7-截断vs思维错误.md" "POC-2.7/POC-2.7-001-完整进度报告.md"
```

### 步骤7：记录审计结果

在执行记录中追加审计结果章节（如§11执行约束遵守记录），包含：
- 审计脚本的输出汇总（PASS/WARN/FAIL计数）
- 每个FAIL/WARN项的修正内容
- 修正后的commit hash

## §5 审计脚本的技术细节

### 5.1 脚本位置

```
POC-2.7/audit_poc_doc_vs_execution.py
```

### 5.2 脚本用法

```bash
# 完整审计（方案文档+执行记录+代码）
python3 audit_poc_doc_vs_execution.py \
    --plan <方案文档路径> \
    --report <执行记录路径> \
    --code <代码文件路径>

# 只审计方案文档
python3 audit_poc_doc_vs_execution.py --plan <方案文档路径>

# 只审计执行记录
python3 audit_poc_doc_vs_execution.py --report <执行记录路径>

# 输出JSON结果
python3 audit_poc_doc_vs_execution.py \
    --plan <方案文档> --report <执行记录> \
    --json <输出路径>
```

### 5.3 检查项的实现逻辑

| 检查ID | 实现方式 |
|---|---|
| PLAN-001 | 正则搜索`\bnohup\b`和`\btmux\s+(new-session\|...)` |
| PLAN-002 | 正则搜索方案文档中`本POC\s*(使用\|默认使用)\s*v[12]方案`，与代码中`default.*v[12]`对比 |
| PLAN-003 | 找规模估算章节，检查是否包含`v2方案\|2\s*pipe\|慢.*2倍`关键词 |
| REPORT-001 | 搜索`docker.*arangodb`、`/data/...`、`which\s+devin`三个模式 |
| REPORT-002 | 搜索`tmux\s+list-sessions`、`results\.json.*增长`、`proof\.md.*生成`、`log.*异常`四个模式 |
| REPORT-003 | 搜索commit hash（7-40位hex）、`git\s+commit`、commit历史表、`git\s+log` |
| REPORT-004 | 搜索`§7\.1\|通过标准`、`样本.*正式判定\|样本.*全量` |
| REPORT-005 | 搜索`修正后的选题流程\|§10\.7`、`Pipe\s*1.*重新分析` |
| REPORT-006 | 搜索`不终止.*run\|§9\.6` |

### 5.4 脚本的局限性

1. **正则匹配可能有假阳性/假阴性**——如方案文档中引用了nohup但只是为了说明"禁止用nohup"，脚本会误报FAIL。需要人工复核。
2. **不检查语义一致性**——如方案文档说"5轮"但代码写`max_rounds=3`，脚本不检查这种数值不一致。
3. **不检查文档结构的完整性**——如方案文档是否包含§0-§10所有章节，脚本不检查。
4. **依赖文档中有明确的关键词**——如执行记录中写了"环境检查"但没有实际命令，脚本可能判PASS。

**建议**：脚本用于快速发现常见差异，人工复核确认后再修正。

## §6 适用范围

本操作手册和审计脚本适用于：

1. **POC方案文档与执行记录的差异审计**——如415号与POC-2.7-001的审计
2. **POC执行过程中的中期审计**——执行到一半时检查方案文档是否需要更新
3. **POC完成后的归档审计**——确保方案文档和执行记录一致后再归档

**不适用于**：
- POC实验本身的科学性审计（如样本量是否足够、对照设计是否合理）
- 代码逻辑的正确性审计（如截断检测逻辑是否正确）
- 数据质量的审计（如export文件是否完整）

## §7 维护规则

- **新增检查项时**：在脚本中添加新的`check_xxx()`函数，在`audit_plan_document()`或`audit_report_document()`中调用，在本手册§2的检查项表中添加一行
- **检查项逻辑变更时**：更新脚本中的正则模式，更新本手册§5.3的实现逻辑说明
- **首次审计案例的记录**：在本手册§4中记录首次审计的修正内容，作为未来审计的参考
