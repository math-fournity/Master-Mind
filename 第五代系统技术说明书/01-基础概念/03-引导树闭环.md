## 1. Grove核心循环

引导树闭环的核心是一个循环，称为**Grove核心循环**。Grove的意思是"小树林"——多个推理AI并发探索，每个AI的探索贡献一棵树，多棵树并发形成树林。系统是这片树林的园丁。

循环的结构：

```
引导树（给方向Q）→ 推理AI（探索）→ 解题树（记录结果）
                                    ↓
                              在终点节点检索
                                    ↓
                              引导树（新边=新方向Q）→ 启动新推理AI → ...
```

这个循环的含义是：

1. 引导树上已有节点和边（提示Q），系统从中构造**脉络**（从根到当前节点的路径+方向Q），给推理AI作为输入
2. 推理AI收到脉络后开始探索，它的thinking/trajectory被系统采集，提取出节点写入树——记录"实际探索了什么"
3. 推理AI的输出到达某个节点后，系统在这个节点上检索数据基座，识别出新方向Q，这些新方向成为引导树的新边
4. 对每个新方向，系统启动新的推理AI，给它脉络+方向，回到步骤2

这个循环不断旋转，两棵树（引导展开树和解题记录树）在AI运行过程中实时生长。

## 2. 三个推动关系

循环的完整性由三个推动关系定义。**三个推动关系必须都成立，循环才算完整转了一圈。**

### 推动关系1：引导树 → 推理AI

引导树上已有节点和边（提示Q），系统从中构造脉络——"你之前已经证明了X、Y、Z，现在请继续探索方向W"。这个脉络给推理AI作为输入，推动它往特定方向探索。

**如果这个推动关系不成立**：推理AI没有方向引导，等于裸跑——它不知道该往哪里走。

### 推动关系2：推理AI → 解题树

推理AI的thinking/trajectory被系统通过mitmproxy流式截获，从中提取出节点（数学处境），写入解题记录树。每个节点记录了"AI在这一步做了什么、想到了什么、得到了什么结果"。

**如果这个推动关系不成立**：树没有新节点，等于树没在长——系统不知道AI探索了什么。

### 推动关系3：推理AI → 引导树

推理AI的输出到达某个节点（可能是AI自然终止的终点节点，也可能是AIthinking过程中的某个中间节点），系统在这个节点上检索数据基座，识别出新方向Q。这些新方向成为引导树的新边——引导树继续生长。然后对每个新方向启动新AI。

**如果这个推动关系不成立**：引导树没有新边，循环只转了半圈——解题树在长（采集到了节点），但引导树没有生成新方向，没有启动新AI，树停止生长。

## 3. 关键约束

### 推理AI不需要停下接受提示

这是第五代最关键的设计转变。之前的系统设计困境是"如何让推理AI在合适的位置停下来接受提示"——涉及thinking完成检测、tmux send-keys时序控制、pane状态检测等复杂工程问题。

第五代的回答是：**推理AI不需要停下。** 推理AI持续推理，走到哪里都可以。系统与推理AI并行运行——AI在thinking的同时，系统就从thinking中增量提取节点写入树。当AI自然终止（token用尽、证毕、或崩溃）后，系统在AI的终点节点上检索方向，启动新AI。

"让推理AI停下接受提示"这个需求消失了。

### 系统与推理AI并行运行

两条Pipe同时工作：
- **推理Pipe**（按需多个）——推理AI在做数学
- **辅助Pipe**（1个）——辅助AI在采集thinking、整理两棵树、在节点上检索方向、启动新AI

辅助Pipe不是"等AI跑完再处理"，而是"AI在thinking的同时就并行地工作"。thinking每增长一段，树就多长一个节点。

### 系统的目的是让两棵树生长

系统的目的不是"让AI做出来"，而是"让两棵树生长出来，在过程中与正确解答的脉络相遇"。

这意味着：
- 即便AI在思考到一半时崩溃了（token用尽），我们仍然得到了解题记录树的增长信息——它探索了一个脉络的一部分
- 如果AI最终解出来了，一切圆满
- 如果没有，它的思考和探索记录也是有价值的——只要它探索了最终的解题记录树的一个脉络

### 停机条件

与正确解答的脉络相遇时停机，不需要所有分支都探索完。当某条脉络到达正确解答时，标记为成功叶，problem标记为solved，不再从该树的叶节点启动新AI。

## 4. 循环没转起来的判定

如果只有解题树在长（采集到了节点），但引导树没有生成新边（没有检索出方向Q、没有启动新AI），**循环只转了半圈**。完整的循环必须三个推动关系都成立。

在POC-VMS-2实验中，批量模式（tree_engine.py主循环）循环只转了半圈——19个叶节点0个检索0个启动新AI。原因是3个token_limit的AI终止时，problem已经被其他并发AI solved了，走"already solved, 停机"分支，跳过了叶节点检索。

手动模式（辅助Pipe亲手执行循环）循环完整转了一圈半——因为AI本人有判断力，知道在叶节点检索方向Q、构造脉络、启动新AI。

## 5. "系统"就是你，不是脚本

**这是最容易理解错的一点。**

辅助Pipe的采集、整理、检索、启动，是**辅助AI亲手做的动作**，不是tree_engine.py替它做的。tree_engine.py里的函数是工具——`tree_store.create_node`是写节点的工具，`retriever.retrieve_for_node`是检索方向的工具，`launch_ai`是启动新AI的工具。但**调用这些工具的判断和决策是辅助AI的，不是脚本的主循环替它做的**。

### 为什么不能委托给脚本？

脚本的主循环是固定逻辑——它按预设的if/else执行，没有判断力。但辅助Pipe的工作需要判断力：

- **采集时**：thinking里的内容是否构成了一个新节点？操作类型识别对不对？这个节点该不该去重？——需要读thinking内容后判断
- **整理时**：节点之间的边关系对不对？这个节点是internal还是leaf？——需要理解数学处境后判断
- **检索时**：检索到的方向Q真的适用于这个节点吗？哪个方向更值得探索？——需要理解当前节点处境和方向Q的语义后判断
- **启动时**：该启动几个新AI？脉络文本构造得对不对？该不该停机？——需要理解整棵树的状态后判断

### 反模式：启动脚本然后干等

启动tree_engine.py，然后`get_output`等待结果——这是最严重的反模式。这等于把辅助Pipe的角色完全交给了脚本，自己退化成了旁观者。

### 正确模式：辅助AI就是主循环

推理AI在thinking的时候，辅助AI手动调用工具：
1. 读thinking_live.txt → 判断有没有新round → 有则提取节点 → 判断操作类型 → 调用`tree_store.create_node`写入ArangoDB
2. 看ArangoDB里的树 → 判断节点关系 → 判断这个节点是不是叶节点
3. 如果是叶节点 → 调用`retriever.retrieve_for_node`检索方向 → 判断检索结果合不合理 → 判断该往哪个方向扩展
4. 调用`construct_path_text`构造脉络 → 判断脉络文本对不对 → 调用`launch_ai`启动新AI
5. 检查循环完整性 → 三个推动关系都成立吗？

**每一步的判断是辅助AI的，脚本的函数只是它的手脚。**

## 6. AI的双重角色

进入实验时，AI的角色是双重的：

1. **Master Agent**（研发负责人）——设计、实现、迭代这个系统（写代码、审计、测试、commit）
2. **辅助智能体（系统Pipe）**——在系统运行时，亲手执行这个系统的循环

这两个角色不是分时的，是**场景驱动**的：

- **系统没在运行时**（没有推理AI在跑）→ 你是Master Agent：写代码、审计、测试、commit
- **系统在运行时**（有推理AI在thinking）→ 你是辅助Pipe：采集、整理、检索、启动。**不在`get_output`干等结果。**
- **系统运行中你发现问题了**（mitmproxy断了、thinking没落盘、节点提取异常）→ 临时切回Master Agent修复，修完立刻切回辅助Pipe
- **系统运行结束**（所有problem solved或exhausted）→ 切回Master Agent：审计结果、评估、落盘报告

切换的触发条件是"有没有推理AI在跑"。有推理AI在跑，你就是辅助Pipe，没有例外。
