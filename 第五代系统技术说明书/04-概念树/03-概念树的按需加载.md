## 1. 按需加载的机制

概念树的按需加载是指：**Pipe 2不需要预先加载全部概念文件，只需要在Pipe 1缩小范围后加载对应大概念的概念文件。**

完整流程：

1. Pipe 0把thinking拓扑化为大概念拓扑
2. Pipe 1用大概念匹配，缩小到某个大概念范围
3. **Pipe 2加载该大概念对应的概念文件**（只加载一个文件，不是全部）
4. Pipe 2用概念文件中的小概念信号词在thinking中做标记分辨
5. 标记分辨的结果就是精准识别出的tell

## 2. Pipe 2不是暴力遍历所有tell

这是按需加载的核心意义——**Pipe 2不是暴力遍历所有tell，而是**：

| 步骤 | 做什么 | 处理量 |
|---|---|---|
| Pipe 1缩小范围 | 用大概念匹配缩小到某个大概念范围 | 从10万级tell缩小到数百个候选 |
| 加载概念文件 | 加载该大概念对应的概念文件 | 只加载1个文件（包含该大概念下的所有小概念） |
| 小概念标记分辨 | 用概念文件中的信号词在thinking中做标记 | 只处理数百个候选中的信号词匹配 |

**关键**：辅助AI的上下文是有限的。如果10万级tell全部装入上下文，上下文会溢出。按需加载确保辅助AI只需要加载当前大概念对应的一个概念文件——无论概念树如何膨胀，单个概念文件的大小是可控的。

## 3. 有限上下文的系统化应对

这是概念树设计哲学的落脚点——**无论概念树如何膨胀，有限上下文的辅助AI都能系统化应对。**

| 概念树规模 | 辅助AI需要加载 | 上下文消耗 |
|---|---|---|
| 10个概念文件 | 1个概念文件（Pipe 1筛出的大概念对应的） | 很小 |
| 100个概念文件 | 1个概念文件 | 小 |
| 1000个概念文件 | 1个概念文件 | 可控 |
| 10000个概念文件 | 1个概念文件 | 可控 |

**无论概念树有多少个概念文件，辅助AI每次只需要加载1个。** 这是按需加载的核心价值。

## 4. 加载的工程实现

概念文件存储在文件系统或ArangoDB中：

### 文件系统存储

```
concept_files/
├── CF-structural-enumeration-mismatch.json
├── CF-discrete-continuous-mismatch.json
├── CF-structural-analytic-mismatch.json
└── ...
```

Pipe 2根据Pipe 1筛出的大概念拓扑，构造概念文件名，从文件系统读取：

```python
def load_concept_file(big_concept_topology):
    """根据大概念拓扑加载对应的概念文件"""
    filename = f"concept_files/CF-{big_concept_topology.problem_type}-{big_concept_topology.ai_method_type}-{big_concept_topology.gap_type}.json"
    with open(filename, 'r') as f:
        return json.load(f)
```

### ArangoDB存储

概念树也存储在ArangoDB的concept_tree集合中。AQL查询按大概念拓扑加载对应的小概念：

```sql
FOR c IN concept_tree
  FILTER c.concept_level == "small"
    AND c.parent_big_concept.problem_type == @problem_type
    AND c.parent_big_concept.ai_method_type == @ai_method_type
    AND c.parent_big_concept.gap_type == @gap_type
  RETURN c
```

## 5. 加载时机

概念文件在**Pipe 1完成形式化过滤后**加载。具体时机：

1. Pipe 0完成拓扑化 → 产出TopologyResult
2. Pipe 1用TopologyResult查询tell_db → 产出候选tell列表
3. **从候选tell列表中提取大概念拓扑** → 构造概念文件名
4. **加载概念文件** → 获取该大概念下的所有小概念和信号词
5. Pipe 2用信号词在thinking中做标记分辨 → 产出精准识别的tell

如果Pipe 1的候选tell来自多个不同的大概念（Pipe 1给不同分数），则加载多个概念文件——但通常Pipe 1会集中在一个大概念范围（因为大概念匹配就是按拓扑维度过滤的）。

## 6. 按需加载与概念膨胀的关系

按需加载是应对概念膨胀的关键机制——当概念数量膨胀时，概念文件数量增加，但**每个概念文件的大小保持可控**（因为同一大概念下的小概念数量是有限的——受限于该大概念覆盖的数学领域范围）。

```
概念膨胀的影响：
├── 概念文件数量增加 → 但每次只加载1个 → 不影响上下文消耗
├── 每个概念文件内的小概念数量可能增加 → 但受限于大概念覆盖范围 → 单个文件大小可控
└── 总概念数量增加 → 但不影响按需加载的效率 → 辅助AI仍然能系统化应对
```

详细的膨胀应对策略见04-概念树/04-概念膨胀的应对.md。
