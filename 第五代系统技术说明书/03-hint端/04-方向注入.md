## 1. 方向注入的机制

方向注入是将hint注入新AI的输入，启动新推理AI在全新Session中走新分支的过程。

完整的方向注入流程：

1. 系统在推理AI的某个节点上识别出tell（通过Pipe 0/1/2）
2. 从tell关联到hint方向（通过tell_db的hint_ids字段）
3. 构造脉络（从根到当前节点的路径+方向Q）
4. 通过solver-harness启动新的devin cli实例
5. 新AI在全新工作目录中运行，收到脉络+方向
6. 新AI开始探索，产生新的thinking
7. 系统采集新AI的thinking，提取节点写入树（推动关系2）
8. 循环继续

## 2. 新Session继承脉络不共享context

方向注入的一个关键约束是：**新AI在全新的Session中运行，不共享原AI的context。**

这是**回溯铁律**的要求——禁止在同一个Session中让AI回溯到某个思路岔口。必须启动新Session，重放Q序列到岔口，在岔口换方向。

原因：
1. **压缩边界风险**——同一Session中回溯会导致context混乱，AI无法区分"之前的思路"和"新的思路"
2. **context污染**——之前思路的推理输出已经进入context，回溯后这些输出会干扰新方向的推理
3. **不可逆性**——AI的推理过程一旦发生，其输出已经影响了对问题的理解，无法在同一Session中"假装没想过"

新Session通过脉络继承解决了这些问题——新AI有一个干净的context，只包含到岔口为止的脉络+方向Q，不包含被回溯的分支。

## 3. 并发DFS的方向注入

并发DFS是第五代的核心展开策略——识别N个tell→匹配N个hint→启动N个新AI→每个走一个方向→并发探索。

### 串行DFS vs并发DFS

| 维度 | 串行DFS | 并发DFS |
|---|---|---|
| 探索方式 | 一次一个方向，走不通回溯 | 同时多个方向，并发探索 |
| 回溯 | 需要新Session重放Q序列 | 不需要回溯——每个方向独立推进 |
| 资源消耗 | 1个推理AI | N个推理AI（N=识别出的tell数） |
| 时间效率 | 串行，慢 | 并发，快 |
| Context污染 | 回溯时有风险 | 无回溯，无污染 |
| 决策点 | 走不通后回溯到岔口选下一个方向 | 多个方向同时走，哪个先成功用哪个 |

并发DFS根本不需要回溯——每个方向从一开始就是独立的Session，独立的推理AI，独立的context。不存在"回溯到岔口"的操作，因为岔口的每个分支都已经有一个独立的探索者在走了。

### 工程实现

每个并发分支通过solver-harness启动一个独立的devin cli实例，在独立的工作目录中运行：

```
/data/math-agent-glm5.2-tmux-agents-dir/
├── experiment-001/                    # 主实验（bare AI）
├── experiment-001-branch-A/           # 并发分支A（tell-1对应的方向）
├── experiment-001-branch-B/           # 并发分支B（tell-2对应的方向）
└── experiment-001-branch-C/           # 并发分支C（tell-3对应的方向）
```

每个分支独立运行，独立记录，独立保留。成功了的结果回收到主实验目录，失败了的结果也保留（用于分析为什么这个方向走不通）。

## 4. 方向注入vs静态hint

POC-VMS-8的关键对比证明了方向注入（脉络继承+方向注入）优于静态hint：

| 方式 | 给AI什么 | 成功率 |
|---|---|---|
| 静态hint（abstract组） | 题目开头给一次"翻译到另一种语言" | 0/3 = 0% |
| 静态hint（dictionary组） | 题目开头给一次完整字典 | 1/6 = 17% |
| 静态hint（matched组） | 题目开头给一次匹配的具体翻译 | 2/6 = 33% |
| **方向注入（tree组）** | **脉络+方向，新AI从转折点继续** | **2/3 = 67%** |

静态hint的问题：
1. AI不知道在**什么时候**用hint——开头给一次，AI可能走了完全不同的路径，到不了需要翻译的点
2. AI不知道**是否该用**hint——静态给一次，AI可能忽略它

方向注入的优势：
1. 脉络把AI引导到**转折点之前**的位置——AI不需要自己走到那里
2. 脉络中明确标注了"从这里继续，探索以下方向"——AI知道这是转折点

## 5. 方向注入的工程实现

方向注入通过solver-harness启动新devin cli实例实现：

```python
def launch_new_ai(problem_id, entry_node, direction_q, lineage_text):
    """启动新推理AI，给它脉络+方向"""
    exp_id = f"{problem_id}-branch-{branch_counter}"
    
    # 1. 通过solver-harness启动新devin cli实例
    solver_harness.launch(
        exp_id=exp_id,
        problem_file=problem_file,
        model="glm-5-2",
        agents_md_template="templates/solver_agents_md_guided.md",  # guided模板含hint.txt读取指令
        extra_prompt=lineage_text  # 脉络+方向作为额外prompt
    )
    
    # 2. 在ArangoDB注册新AI实例
    ai_instance = tree_store.create_ai_instance({
        "problem_id": problem_id,
        "entry_node_key": entry_node.key,
        "entry_edge_key": new_edge.key,
        "lineage_text": lineage_text,
        "hint_q": direction_q,
        "status": "running"
    })
    
    # 3. 创建新边（引导树长出新边）
    new_edge = tree_store.create_edge({
        "_from": entry_node.key,
        "_to": None,  # 新节点在新AI产出后创建
        "problem_id": problem_id,
        "hint_q": direction_q,
        "ai_instance_id": ai_instance.key
    })
    
    return ai_instance
```

## 6. 注入时序

方向注入的时序是：**推理AI自然终止后在终点节点检索方向→构造脉络→启动新AI。**

这是第五代的关键设计——不需要让推理AI停下来接受提示。

| 阶段 | 推理AI在做什么 | 系统在做什么 |
|---|---|---|
| AI运行中 | thinking、推理、写证明 | 采集thinking、提取节点写入树 |
| AI终止 | 自然终止（token_limit/证毕/崩溃） | 在终点节点检索方向（Pipe 0/1/2） |
| 新AI启动 | （已终止） | 构造脉络→启动新AI→新AI开始探索 |

系统与推理AI**并行运行**——AI在thinking的同时系统就在采集和整理树，不需要等AI终止才开始工作。AI终止后系统在终点节点做检索和启动新AI，这是推动关系3的实现。
