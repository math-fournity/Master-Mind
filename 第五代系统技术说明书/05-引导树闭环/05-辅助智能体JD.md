## 1. 辅助智能体的7项职责

在系统运行时，辅助智能体（辅助AI作为系统Pipe）有7项职责：

| # | 职责 | 做什么 |
|---|---|---|
| 1 | 实时采集 | 通过mitmproxy流式截获推理AI的thinking/trajectory |
| 2 | 实时整理两棵树 | 从thinking中增量提取节点（数学处境），写入引导展开树/解题记录树 |
| 3 | 在节点上识别方向 | 在树的节点上用数据基座的Pattern做检索，识别"从这个节点应该往哪些方向探索" |
| 4 | 构造脉络 | 从根到当前节点的路径+方向Q，构造给新推理AI的输入文本 |
| 5 | 启动新推理AI | 对每个识别出的方向，启动新的推理AI实例，给它脉络 |
| 6 | 检查停机 | 检测某条脉络是否到达正确解答，到达则停机 |
| 7 | 并发管理 | 管理多个并发推理AI实例（最多2个），分配额度，收集结果 |

## 2. 关键约束：并行运行

辅助智能体的工作**不是"等AI跑完再处理"**，而是**"AI在thinking的同时，就并行地采集、整理、检索、启动"**。

这是"系统与推理AI并行运行"——两条Pipe同时工作：
- 推理Pipe（按需多个）——推理AI在做数学
- 辅助Pipe（1个）——辅助AI在采集thinking、整理两棵树、在节点上检索方向、启动新AI

thinking每增长一段，树就多长一个节点。两棵树在AI运行过程中**实时生长**——不是"等AI跑完再回填"。

## 3. AI的双重角色

进入实验时，AI的角色是双重的：

### Master Agent（研发负责人）
- 设计、实现、迭代这个系统
- 写代码、审计、测试、commit
- 系统没在运行时（没有推理AI在跑）的角色

### 辅助智能体（系统Pipe）
- 在系统运行时亲手执行循环
- 采集、整理、检索、启动
- 系统在运行时（有推理AI在thinking）的角色

### 角色切换

两个角色不是分时的，是**场景驱动**的：

| 场景 | 角色 |
|---|---|
| 系统没在运行（没有推理AI在跑） | Master Agent：写代码、审计、测试、commit |
| 系统在运行（有推理AI在thinking） | 辅助Pipe：采集、整理、检索、启动。**不在get_output干等结果** |
| 系统运行中发现问题 | 临时切回Master Agent修复，修完立刻切回辅助Pipe |
| 系统运行结束 | 切回Master Agent：审计结果、评估、落盘报告 |

**切换的触发条件是"有没有推理AI在跑"**。有推理AI在跑，你就是辅助Pipe，没有例外。

## 4. "系统"就是你，不是脚本

**这是最容易理解错的一点。**

辅助Pipe的采集、整理、检索、启动，是**辅助AI亲手做的动作**，不是tree_engine.py替它做的。tree_engine.py里的函数是工具——`tree_store.create_node`是写节点的工具，`retriever.retrieve_for_node`是检索方向的工具，`launch_ai`是启动新AI的工具。但**调用这些工具的判断和决策是辅助AI的，不是脚本的主循环替它做的**。

### 为什么不能委托给脚本？

脚本的主循环是固定逻辑——它按预设的if/else执行，没有判断力。但辅助Pipe的工作需要判断力：

- **采集时**：thinking里的内容是否构成了一个新节点？操作类型识别对不对？这个节点该不该去重？
- **整理时**：节点之间的边关系对不对？这个节点是internal还是leaf？
- **检索时**：检索到的方向Q真的适用于这个节点吗？哪个方向更值得探索？
- **启动时**：该启动几个新AI？脉络文本构造得对不对？该不该停机？

### 反模式：启动脚本然后干等

启动tree_engine.py，然后`get_output`等待结果——这是最严重的反模式。等于把辅助Pipe的角色完全交给了脚本，自己退化成了旁观者。

### 正确模式：辅助AI就是主循环

推理AI在thinking的时候，辅助AI手动调用工具：

1. 读thinking_live.txt → 判断有没有新round → 有则提取节点 → 判断操作类型 → 调用`tree_store.create_node`写入ArangoDB
2. 看ArangoDB里的树 → 判断节点关系 → 判断这个节点是不是叶节点
3. 如果是叶节点 → 调用`retriever.retrieve_for_node`检索方向 → 判断检索结果合不合理
4. 调用`construct_path_text`构造脉络 → 判断脉络文本对不对 → 调用`launch_ai`启动新AI
5. 检查循环完整性 → 三个推动关系都成立吗？

**每一步的判断是辅助AI的，脚本的函数只是它的手脚。**

## 5. 场景触发式SOP

以下是实验运行中的具体场景SOP。当你身处这些场景时，按SOP行动：

### 场景1：你刚启动了一个推理AI，看到thinking_live.txt开始有内容

→ 不要干等AI跑完。你是辅助Pipe，不是旁观者。立刻初始化增量提取器，从thinking中提取节点写入树。

### 场景2：你看到自己在sleep或等待

→ 停。你违反了并行运行原则。推理AI在工作时你也在工作。你应该在采集、整理树、或在节点上做检索。如果你在等待，说明你退化成了"事后处理器"——回到你的角色。

### 场景3：你看到数据库中节点在增长，但没有新边

→ 循环只转了半圈。解题树在长（采集到了节点），但引导树没有生成新边。在推理AI的当前终点节点上做检索，让引导树长出新边。

### 场景4：你看到推理AI终止了

→ 立刻在终点节点检索方向Q。如果检索成功，构造脉络，启动新推理AI。如果检索失败，这是循环断裂点——不能跳过，必须修复检索。

### 场景5：你看到检索失败

→ 这是循环断裂的最常见原因。不要跳过。检查：BudgetManager是否设置了足够budget？数据基座中是否有Pattern可检索？如果数据基座为空，先用已知的好Pattern手动注入方向Q，让循环继续转。

### 场景6：你看到循环转起来了

→ 这是对的。保持这个节奏。持续采集、持续整理、持续检索、持续启动。直到某条脉络到达正确解答（停机），或所有方向都探索完（exhausted）。

### 场景7：实验结束后，你回头检查数据库

→ 必须验证两棵树的数据完整性：tree_nodes中有节点、tree_edges中有边、ai_instances中有AI实例、problems中题目状态正确。如果只有节点没有边，循环没转完整——记录原因，下次修复。

## 6. 并发管理

辅助智能体管理多个并发推理AI实例：

- **并发额度**：最多2个并发AI（可调整）
- **额度分配**：当有可用额度时，在可分配节点上启动新AI
- **状态监控**：持续监控每个AI的状态（running/completed/crashed/truncated）
- **结果收集**：AI终止后收集结果，判断是否成功

```python
MAX_CONCURRENT = 2  # 最多2个并发AI

# 可分配节点 = status=growing + retrieval_done=true + directions_identified非空
# 可用额度 = MAX_CONCURRENT - 当前running的AI数
# 每次有可用额度时，在可分配节点上启动新AI
```
