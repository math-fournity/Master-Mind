## 1. 三个推动关系总览

引导树闭环的完整性由三个推动关系定义。三个推动关系必须都成立，循环才算完整转了一圈。

```
推动关系1：引导树 → 推理AI
     （构造脉络，给推理AI作为输入）
                    ↓
推动关系2：推理AI → 解题树
     （采集thinking，提取节点写入树）
                    ↓
推动关系3：推理AI → 引导树
     （在节点上检索方向Q，引导树长出新边）
                    ↓
              启动新推理AI → 回到推动关系1
```

## 2. 推动关系1：引导树 → 推理AI

引导树上已有节点和边（提示Q），系统从中构造**脉络**——从根到当前节点的路径+方向Q。这个脉络给推理AI作为输入，推动它往特定方向探索。

### 脉络的构造

脉络通过`construct_path_text`函数构造（详见03-hint端/03-脉络继承.md）。脉络文本包含：
- 题目原文
- 从根到当前节点的每个节点的处境描述
- 每个节点已证明的结论和当前表示
- 方向Q（给新AI的探索方向）

### 如果这个推动关系不成立

推理AI没有方向引导，等于裸跑——它不知道该往哪里走。虽然裸跑AI也可能碰巧走对方向，但系统失去了引导能力——树的生长方向不受控制。

## 3. 推动关系2：推理AI → 解题树

推理AI的thinking/trajectory被系统通过mitmproxy流式截获，从中提取出节点（数学处境），写入解题记录树。每个节点记录了AI在这一步做了什么、想到了什么、得到了什么结果。

### 节点提取的过程

1. mitmproxy流式截获推理AI的thinking（token级，~0ms延迟）
2. thinking_live.jsonl按round分组，每个round对应一个思维操作
3. `node_extractor.py`的`identify_operation`识别每个round的操作类型（读题/计算/推理/验证/...）
4. `tree_store.create_node`将节点写入ArangoDB的tree_nodes集合

### 节点的数据结构

每个节点包含：
- node_type：root/internal/leaf_success/leaf_deadend/leaf_truncated
- situation：数学处境（六元组状态）
- situation_text：处境的自然语言描述
- depth：在树中的深度
- path_from_root：从根到本节点的路径（冗余存储加速脉络构造）
- created_by_ai：贡献这个节点的推理AI实例ID
- trajectory_segment：本节点对应的trajectory片段
- status：growing/completed/deadend/truncated
- retrieval_done：系统是否已在此节点做过检索
- directions_identified：检索识别出的方向Q的ID列表

### 如果这个推动关系不成立

树没有新节点，等于树没在长——系统不知道AI探索了什么。后续的检索和启动新AI都没有基础——没有节点就没有检索的起点。

## 4. 推动关系3：推理AI → 引导树

推理AI的输出到达某个节点（通常是AI自然终止的终点节点），系统在这个节点上检索数据基座，识别出新方向Q。这些新方向成为引导树的新边——引导树继续生长。然后对每个新方向启动新AI。

### 检索的过程

1. 推理AI终止（token_limit/crash/solution_found/manual_stop）
2. 获取AI的最后一个节点（叶节点）
3. 在叶节点上做检索：
   - Pipe 0拓扑化：把AI的thinking编码为拓扑结构
   - Pipe 1形式化过滤：用大概念匹配缩小tell范围
   - Pipe 2小概念标记分辨：在同分候选中精准识别
4. 识别出tell后，从tell关联到hint方向
5. 标记叶节点retrieval_done=True，记录directions_identified
6. 对每个方向，构造脉络，启动新AI

### 如果这个推动关系不成立

引导树没有新边，**循环只转了半圈**——解题树在长（采集到了节点），但引导树没有生成新方向，没有启动新AI，树停止生长。

这是POC-VMS-2批量模式中出现的情况——19个叶节点0个检索0个启动新AI。原因是3个token_limit的AI终止时，problem已经被其他并发AI solved了，走"already solved, 停机"分支，跳过了叶节点检索。

## 5. ArangoDB schema

三个推动关系的数据存储在ArangoDB的4个集合中：

### tree_nodes集合（document类型）

每个节点是一个数学处境。字段包括：_key, problem_id, node_type, situation, situation_text, depth, parent_edge_key, path_from_root, created_by_ai, created_at, trajectory_segment, status, retrieval_done, directions_identified, ai_instances_started。

### tree_edges集合（edge类型）

每条边是一个提示Q。字段包括：_key, _from, _to, problem_id, hint_q, hint_q_id, hint_level, ai_instance_id, created_at, edge_status。

### problems集合（document类型）

每道题一棵树。字段包括：_key, problem_text, root_node_key, status, solution_path, created_at, solved_at, total_nodes, total_edges, ai_instances_used。

### ai_instances集合（document类型）

每个推理AI实例的注册信息。字段包括：_key, problem_id, entry_node_key, entry_edge_key, 脉络文本, hint_q, tmux_session, devin_session_id, status, started_at, ended_at, end_reason, trajectory_dir, nodes_contributed。

详细的schema定义见07-工程规格/05-ArangoDB-schema.md。

## 6. AQL查询模板

### 获取某棵树的所有节点

```sql
FOR node IN tree_nodes
  FILTER node.problem_id == @problem_id
  RETURN node
```

### 获取从根到某节点的路径（脉络构造）

利用path_from_root冗余字段直接获取，无需递归查询：

```sql
FOR node IN tree_nodes
  FILTER node._key == @node_key
  RETURN node.path_from_root
```

### 获取所有可分配新AI的节点

```sql
FOR node IN tree_nodes
  FILTER node.problem_id == @problem_id
    AND node.status == "growing"
    AND node.retrieval_done == true
    AND node.directions_identified != []
  RETURN node
```

### 获取某棵树的成功路径

```sql
FOR node IN tree_nodes
  FILTER node.problem_id == @problem_id
    AND node.node_type == "leaf_success"
  RETURN node.path_from_root
```

详细的AQL查询模板见07-工程规格/06-AQL查询模板.md。
