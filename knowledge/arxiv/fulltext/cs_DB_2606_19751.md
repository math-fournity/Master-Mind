## Abstract

DeQL (Decision Query Language) extends SQL to express decision queries: given options drawn from relational data, constraints from policy, and a measurable objective, a DeQL query computes the best course of action. Two constructs carry the extension: CREATE CANDIDATES, which defines the space of options from relational sources, and DECIDE, which declares decision variables, named constraints, and an objective over them. The design follows SQL's principles: the user states what to optimize while the engine chooses how to solve it, every query consumes and produces relations, and the structure of a problem stays visible to the engine. This document specifies the language (its design principles, syntax, formal grammar, and execution model) with examples spanning subset selection, allocation, assignment, scheduling, and decisions at multiple levels of aggregation, and extensions for optimization under uncertainty, inline model scoring, and time- and quality-bounded solving. It is the first version of the specification; the language is under active development, and this version fixes the core constructs on which later revisions will build.

## 1Introduction

Data systems today answer two broad kinds of question.Descriptivequeries report what the data records: SQL joins and aggregates over warehouses and lakehouses answer “what happened?”Predictivequeries, increasingly expressed inside the database through in-database machine learning, estimate “what will happen?” A third kind,prescriptive, asks what todo: which routes to activate, how much capacity to allocate to each workload, which items to select under a budget, when to schedule each task. These aredecision queries: given options drawn from relational data, constraints from policy, and a measurable objective, a decision query computes the best course of action. SQL has no construct for them; expressing one means dropping to a separate solver or modeling tool and encoding the formulation by hand. DeQL (Decision Query Language, pronounced “dee-kwl”) extends SQL to express decision queries declaratively.

The design rests on four principles inherited from SQL.
- •

Declarative separation.The user stateswhatto optimize (the variables, constraints, and objective) and the engine determineshowto solve it, choosing a mathematical formulation and an algorithm (Section˜11).
- •

Relational closure.A decision query consumes relations and produces a relation. Decisions are data, so results compose with SQL and with further decision queries, asCREATE TABLE AScomposes in SQL.
- •

Preserved structure.DeQL keeps a decision problem’s structure visible to the engine: which entities a decision concerns, how decisions are grouped, and which decisions each constraint involves stay explicit in the query. The engine reads this structure to recognize problems it can solve with specialized, efficient algorithms (Section˜11).
- •

Conservative extension.DeQL reuses SQL’s keywords and semantics wherever they apply, so a reader fluent in SQL meets few new concepts and existing SQL operations behave unchanged.

These principles distinguish DeQL from modeling languages such as AMPL[7], Pyomo[9], and JuMP[6], which express a chosen formulation over parameters extracted into a separate modeling environment. DeQL operates on relational data directly and offers a small set of composable primitives (typed variables, grouped and filtered constraints, and joins that relate decisions made at different levels of aggregation;Section˜2) that users combine, rather than a fixed catalogue of problem templates. It builds on PaQL[1], which introduced declarative package queries, and SolveDB[11], which integrated solvers into SQL; DeQL generalizes package selection to typed decision variables and grouped constraints and leaves the choice of formulation to the engine.

This document specifies the DeQL language; the Decisionhouse vision paper[4]presents the system that executes it (its architecture, compilation pipeline, and research agenda), and the DeQL Studio demonstration[3]shows it in use. The remainder specifies the language and its example queries (Section˜2onward), the formal grammar (Section˜10), the execution model (Section˜11), and the current scope and limitations (Section˜12). This is the first version of the specification: it fixes the core constructs, and we expect the language to grow as the system and its applications mature.

## 2The DeQL Language

This section introduces DeQL with one decision query end to end; the sections that follow specify its constructs in turn, andSection˜9collects example queries.

## 2.1A Decision Query at a Glance

Making a decision in DeQL involves two statements:CREATE CANDIDATESdefines the options, and aDECIDEquery chooses among them. ## 3Defining Candidates

## 3.1CREATE CANDIDATES

CREATE CANDIDATESdefines the decision domain from relational sources. Like a view, it is defined by a query rather than populated directly; like a table, it is a named relation thatDECIDEqueries reference. Beyond both, it carries decision-specific structure: aDECISION KEY, and optionally decision columns and constraints.⬇CREATECANDIDATES<name>DECISIONKEY(<column_list>)AS<select_query>;

TheDECISION KEYspecifies which columns identify a single decision entity; the system instantiates one set of decision variables per distinct value. Just as aPRIMARY KEYfixes row identity for storage, theDECISION KEYfixes decision identity for optimization, and like aPRIMARY KEYits columns must genuinely identify a row: non-NULLand unique, so the defining query yields at most one row per value and functionally determines every other column. A candidate that violates this is rejected at materialization with the offending values reported; the defining query must collapse duplicates itself (e.g., withDISTINCTorGROUP BY).

Example.Shipping routes as candidates:⬇CREATECANDIDATESshipping_routesDECISIONKEY(wh_id,store_id)ASSELECTr.from_whASwh_id,r.to_storeASstore_id,w.capacity,s.demand,r.cost,r.time_hrsFROMroutesrJOINwarehouseswONr.from_wh=w.wh_idJOINstoressONr.to_store=s.store_id;

The candidate definition accepts any SQL query supported by the underlying system. A candidate set is a first-class object the system owns: it chooses the physical representation (virtual, in-memory, or persisted) by query complexity and reuse, and the structures derived from the candidates, such as the clustering abstractions used for decomposition (Section˜3.3), are attached to it and shared across the queries that reference it.

A flat join of warehouses, stores, and routes does not say whether a decision is made per warehouse, per store, or per route;DECISION KEY (wh_id, store_id)fixes it at one decision per warehouse-store pair, and from there governs how many variables are created, how constraints group, and how results map back to tuples.

A per-column grain (theBYclause ofSection˜4.2) sets how coarsely a single column is decided. TheDECISION KEY, in contrast, grains the entire candidate set, and it gives DeQL three properties a per-column grain alone does not provide. (Modeling languages take the other route, indexing each variable family on its own set, as invar x{Sites, Hours}in AMPL.) First, data columns derive their grain from it: inshipping_routes,costis single-valued per warehouse-store pair, so a per-row constraint over it instantiates once per pair. Second, the key is an integrity constraint:DECISION KEY (wh_id, store_id)asserts one decision per warehouse-store pair, and a defining query that produces two rows for a pair is rejected rather than silently double-counted. Third, it fixes the result’s shape, one row per key value (or the chosen subset, for aSELECTIONdecision), and is what aFOREIGN DECISION KEYreferences when decisions compose across candidate sets (Section˜6.1).

WhereDECISION KEYsays what each decision isabout,DECISION COLUMNSdeclares what isdecidedfor it. An optionalDECISION COLUMNSclause can be included directly inCREATE CANDIDATESto declare default decision columns at the schema level:⬇CREATECANDIDATESshipping_routesDECISIONKEY(wh_id,store_id)DECISIONCOLUMNS(activeSELECTIONBINARY,quantityCONTINUOUSBETWEEN0ANDcapacity)ASSELECT...;

WhenDECISION COLUMNSis declared at the schema level,DECIDEqueries can omit variable declarations and inherit them from the candidate definition.

## 3.2Schema-Level Constructs

CREATE CANDIDATEScan include schema-levelDECISION COLUMNSandCONSTRAINTSblocks that are automatically enforced in anyDECIDEquery referencing the candidates.⬇CREATECANDIDATESitem_batch_assignmentsDECISIONKEY(item_id,batch_id)FOREIGNDECISIONKEY(batch_id)REFERENCESbatch_timing(batch_id)AStDECISIONCOLUMNS(assignedSELECTIONBINARY,batch_load=SUM(weight*assigned)REFERENCESbatch_timing(batch_id))CONSTRAINTS(one_batch:SUM(assigned)=1BYitem_id,batch_cap:batch_load<=capacity)ASSELECT...;
- •

Plain decision columns, declared exactly as in aDECIDEquery (e.g.,assigned SELECTION BINARY).
- •

Derived decision columnsuse=syntax to define a variable whose value is determined by an aggregate over related rows. For example,batch_load = SUM(weight * assigned)withREFERENCES batch_timing(batch_id)creates a batch-level variable equal to the sum of assigned item weights. TheREFERENCESclause specifies which foreign candidate table the derived variable belongs to.
- •

CONSTRAINTSdeclares structural constraints that are always enforced. Schema-level constraints are immutable: they cannot be overridden or relaxed inDECIDEqueries. Structural constraints that always hold are declared once in the schema, while problem-specific business constraints go inDECIDEqueries. For example, a workforce scheduling schema might enforce that no employee works more than one shift at a time, a physical impossibility rather than a business preference.

## 3.3Candidate Abstractions

CREATE ABSTRACTIONdefines a coarser view of a candidate set by grouping candidates into representative clusters. An abstraction lets the engine solve a reduced problem over the representatives and then refine within promising groups, trading bounded optimality loss for scalability on large candidate sets (Section˜11).⬇CREATEABSTRACTIONassignment_clustersONgpu_assignments(cost,demand,capacity)USINGKMEANS(k=1000);

TheONclause names the candidate set and the columns used for clustering; theUSINGclause names the clustering method and its parameters (kk-means into 1000 groups here). An abstraction is a derived object, much like a database index: it does not alter the candidate set, andDECIDEqueries continue to reference the original candidates. Where an index returns the same answer faster, an abstraction returns a faster approximate one, at the bounded optimality loss above.

## 4The DECIDE Query

## 4.1The DECIDE Statement

TheDECIDEstatement is the core prescriptive query. It optimizes over a candidate set and returns a result relation. The result extends the candidate columns with the declared decision columns, populated with the optimal assignment. Its anatomy:⬇DECIDE<result_name>FROM<candidate_ref>[JOIN...][DECISIONCOLUMNS(<variable_declarations>)][WHERE<filter_predicate>]SUBJECTTO<constraint_list>[MINIMIZE|MAXIMIZE<objective_expression>];
- •

FROMreferences one or more candidate sets, each either a named set created byCREATE CANDIDATESor a table or subquery given an inlineDECISION KEY.
- •

DECISION COLUMNSdeclaresdecision columns: new columns of the result, one per candidate entity, whose values the engine computes (thedecision variables). Each declares a name, type (BINARY,INTEGER,CONTINUOUS), optionalSELECTIONmodifier, optional bounds (BETWEENℓ\ellANDuu), and an optionalBYgrain (Section˜4.2).
- •

WHEREfilters candidates before optimization (predicate pushdown: candidates not satisfying the predicate are excluded from the decision domain). The predicate may reference only data columns; decision columns have no values until the query is solved.
- •

SUBJECT TOintroduces the constraint block: a comma-separated list of constraints, each optionally named.
- •

MINIMIZE/MAXIMIZEspecifies the objective function as an aggregate expression over candidate columns and decision variables. The objective must have the empty grain, i.e., denote a single value: an ungrouped aggregate, or terms built fromBY ()variables and constants (Section˜4.2). The objective is optional: aDECIDEwith noMINIMIZEorMAXIMIZEis a feasibility query, returning any solution that satisfies the constraints.

Example.Shipping plan with mixed variables:⬇DECIDEshipping_planFROMshipping_routesDECISIONCOLUMNS(activeSELECTIONBINARY,quantityCONTINUOUSBETWEEN0ANDcapacity)WHEREtime_hrs<=48SUBJECTTOCONSTRAINTsupply_limit:SUM(quantity)<=capacityBYwh_id,CONSTRAINTmeet_demand:SUM(quantity)=demandBYstore_idMINIMIZESUM(cost*quantity);

TheSELECTION BINARYmodifier onactiveprovides auto-multiply, auto-link, and auto-bound semantics (Section˜4.3).

Inline candidate sets.A candidate set named withCREATE CANDIDATEScan be reused across queries, can carry schema-level constraints enforced on every decision over it (Section˜3.2), and can be referenced by aFOREIGN DECISION KEY(Section˜6.1). When a decision is one-off and needs none of these, aDECIDEquery may define its options inline, attaching theDECISION KEYto a table or subquery, as PaQL[1]states the options and the decision in one query:⬇DECIDEcartFROM(SELECTproduct_id,price,ratingFROMCatalog)DECISIONKEY(product_id)DECISIONCOLUMNS(chosenSELECTIONBINARY)SUBJECTTOCONSTRAINTbudget:SUM(price)<=1000MAXIMIZESUM(rating);

Defining the candidate set by name parallels a view; inlining it parallels a subquery.

## 4.2Decision Column Grain

A decision column’sgrainis the set of columns that determine how many variables it expands into: one per distinct combination of their values. By default the grain is the candidate’sDECISION KEY, giving one variable per row. ABYclause instead groups the column likeGROUP BY, one variable per group:BY regiongives one variable per region,BY (region, zone)one per region-zone combination, andBY ()a single variable over the whole set. Because grain columns are data columns fixed by theDECISION KEY, aBYgrain is always coarser than the per-row default, never finer. The sameBYforms apply to grouped constraints (Section˜5.1). How many variables exist depends on the data: the groups are the distinct combinations present after theDECIDEquery’sWHEREfilter, a group with no surviving rows gets no variable, and aNULLin a grain column is an error (Section˜7).

Each column’s grain reads off itsBYclause; for a candidate set keyed on(region, sector, store):⬇DECISIONCOLUMNS(reservedCONTINUOUSBY(),--onevariabletotalquantityCONTINUOUSBYregion,--oneperregionamountCONTINUOUSBY(region,sector),--oneperregion-sectorspotCONTINUOUS)--oneperrow(thekey)

Grain is per column.ABYgrain sets how coarsely a single column is decided; theDECISION KEYstill identifies the decision and fixes the result shape at one row per key value (Section˜3.1). The key spans the whole candidate set, so different decision columns may carry different grains while sharing it.

Example.Reserve a baseline capacity per region, then meet each store’s demand from that reservation or from spot capacity:⬇CREATECANDIDATESstore_demandDECISIONKEY(region,store_id)ASSELECTregion,store_id,demand,spot_priceFROMStores;DECIDEplanFROMstore_demandDECISIONCOLUMNS(reservedCONTINUOUSBYregion,spotCONTINUOUS)SUBJECTTOCONSTRAINTmeet_demand:reserved+spot>=demandMINIMIZE50*SUM(reserved)+SUM(spot_price*spot);

reservedis one variable per region (BY region);spotis one per store. The per-row constraintreserved + spot >= demandapplies a region’s singlereservedto each store in it, andSUM(reserved)in the objective contributes one term per region, not one per store. The result has one row perDECISION KEYvalue, one per store; a coarse-grain variable appears constant within each of its groups, soreservedrepeats across a region’s stores (Table˜3) and is read back withSELECT DISTINCT region, reserved FROM plan. A grain that cross-cuts the key (say, a store tier spanning regions) repeats its value across every store of that tier, coupling stores in different regions. Grain of expressions.Every expression has a grain. A constant has the empty grain(); a data column has the fullDECISION KEYgrain, even when its values repeat; a decision column has its declared grain; and a scalar operator’s result has the union of its operands’ grains, so a coarser operand is broadcast across the finer ones, as aPARTITION BYvalue is present on every row of its partition. This applies to decision columns too: invar1 * var2withvar1coarser thanvar2, the singlevar1is broadcast onto each finervar2row. An aggregate’s result has the empty grain, or the grouping columns’ grain inside a constraint groupedBY(Section˜5.1). Aggregates do not nest, as in SQL.

Aggregation over grain.An aggregate ranges over the distinct values of its argument’s grain, not over the candidate rows. In the objective above,50 * reservedis a single term becausereservedhas grain(); written withreserved BY region,SUM(50 * reserved)contributes one term per region rather than one per hour. This extends the rule that decision variables are not duplicated across rows (Section˜6.1) to aggregates: a coarse variable summed over a finer candidate set is counted once per its own group.

Mixed grains.When the operands have different grains, the union rule above sets what the aggregate ranges over.SUM(demand * reserved)withreserved BY regionranges over the hours, becausedemandsits at the row grain, and each region’s single variable enters with coefficient equal to the total demand over that region’s hours. In general the aggregate runs once over each distinct combination of its argument’s grain, reading each operand at that combination. This row-weighted reading is usually the intent:SUM(hourly_rate * reserved)withreserved BY sitecharges the rate for every hour the reservation is held. When a charge should instead fall once per group, the cost column must sit on a candidate at that grain, as in the facility-location example (Section˜9.7).

Divergences from SQL.Two consequences follow that SQL does not share. An aggregate of a constant collapses to the constant:SUM(1)is 1, since a constant has grain(); useCOUNT(*)to count candidates. AndAVGover a coarse argument divides by the number of groups, not the number of rows.

## 4.3SELECTION Semantics

TheSELECTIONmodifier on a decision column applies three automatic transformations (desugaring rules detailed inTable˜4). PaQL[1]introduced the first, auto-multiply; DeQL adds auto-link and auto-bound.

Auto-multiply.Aggregates over data columns (columns from the candidate definition, not decision variables) are automatically multiplied by the selection variable. Withactive SELECTION BINARY:
- •

SUM(cost)in a constraint becomesSUM(cost * active)
- •

COUNT(*)becomesSUM(active)

Auto-link.Whenactive = 0, all companion decision variables for that entity are forced to zero. Forquantity CONTINUOUS BETWEEN 0 AND capacity, the system generates:quantity≤capacity⋅active\texttt{quantity}\leq\texttt{capacity}\cdot\texttt{active}.

Auto-bound.A positive lower bound applies only when the entity is selected. Forweight CONTINUOUS BETWEEN 0.01 AND 0.08, auto-bound generatesweight≥0.01⋅active\texttt{weight}\geq 0.01\cdot\texttt{active}; the upper sideweight≤0.08⋅active\texttt{weight}\leq 0.08\cdot\texttt{active}comes from auto-link.

Bounded repetition.ASELECTION INTEGERvariable counts how many copies of a candidate to take, with the range set by ordinary bounds:⬇DECISIONCOLUMNS(qtySELECTIONINTEGERBETWEEN0AND5)

This lets each candidate appear 0 to 5 times, the integer-multiplicity counterpart of PaQL’sREPEAT(Section˜12.2). Aggregates then count each copy:COUNT(*)becomesSUM(qty), andSUM(cost)becomesSUM(cost * qty).

Result rows.Beyond rewriting constraints,SELECTIONshapes the result: a candidate whose selection variable is0is omitted, so aDECIDEquery with aSELECTIONcolumn returns the selected subset, one row per chosen candidate, generalizing PaQL’s package semantics. ## 4.4Composability

DECIDEcreates a standard table (analogous toCREATE TABLE AS). This enables three forms of composition:

SQL on results.Decision results can be queried, joined, and aggregated with standard SQL:⬇SELECTwh_id,SUM(quantity)AStotal_shippedFROMshipping_planGROUPBYwh_id;

Decision chaining.The output of oneDECIDEbecomes input to another, enabling sequential decision-making:⬇CREATECANDIDATESsecond_stageDECISIONKEY(wh_id,store_id)ASSELECT*FROMshipping_planWHEREquantity>0;DECIDErefined_planFROMsecond_stage...;

CTE integration.ADECIDEcan be a named step in aWITHclause, so SQL steps and a decision step compose in one query. Below, one step forecasts demand in ordinary SQL, aDECIDEstep plans the restock within a budget, and a finalSELECTcombines the two:⬇WITHforecastAS(SELECTproduct_id,AVG(units_sold)ASdemandFROMsalesGROUPBYproduct_id),restockAS(DECIDEFROMrestock_candidatesDECISIONCOLUMNS(qtyINTEGERBETWEEN0ANDmax_qty)SUBJECTTOCONSTRAINTbudget:SUM(unit_cost*qty)<=50000MAXIMIZESUM(qty))SELECTf.product_id,f.demand,r.qtyFROMforecastfJOINrestockrONf.product_id=r.product_id;

ADECIDEwritten this way takes the step’s name as its result table. EachDECIDEis solved independently, and its result is an ordinary table to the rest of the query; two decisions in separate steps cannot share a constraint or objective, so coupling them requires a singleDECIDEover joined candidates (Section˜6.1).

The relational closure property (every DeQL operator consumes and produces relations) mirrors SQL’s composability, so decision queries compose into existing SQL pipelines.

## 5Constraints

## 5.1Constraint Syntax

Constraints in DeQL keep their structure visible: each may be named, grouped withBY, and filtered withFILTER. A name (CONSTRAINT supply_limit: ...) is optional; it supports governance (reporting which constraint was violated), debugging (relaxing a constraint and re-solving), and documentation. An unnamed constraint is written as its body alone.

Aggregate constraints, the most common form, follow the pattern:⬇CONSTRAINT<name>:<aggregate_expr>[FILTER(WHERE<predicate>)]<comparison_op><bound_expr>[BY<col_list>]

Aggregate constraints.Standard SQL aggregates (SUM,COUNT,MIN,MAX,AVG) over expressions involving candidate columns and decision variables:⬇CONSTRAINTbudget:SUM(price)<=100

Grouped constraints (BY).TheBYclause generates one constraint per group value, analogous toGROUP BY:⬇CONSTRAINTsupply_limit:SUM(quantity)<=capacityBYwh_id

With 10 warehouses, this generates 10 constraints, each bounding the total quantity shipped from one warehouse. The bound is evaluated per group, so every data column it references must be single-valued within each group (here,wh_idmust functionally determinecapacity); this is the same single-value rule SQL applies to non-grouped columns underGROUP BY, and a constraint whose bound varies within a group is rejected.

Filtered constraints (FILTER).TheFILTERclause restricts which candidates participate:⬇CONSTRAINTcap_tech:SUM(weight)FILTER(WHEREsector=’Technology’)<=0.25

BYandFILTERcompose:SUM(qty) FILTER (WHERE region = ’US’) <= limit BY categorygenerates one constraint per category, considering only US-region candidates.FILTERis distinct from the query-levelWHERE(Section˜4.1):WHEREremoves candidates from the whole problem, whereasFILTERscopes a single aggregate, so a candidate it excludes still exists and can participate in other constraints.

Per-row constraints.Expressions without aggregates generate one constraint instance per distinct value of the expression’s grain (Section˜4.2). When the operands are at the fullDECISION KEYgrain, this is one constraint per candidate row; coarser operands give one per group:⬇CONSTRAINTmeet_deadline:start_time+processing_time<=deadline

Scheduling constraints.Two constraint forms borrow the global-constraint semantics of constraint programming languages such as MiniZinc[10].DISJUNCTIVE(s,d)(s,d)takes a start timessand a durationddand forbids overlap: within each group, the half-open intervals[s,s+d)[s,\,s+d)are pairwise disjoint, so no two tasks on a machine run at once:⬇CONSTRAINTno_overlap:DISJUNCTIVE(start_time,processing_time)BYmachine

CUMULATIVE(s,d,r)(s,d,r)adds a per-task resource demandrrand bounds concurrent use: within each group, at every instantttthe totalrrover the tasks running then (s≤t<s+ds\leq t<s+d) is at most the bound:⬇CONSTRAINTresource_cap:CUMULATIVE(start_time,processing_time,demand)<=max_capacity

Each accepts aBYclause, asno_overlapgroups bymachine. NULLs.ANULLin the data, reached while materializing a coefficient, objective term, or bound, is an error that names the offending rows. The oneNULLthat is not an error is a window function’s value at a boundary (Section˜5.2), which drops that row’s constraint by design.

## 5.2Window Constraints

A constraint can relate a candidate’s decision to the decisions taken before or after it in an order, through SQL window functions over decision columns.LAGandLEADrefer to the previous and next row of anORDER BY, andFIRST_VALUEandLAST_VALUEto the first and last. The order is given by the window’sORDER BY, and any grouping by the constraint’sBYclause rather thanPARTITION BY. A production plan over time, with a per-product schedule ordered by period, exercises each:⬇DECIDEplanFROMproduction_planDECISIONCOLUMNS(produceCONTINUOUSBETWEEN0ANDmax_rate,inventoryCONTINUOUSBETWEEN0ANDwarehouse_cap)SUBJECTTOCONSTRAINTbalance:inventory=COALESCE(LAG(inventory)OVER(ORDERBYperiod),opening_stock)+produce-demandBYproduct,CONSTRAINTramp:LEAD(produce)OVER(ORDERBYperiod)-produce<=max_rampBYproduct,CONSTRAINTopening:FIRST_VALUE(inventory)OVER(ORDERBYperiod)>=safety_stockBYproduct,CONSTRAINTclosing:LAST_VALUE(inventory)OVER(ORDERBYperiod)>=safety_stockBYproductMINIMIZESUM(hold_cost*inventory+run_cost*produce);

Within each product, rows are taken inperiodorder.balancecarries inventory forward:LAG(inventory)is the previous period’s stock, and in the first period, where there is none,COALESCEsuppliesopening_stock.rampbounds the period-to-period increase throughLEAD(produce), which isNULLin the last period and dropsrampthere.openingandclosinghold the safety stock at the first and last periods, throughFIRST_VALUEandLAST_VALUE.

A window function carries anORDER BYand no frame (ROWSorRANGE) clause, andFIRST_VALUEandLAST_VALUErange over the whole ordered group. DeQL’s principle is to follow SQL’s window semantics; here it deliberately does otherwise forLAST_VALUE. Under SQL’s default frame an ordered window ends at the current row, so a framelessLAST_VALUEwould return that row rather than the group’s last. Because a constraint likeclosingmeans the final period’s stock, DeQL fixes the window to the whole group, makingLAST_VALUEthe last row of the order;FIRST_VALUEalready matches SQL, whose default frame begins at the first row.LAGandLEADdefault toNULL, which drops the boundary row’s constraint, or to an explicit 0, which retains it. Windowed aggregates such asSUM(...) OVER (ORDER BY ...)are also available for running totals.

## 6Multi-Granularity Decisions

## 6.1Joining Candidates in Decision Queries

Many problems decide at two levels of granularity at once. Batch manufacturing is typical: over a fixed set of items and batches, the plan both assigns items to production batches (a choice per item-batch pair) and schedules when each batch starts (a choice per batch). The two decisions share the same batches and are solved together.

BYalone already expresses this, by folding both levels into one candidate set:⬇CREATECANDIDATESassignmentsDECISIONKEY(item_id,batch_id)ASSELECTi.item_id,b.batch_id,i.weight,b.capacity,b.processing_timeFROMitemsiCROSSJOINbatchesb;DECIDEscheduleFROMassignmentsDECISIONCOLUMNS(assignedSELECTIONBINARY,start_timeCONTINUOUSBETWEEN0AND1440BYbatch_id)SUBJECTTOCONSTRAINTone_batch:SUM(assigned)=1BYitem_id,CONSTRAINTbatch_cap:SUM(weight*assigned)<=capacityBYbatch_idMINIMIZEMAX(start_time+processing_time);

This is expressible, but folding both levels into one candidate set duplicates the batch across the product. With 100 items and 10 batches,assignmentshas 1000 rows, and each batch’scapacity,processing_time, andstart_timerepeat across the 100 rows sharing itsbatch_id. There are only 10 batch-level start times, yetstart_timeis declared over all 1000 rows and collapsed back to one per batch withBY. The more a batch carries, the more of the query goes to replicating it and collapsing it back.

DeQL instead lets each level be its own candidate set, joined on the shared key:⬇CREATECANDIDATESassignmentsDECISIONKEY(item_id,batch_id)ASSELECTi.item_id,b.batch_id,i.weightFROMitemsiCROSSJOINbatchesb;CREATECANDIDATEStimingDECISIONKEY(batch_id)ASSELECTbatch_id,capacity,processing_timeFROMbatches;DECIDEscheduleFROMassignmentsaJOINtimingtONa.batch_id=t.batch_idDECISIONCOLUMNS(assignedSELECTIONBINARYONa,start_timeCONTINUOUSBETWEEN0AND1440ONt)SUBJECTTOCONSTRAINTone_batch:SUM(assigned)=1BYitem_id,CONSTRAINTbatch_cap:SUM(weight*assigned)<=capacityBYbatch_idMINIMIZEMAX(start_time+processing_time);

assignmentshas one row per item-batch pair;timinghas one row per batch. The join pairs them onbatch_id, and each batch’sstart_timeis one variable shared across the rows it joins to, not one per pair.

The query still produces a single result relation,schedule, not two: the join of the candidate sets with the decision columns filled in, one row per item-batch pair.assignedvaries by pair, while each batch’sstart_timeholds the same value across that batch’s rows. Like anyDECIDEresult, it is an ordinary relation that further SQL or decision queries can read.

Keeping the levels apart has two advantages over folding them together: a batch’s data and decisions live in their own table, one row per batch, instead of the data being repeated across every item-batch row and the batch variable recovered withBY; and the engine can solve the two separately keyed levels by decomposition (Section˜11).

ON clause.In a joinedDECIDE, each decision column is tagged withONto say which candidate table it belongs to, asassigned(ONa) andstart_time(ONt) are above; this tells the engine which key grains each variable.

FOREIGN DECISION KEY.Declares referential relationships between candidate tables at the schema level:⬇CREATECANDIDATESitem_batch_assignmentsDECISIONKEY(item_id,batch_id)FOREIGNDECISIONKEY(batch_id)REFERENCESbatch_timing(batch_id)ASSELECT...;

This enables the system to validate join structure and identify subproblems it can solve independently.

Design principle.Decision variables must not appear in JOIN conditions; they belong inSUBJECT TO. JOIN links candidate tables by data columns; constraints link their decision variables.

## 7Validity and Errors

Validity has a static part, checked on the query alone, and a data-dependent part, checked once the candidate data is read; a key with a duplicate value, or aNULLcoefficient, cannot be caught earlier. A conforming DeQL implementation enforces both, along three lines.First, it rejects what cannot be given a meaning.Three checks share one pattern, the single-value rule SQL applies to non-grouped columns underGROUP BY: theDECISION KEYmust functionally determine every candidate column (Section˜3.1), a grouped constraint’s bound must be single-valued within each group (Section˜5.1), and a coarse variable’s bounds must be single-valued within each grain group (Section˜4.2). ANULLreaching a grain column, coefficient, or bound is rejected for the same reason; and every constraint, and the objective, must reference at least one decision variable, since one that does not asserts a fact about the data rather than constraining the decision.Second, it rejects, in this version, combinations whose intended meaning is not yet specified.For instance, aFILTERpredicate that reads a column finer than the aggregated expression’s grain, which the union-grain rule would read as a per-row count rather than the intended “any matching row” test; precompute a same-grain flag inCREATE CANDIDATESinstead. A later revision may define and admit such cases, and restricting them now keeps existing queries valid when it does.Third, patterns that are well-defined but sometimes unintended execute with their documented meaning,with diagnostics flagging likely mistakes: a row-grain data column multiplying a coarse variable (Section˜4.2), or a coarse variable that spans several of a grouped constraint’s groups and is charged in full against each.

## 8Extensions

DeQL provides optional extensions for three needs beyond the core: optimization under uncertainty, inline model scoring, and time- and quality-bounded solving.

## 8.1Stochastic Constraints

Following SPaQL[2], DeQL supports stochastic constraints for optimization under uncertainty. The GPU allocation ofSection˜9.8took each workload’s demand as known; in practice it is uncertain. Uncertain data columns are declared with theSTOCHASTICfunction inCREATE CANDIDATES, specifying a distribution family and parameters drawn from base table columns:⬇CREATECANDIDATESgpu_assignmentsDECISIONKEY(pool_id,workload_id)ASSELECTa.pool_id,a.workload_id,p.capacity,a.cost,a.latency_ms,STOCHASTIC(’normal’,w.demand_mean,w.demand_std)ASdemandFROMassignmentsaJOINgpu_poolspONa.pool_id=p.pool_idJOINworkloadswONa.workload_id=w.workload_id;

Constraints over stochastic columns useWITH PROBABILITYto specify chance constraints, and the objective can useEXPECTEDto optimize in expectation:⬇DECIDEallocation_planFROMgpu_assignmentsDECISIONCOLUMNS(activeSELECTIONBINARY,quantityCONTINUOUSBETWEEN0ANDcapacity)WHERElatency_ms<=200SUBJECTTOCONSTRAINTpool_capacity:SUM(quantity)<=capacityBYpool_id,CONSTRAINTmeet_demand:SUM(quantity)>=demandBYworkload_idWITHPROBABILITY>=0.95MINIMIZEEXPECTEDSUM(cost*quantity);

TheWITH PROBABILITYclause on a constraint enforces it as a chance constraint: the system samples scenarios from the declared distributions and ensures the constraint holds with at least the specified probability.EXPECTEDon the objective optimizes the expected value across scenarios.

## 8.2Inline Model Scoring

PREDICTinvokes a registered model during candidate construction, inside theSELECTofCREATE CANDIDATES, to populate a data column from other columns. The model may be classical ML or an LLM;PREDICT(model,args) returns a scalar that then participates in constraints and objectives like any other data column, following thePREDICTpattern of BigQuery ML[8]. The budget-allocation example (Section˜9.6) scores expected ROI this way.

## 8.3Quality Modifiers

Quality modifiersWITHINandTIMEOUTon the objective clause grant the decision planner permission to trade solution quality for speed. Two modifiers are supported:⬇MINIMIZESUM(cost*quantity)WITHIN5%TIMEOUT30s

WITHINXX%asks the planner to stop once the solution is provably withinXX% of optimal; on its own, it bounds the optimality gap.TIMEOUTXXscaps solve time, returning the best feasible solution found withinXXseconds. Both modifiers are optional and compose: given both, the planner stops at whichever bound is reached first and reports the achieved gap, so a timeout that fires before the gap is proven returns the best solution found rather than a gap-bounded one. They enable the decision planner to select abstraction-based decomposition or approximation algorithms when solving exactly is impractical for large instances (Section˜11).

## 9.1Subset Selection (Knapsack)

## 9.4Assignment (Worker-Shift Matching)

Assign workers to shifts such that each worker gets at most one shift and each shift has exactly one worker, minimizing skill mismatch:⬇CREATECANDIDATESworker_shiftsDECISIONKEY(worker_id,shift_id)DECISIONCOLUMNS(assignedSELECTIONBINARY)ASSELECTw.worker_id,s.shift_id,ABS(w.skill_level-s.required_skill)ASmismatchFROMWorkerswCROSSJOINShiftssWHEREw.skill_level>=s.required_skill;DECIDEscheduleFROMworker_shiftsSUBJECTTOCONSTRAINTone_shift:COUNT(*)<=1BYworker_id,CONSTRAINTone_worker:COUNT(*)=1BYshift_idMINIMIZESUM(mismatch);

## 9.6Budget Allocation (ML Scoring)

## 9.7Facility Location (Multi-Granularity)

Decide which facilities to open (facility-level binary decision) and how much demand each facility serves for each customer (facility-customer-level continuous decision):⬇CREATECANDIDATESfacilitiesDECISIONKEY(facility_id)ASSELECTfacility_id,open_cost,capacityFROMFacilities;CREATECANDIDATESfacility_assignmentsDECISIONKEY(facility_id,customer_id)ASSELECTf.facility_id,c.customer_id,c.demand,t.transport_costFROMFacilitiesfCROSSJOINCustomerscJOINTransportCoststONt.facility_id=f.facility_idANDt.customer_id=c.customer_id;DECIDElocation_planFROMfacilitiesfJOINfacility_assignmentsaONf.facility_id=a.facility_idDECISIONCOLUMNS(openedBINARYONf,amountCONTINUOUSBETWEEN0ANDdemandONa)SUBJECTTOCONSTRAINTserve:SUM(amount)=demandBYcustomer_id,CONSTRAINTfacility_cap:SUM(amount)<=capacity*openedBYfacility_idMINIMIZESUM(open_cost*opened)+SUM(transport_cost*amount);

Theopenedvariable is indexed byfacility_id; theamountvariable is indexed by(facility_id, customer_id). The constraintSUM(amount) <= capacity * opened BY facility_idlinks the two levels: a closed facility serves no demand. The objective termSUM(open_cost * opened)is grain-scoped (Section˜4.2): each facility’s fixed cost is counted once, not once per customer it serves, becauseopen_costlives on the facility-grainfacilitiescandidate. Carried instead on the finerfacility_assignments, the sameSUMwould bill it once per customer served.

## 9.8Multi-Resource Allocation with QoS (GPU Scheduling)

The two resources, compute (pool_capacity) and memory (mem_capacity), are independent constraints groupedBYpool_id; a further resource is a further constraint, not a new construct.

## 11Execution Model

A DeQL query flows through three intermediate representations before producing a result relation, following a Three-IR design.

Theparser(a Rust-based SQL parser extension) tokenizes the query and producesAbstract IR, a normalized, symbolic, database-agnostic representation that preserves column references, symbolic expressions, constraint structure with grouping and filtering, and decision column declarations with their grains, together with each candidate’sDECISION KEY. Abstract IR encodes no algorithm choice and binds no data. Expression grains (Section˜4.2) are inferred on these surface expressions, before any algebraic simplification: rewriting can change a grain. Withcap BY site,SUM(cap)is one term per site, butSUM(cap * flag)withflaga data column ranges over the rows even whereflagis constantly 1, so eliminating the factor would change the result.

Thedecision planneranalyzes the Abstract IR through structure detection (e.g., recognizing network flow or total unimodularity from variable-constraint patterns) and formulation selection. The decision planner producesConcrete IR, which encodes the chosen mathematical formulation (still symbolic, using column references rather than actual values). Different formulations produce structurally different Concrete IRs from the same Abstract IR (e.g., generic MILP vs. LP relaxation vs. min-cost network flow).

Thematerializerfetches candidate data from the underlying sources and evaluates symbolic expressions against actual rows, producingMaterialized IR: an objective coefficient vector, a sparse constraint matrix, variable bounds, and type annotations. This is what the chosen backend receives. Theexecutordispatches the Materialized IR to a solver or algorithm suited to the formulation (a general-purpose LP/MILP solver for a coefficient matrix, a network-flow algorithm for a flow graph), then joins the resulting variable assignments back with candidate metadata to form the output relation. Backends are pluggable: the language commits to no solver, and the planner can target new ones as they are added.

The output is a standard relation that can be queried with SQL, joined with other tables, or fed as input to anotherDECIDEquery.

## 12Scope and Limitations

## 12.1Current Scope

DeQL’s scope follows from its architecture (Section˜11). Any problem stated as typed decision variables, constraints, and an objective over candidate relations is captured symbolically in the Abstract IR; finding a formulation and a solver or algorithm for it is the planner’s responsibility. The language therefore expresses a range of problems, including:
- •

Linear decision problems: subset selection, resource allocation, assignment, and scheduling, expressed withBINARY,INTEGER, andCONTINUOUSdecision variables, linear objectives and constraints, andSELECTIONdesugaring.
- •

Nonlinear and quadratic objectives and constraints: expressions in which decision variables are multiplied or divided, for example portfolio variance from a covariance term or cannibalization penalties in budget allocation. Expressions may be linear, quadratic, or nonlinear in the decision variables; selecting a solver or algorithm for them is the engine’s responsibility and lies outside this specification.
- •

Constraint programming constructs:DISJUNCTIVEandCUMULATIVEfor scheduling problems, which desugar to mixed-integer constraints (Section˜5.1).
- •

Extensions beyond the core: optimization under uncertainty (STOCHASTIC, chance constraints, expected objectives), inline model scoring (PREDICT), and time- and quality-bounded solving (WITHIN,TIMEOUT), each specified inSection˜8.

## 12.2Relationship to PaQL

DeQL is backward-compatible with PaQL[1]: every package query has aDECIDEequivalent. PaQL states the options and the package constraints in one statement. The query below builds a meal plan from gluten-free recipes, taking up to each recipe’s ownmax_servingsto meet a calorie floor at minimum fat; its DeQL translation follows.

PaQL:⬇SELECTPACKAGE(*)ASmeal_planFROMRecipesREPEATmax_servingsWHEREgluten=0SUCHTHATSUM(kcal)>=2000MINIMIZESUM(fat)

DeQL:⬇CREATECANDIDATESgluten_free_recipesDECISIONKEY(recipe_id)ASSELECTrecipe_id,kcal,fat,max_servingsFROMRecipesWHEREgluten=0;DECIDEmeal_planFROMgluten_free_recipesDECISIONCOLUMNS(servingsSELECTIONINTEGERBETWEEN0ANDmax_servings)SUBJECTTOCONSTRAINTcalories:SUM(kcal)>=2000MINIMIZESUM(fat);

Each PaQL clause has a DeQL counterpart.PACKAGE(*)corresponds to aDECIDEover a candidate set; PaQL’s tuple-levelWHEREto the candidate-definingWHERE; and each package-levelSUCH THATconstraint to a namedSUBJECT TOconstraint.REPEAT, which permits up to a given number of copies of a tuple, becomes aSELECTION INTEGERvariable with that number as its upper bound; here the bound is the data columnmax_servings, so each recipe is capped by its own value (a bound may reference data columns, evaluated per candidate). The keep-or-drop case (noREPEAT) isSELECTION BINARY, as in the cart ofSection˜2.1.SELECTIONthen supplies auto-multiply (Section˜4.3), so aggregates count with multiplicity:SUM(kcal)reads asSUM(kcal * servings)andCOUNT(*)asSUM(servings), a recipe takenkktimes contributingkk-fold, exactly PaQL’s package semantics.

DeQL also expresses problems beyond package selection. A grouped constraint such asSUM(weight) <= 20 BY category(theper_categoryconstraint ofSection˜9.1) has no PaQL form:SUCH THATstates a single constraint over the whole package, whereasBY(Section˜5.1) generates one per group. Filtered constraints (FILTER), companion decision variables with auto-link and auto-bound, multi-granularity joins (Section˜6.1), and continuous variables are likewise outside PaQL’s scope.

## 12.3Limitations and Future Work

These are outside the scope of this first version; each would extend the language with new constructs and semantics, and we expect to add them as DeQL matures:
- •

Multi-stage stochastic optimization.Problems where decisions alternate with uncertain observations (e.g., decide inventory levels, observe demand, adjust orders) require a recourse or dynamic programming framework beyond the current single-stage model. Deterministic sequential decisions are already supported via decision chaining (Section˜4.4).
- •

Lazy constraint generation.Some formulations have exponentially many constraints that a solver adds on demand during solving rather than stating up front, as with the subtour-elimination constraints of the traveling salesman problem[5]or with cutting planes. Generating constraints this way relies on solver callbacks the current language does not expose.
- •

Multi-objective optimization.The current language supports a single objective. An extension such asMINIMIZE (cost, -profit) PARETOwould return the Pareto frontier as a set of non-dominated solutions, each materialized as a separate result relation.
