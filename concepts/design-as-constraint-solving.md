# 系统设计即多约束求解（Design as Constraint Solving）

## 定义

AI数学工程系统的设计过程可以建模为一个多约束求解问题（CSP）：用可用的原语集合作为域，在系统需求、面相期望、已知局限等约束下，搜索满足所有约束的系统设计。

但这个CSP不是标准CSP——它是**开放世界CSP**：域在求解中扩展（发现新原语），约束在求解中演化（面相修正），解成为下一轮的约束（自举）。

## 来源

- **面相归属**：C（设计过程自举）+ B（知识选取——CSP框架来自计算机科学/运筹学）
- **出处**：246号对话中由用户提出原语=约束、系统设计=求解的映射，AI修正为原语=domain、并识别出开放世界CSP特性

## 指导了什么

- 指导了 facet-C（设计过程自举）的表述——CSP是自举循环的形式化语言
- 指导了"AI作为设计者"的角色定位——多约束求解是AI的核心能力，系统设计CSP是AI可以参与的
- 指导了原语目录的管理方向——原语是CSP的domain，domain的扩展性要求原语目录是living reference

## 适用边界

1. **CSP是隐喻不是等式**——系统设计不能被完全形式化为CSP（变量、域、约束都不完全可枚举）。CSP是用来理解设计过程的框架，不是用来自动求解的算法。
2. **开放世界特性使自动求解不可行**——标准CSP求解器假设domain和constraint固定。开放世界CSP没有现成求解器。AI作为"求解器"时，它做的是启发式搜索，不是精确求解。
3. **"解"不是唯一的最优解**——系统设计CSP的解空间很大，可能有很多满足约束的设计。没有"最优"，只有"够好"或"比上一代好"。

## 演化

### CSP schema的映射（246号对话中确认）

| CSP角色 | 系统设计中的对应 | 说明 |
|---|---|---|
| **域（domain）** | 可用原语集合 + 可能的架构 | 解的词汇表。通过发现新原语扩展（面相A/B） |
| **变量（variables）** | 设计决策：用哪些原语、怎么组合、什么角色 | 每个设计决策是一个变量，它的取值范围是domain中的原语 |
| **约束（constraints）** | 系统需求 + 面相期望 + 已知局限 + 验证状态 + 当前系统行为 | 解必须满足的条件。通过面相修正和新需求出现而演化 |
| **解（solution）** | 下一代系统设计 | 不是单个解，是解的轨迹——每代系统是上一代的解，也是下一代的约束 |

### 开放世界CSP的三个特性

1. **domain在求解中扩展**——求解过程中发现现有原语不够用，涌现/选取新原语。就像数学证明搜索中发现新引理——引理不是预先给定的，是搜索中产生的。

2. **constraint在求解中演化**——面相被修正（面相3修正面相1），新需求出现（发现需要处理某种新题型）。约束不是固定的，是动态的。

3. **解成为下一轮的约束**——自举。每代系统的行为成为下一代设计的约束之一。"上一代系统在这些题上表现如何"是设计下一代时的输入。

### CSP角色与现有分类的正交关系

```
              domain    constraint    solution
primitives      ✓          ×            ×
concepts        ✓(部分)    ✓(部分)       ×
criteria        ×          ✓             ×
facets          ×          ✓             ×
系统设计(每代)   ×          ×            ✓
```

CSP角色分类是"按东西在设计中扮演什么角色分类"，现有分类（primitives/concepts/criteria/facets）是"按东西是什么分类"。两者正交，不互相替代。

## 开放问题

1. **变量是什么**——CSP需要明确的变量。系统设计的"变量"是设计决策，但设计决策的粒度是什么？是"用不用Pipe"这种粗粒度，还是"Pipe的输入格式是什么"这种细粒度？
2. **约束的优先级**——所有约束等权吗？还是有些约束是硬约束（必须满足），有些是软约束（尽量满足）？验证状态可能决定优先级——tested原语构成的约束比untested的更硬。
3. **开放世界CSP有没有现成的形式化框架**——数学或CS中有没有研究"domain/constraint在求解中变化"的CSP变体？这可能值得搜索文献。
