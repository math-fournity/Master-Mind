## 0. 为什么建立本文档

321号建立了"提示词是核心资产"的认知。322-324号设计了VMS-28的提示词V1→V2→V3→V4。

但用户提出了一个更深层的设计思想：同一个Pipe阶段，我们可能有多套提示词——不是同一个提示词的不同版本号，而是**完全不同的一套提示词**。多套提示词并发给AI处理，结果汇总或各自流向下一个Pipe。

这个思想和解放思想原则（318号/principles.py）的"多个AI"维度一致——同一函数可以由多个AI实例并发执行。但这里更进一步——不只是多个AI实例用同一提示词，而是多个AI实例用**不同套的提示词**。

## 1. 核心思想

### 1.1 同一Pipe阶段可能有多套提示词

同一个Pipe阶段（如pipe_1_parser的step_2_grid_vein），我们可能有多套提示词：

- **套A**：用FCA/Hasse图启发的提示词（V4提示词就是这一套）
- **套B**：不用FCA，直接让AI用数学直觉做格化的提示词
- **套C**：用具体例子引导的提示词（举多个完整解答的格化例子）
- **套D**：用反模式引导的提示词（先告诉AI什么是对的，再告诉AI什么是错的）

这些不是同一个提示词的不同版本号——版本号是同一套提示词的改进（V1→V2→V3→V4）。**套**是完全不同的提示词设计——用不同的思路启发AI做同一件事。

### 1.2 多套提示词并发给AI处理

多套提示词可以并发给多个AI实例处理同一个输入：

```
同一个输入（如一道题的解答）
  ├── AI实例1 + 套A提示词 → 产出1
  ├── AI实例2 + 套B提示词 → 产出2
  ├── AI实例3 + 套C提示词 → 产出3
  └── AI实例4 + 套D提示词 → 产出4
```

### 1.3 结果的两种流向

多套提示词的产出有两种流向：

**流向1：汇总**
- 把多个产出汇总成一个——如取交集（多套提示词都识别出的trace更可靠）、取并集（多套提示词识别出的所有trace）、取加权平均（按提示词的验证状态加权）
- 适用于：trace识别——多套提示词各自识别trace，汇总后得到更完整的trace集合

**流向2：各自流向下一个Pipe**
- 不汇总，每个产出独立流向下一个Pipe——如每个产出独立做trace→tell匹配，独立驱动引导树生长
- 适用于：引导树生长——多套提示词各自驱动引导树长出不同的分支，让树更"妖娆"

### 1.3 和解放思想原则的关系

解放思想原则（principles.py）的三个维度：
1. 多种方式——同一函数多种实现
2. 多个AI——同一函数多个AI实例并发
3. 多个子pipe——函数拆分为子函数

多套提示词并发是"多个AI"维度的扩展——不只是多个AI实例用**同一提示词**，而是多个AI实例用**不同套提示词**。这让并发更有意义——不同套提示词产出的差异不是随机差异（同一提示词不同运行的差异），而是设计差异（不同提示词设计的差异），这些差异更有可能互补。

### 1.4 和反射原则的关系

多套提示词并发后，反射可以比较不同套提示词的效果：
- 哪套提示词产出的trace更准确？
- 哪套提示词产出的trace更全面？
- 哪套提示词产出的非局部trace更多？
- 汇总后的效果比单套好多少？

反射结果可以决定：保留效果好的套，淘汰效果差的套，或者改进某套提示词。

## 2. 提示词目录结构

### 2.1 目录设计

```
第六代系统提示词积累目录/
├── README.md                          # 说明文档
├── pipe_0_solver/                     # Pipe 0: Solver AI的提示词
│   ├── set_A/                         # 套A（脉络+方向Q）
│   │   ├── README.md                  # 这套提示词的设计思路
│   │   ├── v1.md                      # V1
│   │   └── v2.md                      # V2（如有改进）
│   └── set_B/                         # 套B（如有不同设计）
│       └── ...
├── pipe_1_parser/                     # Pipe 1: Parser AI的提示词
│   ├── step_1_analyze_vein/           # 步骤1：分析脉络
│   │   ├── set_A/

│   │   │   └── v1.md
│   │   └── set_B/

│   │   ├── set_A_fca_hassee/          # 套A：用FCA/Hasse图启发
│   │   │   ├── README.md              # 这套提示词的设计思路
│   │   │   ├── v1.md                  # V1（320号§2.3）
│   │   │   ├── v2.md                  # V2（322号§1）

│   │   │   └── v4.md                  # V4（324号§1）

│   │   │   ├── README.md

│   │   ├── set_C_example_guided/      # 套C：用具体例子引导
│   │   │   ├── README.md
│   │   │   └── v1.md
│   │   └── set_D_anti_pattern/        # 套D：用反模式引导

│   └── ...
├── pipe_3_guide/                      # Pipe 3: Guide AI的提示词
│   └── ...
└── step_5_branch/                     # 步骤5分叉的提示词
    ├── process_A/                     # 过程A
    │   └── ...
    └── process_B/                     # 过程B
        └── ...
```

### 2.2 目录命名规则

- **第一层**：Pipe阶段名（如`pipe_1_parser`）
- **第二层**：子pipe名（如`step_2_grid_vein`）——如果没有子pipe，省略这一层
- **第三层**：提示词套名（如`set_A_fca_hassee`）——格式为`set_<编号>_<简短描述>`
- **第四层**：版本文件（如`v1.md`、`v2.md`）+ `README.md`（这套提示词的设计思路）

### 2.3 每个套的README.md内容

```
# 套A：用FCA/Hasse图启发

## 设计思路
用FCA闭包算子和Hasse图的概念启发AI的直觉，让AI理解"格"的结构。
不运行FCA算法，只用作理论指导。

## 和其他套的区别
- 套B（纯直觉）：不用FCA概念，直接让AI用数学直觉
- 套C（例子引导）：用具体例子引导，不用FCA概念
- 套D（反模式）：用反模式引导，先说对的再说错的

## 版本演进
- V1：只给FCA闭包算子定义（320号§2.3）
- V2：+Hasse图启发+例子+8种复杂情况（322号§1）
- V3：+为什么+影响例子+7种反模式（323号§1）
- V4：+树状/线性输入区分（324号§1）

## 验证状态
- V4待VMS-28验证

## 并发使用
可以和套B/C/D并发使用——多套提示词各自给AI处理同一输入，
结果汇总（取并集得到更完整的trace集合）或各自流向下一个Pipe
（各自驱动引导树长出不同分支）。
```
