## 1. 根本认知——系统目的是让两棵树生长

**系统的目的不是"让AI做出来"，而是"让两棵树生长出来，在过程中与正确解答的脉络相遇"。**

这是第五代已确立的认知（第五代技术说明书`01-基础概念/04-两棵树.md`§6、`05-引导树闭环/04-停机条件.md`§2），第六代继承并推进。

这个根本认知带来一系列设计转变：

| 旧认知（让AI做出来） | 新认知（让树生长） |
|---|---|
| 推理AI需要停下接受提示 | 推理AI不需要停下，走到哪里都接受 |
| 系统等AI跑完再处理 | 系统与推理AI并行运行 |
| hint的作用是让AI做出来 | hint的作用是让树分叉出新方向 |
| 一个tell对应多个hint需要选择 | 全选，树分叉多方向 |
| 多个结果需要汇总去重 | 不汇总，引导树照单全收 |
| 匹配失败是问题 | 匹配失败存档启发Parser AI |
| 评测标准：做没做出来 | 评测标准：树长得多完整（多妖娆） |
| 停机条件：做出来或放弃 | 停机条件：某条脉络与正确解答相遇 |

**引导树的理想面相是"妖娆"——高速地在不同Level上随着推理AI并发探索，在Telling AI支持下快速生出更多探索方向。** 方向越多，某条脉络到达正确解答的概率越大。

## 2. 两棵树

### 2.1 引导展开树（过程）

**引导展开树（Guided Expansion Tree）** 是从题目出发，在提示驱动下展开的所有可能解题路径构成的空间。

- 每个节点 = 一个数学处境
- 每条边 = 一个提示Q（一个hint）
- 每条从根到叶的路径 = 一次完整的解题尝试
- 树的分支 = 在某个处境岔口，有不同的提示方向

引导展开树是**活的、正在生长的**。每当系统识别出一个trace并匹配了tell→hint，引导树就长出一条新边，启动的新AI在新边上探索，产生新节点。

### 2.2 解题记录树（产物）

**解题记录树（Solution Record Tree）** 是一道题在引导下被探索过的所有路径的完整记录——包括成功路径和失败路径。

- 根 = 题目
- 内部节点 = 解题过程中经过的各个处境
- 边 = 提示Q
- 叶节点 = 成功叶（证毕）/ 死路叶（走不通）/ 截断叶（超限停止）

解题记录树是**展开完成后凝固的树**——引导展开树的完成态。

### 2.3 两棵树的关系

两棵树是同一棵树的不同阶段：
- 引导展开树 = 过程中正在生长的树，活的
- 解题记录树 = 展开完成后凝固的树

### 2.4 第六代的新增——树的Level

第六代引入非局部trace后，两棵树需要考虑Level：
- 局部trace对应的hint针对单个节点——在引导树的单个节点上开新边
- 非局部trace对应的hint针对一段节点——在引导树的段级位置开新边

这是小问题——两棵树的基本结构不变，只是"在树的哪个Level开新边"的细节。

## 3. 系统中的AI角色

第六代系统中有四种AI角色：

### 3.1 推理AI（Solver）

对题目进行探索，产生thinking/trajectory。系统中有多个推理AI并发探索，每个走一个方向。

推理AI不需要停下接受提示——它持续推理，走到哪里都可以。它自然终止（token用尽、证毕、崩溃）后，系统在它的终点节点上检索方向，启动新AI。

### 3.2 分析AI

对推理AI的探索全程进行分析，分析出思维脉络，格化脉络找出所有Level视图，从局部到整体识别trace。

分析AI是"脉络分析管线"的使用者之一（另一个是Parser AI）。

### 3.3 Telling AI

并发地拿着trace找tell。每个Telling AI是一个Devin CLI实例，在对应分类的目录中启动，加载该目录的AGENTS.md，以可审计方式遍历该分类下的所有tell，判断是否命中被分配的trace。

多个Telling AI并发运行，各自返回结果，不需要汇总——引导树照单全收。

### 3.4 Parser AI

处理需要导入系统的外部题目和解答数据。从外部解答记录中识别trace，进入Telling AI并发分类分析，没匹配到tell的trace直接成为新tell并建立新的(tell, hint)对。

Parser AI是"脉络分析管线"的另一个使用者。它和分析AI共用步骤1-4（分析脉络→格化→识别trace→Telling AI并发分析），只在步骤5分叉。

Parser AI有两个输入：
1. 已有tell——用于匹配
2. 没匹配到tell的trace（分析AI产出的孤悬trace）——用于启发"从什么Level观察外部解答记录"

## 4. 数据基座

### 4.1 Tell分类学（目录结构+AGENTS.md）

Tell按分类学存储和组织。分类学对应目录结构，每个分类/子分类是一个目录，每个目录的AGENTS.md存放该分类的tell。

```
tell_library/
├── 数论/
│   ├── AGENTS.md  ← 数论domain的tell
│   ├── 局部trace/
│   │   └── AGENTS.md
│   └── 非局部trace/
│       ├── 构造-分析-排除/
│       │   └── AGENTS.md
│       ├── 追逐/
│       │   └── AGENTS.md
│       └── ...
├── 代数/
│   └── ...
└── ...
```

Telling AI在对应目录中启动Devin CLI，加载AGENTS.md获取该分类的tell。

### 4.2 Hint数据库

Hint存储在数据库中（ArangoDB），通过tell_id关联查询。tell和hint是多对多关系——一个tell可以对应多个hint（一道题有多种解法），一个hint可以被多个tell触发。

### 4.3 孤悬trace存档

分析AI产出的、有意义但没匹配到tell的trace，按tell分类学分类存档。这些trace不是废物——它们是Parser AI的启发信号，等待Parser AI从外部解答记录中验证后升级为正式tell。

## 5. 脉络分析管线——分析AI和Parser AI共用的核心管线

分析AI处理推理AI上下文（过程A）和Parser AI处理外部解答记录（过程B）共用同一套管线（步骤1-4），只在步骤5分叉。

### 5.1 共用管线（步骤1-4）

```
任何数学推理脉络 → [步骤1-4：脉络分析管线] → trace + trace→tell匹配结果
```

**步骤1：分析出思维脉络**

分析输入的推理内容（thinking或解答记录），分析出整个思维脉络。脉络可能是一棵树或DAG（如果推理中有分叉），无论是什么结构，都梳理成从根到叶子的一条条脉络。

**步骤2：格化脉络，找出所有Level的脉络视图**

把脉络"格"化——找出所有Level的脉络视图。最细Level（每个推理步骤是一个节点）、最粗Level（整个脉络是一个节点）、中间Level（几个步骤合并成一段）。用FCA格遍历算法系统化地找出有意义的Level视图，不暴力枚举2^(n-1)种看法。

**步骤3：从局部到整体识别trace**

在所有Level的脉络视图上识别trace：
- 最细Level → 局部trace（单点/单段特征）
- 中间Level → 非局部trace（跨段模式/段结构模式/构造目的）
- 最粗Level → 整体trace（整体策略）

**步骤4：trace进入Telling AI并发分类分析**

拿着trace并发地找tell。在每个对应分类的目录中启动Devin CLI实例，加载该目录的AGENTS.md，以可审计方式遍历该分类下的所有tell，判断是否命中被分配的trace。

### 5.2 步骤5分叉

```
                    ┌──────────────────────────┐
                    │ 步骤5：分叉                │
                    ├──────────────┬──────────────┤
                    │ 过程A        │ 过程B        │
                    │ 分析推理AI上下文│ Parser AI处理素材│
                    │              │              │
                    │ 匹配到tell:   │ 匹配到tell:   │
                    │ 取hint→填引导树│ 确认匹配      │
                    │              │              │
                    │ 没匹配到tell: │ 没匹配到tell: │
                    │ trace存档→   │ trace成为新tell│
                    │ 启发Parser AI │ →建立(tell,hint)│
                    └──────────────┴──────────────┘
```

**过程A（分析AI处理推理AI上下文）**：
- 匹配到tell → 取hint → 填充引导树 → 引导树长新边 → 启动新推理AI
- 没匹配到tell → trace按tell分类学分类存档 → 启发Parser AI

**过程B（Parser AI处理外部解答记录）**：
- 匹配到tell → 确认匹配（不需要新建）
- 没匹配到tell → trace直接成为新tell → 建立新的(tell, hint) → 存入对应目录的AGENTS.md

**为什么过程B的trace可以直接成为tell**：因为外部解答记录是完整正确解答，trace被验证过。过程A的trace是探索中的，可能走对了也可能走错了，不能直接升级为tell，只能存档待Parser AI验证。

### 5.3 两个过程的统一依据

两个过程的输入本质上是同一种东西——**数学推理的脉络**：
- 推理AI的上下文 = 未完成的、可能有错误的脉络
- 外部解答记录 = 已完成的、正确的脉络

处理脉络的过程一样——分析脉络→格化→识别trace→匹配tell。区别只在步骤5。

### 5.4 两个过程形成的闭环

```
过程A产出孤悬trace → 按tell分类学分类存档
  → 启发过程B（Parser AI）
  → 过程B从外部解答记录中验证相同模式的trace
  → trace升级为正式tell → 建立新的(tell, hint)对
  → 存入对应目录的AGENTS.md
  → 新tell可用于过程A的未来匹配
  → 过程A能匹配到更多tell → 取更多hint → 引导树更妖娆
```

## 6. 完整工作过程——端到端

### 6.1 启动

第一个推理AI收到题目本身（裸做题，无初始hint），开始探索，产生thinking/trajectory。

### 6.2 循环

```
阶段1：推理AI探索
  推理AI对题目探索 → 产生thinking/trajectory
  推理AI不需要停下——持续推理，走到哪里都可以
     │
     ▼
阶段2：思维脉络分析（脉络分析管线步骤1-2）
  分析AI对探索全程分析 → 思维脉络（可能是一棵树或DAG）
  梳理成从根到叶子的一条条脉络
  格化脉络→找出所有Level的脉络视图（FCA格遍历算法）
     │
     ▼
阶段3：trace识别——从局部到整体（脉络分析管线步骤3）
  在所有Level脉络上识别trace
  局部trace（单点特征）+ 非局部trace（跨段模式/高Level策略）+ 整体trace
     │
     ▼
阶段4：并发找tell（脉络分析管线步骤4）
  拿着trace并发地找tell
  在对应分类目录中启动Devin CLI实例
  Devin CLI加载该目录AGENTS.md，以可审计方式遍历tell
  判断是否命中被分配的trace
     │
     ▼
阶段5：trace→tell匹配（脉络分析管线步骤5分叉——过程A）
  每个Telling AI（Devin CLI实例）找到trace对应的tell
  没找到的trace → 按tell分类学分类存档 → 启发Parser AI
     │
     ▼
阶段6：tell→hint查询
  根据匹配到的tell从数据库中查出对应的hint
  一个tell可能对应多个hint——全选（一道题有多种解法）
     │
     ▼
阶段7：引导树填充
  用hint填充引导树 → 引导树长出新边（新方向）
  每个hint开一条新边，每个方向启动一个新推理AI
  考虑Level——非局部trace的hint在段级位置开新边
     │
     ▼
  启动新推理AI → 回到阶段1（Grove核心循环继续）
```

### 6.3 并行运行

系统与推理AI并行运行——推理AI在thinking的同时，系统就在：
- 采集thinking（阶段2的输入）
- 整理两棵树（节点写入解题树）
- 在节点上做检索（阶段2-7）

**系统不在`get_output`干等结果。** 两条Pipe同时工作：
- 推理Pipe（多个）——推理AI在做数学
- 辅助Pipe（1个）——系统在采集、整理、检索、启动

### 6.4 停机

**与正确解答的脉络相遇时停机。** 当某条脉络到达正确解答时，标记为成功叶，problem标记为solved，不再从该树的叶节点启动新AI。

不需要所有分支都探索完。引导树上方向越多，某条脉络到达正确解答的概率越大——这就是积累(tell, hint)让树妖娆生长的意义。

穷尽停机：所有方向都探索完但没有找到正确解答。穷尽停机时树的生长过程本身有价值——记录了哪些方向走不通、为什么走不通。

### 6.5 tell库的持续增长（Parser AI的并行工作）

在系统运行循环的同时（或间歇期），Parser AI处理外部题目和解答数据：
- 用脉络分析管线（步骤1-4）分析外部解答记录
- 步骤5分叉到过程B：没匹配到tell的trace直接成为新tell→建立(tell, hint)
- 参考分析AI产出的孤悬trace作为启发信号
- 新(tell, hint)存入对应目录的AGENTS.md

tell库持续增长 → 未来系统运行时能匹配到更多tell → 取更多hint → 引导树更妖娆 → 求解概率更大。

## 7. 系统的创新

**传统AI数学系统的目标是"让AI做出来"——评测标准是做没做出来，停机条件是做出来或放弃。我们的系统目标是"让两棵树生长出来"——评测标准是树长得多完整（多妖娆），停机条件是某条脉络与正确解答相遇。**

这个根本认知转变是第五代已确立的创新，第六代在此基础上推进：

| 第五代 | 第六代 |
|---|---|
| 推理AI不需要停下 | 继承 |
| 系统与推理AI并行 | 继承 |
| hint让树分叉不是让AI做出来 | 继承 |
| Grove核心循环 | 继承 |
| tell端三层Pipe（Pipe 0/1/2） | 升级为脉络分析管线+并发Telling AI |
| 大概念→小概念→概念树 | 升级为Tell分类学（目录结构+AGENTS.md+FCA数学基础） |
| 只有局部tell（最粗Level拓扑化） | 新增非局部tell（所有Level视图+非局部trace识别） |
| 单一分析过程（分析推理AI上下文） | 新增Parser AI（分析外部解答记录）+脉络分析管线统一 |
| tell存储在ArangoDB | 新增tell存储在目录AGENTS.md |
| 2并发推理AI | 扩展到更多并发 |

**第六代的独特贡献**：
1. 非局部trace的正式化——识别跨段模式/高Level策略
2. 推理脉络的格化——用FCA格遍历算法找出所有Level视图
3. 并发Telling AI——多个Devin CLI实例在分类目录中并发做trace→tell匹配
4. Tell分类学——分类体系对应目录结构，AGENTS.md存储tell
5. Parser AI——从外部解答记录持续丰富tell库
6. 脉络分析管线——分析AI和Parser AI共用步骤1-4，只在步骤5分叉
7. trace的第二用途——没匹配到tell的trace启发Parser AI
8. tell库增长的闭环——过程A产出孤悬trace→启发过程B→过程B验证升级为正式tell→新tell用于过程A的未来匹配

## 8. 达到理想状态需要解决的障碍（314号三个问题）

理想化工作过程描述的是问题都解决后的样子。达到理想状态需要解决三个障碍：

### 8.1 问题1：现有tell库只有局部tell，没有非局部tell

现有4164个tell全是第五代局部分析方法的产物，没有经过非局部分析。tell库中看不到"反证法"、"同构之桥"、"构造-分析-排除"等高Level/非局部tell。

**解决方向**：建立非局部trace的识别方法→重新分析现有455个profile→补充非局部tell到库中。

### 8.2 问题2：推理脉络的"格"化

n个节点的脉络有2^(n-1)种看法，不能全枚举。需要用FCA格遍历算法系统化地找出有意义的Level视图。

**解决方向**：定义"有意义的合并"→把推理脉络转化为FCA形式上下文→用Next Closure/In-Close算法枚举闭元素。

问题2是问题1的前置——先能格化脉络找出所有Level视图，才能在每个Level上识别非局部trace。

### 8.3 问题3：Tell的分类学

建立同时覆盖局部tell和非局部tell的分类体系，用目录结构+AGENTS.md存储，用FCA数学基础定义分类体系。

**解决方向**：313号六步研究路线——现状调查→分类维度设计→段结构模式收集→FCA形式上下文→分区验证→POC验证。

问题3依赖问题1和问题2，但局部tell的分类部分可以独立先行。

### 8.4 三个问题的关系

```
问题2（格化脉络）→ 问题1（识别非局部trace + 补充非局部tell到库）
                         ↓
                    问题3（在完整库上建立分类学）
                         ↓
                    理想化工作过程可实现
```
