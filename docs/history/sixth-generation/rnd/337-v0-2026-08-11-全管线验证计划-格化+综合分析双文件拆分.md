## 2. 验证什么——6个验证维度

### 验证维度1：流程能跑通

**验证内容**：三阶段架构的完整流程能跑通——4个格化session并发+程序枚举闭元素+综合分析4阶段都完成。

**判定标准**：
- 4个格化session都产出DONE.md
- V7/V8/V10都产出segments.json + formal_context.json
- V5产出segments.json
- V10产出key_entities.json
- 程序枚举产出V7/V8/V10的closed_elements.json
- 综合分析产出comparison.json + closed_element_traces.json + content_based_traces.json + output.json + output.md + DONE.md

**为什么重要**：这是最基础的验证——如果流程跑不通，其他验证都没有意义。

### 验证维度2：V8格化不退化

**验证内容**：V8的2步文件拆分（方案D）在全管线中不退化——闭元素数量和0009一致。

**判定标准**：
- V8的segments.json段数 ≥ 0009的V8段数（22段）
- V8的formal_context.json特征数 ≥ 0009的V8特征数（40个）
- V8的closed_elements.json闭元素数 ≥ 0009的V8闭元素数的80%（39个×80%=31个）

**为什么重要**：335号方案D的单独测试验证了闭元素48=48不退化，但那是在`/tmp/v8_test`中单独测试的。全管线中V8的运行环境不同（和其他3个版本并发），需要确认并发不会导致退化。

**历史对比基线**：

| 运行 | V8段数 | V8特征数 | V8闭元素数 |
|---|---|---|---|
| 0005 | 32 | 32 | 48 |
| 0008 | 22 | 40 | 39 |
| 0009 | 22 | 40 | 39 |

### 验证维度3：综合分析4阶段不退化

**验证内容**：综合分析的4阶段文件拆分在全管线中不退化——trace数量≥0009的43。

**判定标准**：
- output.json的trace总数 ≥ 0009的43的80%（即≥35）
- output.json的global trace数 ≥ 0009的7的70%（即≥5）
- output.json的AI优势数 ≥ 0009的7的70%（即≥5）

**为什么重要**：336号的单独测试（0010）用0009的格化结果作为输入，trace从43提升到88。但全管线中格化是新跑的——格化结果可能和0009不完全一样，综合分析的输入不同，trace数量可能不同。需要确认全管线中综合分析4阶段仍然不退化。

### 验证维度4：综合分析4阶段是否还能提升

**验证内容**：全管线中综合分析4阶段的trace数量是否接近0010的88。

**判定标准**：
- 如果trace数量 ≥ 60——4阶段拆分在全管线中仍然大幅提升 ✅
- 如果trace数量在43-60之间——4阶段拆分在全管线中有提升但不显著 ⚠️
- 如果trace数量 < 43——4阶段拆分在全管线中退化 ❌

**为什么重要**：0010的88是用0009的格化结果作为输入——0009的格化结果已经经过验证是好的。全管线中格化是新跑的，格化结果可能有波动。如果格化结果变差，综合分析的输入也会变差，trace数量可能下降。这个验证维度告诉我们"4阶段拆分的提升是否依赖格化结果的质量"。

### 验证维度5：审计对比——无真正退化

**验证内容**：用run_audit.py和baseline+0004+0005+0008+0009对比，确认无真正退化。

**判定标准**：
- 审计脚本判定"无退化"或"退化点都是baseline并集导致的假退化"
- 不出现新的真正退化点（如0008的global=0那种）

**为什么重要**：这是最终的验收标准——审计脚本的综合判定。前面4个维度是分项检查，这个维度是综合检查。

### 验证维度6：耗时

**验证内容**：全管线总耗时，以及各阶段耗时。

**判定标准**：
- 格化阶段 ≤ 0009的格化耗时（约5分钟）
- 综合分析阶段 ≤ 0009的综合分析耗时（约8分钟）——4阶段拆分应该更快或相当
- 全管线总耗时 ≤ 0009的总耗时（约15分钟）

**为什么重要**：文件拆分流程控制的初衷是控制thinking大小、降低耗时。需要确认全管线中耗时确实没有增加。

**历史对比基线**：

| 运行 | 格化耗时 | 综合分析耗时 | 总耗时 |
|---|---|---|---|
| 0009 | ~5分钟 | ~8分钟 | ~15分钟 |
| 0010（仅综合分析） | - | ~12分钟 | - |

**注意**：0010的综合分析耗时12分钟比0009的8分钟更长——因为4阶段拆分让AI做了更细致的工作（trace从43到88），thinking总量增加了。这是"用时间换质量"——如果trace数量大幅提升，耗时增加是可接受的。

## 3. 验证方法

### 3.1 运行方式

用`system/run_imo2009p6_three_phase.py`运行全管线，run_id=0011。

**不套tmux**——直接用exec后台运行脚本（脚本内部自己管理tmux session）。

**不sleep干等**——脚本运行时做检查者工作：定期检查格化session的DONE.md、检查综合分析的step完成标记。

### 3.2 检查点

| 时间点 | 检查什么 |
|---|---|
| 启动后1分钟 | 4个格化session是否都启动了 |
| 启动后5分钟 | 格化session的DONE.md是否开始出现 |
| 格化全部完成后 | 各版本的segments.json/formal_context.json是否产出 |
| 程序枚举完成后 | closed_elements.json是否产出 |
| 综合分析启动后2分钟 | comparison.json是否填充（阶段1完成） |
| 综合分析启动后6分钟 | closed_element_traces.json是否填充（阶段2完成） |
| 综合分析启动后9分钟 | content_based_traces.json是否填充（阶段3完成） |
| 综合分析启动后13分钟 | output.json+DONE.md是否产出（阶段4完成） |

### 3.3 验证执行

全管线完成后：

1. **存档**——把0011的产出复制到`system/tests/vein_analysis/runs/0011/`
2. **维度1检查**——确认所有产出文件都存在
3. **维度2检查**——对比V8的段数/特征数/闭元素数 vs 0009
4. **维度3+4检查**——对比trace总数/类型分布/AI优势 vs 0009和0010
5. **维度5检查**——运行run_audit.py 0011
6. **维度6检查**——从文件时间戳计算各阶段耗时
7. **生成验证报告**——把6个维度的检查结果写入验证报告
