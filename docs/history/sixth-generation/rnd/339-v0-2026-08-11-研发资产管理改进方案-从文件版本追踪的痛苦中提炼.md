# 339号 · 研发资产管理改进方案——从文件版本追踪的痛苦中提炼

**日期**：2026-08-11
**状态**：方案设计
**来源**：338号文件版本追踪过程中暴露的研发资产管理问题

---

## 1. 问题暴露——338号文件版本追踪的痛苦

在338号文档中，用户要求"每次运行使用的子管线、版本、提示词文件在哪里、是否被更新、需要指定git log id"。为了回答这个问题，我不得不：

1. **用md5对比工作目录中的prompt.md和git历史中各commit的版本**——手动找了20+次md5
2. **从git log时间线推断每次运行用了哪个commit的vein_analysis.py**——不精确，只能推断
3. **发现baseline（POC时期）的提示词文件完全不可追溯**——只保留了output.json
4. **发现7条数据库记录没有run_id**——早期运行没有入题序号
5. **发现8条数据库记录是running状态未清理**——中断的运行没有清理

**这些痛苦的根因**：运行时没有记录资产版本——没有在元数据文件中记录"这次运行用了哪个提示词文件、哪个git commit、哪个版本的vein_analysis.py"。

---

## 2. 暴露的6个问题

### 问题1：运行时没有记录资产版本

**现状**：vein_analysis.py运行时只写meta.json（记录problem_id/versions/session_names），不记录用了哪个提示词文件、哪个git commit。

**后果**：回头审计时需要用md5对比git历史才能找到文件版本——338号7.5节花了大量篇幅做这个追踪。

**根因**：vein_analysis.py在启动时没有生成run_manifest.json记录资产版本。

### 问题2：目录命名不统一

**现状**：
```
imo2009p6/                    ← 无run_id（早期调试）
0004_imo2009p6/               ← 有run_id
0008_imo2009p6_v8test/        ← 有后缀（单独测试）
0008_imo2009p6/               ← 和_v8test同名不同后缀
0010_imo2009p6_synthtest/     ← 有后缀（单独测试）
```

**后果**：目录命名混乱，无法从目录名一眼看出运行的性质和run_id。

**根因**：没有目录命名规范，run_imo2009p6_three_phase.py允许自定义后缀。

### 问题3：资产散落——palyground和system/tests两份

**现状**：
- `palyground/absorb/vein_analysis/`——运行时的工作目录（7个目录）
- `system/tests/vein_analysis/runs/`——归档目录（5个目录）

**后果**：同一个运行有两份资产，不确定哪份是权威的。palyground的可能是最新的，system/tests的可能是归档时的快照。

**根因**：归档是手动做的（`cp`命令），不是自动的。归档时机不确定——有的运行归档了，有的没有。

### 问题4：数据库记录不完整

**现状**：
- 13条problem_entries记录中，7条没有run_id（早期运行）
- 8条是running状态未清理（中断的运行）
- 0010没有数据库记录（单独测试没走完整管线）

**后果**：从数据库run_id无法找到所有运行——需要同时查文件系统才能完整。

**根因**：
- 早期运行没有入题序号机制（74385ac之后才有）
- 中断的运行没有清理逻辑
- 单独测试不走vein_analysis_three_phase()，不写数据库

### 问题5：baseline（POC时期）资产不可追溯

**现状**：baseline只保留了output.json，没有保留当时的prompt.md和AGENTS.md。

**后果**：无法知道baseline用了什么提示词——只能从output.json的内容推断。

**根因**：POC时期的提示词在grove repo中，没有同步到当前repo。baseline从grove repo复制时只复制了output.json。

### 问题6：vein_analysis.py版本不可追溯

**现状**：每次运行用了哪个commit的vein_analysis.py，只能从git log时间线推断——不精确。

**后果**：如果vein_analysis.py有bug，不知道哪些运行受影响。

**根因**：运行时没有记录代码版本（git commit hash）。

## 3. 改进方案——4层保证

### 3.1 第1层：代码层面——vein_analysis.py自动生成run_manifest.json

**做什么**：vein_analysis_three_phase()启动时，在工作目录中生成`run_manifest.json`，记录：

```json
{
  "run_id": 11,
  "problem_id": "imo2009p6",
  "started_at": "2026-08-11T13:00:00",
  "git_commit": "43071f0",
  "git_branch": "glm5.2",
  "phases": {
    "phase1_grading": {
      "versions": ["V5", "V7", "V8", "V10"],
      "prompt_files": {
        "V5": {"path": "第六代系统提示词积累目录/.../v5_grading.md", "md5": "e431313f"},
        "V7": {"path": ".../v7_grading.md", "md5": "eb417386"},
        "V8": {"path": ".../v8_grading.md", "md5": "9b02c7fe"},
        "V10": {"path": ".../v10_grading.md", "md5": "294513c0"}
      },
      "agents_templates": {
        "V5": {"path": "system/assets/vein_analysis/AGENTS_V5.md", "md5": "aef46642"},
        ...
      },
      "step_files": {
        "V8_step1": {"path": ".../v8_step1_requirements.md", "md5": "3e05be78"},
        "V8_step2": {"path": ".../v8_step2_requirements.md", "md5": "b0053e8f"}
      }
    },
    "phase1_5_enumerate": {
      "script": "six/verify_lattice_completeness.py",
      "script_md5": "..."
    },
    "phase2_synthesis": {
      "prompt_file": {"path": ".../synthesis.md", "md5": "59eec5bd"},
      "agents_template": {"path": "system/assets/vein_analysis/AGENTS_synthesis.md", "md5": "5d76772c"},
      "step_files": {
        "step1": {"path": ".../synthesis_step1_requirements.md", "md5": "f3c32708"},
        "step2": {"path": ".../synthesis_step2_requirements.md", "md5": "e9c0e988"},
        "step3": {"path": ".../synthesis_step3_requirements.md", "md5": "54b29f48"},
        "step4": {"path": ".../synthesis_step4_requirements.md", "md5": "ab4d50a6"}
      }
    }
  },
  "code_version": {
    "vein_analysis_py": {"md5": "9ed7a37a"},
    "verify_lattice_completeness_py": {"md5": "..."}
  }
}
```

**实现**：在vein_analysis.py中加一个`_write_run_manifest()`函数，在`vein_analysis_three_phase()`开始时调用。

**效果**：回头审计时直接读run_manifest.json，不需要md5对比git历史。

### 3.2 第2层：规则层面——.devin/rules/加研发资产管理规则

**做什么**：创建`.devin/rules/six-asset-management.md`，规定：

1. **目录命名规范**：`{run_id:04d}_{problem_id}`，不允许自定义后缀。单独测试用`{run_id:04d}_{problem_id}_{test_type}`，test_type只能是`synthtest`/`v8test`等预定义值。
2. **归档规范**：运行完成后必须归档到`system/tests/vein_analysis/runs/{run_id}/`，归档是自动的（vein_analysis.py在结束时自动复制）。
3. **数据库记录规范**：每次运行必须写数据库，中断的运行必须标记为interrupted。
4. **run_manifest.json规范**：每次运行必须生成run_manifest.json，记录所有资产版本。

### 3.3 第3层：AGENTS.md——加研发资产管理节

**做什么**：在AGENTS.md中加"研发资产管理"节，作为跨session AI的认知保证：

```markdown
## 研发资产管理

### 运行资产
- 每次运行的工作目录：palyground/absorb/vein_analysis/{run_id:04d}_{problem_id}/
- 每次运行的归档目录：system/tests/vein_analysis/runs/{run_id}/
- 每次运行必须生成run_manifest.json——记录所有提示词文件、AGENTS模板、代码的md5和git commit
- 回头审计时从run_manifest.json找文件版本，不需要md5对比git历史

### 目录命名
- 正式运行：{run_id:04d}_{problem_id}
- 单独测试：{run_id:04d}_{problem_id}_{test_type}
- 不允许无run_id的目录（早期imo2009p6是历史遗留，不再新增）

### 数据库记录
- 每次运行必须写problem_entries集合
- 中断的运行必须标记为interrupted（不是running）
- 单独测试也要写数据库（run_id字段标注为test）
```

### 3.4 第4层：数据库表设计改进

**做什么**：problem_entries集合加字段：

```json
{
  "run_id": 11,
  "problem_id": "imo2009p6",
  "status": "completed",  // completed/interrupted/failed/running
  "started_at": "...",
  "ended_at": "...",
  "manifest_path": "palyground/absorb/vein_analysis/0011_imo2009p6/run_manifest.json",
  "archive_path": "system/tests/vein_analysis/runs/0011/",
  "git_commit": "43071f0",
  "phases": {
    "phase1_grading": "completed",
    "phase1_5_enumerate": "completed",
    "phase2_synthesis": "completed"
  }
}
```

**新增字段**：
- `manifest_path`——run_manifest.json的路径，从数据库可以直接找到资产版本
- `archive_path`——归档目录路径
- `git_commit`——运行时的git commit hash
- `phases`——各阶段状态

## 4. 落实方案——4步执行

| 步骤 | 内容 | 层级 | 优先级 |
|---|---|---|---|
| 1 | vein_analysis.py加`_write_run_manifest()`函数 | 代码 | 高 |
| 2 | vein_analysis.py加自动归档逻辑（运行结束后自动复制到system/tests/runs/） | 代码 | 高 |
| 3 | 创建`.devin/rules/six-asset-management.md` | 规则 | 中 |
| 4 | AGENTS.md加"研发资产管理"节 | AGENTS.md | 中 |

**不需要做的**：
- 不需要清理历史遗留的目录命名（imo2009p6等）——历史遗留不动
- 不需要补写历史运行的run_manifest.json——过去的已经过去了，只对未来的运行保证
- 不需要改数据库表结构（ArangoDB是schema-free的）——只需要在代码中写新字段

---

## 5. 改进后的审计流程

**改进前**（338号的痛苦流程）：
1. 从文件系统找运行目录
2. 从数据库找run_id
3. 用md5对比工作目录中的prompt.md和git历史中各commit版本
4. 从git log时间线推断vein_analysis.py版本
5. 手动整理成表格

**改进后**（目标流程）：
1. 从数据库查run_id → 直接得到manifest_path和archive_path
2. 读run_manifest.json → 直接得到所有文件版本、md5、git commit
3. `git show <commit>:<文件路径>` → 查看当时的文件内容

**从5步缩减到3步，且每步都是确定性的（不需要推断）。**
