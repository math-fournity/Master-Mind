## 1. 第六代系统是什么

第六代系统是第五代系统的演进，仍然是一个**引导式数学解题系统**。它的核心思想不变：

> 一个AI（推理AI）在做数学题时可能会走错路。另一个AI（辅助AI）观察推理AI的完整思维过程，识别出那些"可以分叉但AI没分叉"的位置，在这些位置上匹配一个新的探索方向，然后启动一个新的推理AI走这个新方向。一道题的探索过程长成一棵树——而不是一条路。

第六代相对于第五代的核心变化可以概括为三点：

- **trace→tell→hint 三步链路**：辅助AI从thinking中识别出trace（结构化识别结果），用trace查库匹配到tell（标准化描述），从tell关联取出hint（方向提示）。三步动作不同——发现、匹配、取用。替代了第五代tell+hint二元组中tell身兼两职（既是识别结果又是库内容）的混淆。
- **并发Telling AI**：Pipe 2从单AI串行变为多Telling AI并行。每个Telling AI负责一个tell分区，带着自己区的tell视角理解thinking，产出自己区视角下的trace。汇总AI从各Telling AI的trace中精筛出最终tell。
- **Pipe 0简化**：从精确拓扑化（3维度8种组合+手工信号词）降级为粗domain分类（数论/代数/组合/几何/跨域），用LLM轻量判断或题目domain标签。Pipe 1角色从"缩小tell范围"变为"选择启动哪些区的Telling AI"。

## 2. 系统全景图

```
推理AI在解题（走了一条路，产生了thinking）
     │
     ▼
[Pipe 0 简化] 粗domain分类——判断thinking属于哪些domain
     │          数论 / 代数 / 组合 / 几何 / 跨域
     │          实现：LLM轻量判断 / 题目domain标签 / thinking开头分类
     ▼
[Pipe 1 新角色] 选择Telling AI实例——根据domain分类确定启动哪些区的Telling AI
     │            不再是缩小tell范围，而是选择Telling AI实例
     ▼
[Pipe 2 并行化] 多Telling AI并行trace识别
     │
     ├── Telling AI #数论 [thinking + 数论区tell] → trace集合#数论
     ├── Telling AI #代数 [thinking + 代数区tell] → trace集合#代数
     └── ...（只启动相关区，不是全部N个区）
     │
     ▼
[汇总AI] 从各Telling AI的trace中精筛——去重/排序/冲突解决
     │     处理几十个trace（不是4164个tell）
     ▼
trace → 匹配tell（库中标准化描述）→ 取出hint（方向提示）
     │
     ▼
构造脉络（从根到当前节点的路径+方向Q）
     │
     ▼
启动新推理AI（给它脉络+方向，在全新Session中运行）
     │
     ▼
新AI走新分支 → 两棵树生长（引导展开树+解题记录树）
     │
     ▼
在终点节点检索 → 识别新trace → 匹配新tell → 取出新hint → 启动新AI → ...
     │
     ▼
某条脉络到达正确解答 → 停机
```

数学大师系统经历了六代演进：

| **第六代** | **（待命名）** | **trace→tell→hint三步链路 + 并发Telling AI + Pipe 0简化** | **并发化、粗分类化、非局部trace正式化** |

第六代从第五代继承了核心架构（引导树闭环、两棵树、概念树、hint端），但有4项独特贡献是第五代没有的：

2. 并发Telling AI——Pipe 2并行化（311号）
3. Pipe 0简化——从精确拓扑化到粗domain分类（311号）
4. 非局部trace的正式化——局部trace和非局部trace统一为trace，用修饰词区分（303/305/309号）

## 6. 关键约定

- **自包含原则**：每个文件可以独立阅读。新概念在首次出现时给出完整解释，不假设读者已经读过其他文件。
- **双轨术语原则**：FCA等理论语言与研发过程中使用的特有表达并重。FCA语言承载精确性（数学定义、可验证性、和学术界对接），工程人话承载理解（系统设计意图的直接表达）。每个术语同时给出FCA标准定义和工程含义，不允许只用一种而废弃另一种。详见编写方案中的"双轨术语原则"和`.devin/rules/six-dual-terminology.md`。
- **术语一致性**：trace/tell/hint/Pipe/拓扑/概念树等术语在全说明书中的定义一致，详见09-附录/01-术语表.md。
- **和第五代的关系**：第六代技术说明书中继承自第五代的内容会明确标注"继承自第五代"，新增内容会标注"第六代新增"。读者可以对照第五代技术说明书理解继承关系。
- **代码引用**：涉及工程实现的内容会引用具体代码文件和函数名，但不包含完整代码。

## 8. 系统物理实现方向（2026-08-10确立）

### 8.1 用户提出的设计方向

> 我们之前用代码来描述整个系统，代码放在six目录中，现在我认为，我们需要考虑，未来整个AI数学系统的物理实现，就是靠代码去驱动的。

> 我的想法是这样的，我们就像真正的软件系统开发过程一样，分组件开发，当然过程中免不了持续地迭代整个系统的架构、完善它的细节。而且所有组件我们都进行测试，也就是那些POC，甚至进行跨组件的联调，直至最终整个系统可以开机工作。这个工作很显然有两个入口，一个入口是喂料入口，也就是外部持续像系统添加题目。一个是加工入口，也就是将需要解答的题目送入系统，让系统来编排整个引导树和解题树的展开，直至最终获得正确的题目解答。

### 8.2 方向的核心含义

系统的物理实现载体从"AI + markdown文档 + 手动操作"转变为"代码 + AI组件"。代码成为系统的骨架，AI作为代码调用的一个组件（负责认知判断的组件）嵌入在流程中。这不是说代码替代AI的判断，而是说代码定义系统的物理形态——流程编排、数据传递、组件调度由代码驱动，每个组件内部的认知判断由AI完成。

当前 `six/` 目录（2498行代码）是架构描述——所有Pipe函数和流程函数只有签名和docstring，实现待填充。本方向确立后，`six/` 的定位从"架构描述"变为"系统骨架"，需要逐步填充真正的物理实现。

### 8.3 两个入口 = 两个Python脚本

系统有两个入口，各是一个Python脚本：

| 入口 | 脚本 | 对应循环 | 输入 | 系统做什么 |
|---|---|---|---|---|
| **入题** | `system/enter.py` | `tell_library_growth_loop()`（解答吸收） | 外部题目+解答记录 | 分析解答记录→格化→识别trace→匹配tell→建立新(tell,hint)→tell库增长 |
| **解题** | `system/solve.py` | `grove_core_loop()`（解题引导） | 需要解答的题目 | 编排引导树+解题树展开→Pipe 0推理→Pipe 1格化→Pipe 2匹配→Pipe 3引导→新AI启动→直至正确解答 |

**命名含义**：
- **入题**——题目进入系统的知识库：外部持续向系统添加题目（及其解答记录），系统从中提炼tell/hint，tell库增长。这是系统的"喂料"过程。
- **解题**——系统解答题目：将需要解答的题目送入系统，系统编排整个引导树和解题树的展开，直至最终获得正确的题目解答。这是系统的"加工"过程。

### 8.5 对现有工作的影响

1. **知识层需要从markdown变成代码可消费的格式**——当前Tell分类学在 `FCA学习笔记/08-先验Tell分类学.md`，高Level概念解释在研发过程文档中，这些是人读的。如果系统是代码驱动的，知识层需要变成代码可读的格式（JSON/YAML/Python数据结构），代码才能直接消费。这是一个新的工作项：知识层代码化。

2. **POC的定位变了**——POC不再是"验证某个想法是否可行"的探索性实验，而是组件测试——每个POC对应一个组件的功能验证。跨组件联调对应多个Pipe串联的集成测试。最终"开机工作"对应全系统端到端测试。

3. **"系统就是你"原则需要演进**——当前AGENTS.md的硬约束"系统就是你，不是脚本"是研发阶段的临时状态。当系统建好后，"系统就是代码+AI组件"。这条原则需要标注演进路径——从研发阶段的"AI手动扮演系统"，到系统建成后的"代码是骨架，AI是判断组件"。

4. **339号融合方案和Tell分类学研究的定位**——339号融合方案（将高Level概念设计思想融合到技术说明书）仍然需要做，但它的产出不只是更新markdown技术说明书，还需要知识层代码化。技术说明书是设计依据，代码是物理实现。

### 8.6 开发方式

像真正的软件系统开发过程一样：

- **分组件开发**——按组件分层独立开发，每个组件有明确的接口和职责
- **持续迭代架构**——过程中免不了持续整个系统的架构、完善细节
- **组件测试（POC）**——所有组件都进行测试，POC就是组件测试
- **跨组件联调**——多个Pipe串联的集成测试
- **直至开机**——最终整个系统可以开机工作，两个入口（入题+解题）可以持续运行

### 8.7 会话与启动目录ID化

系统在运行过程中需要启动devin cli实例来处理各种内容（脉络分析、trace匹配、引导展开等）。每个devin cli实例的启动目录是ID化的——以题目ID命名。这保证不同题目、不同会话的devin cli实例彼此隔离，工作目录不混淆。

**一次入题 = 数据库中一条会话记录。一次解题 = 数据库中一条会话记录。**

| 会话类型 | 关联ID | 数据库记录 |
|---|---|---|
| 入题（解答吸收） | 题目ID | sessions表一条记录，type=absorb |
| 解题（解题引导） | 题目ID | sessions表一条记录，type=solve |

会话记录的内容包括：会话ID、类型（入题/解题）、题目ID、状态（运行中/完成/失败）、启动时间、完成时间、工作目录路径、会话结果摘要。

**运行时工作目录**：`palyground/` 是系统的运行时工作目录根。系统为devin cli实例创建的启动目录都在 `palyground/` 下。不同阶段的devin cli实例启动在不同的子目录中，每个子目录下再以题目ID创建工作目录：

```
palyground/
├── solve/                                # 解题引导
│   ├── inference_explore/{题目ID}/      # 推理探索——推理AI
│   ├── vein_analysis/{题目ID}/          # 脉络分析——脉络分析AI
│   ├── trace_match/{题目ID}/            # trace匹配——匹配AI（可并发多个）
│   └── guide_expand/{题目ID}/           # 引导展开——引导AI
├── absorb/                               # 解答吸收
│   ├── vein_analysis/{题目ID}/          # 脉络分析——脉络分析AI
│   ├── trace_match/{题目ID}/            # trace匹配——匹配AI（可并发多个）
│   └── knowledge_deposit/{题目ID}/      # 知识沉淀——去特化AI
```

- 解答录入和方向取用是纯系统逻辑，不需要启动devin cli，没有工作目录
- trace匹配阶段可能并发启动多个匹配AI，它们共享同一个 `{题目ID}/` 目录或各自有子目录，后续迭代确定

**数据库表设计是迭代的**——当前只定义会话表的最小字段，后续随着系统实现推进，会逐步增加字段和新增表（如trace存档表、孤悬trace表、tell库变更日志等）。表设计在 `system/db_schema.py` 中代码化，随系统迭代。
