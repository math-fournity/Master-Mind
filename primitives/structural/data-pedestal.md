# 数据基座（data-pedestal）

## 定义

数据基座不是"数学工程单元库"——它是形式化边界的显式记录。每个数学工程单元标记着形式化边界的一个位置——这个位置上的东西已经被形式化了。数据基座的增长 = 形式化边界的推进。

## 架构位置

### 数据基座不是RAG

| 维度 | RAG | 数据基座 |
|---|---|---|
| 基本单位 | 文档块 | 数学工程单元 |
| 检索目标 | 找相似文本 | 找相似的边界推进路径 |
| 相似性度量 | embedding相似度 | 路径结构相似度 |
| 内容 | "这篇文档里说了什么" | "这段数学材料能在系统里做什么" |

### 数学工程单元的四阶段结构

1. **边界标记**：处境描述+表示图册（原始/规范化/对偶/形式化）
2. **跨越边界**：语义移动+表示变换（中心化/换基/归一化/对偶化/构造辅助对象）
3. **边界以内**：证书目标+证书结果+依赖关系+经典任务
4. **边界以外的感知沉淀**：模式模板+自然性测试+反例边界

四阶段形成时间结构：起点→过程→产物→经验→下一轮的起点。

### 分层形式化

不要求所有材料一开始就完全形式化。五层：
1. 结构化：拆成对象/条件/目标/步骤/依赖
2. 规范化：同类操作统一命名
3. 可执行化：编译成计算任务
4. 局部证书化：计算结果写成可复查证书
5. 完整形式化证明：最高层，不是所有材料都能达到

### 检索机制

检索不是找相似文本，是找**相似的边界推进路径**。两个处境"相似" = 面临相似的不自然 + 需要相似的跨越 + 产生相似的证书目标。

### 抽取机制

**抽取就是闭环本身。** 求解过程自然产生数据基座条目——不需要单独做抽取。**单任务双产出**——跑一次闭环，同时产出问题的解和数据基座条目。

## 开放问题

### 1. 数据基座怎么实现

数学工程单元的四阶段结构是清晰的，但实现需要：用什么数据库（ArangoDB？）？单元之间怎么关联？检索机制怎么实现（路径结构匹配）？

### 2. 抽取就是闭环本身——真的吗

"单任务双产出"是理想——跑一次闭环同时产出解和数据基座条目。但实际中，闭环的每一步需要额外记录多少东西才能成为数据基座条目？记录的成本会不会影响闭环的效率？
