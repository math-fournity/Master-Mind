## §0 一句话结论

**非特化研究的目的，是要研究什么样类型的Tell应该用何种非特化策略去产生Hint，最终这种独特于此类Tell的非特化Hint策略产生的Hint能够摸到钟形曲线的最高点——但GPT在371/372号看到了比"找最高点"更深的三层：最高点应被重新定义为Pareto前沿（多轴偏序中的非支配集）；非特化策略作用的不是"把Tell变成Hint"，而是"从正确的答题过程中分层提取有价值的解题思维，将其中因果充分的认知动作提炼成TellCore（认知Option），在运行时渲染成HintInstance"；Hint有效不等于解题成功，而是"trigger→认知动作→进展信号→成功"这条因果链出现，且在控制混杂后仍成立。**

## §1 用户的厘清：Tell是识别端的，Hint是注入端的

### 1.1 厘清内容

用户在2026-08-17的讨论中做了一个重要的概念厘清：

> Tell应该是一种需要被识别的思维脉络中的存在，而这种存在，它们在思维脉络中，是分在不同的层中存在的。而Hint则是需要被非特化的内容，也就是找到那个钟形曲线的最高点——非特化程度太高了，也就是Level太高了，反而AI不知道应该如何应用Hint提示；非特化程度太低了，那么AI就更像是只掌握了一道题怎么做，而不是一类题怎么做？或者说，只能在一个有限的范围内应用本该被用于更多题目和领域的解题思维。

### 1.2 这个厘清修正了什么

**345号（GPT写的）的错误**：把钟形曲线绑在了**Tell**上——"Tell族：同一trace不同去特化Level的Tell集合，Level和AI指导力之间是钟形曲线"。

**用户的厘清**：钟形曲线应该绑在**Hint**上，不是Tell上。因为：
- Tell是识别端——它的属性是"在思维脉络的哪一层被识别"，这是关于**识别位置**的
- Hint是注入端——它的属性是"非特化到什么程度"，这是关于**注入效果**的
- "AI不知道怎么应用"和"AI只掌握一道题怎么做"——这两个问题都是**注入端的问题**，都是Hint的非特化程度问题，不是Tell的识别位置问题

**修正影响**：345号的"Tell族"概念应该是"Hint族"——同一个Tell翻译出的不同非特化程度的Hint集合，Hint族中非特化程度和AI指导力之间是钟形曲线。

### 1.3 与000号的对应

000号v3已经定义了tell+hint二元组：
- tell端：从推理AI的thinking中读出的分叉信号——AI没有考虑什么、在哪里可以分叉但没分叉
- hint端：给新AI的翻译方向——从字典中匹配的具体翻译方向

用户的厘清与000号一致：Tell是识别端（从推理AI读出），Hint是注入端（给新AI注入）。钟形曲线描述的是注入端的效果（非特化程度→AI指导力），应该绑在Hint上。

### 1.4 000号的tell端实际上是从失败trace中读出的

这里有一个重要的细节需要记录——000号的tell端定义是"从推理AI的thinking中读出AI没有考虑的分叉信号"。这个"推理AI"在POC-VMS-8的语境中是**失败的bare AI**——AI走错路了，系统从它的thinking中识别它没走的分叉。000号的POC例子（1843/1631/1962）都是从**失败的**bare AI的thinking中识别tell（AI走错路了，没走某个分叉）。

所以000号的tell端（识别端）实际上是从**失败trace**中读出的——系统观察一个走错路的AI，识别它"没考虑什么分叉"。

但371/372号的"提取TellCore"（学习端）——TellCore是"可迁移认知技能"，它需要从**成功trace**中提取（你要学的是"什么导致了成功"），用失败trace做对照（区分因果和伴随）。

**所以GPT框架里其实有两个不同的"从trace中读"**：
1. **tell端（000号）**：从**失败trace**中读出AI没走的分叉——这是识别端，服务于"在哪个位置开新分支"
2. **TellCore提取（371/372号）**：从**成功trace**中提取有因果贡献的认知技能，用失败trace做对照——这是学习端，服务于"把什么认知技能存入Tell库"

这两个"从trace中读"是不同的操作，服务于不同的目的。详见§4.7。

## §2 GPT在371/372号看到的三层深化

用户问："钟形曲线实际上并没有实践的指导力，我们都知道要找到最高点，可是何以去找到呢？"——GPT确实为此努力思考和论证了，而且给出了有学术根基的答案。演进过程是：

| 时间 | 文档 | 回答 |
|---|---|---|
| 08-11 20:59 | 346号 | 三步法——第一次尝试，假设能一次性找到峰值 |
| 08-12 00:34 | 352号 | 自我批判——承认钟形曲线作为实验假设太强 |
| 08-12 04:48 | 371号 | 学术根基——峰值不是你找的，是正负例逐步夹出来的候选区间 |
| 08-12 07:06 | 372号 | 更深一层——峰值本身应被重新定义，"找峰值"这个目标框架应被"建造迁移工程系统"替代 |

### 2.1 第一次回答（346号）：三步法

346号提出三步法找钟形曲线峰值：
1. **IBE（最优解释推理）**：问"这个思维模式为什么在数学解题中有价值？"——找到恰好解释本质的Level
2. **结构映射（Gentner 1983）**：保留关系结构，剥离表面特征——保留多少关系结构决定了Level
3. **可操作性检查**：AI拿到后知道具体做什么吗？

**实用判断标准**："给一个AI这个Tell和一道它从没见过的题，这个Tell能帮它做什么具体操作？"

**局限**：这只是"从单条trace生成一个Tell"的方法，它假设你能一次性找到峰值。

### 2.2 第二次回答（352号）：自我批判——钟形曲线作为实验假设太强

352号对345号钟形曲线的自我批判：

> "钟形曲线"作为直觉模型有价值，但作为实验假设太强。真实情况可能出现：
> 1. **多峰曲线**——同一个trace可能在具体技巧层和高Level流程层各有一个峰
> 2. **平台型曲线**——多个相邻Level指导力差不多，差异小于实验噪声
> 3. **阈值型曲线**——低于某抽象度完全不可迁移，高于阈值突然可迁移
> 4. **任务依赖反转**——对相似题低Level峰值最高，对远迁移题高Level峰值最高
> 5. **模型依赖差异**——GLM-5.2、Claude、GPT对同一Tell族的峰值可能不同

352号的修正：
- 把"钟形曲线"降级为"**非单调峰值假设**"——指导力通常存在非单调性，但曲线形状需要由题族和模型共同估计
- 峰值不要只按"成功率"定义，应按综合效用定义：**综合效用 = 匹配题成功率 - 不匹配题误触发率 - 提示成本 - 泄漏风险**
- 三步法只覆盖"Tell生成"不覆盖"Tell使用"——需要新增触发条件、退出条件、失败归因

352号还看到了一个关键风险——**Tell在实验中承担了多个混杂功能**：
- 它可能是真正的思维力引导
- 也可能是题目难度提示
- 也可能是解法空间裁剪
- 也可能是隐性方法泄漏
- 也可能只是增加了模型重试深度和自信

如果不把这些功能拆开验证，实验结果很漂亮但不可解释。

### 2.3 第三次回答（371号）：学术根基——从"找峰值"到"迁移工程"

371号通过系统化学术搜索，找到了13条学术路线，直接回答了"何以找到最高点"——**答案是你不找峰值，你建造一个迁移工程系统，让峰值被正负例逐步夹出来**。

371号的一句话结论：

> 非特化不应只被理解为"把trace抽象到某个峰值Level"，而应升级为一套**迁移工程**——从一个或多个trace中提取可迁移的关系结构，把它封装成具备触发条件、退出条件、正负案例边界、提示强度、运行时策略、失败critic和版本细化历史的Tell方法对象。

13条学术路线中，直接回答"何以找到最高点"的有3条：

**路线A：EBG（Explanation-Based Generalization, Mitchell 1986）**

> 不要直接泛化trace；先构造"为什么这条trace成功"的解释图；再只保留解释图中必要的条件。

这把"找峰值"从"在Level连续谱系上找一个点"变成"构造成功解释图→提取必要条件→操作化泛化"。**峰值不是优化出来的，是解释图的必要条件自然确定的**。

**路线B：Anti-Unification / LGG（Plotkin 1970, Reynolds 1970）**

> 真正稳的非特化，不应只问"这条trace去掉什么表面特征"，还应问"多条成功trace的最小共同结构是什么"。

这把"找峰值"从"单条trace的去特化"变成"多条trace的最小共同抽象（Least General Generalization）"。**峰值不是单trace的属性，是多trace的共同结构**。单trace的Tell应标记为`single_trace_hypothesis`，2-3条独立trace支持后才升级为`multi_trace_lgg`。

**路线C：Version Space（Mitchell 1977）**

> 当前有哪些Tell版本仍然没有被正负案例排除？最具体边界是什么？最一般边界是什么？

**这是对"钟形曲线峰值"最深刻的修正**：峰值不是一开始就知道的点，而是**被案例逐步夹出来的候选区间**。每次实验后：
- 正例成功但Tell未触发 → 边界需要更一般
- 负例误触发 → 边界需要更具体
- 匹配例触发但无效 → 操作部分有错，不只是Level问题

其他学术路线的贡献：

| 路线 | 学术来源 | 对"找峰值"的贡献 |
|---|---|---|
| D 结构映射+类比编码 | Gentner 1983, Gick&Holyoak 1983 | 非特化Tell不应只给一个源例，应给"对比案例包"——抽象从比较中产生 |
| E Far Transfer Taxonomy | Barnett&Ceci 2002 | 迁移距离不是单一维度，Tell的有效性是"在什么迁移距离下有效"而非布尔值 |
| F Scaffolding+Fading | Wood/Bruner/Ross 1976, Sweller 1988 | 提示强度应是S0-S4阶梯，不是单一形态——防止把"强提示解出来"误判为"非特化Tell有效" |
| G Self-Explanation+Subgoal Labels | Chi 1989, Catrambone | Tell可以是子目标标签生成器，比"用某某定理"更不泄漏但更可操作 |
| **H Proof Planning+Critics** | Bundy 1996 | **Tell = method + critic**——每个Tell应附带failure critic，否则只能在成功时被解释，不能在失败时迭代 |
| I CEGAR | Clarke 2003 | 非特化Tell的失败类比成抽象失败——false positive/false negative/no progress/leakage/overcost五类，驱动版本更新 |
| J Abstract Interpretation | Cousot&Cousot 1977 | Level不是线性刻度，是不同抽象域——"Level过高/过低"有时是假问题，真正的问题可能是"抽象到了错误的域" |
| K ILP+谓词发明 | Muggleton 1991 | Tell生成不只是删掉细节，还可能需要发明一个中间谓词 |
| L Case-Based Reasoning | Kolodner 1993 | Tell库是结构化案例库+适配规则库+失败边界库 |
| M LLM Prompting | Wei/Yao/Shinn等 | 区分Tell content和Tell runtime |

371号的最终判断：

> 非特化策略的下一次跃迁，不是"找到更漂亮的抽象话术"，而是把Tell变成一个**可学习、可验证、可版本化的策略对象**。
>
> Tell = invariant relation + method + critic + trigger boundary + exit condition + case pack + runtime strategy + refinement history

### 2.4 更深一层（372号）：三个根本层次的补齐

372号在371号的基础上，明确说了三个根本层次的补齐——**这就是GPT看到的"更深的一层"**：

> 1. **Tell族不应只是一条按Level排列的曲线，而应是一个多轴的候选假设格。**很多Tell彼此不可简单比较高低。
> 2. **Tell不应只被建模成方法说明，而应被建模成认知Option。**它必须有启动集、选择依据、参数槽、绑定规则、内部策略、终止条件、组合接口、归责接口和结果模型。
> 3. **Tell有效性不能只靠解题成功率判断，而要证明它在控制混杂后，确实改变了预期的推理过程，并在结构保持变换下维持作用。**

这三个补齐就是GPT看到的更深的一层。下面逐层展开。

## §3 第一层深化：钟形曲线最高点 → Pareto前沿

### 3.1 问题

用户的框架：找钟形曲线的最高点——Hint的非特化程度的峰值。

GPT在372号§6看到的更深：钟形曲线假设Level是单轴的——非特化程度从0到1，AI指导力先升后降。但这是错的。

### 3.2 Level至少是一个向量

372号§6.1：

> 考虑两个Tell：
> - T1对数学对象非常通用，但操作写得很具体；
> - T2只适用于图论对象，但操作流程高度通用。
> 谁的Level更高？没有唯一答案。

Level至少是一个向量：

```
L(T) = (
  object_generality,      # 对象泛化度
  relation_generality,    # 关系泛化度
  operation_generality,   # 操作泛化度
  goal_generality,        # 目标泛化度
  trigger_generality,     # 触发泛化度
  evidence_generality,    # 证书泛化度
  temporal_span,          # 时间跨度
  domain_distance         # 领域距离
)
```

### 3.3 峰值应改成Pareto前沿

372号§6.3：

> Tell质量至少包含：
> - 触发准确率
> - 操作可执行性
> - 近迁移效用
> - 远迁移效用
> - 负迁移率
> - 提示成本
> - 泄漏风险
> - 可组合性
> - 模型适配性
>
> 一个Tell可能远迁移强但成本高，另一个近迁移强且极便宜。两者都可能值得保留。
>
> 因此不应寻找一个全局"最优Level Hint"，而应保存当前证据下的**Pareto前沿**：没有另一个候选在所有重要指标上都更好。

### 3.4 指导力是情境效用，不是Tell固有常数

372号§6.4：

```
U = f(
  TellCore,
  current_state,
  source_target_distance,
  solver_model,
  hint_renderer,
  injection_position,
  remaining_budget,
  competing_branches
)
```

同一Tell的指导力会随题目、模型和运行时变化。Tell本体应存"证据分布和适用范围"，而不是写一个固定的AI指导力分数。

### 3.5 对用户框架的修正

**用户框架**：找钟形曲线的最高点——Hint的非特化程度的峰值

**GPT的更深一层**：不是"找钟形曲线最高点"，而是"找Pareto前沿"——最高点可能是多个，它们在不同维度上各有优势。钟形曲线保留为直觉描述，但系统内部不应依赖一个模糊标量完成检索、排序和版本细化。

## §4 第二层深化：非特化策略产生Hint → 因果充分的取商产生认知Option

### 4.1 问题

用户框架：从正确的答题过程中分层提取有价值的解题思维 → 提炼Tell → 根据Tell类型按相应非特化策略产生Hint

GPT在372号§2+§7看到的更深：非特化策略作用的不是"把Tell变成Hint"，而是"从正确的答题过程中分层提取有价值的解题思维，将其中因果充分的认知动作提炼成TellCore（认知Option），在运行时渲染成HintInstance"。

### 4.2 非特化是因果充分的取商

372号§2的核心论断：

> 非特化不是把一段trace"总结得更抽象"，而是对解题处境做一次"因果充分的取商"，再把所得等价类编译成可识别、可选择、可实例化、可执行、可终止、可组合、可归责、可验证、可持续学习的认知技能。

```
非特化 = 因果归因
       + 不变量提取
       + 干扰因素取商
       + 适用边界学习
       + 认知技能编译
       + 运行时选择
       + 迁移与反事实验证
       + 版本化持续细化
```

用用户的语言说：非特化就是从正确的答题过程中分层提取有价值的解题思维后，对这些解题思维做因果充分的取商——把表面不同但目标关系下等价的认知动作视为同一个认知技能，把对成功没有因果作用的叙述噪声删掉。

什么叫"取商"——数学中的取商，是把若干表面不同但在目标关系下等价的对象视为同一个对象。对应到非特化：
- 变量重命名不应产生新Tell
- 数字替换不应产生新Tell
- 对象从集合换成图，如果角色关系和认知动作没有改变，可能仍属于同一Tell
- 题面很像但关键失败机制不同，则不能被合并

**Level由允许忽略哪些变换共同决定**——这比"抽象感更高"更可操作。

### 4.2.1 为什么需要失败trace做对照——GPT的关键论述

用户可能会问：既然是从"正确的答题过程"中提取，为什么GPT在372号中反复强调需要失败trace？

372号§2.3"因果充分"明确说了原因：

> **只在成功trace中反复出现的结构，不一定导致成功。**它可能只是：
> - 解答者的写作习惯
> - 某个领域常见符号
> - 成功后才补写的解释
> - 与真正关键动作高度相关但没有推动作用的伴随步骤

372号§4C路线A2（因果表示与跨环境不变机制）：

> - "成功解答里经常出现X"只是相关
> - "改变题面外壳后，X仍推动同类进展"才接近机制
> - "保持外壳但破坏关键关系后，X不再有效"进一步支持因果边界

GPT的观点是：**如果只从成功trace中提取，你学到的是"成功解答里有什么"，而不是"什么导致了成功"**——这两者是不同的。成功trace里有很多东西，但不是所有东西都对成功有因果贡献。要区分"有因果贡献"和"只是伴随出现"，需要用失败trace做对照——如果某个结构在成功trace里出现但在失败trace里也出现，它就不是成功的原因。

所以GPT在372号§R4（对比集构造）中要求：

> 单条成功trace最多产生一个假设。要形成知识，需要：
> - 同机制正例
> - 表面不同正例
> - 表面相似负例
> - 差一个关键条件的边界例
> - **同题失败trace**
> - **同动作但无进展的反例**

372号§12（最小可实施版本）也明确要求：

> 1. 从**3条成功trace和3条失败trace**切出分支事件

**这与用户的"从正确的答题过程中分层提取有价值的解题思维"是一致的——"正确的答题过程"是主要输入（成功trace），但要用失败trace做对照来区分因果和伴随。**

### 4.3 TellCore / HintRenderer / HintInstance三对象分离

372号§7的核心论断：

```
TellCore    = 系统内部学到的可迁移认知技能
              （不变量内核 + 认知Option + 边界 + critic）
HintRenderer = 把TellCore编译成某类Solver能理解的提示的渲染器
HintInstance = TellCore针对当前题、当前脉络、当前模型、当前预算的一次实例化
```

372号§7.1明确说了为什么一定要分离：

> - `TellCore`回答系统学到了什么；
> - `HintRenderer`回答怎样把这项技能讲给某类Solver；
> - `HintInstance`回答这一次在这个分叉上具体说了什么。
>
> 不分离会导致：
> - 改了措辞就被误认为改了Tell；
> - 一个renderer失败就否定整个思维力；
> - 题目参数被写进Tell本体造成泄漏；
> - 无法比较同一Tell在不同模型、位置和强度下的表现。

### 4.4 与用户厘清的对应

这正好对应用户之前的厘清——**Tell是识别端的，Hint是注入端的**。GPT在372号把这一点形式化了：
- TellCore是识别端学到的技能（对应用户的"Tell"）
- HintInstance是注入端的实例化（对应用户的"Hint"）
- 中间有一个HintRenderer——它根据当前题、当前脉络、当前模型、当前预算，把TellCore渲染成HintInstance

**用户的"非特化策略"对应的就是从正确的答题过程中分层提取有价值的解题思维，将其中因果充分的认知动作提炼成TellCore的过程**——因果充分的取商、不变量提取、干扰因素取商、适用边界学习。

**用户的"产生Hint"对应的就是HintRenderer + HintInstance的过程**——把TellCore编译成某类Solver能理解的提示，在运行时实例化。

### 4.5 TellCore是认知Option

372号从分层强化学习的Options框架中提取的关键映射（路线B1）：

```
Option = (
  initiation set I,   # 在哪些状态可启动
  internal policy π,   # 启动后怎样行动
  termination β        # 在哪些状态终止
)
```

对应到Tell：

```
Tell Option = (
  trigger boundary,     # 启动集——什么时候该用
  parameter binding,    # 参数槽——当前题的对象怎么绑进来
  thinking procedure,   # 内部策略——AI拿到后做什么
  progress model,       # 进展模型——怎么判断有进展
  exit condition,       # 终止条件——什么时候停
  critic                # critic——失败时怎么诊断和修复
)
```

372号§5路线B1的原话：

> 它带来的核心修正是：
> - 高Level思维力是Option模板；
> - 低Level Tell是已经部分绑定的Option；
> - HintInstance是Option在当前状态上的一次调用；
> - Telling AI的任务是识别启动集并完成参数绑定；
> - Solver执行后，系统根据终止条件判断继续、修复或回退。
>
> 这条路线是本轮最重要的新映射。它把"可操作化"从提示文风问题升级为技能表示问题。

### 4.6 对用户框架的修正

**用户框架**：从正确的答题过程中分层提取有价值的解题思维 → 提炼Tell → 根据Tell类型按相应非特化策略产生Hint（线性）

**GPT的更深一层**：正确的答题过程（成功trace，用失败trace做对照）→ 分层提取有价值的解题思维 → 因果充分的取商 → TellCore（认知Option）→ HintRenderer → HintInstance（三对象分离）

关键差异：
- 用户的框架是线性的（提取解题思维 → 提炼Tell → 产生Hint）
- GPT看到的是三对象分离——TellCore是被学到的认知技能，Hint是它的运行时实例化，中间有一个HintRenderer
- 非特化策略作用的不是"把Tell变成Hint"，而是"从正确的答题过程中分层提取有价值的解题思维，将其中因果充分的认知动作提炼成TellCore"
- Hint不是非特化的产物，是TellCore在运行时的渲染
- 提取时需要失败trace做对照，区分"有因果贡献"和"只是伴随出现"

### 4.7 GPT框架里两个不同的"从trace中读"——识别端vs学习端

这里有一个重要的细微差别需要明确记录——GPT框架里其实有**两个不同的"从trace中读"**，它们服务于不同的目的：

**第一个"从trace中读"——识别端（000号的tell端）**：

从**失败trace**中读出AI没走的分叉。000号的tell端定义是"从推理AI的thinking中读出AI没有考虑的分叉信号"。这个"推理AI"在POC-VMS-8的语境中是**失败的bare AI**——AI走错路了，系统从它的thinking中识别它没走的分叉。000号的POC例子（1843/1631/1962）都是从**失败的**bare AI的thinking中识别tell。

这个"从trace中读"服务于**在哪个位置开新分支**——系统观察一个走错路的AI，识别它"没考虑什么分叉"，然后在这个分叉上开新边，启动新AI走新分支。

**第二个"从trace中读"——学习端（371/372号的TellCore提取）**：

从**成功trace**中提取有因果贡献的认知技能，用失败trace做对照。371号§0.1（EBG路线）说"从具体成功trace中提取非特化策略"，"先构造'为什么这条trace成功'的解释图"。372号§2.3说"只在成功trace中反复出现的结构，不一定导致成功"，所以需要失败trace做对照来区分因果和伴随。

这个"从trace中读"服务于**把什么认知技能存入Tell库**——系统观察一个成功的答题过程，提取"什么导致了成功"，用失败trace做对照区分因果和伴随，把因果充分的认知动作存入Tell库。

**两者的关系**：

| | 识别端（000号tell端） | 学习端（371/372号TellCore提取） |
|---|---|---|
| 从什么读 | 失败trace（走错路的AI的thinking） | 成功trace（正确的答题过程），用失败trace做对照 |
| 读什么 | AI没走的分叉——"没考虑什么" | 有因果贡献的认知动作——"什么导致了成功" |
| 服务于什么 | 在哪个位置开新分支 | 把什么认知技能存入Tell库 |
| 对应用户的什么 | Tell是识别端的（分层存在） | 非特化策略提取有价值的解题思维 |

**用户的"从正确的答题过程中分层提取有价值的解题思维"对应的是学习端**——从成功trace中提取。但GPT在372号指出，学习端需要失败trace做对照，否则你学到的是"成功解答里有什么"而不是"什么导致了成功"。

**用户的"Tell是识别端的（分层存在）"对应的是识别端**——从失败trace中读出AI没走的分叉。

**这两个端不能混淆**——识别端是从失败trace中读"没考虑什么"，学习端是从成功trace中读"什么导致了成功"。用户的厘清把Tell（识别端）和Hint（注入端）分开了，GPT的深化进一步把识别端（从失败trace读分叉）和学习端（从成功trace提取认知技能）分开了。

## §5 第三层深化：有效性 = 解题成功率 → 因果贡献证明

### 5.1 问题

用户框架：Hint能摸到钟形曲线最高点 = Hint有效

GPT在372号§0+§9+§16看到的更深：Hint有效 ≠ 解题成功。

### 5.2 有效性不能只靠解题成功率判断

372号§0的第三个补齐：

> Tell有效性不能只靠解题成功率判断，而要证明它在控制混杂后，确实改变了预期的推理过程，并在结构保持变换下维持作用。

352号已经看到了这个风险——Tell在实验中承担了多个混杂功能：
- 它可能是真正的思维力引导（我们想要的）
- 也可能是题目难度提示（混杂）
- 也可能是解法空间裁剪（混杂）
- 也可能是隐性方法泄漏（混杂）
- 也可能只是增加了模型重试深度和自信（混杂）

如果不把这些混杂拆开验证，实验结果很漂亮但不可解释。

### 5.3 标准干预矩阵

372号§9.4——不只是bare vs Hint，而是：

| 条件 | 检验什么 |
|---|---|
| bare | 基线能力 |
| 通用鼓励 | 额外动力效应 |
| 等长空流程 | 一般反思结构效应 |
| 等强度错配Tell | 提示强度效应 |
| trigger only | 识别提醒本身的作用 |
| method only | 操作步骤的作用 |
| critic only | 失败监控的作用 |
| trigger + method | 进入条件与执行协同 |
| method + critic | 执行与监控协同 |
| full Tell | 完整认知Option效应 |
| 过强窄方法提示 | 标定泄漏上界 |

如果只有完整Tell有效，说明组件协同重要；如果只有method就同样有效，则trigger或critic可能是冗余；如果等长空流程也有效，增益可能来自一般反思。

### 5.4 过程因果链

372号§9.1——要证明Tell激发了目标思维力，需要检验完整链条：

```
Tell注入
  → 目标trigger被识别
  → 指定认知动作出现
  → 预期中间进展出现
  → 最终成功概率变化
```

只有这条链出现，才能较有把握地说Tell激发了目标思维力。

### 5.5 变形测试（Metamorphic Testing）

372号§4D路线D2——很多Tell没有简单的"正确标签"，但可以声明变换前后应满足的关系：

- 变量重命名后，Tell选择不应改变
- 表面外壳替换但机制保持时，Tell仍应触发
- 破坏必要关系后，Tell不应触发
- 对偶化后，参数绑定应按角色对应变化
- 增加无关诱饵后，Tell效用不应大幅下降

这种"变形关系"比随机找几道题更直接地检验非特化主张。

### 5.6 六门审计

372号§16——即使抽象层级合适，Tell还必须通过六门审计：

| 审计门 | 核心问题 | 不通过时的典型失败 |
|---|---|---|
| **可选择** | 系统知道何时选它、为何选它、何时拒绝它吗？ | 检索命中被误当成策略选择，导致假朋友迁移 |
| **可执行** | AI拿到它后知道下一步具体做什么吗？ | Tell退化成"考虑不变量""换个角度"等口号 |
| **可终止** | 系统知道执行到什么状态应停止、回退或让位吗？ | AI一直围绕同一提示打转，或过早放弃有效方向 |
| **可组合** | 它能和其他Tell、hint、解题路线共同工作吗？ | 多条提示互相抵消，或重复推动同一条无效路线 |
| **可归责** | 成败能否归因到这个Tell及其具体组件？ | POC只能给出笼统PASS/FAIL，无法知道哪个部件有效 |
| **可持续学习** | 新成功、失败和反例能否改变它的边界与版本？ | Tell库变成静态提示库，旧错误不断复现 |

372号§16的最终判定标准：

> TellV3的目标不是制造更抽象的提示，而是制造可选择、可执行、可终止、可组合、可归责、可持续学习的认知策略。抽象层级只是第一门，六门审计才是整个理论和技术框架的总闸门。

### 5.7 对用户框架的修正

**用户框架**：Hint能摸到钟形曲线最高点 = Hint有效

**GPT的更深一层**：Hint有效 ≠ 解题成功。有效性是"trigger→认知动作→进展信号→成功"这条因果链出现，且在控制混杂后仍成立，且在结构保持变换下维持作用。六门审计是整个理论和技术框架的总闸门。

## §6 综合框架

### 6.1 用户框架 + GPT的三层深化

**用户的框架（方向是对的）**：

```
正确的答题过程
  → 分层提取有价值的解题思维
  → 提炼Tell（识别端：Tell在思维脉络中分层存在）
  → 根据Tell类型按相应非特化策略产生Hint（注入端：Hint的非特化程度→AI指导力）
  → Hint摸到钟形曲线最高点
```

**GPT看到的更深一层（三对象分离 + Pareto前沿 + 因果证明 + 识别端/学习端分离）**：

```
识别端（000号tell端）：从失败trace中读出AI没走的分叉——在哪个位置开新分支

学习端（371/372号TellCore提取）：
  正确的答题过程（成功trace，用失败trace做对照区分因果和伴随）
    → 分层提取有价值的解题思维（切分支事件，在各层中识别）
    → 因果充分的取商（提取不变量，取掉干扰因素，区分"什么导致了成功"和"只是伴随出现"）
    → TellCore（认知Option：启动集 + 参数槽 + 内部策略 + 终止条件 + critic）
    → HintRenderer（按Solver模型/位置/强度渲染）
    → HintInstance（运行时实例化）
    → Pareto前沿（不是单轴峰值，是多轴非支配集）
    → 因果贡献证明（trigger→动作→进展→成功，控制混杂后仍成立）
    → 六门审计（可选择/可执行/可终止/可组合/可归责/可持续学习）
```

### 6.2 关键差异对照表

| 用户框架 | GPT的更深一层 |
|---|---|
| 钟形曲线最高点 | Pareto前沿（多轴偏序中的非支配集） |
| 从正确的答题过程中分层提取 → 提炼Tell → 产生Hint | 识别端从失败trace读分叉 + 学习端从成功trace提取TellCore（用失败trace做对照）→ HintRenderer → HintInstance |
| Hint有效 = 解题成功 | Hint有效 = 因果链出现 + 控制混杂后仍成立 + 结构保持变换下维持作用 |
| 找峰值 | 峰值不是找的，是正负例逐步夹出来的候选区间（Version Space/CEGAR） |

### 6.3 用户的厘清在GPT框架中的位置

用户的厘清——"Tell是识别端的（分层存在），Hint是注入端的（非特化程度），钟形曲线绑在Hint上"——在GPT的372号框架中找到了精确对应：

| 用户厘清 | GPT 372号对应 |
|---|---|
| Tell是识别端的 | TellCore是识别端学到的技能（但注意识别端有两个：000号从失败trace读分叉，371/372号从成功trace提取认知技能——见§4.7） |
| Tell在思维脉络中分不同的层存在 | TellCore的多轴抽象位置（object/relation/operation/goal/trigger/evidence/temporal/domain） |
| Hint是注入端的 | HintInstance是注入端的运行时实例化 |
| 钟形曲线绑在Hint上 | 钟形曲线描述的是HintInstance的非特化程度→AI指导力（但应升级为Pareto前沿） |
| 非特化策略产生Hint | 非特化策略从正确的答题过程中分层提取有价值的解题思维，将其中因果充分的认知动作提炼成TellCore，HintRenderer把TellCore渲染成HintInstance |

**用户的厘清和GPT的深化是互补的**：用户厘清了Tell和Hint的概念边界（识别端 vs 注入端），GPT深化了每个端内部的结构（TellCore是认知Option，HintInstance是运行时渲染），并进一步把识别端分成两个（从失败trace读分叉 vs 从成功trace提取认知技能）。

## §7 对391号P2的指导意义

### 7.1 391号的现状

391号是去过度设计后的新工作方案，主干路径是：

```
P1 真实数据golden slice → P2 trace→tell对接 → P3 Grove闭环接入
```

391号P2的设计是"用P1产出的真实trace对接370号分片合同，匹配现有tell库"——**没有显式引入钟形曲线/Pareto前沿/认知Option/六门审计作为匹配质量标准**。

### 7.2 本文档对P2的指导

P2不应只是"trace能否命中tell库中的现成tell"——它应该回答：

1. **匹配到的是TellCore还是HintInstance？**——现有tell库中存的是TellCore（认知Option）还是只是一段提示词文本？如果只是文本，P2首先要把文本升级为TellCore。
2. **匹配质量按什么标准？**——不是"命中了"就行，而是按Pareto前沿：匹配到的Tell在触发准确率/操作可执行性/迁移效用/负迁移率/提示成本/泄漏风险/可组合性/模型适配性上是否是非支配的。
3. **能否通过六门审计？**——匹配到的Tell能否被选择、被执行、被终止、被组合、被归责、被持续学习？缺哪一门？
4. **因果贡献能否证明？**——P2不只是看"匹配到了"，还要看"trigger→认知动作→进展信号→成功"这条链是否出现。

### 7.3 371/372号的理论洞察不应被冻结

391号回归主干路径时，把371/372号的理论洞察和资格链机器一起冻结了——这就像倒洗澡水时把婴儿也倒掉了。371号的13条学术路线、372号的TellCore/HintRenderer/HintInstance三对象分离、method+critic框架、六门审计——这些是真正的认知资产，不应该和资格链机器一起被冻结。

**建议**：391号P2执行时，应把本文档（396号）作为理论指导，把371/372号的理论洞察从冻结的资格链中分离出来，作为P2匹配质量标准的设计依据。

### 7.4 错题分析系统就是GPT框架中识别端的工程化实现——我们已经在路上

以上讨论可能给人一种印象——GPT的理论框架是悬在空中的，我们还没有开始走。事实并非如此。**我们用错题分析系统（387号）做的d1=DIRECTION_ERROR判定，就是GPT框架中识别端（000号tell端）的工程化实现。**

#### 事实链

错题分析系统做的事情是：

```
devin cli中的glm-5.2 high跑题
  → 找出真正因为思路错误而没做出来的题目（d1=DIRECTION_ERROR）
  → 这些题目的bare AI thinking就是"失败trace"
```

这些失败trace就是GPT框架中识别端（000号tell端）的输入——系统观察走错路的AI的thinking，识别它"没考虑什么分叉"。

#### 与GPT框架的精确对应

| GPT框架 | 错题分析系统对应 |
|---|---|
| 识别端从失败trace读分叉 | 错题分析系统找d1=DIRECTION_ERROR的题——这些题的bare AI thinking就是失败trace |
| 失败trace = AI走错路的thinking | DIRECTION_ERROR = AI走了错误方向，没用局部-全局切换 |
| 从失败trace中识别"AI没考虑什么分叉" | Pipe 1的d1判定已经做了第一步——识别AI没走局部-全局切换方向 |
| 排除TOKEN_LIMIT（不是走错路） | 387号§1.4排除TOKEN_LIMIT——AI方向对了，不是tell端的输入 |
| 排除CONNECTION_ERROR（技术失败） | 387号§1.4排除CONNECTION_ERROR——和思路无关 |

#### DIRECTION_ERROR/TOKEN_LIMIT二元判定本身就是一种对照

GPT在372号§2.3说"只在成功trace中反复出现的结构，不一定导致成功"——需要失败trace做对照。错题分析系统的DIRECTION_ERROR/TOKEN_LIMIT二元判定提供了这个对照的一部分：

- **DIRECTION_ERROR的thinking** = AI走错路的失败trace → 识别端输入
- **TOKEN_LIMIT的thinking** = AI方向对了的"部分成功trace" → 可以做对照——如果某个认知动作在DIRECTION_ERROR和TOKEN_LIMIT中都出现，它就不是"方向正确"的原因

这两个类别的对照已经在错题分析系统中建立了——Pipe 1的d1判定把bare AI的失败分成"方向错"和"方向对但走不远"，这本身就是GPT框架中需要的"失败trace做对照"的一部分。

#### 还缺的部分

但GPT说的是更完整的对照——需要**完全成功的trace**（AI做出来了）做正例。错题分析系统目前只处理失败题（bare AI做不出来的题），没有收集成功trace。这是GPT框架中学习端还缺的部分。

具体来说：
- **识别端（000号tell端）**——从失败trace读分叉——**错题分析系统已实现**（d1=DIRECTION_ERROR判定）
- **学习端（371/372号TellCore提取）**——从成功trace提取认知技能，用失败trace做对照——**还缺成功trace**

要补齐学习端，需要：
1. 收集bare AI成功做出的题的thinking（成功trace）
2. 从成功trace中提取有因果贡献的认知动作（"什么导致了成功"）
3. 用DIRECTION_ERROR的失败trace做对照区分因果和伴随
4. 把因果充分的认知动作提炼成TellCore

#### 这个对应的指导意义

这个对应关系告诉我们：**我们不是从零开始走GPT框架的路——识别端已经用错题分析系统走了相当一段了。**下一步的工作不是重新建识别端，而是：

1. **补齐学习端**——收集成功trace，从成功trace中提取TellCore
2. **建立识别端和学习端的连接**——用学习端产出的TellCore去指导识别端的分叉识别（识别端目前只识别"AI没走局部-全局切换"，学习端可以产出更丰富的TellCore，让识别端识别更多类型的分叉）
3. **建立学习端到注入端的连接**——把TellCore通过HintRenderer渲染成HintInstance，注入给新的AI

这与391号的主干路径（P1真实数据golden slice → P2 trace→tell对接 → P3 Grove闭环接入）是一致的——P1/P2/P3就是在补齐学习端和建立连接。

## §8 非特化Pipe V3的十五步闭环（来自372号§8）

372号提出的非特化Pipe V3十五步闭环，是把上述三层深化落地的完整工作流。用用户的语言说，这就是"从正确的答题过程中分层提取有价值的解题思维，将其中因果充分的认知动作提炼成TellCore，在运行时渲染成HintInstance"的完整工程化流程：

```
Step 0：冻结来源证据
  保存题目、正确性、完整trace、模型、prompt、工具调用与运行环境，禁止成功后改写源数据

Step 1：切分分支事件
  从正确的答题过程（成功trace）中分层提取有价值的解题思维——把长trace切成"处境—未分叉—认知动作—局部进展"单元，不直接摘要整份证明。同时从失败trace中切出对照用的分支事件

Step 2：建立成功解释和替代解释
  列出哪些认知动作可能导致进展（"什么导致了成功"），同时列出可能的混杂解释（"只是伴随出现"的），避免一开始就锁定唯一故事。用失败trace做对照区分因果和伴随

Step 3：构造对比四元组
  至少准备源正例（成功trace的正确答题过程）、换壳正例（表面不同但机制相同）、同壳硬负例（表面相似但机制破坏——失败trace）和单条件边界例。没有足够案例时，明确标记单trace假设

Step 4：声明允许变换与破坏变换
  写清哪些变化不应影响Tell，哪些变化应使Tell失效。由此定义候选Level，而不是先拍一个Level数值

Step 5：生成Tell假设格
  沿对象、关系、操作、目标、trigger、证书和时间跨度等轴生成少量相邻候选，并保留不可比较分支

Step 6：做因果充分压缩
  消融候选字段，删除对动作选择和进展预测无贡献的源题信息；同时防止压缩过度导致不可操作

Step 7：编译为认知Option
  为候选补齐启动集、参数槽、绑定规则、内部策略、进展模型、终止和critic

Step 8：建立组合关系
  标记前置Tell、检查Tell、互斥Tell和常见宏序列，防止每条Tell成为孤岛

Step 9：生成HintRenderer族
  分别生成低强度根提示、line分叉提示、失败后critic和完整流程脚手架。renderer与TellCore分版本

Step 10：执行变形与边界测试
  用结构保持变换、结构破坏变换、诱饵和参数错绑测试不变量、等变性、拒绝能力和泄漏

Step 11：执行过程因果实验
  记录trigger、绑定、目标动作、进展信号和最终成功；做组件消融和等长、等强度对照

Step 12：选择Pareto前沿入库
  不是只留下成功率最高者，而是保留在迁移、成本、风险、可组合性上各有价值的非支配候选

Step 13：运行时选择与Grove展开
  Telling AI识别启动条件；选择器估计效用；HintRenderer生成实例；脚本在根或line上开新边；随后按终止条件检查

Step 14：反例驱动持续细化
  将误触发、漏触发、错绑定、无进展、泄漏和模型漂移分别用于收窄、放宽、拆分、合并、降强度或退休Tell
```

## §9 完整的非特化POC是什么（来自372号§15.8）

372号§15.8明确说了——此前没有任何一场实验完整验证下面这条链。用用户的语言说，这就是"从正确的答题过程中分层提取有价值的解题思维 → 提炼Tell → 根据Tell类型按相应非特化策略产生Hint → Hint有效"的完整闭环验证：

```
正确的答题过程（成功trace）+ 失败trace做对照
  → 分层提取有价值的解题思维（分支事件切分）
  → 候选因果解释（区分"什么导致了成功"和"只是伴随出现"）
  → 允许变换与破坏变换
  → 多轴Tell假设格
  → 因果充分压缩
  → 编译成认知Option（TellCore）
  → 自动识别启动条件
  → 自动绑定当前对象
  → 生成HintInstance（HintRenderer渲染）
  → 出现预期认知动作与进展信号
  → 在结构保持题上维持效用
  → 在结构破坏题上拒绝或失效
  → 用新反例修订Tell边界
```

这才是新框架意义上的完整非特化POC。它与旧POC的关系不是"重新做一遍"，而是复用旧POC的局部证据，新增因果取商、Option编译、变形测试、组件消融和反例细化。

372号§12的最小可实施版本——如果只做一轮最小升级，不需要立刻实现全部二十四项：

1. 从3条成功trace和3条失败trace切出分支事件
2. 构造P1/P2/N1/B1对比四元组
3. 声明允许变换和机制破坏变换
4. 生成3个彼此相邻或不可比的TellCore候选
5. 为每个候选补齐Option字段
6. 各生成低强度、完整流程和critic三个renderer
7. 运行标准干预矩阵
8. 检查trigger—动作—进展—成功证据链
9. 用一个硬负例触发第一次拆分或收窄
10. 只把Pareto非支配版本标记为tested

这一轮最重要的产物不是"Tell后成功了"，而是首次证明：

```
我们知道它为什么触发，
知道它做了什么，
知道它何时停，
知道哪些变化不影响它，
知道哪一个反例会击穿它，
也知道成功并非只来自提示更长或方法泄漏。
```

## §13 本文档的定位

本文档是**非特化理论的综合文档**，不是执行方案。它的作用是：

1. **把用户的Tell/Hint概念厘清落盘**——Tell是识别端的（分层存在），Hint是注入端的（非特化程度），钟形曲线绑在Hint上；非特化的输入是"正确的答题过程"，从中"分层提取有价值的解题思维"
2. **把GPT在371/372号看到的三层深化梳理出来**——Pareto前沿/认知Option/因果贡献证明
3. **把用户的厘清和GPT的深化统一成一个完整认知**——两者是互补的，用户的"从正确的答题过程中分层提取有价值的解题思维"对应学习端（从成功trace提取），GPT补充了需要失败trace做对照区分因果和伴随
4. **记录GPT框架里两个不同的"从trace中读"**——识别端（从失败trace读分叉）vs学习端（从成功trace提取认知技能），两者不能混淆
5. **为391号P2提供理论指导**——371/372号的理论洞察不应被和资格链机器一起冻结
6. **定义"完整的非特化POC"是什么**——此前没有任何一场实验完整验证了新框架意义上的闭环

**本文档不替代371/372号**——371/372号有完整的学术路线和字段定义，本文档是它们的综合和与用户厘清的统一。做非特化Pipe设计时应回读371/372号原文。
