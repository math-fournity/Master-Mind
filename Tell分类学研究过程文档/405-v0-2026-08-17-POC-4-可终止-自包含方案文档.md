一份POC方案文档要让未来20万上下文的AI**只加载这份文档+它索引的少数核心文档**，就能完整了解做好这次POC所需的所有背景知识，不需要用户另外指点应该读什么。

### 0.3 "自包含"的含义

"自包含"不是把所有背景知识复制进文档——那样文档会膨胀到无法加载。"自包含"是指：

1. **文档本身包含这个POC执行所需的全部操作信息**——输入/方法/输出/通过标准/执行约束
2. **文档明确列出需要全文加载的背景文档清单**——每份说明加载理由（这个POC为什么需要这份文档的内容）
3. **未来AI加载这份POC方案后，按照§8清单去全文加载被索引的文档**——不需要用户另外指点

### 0.4 被索引文档的精挑细选原则

每份POC方案文档的§8清单应该精挑细选——只列这个POC真正需要的背景文档，通常3-7份。如果索引太多，未来AI加载不完。

**挑选标准**：
- **必须加载**：这个POC不加载这份文档就无法正确执行（如题包/TellCore定义/通过标准来源）
- **建议加载**：这个POC加载这份文档能更好理解为什么这么做（如理论背景/原设计文档）
- **不列**：这个POC不需要这份文档的内容（如其他POC的方案文档）

### 1.3 核心问题

**POC-4回答**：

> Tell被启动后，系统是否知道何时继续、停止、回退或让位？

这是防止高Level Tell变成无限反思陷阱的关键POC。一个Tell如果不能正确终止——要么过早退出有效方向，要么在无进展时反复打转，要么在边界冲突时强行使用——那它就不是可被运行时调度的认知策略，而是一个失控的提示。

### 1.4 为什么在Phase B的最后

POC-4排在Phase B基础验证的最后，因为它依赖前面的基础已经成立：

- POC-2.5确认了Hint有基础因果效应（如果Hint无效，终止行为没有意义）
- POC-3确认了AI拿到HintInstance后会执行预期认知动作（如果AI不执行，终止无从谈起）
- POC-3.5确认了不同非特化程度的HintInstance有差异（终止行为也受HintInstance强度影响）

只有这些基础成立后，测试终止行为才有意义——你需要知道"有效场景下Tell确实有效"和"AI确实在执行Tell"这两个前提，才能判断"终止行为是否正确"。

## §2 理论背景——为什么需要这个POC

### 2.1 防止高Level Tell变成无限反思陷阱

372号§16六门审计中的**可终止门**明确指出：

> 高Level思维力是Option模板——它有启动集（initiation set）、内部策略（internal policy）和终止条件（termination β）。如果终止条件缺失或不正确，Tell会变成无限反思陷阱——AI一直围绕同一提示打转，或过早放弃有效方向。

这是真实的失败模式。一个高Level Tell（如"切换到局部表示"）如果没有明确的终止条件：
- **过早退出**：AI刚进入局部表示就退出，还没找到不变量就放弃了
- **无限打转**：AI在局部表示下反复尝试但无进展，不知道应该停止或回退
- **强行使用**：边界冲突场景中（negative boundary出现），AI仍然强行使用目标Tell而不是让位给其他策略

### 2.2 396号§4.5——Tell是认知Option，终止条件是Option的关键组成

396号§4.5引用了372号的Options框架映射：

```
Tell Option = (
  trigger boundary,     # 启动集——什么时候该用
  parameter binding,    # 参数槽——当前题的对象怎么绑进来
  thinking procedure,   # 内部策略——AI拿到后做什么
  progress model,       # 进展模型——怎么判断有进展
  exit condition,       # 终止条件——什么时候停
  critic                # critic——失败时怎么诊断和修复
)
```

POC-4验证的就是`exit condition`——终止条件。一个认知Option如果没有正确的终止条件，它就不是一个可被运行时调度的策略，因为运行时不知道何时该停止这个Option、回退到搜索或让位给另一个Option。

### 2.3 397号§1.5的审视结论

397号§1.5审视了373号的POC-4设计，结论是：

> **合理。**防止高Level Tell变成无限反思陷阱——这是真实的失败模式。通过标准（有效场景中不应过早退出/无进展场景中不应一直重复同一动作/边界冲突场景中不应强行使用目标Tell/退出理由必须能落到progress model或negative boundary/让位时要说明被哪个Tell接管）是合理的。**无过度设计。**

POC-4原设计保持不变，直接采用。

### 2.4 终止行为的三个判定依据

TellCore v0的7字段中，与终止直接相关的有两个：

1. **progress_model**——进展模型。它定义了"什么算有进展"（如"引入新表示→比较原表示与新表示→找到不变量→产生可验证lemma"）。如果progress model预期的中间信号出现，应该继续；如果不出现，应该考虑退出。

2. **negative_boundary**——负边界。它定义了"什么情况下不应使用目标Tell"。如果negative boundary被触发（如题目的关键结构与Tell假设的不变量不兼容），应该停止或让位。

POC-4验证的就是：**AI的终止决策是否能正确落到这两个依据上**——退出时能说清楚是"progress model没有预期的进展信号"还是"negative boundary被触发"，而不是"我累了"或"我试了很多次"。

### 2.5 不验证会留下什么gap

如果不做POC-4：
- POC-6可归责无法正确归因——如果AI在有效场景中过早退出导致失败，这个失败会被错误归因到"Tell无效"，而实际原因是"终止条件错误"
- POC-8端到端闭环无法成立——闭环中Tell需要在多个场景中正确终止才能让循环转起来，如果终止行为错误，循环会卡住或走偏
- TellStrategy不能被称为"可被运行时调度的认知策略"——没有正确终止条件的Option不是可调度的

## §4 输入——这个POC需要什么

### 4.1 题包——三类场景题

从382号CasePack v0的22道题中取三类场景题（373号§9.2）：

**第一类：有效场景题（2-3道）**

从正迁移题中选取——这些题bare失败、目标Tell是低搜索成本主路、过程可观察。在有效场景中，预期行为是**继续执行直到出现证书或主路线**。

选取标准：
- 已确认bare失败（POC-2.5已验证）
- 已确认Hint+vein能成功（POC-2.5已验证）
- 目标认知动作可观察（POC-3已验证）
- thinking中能看见progress model预期的中间信号

**第二类：无进展场景题（2-3道）**

需要构造或选取——这些题在目标Tell启动后，progress model预期的中间信号不出现。在无进展场景中，预期行为是**观察到无进展信号后退出**。

构造方式：
- 选取目标Tell结构适用但难度过高的题——AI切换到局部表示后找不到不变量
- 或选取目标Tell结构适用但需要额外条件的题——AI切换到局部表示后发现局部表示本身不够用
- 关键：这些题不是"目标Tell不适用"（那是假朋友题），而是"目标Tell适用但进展不顺利"

**第三类：边界冲突场景题（2-3道）**

从边界题中选取——这些题只改一个关键条件，使negative boundary被触发。在边界冲突场景中，预期行为是**停止使用目标Tell或让位给其他策略**。

选取标准：
- 来自382号CasePack v0的边界题（3道）
- negative_boundary被触发——题目的关键结构与Tell假设的不变量不兼容
- 系统应识别negative boundary并停止或让位

### 4.2 TellCore

383号确定的TellCore v0候选C（局部-全局表示切换），7字段最小充分集：
1. invariant_claim
2. trigger_boundary
3. negative_boundary
4. parameter_slots
5. internal_policy
6. progress_model
7. termination

POC-4重点使用**progress_model**和**negative_boundary**字段作为终止判定的依据，以及**termination**字段本身。

### 4.3 HintInstance

由HintRenderer把TellCore v0渲染成HintInstance。POC-4使用POC-3.5确定的**中等非特化程度的HintInstance**（钟形曲线峰值附近）——因为这个强度的HintInstance在POC-3中已经确认能让AI执行预期认知动作，适合测试终止行为。

### 4.4 Solver模型

主模型：GLM-5.2 High（通过solver_harness启动）

### 4.5 脉络（vein）

从source trace题提取脉络。有效场景和无进展场景需要脉络（让AI进入Tell的执行上下文），边界冲突场景可能需要部分脉络或不需要脉络（测试系统是否能从脉络中识别negative boundary）。

## §5 方法——这个POC怎么做

### 5.1 实验设计

对三类场景题，每类2-3道，测试终止行为（373号§9.2）：

| 场景 | 给AI什么 | 预期终止行为 | 验证什么 |
|---|---|---|---|
| **有效场景** | 题目+脉络+HintInstance | 继续执行，直到出现证书或主路线 | 不应过早退出 |
| **无进展场景** | 题目+脉络+HintInstance | 观察不到progress signal时退出 | 不应一直重复同一动作 |
| **边界冲突场景** | 题目+脉络+HintInstance | negative trigger出现时停止或让位 | 不应强行使用目标Tell |

### 5.2 观察指标

每个run记录（373号§9.3 TerminationEvidence结构）：

- **expected_termination**：预期终止行为（继续/退出/让位）
- **observed_progress**：实际观察到的progress model预期信号
- **stop_or_continue_decision**：AI实际的停止/继续决策
- **decision_time**：做出决策的时间点（在thinking的哪个阶段）
- **replacement_tell**：让位时是否说明被哪个Tell接管（或为什么abstain）
- **outcome**：最终结果（成功/失败/部分成功/超时）

### 5.3 判定逻辑

**有效场景**：
- **通过**：AI继续执行，progress model预期信号陆续出现，最终完成或出现明确主路线
- **失败（过早退出）**：AI在progress model预期信号尚未出现时就退出——这不是"Tell无效"，而是"终止条件错误"
- **失败（无限打转）**：AI在有效方向上反复尝试但无法推进——可能progress model定义不够清晰，AI不知道"什么算有进展"

**无进展场景**：
- **通过**：AI观察到progress model预期信号不出现后，主动退出或回退——说明终止条件正确
- **失败（无限打转）**：AI在无进展状态下反复重复同一动作（如反复切换表示但不找不变量）——说明终止条件缺失
- **失败（误判退出）**：AI在有微弱进展时就退出——说明progress model定义过严

**边界冲突场景**：
- **通过**：AI识别negative boundary被触发，停止使用目标Tell或让位给其他策略，并说明被哪个Tell接管——说明negative_boundary字段有效
- **失败（强行使用）**：AI无视negative boundary，强行使用目标Tell——说明negative_boundary字段不够明确或AI没有读它
- **失败（误判让位）**：AI在不是negative boundary的情况下也让位——说明negative_boundary过宽

### 5.4 操作步骤

1. 从382号CasePack v0取2-3道有效场景题（从正迁移题中选）
2. 构造或选取2-3道无进展场景题（目标Tell适用但进展不顺利）
3. 从382号CasePack v0取2-3道边界冲突场景题（从边界题中选）
4. 从383号TellCore v0用HintRenderer生成中等非特化程度的HintInstance
5. 从382号source trace题提取脉络
6. 对每道场景题，通过solver_harness启动run（题目+脉络+HintInstance）
7. 记录每个run的终止行为（expected_termination/observed_progress/stop_or_continue_decision/decision_time/replacement_tell/outcome）
8. 按§5.3的判定逻辑分析结果
9. 产出TerminationEvidence

### 5.5 与POC-3的关键差异

POC-3验证的是"AI是否执行了预期认知动作"，POC-4验证的是"AI执行后是否知道何时停止"。两者的关注点不同：

| | POC-3 可执行 | POC-4 可终止 |
|---|---|---|
| 问题 | AI执行了预期认知动作吗？ | AI知道何时停止执行吗？ |
| 关注阶段 | Tell启动→认知动作出现 | 认知动作出现→终止决策 |
| 成功标准 | 目标认知动作出现率高于bare | 终止决策正确（不过早/不打转/不强行） |
| 失败模式 | 没有执行/执行但无进展/执行后方向错误 | 过早退出/无限打转/强行使用 |

## §7 通过标准

### 7.1 通过标准（373号§9.4）

**POC-4通过，需要满足**：

1. **有效场景中不应过早退出**——AI在progress model预期信号陆续出现时继续执行，直到出现证书或主路线
2. **无进展场景中不应一直重复同一动作**——AI观察到progress model预期信号不出现后主动退出或回退
3. **边界冲突场景中不应强行使用目标Tell**——AI识别negative boundary被触发后停止或让位
4. **退出理由必须能落到progress model或negative boundary**——AI退出时能说清楚是"progress model没有预期信号"还是"negative boundary被触发"，而不是"我累了"或"我试了很多次"
5. **让位时要说明被哪个Tell接管，或为什么abstain**——让位不是简单放弃，而是有明确接替策略或明确弃权理由

### 7.2 不通过的处理

**如果条件1不满足（有效场景过早退出）**：
- 分析progress_model定义是否过严——AI可能认为"没有立刻找到不变量"就是"无进展"
- 修订TellCore的progress_model字段——更明确地定义"什么算有进展"的中间信号
- 可能需要回到POC-1审视TellCore的progress_model字段是否准确

**如果条件2不满足（无进展场景无限打转）**：
- 分析termination字段是否缺失或不够明确——AI可能不知道"什么时候应该停止"
- 修订TellCore的termination字段——增加明确的终止条件（如"连续N次切换表示后仍未找到不变量则退出"）
- 可能需要回到POC-1审视TellCore的termination字段是否完备

**如果条件3不满足（边界冲突场景强行使用）**：
- 分析negative_boundary字段是否不够明确——AI可能没有读negative_boundary或不知道它是什么意思
- 修订TellCore的negative_boundary字段——更明确地定义"什么情况下不应使用目标Tell"
- 可能需要在HintInstance中显式渲染negative_boundary

**如果条件4不满足（退出理由不落到progress model或negative boundary）**：
- 分析AI的退出理由是什么——如果是"我累了"或"我试了很多次"，说明AI没有用progress model或negative_boundary作为判定依据
- 可能需要在HintInstance中更明确地渲染progress_model和negative_boundary，让AI知道"用什么判断进展"和"什么时候应该退出"

**如果条件5不满足（让位时不说明接替策略）**：
- 分析AI让位时是否有明确接替策略——如果没有，说明让位变成了简单放弃
- 可能需要在TellCore中增加handoff_rule——让位时应该转向什么策略

### 7.3 模糊结果的处理

**如果结果是mixed（有些场景正确有些错误）**：
- 记录哪些场景终止行为正确、哪些错误
- 分析差异——是场景类型不同、还是题目特征不同、还是HintInstance强度不同
- 模糊结果不阻塞POC-6，但要在TerminationEvidence中明确记录哪些场景终止行为正确，后续POC只在这些场景上做

### 7.4 通过后不意味着终止行为"完美"——只意味着"基本正确"

**重要**：POC-4通过只说明终止行为在三类场景中基本正确——这是最基本的验证。但这不意味着终止行为"完美"——因为：
- 可能存在更复杂的终止场景（如多重Tell交叉的终止决策）——需要POC-5可组合（推迟到第二个Tell家族）来验证
- 可能存在模型依赖的终止差异——不同模型对progress model的理解可能不同——需要POC-8端到端闭环中的对照模型来验证

POC-4通过后，继续做POC-6（可归责）和POC-8（端到端闭环）来进一步验证。

## §9 执行约束

### 9.1 Solver启动

数学Solver必须通过`xishujuzhen/solver_harness/solver_harness.py launch`启动，不能手动tmux、nohup或绕过harness。

### 9.2 ArangoDB

启动任何连接ArangoDB的脚本前，必须确认`echo $ARANGO_DB`输出`xishujuzhen_math_glm52`。

### 9.3 Git

- Git add必须显式路径，不能`git add -A`或`git add .`
- 产物文件（poc_4_result.yaml / poc_4_analysis.md / 每个run的导出）必须commit

### 9.4 POC运行记录

POC运行记录必须保留thinking、trajectory、proof或TUI导出。通过solver_harness自动保存。

### 9.5 证据分层

POC结论必须写成证据分层——不把"终止行为基本正确"升级成"Tell可被运行时调度"。终止行为只是六门审计中的一门，Tell是否可被运行时调度需要POC-8端到端闭环来验证。

### 9.6 失败不是废结果

如果POC-4不通过（终止行为错误），这不是废结果——这是重要发现。要么揭示了progress_model定义不够清晰，要么揭示了termination字段不完备，要么揭示了negative_boundary不够明确。不通过的结果必须完整记录，并触发对POC-1 TellCore的termination/progress_model/negative_boundary字段的修订。

### 9.7 无进展场景题的构造质量

无进展场景题的构造是POC-4的关键难点——这些题不是"目标Tell不适用"（那是假朋友题），而是"目标Tell适用但进展不顺利"。如果无进展场景题实际上只是假朋友题（目标Tell根本不适用），那么"AI退出"不是因为终止条件正确，而是因为Tell本来就不该启动。构造无进展场景题时必须确认：目标Tell的trigger_boundary确实被满足，只是progress model预期的中间信号不出现。

### 10.1 前置关系

```

### 10.2 后续关系

```
★ POC-4（可终止）★ → POC-6（可归责）→ POC-7（可持续学习简化版）→ POC-8（端到端闭环）
