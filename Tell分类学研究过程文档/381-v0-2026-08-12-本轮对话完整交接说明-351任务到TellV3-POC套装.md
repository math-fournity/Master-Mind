## 4. 本轮最终形成的核心认知

### 4.1 不要再把非特化理解成“抽象得更高”

旧表达：

```text
trace → 更抽象的Tell
```

新表达：

```text
trace集合
  → 分支事件
  → 候选因果解释
  → 因果充分取商
  → TellCore
  → 认知Option
  → HintInstance
  → 运行时选择/执行/终止/归责/学习
```

也就是说，非特化不是一句话改写，而是把源题经验压缩成一个未来可运行的认知策略。

### 4.2 抽象Level合适只是第一门

用户明确指出并认可了这条要求：

```text
即使Tell的抽象层级合适，
也要继续问它是否已经成为
可选择、可执行、可终止、可组合、可归责、可持续学习的认知策略。
```

这句话已经写入372号第16节，并成为后续审计整个理论和技术框架的总闸门。

### 4.3 旧POC全部保留，但要降级为EvidenceRecord

旧POC不是废弃，而是重新定位：

- VMS-8：支持lineage + runtime hint的局部可执行性。
- VMS-9/10：支持tell端粗筛与近邻细分的局部可选择性。
- VMS-28：支持trace分支切分、FCA视角和语义不变量抽取。
- no-loss POC：说明压缩不能丢失关键语义。
- 350/352号：提供对照、泄漏审查和失败归因框架。
- bare筛选线：提供题目准入与baseline控制。

但这些不能被写成：

```text
非特化已经端到端验证通过。
```

只能写成：

```text
某条EvidenceRecord支持或反驳某个TellV3组件主张。
```

### 4.4 POC设计要从结果成功转向过程归责

TellV3的POC不能只问：

```text
给了Tell以后，AI做出来了吗？
```

而要问：

```text
是否选对Tell？
是否执行目标认知动作？
是否出现预期进展信号？
是否在无进展时退出？
是否能和其他Tell组合？
成功或失败归因到哪个组件？
反例是否改变Tell版本？
```

### 4.5 题目选择是POC成败的地基

题目不能只难。名副其实的验证题必须满足：

```text
真实bare失败
+ 正路可诊断
+ 过程可观察
+ 变形可生成
+ 假朋友可构造
```

如果下一位AI继续设计POC，最先要做的是把候选题写成`CaseCard`，而不是直接运行测试。
