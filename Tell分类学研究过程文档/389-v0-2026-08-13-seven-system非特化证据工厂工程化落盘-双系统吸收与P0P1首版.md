## 0. 一句话结论

基于387/388号研究、当前大规模高并发题海系统和第六代`system/`的真实实现边界，本轮新建独立`seven-system/`：代码、运行资产、文档、Schema和测试全部自包含于repo；大对象与未来数据库运行数据留在D盘。首版只实现可验证的P0与P1 scaffold控制面（不是387号完整P1），不连接数据库、不写Redis、不启动Solver，也不把脚手架冒充完整证据工厂。

## 1. 用户提出的工程目标

用户明确提供两套现有系统作为工程输入：

1. 正在运行的大规模高并发Devin题目测试系统；
2. 未来的第六代AI数学系统`system/`。

用户要求：

- 非特化研究考虑自动化和高并发；
- 建立独立`seven-system/`目录；
- scripts、运行资产、文档和测试都放在该目录；
- 大块数据放D盘；
- 需要进入数据库的内容进入D盘承载的数据库；
- AGENTS.md索引一套Seven System操作手册。

## 2. 为什么是第三个独立系统，而不是改造现有系统

### 2.1 题海系统的科学职责不同

题海系统的目标是大规模测量模型能力边界：设计上要求高并发Solver不调用工具，形成bare成功/失败、runtime verdict和trajectory；该“无工具”能力在现实现中尚未被物理层证明。

它最适合作为Seven的候选发现上游，而不是Tell因果实验本身。理由：

- `candidate_solved`只说明有候选proof文本，不说明数学证明已独立核验；
- `failed_token_limit`可能只是单次输出被截断；
- attempt失败不自动等于problem-level稳定bare失败；
- 题海生产队列不能被证据实验的arm、重试和人工Gate污染。

因此Seven只读消费未来冻结的CandidateManifest，不写现有`math:*`队列，也不改生产题目状态。

### 2.2 第六代system尚不是可依赖的完整producer

只读工程审计表明：`system/`当前真正有历史POC基础的是入题侧脉络分析的Parser子阶段；完整入题与解题尚未形成端到端实现：

- `enter.py`加载器未实现，当前脚本入口还有包导入问题；
- `process_absorb.py`的trace匹配、知识沉淀、孤悬trace与Tell保存未实现；
- `solve.py/process_solve.py`主体未实现；
- `system/schema.py`、DB与测试资产存在版本漂移和降维风险。

所以Seven不能直接`import system.*`、共享其DB写模型或运行目录。未来只允许：

```text
system producer
→ versioned JSON bundle + SHA-256 + artifacts
→ seven anti-corruption adapter
→ seven内部对象
```

### 2.3 Seven的职责是证据归责

Seven面向的问题不是“能不能跑一道题”，而是：

- 等资源restart后，Tell是否仍有增量；
- Solver是否真的执行目标题机制；
- proof是否正确；
- payload是否泄漏答案；
- Selector、Renderer、lineage、位置和额外预算分别贡献多少；
- 反例究竟应更新Core、boundary、Selector还是Renderer；
- 最终结论能否重放和回滚。

这需要387号的Epoch、Phase/Gate、三审、contrast EvidenceRecord和人工Revision Gate，不能塞进题海生产pipe。

## 3. 从高并发系统吸收什么

### 3.1 吸收的工程经验

- Solver工作目录必须在repo之外；
- 真实Solver只能通过`solver_harness.py launch`；
- Solver叶子实例在实验契约上不得做工具调用；
- 题面和干预应在启动时直接可见，避免读文件工具；
- 管道服务与Solver session解耦；
- Runner/Collector/Reporter/Retry职责分离的思想；
- Redis、ArangoDB、文件证据三层分工；
- 3秒launch interval是当前站点重要下限；
- 基础设施失败与科学终态分开；
- status/health必须到tmux、文件、trajectory前线，不能只信DB数字；
- graceful stop、dry-run-first recovery和双向追溯。

### 3.2 不复制的实现

现有实现存在不能进入确认性证据工厂的信任缺口：

1. Runner先写严格无工具AGENTS，Harness随后二次包装，外层语义和内层存在冲突；
2. CLI仍以dangerous permission运行，Prompt约束不等于工具表面被关闭；
3. 现有Collector/完整性检查查`*.db`工具记录，但Harness实际主要产出`trajectory.jsonl`；缺文件时会当成无工具，形成fail-open；
4. 工具检查主要挂在proof成功分支，而不是所有终态独立执行；
5. Redis claim的dequeue→running不是完整事务；
6. DB写失败后仍可能ACK/删除running；
7. 部分审计在零文件时可能vacuous PASS；
8. 旧`math:*`全局命名空间和clear操作不适合确认性实验。

因此Seven把真实live P0冻结为：没有独立`NoToolSolverCapabilityReport=PASS`、安全launch能力、答案隔离和strict DB能力时，必须BLOCKED。

## 4. 从第六代system吸收什么

- `FormalContext`闭元素枚举这一纯算法资产；
- 多套Prompt作为版本化运行资产。

不直接吸收：

- 五类trace压成三类、字符串Level压成0的有损转换；
- `DONE.md`或计数阈值作为科学完成门。

## 8. 当前P0能力契约

Live模式未来至少需要四份独立PASS报告：

1. Database Capability；
2. Safe Launch Capability；
3. No Tool Capability；
4. Answer Isolation Capability。

报告不能只写`verdict=PASS`，还必须包含：

- capability identity；
- subject hash；
- 非空检查清单；
- 生成时间；
- 能力特定的全true claims。

例如No Tool必须证明：

- tool surface被移除或registry为空；
- 观测缺失fail-closed；
- 所有终态都做工具审计；
- Solver没有DB/Vault凭据。

报告的`subject_hash`还必须由当前Harness、Solver资产、站点路径与隔离边界重新计算匹配；任一内部check非PASS或claim缺失都会BLOCK。即使四份报告齐全，v0.1.0 live仍被`live_execution_implementation=BLOCK`，直到另一个实现工作包明确移除。

## 9. 验证结果

本轮实际执行：

```text
Python compileall: PASS
unittest: 25/25 PASS
capabilities: PASS（P1上限明确）
真实站点preflight: 预期BLOCKED
DB connections: 0
Redis writes: 0
Solver launches: 0
D盘writes: 0
```

测试覆盖：

- canonical hash对mapping顺序与换行稳定；
- 同内容重复提交不重复写；
- 不同内容不能覆盖；
- data_root放进repo时BLOCK；
- `math:*`命名空间BLOCK；
- live即使伪装有能力文件仍因未实现而BLOCK；
- capability subject、内部checks和claims不能靠顶层PASS伪造；
- manifest、verdict和dry-run report被篡改可检测，非object JSON被拒绝；
- `epochs/<id>`符号链接逃逸被拒绝；
- 已存在Epoch仍重跑P0，不能绕过卷README等环境漂移；
- 新Epoch首次返回成功前强制执行完整性与当前运行兼容性双轴自验；
- 运行配置真正执行Schema，未知字段不会被静默忽略；
- Schema与显式非主张共同阻止把scaffold改写成Tell科学PASS；
- 一致的P1 FAIL可seal和重放，不与artifact corruption混淆；
- Solver资产含禁工具和终止契约，无答案/解答占位符；
- JSON Schema文件均可解析。

## 10. AGENTS.md索引决策
