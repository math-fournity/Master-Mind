## 0. 一句话结论

基于387/388号研究、当前大规模高并发题海系统和第六代`system/`的真实实现边界，本轮新建独立`seven-system/`：代码、运行资产、文档、Schema和测试全部自包含于repo；大对象、日志和Epoch留在D盘，未来小型数据库元数据、事件与artifact引用复用原逻辑数据库并使用Seven独立命名空间。首版只实现可验证的P0与P1 scaffold控制面（不是387号完整P1），不连接数据库、不写Redis、不启动Solver，也不把脚手架冒充完整证据工厂。

## 2. 为什么是第三个独立系统，而不是改造现有系统

### 2.1 题海系统的科学职责不同

题海系统的目标是大规模测量模型能力边界：设计上要求高并发Solver不调用工具，形成bare成功/失败、runtime verdict和trajectory；该“无工具”能力在现实现中尚未被物理层证明。

它最适合作为Seven的候选发现上游，而不是Tell因果实验本身。理由：

- `candidate_solved`只说明有候选proof文本，不说明数学证明已独立核验；
- `failed_token_limit`可能只是单次输出被截断；
- attempt失败不自动等于problem-level稳定bare失败；
- 题海生产队列不能被证据实验的arm、重试和人工Gate污染。

因此Seven只读消费未来冻结的CandidateManifest，不写现有`math:*`队列，也不改生产题目状态。

### 2.2 第六代system尚不是可依赖的完整producer

只读工程审计表明：`system/`当前真正有历史POC基础的是入题侧脉络分析的Parser子阶段；完整入题与解题尚未形成端到端实现：

- `enter.py`加载器未实现，当前脚本入口还有包导入问题；
- `process_absorb.py`的trace匹配、知识沉淀、孤悬trace与Tell保存未实现；
- `solve.py/process_solve.py`主体未实现；
- `system/schema.py`、DB与测试资产存在版本漂移和降维风险。

所以Seven不能直接`import system.*`、共享其DB写模型或运行目录。未来只允许：

```text
system producer
→ versioned JSON bundle + SHA-256 + artifacts
→ seven anti-corruption adapter
→ seven内部对象
```

### 2.3 Seven的职责是证据归责

Seven面向的问题不是“能不能跑一道题”，而是：

- 等资源restart后，Tell是否仍有增量；
- Solver是否真的执行目标题机制；
- proof是否正确；
- payload是否泄漏答案；
- Selector、Renderer、lineage、位置和额外预算分别贡献多少；
- 反例究竟应更新Core、boundary、Selector还是Renderer；
- 最终结论能否重放和回滚。

这需要387号的Epoch、Phase/Gate、三审、contrast EvidenceRecord和人工Revision Gate，不能塞进题海生产pipe。

## 3. 从高并发系统吸收什么

### 3.1 吸收的工程经验

- Solver工作目录必须在repo之外；
- 真实Solver只能通过`solver_harness.py launch`；
- Solver叶子实例在实验契约上不得做工具调用；
- 题面和干预应在启动时直接可见，避免读文件工具；
- 管道服务与Solver session解耦；
- Runner/Collector/Reporter/Retry职责分离的思想；
- Redis、ArangoDB、文件证据三层分工；
- 3秒launch interval是当前站点重要下限；
- 基础设施失败与科学终态分开；
- status/health必须到tmux、文件、trajectory前线，不能只信DB数字；
- graceful stop、dry-run-first recovery和双向追溯。

### 3.2 不复制的实现

现有实现存在不能进入确认性证据工厂的信任缺口：

1. Runner先写严格无工具AGENTS，Harness随后二次包装，外层语义和内层存在冲突；
2. CLI仍以dangerous permission运行，Prompt约束不等于工具表面被关闭；
3. 现有Collector/完整性检查查`*.db`工具记录，但Harness实际主要产出`trajectory.jsonl`；缺文件时会当成无工具，形成fail-open；
4. 工具检查主要挂在proof成功分支，而不是所有终态独立执行；
5. Redis claim的dequeue→running不是完整事务；
6. DB写失败后仍可能ACK/删除running；
7. 部分审计在零文件时可能vacuous PASS；
8. 旧`math:*`全局命名空间和clear操作不适合确认性实验。

因此Seven v0.1的legacy live P0先保留四个槽：NoTool、SafeLaunch、AnswerIsolation和Strict DB，任一不PASS都必须BLOCKED。387号canonical live P0在此基础上还独立要求Harness资源强制与CognitiveWorker能力，总计至少六类；旧四槽不能冒充新版P0完整。

## 8. 当前P0能力契约

v0.1.0 preflight历史上预留了四份live能力报告：

1. Database Capability；
2. Safe Launch Capability；
3. No Tool Capability；
4. Answer Isolation Capability。

§16记录多模型执行方向后，387号完整P0在四类旧槽位之外还要求独立`HarnessCapabilityReport`与`CognitiveWorkerCapabilityReport`，总计至少六类，并按实际adapter、模型配置与角色合同保存适用报告。四类旧槽位只描述当前代码历史；Safe Launch不能代替资源强制报告，它们也不能满足新版Golden Slice的认知Worker能力门。

报告不能只写`verdict=PASS`，还必须包含：

- capability identity；
- subject hash；
- 非空检查清单；
- 生成时间；
- 能力特定的全true claims。

例如No Tool必须证明：

- tool surface被移除或registry为空；
- 观测缺失fail-closed；
- 所有终态都做工具审计；
- Solver没有DB/Vault凭据。

报告的`subject_hash`还必须由当前Harness、Solver资产、站点路径与隔离边界重新计算匹配；任一内部check非PASS或claim缺失都会BLOCK。即使现有四份报告齐全，v0.1.0 live仍被`live_execution_implementation=BLOCK`；认知Worker报告目前连Schema/consumer都没有。只有后续工作包分别实现并验证相应执行面，才允许按该Epoch实际角色集合解除对应Gate。

## 16. 2026-08-14架构修正初版：目标Solver与认知执行面分离

> **版本说明**：本节保留第一版决策的完整推演。它正确建立了`TargetSolverPort`与`ModelRolePort`的物理隔离，但把“Devin CLI只能承载目标Solver”写成了过窄的载体限制。该限制已被§17取代；本节其余关于端口分离、答案隔离、QuestionRelease、双Gate、能力报告和盲化Bakeoff的原则继续有效。

### 16.1 用户问题与本轮确认继续推进的设计方向

用户指出：实验中的“做题者”当然可以继续由Devin CLI承载，但正交出题本身需要很强的数学命题能力。如果整个自动化管线只集成Devin，就会把“实验对象是谁”和“谁最适合出题、核验与审计”错误地绑成同一个问题。

该担心成立。本轮设计稿据此采用以下角色—载体分离原则：

1. **目标Solver**继续固定为Devin CLI，并且只能通过`solver_harness`、在独立工作目录中、以可验证的无工具能力运行；
2. **出题、解答核验、对抗审稿、Proof Judge及其他认知审计角色**不绑定Devin，统一经未来的provider-neutral `ModelRolePort`运行；“Cognitive Worker”是子系统/worker类别名，不另造平行Port；
3. Codex中的GPT-5.6高推理配置是第一候选出题载体，但“更会出题”目前只是待检验假设，不是已经成立的能力事实；
4. Blinding、hash、状态迁移、聚合和Gate规则由纯程序实现；题目发布与Case角色冻结仍由人工Gate批准；
5. 历史文档中“从分类目录启动Devin Telling AI”只保留为一种旧部署adapter，不再定义抽象角色本身。

因此Seven不是“Devin全管线”，也不是“用Codex替换Devin”。它是一个按科学角色选择载体、同时保留物理隔离和完整调用谱系的多模型证据工厂。

### 16.2 两个执行端口不能合并

```text
Role Router
├── TargetSolverPort
│   └── DevinSolverAdapter
│       └── solver_harness
│           └── no-tool target Solver
├── ModelRolePort（机器AI角色）
    ├── CodexWorkerAdapter（首个候选，尚未实现/验证）
    └── future provider/model adapters
├── HumanTaskPort（人工复核队列，不能签Gate）
└── HumanGateService（签发不可自动跨越的GateDecision）
```

两个端口的安全契约不同：Solver不得见答案、不得有工具表面、必须接受严格的arm资源公平控制；出题者和数学核验者可能需要计算或只读检索工具；Process Auditor不能见答案，Proof Judge和Leakage Auditor则需要各自不同的密封视图。把Codex出题塞进`solver_harness`，或让所有角色共用同一工作目录、会话和权限，会同时破坏角色语义与答案隔离。

未来接口在语义上至少包括：

```python
class TargetSolverPort(Protocol):
    def launch(self, frozen_solver_job): ...
    def observe(self, ticket): ...
    def collect(self, ticket): ...
    def cancel(self, ticket, fence_token): ...

class ModelRolePort(Protocol):
    def submit(self, frozen_role_job): ...
    def observe(self, ticket): ...
    def collect(self, ticket): ...
    def cancel(self, ticket, fence_token): ...
```

`QuestionArchitectPort`、`AdversarialEditorPort`、`MathVerifierPort`、`ProofJudgePort`等是`ModelRolePort`之上的角色契约，不是各自偷接某个CLI的旁路。

### 16.3 默认角色分工

| 科学角色 | 首选载体/策略 | 不变量 |
|---|---|---|
| Question Architect | Codex/Responses中的`gpt-5.6-sol`高推理配置作为首个候选 | 只按冻结`MechanismContract + CoverageCell + AuthoringBrief`出题；不自行发布 |
| Adversarial Editor | 新鲜、隔离的Codex或异构模型 | statement-only；寻找歧义、捷径、经典外壳和替代低成本路线 |
| Math Verifier | 独立上下文的强模型；确认性题优先加异模型、人工或形式工具 | 看题面与候选解，不看作者scratch、Tell、Devin结果 |
| Target Solver | Devin CLI，经唯一`solver_harness` | bare/guided/control全部等资源、无工具、无答案 |
| Proof Judge | 新鲜、隔离的强模型 | 只见题面、Devin final proof和最小Verification view；不见arm、Tell和完整thinking |
| Human Gate | 人 | 批准不可变QuestionRelease与Case角色；AI不得自批 |
| Blinding/状态/hash/聚合 | 程序 | 确定性、可重放、append-only |

同一个模型的新会话只证明**上下文独立**，不等于**模型独立**或**provider独立**。每份确认性审查都必须写`ReviewIndependenceRecord`，明确是新上下文、不同模型、不同provider、AI+人工还是AI+形式工具，不得笼统写“独立审查”。

### 16.4 从出题brief到Devin实验的冻结链

```text
MechanismContract + TargetCoverageCell
→ AuthoringBrief
→ ModelRelease + RolePromptRelease
→ AIInvocationReceipt
→ QuestionDraftVersion
   ├── public_statement_ref
   └── sealed_solution_ref
→ AdversarialReview
→ VerificationDossier
→ HumanGateDecision (G-Q-RELEASE)
→ immutable QuestionRelease
→ Devin BareBaseline
→ BareQualificationResult
→ AdmissionDecision / HumanGateDecision / CasePackVersion (P3C / G-CASE-ROLE)
```

`QuestionDraftVersion`直接复用388号的`AuthoringBlueprint`（core/shell/decoy/lock/certificate/margin，以及solution/obstacle script）作为作者谱系，不把它当作题目质量或Tell效应证据。题面任意字符发生变化都必须生成新版本，并使旧候选解、审稿、VerificationDossier和bare结果失效；不得原地改题后沿用旧物证。

自然发现的真实bare失败仍是主要题源。Codex受控生成只负责填补CoverageTensor空格和构造正迁移、假朋友、最小边界对等正交关系。生成策略不得“不断改题直到Devin失败”；最大草稿数、最大修订轮次、准入规则与停止条件必须预注册，所有拒绝和隔离的草稿及其成本都要保留。

### 16.5 角色执行契约与调用收据

`FrozenRoleJob`不是第二套合同；它是`RoleExecutionContract`在某个Epoch内绑定input view、budget和idempotency key后的不可变序列化实例。每个`FrozenRoleJob`至少冻结请求与准入契约，不能预先伪造运行后才可观察的effective事实：

- `epoch_id / job_id / attempt_id / role`；
- 输入view的引用与hash、ACL capability；
- carrier、provider、adapter版本和代码hash；
- requested model、reasoning effort、reasoning mode与orchestration mode，以及这些字段必须可观察的规则；
- model release、role prompt、tool/network/sandbox policy及output schema的版本/hash；
- token、墙钟、费用、并发和人工审阅预算；
- seed支持状态、requested seed、幂等键和retry contract；
- independence class及禁止共用的会话、目录和secret范围；
- 按类型列出的全部required CapabilityReport（ID/hash/subject或profile hash）；Target Solver至少绑定Harness、NoTool、SafeLaunch、AnswerIsolation，认知角色按其view再绑定CognitiveWorker与AnswerIsolation，不能用单一泛化PASS解锁整组能力。

每次运行形成append-only `AIInvocationReceipt`，在事后记录CLI/API版本、可执行文件hash、脱敏request的ref/hash、provider response/thread ID、原始JSONL/事件流的ref/hash与Schema版本、工具事件、输入输出hash、effective model/effort/reasoning mode/orchestration、output-schema验证、工具/网络/沙箱观察判定、usage/cost、时间、退出原因、capability report及retry/replay lineage。若provider只提供会漂移的model alias，则标记`UNPINNED_ALIAS`；可重放的是冻结输入、执行谱系和历史物证，不得声称能逐token再生相同文本。

任何载体在进入自动管线前都要有`CognitiveWorkerCapabilityReport`。报告必须绑定provider、adapter代码hash与一条精确的`model + effort + reasoning mode + orchestration + tool/network/sandbox + output schema`测试profile，并逐字段记录requested、observed/effective与不可观察状态；一个profile的PASS不能解锁未测组合。根据[OpenAI官方GPT-5.6模型指南](https://developers.openai.com/api/docs/guides/latest-model)，`gpt-5.6` alias当前路由到`gpt-5.6-sol`，单模型`reasoning.effort`支持到`max`；standard/pro是独立`reasoning.mode`，Responses multi-agent beta则只是“类似Codex ultra mode”。因此模型、`xhigh/max` effort、standard/pro reasoning mode与single/multi-agent（Ultra-like）orchestration必须分别探测requested/effective值，不能混成一个未经验证的开关。本轮没有调用Codex或Devin，以上能力全部仍为`NOT_TESTED/NOT_IMPLEMENTED`。

### 16.6 答案隔离与并发资源池

答案隔离必须是物理视图隔离，不是从一个JSON里删掉字段：

- Architect的完整原始输出默认进入Vault；普通日志只得到机械提取并通过泄漏扫描的题面；
- Adversarial Editor只见题面，其可能产生替代解的原始输出也进入Vault；
- Math Verifier见题面和候选解，但不见作者scratch、Tell或Solver结果；
- Devin只见QuestionRelease公开题面和当前arm允许的Hint；
- Process Auditor不见答案；Proof Judge与Leakage Auditor只得到各自最小授权视图；
- Architect、Editor、Math Verifier、Proof Judge和Leakage Auditor的request、raw event与output只要可能复述候选解、密封解答、关键lemma或holdout内容，就必须标为`solution_bearing/holdout_bearing`并写入受限Vault；普通ledger/receipt只留ref/hash与ACL分类；
- 同一session、同一工作目录或继承先前rollout都不构成独立性。

并发也不能继续用单一全局数字：

```text
author_pool  = 低并发、昂贵、按角色决定是否允许工具
review_pool  = 独立审查可并行，禁止继承作者上下文
judge_pool   = 独立限流、盲化输入
solver_pool  = 高并发、无工具、只经solver_harness
```

`RuntimeManifest`未来必须按pool冻结provider并发、in-flight token/费用、最大backlog、launch interval、retry和停止规则。作者成本不进入某个Solver arm的资源公平对比，但必须计入端到端`cost_per_verified_question`、`cost_per_admitted_case`和`cost_per_evidence_record`。

### 16.7 不凭直觉指定“最会出题的模型”

候选模型不是已经胜出的生产作者；进入规模化出题前需运行两段盲化Authoring Evaluation。A段在QA0内完成，不启动Target Solver：

```text
同一 MechanismContract + CoverageCell + AuthoringBrief
→ Codex候选 / 至少一个通过能力门的其他provider或model候选 / 适用时人工基线分别生成
→ 隐去作者身份
→ 独立评估：
   数学正确率
   机制忠实度与正交距离
   歧义、经典捷径和答案泄漏率
   多样性与重复族
   token、费用、墙钟和人工分钟
```

只有题稿已经不可变发布后，QA1/B段才对专用calibration releases增加Devin problem-only bare准入率。该结果不能回流修改同一题稿或删除成功题，也不能成为作者质量的唯一指标；否则会再次激励“造到Devin失败为止”。

A/B题稿属于独立`AuthoringEvaluationPack(purpose=calibration)`，只用于选adapter，默认不得进入P5/P7确认性证据。选定默认adapter前，还要在未见`AuthoringEvaluationPack(purpose=qualification)`上复验，禁止同一批brief既选赢家又证明赢家泛化。

### 16.8 新工作包与依赖顺序

此前§11的`WP-2 No-tool Harness Adapter`仍然有效，但它只实现目标Devin Solver，不能被P3A/P3N机器认知角色或P6 Judge复用。新增三条workstream、五个work package，并先做最小离线纵切：

1. **WP-CW0：Offline Cognitive Worker Runtime**

   只实现一个候选adapter、Question Architect/Adversarial Editor/Math Verifier三个角色、RoleExecutionContract、CapabilityReport、InvocationReceipt、D盘file-backed artifact/Vault和串行/低并发author/review pool；不连DB/Redis/Devin，不实现Judge pool或distributed reconcile。没有该工作包，P3A机器认知角色不得暗中直接调用Codex或Devin。solver pool始终归WP-2/TargetSolver控制面，不属于Cognitive Worker Runtime。

2. **WP-HG0：Offline Human Task & Gate Runtime**

   先以file-backed append-only对象实现人工任务、actor identity、职责分离、签名`HumanGateDecision`、HUMAN_PENDING、拒绝/超时不默认通过和审计。它不能复用ModelRolePort，也不能让作者/自动化自己签`G-Q-RELEASE`或`G-CASE-ROLE`。

3. **WP-QA0：Offline Authoring Lab**

   使用一个人工批准的MechanismContract和一个CoverageCell，运行一个候选Question Architect、statement-only对抗审稿、独立数学核验和人工`G-Q-RELEASE`；只向D盘append-only artifact/Vault写入，不连DB/Redis、不启动Devin、不产生Tell科学结论。

4. **WP-QA1：Question Admission（P3B/P3C）**

   只有QuestionRelease、Vault、D盘存储/空间、预算、`P3A/G-Q-RELEASE`，以及Database site、TargetSolverPort/Devin adapter、Harness资源、NoTool、SafeLaunch、AnswerIsolation、artifact seal/reconcile能力都PASS后，才把不可变题面交给Devin做problem-level bare复测，并经`G-CASE-ROLE`冻结Case角色。它不要求完整P2/P3预先PASS，也不是P5确认性实验；file-only实验必须标`OFFLINE_ADMISSION_LAB`，不能冒充canonical P3B。

5. **WP-CW1：Production Cognitive Worker Expansion**

   在QA0证明离线链可工作后，才增加P3N/P6角色、judge pool、DB-backed lease/fence、provider reattach、partial→seal/reconcile与长期背压；它仍不拥有solver pool，也不能跨HumanGate。

两条入口分别是：自然题走`P2A历史物证审计 → 按需P2B当前bare qualification → P3N机制/数学审查 → P3C`；受控生成题走`P3A authoring/G-Q-RELEASE → WP-QA1/P3B generated bare → P3C G-CASE-ROLE`。P2B/P3B都是admission-only problem-only Solver调用，P5才是第一阶段正式guided/control因果实验。依赖顺序是：先冻结角色合同和能力边界，再分别实现机器认知执行面与人门执行面，然后做离线authoring；先发布不可变题目，再启动Devin；先完成bare准入和Case角色冻结，再进入guided因果实验。任何阶段缺少能力报告、Vault、最小视图或人工Gate时都必须`BLOCKED`，不得fallback到当前交互式Codex会话或手工复制提示词。

## 17. 2026-08-14最新修正：Devin CLI同时进入认知执行面

### 17.1 用户修正与最终架构裁决

用户进一步明确：Seven不能把Codex写成认知角色的唯一实现路径。Devin CLI使用`glm-5.2` High时，也必须能够承担出题、编辑、数学核验、Judge和Auditor等所有原计划由Codex承担的机器认知角色。

这不会推翻§16建立的两个端口，反而要求更严格地把**角色、载体和执行面**三者正交化：

```text
Role Router
├── TargetSolverPort
│   └── DevinSolverAdapter
│       └── solver_harness
│           └── no-tool Target Solver
├── ModelRolePort
│   ├── DevinCliModelRoleAdapter
│   │   └── glm-5-2 / normalized effort=high
│   ├── CodexExecModelRoleAdapter
│   └── future provider/model adapters
├── HumanTaskPort
└── HumanGateService
```

最终硬约束是：

1. **只有Target Solver作业可以进入`solver_harness`**；
2. **Devin CLI并不专属于Target Solver**，它可以通过独立的`DevinCliModelRoleAdapter`执行全部机器认知角色；
3. Target Solver不得改走通用ModelRole adapter，Devin认知角色也不得借用Solver Harness；
4. Devin与Codex在`ModelRolePort`中是并列候选，必须按角色和精确profile分别通过能力门、纵切与盲化Bakeoff；
5. 相同Devin二进制或相同GLM模型出现在两个执行面，不允许共享session、workspace、配置、权限、输入view、artifact sink、receipt、lane/scientific budget、资源池或重试谱系；但两者必须共同受carrier-global账户/配额硬上限约束。

因此系统允许“Devin做全部AI认知工作”，但不允许“用一个万能Devin调用路径混做所有角色”。

这只是requested合同，不是能力PASS。运行后还必须从强制export的ATIF/事件物证核对`agent.model_name`、每个generation-bearing assistant/model step的`generation_model`、工具定义/事件、token、退出原因和完整输出；user/tool/telemetry step不要求该字段，但任一generation-bearing step不是`glm-5-2`、缺字段、物证缺失或无法观察时，精确profile必须`BLOCKED/QUARANTINED`。CLI没有暴露的effective reasoning/orchestration mode要写`UNOBSERVABLE`，不能用CLI帮助文本或模型目录自证。

### 17.3 两种Devin adapter必须物理隔离

| 维度 | `DevinSolverAdapter` | `DevinCliModelRoleAdapter` |
|---|---|---|
| 入口 | 只能经`solver_harness` | 只能经`ModelRolePort` |
| 目的 | 被研究的Target Solver | Question Architect、Editor、Verifier、Judge、Auditor |
| 工具 | 能力层强制NoTool | 由角色policy决定；不得从Solver配置继承 |
| 工作目录 | repo外的Solver专用目录 | D盘独立role/attempt目录 |
| 会话 | Solver attempt专属 | 每个role attempt全新会话，禁止resume/continue |
| 输入 | QuestionRelease与arm允许的Hint | 角色最小view；按ACL决定是否可见解答 |
| 输出 | thinking/proof/trajectory | raw event/export/output；solution-bearing内容进Vault |
| 资源池 | 独立`solver_pool` | `author_pool/review_pool/judge_pool` |
| 能力报告 | Harness/NoTool/SafeLaunch/AnswerIsolation | CognitiveWorker/角色ACL/模型与usage可观察性 |

Devin认知adapter的实现不能照抄历史非Solver直调脚本。它至少必须使用结构化argv、冻结prompt file、专用最小env/config、全新session、强制export、受限artifact sink、timeout/cancel/fence、unknown-start quarantine和append-only`AIInvocationReceipt`。外部请求可能已经被接受但启动状态未知时，不得自动换到Codex或再次调用Devin；跨载体fallback是新的物理attempt和新的实验条件。

### 17.4 角色视图、独立性与并发

- Architect原始输出可能含题面和候选解，整体进入Vault，只由程序机械导出公开statement；
- Editor只见statement，不能见MechanismContract、作者scratch或密封解；
- Math Verifier见statement与候选解，不能见Target Solver结果；
- Process Auditor不见答案；Proof Judge与Leakage Auditor各自只见经ACL物化的最小密封view；
- 同一个`glm-5-2`在fresh session中担任作者和审稿者，只能记为`context_independent`，不能冒充`model_independent`或`provider_independent`；
- Devin认知并发从每个role profile的1并发资格测试起，不继承题海Solver“历史60并发”经验；还需carrier-global limiter，防止认知worker和题海Solver彼此饿死；
- 永久禁止`retry-until-desired-output`和`retry-until-Devin-fails`，所有失败草稿、被拒题目、未知启动与成本必须保留。
