## 0. 你要完成什么

目标不是“让 Devin 多做几道题”，而是建立一个可持续的观测系统，回答四个问题：

1. 哪些竞赛题 GLM-5.2 bare 能做出来？
2. 它是怎么做出来的？关键路线、工具调用、证明落盘过程是什么？

4. 做不出来的原因是什么：数学卡点、错误方向、证明缺口、工具卡死、token limit、限流，还是基础设施问题？

最终系统必须支持从本地题库按“从难到易”抽题，10并发启动 Devin Solver，并把每个运行目录和数据库中题目表的唯一数字ID对应起来。

## 2. 最高硬约束

1. **Solver 启动必须通过 solver-harness**  
   只能调用：

   ```bash
   python xishujuzhen/solver_harness/solver_harness.py launch ...
   ```

   禁止手写 tmux 启动 Solver，禁止 nohup，禁止直接 subprocess 跑 `devin`。

2. **数据库必须是本 repo 专用库**

   ```bash
   set -a; source .env; set +a
   echo $ARANGO_DB
   # 必须输出 xishujuzhen_math_glm52
   ```

3. **运行目录必须带题目唯一数字ID**  
   目录名必须含 `problem_extraction_progress._key`，例如：

   ```text
   dpb-20260812-153000-tier1-bare-01-p329030-g000002-compfiles_imo1963p5
   ```

   其中 `p329030` 是题目表唯一数字ID。没有这个 ID 的题，不能直接进入正式批量运行；必须先建立映射记录。

4. **不能向 Solver 泄漏解答**  
   Solver 工作目录里的 `problem.txt` 只能包含题面和“写入 proof.md”的要求。`solution_text` 只能用于事后审稿，不能进入 Devin 解题上下文。

5. **tmux 是可观测性要求，不是可替代 harness 的理由**  
   我们使用 tmux 是为了能随时 attach/capture，看 TUI 是否限流、卡死、报错。tmux 的创建仍由 solver-harness 完成。

## 4. 目标系统结构

系统分五层：

1. **题目选择层**：从数据库按难度、来源、历史预测、是否已跑过选题。
2. **输入冻结层**：把本批次题目列表、题面、progress key、profile key、source path 写入 batch manifest。
3. **运行编排层**：最多10个 harness Solver 并发，运行结束一个补一个。
4. **观测采集层**：轮询 tmux、proof、thinking、trajectory、export、TUI 文本、限流/错误 marker。
5. **verdict 审计层**：运行层自动分类，数学正确性由后续 proof review 决定。

不要把这五层混在一个长函数里。

## 5. 数据库契约

360号已提出三表，接手时优先沿用，不要另起名字：

| 集合 | 作用 |
|---|---|
| `devin_batch_runs` | 一批实验一条记录 |
| `devin_problem_runs` | 一道题一次 attempt 一条记录 |
| `devin_run_events` | 批次和 attempt 的事件流 |

建议在 `devin_problem_runs.verdict` 中保留两级判定：

```json
{
  "runner_status": "candidate_solved | failed_no_proof | failed_token_limit | failed_tool_stall | rate_limited | infra_error",
  "math_review_status": "unreviewed | proof_valid | proof_invalid | partial_route_valid | wrong_answer",
  "failure_reason": "missing_key_lemma | wrong_representation | case_split_explosion | tool_overuse | proof_gap | token_limit | rate_limit | connection_error | no_final_write",
  "failure_summary": "...",
  "reviewer_notes_path": "..."
}
```

关键点：`proof.md` 存在只能判为 `candidate_solved`，不能自动判为 `proof_valid`。

## 7. 并发策略

默认目标是 `concurrency=10`。但 10 是上限，不是盲目硬顶。

执行策略：

1. 启动前确认共享 mitmproxy 状态。
2. 每个新 Solver launch 之间间隔 5-15 秒，避免瞬间打满。
3. 运行中保持 active attempts <= 10。
4. 如果出现 rate limit / 429 / quota / TUI 限流提示：
   - 立即把 batch 标记 `rate_limited_warning`；
   - 暂停补新题；
   - 保留当前 tmux 截屏/日志；
   - 根据 TUI 状态决定降到 5 并发或等待恢复。
5. 如果只是单题工具卡死，不降低全局并发，标记该题 `failed_tool_stall` 后 stop 它并补下一题。

必须提供一个 dashboard/status 命令，至少显示：

| 字段 | 说明 |
|---|---|
| batch_id | 当前批次 |
| running/queued/terminal counts | 状态计数 |
| attempt_key | 当前题 |
| progress_key | 题目唯一数字ID |
| tmux_session | 可 attach 的 session |
| proof exists | 是否已有 proof.md |
| thinking bytes | thinking 是否增长 |
| last activity | 最近活动时间 |
| markers | token limit / rate limit / connection / tool stall |

## 8. 选题策略

第一阶段不要随机抽。按以下优先级：

1. **P0：历史强证据 bare 失败题**  
   来自359号和 VMS 记录。必须先找到或建立 `progress_key` 映射。

2. **P1：`problem_profiles.bare_ai_expected=fail` 且 Tier 1 的题**  
   按 `problem_extraction_progress.global_sequence ASC` 取最难的一批。

3. **P2：`bare_ai_expected=marginal` 的 Tier 1/2 题**  
   用于补足10并发或扩展覆盖面。

4. **P3：用户/研究过程新造题**  
   只有在题面入库并有唯一数字ID后才能纳入正式批次。

首批建议：

```text
4道历史强证据题 + 6道 Tier 1 predicted fail 题 = 10并发
```

但注意：1709 刚复测已 bare 成功，不能继续当作稳定 bare 失败，只能作为“曾经失败、现在成功”的对照样本。

## 10. Failure taxonomy

每个失败 attempt 至少归入一个主类：

| 类型 | 判定依据 |
|---|---|
| `failed_token_limit` | tmux/log/thinking 中出现 response truncated、token limit、context limit |
| `failed_tool_stall` | Devin 自己启动的工具长时间不返回，如重型 SymPy `real_roots` |
| `failed_no_proof` | Devin 自然结束但没有 `proof.md` |
| `rate_limited` | TUI 或日志出现 rate limit、429、quota |
| `failed_connection` | connection failed、network/API error |
| `proof_gap` | 有 proof，但关键 lemma 未证或结论跳步 |
| `wrong_answer` | proof 给出错误答案，例如漏解/多解 |
| `case_split_explosion` | thinking 长时间陷入分情形，未闭合 |
| `wrong_representation` | 选错建模/翻译方式，后续路线无法收束 |
| `tool_overuse` | 用计算验证替代证明，并因规模扩大失败 |

失败归因不能只写“没做出来”。要引用证据文件，例如：

```text
trajectory_dir/mitm/thinking_readable.txt around final 3000 chars
trajectory_dir/tmux/tmux.log
solver_dir/proof.md line ...
```

## 11. 操作命令模板

### 查看 mitmproxy

```bash
python xishujuzhen/solver_harness/solver_harness.py mitm status
```

### 启动 profile 题库批次

```bash
set -a; source .env; set +a
.venv/bin/python xishujuzhen/solver_harness/batch_problem_runner.py \
  run \
  --limit 10 \
  --tier 1 \
  --bare-ai-expected fail \
  --concurrency 10 \
  --label tier1-bare \
  --poll-seconds 60 \
  --max-runtime-seconds 7200 \
  --stall-seconds 900
```

### 启动历史文件批次

只有在每个文件都映射到 `progress_key` 后才允许：

```bash
set -a; source .env; set +a
.venv/bin/python xishujuzhen/solver_harness/batch_problem_runner.py \
  run-files \
  --case <progress_key>:<problem_file>:<problem_id> \
  --case <progress_key>:<problem_file>:<problem_id> \
  --concurrency 10 \
  --label historical-bare
```

### 观察

```bash
.venv/bin/python xishujuzhen/solver_harness/batch_problem_runner.py \
  monitor --batch-id <batch_id>

tmux list-sessions | rg 'harness-<batch_id>|harness-dpb'
tmux capture-pane -pt <tmux_session> -S -80
```

### 停止批次

```bash
.venv/bin/python xishujuzhen/solver_harness/batch_problem_runner.py \
  stop --batch-id <batch_id>
```
