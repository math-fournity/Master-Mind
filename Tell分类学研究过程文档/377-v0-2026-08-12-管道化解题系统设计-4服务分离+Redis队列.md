## 1. 背景与动机

### 1.1 当前架构问题

当前`auto_runner.py`把三件事混在一个进程里：
1. **启动新题**（运行职责）
2. **刷新活跃attempt状态**（收集职责）
3. **判定终态+更新queue**（整理职责）

30并发时勉强能用，但100并发时每30秒要刷新100个attempt的tmux capture-pane，一轮刷新还没跑完下一轮又开始了。

### 1.2 目标

- **4服务全分离**：Feeder、Runner、Collector、Reporter各自独立进程
- **Redis持久化队列**：替代ArangoDB的problem_queue表，数据在D盘
- **先30并发跑通管道**，确认稳定后再加组
- **2.4M题的规模**：能持续运行不中断

## 2. 架构设计

### 2.1 整体架构

```
                    ArangoDB (problem_extraction_progress, 2.4M题)
                           │
                           ▼
                   ┌──────────────┐
                   │   Feeder     │  服务1：选题入队
                   │  (独立进程)   │  从ArangoDB按tier选题→写入Redis队列
                   └──────┬───────┘
                          │ LPUSH / ZADD
                          ▼
                   ┌──────────────┐
                   │    Redis     │  持久化队列（D盘AOF）
                   │  (容器服务)   │  queue:pending (Sorted Set, 按priority)
                   │              │  queue:running (Hash, attempt_id→metadata)
                   │              │  queue:completed (List)
                   │              │  queue:failed (List)
                   └──┬───────┬───┘
                      │       │
         BRPOP        │       │  HGETALL
                      ▼       ▼
              ┌──────────┐  ┌──────────────┐
              │  Runner  │  │  Collector   │
              │(独立进程) │  │  (独立进程)   │
              │ 取题→    │  │  扫描running │
              │ 启动devin│  │  →判定终态   │
              │ cli      │  │  →更新Redis  │
              └────┬─────┘  └──────┬───────┘
                   │               │
                   │ tmux session  │ tmux capture-pane
                   ▼               │
              ┌──────────┐         │
              │ Devin CLI│         │
              │ (×30并发)│         │
              └──────────┘         │
                                   ▼
                          ┌──────────────┐
                          │  Reporter    │  服务4：统计报告
                          │  (独立进程)   │  定时从Redis读统计
                          │              │  →输出进度+告警
                          └──────────────┘
```

### 2.2 Redis队列结构

| Key | 类型 | 用途 | 内容 |
|-----|------|------|------|
| `math:pending` | Sorted Set | 待处理队列 | score=priority, member=problem_id |
| `math:running` | Hash | 运行中 | field=attempt_id, value=JSON(problem_id, start_time, tmux_session) |
| `math:completed` | List | 已完成 | JSON(attempt_id, problem_id, verdict, duration) |
| `math:failed` | List | 已失败 | JSON(attempt_id, problem_id, error, retry_count) |
| `math:stats` | Hash | 实时统计 | total/enqueued/running/completed/failed |

**为什么用Sorted Set做pending队列**：
- 优先级排序（tier 1的score=1，先出队）
- 同优先级按入队时间排序（Redis自动按score排序）
- ZPOPMIN原子取出最高优先级题

### 2.3 四个服务

#### 服务1：Feeder（选题入队）

**职责**：从ArangoDB的`problem_extraction_progress`表按tier选题，写入Redis的`math:pending`队列。

**独立进程**：`feeder.py`，tmux session `feeder`

**工作流程**：
1. 查询ArangoDB：`FILTER extraction_status == "pending" SORT priority ASC LIMIT batch_size`
2. 对每道题：`ZADD math:pending {priority} {problem_id}`
3. 更新ArangoDB：`extraction_status = "queued"`
4. 检查Redis中`math:pending`长度，低于阈值时补充
5. 循环，直到所有题入队

**关键参数**：
- `--batch-size 1000`：每次从ArangoDB取1000题
- `--low-water-mark 100`：pending队列低于100时补充
- `--tier 1,2,3`：按tier筛选（先跑tier 1）

#### 服务2：Runner（纯启动）

**职责**：从Redis取题，启动devin cli，不做任何状态判定。

**独立进程**：`runner.py`，tmux session `runner`

**工作流程**：
1. 统计当前running数：`HLEN math:running`
2. 计算可用槽位：`slots = concurrency - running_count`
3. 如果有槽位：`ZPOPMIN math:pending {slots}`（原子批量取题）
4. 对每道题：
   - 从ArangoDB读取题目文本
   - 写AGENTS.md（题目+指令）
   - `tmux new-session`启动devin cli
   - `HSET math:running {attempt_id} {json_metadata}`
5. sleep(poll_interval)，循环

**关键参数**：
- `--concurrency 30`：30并发（先跑通）
- `--poll-interval 5`：每5秒检查一次槽位

**不做的事**：
- ❌ 不检测PROOF COMPLETE
- ❌ 不判定终态
- ❌ 不更新ArangoDB的attempt状态
- ❌ 不做trajectory采集

#### 服务3：Collector（状态收集+判定）

**职责**：扫描running队列，检测终态，更新Redis和ArangoDB。

**独立进程**：`collector.py`，tmux session `collector`

**工作流程**：
1. 读取running队列：`HGETALL math:running`
2. 对每个running attempt：
   - `tmux capture-pane`检测PROOF COMPLETE / ANSWER LEAK
   - 检测超时（start_time + timeout < now）
   - 检测stall（文件大小长时间不变）
   - 检测dead session（tmux session不存在）
3. 判定终态：
   - PROOF COMPLETE → `LPUSH math:completed`，更新ArangoDB verdict=solved
   - 超时/stall/dead → `LPUSH math:failed`，更新ArangoDB verdict=failed
   - 否则 → 跳过，下次再查
4. 从running移除：`HDEL math:running {attempt_id}`
5. kill已完成的tmux session
6. sleep(poll_interval)，循环

**关键参数**：
- `--poll-interval 10`：每10秒扫描一轮
- `--timeout 1800`：30分钟超时
- `--stall-time 300`：5分钟无变化判stall

#### 服务4：Reporter（统计+告警）

**职责**：定时从Redis读统计，输出进度报告。

**独立进程**：`reporter.py`，tmux session `reporter`

**工作流程**：
1. 读取Redis统计：`HGETALL math:stats`
2. 计算实时统计：
   - pending长度：`ZCARD math:pending`
   - running长度：`HLEN math:running`
   - completed长度：`LLEN math:completed`
   - failed长度：`LLEN math:failed`
3. 输出报告到stdout和日志文件
4. 检测告警条件：
   - running数突然下降（可能批量失败）
   - failed率 > 50%
   - pending队列空但Feeder没在跑
5. sleep(report_interval)，循环

**关键参数**：
- `--report-interval 60`：每60秒报告一次

## 3. Redis容器配置

### 3.1 容器参数

```bash
docker run -d \
  --name redis-queue \
  --restart unless-stopped \
  --memory=4g \          # 容器内存限制4G（防OOM）
  --memory-swap=4g \     # 不允许swap（防性能退化）
  -p 6379:6379 \
  -v /data/redis/data:/data \           # 数据在D盘
  -v /data/redis/redis.conf:/usr/local/etc/redis/redis.conf \
  redis:7-alpine \
  redis-server /usr/local/etc/redis/redis.conf
```

### 3.2 防OOM关键配置

| 配置 | 值 | 作用 |
|------|-----|------|
| `maxmemory 4gb` | 4G | Redis最大内存，超过时拒绝写入 |
| `maxmemory-policy noeviction` | 不驱逐 | 队列数据不能丢，满时报错而不是删数据 |
| `--memory=4g` | 容器4G | Docker容器内存限制 |
| `--memory-swap=4g` | 不swap | 防止swap导致性能退化 |
| `client-output-buffer-limit` | 限制 | 防客户端缓冲区吃光内存 |
| `appendfsync everysec` | 每秒 | AOF每秒fsync，最多丢1秒数据 |

### 3.3 内存估算

2.4M题在Redis Sorted Set中：
- 每个member约30字节（problem_id），score 8字节
- 2.4M × 38字节 ≈ 91MB
- 加上running/completed/failed队列和开销：约500MB
- 4G限制绰绰有余

## 7. 数据管理完备性要求（2026-08-12 20:00补充）

### 7.1 核心原则：全部历史任何时候都是可审计的

**所有运行产生的数据——题目、运行记录、export导出、tmux pane导出——必须用唯一数字ID索引，任何时候都可双向追溯。**

这不是"保留痕迹"的要求，而是"保留后必须能顺藤摸瓜"的要求。具体到管道化系统：

### 7.2 唯一数字ID索引

**题目层**：
- 每道题在ArangoDB中有唯一`_key`（如`amo_bench_00000005`）
- 每道题的`problem_hash`是内容唯一标识（MD5 of 题目文本前500字符）
- 题目文件存放在`_pipe/problems/{exp_id}/AGENTS.md`，exp_id是唯一运行ID

**运行层**：
- 每次运行有唯一`exp_id`（如`p454455a9584542029b85`）
- 每次运行在ArangoDB `devin_problem_runs`中有唯一`_key`（如`pipe_p454455a9584542029b85`）
- 每次运行的tmux session名包含exp_id（如`harness-p454455a9584542029b85`）
- 每次运行的工作目录名包含exp_id（如`/data/.../p454455a9584542029b85/`）

**追溯链**：
```
DB problem_extraction_progress._key
  → DB devin_problem_runs.problem_id (关联题目)
  → DB devin_problem_runs._key (运行记录)
  → DB devin_problem_runs.paths (所有物理文件路径)
  → 物理文件: trajectory_dir/{exp_id}/tmux/tmux_pipe.log
  → 物理文件: trajectory_dir/{exp_id}/sessions_db/trajectory.jsonl
  → 物理文件: trajectory_dir/{exp_id}/exports/conversation.json

反之:
  物理文件目录名 {exp_id}
  → DB devin_problem_runs._key = "pipe_{exp_id}"
  → DB devin_problem_runs.problem_id
  → DB problem_extraction_progress._key
  → 题目原文 + 来源数据集 + 入库时间
```

### 7.3 答案泄漏检查（运行时）

**每次运行启动时，Runner必须检查给AI的题目数据是否因为清洗时的疏忽，导致答案也同时进入了AI的上下文。**

检查内容：
1. 题目文本（`problem_text`）中是否包含`answer`字段的值
2. 题目文本中是否包含`solution_text`的关键片段
3. AGENTS.md文件中是否意外包含了答案

检查时机：
- Runner写入AGENTS.md后、启动devin cli前
- 如果检测到泄漏，不入running队列，直接入failed队列，verdict=`answer_leak_in_input`

### 7.4 失败分类记录

**AI运行失败的各种情况，必须分类记录，不能笼统记为"failed"。**

失败分类（verdict字段）：

| verdict | 含义 | 检测方法 |
|---|---|---|
| `candidate_solved` | 检测到PROOF COMPLETE | tmux pane中有`### PROOF COMPLETE` |
| `answer_leak` | AI自检发现答案泄漏 | tmux pane中有`### ANSWER LEAK DETECTED` |
| `answer_leak_in_input` | 运行前检查发现题目文本含答案 | Runner启动前检查 |
| `rate_limited` | API限流 | pane/log中有rate limit/429模式 |
| `failed_token_limit` | token/context超限 | pane/log中有token limit模式 |
| `failed_connection` | 连接错误 | pane/log中有connection error模式 |
| `failed_timeout` | 运行超时 | elapsed > timeout阈值 |
| `failed_stall` | 长时间无活动 | 文件大小长时间不变 |
| `dead_session` | tmux session在但pane空白 | tmux_running=True但pane_empty=True |
| `failed_no_proof` | session结束但无PROOF COMPLETE | tmux结束+无标记+无错误模式 |
| `launch_error` | 启动失败 | solver_harness launch退出码≠0 |

每类失败在ArangoDB `devin_problem_runs`中记录：
- `status`: 终态status名
- `verdict`: 上述分类
- `end_reason`: 具体原因描述
- `ended_at`: 结束时间
- `runtime_seconds`: 运行时长
- `observability.markers`: 检测到的标记

### 7.5 脚本化查询约束

**所有查询必须脚本化，严格限制inline脚本的使用。**

依据`no-inline-scripts`规则：禁止用`python -c "..."`写超过3行的脚本。所有查询脚本必须：
1. 写到`xishujuzhen/solver_harness/pipe/`目录中
2. 在AGENTS.md中做好索引
3. 持续维护，不重写

需要的查询脚本（见378号测试策略文档）：
- `audit_trace.py`: 双向追溯验证（DB→文件，文件→DB）
- `check_answer_leak.py`: 答案泄漏检查
- `query_failures.py`: 失败分类统计查询
- `query_progress.py`: 运行进度查询
- `verify_completeness.py`: 数据完备性验证（remainder=0）
- `verify_run_integrity.py`: 运行完整性验证（无工具调用+真实thinking+真实proof）
- `retry_infrastructure.py`: 基础设施失败自动重试
- `build_profile.py`: GLM-5.2能力边界Profile构建
- `extract_solve_time.py`: 精确解题时间提取（从conversation.json/trajectory.jsonl/tmux_pipe.log）

## 8. 核心验证原则与系统目标（2026-08-12 20:30补充）

### 8.1 系统目标：GLM-5.2数学能力边界Profile

**这个系统的最终目的不是"让AI做题"，而是"找出GLM-5.2的数学能力边界"。**

我们要在2.4M道竞赛级数学题上运行GLM-5.2（通过devin cli），构建一个能力边界Profile：
- 哪些题GLM-5.2能做出来（candidate_solved）
- 哪些题GLM-5.2做不出来（模型自身能力不足）
- 做不出来的题按失败类型分类（token限制/承认无法做/thinking spin等）
- 按数据集、难度tier、题目类型统计能力分布

**关键区分：基础设施失败 ≠ 模型能力失败**

| 类别 | 含义 | 处理方式 | 是否计入Profile |
|---|---|---|---|
| **基础设施失败** | 网络断连、API限流、连接超时、launch失败 | 记录后自动重试 | ❌ 不计入（不是模型能力问题） |
| **模型能力失败** | token/output长度限制、AI承认无法做、thinking spin、逻辑错误 | 记录为Profile数据 | ✅ 计入（这是能力边界） |
| **成功** | PROOF COMPLETE且有真实proof内容 | 记录为成功 | ✅ 计入 |

### 8.2 眼见为实：验证原则

**所有终态判定必须"眼见为实"——不能只靠标记模式匹配，必须真正看到AI的状态。**

#### 8.2.1 真实thinking检测

不能只检查tmux session是否存在。必须检查：
1. **tmux pane内容**：capture-pane后检查是否有thinking内容（数学符号、推理步骤）
2. **文件增长**：tmux_pipe.log或sessions_db/trajectory.jsonl是否在增长
3. **thinking标记**：pane中是否有"Thinking · Xs"等devin cli的thinking状态标记
4. **空白pane检测**：pane空白=Devin CLI已退出（dead session）

#### 8.2.2 真实proof验证

不能只检查`### PROOF COMPLETE`标记存在。必须验证：
1. **标记存在**：pane或log中有`### PROOF COMPLETE`
2. **proof有内容**：标记之前有实质性的数学推理内容（不是空证明）
3. **proof长度合理**：proof内容至少100字符（防止只有标记没有内容）
4. **无矛盾标记**：没有同时出现`### ANSWER LEAK DETECTED`或`I cannot solve`等放弃标记

#### 8.2.3 无工具调用验证（关键约束）

**除了devin cli默认加载的AGENTS.md，绝对不发生任何工具调用。**

这是测试纯数学thinking能力的硬约束——如果AI调用了工具（写文件、执行命令、搜索等），那不是在测试数学能力，是在测试工具使用能力。

验证方法：
1. **检查sessions.db**：查message_nodes表中是否有tool_call类型的节点
2. **检查trajectory.jsonl**：查是否有tool_use/tool_result事件
3. **检查工作目录**：除AGENTS.md和trajectory文件外，不应有其他新建文件
4. **AGENTS.md中明确禁止**：在给AI的AGENTS.md中写明"不要使用任何工具，只在TUI中用thinking解题"

如果检测到工具调用：
- 该次运行标记为`invalid_tool_use`
- 不计入Profile
- 需要重新运行

### 8.3 失败分类重构

#### 8.3.1 基础设施失败（重试，不计入Profile）

| verdict | 含义 | 检测方法 | 重试策略 |
|---|---|---|---|
| `failed_connection` | API连接错误 | pane/log中connection error模式 | 自动重试，最多3次 |
| `rate_limited` | API限流 | pane/log中rate limit/429模式 | 延迟60秒后重试 |
| `launch_error` | solver_harness启动失败 | launch退出码≠0 | 自动重试，最多3次 |
| `dead_session` | tmux在但pane空白 | tmux_running=True但pane_empty=True | 自动重试，最多3次 |

#### 8.3.2 模型能力失败（Profile数据，不重试）

| verdict | 含义 | 检测方法 | Profile意义 |
|---|---|---|---|
| `failed_token_limit` | token/context超限 | pane/log中token limit模式 | AI思维空间不足 |
| `failed_output_limit` | 输出长度限制导致中断 | proof内容被截断 | AI表达空间不足 |
| `ai_gave_up` | AI承认无法做 | pane中出现"I cannot"/"无法"/"give up"等 | AI自知力边界 |
| `failed_thinking_spin` | thinking循环不收敛 | 长时间无新内容但有thinking标记 | AI推理死循环 |
| `failed_no_proof` | session结束但无PROOF COMPLETE | tmux结束+无标记+无错误模式 | AI未完成证明 |
| `failed_stall` | 长时间无活动 | 文件大小长时间不变 | AI卡住 |
| `invalid_tool_use` | 检测到工具调用 | sessions.db中有tool_call | 运行无效，不计入 |

#### 8.3.3 成功

| verdict | 含义 | 检测方法 | Profile意义 |
|---|---|---|---|
| `candidate_solved` | PROOF COMPLETE且有真实proof | 标记存在+proof内容≥100字符+无工具调用 | AI做出来了 |

### 8.6 精确解题时间记录（2026-08-12 21:00补充）

**解题时间长度是Profile的核心维度之一——GLM-5.2做一道题需要多长时间，是能力边界的重要指标。**

#### 问题：粗略elapsed ≠ 精确解题时间

目前Collector记录的`elapsed`是从Runner入队列到Collector判定的时间，包含：
- launch_overhead（Runner启动devin cli的时间）
- init_overhead（devin cli初始化时间）
- solve_time（AI实际解题时间）← 这是我们要的
- tail_overhead（AI完成到Collector判定的时间）
- judge_delay（Collector轮询间隔带来的延迟）

实测数据（旧系统运行）：
```
init_overhead:     0.2s
solve_time:        116.1s  ← AI实际解题时间
tail_overhead:     96.9s
total_session:     213.1s  ← 粗略elapsed会记录这个
```
粗略elapsed（213s）是精确solve_time（116s）的1.8倍——误差太大。

#### 精确时间提取方案

`extract_solve_time.py`从多个数据源提取精确时间，按优先级：

1. **exports/conversation.json**（ATIF-v1.7格式，毫秒级ISO时间戳）——最精确
   - `steps`数组中每步都有`timestamp`字段
   - solve_time = 最后一个step的timestamp - 第一个step的timestamp
   - 还能提取token统计（prompt_tokens/completion_tokens/cached_tokens）

2. **sessions_db/trajectory.jsonl**（Unix timestamp）——备选
   - 每行有`created_at`字段
   - solve_time = 最后一行的created_at - 第一行的created_at

3. **tmux_pipe.log文件时间**（粗略）——最后fallback
   - solve_time ≈ 文件修改时间 - 文件创建时间

#### 时间分解

```
runner.start_time (Runner入队列)
  → session_info.start_timestamp (devin cli启动)       = launch_overhead
  → conversation第一个step (AI开始工作)                  = init_overhead
  → conversation最后一个step (AI完成最后输出)            = solve_time ← 核心指标
  → collector判定时间                                    = judge_delay
```

#### Collector集成

Collector在判定终态时：
1. 调用`extract_solve_time`提取精确时间
2. 在kill tmux session前等待conversation.json生成（最多等10秒）
3. 将`solve_time_seconds`和`solve_time_source`写入Redis结果和DB

#### DB记录字段

每次运行在`devin_problem_runs`中记录：
- `runtime_seconds`: 粗略elapsed（保留，用于对比）
- `solve_time_seconds`: 精确解题时间（核心指标）
- `solve_time_source`: 时间来源（conversation.json/trajectory.jsonl/tmux_pipe.log mtime）
- `init_overhead_seconds`: 初始化开销
- `prompt_tokens`: prompt token数
- `completion_tokens`: completion token数
- `cached_tokens`: cached token数
- `total_steps`: 总step数

#### Profile中的时间统计

`build_profile.py`中增加：
- **时间分布**：min/P50/P90/P99/max/avg
- **成功vs失败时间对比**：成功题目的平均解题时间 vs 失败题目的平均解题时间
- 这个对比能揭示：是做不出来的题花的时间更长（卡住后超时），还是做出来的题花的时间更长（复杂题需要更多推理）

### 9.2 日志规范

#### 9.2.1 日志基础设施

- **日志模块**：`shared_logger.py`
- **日志目录**：`/data/math-agent-glm5.2-tmux-agents-trajectory/_pipe/logs/`
- **单文件分片**：1MB
- **总量限制**：10GB（约10240个分片）
- **滚动方式**：RotatingFileHandler，达到上限后覆盖最老的文件
- **格式**：`[时间] [级别] [模块名] 消息`

#### 9.2.2 日志文件

每个模块有独立的日志文件，同时写入统一的`pipe.log`：

| 文件 | 内容 |
|---|---|
| `runner.log` | Runner服务日志（启动、选题、launch、答案泄漏检查） |
| `collector.log` | Collector服务日志（扫描、判定、终态、时间提取） |
| `feeder.log` | Feeder服务日志（选题AQL、入队、水位检查） |
| `reporter.log` | Reporter服务日志（统计、告警） |
| `retry.log` | 重试服务日志（基础设施失败重试） |
| `pipe.log` | 统一日志（所有模块的日志合并，方便查看全局状态） |

#### 9.2.3 日志级别规范

| 级别 | 使用场景 | 示例 |
|---|---|---|
| ERROR | 连接失败、DB写入失败、launch失败 | `logger.error("Redis连接失败")` |
| WARNING | 答案泄漏、工具调用检测、pane空白、异常 | `logger.warning("答案泄漏: {problem_key}")` |
| INFO | 终态判定、每轮统计、启动/停止、重要状态变化 | `logger.info("SOLVED {key} ({elapsed}s)")` |
| DEBUG | 详细的pane分析、标记匹配、时间提取细节 | `logger.debug("pane内容: math_count=8, thinking=True")` |

#### 9.2.4 各模块的日志要点

**Runner**：
- 启动参数（concurrency/model/poll_interval）
- 每次poll的slots和取到的题数
- 每题的launch过程（开始/成功/失败/耗时）
- 答案泄漏检查结果
- attempt记录创建

**Collector**：
- 每轮扫描的running数
- 每个attempt的判定过程（检测到什么标记、pane内容分析、thinking状态）
- 终态判定结果（verdict + 依据）
- pane snapshot保存（行数、文件大小）
- 精确时间提取（来源、solve_time值）
- export等待（等了多少秒、是否成功）

**Feeder**：
- 选题AQL执行（tier/batch_size/limit）
- 入队每题的key和priority
- 水位检查（pending低于low-water-mark时补充）

**Reporter**：
- 每次统计的数值变化
- 告警触发条件
- 吞吐量计算（每分钟完成数）

**Retry**：
- 每个failed项的verdict判定
- 重试决策（重试/不重试/达到上限）
- 重试次数查询结果
