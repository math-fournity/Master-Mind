## §0 自包含POC方案文档的设计规范（本节是所有POC方案文档的共用规范）

### 0.1 设计目标

一份POC方案文档要让未来20万上下文的AI**只加载这份文档+它索引的少数核心文档**，就能完整了解做好这次POC所需的所有背景知识，不需要用户另外指点应该读什么。

### 0.3 "自包含"的含义

"自包含"不是把所有背景知识复制进文档——那样文档会膨胀到无法加载。"自包含"是指：

1. **文档本身包含这个POC执行所需的全部操作信息**——输入/方法/输出/通过标准/执行约束
2. **文档明确列出需要全文加载的背景文档清单**——每份说明加载理由（这个POC为什么需要这份文档的内容）
3. **未来AI加载这份POC方案后，按照§8清单去全文加载被索引的文档**——不需要用户另外指点

### 0.4 被索引文档的精挑细选原则

每份POC方案文档的§8清单应该精挑细选——只列这个POC真正需要的背景文档，通常3-7份。如果索引太多，未来AI加载不完。

**挑选标准**：
- **必须加载**：这个POC不加载这份文档就无法正确执行（如题包/TellCore定义/通过标准来源）
- **建议加载**：这个POC加载这份文档能更好理解为什么这么做（如理论背景/原设计文档）
- **不列**：这个POC不需要这份文档的内容（如其他POC的方案文档）

```
{编号}-v0-{日期}-POC-{POC编号}-{POC名称}-自包含方案文档.md
```

## §1 本POC的定位与核心问题

### 1.1 POC编号与名称

**POC-2：可选择**

### 1.2 在POC系列中的位置

POC-2在修订后的11个POC系列中位于**Phase B基础验证的第一个**：

```
Phase A：策略对象成形
  POC-0 Case Pack冻结（✅已完成）
  POC-0.5 变形关系声明（新增）
  POC-1 因果取商（✅已完成）

Phase B：基础验证
  ★ POC-2 可选择（本POC）★
  POC-2.5 基础因果效应验证（快速失败门）
  POC-3.5 Hint非特化程度验证
  POC-3 可执行
  POC-4 可终止

Phase C：归责与学习
  POC-6 可归责
  POC-7 可持续学习（简化版）

Phase D：端到端
  POC-8 端到端闭环（+对照模型）
  POC-9 识别端验证
```

POC-5可组合推迟到第二个Tell家族验证后。

POC-2是Phase B的入口——在Phase A产出TellCore之后，第一个要验证的不是"Hint有没有用"（那是POC-2.5的事），而是"系统能否正确选择Tell"。

### 1.3 核心问题

**POC-2回答**：

> 当Tell库中存在多个候选Tell时，系统是否知道什么时候选目标Tell，什么时候拒绝它？

这一步主要测试**selector**——给定一道题的problem state，selector能否从Tell库中正确选中目标TellCore，能否在假朋友题上正确拒绝或降权目标TellCore。**POC-2不测试hint是否有效**——不测试HintInstance给出后AI能否成功解题。那是POC-2.5和POC-3的工作。

### 1.4 为什么selector需要单独验证

373号§3.2指出一个关键风险：**检索命中被误当成策略选择**。如果selector只是按相似度排序，不做trigger条件检查和negative boundary检查，那么表面相似但关键结构缺失的假朋友题也会被选中目标Tell——这会导致假朋友迁移，即Tell在不应触发的地方触发了。

selector的正确行为应该是：
- **正迁移题**：目标Tell进入top-k（因为trigger条件满足，且negative boundary不满足）
- **假朋友题**：目标Tell被拒绝或降权（因为negative boundary满足，或trigger条件不满足）
- **边界题**：标为boundary，不强行归为正例或负例

POC-2就是验证selector能否做到这些。

### 1.5 397号审视结论

397号§1.3审视结论：**POC-2合理，无过度设计。**

- selector验证是必要的——检索命中被误当成策略选择会导致假朋友迁移
- 通过标准（正迁移题中目标Tell进入top-2达80%/假朋友题中目标Tell被拒绝或降权达80%/selector必须输出理由不能只输出相似度分数/错选时必须能归因）是合理的
- 80%只是小样本工程门槛不是科学显著性结论——这个声明是诚实的

## §2 理论背景——为什么需要这个POC

### 2.1 396号的三对象分离

396号§4.3建立了TellCore/HintRenderer/HintInstance三对象分离的理论框架：

- **TellCore**：策略的内核——不变量声明、触发条件、负边界、参数槽、内部策略、进展模型、终止条件。TellCore是识别端和学习端的交接物——从成功trace中提取，供selector选择。
- **HintRenderer**：把TellCore渲染成HintInstance的组件——控制非特化程度（Level低/中/高）。
- **HintInstance**：注入到AI解题过程中的具体提示——是HintRenderer的产物。

**关键论断**：selector选择的是**TellCore**，不是HintInstance。selector在题目输入后、HintRenderer运行之前工作——它从Tell库中选出适合当前题目的TellCore，然后才由HintRenderer把选中的TellCore渲染成HintInstance。

POC-2验证的就是这个选择环节——给定problem state，selector能否正确选择TellCore。

### 2.2 372号六门审计中的"可选择门"

372号§16提出六门审计：Tell必须成为**可选择、可执行、可终止、可组合、可归责、可持续学习**的认知策略。

"可选择"是六门的第一门——如果系统连"什么时候用这个Tell、什么时候不用"都判断不了，后面的可执行、可终止、可归责都没有意义。selector是整个Tell系统的入口控制。

### 2.3 不验证会留下什么gap

如果跳过POC-2直接做POC-2.5（基础因果效应验证）：

- **假朋友迁移风险**：如果selector在假朋友题上也选中目标Tell，然后HintRenderer渲染成HintInstance注入AI——AI可能在不应使用局部-全局切换的题上被误导。POC-2.5的"bare+Hint"对照会混淆"Hint无效"和"Hint选错了Tell"两种情况。
- **无法归因**：如果POC-2.5中Hint无效，无法区分是"TellCore本身不对"还是"selector选错了Tell"——因为selector没有先验证过。

所以POC-2必须在POC-2.5之前——先确认selector能正确选择，然后才能在POC-2.5中测试选中后的Tell是否有效。

### 2.4 selector的输出不只是排序

373号§7.4明确要求：**selector必须输出理由，不能只输出相似度分数。**

这意味着selector不是一个黑盒检索器——它必须输出：
- 选择理由（为什么选这个TellCore，trigger条件哪些满足）
- 拒绝理由（为什么不选其他TellCore，negative boundary哪些满足）
- 绑定预览（参数槽如何绑定到当前题目的对象）

POC-2验证的不仅是"选对了没有"，还有"选择理由对不对"——因为只有理由正确，后续的归责（POC-6）和可持续学习（POC-7）才能依赖selector的输出。

## §4 输入——这个POC需要什么

### 4.1 题包

从382号CasePack v0的22道题中取以下几类：

| 题目类别 | 数量 | 在POC-2中的角色 |
|---|---|---|
| 正迁移题 | 4道 | 目标Tell应被选中——验证selector在"该选时能否选对" |
| 假朋友题 | 5道 | 目标Tell应被拒绝或降权——验证selector在"不该选时能否拒绝" |
| 边界题 | 3道 | 目标Tell应标为boundary——验证selector在边界附近是否谨慎 |

**正迁移题的标准**（来自382号§1.2和373号§14.8）：
- 真实bare失败（有完整bare失败记录）
- 目标Tell（局部-全局表示切换）是低搜索成本主路
- 过程可观察（thinking中能看见表示切换的过程信号）
- 解答可核验（有verified solution）
- 泄漏安全（Tell只给策略不给答案）

**假朋友题的标准**（来自373号§14.8）：
- 表面像目标题，但关键结构缺失
- 必须写清楚：哪几个表面特征诱导误触发，哪一个关键结构缺失导致目标Tell不应执行
- 不能太明显（否则selector拒绝没有意义），也不能本质上仍适用目标Tell（否则误把正例当负例）

**边界题的标准**（来自373号§14.8）：
- 只改变一个关键条件
- 用来测trigger边缘——如果系统选择boundary或abstain，通常比强行选择或强行拒绝更健康

### 4.2 目标TellCore

383号确定的TellCore v0候选C（局部-全局表示切换），7字段最小充分集：

1. **invariant_claim**——不变量声明（切换到局部表示后能找到什么不变量）
2. **trigger_boundary**——触发条件（什么情况下应该切换表示）
3. **negative_boundary**——负边界（什么情况下不应切换表示）
4. **parameter_slots**——参数槽（绑定到当前题目的什么对象）
5. **internal_policy**——内部策略（切换后做什么认知动作）
6. **progress_model**——进展模型（预期可观察的中间信号）
7. **termination**——终止条件（什么时候停止或让位）

### 4.3 小型Tell库

373号§7.2要求构造一个小型Tell库，包含以下几类TellCore：

| TellCore类型 | 数量 | 作用 |
|---|---|---|
| 目标TellCore | 1个 | 局部-全局表示切换（383号TellCore v0候选C） |
| 近邻TellCore | 2-4个 | 与目标TellCore结构相近但trigger条件不同——测试selector能否区分近邻 |
| 错配TellCore | 2个 | 与目标TellCore明显不匹配的TellCore——测试selector能否在错配题上不选目标 |
| 通用反思TellCore | 1个 | "仔细检查你的证明"之类的通用反思——作为干扰项，测试selector能否不被通用Tell抢占 |

**近邻TellCore的构造原则**：近邻TellCore应该是与目标TellCore在某个维度上相似但trigger条件不同的Tell。例如：
- "不变量识别"型Tell——与"局部-全局切换"在"找不变量"上相似，但trigger条件不同（不需要切换表示）
- "构造-分析-排除"型Tell——与"局部-全局切换"在"换视角"上相似，但操作策略不同

**错配TellCore的构造原则**：错配TellCore应该是在目标题包的题上完全不应触发的Tell。例如：
- "归纳法"型Tell——在需要表示切换的题上不应首选
- "极端原理"型Tell——在需要局部-全局切换的题上不应首选

**通用反思TellCore**：如"当你卡住时，重新审视题目条件，检查是否有遗漏的约束"——这种Tell对任何题都"有点用"但不是目标Tell，测试selector能否不被它抢占top位置。

### 4.4 Selector

selector是POC-2的被测对象。selector的输入和输出：

**输入**：
- problem state（题目状态——题面+当前解题进展，如果有的话）
- Tell库（§4.3的小型Tell库，6-8个TellCore）

**输出**（373号§7.3的SelectorEvidence）：
- top-k Tell候选（k建议为3）
- 每个候选的ranking_reason（为什么排在这里）
- trigger_features（哪些trigger条件满足）
- negative_features（哪些negative boundary满足）
- binding_preview（参数槽如何绑定到当前题目对象）
- decision（select / reject / abstain / boundary）

### 4.5 模型

POC-2主要测试selector，不启动Solver做解题。selector本身可以由AI（GLM-5.2 High）担任——即让AI读题目和Tell库，输出选择决策和理由。

如果selector是独立程序（非AI），则需要该程序的输入输出接口。当前阶段selector可以是AI扮演的——让AI读题+读Tell库，输出SelectorEvidence。

## §5 方法——这个POC怎么做

### 5.1 实验设计

373号§7.2的方法：对CasePack中的题逐题执行选择。

```
problem state
  → selector
  → top-k Tell候选
  → abstention或选择
  → 记录选择理由
```

对每道题，selector输出：
1. top-k候选TellCore的排序
2. 每个候选的选择理由
3. trigger_features和negative_features的检查结果
4. binding_preview
5. 最终decision（select/reject/abstain/boundary）

### 5.2 对照矩阵

对12道题（4正迁移+5假朋友+3边界），每道题执行1次选择，共12个选择事件。

每个选择事件记录：

| 指标 | 内容 |
|---|---|
| expected_decision | 预期决策（来自CasePack的预注册——select/reject/abstain/boundary） |
| actual_decision | selector实际输出的决策 |
| decision_correct | 决策是否正确（actual == expected） |
| target_in_top_k | 目标TellCore是否在top-k中 |
| target_rank | 目标TellCore在排序中的具体位置（1/2/3/未入选） |
| ranking_reason | selector给出的排序理由 |
| trigger_features_checked | trigger条件检查结果 |
| negative_features_checked | negative boundary检查结果 |
| binding_preview | 参数槽绑定预览 |
| misselection_attribution | 如果错选，归因到什么原因（见§5.4） |

### 5.3 分题目类别的预期行为

**正迁移题（4道）**：
- expected_decision: select
- 目标TellCore应进入top-2
- selector应输出trigger条件满足的理由
- negative boundary应不满足
- binding_preview应正确绑定参数槽到题目对象

**假朋友题（5道）**：
- expected_decision: reject或降权（目标TellCore不在top-2）
- selector应输出negative boundary满足的理由，或trigger条件不满足的理由
- 如果selector仍然选中目标TellCore——这是误触发，需要归因

**边界题（3道）**：
- expected_decision: boundary或abstain
- selector不应强行归为正例或负例
- 如果selector选择boundary——这是健康的行为
- 如果selector强行select或强行reject——需要分析trigger边界是否写得太宽或太窄

### 5.4 错选归因

373号§7.4要求：**错选时必须能归因到trigger缺失、negative trigger缺失、绑定错误或候选Tell过近。**

当selector的决策与expected_decision不一致时，必须分析错选原因：

| 错选类型 | 可能原因 | 归因方向 |
|---|---|---|
| 正迁移题目标Tell未进top-2 | trigger条件写得太窄 | 修订trigger_boundary |
| 正迁移题目标Tell未进top-2 | 近邻TellCore太近，挤掉了目标 | 修订近邻TellCore或调整排序权重 |
| 假朋友题目标Tell被选中 | negative boundary写得太宽 | 修订negative_boundary |
| 假朋友题目标Tell被选中 | trigger条件写得太宽 | 修订trigger_boundary |
| 假朋友题目标Tell被选中 | binding错误——参数槽绑到了错误的表面特征 | 修订binding_rules |
| 边界题被强行select | trigger边界未覆盖此边界情况 | 修订trigger_boundary |
| 边界题被强行reject | negative boundary过宽 | 修订negative_boundary |
| 通用反思Tell抢占top-1 | selector没有做trigger条件检查，只按相似度排序 | 修订selector逻辑 |

### 5.5 操作步骤

1. 从382号CasePack v0取4道正迁移题、5道假朋友题、3道边界题
2. 从383号TellCore v0取目标TellCore（局部-全局表示切换，7字段最小充分集）
3. 构造小型Tell库：1个目标TellCore + 2-4个近邻TellCore + 2个错配TellCore + 1个通用反思TellCore（共6-8个TellCore）
4. 对每道题，把problem state和Tell库输入selector
5. selector输出SelectorEvidence（top-k排序+理由+trigger检查+negative检查+binding预览+decision）
6. 对比expected_decision和actual_decision，记录decision_correct
7. 如果错选，按§5.4归因
8. 汇总12个选择事件的结果，产出SelectorEvidence汇总
9. 按§7的通过标准判定

### 5.6 与POC-2.5的关键区别

POC-2和POC-2.5都涉及"给AI什么"，但测试的对象完全不同：

| | POC-2 可选择 | POC-2.5 基础因果效应 |
|---|---|---|
| 被测对象 | selector | HintInstance |
| 输入 | problem state + Tell库 | 题目 + HintInstance |
| 输出 | top-k排序+决策+理由 | 解题成功/失败+过程信号 |
| 核心问题 | 选对Tell没有 | 给了Hint后AI更好没有 |
| 是否启动Solver | 否（只做选择，不解题） | 是（跑bare vs bare+Hint对照） |

**POC-2不启动Solver解题**——它只测试selector的选择能力，不测试Hint是否有效。只有POC-2通过（selector能选对），才进入POC-2.5测试选中后的Tell是否有效。

## §7 通过标准

### 7.1 通过标准

**POC-2通过，需要满足以下全部条件**（来自373号§7.4）：

1. **正迁移题中目标Tell进入top-2的比例达到80%左右**——4道正迁移题中至少3道目标Tell进入top-2
2. **假朋友题中目标Tell被拒绝或降权的比例达到80%左右**——5道假朋友题中至少4道目标Tell被拒绝或降权（不在top-2）
3. **边界题可以标为boundary，不能强行归为正例**——3道边界题中不应有强行select的
4. **selector必须输出理由，不能只输出相似度分数**——12个选择事件中每个都有ranking_reason
5. **错选时必须能归因到trigger缺失、negative trigger缺失、绑定错误或候选Tell过近**——所有错选事件都有misselection_attribution

**关于80%**：这里的80%只是小样本工程门槛，不是科学显著性结论。12道题的样本量太小，无法做统计检验。80%是一个工程上"大部分对了"的阈值——如果连80%都达不到，说明selector有系统性问题，不是随机波动。

### 7.2 不通过的处理

**如果条件1不满足（正迁移题目标Tell未进top-2）**：

- 可能是trigger_boundary写得太窄——目标TellCore的trigger条件没有覆盖正迁移题的关键特征
- 可能是近邻TellCore太近——近邻TellCore与目标TellCore在trigger条件上重叠太多，挤掉了目标TellCore
- 处理：修订trigger_boundary或调整近邻TellCore的trigger条件，使其与目标TellCore有更清晰的区分

**如果条件2不满足（假朋友题目标Tell未被拒绝或降权）**：

- 可能是negative_boundary写得太宽——目标TellCore的negative boundary没有覆盖假朋友题的关键结构缺失
- 可能是trigger_boundary写得太宽——目标TellCore的trigger条件被假朋友题的表面特征满足
- 可能是binding错误——参数槽绑到了假朋友题的表面特征而非结构特征
- 处理：修订negative_boundary或trigger_boundary或binding_rules

**如果条件3不满足（边界题被强行select）**：

- 可能是trigger边界未覆盖此边界情况——trigger_boundary的粒度不够细
- 处理：在trigger_boundary中增加此边界情况的说明，使selector在边界附近选择boundary或abstain

**如果条件4不满足（selector只输出相似度分数没有理由）**：

- selector的实现有问题——没有做trigger条件检查和negative boundary检查
- 处理：修订selector的实现，要求它输出trigger_features、negative_features、binding_preview

**如果条件5不满足（错选时无法归因）**：

- selector的输出信息不够——没有输出足够的信息来诊断错选原因
- 处理：修订selector的输出格式，要求它输出足够的信息（trigger检查结果/negative检查结果/binding预览）来支持归因

### 7.3 模糊结果的处理

**如果结果是ambiguous（有些题选对了有些选错了）**：

- 记录哪些题选对了哪些选错了
- 分析差异——是题目类型不同、还是trigger边界在某些题上不清楚
- 模糊结果不阻塞POC-2.5——可以在选对的题上先做POC-2.5，同时修订selector后重跑选错的题
- 但要在SelectorEvidence中明确记录哪些题上selector可靠，后续POC只在这些题上做

### 7.4 通过后不意味着selector"完美"——只意味着"工程可用"

**重要**：POC-2通过只说明selector在该题包上达到了工程门槛——这是最基础的验证。但这不意味着selector"完美"——因为：

- 12道题的样本量太小，无法做统计检验
- 小型Tell库只有6-8个TellCore——真实Tell库可能有几十个，选择难度更大
- selector可能是AI扮演的——真实selector可能是独立程序，行为可能不同

POC-2通过后，继续做POC-2.5（基础因果效应验证），在POC-2.5中可以用selector自动选择目标Tell，也可以人工指定用目标TellCore（作为对照）。

## §9 执行约束

### 9.1 Solver启动

POC-2主要测试selector，**不启动Solver解题**。selector可以由AI（GLM-5.2 High）担任——让AI读题+读Tell库，输出SelectorEvidence。

如果后续需要将selector独立为程序，则该程序的启动仍需遵守项目硬约束。但POC-2阶段不涉及Solver启动。

### 9.2 ArangoDB

POC-2不连接ArangoDB（不读不写数据库）。小型Tell库和SelectorEvidence都以文件形式存储。

### 9.3 Git

- Git add必须显式路径，不能`git add -A`或`git add .`
- 产物文件（poc_2_selector_evidence.yaml / poc_2_per_problem/ / poc_2_tell_library.yaml / poc_2_analysis.md）必须commit

### 9.4 POC运行记录

POC-2的运行记录是12个SelectorEvidence文件——每个记录selector对一道题的选择决策和理由。这些文件必须完整保存。

### 9.5 证据分层

POC结论必须写成证据分层——不把"selector在该题包上达到工程门槛"升级成"selector在所有题上都能正确选择"。

POC-2通过只说明selector在382号CasePack v0的12道题上达到了工程门槛。这不意味着：
- selector在更大Tell库（>8个TellCore）上也能正确选择
- selector在其他题型上也能正确选择
- selector是AI扮演时和独立程序时的行为一致

### 9.6 题包先冻结不能补题

373号§3.2的铁律：题包先冻结，实验后不能补题。POC-2用的12道题来自382号CasePack v0，已冻结。不能因为selector在某些题上选错了就临时换题。选错的题要记录为反例，按§7.2分析原因。

### 9.7 失败不是废结果

如果POC-2不通过（selector选择能力不达标），这不是废结果——这揭示了TellCore的trigger_boundary或negative_boundary需要修订。不通过的结果必须完整记录，并触发对POC-1 TellCore的trigger_boundary/negative_boundary/binding_rules的修订。

## §10 与其他POC的关系

### 10.1 前置关系

```
POC-0（题包冻结）→ POC-1（TellCore确定）→ ★ POC-2（selector验证）★
```

POC-2依赖POC-0的题包（正迁移题/假朋友题/边界题）和POC-1的TellCore（目标TellCore）。POC-0和POC-1均已完成，POC-2可以立即执行。

### 10.2 后续关系

```
★ POC-2（selector验证）★ → POC-2.5（基础因果效应验证）→ POC-3.5（Hint非特化程度验证）→ POC-3（可执行）→ POC-4（可终止）
```

**POC-2通过后才能做POC-2.5**——如果selector都选不中目标Tell，POC-2.5无法进行。POC-2.5需要在"selector已验证能选对目标Tell"的前提下，测试选中后的Tell是否有效。如果selector选错了Tell，POC-2.5的"bare+Hint"对照会混淆"Hint无效"和"Hint选错了Tell"两种情况。

**POC-2通过后才能做POC-6（可归责）**——POC-6的干预矩阵中有"错配Tell"对照。如果selector无法区分目标Tell和错配Tell，POC-6的"错配Tell"对照就不可靠——可能是selector选了目标Tell而非错配Tell。

### 10.3 如果POC-2不通过

- **不通过不阻塞POC-9（识别端验证）**——识别端从失败trace读分叉，不依赖selector
- **不通过阻塞POC-2.5/3.5/3/4/6/7/8**——这些POC都依赖selector能正确选择目标Tell
- **不通过触发对POC-1 TellCore的修订**——如果selector选错，可能是TellCore的trigger_boundary或negative_boundary写得不对
- **不通过触发对小型Tell库的修订**——如果近邻TellCore太近导致挤掉目标TellCore，需要调整近邻TellCore的trigger条件
- **不通过触发对selector逻辑的修订**——如果selector只按相似度排序不做trigger条件检查，需要修订selector的实现

### 10.4 POC-2与POC-2.5的协作

POC-2通过后，POC-2.5可以：
- 用selector自动选择目标Tell（推荐——验证了的选择路径）
- 同时人工指定用目标TellCore作为对照（确认selector选的就是目标TellCore）

两种方式同时做，可以区分"selector选对了"和"人工指定选对了"的差异——如果两种方式结果一致，说明selector可靠；如果结果不一致，说明selector在某些题上选的不是目标TellCore。
