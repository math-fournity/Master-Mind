# 344号 · trace去特化后长什么样——去特化程度决定产出是普通Tell还是高Level Tell

**日期**：2026-08-11
**触发原因**：用户提问"一个trace去特化之后长什么样子呢？难道是一个高Level的Tell？"，随后追问"去特化后的trace，和高Level的Tell，它们两者之间的区别是什么？"
**上下文**：入题侧脉络分析1.0完成后，讨论下一个Pipe（trace去特化→(tell,hint)→按分类学存储）

---

## 核心结论（v1修正）

**trace去特化后的产出不总是普通Tell——去特化的程度和trace本身的抽象程度共同决定产出是普通Tell还是高Level Tell。**

- 去特化到**具体概念层**（第三层属性维度） → 普通Tell——坐标系中的**点**，有明确{domain, 段结构模式}属性，可以被归入某个分类目录
- 去特化到**段结构模式层或更高**（第二层属性维度及以上） → 高Level Tell——坐标系中的**坐标轴/刻度**，不可被归入某个分类目录，它本身就是分类目录

**v0结论的错误**：v0说"去特化后是普通Tell，不是高Level Tell"——这个结论太绝对了。去特化是有程度的，344号v0自己也提到了"过宽/过窄/恰好"的问题，但没有意识到"过宽"的极端就是高Level Tell。

---

## 去特化的两种产出

### 产出1：普通Tell（去特化到具体概念层）

**在分类学中的位置**：坐标系中的**点**——有明确{domain, 段结构模式}属性，可以被归入某个分类目录

**是结构知识还是内容知识**（336号）：内容知识

**存储方式**：存入对应分类目录的tell库（AGENTS.md目录+devin cli从中启动）

**识别逻辑**：遍历tell条目逐一匹配trace

**例子**（来自VMS-28c验证结果）：

| trace | 去特化后的tell | 分类位置 |
|---|---|---|
| trace_3 "鸽巢论证找存在性元素" | 鸽巢论证找存在性元素 | {组合, 构造-分析-排除, 鸽巢论证} |
| trace_13 "强归纳作为统一框架" | 强归纳 | {组合, 归约策略, 强归纳} |
| trace_15 "定义辅助变量简化归纳结构" | 辅助变量简化 | {代数, 构造-分析-排除, 辅助函数} |
| trace_8 "swap避障技巧" | 排列构造中的swap修复技巧 | {组合, 构造-分析-排除, swap修复}（新类型） |

这些tell都有明确的domain和段结构模式属性，是坐标系中的点。

### 产出2：高Level Tell（去特化到段结构模式层或更高）

**在分类学中的位置**：坐标系中的**坐标轴/刻度**——不可被归入某个分类目录，它本身就是分类目录

**是结构知识还是内容知识**（336号）：结构知识

**存储方式**：存入高Level概念解释库（技术说明书04-概念树/07），有专门的AGENTS.md目录承载（338号）

**识别逻辑**：理解概念+格化脉络+判断适用条件（无列表可遍历，340号第二种类型）

**例子**：

| trace | 去特化后的tell | 分类位置 | 类型 |
|---|---|---|---|
| trace_17 "四步元模式（定义→归纳→构造→验证）跨Case复用" | 累积-收敛 | 段结构模式层——坐标轴上的刻度 | 高Level Tell（可展开的，340号第一种） |
| "x贯穿整个证明" | 关键实体贯穿性 | 超出当前分类学——可能是新的结构维度 | 高Level Tell（可能需要分类学修正） |
| "整体策略是强归纳+情况分析+鸽巢计数的组合" | 归约策略+构造-分析-排除的组合 | 多个段结构模式的组合——坐标轴的组合 | 高Level Tell（组合型） |

这些tell没有单一的{domain, 段结构模式}属性——它们要么本身就是段结构模式（坐标轴的刻度），要么是多个段结构模式的组合（坐标轴的组合），要么超出当前分类学（可能是新的坐标轴）。

## 两种产出的核心区别

| | 普通Tell（去特化到具体概念层） | 高Level Tell（去特化到段结构模式层或更高） |
|---|---|---|
| **在分类学中的位置** | 坐标系中的**点** | 坐标系中的**坐标轴/刻度** |
| **有明确{domain, 段结构模式}属性** | 有——可以被归入某个分类目录 | 它**本身就是**分类目录——不可被归入 |
| **是结构知识还是内容知识** | 内容知识 | 结构知识（336号） |
| **存储方式** | 存入对应分类目录的tell库 | 存入高Level概念解释库（338号） |
| **识别逻辑** | 遍历tell条目逐一匹配 | 理解概念+格化脉络+判断适用条件（340号） |
| **组合爆炸风险** | 无——每个tell是独立的点 | 有（333号两个担忧）——可展开的类型组合爆炸可控，无法指定展开方向的类型覆盖缺口永远存在 |
| **case_source标记** | 不需要——有具体案例 | 需要（333号）——mathematics/system/none |

## 去特化的程度谱系

去特化不是二元的（普通Tell vs 高Level Tell），而是一个连续谱系：

```
Level 0（题目特化）
  trace_8 "swap避障技巧——通过交换排列中元素位置跳过障碍"（IMO 2009 P6特化）
    ↓ 去特化
Level 1（具体概念层）→ 普通Tell
  "排列构造中的swap修复技巧" {组合, 构造-分析-排除, swap修复}
    ↓ 进一步去特化
Level 2（段结构模式层）→ 高Level Tell
  "构造-分析-排除"（段结构模式本身，坐标轴上的刻度）
    ↓ 进一步去特化
Level 3（更高抽象）→ 高Level Tell（可能超出当前分类学）
  "构造性证明策略"（多个段结构模式的组合，或新的结构维度）
```

**去特化的度需要AI把握**：
- **去特化不够**（停留在Level 0）→ 仍然是trace，不是tell，不可泛化
- **去特化到Level 1** → 普通Tell，恰好可泛化，有明确分类位置
- **去特化到Level 2或更高** → 高Level Tell，是分类学的结构本身，需要不同的存储和识别方式
- **去特化过度**（过于抽象）→ 失去指导性，如"构造对象完成证明"匹配太多不相关的tell

## trace和tell的区别

**trace**（脉络分析产出）是Level 0的、和当前题目绑定的：
- 只有pattern_description（模式描述）
- 例：trace_8 "swap避障技巧——通过交换排列中元素位置跳过障碍"（IMO 2009 P6特化）

**tell**（去特化后的产物）是可泛化的、标准化的：
- 有完整的四个组成成分（000号文档定义）：
  1. branch_signal：分叉信号——可以分叉但AI没分叉的位置
  2. branch_type：分叉类型——翻译类型/操作路径类型/...
  3. unexplored_diagnosis：未探索诊断——AI为什么没走这条路
  4. direction_matching：方向匹配——从诊断到翻译方向的映射
- 有分类学位置——但位置在哪一层取决于去特化的程度：
  - 去特化到具体概念层 → 有{domain, 段结构模式, 具体概念}三层属性（普通Tell）
  - 去特化到段结构模式层 → 本身就是段结构模式（高Level Tell，是坐标轴不是点）

### 可能去特化到高Level Tell的trace

| trace | 去特化后的tell类型 | 说明 |
|---|---|---|
| trace_17 | 四步元模式（定义→归纳→构造→验证）跨Case复用 | 可能去特化为"累积-收敛"段结构模式——这是高Level Tell（坐标轴上的刻度） |
| trace_18 | 避障技巧的双重策略——预防性vs修复性 | 可能去特化为"构造-分析-排除"的子模式——这是具体概念层的普通Tell，但如果进一步抽象为"策略分类"则可能是高Level Tell |

### 去特化需要把握的度

- **太宽泛**：trace_11"排列构造跨Case复用"去特化为"构造对象完成证明"——匹配太多不相关的tell。需要收窄为"构造排列+验证避障"。
- **太狭窄**：trace_5"定义z=max(M)和M'后应用归纳"——"定义z=max(M)"太具体。需要拓宽为"定义辅助变量缩小问题规模后应用归纳"。
- **恰好**：trace_3"鸽巢论证找存在性元素"——既可泛化又不失指导性。

## 去特化的定义（来自287号）

**去特化**：把tell从Level 0（题目特化）提升到可泛化的Level，使tell可以被穷举。

**穷举是降低tell识别难度的手段**——tell需要被穷举成一组可枚举的模式，就像hint端的24个翻译方向是从"翻译语言"这个高Level方向展开的一样。

**去特化后的tell规模会很大**——10万级别是一个虚数，意思是不能假设全部tell可以放入辅助AI的上下文中，需要用分类学+检索Pipe降低到合理量级。

## 入题侧vs解题侧的区别

**入题侧（解答吸收）**：
- 输入是已验证的正确解答
- traces来自正确解答，可以直接去特化成为新(tell, hint)
- 不需要Telling AI匹配已有tell库——因为目的是增长tell库，不是检索
- 1.0版本可以暂时不考虑和解题侧积累的trace发生关系

**解题侧（解题引导）**：
- 输入是探索中的AI的thinking
- traces可能走对了也可能走错了
- 需要Telling AI匹配已有tell库验证
- 匹配到tell → 取hint填引导树
- 没匹配到 → 孤悬trace存档→启发解答吸收

## 入题侧下一个Pipe的工作（v1修正）

**把traces去特化成Tells，关联Hints，按分类学存储到运行时。**

但存储方式取决于去特化产出的类型：

**普通Tell（去特化到具体概念层）**：
- 存入对应分类目录的tell库（{domain, 段结构模式}交叉对应的AGENTS.md目录）
- 作为内容知识存储——是坐标系中的点

**高Level Tell（去特化到段结构模式层或更高）**：
- 存入高Level概念解释库（338号）
- 作为结构知识存储——是坐标轴上的刻度
- 需要标记case_source（333号）——mathematics/system/none
- 需要判断是340号第一种（可展开的）还是第二种（无法指定展开方向的），处理策略不同
- 如果是新的结构维度（超出当前分类学），可能需要触发分类学修正流程（7条铁律）

这个Pipe需要AI来做——因为以下都是语义判断，不是程序能做的：
- 判断trace去特化到什么程度（Level 1普通Tell / Level 2高Level Tell / Level 3更高抽象）
- 判断去特化的度是否恰好（不过宽不过窄）
- 补全Tell的四个组成成分（branch_signal/branch_type/unexplored_diagnosis/direction_matching）
- 确定分类学位置（普通Tell→{domain, 段结构模式, 具体概念}；高Level Tell→段结构模式层或更高）
- 判断高Level Tell是340号第一种还是第二种
- 关联hint（一个tell可以对应多个hint）
