## 0. 先不搜索：重新思考非特化的全部需求

如果从系统目标倒推，非特化不是“总结得更抽象一点”。它至少同时承担八个契约。

### 0.1 语义契约：它到底保留了什么

一个trace里有大量表面内容：

- 题面对象；
- 具体符号；
- 特定数字；
- 特定定理；
- 某一步漂亮技巧；
- Solver偶然说出的语言。

非特化真正要保留的是：

```text
在什么数学处境中，
哪一种关系结构导致常规路径失效，
哪一种转向能改变问题表征，
改变后会出现什么可验证的进展信号。
```

因此，Tell不是“技巧名”，也不是“题目解法摘要”，而是一个**关系结构 + 操作转向 + 成功信号**。

### 0.2 操作契约：AI拿到后能做什么

抽象概念如果不能转成操作，就是装饰性标签。一个合格Tell至少要回答：

- 下一步看什么对象；
- 把哪些对象重命名、编码、取商、对偶化、极值化、随机化或证书化；
- 哪条常规路线应该降权；
- 该尝试生成什么中间产物；
- 怎样判断这条尝试已经有进展。

这说明344-347号的“AI指导力”不能只作为经验感觉，应拆成可检查字段。

### 0.3 触发契约：什么时候应该想起它

非特化Tell若没有触发条件，就只能靠大模型自由联想。系统需要的是可检索、可匹配、可排除的触发结构：

- 正触发：哪些thinking tell显示“这里值得试”；
- 负触发：哪些thinking tell显示“这里不该试”；
- 边界触发：哪些处境相似但本质不同，必须防止误触发。

这与337号“分类学是排除机制”一致：非特化不是把更多题都纳入同一个概念，而是更清楚地知道**哪些题不属于它**。

### 0.4 退出契约：什么时候应该停

高Level Tell最危险的失败方式是“越想越空”。因此每个Tell需要退出条件：

- 尝试后没有产生新对象；
- 产生的新对象没有降低自由度；
- 证书无法被局部验证；
- 同一转向重复多次仍未改变搜索空间；
- 与负案例边界发生冲突。

退出条件使Tell从“启发口号”变成“受控方法”。

### 0.5 迁移契约：它支持多远的迁移

“非特化”不等于“越远越好”。系统必须区分：

```text
near transfer  : 同领域、同对象、换参数/换包装
middle transfer: 同关系结构、换对象系统
far transfer   : 不同领域、保留深层操作结构
negative case  : 表面相似但不应触发
```

Tell的Level应和迁移距离绑定，而不是单独记一个抽象程度。

### 0.6 反泄漏契约：它不能夹带题解答案

非特化Tell的最大实验风险是“看起来抽象，实际泄漏了关键构造”。因此Tell需要记录：

- 是否包含源题特有数字；
- 是否包含源题特有构造；
- 是否直接给出最终证书；
- 是否把原题的唯一关键中间对象换了个名字写出来；
- 是否给了目标题的答案形态。

反泄漏不是文风问题，是系统科学性问题。

### 0.7 负迁移契约：它什么时候会害AI

一个Tell即使能解A题，也可能误导B题。非特化策略需要主动记录负迁移：

- 表面相似但结构不同；
- 结构相似但操作方向相反；
- 操作相同但成本过高；
- 转向会遮蔽更短证书；
- 提示强度太高导致AI跳过必要验证。

这意味着验证集必须包含“不该触发”的题，而不是只看命中题。

### 0.8 成本契约：它占多少注意力和上下文

系统最终是运行时系统。一个Tell还需要成本字段：

- 提示长度；
- 需要Solver做几步额外分析；
- 是否需要多分支并发；
- 是否容易引发长篇空想；
- 是否适合放入根提示、line提示、critic提示或事后反思提示。

因此，非特化策略的最终产物应接近下面这个对象，而不只是自然语言段落。

```yaml
tell_id:
source_traces:
thinking_capacity:
invariant_relation:
surface_features_removed:
level_band:
transfer_distance_supported:
prompt_shape:
runtime_strategy:
function_type:
positive_triggers:
negative_triggers:
exit_conditions:
operation_steps:
expected_effect:
success_signal:
near_transfer_cases:
middle_transfer_cases:
far_transfer_cases:
negative_cases:
leakage_risk:
prompt_cost:
failure_critics:
refinement_history:
```

## 1. 学术搜索路线

本次搜索不是“找所有相关论文”，而是围绕一个系统问题做理论补强：

```text
如何从具体成功trace中提取非特化策略，
使它既能迁移，又不泄漏答案，
既能触发，又能排除，
既能指导AI，又能被实验细化？
```

搜索范围分成四类：

| 类别 | 搜索目标 | 代表关键词 |
|---|---|---|
| 机器学习中的泛化 | 从例子中抽规则 | explanation-based generalization, anti-unification, version space, inductive logic programming |
| 认知科学中的迁移 | 人如何从例题迁移到新题 | analogical encoding, schema induction, far transfer, self-explanation, subgoal labels |
| 自动推理/验证 | 如何把策略变成可执行方法 | proof planning, critics, rippling, CEGAR, abstract interpretation |
| LLM提示与agent运行时 | 如何把策略注入推理过程 | chain-of-thought, least-to-most, self-consistency, tree of thoughts, ReAct, Reflexion, Self-Refine, analogical prompting |

检索后得到的核心判断是：

```text
非特化策略不是单点问题，而是跨越“抽象、迁移、教学、证明搜索、运行时控制”的复合问题。
```

## 2. 路线A：Explanation-Based Generalization

### 2.1 学术来源

Mitchell, Keller, Kedar-Cabelli 的 Explanation-Based Generalization（EBG）把“从例子中学习”改写为：先解释为什么例子成立，再把解释中不必要的具体条件去掉，得到可操作的泛化规则。

来源：

- Mitchell, Keller, Kedar-Cabelli, *Explanation-Based Generalization: A Unifying View*, Machine Learning, 1986  
  <https://link.springer.com/article/10.1023/A%3A1022691120807>

### 2.2 对非特化的启发

我们现在的非特化常说“剥离表面，保留结构”。EBG给出更强约束：

```text
不要直接泛化trace；
先构造“为什么这条trace成功”的解释图；
再只保留解释图中必要的条件。
```

这可以把非特化流程改成：

```text
trace
  -> success explanation graph
  -> necessary condition extraction
  -> operational generalization
  -> Tell candidate
```

### 2.3 可落地字段

建议给Tell增加四个字段：

```yaml
success_explanation:
  why_this_move_worked:
  which_constraint_it_exploited:
  what_search_space_it_pruned:

necessary_conditions:
  must_hold:
  useful_but_not_necessary:
  source_specific_and_removed:

operational_generalization:
  if_you_see:
  try_to_construct:
  progress_is:
```

### 2.4 对352号的修订

352号说“要审查是否泄漏”。EBG进一步要求：

```text
凡是没有出现在成功解释图里的源题细节，都默认不得进入Tell。
```

这比人工看“像不像泄漏”更强，因为它把反泄漏绑定到解释必要性。

## 3. 路线B：Anti-Unification 与 Least General Generalization

### 3.1 学术来源

Plotkin 和 Reynolds 在1970年前后提出了 least general generalization / anti-unification 思想：给定多个表达式，求一个最不泛化但足以覆盖它们的共同抽象。近年的anti-unification综述也把它视为程序、逻辑、自动推理中的通用泛化工具。

来源：

- Plotkin, *A Note on Inductive Generalization*, 1970  
  <https://homepages.inf.ed.ac.uk/gdp/publications/MI5_note_ind_gen.pdf>
- Reynolds, *Transformational Systems and the Algebraic Structure of Atomic Formulas*, 1970  
  <https://www.cs.cmu.edu/afs/cs/user/jcr/ftp/transysalg.pdf>
- Cerna, Kutsia, Levy, Villaret, *Anti-Unification and Generalization: A Survey*, IJCAI 2023  
  <https://www.ijcai.org/proceedings/2023/0736.pdf>

### 3.2 对非特化的启发

当前系统常从单条trace去特化，这天然不稳定。Anti-unification给出一个强提醒：

```text
真正稳的非特化，不应只问“这条trace去掉什么表面特征”，
还应问“多条成功trace的最小共同结构是什么”。
```

这与345号Tell族不同。Tell族是同一trace的不同Level；anti-unification推动的是：

```text
多trace -> 共同结构 -> 最小充分抽象
```

### 3.3 可落地方案

对每个思维力，不只存单个Tell，而应维护一个小型例簇：

```yaml
positive_trace_cluster:
  - trace_id: ...
    domain:
    surface_objects:
    key_operation:
  - trace_id: ...

lgg_candidate:
  shared_relation_slots:
  variable_slots:
  operation_schema:
  proof_obligation_schema:
```

如果一个Tell只来自单例，它应被标记为：

```yaml
evidence_status: single_trace_hypothesis
```

当有两到三条独立trace支持后，升级为：

```yaml
evidence_status: multi_trace_lgg
```

### 3.4 对实验协议的影响

“至少3道题验证”不够精确。更好的设计是：

```text
2-3个正例用于抽象；
1-2个近迁移例用于确认；
1-2个远迁移例用于压力测试；
2个负例用于排除边界。
```

## 4. 路线C：Version Space 与正负边界学习

### 4.1 学术来源

Mitchell 的 version space / candidate elimination 方法不是维护单一最佳规则，而是维护所有仍与正负例一致的候选规则空间，并用正例和负例逐步收缩边界。

来源：

- Mitchell, *Version Spaces: A Candidate Elimination Approach to Rule Learning*, IJCAI 1977  
  <https://www.ijcai.org/Proceedings/77-1/Papers/048.pdf>

### 4.2 对非特化的启发

我们现在容易问：

```text
这个Tell的最佳Level是多少？
```

Version space会把问题改成：

```text
当前有哪些Tell版本仍然没有被正负案例排除？
最具体边界是什么？
最一般边界是什么？
```

这对“钟形曲线峰值”是重要修正。峰值不是一开始就知道的点，而是被案例逐步夹出来的候选区间。

### 4.3 可落地方案

把Tell族改造成候选空间：

```yaml
tell_family:
  most_specific_boundary:
    - tell_version:
  most_general_boundary:
    - tell_version:
  surviving_candidates:
    - tell_version:
  eliminated_candidates:
    - tell_version:
      eliminated_by_case:
      reason:
```

每次实验后更新边界：

```text
正例成功但Tell未触发 -> 边界需要更一般
负例误触发 -> 边界需要更具体
匹配例触发但无效 -> 操作部分有错，不只是Level问题
```

## 5. 路线D：结构映射、类比编码与Schema Induction

### 5.1 学术来源

Gentner 的 structure-mapping theory强调类比迁移中真正重要的是关系结构，而不是对象属性。Gick & Holyoak 的schema induction研究显示，仅看单例往往迁移弱；比较多个类比案例更容易抽出schema。Gentner, Loewenstein, Thompson 的 analogical encoding进一步说明，对比相似案例可以促进抽象关系的学习。

来源：

- Gentner, *Structure-Mapping: A Theoretical Framework for Analogy*, Cognitive Science, 1983  
  <https://www.sciencedirect.com/science/article/pii/S0364021383800093>
- Gick & Holyoak, *Schema Induction and Analogical Transfer*, Cognitive Psychology, 1983  
  <https://sites.lifesci.ucla.edu/psych-reasoninglab/wp-content/uploads/sites/273/2021/04/Gick_Holyoak1983_SchemaInduction.pdf>
- Gentner, Loewenstein, Thompson, *Learning and Transfer: A General Role for Analogical Encoding*, 2003  
  <https://groups.psych.northwestern.edu/gentner/papers/GentnerLoewensteinThompson03.pdf>

### 5.2 对非特化的启发

我们的“同构之桥”本质上正是结构映射。但学术路线提示一个关键改进：

```text
非特化Tell不应只给一个源例；
应给系统一个“对比案例包”，让抽象从比较中产生。
```

案例包不需要都给Solver，但需要给Tell生成器。

### 5.3 Case Pack模板

```yaml
case_pack:
  source_success_case:
    why_it_is_positive:
  near_positive_case:
    same_structure_different_surface:
  far_positive_case:
    same_deep_relation_different_domain:
  surface_negative_case:
    looks_similar_but_wrong_relation:
  boundary_case:
    partially_matches_but_operation_fails:
```

这比“3道测试题”更有认知价值，因为每个案例承担不同功能。

### 5.4 对Tell生成提示词的改写

旧问法：

```text
请从这条trace中提取一个非特化Tell。
```

新问法：

```text
请比较这些正例、负例和边界例：
1. 找出正例共享的关系结构；
2. 找出负例缺失的关键条件；
3. 找出边界例中导致操作失败的条件；
4. 产出一个只覆盖正例、不覆盖负例的Tell。
```

## 6. 路线E：Far Transfer Taxonomy

### 6.1 学术来源

Barnett & Ceci 对“远迁移”做了系统分类，强调迁移距离不是单一维度，而涉及知识领域、物理/功能/时间/社会情境、提示方式等多维差异。

来源：

- Barnett & Ceci, *When and Where Do We Apply What We Learn? A Taxonomy for Far Transfer*, Psychological Bulletin, 2002  
  <https://pubmed.ncbi.nlm.nih.gov/12081085/>

### 6.2 对非特化的启发

我们过去说near/far transfer时，容易只按“领域远近”判断。但数学中的迁移至少有这些维度：

| 维度 | 近迁移 | 远迁移 |
|---|---|---|
| 数学领域 | 同为组合/数论/几何 | 组合机制迁移到代数或分析 |
| 对象类型 | 集合到集合 | 集合到函数、图、序列、空间 |
| 操作类型 | 同样构造证书 | 从构造证书变为排除证书 |
| 入口表象 | 题面直接暗示 | 题面强烈误导 |
| 提示可见性 | Tell直接点出操作 | Tell只点出方向 |
| 验证形态 | 局部代入验证 | 需要全局不变量或极值证书 |

### 6.3 可落地方案：迁移矩阵

每个Tell验证时维护：

```yaml
transfer_matrix:
  same_domain_same_operation:
  same_domain_different_operation:
  different_domain_same_relation:
  different_domain_different_surface:
  misleading_surface_negative:
  high_prompt_visibility:
  low_prompt_visibility:
```

Tell的有效性不再是一个布尔值，而是：

```text
在什么迁移距离下有效。
```

## 7. 路线F：Scaffolding、Fading 与 Cognitive Load

### 7.1 学术来源

Wood, Bruner, Ross 的scaffolding研究强调，指导不是一次性告诉答案，而是根据学习者状态减少自由度、维持方向、标记关键特征，并在能力形成后逐步撤掉支架。Sweller 的cognitive load理论强调，问题求解中的搜索负担会消耗认知资源，例题和schema能改变学习者如何分类问题。

来源：

- Wood, Bruner, Ross, *The Role of Tutoring in Problem Solving*, Journal of Child Psychology and Psychiatry, 1976  
  <https://pubmed.ncbi.nlm.nih.gov/932126/>
- Sweller, *Cognitive Load During Problem Solving: Effects on Learning*, Cognitive Science, 1988  
  <https://www.sciencedirect.com/science/article/abs/pii/0364021388900237>

### 7.2 对非特化的启发

“提示强度”不该只分匹配Tell/不匹配Tell/纯鼓励。应该有一个fading阶梯：

| 强度 | 形态 | 用途 |
|---|---|---|
| S0 | 不提示 | bare基线 |
| S1 | 方向标签 | 测抽象标签是否足够 |
| S2 | 触发识别 | 告诉它看什么信号 |
| S3 | 操作流程 | 告诉它执行哪些步骤 |
| S4 | 局部证书形态 | 接近答案，通常只用于调试，不用于正式有效性证明 |

正式实验应优先比较：

```text
S0 bare
S1 抽象标签
S2 触发识别
S3 操作流程
纯鼓励对照
不匹配Tell对照
```

### 7.3 对347号的修订

347号“三种提示词形态”可以扩展为：

```text
prompt_shape + scaffold_strength + fading_policy
```

例如：

```yaml
prompt_shape: operation_process
scaffold_strength: S3
fading_policy:
  first_attempt: S2
  if_stalled: S3
  never_expose: S4
```

这能防止系统把“强提示解出来”误判为“非特化Tell有效”。

## 8. 路线G：Self-Explanation 与 Subgoal Labels

### 8.1 学术来源

Chi 等人的self-explanation研究显示，学习者主动解释例题步骤有助于形成更深schema。Catrambone 的subgoal labels研究显示，给例题步骤标出子目标，可以帮助学习者迁移到新问题。

来源：

- Chi, Bassok, Lewis, Reimann, Glaser, *Self-Explanations: How Students Study and Use Examples in Learning to Solve Problems*, Cognitive Science, 1989  
  <https://education.asu.edu/lcl/publications/chi-m-t-h-bassok-m-lewis-reimann-p-glaser-r-1989-self-explanations-how-students>
- Catrambone, subgoal labels / example learning work  
  <https://escholarship.org/content/qt18r7k1ds/qt18r7k1ds_noSplash_21260bb90c0aa8699226af0303ab3884.pdf>

### 8.2 对非特化的启发

很多高Level思维力的问题，不是AI完全不会，而是没有把当前步骤识别成一个子目标。例如：

- “我现在不是在算，而是在找证书”；
- “我现在不是在构造对象，而是在选择规范代表元”；
- “我现在不是在证明不等式，而是在制造对偶不可行证书”；
- “我现在不是在枚举策略，而是在写对抗者不变量”。

因此，Tell可以被设计成**子目标标签生成器**：

```yaml
subgoal_label:
  name:
  when_to_assign:
  what_to_ignore_after_assigning:
  what_artifact_to_produce:
```

### 8.3 对系统的意义

这对非特化尤其重要，因为它允许高Level Tell不直接给出具体技巧，而是重命名Solver当前处境：

```text
“你现在处在一个需要寻找对偶证书的处境。”
```

这类提示比“用某某定理”更不泄漏，但比“寻找结构”更可操作。

## 9. 路线H：Proof Planning、Methods、Critics 与 Rippling

### 9.1 学术来源

Bundy 的proof planning把证明搜索从低层推理步骤提升为高层“方法”选择：每个method有前置条件、效果和适用场景；critic负责在失败时诊断并修补计划。Bundy等关于productive use of failure和rippling的工作也强调，失败不是噪声，而是触发修补和新lemma发现的信号。

来源：

- Bundy, *The Use of Explicit Plans to Guide Inductive Proofs*, AIPS 1996  
  <https://cdn.aaai.org/AIPS/1996/AIPS96-033.pdf>
- Ireland & Bundy, *Productive Use of Failure in Inductive Proof*, Journal of Automated Reasoning, 1996  
  <https://link.springer.com/article/10.1007/BF00244460>
- Bundy et al., *Rippling: A Heuristic for Guiding Inductive Proofs*, Artificial Intelligence, 1993  
  <https://www.sciencedirect.com/science/article/pii/000437029390079Q>

### 9.2 对非特化的启发

这是本次搜索中对系统最直接的路线。Tell不应只是prompt文本，而应当是：

```text
method + critic
```

也就是：

```yaml
method:
  trigger:
  preconditions:
  operation:
  expected_effect:
  success_signal:

critic:
  failure_signal:
  diagnosis:
  patch:
  fallback_tell:
```

### 9.3 对Tell分类学的影响

原来的Tell分类更偏“识别哪种思维力”。Proof planning推动分类学多一个维度：

```text
这个Tell在证明搜索中扮演什么method？
```

可能的method类型：

- 表征转换method；
- 证书构造method；
- 搜索空间剪枝method；
- 失败诊断method；
- lemma生成method；
- 反例压力method；
- 规范化/取商method；
- 对抗者策略method。

### 9.4 最重要修订

每个非特化Tell都应该附带failure critic。否则它只能在成功时被解释，不能在失败时迭代。

```yaml
failure_critic:
  if_ai_did_not_trigger:
    likely_reason:
    refinement:
  if_ai_triggered_but_no_progress:
    likely_reason:
    refinement:
  if_ai_misapplied:
    likely_reason:
    add_negative_trigger:
```

这能把“Tell不好用”拆成可诊断原因，而不是直接废弃。

## 10. 路线I：CEGAR 与抽象细化循环

### 10.1 学术来源

Counterexample-Guided Abstraction Refinement（CEGAR）在模型检测中使用抽象模型快速分析；如果出现反例，再判断反例是否真实，若是伪反例则细化抽象。

来源：

- Clarke, Grumberg, Jha, Lu, Veith, *Counterexample-Guided Abstraction Refinement*, Journal of the ACM, 2003  
  <https://www.cs.cmu.edu/~emc/papers/Papers%20In%20Refereed%20Journals/Counterexample-guided%20abstraction%20refinement.pdf>

### 10.2 对非特化的启发

非特化Tell的失败可以类比成抽象失败：

| Tell现象 | CEGAR类比 | 处理 |
|---|---|---|
| 负例误触发 | 抽象太粗，出现伪匹配 | 加负触发/细化前置条件 |
| 正例不触发 | 抽象太窄 | 放宽触发条件 |
| 触发但无操作进展 | 抽象不可执行 | 增加operation steps |
| 操作进展但证明失败 | method局部有效，全局条件缺失 | 加preconditions |
| 远迁移失败 | 抽象跨域能力不足 | 生成中间Level成员 |

### 10.3 Tell Level Refinement Loop

建议把非特化迭代显式写成：

```text
1. 生成Tell候选
2. 在正例/负例/边界例上测试
3. 把失败归类为 false positive / false negative / no progress / leakage / overcost
4. 根据失败类型细化Tell
5. 保留版本历史，不覆盖旧版本
```

对应字段：

```yaml
refinement_history:
  - version:
    changed_because:
    evidence_case:
    refinement_action:
    expected_effect:
```

## 11. 路线J：Abstract Interpretation

### 11.1 学术来源

Cousot & Cousot 的abstract interpretation把程序语义映射到更抽象的语义域，在精度和可计算性之间做受控折中。它最重要的启发不是“程序分析”，而是“抽象层级可以有形式化偏序和一致性约束”。

来源：

- Cousot & Cousot, *Abstract Interpretation: A Unified Lattice Model for Static Analysis of Programs by Construction or Approximation of Fixpoints*, POPL 1977  
  <https://www.di.ens.fr/~cousot/COUSOTpapers/POPL77.shtml>

### 11.2 对非特化的启发

344-347号把Level描述为模糊连续谱系，这是对的；但工程上需要一个可操作近似。Abstract interpretation提示我们：

```text
可以把Tell Level看成不同抽象域，而不是一个线性刻度。
```

例如同一trace可以投影到多个抽象域：

| 抽象域 | 保留什么 | 丢弃什么 |
|---|---|---|
| 对象域 | 数学对象类型 | 具体参数 |
| 关系域 | 对象间关系 | 对象名字 |
| 操作域 | 可执行转向 | 证明文本 |
| 证书域 | 成功验证形态 | 构造细节 |
| 失败域 | 原路线为什么失败 | 成功路线 |

### 11.3 具体影响

“Level过高/过低”有时是假问题。真正的问题可能是：

```text
抽象到了错误的域。
```

例如一个Tell丢掉了对象细节，却没有保留失败机制；它不是Level太高，而是抽象投影错了。

因此Tell生成器应同时产出：

```yaml
abstraction_domain:
  object_level:
  relation_level:
  operation_level:
  certificate_level:
  failure_level:
```

## 12. 路线K：Inductive Logic Programming 与谓词发明

### 12.1 学术来源

Inductive Logic Programming（ILP）从正负例和背景知识中学习逻辑规则，并强调背景知识、关系表示和谓词发明。Muggleton的工作是代表路线之一。

来源：

- Muggleton, *Inductive Logic Programming*, New Generation Computing, 1991  
  <https://link.springer.com/article/10.1007/BF03037089>

### 12.2 对非特化的启发

数学Tell往往不是简单属性规则，而是关系规则。ILP提醒系统：

```text
Tell生成不只是删掉细节，还可能需要发明一个中间谓词。
```

这与353号的C8“语义不变量命名”高度相关。

例子：

```text
原trace中没有显式概念“规范代表元”，
但多个步骤共同显示它在选择等价类代表。
```

这时非特化产物不应只是：

```text
考虑对称性。
```

而应发明可用谓词：

```text
存在一个等价关系，使每个候选对象都可压缩到一个规范代表元；先在代表元上证明，再提升回原对象。
```

### 12.3 可落地字段

```yaml
invented_predicates:
  - name:
    definition:
    evidence_steps:
    why_needed:
    how_to_trigger:
```

## 13. 路线L：Case-Based Reasoning

### 13.1 学术来源

Case-Based Reasoning（CBR）强调通过记忆旧案例、检索相似案例、适配旧解法、保留新经验来解决新问题。Kolodner的case-based learning是代表性来源。

来源：

- Kolodner, *Case-Based Learning*, Springer, 1993  
  <https://link.springer.com/book/10.1007/978-1-4615-3228-6>

### 13.2 对非特化的启发

我们的Tell库不是传统规则库，也不是单纯向量库，更像：

```text
结构化案例库 + 适配规则库 + 失败边界库。
```

CBR的关键问题是indexing：旧案例如何被正确召回。对应到系统：

```text
Tell的触发字段就是案例索引。
```

### 13.3 可落地方案

每个Tell都应有两类索引：

```yaml
retrieval_index:
  surface_terms:
  structural_terms:
  failure_terms:
  operation_terms:
  certificate_terms:

adaptation_notes:
  what_can_change:
  what_must_not_change:
  common_bad_adaptations:
```

这能帮助系统区分：

- “检索到了相关案例”；
- “知道该如何迁移这个案例”。

## 14. 路线M：LLM Prompting 与Agent运行时策略

### 14.1 学术来源

LLM路线本身不解决“Tell内容应该是什么”，但能解决“Tell如何在运行时发挥作用”。本次搜索覆盖了以下代表方法：

| 方法 | 来源 | 对Tell runtime的启发 |
|---|---|---|
| Chain-of-Thought | Wei et al., 2022, <https://arxiv.org/abs/2201.11903> | 让Solver显式展开中间推理 |
| Least-to-Most | Zhou et al., 2022, <https://arxiv.org/abs/2205.10625> | 把高Level Tell拆成子问题序列 |
| Self-Consistency | Wang et al., 2022, <https://arxiv.org/abs/2203.11171> | 同一Tell多路线采样，看是否收敛 |
| Tree of Thoughts | Yao et al., 2023, <https://arxiv.org/abs/2305.10601> | Tell可作为分支生成/评估策略 |
| ReAct | Yao et al., 2022, <https://arxiv.org/abs/2210.03629> | 把推理和工具/观察交替组织 |
| Reflexion | Shinn et al., 2023, <https://arxiv.org/abs/2303.11366> | 失败后生成语言反思，更新后续尝试 |
| Self-Refine | Madaan et al., 2023, <https://arxiv.org/abs/2303.17651> | 生成-反馈-修订循环 |
| Analogical Prompting | Yasunaga et al., 2023, <https://arxiv.org/abs/2310.01714> | 让模型自己生成类比示例再解题 |

### 14.2 关键区分

必须把两件事分开：

```text
Tell content  = 要迁移的数学思维内容
Tell runtime  = 如何把内容注入Solver过程
```

同一个Tell content可以有多种runtime：

```yaml
runtime_strategy:
  root_hint:
  line_branch_hint:
  critic_after_failure:
  multi_sample_self_consistency:
  tree_of_thought_branch:
  least_to_most_decomposition:
  analogical_case_generation:
```

### 14.3 对系统的影响

一次Tell测试失败，不一定说明Tell内容错，可能是runtime错：

- 根提示太早，AI忽略；
- 中途提示太晚，路线已固化；
- 提示太抽象，需要S2/S3支架；
- 单路采样失败，但多路自洽能成功；
- 需要先让AI生成类比例子，再执行Tell。

因此失败归因矩阵必须加入：

```yaml
runtime_failure:
  injection_timing:
  prompt_strength:
  branching_policy:
  sampling_policy:
  reflection_policy:
```

## 15. 汇总：非特化策略的新版九步管线

结合上面学术路线，建议把非特化Pipe改成九步：

```text
Step 1. trace规范化
  把Solver thinking切成对象、操作、失败、证书、转向、验证信号。

Step 2. 成功解释图
  解释为什么关键转向有效，哪些条件是必要条件。

Step 3. 多例结构对齐
  用多个正例做关系结构对齐，求最小共同抽象。

Step 4. 对比边界构造
  加入近正例、远正例、表面负例、边界例。

Step 5. Tell候选族生成
  生成多个抽象域、多个Level、多个prompt_shape的候选。

Step 6. method + critic结构化
  每个Tell都写成可执行method，并附带失败critic。

Step 7. runtime策略选择
  决定它适合根提示、line提示、失败后critic、多采样、ToT分支还是least-to-most。

Step 8. 迁移矩阵验证
  在near/middle/far/negative案例上测触发、有效性、泄漏、成本。

Step 9. CEGAR式版本细化
  根据false positive/false negative/no progress/leakage/overcost更新Tell版本。
```

```text
同样高Level的Tell，
```

所以“高Level必然没指导力”是错的；真正问题是：

```text
高Level Tell有没有被操作化、边界化、运行时化。
```

## 18. 优先级排序

如果按对系统的性价比排序，本轮最应该吸收的不是全部论文，而是四个核心机制。

### P0：Proof Planning + Critics

原因：最直接改造Tell结构，使Tell从“提示文本”变成“方法对象”。这是系统工程收益最高的一条。

落地：

```text
每个Tell必须有method字段和critic字段。
```

### P0：EBG + Anti-Unification

原因：解决“从trace抽什么”的核心问题。EBG处理单trace解释必要性，anti-unification处理多trace共同结构。

落地：

```text
先解释再泛化；多例对齐后再确定候选Level。
```

### P0：Case Pack + Version Space

原因：解决边界问题，防止Tell无限泛化或误触发。

落地：

```text
用正例和负例维护Tell候选空间，而不是只找一个峰值版本。
```

### P1：Scaffolding + Subgoal Labels

原因：解决高Level Tell怎样仍然可操作。

落地：

```text
同一Tell提供S1/S2/S3多个提示强度版本，并优先采用子目标标签。
```

### P1：CEGAR式迭代

原因：解决实验失败后如何细化，而不是每次从头解释。

落地：

```text
所有失败进入false positive/false negative/no progress/leakage/overcost分类，并驱动版本更新。
```

### P2：LLM Runtime策略

原因：这是增强器，不是本体。先把Tell内容做扎实，再考虑多采样、ToT、Reflexion等运行时。

## 22. 本文最终判断

非特化策略的下一次跃迁，不是“找到更漂亮的抽象话术”，而是把Tell变成一个可学习、可验证、可版本化的策略对象。

最小落地版本应包含：

```text
Tell = invariant relation
     + method
     + critic
     + trigger boundary
     + exit condition
     + case pack
     + runtime strategy
     + refinement history
```

这会直接改变系统后续研发方式：

1. 非特化Pipe不再只生成一句提示词，而生成TellV2对象。
2. Tell验证不再只问“有没有解出来”，而问“在什么迁移距离、提示强度、运行时策略下有效”。
3. Tell失败不再是废弃，而进入CEGAR式细化。
4. 高Level思维力不再因抽象而天然弱，只要被写成method + critic + subgoal label，它仍然可以有强指导力。
5. 分类学不只是概念树，而是一个带正负边界、失败critic和迁移矩阵的策略空间。

这条路比“继续找更多思维力”更底层：它决定了任何新思维力被发现之后，系统是否真的能把它学会、迁移、验证并长期积累。
