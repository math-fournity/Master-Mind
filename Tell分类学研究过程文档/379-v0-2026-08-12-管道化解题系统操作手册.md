## 1. 系统概览

### 1.1 架构

```
ArangoDB (2.4M题) → Feeder → Redis pending队列
                                    ↓
                              Runner (30并发) → 启动devin cli
                                    ↓
                              Redis running队列
                                    ↓
                              Collector (眼见为实判定)
                                    ↓
                         Redis completed/failed队列
                                    ↓
                              Reporter (统计+告警)
```

### 1.2 服务清单

| 服务 | 脚本 | 职责 |
|---|---|---|
| Feeder | `feeder.py` | 从ArangoDB选题入Redis pending队列 |
| Runner | `runner.py` | 从Redis取题启动devin cli（纯启动） |
| Collector | `collector.py` | 扫描running队列，眼见为实判定终态 |
| Reporter | `reporter.py` | 定时统计报告+告警 |
| Retry | `retry_infrastructure.py` | 基础设施失败自动重试 |

### 1.3 查询/验证脚本清单

| 脚本 | 用途 |
|---|---|
| `pipe_control.py` | 启动/停止/状态管理 |
| `query_progress.py` | 运行进度查询 |
| `query_failures.py` | 失败分类统计 |
| `audit_trace.py` | 双向追溯验证 |
| `verify_completeness.py` | 数据完备性验证 |
| `verify_run_integrity.py` | 运行完整性验证（无工具调用+真实proof） |
| `check_answer_leak.py` | 答案泄漏检查 |
| `extract_solve_time.py` | 精确解题时间提取 |
| `build_profile.py` | GLM-5.2能力边界Profile构建 |

## 2. 启动流程

### 2.1 前置检查

```bash
# 1. 检查Redis容器
docker ps | grep redis

# 2. 检查ArangoDB
curl -s http://localhost:8529/_api/version

# 3. 检查D盘空间
df -h /data

# 4. 检查tmux
tmux list-sessions
```

### 2.2 启动30并发解题

```bash
cd ~/master-mind-glm5.2-worktree

# 一键启动（清空Redis + 启动所有服务）
.venv/bin/python3 xishujuzhen/solver_harness/pipe/pipe_control.py start \
  --concurrency 30 \
  --tier 1 \
  --batch-size 100 \
  --clear

# 或分步启动
.venv/bin/python3 xishujuzhen/solver_harness/pipe/pipe_control.py clear
.venv/bin/python3 xishujuzhen/solver_harness/pipe/feeder.py --tier 1 --batch-size 100 --limit 100
tmux new-session -d -s pipe-runner ".venv/bin/python3 xishujuzhen/solver_harness/pipe/runner.py --concurrency 30"
tmux new-session -d -s pipe-collector ".venv/bin/python3 xishujuzhen/solver_harness/pipe/collector.py --poll-interval 10 --timeout 1800"
tmux new-session -d -s pipe-reporter ".venv/bin/python3 xishujuzhen/solver_harness/pipe/reporter.py --interval 60"
```

### 2.3 启动重试服务

```bash
# 基础设施失败自动重试（循环模式，每60秒扫描一次）
tmux new-session -d -s pipe-retry ".venv/bin/python3 xishujuzhen/solver_harness/pipe/retry_infrastructure.py --max-retries 3 --interval 60"
```

## 4. 停止流程

### 4.1 优雅停止（推荐）

```bash
# 优雅停止所有服务——发送SIGINT，等待10秒
.venv/bin/python3 xishujuzhen/solver_harness/pipe/pipe_control.py stop

# 优雅停止但保留harness session（默认行为，显式声明）
.venv/bin/python3 xishujuzhen/solver_harness/pipe/pipe_control.py stop --keep-harness

# 设置更长的等待超时
.venv/bin/python3 xishujuzhen/solver_harness/pipe/pipe_control.py stop --timeout 30
```

**优雅停止的行为**：
- 发送SIGINT给服务进程
- 服务完成当前操作后退出（不kill harness session）
- harness-xxx session继续独立运行
- Collector重启后会继续处理running队列中的attempt

### 4.2 强制停止

```bash
# 强制停止——直接kill-session
.venv/bin/python3 xishujuzhen/solver_harness/pipe/pipe_control.py stop --force

# 停止同时kill所有harness session
.venv/bin/python3 xishujuzhen/solver_harness/pipe/pipe_control.py stop --kill-harness
```

### 4.3 手动停止单个服务

```bash
# 停止单个服务（优雅）
tmux send-keys -t pipe-collector C-c ""

# 等待退出后确认
tmux has-session -t pipe-collector 2>/dev/null && echo "还在运行" || echo "已退出"
```

### 4.4 代码热替换

```bash
# 1. 优雅停止要替换的服务（如Collector）
tmux send-keys -t pipe-collector C-c ""
# 等待退出
sleep 5
tmux has-session -t pipe-collector 2>/dev/null && tmux kill-session -t pipe-collector

# 2. 替换代码
# ... 编辑collector.py ...

# 3. 重启服务
cd ~/master-mind-glm5.2-worktree
tmux new-session -d -s pipe-collector ".venv/bin/python3 xishujuzhen/solver_harness/pipe/collector.py --poll-interval 10 --timeout 1800"

# 4. Collector从Redis running队列继续处理——harness session一直在运行
```

## 5. 断电恢复流程

### 5.1 恢复检查

```bash
# 检查（不修改）——看有多少僵尸记录
.venv/bin/python3 xishujuzhen/solver_harness/pipe/recover_from_crash.py --dry-run

# 或通过pipe_control
.venv/bin/python3 xishujuzhen/solver_harness/pipe/pipe_control.py recover --dry-run
```

### 5.2 执行恢复

```bash
# 执行恢复
.venv/bin/python3 xishujuzhen/solver_harness/pipe/recover_from_crash.py

# 恢复后自动重启所有服务
.venv/bin/python3 xishujuzhen/solver_harness/pipe/recover_from_crash.py --auto-restart
```

### 5.3 恢复做了什么

1. **running队列清理**：session不存在的记录标记为`crash_recovered`，移到failed队列，problem状态恢复为pending（可重新入队）
2. **孤儿session清理**：tmux中存在但Redis running队列中没有对应记录的harness session被kill
3. **ArangoDB修复**：status=running但实际已结束的attempt被更新为正确状态

### 5.4 恢复后验证

```bash
# 检查Redis状态
.venv/bin/python3 xishujuzhen/solver_harness/pipe/query_progress.py

# 检查数据完整性
.venv/bin/python3 xishujuzhen/solver_harness/pipe/verify_completeness.py --all

# 检查tmux session
tmux list-sessions
```

## 6. 故障处理

### 6.1 Redis连接失败

```bash
# 检查Redis容器
docker ps | grep redis
# 重启Redis
docker restart redis-pipe
```

### 6.2 ArangoDB连接失败

```bash
# 检查ArangoDB
curl -s http://localhost:8529/_api/version
# 重启ArangoDB（根据安装方式）
```

### 6.3 大量failed_connection

```bash
# 查看连接错误详情
.venv/bin/python3 xishujuzhen/solver_harness/pipe/query_failures.py --verdict failed_connection --limit 50

# 降低并发数
.venv/bin/python3 xishujuzhen/solver_harness/pipe/pipe_control.py stop
.venv/bin/python3 xishujuzhen/solver_harness/pipe/pipe_control.py start --concurrency 15 --tier 1

# 重试基础设施失败
.venv/bin/python3 xishujuzhen/solver_harness/pipe/retry_infrastructure.py --once
```

### 6.4 export不完整

```bash
# 检查哪些运行没有conversation.json
for d in /data/math-agent-glm5.2-tmux-agents-trajectory/p*/; do
    if [ ! -f "$d/exports/conversation.json" ]; then
        echo "missing: $(basename $d)"
    fi
done
```

## 6. 日志规范

### 7.1 日志配置

- **目录**: `/data/math-agent-glm5.2-tmux-agents-trajectory/_pipe/logs/`
- **单文件**: 1MB
- **总量限制**: 10GB
- **滚动**: 自动覆盖最老文件

### 7.2 日志文件

| 文件 | 内容 |
|---|---|
| `pipe.log` | 统一日志（所有模块） |
| `runner.log` | Runner服务 |
| `collector.log` | Collector服务 |
| `feeder.log` | Feeder服务 |
| `reporter.log` | Reporter服务 |
| `retry.log` | 重试服务 |

### 7.3 日志级别

| 级别 | 场景 |
|---|---|
| ERROR | 连接失败、DB写入失败、launch失败 |
| WARNING | 答案泄漏、工具调用、pane空白 |
| INFO | 终态判定、统计、启动/停止 |
| DEBUG | 详细分析、标记匹配、时间提取 |
