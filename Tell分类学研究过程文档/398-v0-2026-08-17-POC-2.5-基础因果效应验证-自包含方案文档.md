## §0 自包含POC方案文档的设计规范（本节是所有POC方案文档的共用规范）

### 0.1 设计目标

一份POC方案文档要让未来20万上下文的AI**只加载这份文档+它索引的少数核心文档**，就能完整了解做好这次POC所需的所有背景知识，不需要用户另外指点应该读什么。

| 节 | 内容 | 作用 |

### 0.3 "自包含"的含义

"自包含"不是把所有背景知识复制进文档——那样文档会膨胀到无法加载。"自包含"是指：

1. **文档本身包含这个POC执行所需的全部操作信息**——输入/方法/输出/通过标准/执行约束
2. **文档明确列出需要全文加载的背景文档清单**——每份说明加载理由（这个POC为什么需要这份文档的内容）
3. **未来AI加载这份POC方案后，按照§8清单去全文加载被索引的文档**——不需要用户另外指点

### 0.4 被索引文档的精挑细选原则

每份POC方案文档的§8清单应该精挑细选——只列这个POC真正需要的背景文档，通常3-7份。如果索引太多，未来AI加载不完。

**挑选标准**：
- **必须加载**：这个POC不加载这份文档就无法正确执行（如题包/TellCore定义/通过标准来源）
- **建议加载**：这个POC加载这份文档能更好理解为什么这么做（如理论背景/原设计文档）
- **不列**：这个POC不需要这份文档的内容（如其他POC的方案文档）

{编号}-v0-{日期}-POC-{POC编号}-{POC名称}-自包含方案文档.md

## §2 理论背景——为什么需要这个POC

### 2.1 396号的核心论断

396号（非特化理论综合）建立了以下理论框架：

1. **Tell是识别端的（分层存在），Hint是注入端的（非特化程度）**——钟形曲线绑在Hint上
2. **非特化策略从正确的答题过程中分层提取有价值的解题思维，将其中因果充分的认知动作提炼成TellCore**
3. **Hint有效 ≠ 解题成功**——有效性是"trigger→认知动作→进展信号→成功"这条因果链出现，且在控制混杂后仍成立

POC-2.5验证的是第3点的**最基础层次**——Hint是否比bare更好。这是因果链的最后一步（"成功"）的最简单验证。如果连这一步都不成立，因果链的其他环节（trigger/认知动作/进展信号）都没有意义。

### 2.2 397号审视发现的缺失

397号§3.8指出：373号的9个POC直接从POC-2（可选择）开始，没有先做最简单的基础验证。Mid-Hint对照实验已经显示基础效应可能不存在（vein够时Hint无因果作用），但373号没有覆盖这个风险。

POC-2.5就是填补这个缺失——在POC-2之后、POC-3之前，先做基础因果效应验证。

### 2.3 与Mid-Hint实验的关系

Mid-Hint实验（387号dev-docs目录§十二~十四）做了4个run：
- 00995 MH（有hint）：SUCCESS（13分钟）
- 00995 CONTROL（无hint）：SUCCESS（8分钟）——**反而更快**
- 00128 MH（有hint）：SUCCESS（4分钟）
- 00128 CONTROL（无hint）：SUCCESS（11分钟）

**核心发现**：vein够时Hint无因果作用——4个run都SUCCESS，Hint只改变方法不改变成败。

POC-2.5要验证的是：**在POC-0/1产出的题包和TellCore上，这个"vein够时Hint无因果作用"的问题是否重现？**

如果重现——需要分析是vein够还是Hint不够还是题目选错了。
如果不重现（Hint确实比bare更好）——继续做POC-3.5~8。

### 2.4 "vein够"问题的特殊性

Mid-Hint实验的"vein够"问题有一个特殊性——Mid-Hint实验给AI的不只是Hint，还有**脉络（vein）**。脉络中已经包含了局部发现（如"D必为偶"），这些局部发现可能本身就足以引导AI完成证明。

POC-2.5要区分两种情况：
1. **bare vs bare+vein+Hint**——如果vein+Hint比bare好，但vein本身就够了（CONTROL也成功），那Hint没有因果作用
2. **bare vs bare+Hint（无vein）**——如果只给Hint不给vein，Hint是否比bare好？

**POC-2.5建议同时测试这两种对照**，以区分"vein的贡献"和"Hint的贡献"。

## §4 输入——这个POC需要什么

### 4.1 题包

从382号CasePack v0的22道题中取**正迁移题4道**。

正迁移题的标准（来自382号§1.2和373号§14.8）：
- 真实bare失败（有完整bare失败记录）
- 目标Tell（局部-全局表示切换）是低搜索成本主路
- 过程可观察（thinking中能看见表示切换的过程信号）
- 解答可核验（有verified solution）
- 泄漏安全（Tell只给策略不给答案）

### 4.2 TellCore

383号确定的TellCore v0候选C（局部-全局表示切换），7字段最小充分集：
1. invariant_claim
2. trigger_boundary
3. negative_boundary
4. parameter_slots
5. internal_policy
6. progress_model
7. termination

### 4.3 HintInstance

由HintRenderer把TellCore v0渲染成HintInstance。POC-2.5先用**一个中等非特化程度的HintInstance**（如Hint-L3"当问题在自然表示下陷入困境时，切换到局部表示Z/pZ"——一句话指示形态）。

**注意**：POC-2.5不测试不同非特化程度的差异（那是POC-3.5的工作）。POC-2.5只用一个HintInstance，验证基础因果效应。

### 4.4 Solver模型

主模型：GLM-5.2 High（通过solver_harness启动）

### 4.5 脉络（vein）

从source trace题（382号CasePack v0的4道source trace题：1631/1843/1709/1962）提取脉络。

**重要**：POC-2.5需要区分"vein的贡献"和"Hint的贡献"，所以要准备两种输入：
- bare（只有题目）
- bare+vein+Hint（题目+脉络+HintInstance）
- bare+Hint（题目+HintInstance，无脉络）——可选，如果前两种对照不够清晰

## §5 方法——这个POC怎么做

### 5.1 实验设计

对4道正迁移题，每道做3-4组对照：

| 条件 | 给AI什么 | 验证什么 |
|---|---|---|
| **bare** | 只有题目 | 基线能力（应失败——正迁移题的定义就是bare失败） |
| **bare+vein** | 题目+脉络（无Hint） | vein本身的贡献（Mid-Hint实验中CONTROL组就是这种） |
| **bare+vein+Hint** | 题目+脉络+HintInstance | vein+Hint的组合效果（Mid-Hint实验中MH组就是这种） |
| **bare+Hint**（可选） | 题目+HintInstance（无vein） | Hint本身的贡献（排除vein的影响） |

### 5.2 对照矩阵

对4道正迁移题×3-4个条件=12-16个run。

每个run记录：
- 解题成功/失败（二元指标）
- 用时
- 证明方法（是否用了局部-全局切换）
- thinking中是否出现目标认知动作（引入新表示/比较原表示与新表示/找到不变量/产生可验证lemma）

### 5.3 判定逻辑

**场景1：bare失败 + bare+vein+Hint成功**
- 这是Mid-Hint实验的结果——但要看bare+vein是否也成功
- 如果bare+vein也成功——**vein够，Hint无因果作用**（Mid-Hint问题重现）
- 如果bare+vein失败——**Hint有因果作用**（vein不够，Hint补上了）

**场景2：bare失败 + bare+vein失败 + bare+vein+Hint成功**
- **Hint有因果作用**——vein不够，Hint补上了
- 这是最理想的结果——继续做POC-3.5~8

**场景3：bare失败 + bare+vein失败 + bare+vein+Hint失败**
- **Hint无效**——连vein+Hint都不够
- 需要分析：是题目太难、Hint不够强、还是TellCore本身有问题
- 可能需要回到POC-1重新审视TellCore

**场景4：bare成功**
- 这道题不是真正的bare失败——正迁移题的准入条件不满足
- 需要换题或确认bare失败记录的可靠性

### 5.4 操作步骤

1. 从382号CasePack v0取4道正迁移题
2. 从383号TellCore v0用HintRenderer生成1个HintInstance（中等非特化程度，一句话指示形态）
3. 从382号4道source trace题提取脉络
4. 对每道正迁移题，通过solver_harness启动4个run（bare/bare+vein/bare+vein+Hint/bare+Hint可选）
5. 记录每个run的解题成功/失败/用时/证明方法/thinking过程信号
6. 按§5.3的判定逻辑分析结果
7. 产出EvidenceRecord

### 5.5 与Mid-Hint实验的关键差异

Mid-Hint实验（387号dev-docs目录）和POC-2.5的对照：

| | Mid-Hint实验 | POC-2.5 |
|---|---|---|
| 题目 | 00995（mod_p_grouping）+ 00128（elevator） | 382号CasePack v0的4道正迁移题 |
| TellCore | 局部-全局切换（人工设计的Hint） | 383号TellCore v0候选C（7字段最小充分集） |
| HintInstance | "switch to local representation" | HintRenderer渲染的中等非特化程度Hint |
| 对照 | MH（vein+Hint）vs CONTROL（vein） | bare / bare+vein / bare+vein+Hint / bare+Hint |
| bare对照 | ❌没有bare对照（只有vein对照） | ✅有bare对照 |
| 关键差异 | Mid-Hint没有bare对照，无法区分"vein够"和"题目本身不难" | POC-2.5有bare对照，可以确认题目确实bare失败 |

**POC-2.5相对Mid-Hint实验的关键改进**：增加了bare对照组。Mid-Hint实验没有bare对照——它只比了MH（vein+Hint）vs CONTROL（vein），没有比bare。所以Mid-Hint实验无法区分"vein够所以Hint无用"和"题目本身不难所以bare也能做"。POC-2.5的bare对照可以确认题目确实bare失败，然后才能判定vein+Hint的效果。

## §7 通过标准

### 7.1 通过标准（继续做POC-3.5~8的条件）

**POC-2.5通过，需要满足**：

1. **4道正迁移题的bare全部失败**——确认题目确实bare失败（如果不是，正迁移题准入条件不满足）
2. **bare+vein+Hint的成功率 > bare的成功率**——vein+Hint比bare更好（最基本的因果效应）
3. **至少2道题出现场景2**（bare失败+vein失败+vein+Hint成功）——vein不够时Hint补上了，这是Hint有因果作用的最强证据

### 7.2 不通过的处理

**如果条件2不满足（bare+vein+Hint不比bare更好）**：

停下来分析原因：
- **如果是场景1（vein够）**——bare+vein也成功，说明vein本身就够了。需要：要么找vein不够的题，要么承认对这类题Hint没有增量价值
- **如果是场景3（Hint无效）**——bare+vein也失败，vein+Hint也失败。需要：回到POC-1审视TellCore是否正确，或审视HintInstance的渲染是否合适
- **如果是场景4（bare成功）**——题目不是真正的bare失败。需要：换题或确认bare失败记录的可靠性

### 7.3 模糊结果的处理

**如果结果是ambiguous（有些题Hint有效有些无效）**：

- 记录哪些题有效哪些无效
- 分析差异——是题目类型不同、还是vein质量不同、还是Hint对某些题不够强
- 模糊结果不阻塞POC-3.5，但要在EvidenceRecord中明确记录哪些题上Hint有效，后续POC只在这些题上做

### 7.4 通过后不意味着Hint"有效"——只意味着"有基础因果效应"

**重要**：POC-2.5通过只说明Hint比bare更好——这是最基础的因果效应。但这不意味着Hint"有效"——因为：
- 可能是提示强度效应（任何提示都能让AI更好）——需要POC-6可归责来排除
- 可能是信息泄漏（Hint包含了题目特定信息）——需要在§4.2的泄漏安全检查中排除
- 可能是vein的功劳不是Hint的功劳——已经通过bare+vein对照部分排除

POC-2.5通过后，继续做POC-3.5（Hint非特化程度验证）和POC-6（可归责）来进一步验证。

## §9 执行约束

### 9.1 Solver启动

数学Solver必须通过`xishujuzhen/solver_harness/solver_harness.py launch`启动，不能手动tmux、nohup或绕过harness。

### 9.2 ArangoDB

启动任何连接ArangoDB的脚本前，必须确认`echo $ARANGO_DB`输出`xishujuzhen_math_glm52`。

### 9.3 Git

- Git add必须显式路径，不能`git add -A`或`git add .`
- 产物文件（poc_2_5_result.yaml / poc_2_5_analysis.md / 每个run的导出）必须commit

### 9.4 POC运行记录

POC运行记录必须保留thinking、trajectory、proof或TUI导出。通过solver_harness自动保存。

### 9.5 证据分层

POC结论必须写成证据分层——不把"基础因果效应存在"升级成"Hint有效"。基础因果效应只是最基础的验证，Hint是否真正"有效"还需要POC-3.5（非特化程度验证）和POC-6（可归责）来进一步验证。

### 9.6 失败不是废结果

如果POC-2.5不通过（Hint无基础因果效应），这不是废结果——这是重要发现。要么揭示了vein够的问题，要么揭示了TellCore或HintInstance的问题。不通过的结果必须完整记录，并触发对POC-1 TellCore或POC-0题包的修订。

## §10 与其他POC的关系

### 10.1 前置关系

```
POC-0（题包冻结）→ POC-1（TellCore确定）→ POC-2（selector验证）→ ★ POC-2.5（基础因果效应）★
```

POC-2.5依赖POC-0的题包和POC-1的TellCore。如果POC-2已完成，POC-2.5可以用selector自动选择目标Tell；如果POC-2未完成，可以人工指定用目标TellCore。

### 10.2 后续关系

```
★ POC-2.5（基础因果效应）★ → POC-3.5（Hint非特化程度验证）→ POC-3（可执行）→ POC-4（可终止）→ POC-6（可归责）
```

POC-2.5通过后才能做POC-3.5——如果基础因果效应都不存在，测试不同非特化程度的差异没有意义。

POC-2.5通过后才能做POC-6——如果基础因果效应都不存在，干预矩阵（bare/通用鼓励/等长空流程/错配Tell/method only/full Tell）没有意义。

### 10.3 如果POC-2.5不通过

- **不通过不阻塞POC-9（识别端验证）**——识别端从失败trace读分叉，不依赖Hint是否有效
- **不通过阻塞POC-3.5/3/4/6/7/8**——这些都是注入端或学习端的POC，依赖Hint有基础因果效应
- **不通过触发对POC-1 TellCore的修订**——如果Hint无效，可能是TellCore不正确
- **不通过触发对POC-0题包的修订**——如果Hint无效，可能是题目选错了（vein够或题目本身不难）
