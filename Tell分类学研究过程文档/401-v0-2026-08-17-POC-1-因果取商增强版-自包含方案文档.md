## §0 自包含POC方案文档的设计规范（本节是所有POC方案文档的共用规范）

### 0.1 设计目标

一份POC方案文档要让未来20万上下文的AI**只加载这份文档+它索引的少数核心文档**，就能完整了解做好这次POC所需的所有背景知识，不需要用户另外指点应该读什么。

### 0.3 "自包含"的含义

"自包含"不是把所有背景知识复制进文档——那样文档会膨胀到无法加载。"自包含"是指：

1. **文档本身包含这个POC执行所需的全部操作信息**——输入/方法/输出/通过标准/执行约束
2. **文档明确列出需要全文加载的背景文档清单**——每份说明加载理由（这个POC为什么需要这份文档的内容）
3. **未来AI加载这份POC方案后，按照§8清单去全文加载被索引的文档**——不需要用户另外指点

### 0.4 被索引文档的精挑细选原则

每份POC方案文档的§8清单应该精挑细选——只列这个POC真正需要的背景文档，通常3-7份。如果索引太多，未来AI加载不完。

**挑选标准**：
- **必须加载**：这个POC不加载这份文档就无法正确执行（如题包/TellCore定义/通过标准来源）
- **建议加载**：这个POC加载这份文档能更好理解为什么这么做（如理论背景/原设计文档）
- **不列**：这个POC不需要这份文档的内容（如其他POC的方案文档）

{编号}-v0-{日期}-POC-{POC编号}-{POC名称}-自包含方案文档.md
```

## §2 理论背景——为什么需要这个POC

### 2.1 396号§4.2：非特化是因果充分的取商

396号§4.2建立了POC-1的核心理论框架：

> 非特化不是把一段trace"总结得更抽象"，而是对解题处境做一次"因果充分的取商"，再把所得等价类编译成可识别、可选择、可实例化、可执行、可终止、可组合、可归责、可验证、可持续学习的认知技能。

"取商"——数学中的取商，是把若干表面不同但在目标关系下等价的对象视为同一个对象。对应到非特化：
- 变量重命名不应产生新Tell
- 数字替换不应产生新Tell
- 对象从集合换成图，如果角色关系和认知动作没有改变，可能仍属于同一Tell
- 题面很像但关键失败机制不同，则不能被合并

**POC-1的因果取商**就是把383号确定的TellCore v0候选C（局部-全局表示切换）做这层"取商"——把4道source trace题（1631/1843/1709/1962）的表面特征压掉，只保留能解释成功转向的关系结构、触发条件、动作策略和证据要求。

**Level由允许忽略哪些变换共同决定**——这比"抽象感更高"更可操作。POC-0.5的变形关系声明（400号）已经显式声明了允许变换和禁止变换，POC-1增强版的提取完备性检查要用这个声明来验证提取是否完备。

### 2.2 397号§3.3：提取过程本身验证的缺失

397号§3.3指出了373号POC-1设计中的一个盲点：

> 373号假设TellCore的提取是正确的，只验证TellCore的字段结构（"删掉某个字段后是否失去迁移解释"），没有验证提取过程本身（"从正确的答题过程中提取的解题思维是否完备、是否准确、是否因果充分"）。

396号§4.7进一步明确了为什么这是一个问题——GPT框架里有两个不同的"从trace中读"：
1. **识别端**（000号tell端）：从**失败trace**中读出AI没走的分叉——服务于"在哪个位置开新分支"
2. **学习端**（371/372号TellCore提取）：从**成功trace**中提取有因果贡献的认知技能，用失败trace做对照——服务于"把什么认知技能存入Tell库"

383号的POC-1只做了学习端的字段结构验证（"删掉某个字段后TellCore是否仍可执行"），但没有验证学习端的提取过程本身——**提取出的解题思维是否完备（有没有遗漏）、是否准确（有没有噪声）、是否因果充分（提取的东西真的导致了成功吗）**。

396号§4.2.1还强调了GPT的关键论述：**"只在成功trace中反复出现的结构，不一定导致成功"**——它可能只是解答者的写作习惯、某个领域常见符号、成功后才补写的解释、或与真正关键动作高度相关但没有推动作用的伴随步骤。要区分"有因果贡献"和"只是伴随出现"，需要用失败trace做对照。

**POC-1增强版的提取完备性检查**就是填补这个缺失——让独立审查者从同一份正确答题过程中独立提取解题思维，与系统提取的TellCore对照，检查是否有遗漏、噪声和偏差。

### 2.3 397号§3.5：Pareto前沿验证的缺失

397号§3.5指出了373号POC-1设计的另一个缺失：

> 373号只测试"通过/不通过"，没有测试多轴非支配性。

396号§3详细论证了为什么"钟形曲线最高点"应改成"Pareto前沿"：
- Level至少是一个向量（object_generality / relation_generality / operation_generality / goal_generality / trigger_generality / evidence_generality / temporal_span / domain_distance）
- Tell质量至少包含8个维度（触发准确率 / 操作可执行性 / 近迁移效用 / 远迁移效用 / 负迁移率 / 提示成本 / 泄漏风险 / 模型适配性）
- 一个Tell可能远迁移强但成本高，另一个近迁移强且极便宜——两者都可能值得保留
- **不应寻找一个全局"最优Level Hint"，而应保存当前证据下的Pareto前沿：没有另一个候选在所有重要指标上都更好**

383号的POC-1只验证了一个TellCore v0候选C，没有比较多个候选的非支配性。**POC-1增强版的Pareto前沿分析**就是填补这个缺失——对3个以内候选TellCore按8维度评分，画出Pareto前沿，保留非支配集而非只选"最好的一个"。

## §4 输入——这个POC需要什么

### 4.1 Source trace题的正确答题过程

从382号CasePack v0的22道题中取**4道source trace题**（1631/1843/1709/1962）的完整正确答题过程（thinking/trajectory/proof）。

这4道题的特点（来自382号§1.2和383号§1.3）：
- 1631：模8+二次剩余——局部-全局切换成功案例，Euler准则
- 1843：模4+符号配对——局部-全局切换成功案例，符号配对
- 1709：p-adic赋值——局部-全局切换成功案例，v_p分析
- 1962：2-adic赋值——**tree组成功但bare组失败**，是因果取商的核心教训（方向Tell不够，需要操作路径Tell）

**提取完备性检查需要的是这4道题的正确答题过程全文**（成功trace），以及1962的bare失败记录（失败trace做对照）。

### 4.2 383号已完成的12字段消融结果

383号对TellCore v0候选C的12个字段做了逐项消融分析，确定了：
- **最小充分字段集（7字段）**：invariant_claim、trigger_boundary、negative_boundary、parameter_slots(p+level+objects)、internal_policy(step2-5)、progress_model、termination
- **重要补充（5字段）**：binding_rules、internal_policy(step1+step6)、critic、composition_contract、parameter_slots(target_structure)
- **元数据/输入（2字段）**：name、source_branch_events
- **7项通过标准验证结果**：全部PASS（部分有条件）

Pareto前沿分析需要用这个7字段最小充分集作为**候选A（baseline）**，再构造2个相邻候选（见§5.4）。

### 4.3 400号变形关系声明

400号（POC-0.5方案文档）声明的变形关系：

| 变换类型 | 是否允许 |
|---|---|
| 变量重命名 | ✅允许 |
| 数值缩放 | ✅允许 |
| 对象换壳（整数→多项式） | ✅允许 |
| 领域迁移（数论→组合） | ✅允许 |
| 表示形式改变（mod p → p-adic） | ✅允许 |
| 机制破坏：构造性而非整除性 | ❌禁止 |
| 机制破坏：已在局部表示下 | ❌禁止 |
| 机制破坏：几何而非代数 | ❌禁止 |
| 增加无关诱饵 | ✅允许 |
| 改变一个关键条件 | 边界 |

提取完备性检查需要用这个声明表验证：系统提取的TellCore是否覆盖了所有允许变换（即TellCore的trigger_boundary和negative_boundary是否正确区分了允许变换和禁止变换）。

### 4.4 独立审查者

提取完备性检查需要一个**独立审查者**——一个不知道383号TellCore内容的AI（或人类专家），从同一份正确答题过程中独立提取解题思维。独立审查者不能加载383号文档。

### 4.5 候选TellCore构造

Pareto前沿分析需要3个以内候选TellCore：
- **候选A（baseline）**：383号的7字段最小充分集（见§4.2）
- **候选B（精简版）**：从候选A中删除trigger_boundary或negative_boundary——测试"更激进的取商"是否仍可执行
- **候选C（扩展版）**：在候选A基础上添加binding_rules和critic——测试"更保守的取商"是否有增量价值

## §5 方法——这个POC怎么做

### 5.0 方法总览

POC-1增强版包含三个部分：

| 部分 | 来源 | 状态 | 本增强版做什么 |
|---|---|---|---|
| Part 1：12字段消融分析 | 383号原始版本 | ✅已完成 | 不重做——直接复用383号结果 |
| Part 2：提取完备性检查 | 397号§3.3新增 | ❌未做 | **本增强版新增**——独立审查者独立提取+对照 |
| Part 3：Pareto前沿分析 | 397号§3.5新增 | ❌未做 | **本增强版新增**——3候选×8维度评分+Pareto前沿 |

### 5.1 Part 1：12字段消融分析（383号已完成，不重做）

383号已对TellCore v0候选C的12个字段（F1~F12）做逐项消融，每个字段问5个问题：
- 问1：删除F后，TellCore是否仍可在新题上执行？
- 问2：删除F后，TellCore是否仍能解释迁移？
- 问3：删除F后，替换表面外壳后是否保持作用？
- 问4：删除F后，改变关键结构后是否应拒绝？
- 问5：删除F后，是否能解释正例和负例的差异？

结果：7字段最小充分集 + 5字段重要补充 + 2字段元数据/输入。详见383号§2~§3。**本增强版不重做这部分，直接引用383号的结果。**

### 5.2 Part 2：提取完备性检查（新增）

#### 5.2.1 设计

提取完备性检查验证的不是TellCore的字段结构（那是Part 1的工作），而是**提取过程本身**——从正确的答题过程中提取的解题思维是否完备、是否准确、是否因果充分。

方法：让独立审查者从同一份正确答题过程中独立提取解题思维，与系统提取的TellCore（383号的7字段最小充分集）对照，检查三个维度：

| 维度 | 检查什么 | 如何检查 |
|---|---|---|
| **完备性（有没有遗漏）** | 独立审查者发现的解题思维，系统是否也提取了？ | 对比独立审查者的提取结果与383号TellCore的字段——如果审查者发现了某个关键解题思维但TellCore中没有对应字段，说明有遗漏 |
| **准确性（有没有噪声）** | 系统提取的解题思维中，哪些不是因果充分的？ | 用1962的bare失败trace做对照——如果某个字段在失败trace中也出现，它就不是"导致成功"的因果因素，可能是噪声 |
| **偏差性（有没有偏向）** | 系统提取的TellCore是否偏向某种类型的解题思维而忽略其他类型？ | 检查4道source trace题的提取是否均衡——如果TellCore主要从1631/1843提取（模p层面）而忽略了1709/1962（p-adic层面），说明有偏差 |

#### 5.2.2 独立审查者的操作

1. **准备**：独立审查者加载382号的4道source trace题（1631/1843/1709/1962）的完整正确答题过程全文。独立审查者**不加载**383号文档——不知道系统已提取的TellCore内容。
2. **独立提取**：审查者从每道题的正确答题过程中独立提取解题思维——回答"什么认知动作导致了成功？"。审查者用自己的语言描述提取的解题思维，不限于任何预设的字段结构。
3. **对照**：将审查者的独立提取结果与383号的TellCore 7字段最小充分集对照：
   - 审查者提取的每个解题思维 → 在TellCore的哪个字段中体现？如果找不到对应字段 → **遗漏**
   - TellCore的每个字段 → 在审查者的提取结果中是否有对应？如果审查者没有提取 → 可能是**噪声**或**过度提取**
   - 审查者提取的解题思维的分布 → 是否与TellCore的字段分布一致？如果不一致 → **偏差**

#### 5.2.3 因果充分性验证（用失败trace做对照）

对TellCore的7个字段，逐个用1962的bare失败trace做对照：
- 如果某个字段描述的认知动作在1962的bare失败trace中也出现了 → 这个字段可能不是"导致成功"的因果因素（只是伴随出现）→ 标记为**候选噪声**
- 如果某个字段描述的认知动作在失败trace中没有出现 → 这个字段更可能是因果充分的 → 保持

**特别注意**：1962是关键对照——1962在bare组失败（方向Tell不够），但在tree组成功（操作路径Tell够）。所以1962的bare失败trace中，"切换到p-adic"这个方向出现了（但不够），而step2-5的操作路径没有出现。这说明"方向"不是因果充分的（失败trace中也有），而"操作路径"是因果充分的（失败trace中没有，成功trace中有）。383号已经发现了这一点（§2 F8的关键发现），提取完备性检查要系统化地验证这个发现。

#### 5.2.4 变形关系对照

用400号的变形关系声明表，检查TellCore的提取完备性：
- 对每个**允许变换**（变量重命名/数值缩放/对象换壳/领域迁移/表示形式改变）→ TellCore的trigger_boundary是否正确覆盖？如果某个允许变换不在trigger_boundary的覆盖范围内 → **遗漏**
- 对每个**禁止变换**（构造性/已在局部表示/几何）→ TellCore的negative_boundary是否正确拒绝？如果某个禁止变换不在negative_boundary的拒绝范围内 → **遗漏**
- 对**边界变换**（改变一个关键条件）→ TellCore的trigger_boundary/negative_boundary是否正确标为boundary？如果缺失 → **遗漏**

### 5.4 Part 3：Pareto前沿分析（新增）

#### 5.4.1 候选TellCore构造

构造3个候选TellCore：

| 候选 | 描述 | 字段组成 | 测试什么 |
|---|---|---|---|
| **候选A（baseline）** | 383号的7字段最小充分集 | invariant_claim + trigger_boundary + negative_boundary + parameter_slots(p+level+objects) + internal_policy(step2-5) + progress_model + termination | 已验证的baseline |
| **候选B（精简版）** | 从A中删除negative_boundary | A的7字段 - negative_boundary | 测试"更激进的取商"——没有负触发条件时，假朋友拒绝能力下降多少 |
| **候选C（扩展版）** | 在A基础上添加binding_rules + critic | A的7字段 + binding_rules + critic | 测试"更保守的取商"——有绑定规则和自检时，操作准确性和假朋友拒绝提升多少 |

**为什么选这3个候选**：
- 候选A是383号已验证的baseline——有一个参照点
- 候选B测试"取商过度"的风险——396号§4.2说"取商"是把表面不同但等价的视为同一个，但如果取商过度（删掉negative_boundary），会失去对假朋友的区分能力
- 候选C测试"取商不足"的风险——396号§4.5说TellCore是认知Option，有critic才能在失败时迭代。如果取商不足（保留太多字段），可能增加成本但边际效用递减

#### 5.4.2 8维度评分

对3个候选，按397号§3.5和396号§3.3的8个维度评分：

| 维度 | 评分标准 | 评分方式 |
|---|---|---|
| 1. 触发准确率 | trigger_boundary能正确触发正迁移题、正确拒绝假朋友题的比例 | 用382号CasePack的22道题做判断（不跑Solver，只做结构分析） |
| 2. 操作可执行性 | internal_policy是否是操作路径而非口号 | 用383号§4.4的验证方法——1962的操作路径验证 |
| 3. 近迁移效用 | 在结构相似的变形题（CC-009~012）上的预期效用 | 结构分析——参数槽能否绑定到变形题 |
| 4. 远迁移效用 | 在跨域变形题（如有）上的预期效用 | 结构分析——trigger_boundary是否覆盖跨域场景 |
| 5. 负迁移率（越低越好） | 假朋友题（CC-013~017）上误触发的预期率 | 结构分析——negative_boundary的覆盖范围 |
| 6. 提示成本 | 渲染成HintInstance后的token长度/认知负载 | 估算——字段越多成本越高 |
| 7. 泄漏风险（越低越好） | 是否包含具体lemma/题目特定信息 | 用383号§5的信息泄漏审查方法 |
| 8. 模型适配性 | 对不同Solver模型的预期适配度 | 结构分析——操作路径是否依赖特定模型的特征 |

**评分标度**：每个维度1-5分（1=最差，5=最好）。对于"越低越好"的维度（5和7），分数转换为"越低越好=分越高"。

#### 5.4.3 Pareto前沿判定

对3个候选的8维度评分，判定Pareto前沿：

- **候选X支配候选Y**：如果X在所有8个维度上都≥Y，且至少在1个维度上>Y
- **Pareto前沿**：不被任何其他候选支配的候选集合
- **非支配集**：Pareto前沿上的所有候选

**预期结果**：
- 候选A在触发准确率和负迁移率上优于B（因为A有negative_boundary）
- 候选C在触发准确率和负迁移率上优于A（因为C有critic做安全网）
- 候选A在提示成本上优于C（因为A字段更少）
- 候选B在提示成本上最优，但负迁移率最差
- **Pareto前沿可能是{A, C}**——A成本低但假朋友拒绝弱，C成本高但假朋友拒绝强，两者各有优势，互不支配

#### 5.4.4 Pareto前沿分析的操作

1. 对3个候选分别做8维度评分（不跑Solver——POC-1是分析性POC，评分基于结构分析）
2. 构建评分矩阵（3候选 × 8维度）
3. 计算Pareto前沿（非支配集）
4. 画出Pareto前沿图（8维度中选2-3个关键维度做散点图，标注非支配候选）
5. 记录分析结论——哪些候选在Pareto前沿上，为什么

### 7.2 新增标准8：提取完备性检查通过

**提取完备性检查通过，需要满足**：

1. **完备性**：独立审查者发现的解题思维中，至少80%在TellCore的7字段中有对应字段——遗漏项不超过20%，且没有high severity的遗漏
2. **准确性**：TellCore的7个字段中，用1962失败trace做对照后，candidate_noise的字段不超过2个——至少5个字段是causally_sufficient
3. **偏差性**：4道source trace题的提取分布没有严重偏差——从1709/1962（p-adic层面）提取的字段数不低于从1631/1843（模p层面）提取的字段数的50%
4. **变形关系覆盖**：400号声明的5个允许变换中至少4个被TellCore覆盖，3个禁止变换中至少2个被TellCore拒绝

### 7.3 新增标准9：Pareto前沿分析完成

**Pareto前沿分析完成，需要满足**：

1. **3个候选全部评分**：候选A/B/C的8维度评分全部完成，没有空缺维度
2. **Pareto前沿已判定**：明确列出非支配集（哪些候选在Pareto前沿上）
3. **Pareto前沿图已产出**：至少用2个关键维度（如"触发准确率"×"提示成本"）画出散点图，标注非支配候选
4. **分析结论已记录**：Pareto前沿上的候选是谁、为什么在前沿上、不在前沿的候选被谁支配

### 7.4 不通过的处理

**如果提取完备性检查不通过**（标准8不满足）：

- **如果是遗漏（omissions）**——独立审查者发现了TellCore中没有的关键解题思维。需要：把遗漏的解题思维补入TellCore的字段中，或说明为什么这个解题思维不属于TellCore的因果结构
- **如果是噪声（noise）**——TellCore中有些字段在失败trace中也出现，不是因果充分的。需要：标记这些字段为"候选噪声"，在后续POC中用经验数据验证是否真的可以删除
- **如果是偏差（bias）**——TellCore偏向某种类型的解题思维。需要：检查是否因为4道source trace题的分布不均衡导致，如果是，考虑补充更多source trace题
- **如果是变形关系覆盖不足**——TellCore的trigger/negative_boundary没有覆盖400号声明的某些变换。需要：补充trigger_boundary或negative_boundary的条目

**如果Pareto前沿分析不通过**（标准9不满足）：

- 如果3个候选全部被一个候选支配——说明只有"最好的一个"，Pareto前沿退化为单点。这不是失败，只是说明候选间差异不大。记录结论即可
- 如果评分无法完成（某个维度无法评分）——说明该维度的评分标准需要更具体的定义。需要：细化评分标准后重做

### 7.5 通过后不意味着TellCore"经验有效"——只意味着"结构完备+提取完备+多轴非支配"

**重要**：POC-1（增强版）通过只说明：
1. TellCore的字段结构通过7项标准（383号已完成）
2. 提取过程本身是完备的、准确的、无严重偏差的
3. 如果有多个候选，Pareto前沿已分析

但这**不意味着TellCore在运行时经验有效**——POC-1是分析性POC，不跑Solver。经验有效性需要POC-2（可选择）、POC-2.5（基础因果效应）、POC-3（可执行）等在Solver上验证。

## §9 执行约束

### 9.1 不启动Solver

POC-1（增强版）是**分析性POC**——不启动Solver，不修改代码，不写入数据库。提取完备性检查和Pareto前沿分析都是基于结构分析和文档对照完成的，不需要运行时实验。

### 9.2 独立审查者的独立性

提取完备性检查的独立审查者**必须独立**——不能加载383号文档，不能知道系统已提取的TellCore内容。如果审查者已知TellCore内容，提取完备性检查就退化为"验证已知答案"而非"独立验证提取过程"。主执行者在安排独立审查者时必须确认这一点。

### 9.3 Git

- Git add必须显式路径，不能`git add -A`或`git add .`
- 产物文件（poc_1_enhanced_extraction_completeness_report.yaml / poc_1_enhanced_pareto_frontier.md / poc_1_enhanced_result.yaml / 独立审查者提取记录）必须commit

### 9.4 证据分层

POC-1（增强版）的结论必须写成证据分层：
- 提取完备性检查的结论分为"完备性/准确性/偏差性"三个维度，各自独立判定
- Pareto前沿分析的结论分为"评分完成/Pareto前沿判定/图已产出/结论已记录"四个子项
- 不把"提取完备"升级成"TellCore经验有效"——经验有效性需要POC-2~8在Solver上验证

### 9.5 383号结果的不可篡改性

383号已完成的12字段消融结果是**冻结的**——本增强版不修改383号的结果，只在383号基础上增加新工作。如果提取完备性检查发现383号的TellCore有遗漏或噪声，应记录为新发现，不直接修改383号文档——383号是历史记录，修订应通过新文档（如POC-7可持续学习）进行。

### 9.6 失败不是废结果

如果提取完备性检查发现TellCore有严重遗漏或严重噪声，这不是废结果——这是重要发现。它说明383号的提取过程本身有问题，需要在POC-7（可持续学习）中修订TellCore。不通过的结果必须完整记录，并触发对TellCore的修订候选记录。

```

- **提取完备性检查不通过阻塞POC-2/2.5/3.5/3/4/6/7/8**——这些都依赖TellCore的正确性。如果TellCore提取有问题，后续验证都建立在有问题的基础上
