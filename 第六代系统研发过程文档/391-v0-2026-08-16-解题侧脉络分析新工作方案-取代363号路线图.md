## §2 新目标与主干路径

**解题侧脉络分析的存在理由是服务Grove核心循环**（AGENTS.md顶部）：推理AI跑完/跑死后，系统从其trajectory中识别trace，匹配/生长tell，变成引导树的新边。原路线后期偏离了这个主干——增量花在"何时允许下一次实验"的流程机器上，而非"分析能力能否在真实轨迹上产出可用trace"上。

主干路径（每一步都直接可见于Grove循环）：

```
真实Solver轨迹（D盘，历史冻结数据）
  → 事件结构化（raw thinking → ReasoningTrajectory/v1）   ← 已知缺口，见§4.1
  → typed DAG（models.py + pipeline.py）
  → FCA多视图 + 七类trace提取（fca.py + pipeline.py）
  → trace_auditor结构审计（branch/failure/revisit/merge/recovery）
  → trace→tell匹配（对接370号分片合同与现有tell库）
  → 引导树新边（Grove循环第三个推动关系）
```

**验收的总原则**：每个阶段的产出必须能回答一个用户可见的问题，而不是产生一份新的流程物证。

## §3 工作原则（防过度设计条款，可检查）

以下条款是硬规则，违反任何一条即视为再次跑偏：

1. **能力-测试挂钩**：新增测试只能挂在新增能力或修复的缺陷上。为"未来可能获批的实验"预建测试/脚本/协议，一律禁止。
2. **同构禁止复制**：第三个出现同构形态的脚本/协议/文档必须触发抽象（提公共库）或取消，而不是第三份复制。原路线VMS-41R1与VMS-42的资格外围即为第二份复制，已冻结。
3. **单一状态源**：本线进度只记在本文件§8看板。不再建route-lock类互锁文件；不维护指针的多重镜像。
4. **哈希只用在有真实对手的地方**：冻结物证的防篡改校验、入题侧保护基线——这两类保留。其余场景（文档-代码-测试日常互锁）禁用sha256。
5. **文档一阶段一份**：每个阶段一份协议+一份结果（或直接在本文件追加结果节）。协议先于执行写，但协议长度与阶段复杂度成比例；禁止为一小时的工作写三百行协议。
6. **即时commit**：每个工作包完成即显式路径add + commit。禁止再出现整线untracked状态。
7. **真实数据优先于模拟**：凡是能用D盘历史真实轨迹验证的，不用合成/fake数据。fake materializer类组件冻结。
8. **负结果也是结果**：实验FAIL直接记录结果文档并报告用户，不进入"修链再试"循环。

### P1 · 真实数据golden slice（核心阶段，零模型）

**目标**：回答"VMS-31核心+trace_auditor在真实Solver轨迹上产出的trace质量如何"——这是原路线始终没有回答的问题。

| 动作 | 说明 |
|---|---|
| P1.1 选材 | 从DB选2-3条**已知结局差异明显**的历史轨迹（1条solved + 1条failed_token_limit + 1条failed_no_proof），优先Tier 1题目；从`problem_entries`反查路径，复制进本线工作目录（只读副本，带exp_id溯源） |
| P1.2 人工事件结构化 | 负责AI**亲手**（不建自动抽取器）把thinking文本转成`ReasoningTrajectory/v1`（models.py合同：events带EventKind/EventStatus）。每条轨迹预计半天内。这一步就是VMS-41想用模型做而4/4 FAIL的事——先用人工打通下游，把"抽取难度"变成可观察的具体困难清单，而不是资格链模拟 |
| P1.3 跑通全链 | pipeline.py（DAG+双FCA+七类trace）→ state_normalization → state_normalized_dag sidecar → trace_auditor |
| P1.4 质量评估与困难清单 | 逐trace人工评估：识别出的branch/failure/revisit/merge/recovery是否真实反映该轨迹的思维过程？记录误报/漏报实例。产出《P1结果：真实轨迹golden slice报告》（392号） |
| P1.5 合同反馈 | 若`ReasoningTrajectory/v1`合同在真实数据上暴露缺口（event kind不够用等），修订models.py并同步`system/docs/solve_vein_analysis.md`，此为正当的代码变更 |

**明确不做**：不建qualification pack；不建hidden-join模拟器；不改22个冻结脚本；不连DB写（只读反查经`system/db.py`，须先`echo $ARANGO_DB`确认）。

**用户决策点1（P1完成后）**：人工结构化的成本与困难清单摆出来之后，用户决定trace质量是否足以进入P2，或是否值得为自动抽取申请真实模型调用。

### P2 · trace→tell对接（依赖P1通过）

- 用P1产出的真实trace对接**370号Trace-Tell-Hint文件分片合同**（items.jsonl权威项集+机械对账——370号本身设计克制，直接复用）；
- 匹配对象优先现有tell库（455 profile的4,164个tell，`problem_profiles`集合，只读）；
- 回答的问题："真实轨迹上识别的trace，能命中tell库中的现成tell吗？命中率与错配实例是什么？"
- 产出：393号（P2协议）+394号（P2结果）。

### P3 · Grove闭环接入（依赖P2）

- P2中未匹配的trace按315号工作流走孤悬trace存档或新tell提案（人工Gate，不自动写库）；
- 终点：一条真实轨迹 → 结构化 → trace → tell/hint → 引导树新边提案，全链在**真实历史数据**上走通一遍（golden slice of the loop）；
- 此后才讨论接实时系统（pipe/5服务、tmux监控），另立阶段。

### 用户决策点2（显式，此前禁止预建）

**模型抽取资格重考（原VMS-41R1）**：只有当（a）P1证明下游链路值得喂，（b）人工结构化的困难清单表明自动抽取有明确改进方向（提示词/合同修订），（c）用户批准LiveRunPermit与额度，三者齐备时才启动。重考时直接使用冻结的资格链脚本按需复活单个（不新建同构物），资格标准沿用371号已冻结的hidden acceptable set设计。
