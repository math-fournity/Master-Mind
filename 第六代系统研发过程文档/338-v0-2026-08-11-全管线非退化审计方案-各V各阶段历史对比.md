# 338号 · 全管线非退化审计方案——各V各阶段历史对比

**日期**：2026-08-11
**状态**：方案设计
**来源**：用户要求"全历史，包含POC那个时候的非退化分析报告。而且是全管线分析，不仅仅是最后的结果分析，是管线的各个部分，就是各个V自己的阶段结束的时候，和历史数据之间的非退化数据分析"

---

## 1. 问题——现有审计只看最终结果

现有`run_audit.py`只审计阶段2综合分析的最终产出（output.json的trace/closed_elements/AI优势），不审计阶段1格化各V的产出。

**这有什么问题**：

- V8格化退化（段数21 vs 0005的32）不会被发现——因为综合分析可能通过其他版本的格化结果补偿
- V10闭元素退化不会被发现——因为综合分析的trace数量可能不受影响
- 各V的格化质量波动无法追踪——不知道哪个版本在退化、哪个版本在提升

**用户要的是**：管线每个部分（每个V的格化阶段）结束时，都和历史数据做非退化分析。这才是全面的。

### 第2层：阶段1.5程序枚举——闭元素历史对比

程序枚举的闭元素数和各V的格化结果直接相关——闭元素数取决于段数和特征数。这层和第1层的闭元素数是同一个数据，但分析角度不同：

**退化判定**：闭元素数和段数/特征数的关系是否合理——如果段数和特征数不变但闭元素数大幅下降，可能是程序bug。

### 3.5 退化判定标准

**第1层（格化）**：
- 段数 < 历史最低值的80% → 退化

- 闭元素数 < 历史最低值的80% → 退化

**第2层（程序枚举）**：
- 闭元素数和段数/特征数的关系异常（如段数特征数不变但闭元素大幅下降）→ 程序bug

**第3层（综合分析）**：
- trace数量 < 历史最低值的80% → 退化
- trace类型 < 历史最低值的70% → 退化
- 和现有run_audit.py一致

## 4. baseline说明

**baseline是什么**：POC时期4套POC的output.json——V5/V7/V8/V10各跑一次完整流程（旧版，没有三阶段架构，每个版本自己做完格化+trace识别+审计）。

**baseline的局限性**：
- V5的baseline段数只有10——因为V5是自由直觉段划分，POC时期的V5提示词和现在不同
- baseline的闭元素数是各版本自己枚举的，不是程序枚举的——枚举方法可能不同
- baseline的trace是各版本自己识别的，不是综合分析阶段识别的——识别标准可能不同

**为什么仍然用baseline做对比**：
- baseline是"POC时期的能力基线"——即使有局限性，它记录了系统最初能做什么
- 如果当前运行比baseline还差，那是真正的退化
- baseline的并集（4套POC的trace合并去重）是一个"能力上界"——单次运行不应该超过它太多，但也不应该比它差太多
