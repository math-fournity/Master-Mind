# 335号 · V8格化session的thinking过大问题分析——保守方案

**日期**：2026-08-11
**状态**：修订v1——文件拆分流程控制方案测试发现退化，修订为不会退化的方案
**来源**：334号方案执行过程中V8反复超时（0005: 500秒, 0006: 1300秒+未完成）引发的拆分讨论；文件拆分流程控制方案测试发现退化

---

## 1. 问题现象

V8在多次运行中都是最慢的版本，且thinking内容大：

| 运行 | V5 | V7 | V8 | V10 |
|---|---|---|---|---|
| 0004 | 120秒 | 180秒 | 500秒 | 260秒 |
| 0005 | 80秒 | 320秒 | 500秒 | 240秒 |
| 0006 | 120秒 | 320秒 | **1300秒+未完成** | 420秒 |

V8的特征数（32个）不是最多的——V10的42个比V8多。但V8最慢。根因不只是特征数——是V8要求AI在thinking中做**"识别关键实体→分析每个关键实体在每个段中的角色→标注角色特征"**的语义分析，加上V8还会做矩阵验证+修正（0005的日志显示V8写完矩阵后发现错误，用Python脚本重新生成），进一步放大thinking量。

---

## 2. 拆分方案的讨论

### 2.1 拆分方案

把V8拆成两个子session：
- **V8a（段划分+常规特征标注）**：和V7一样，只做段划分+常规思维特征标注
- **V8b（关键实体角色特征补充）**：读V8a的segments.json，识别关键实体，对每个段分析关键实体的角色，补充角色特征到formal_context.json
- 程序合并V8a和V8b的形式上下文

### 2.2 拆分方案的风险

**风险1：认知过程断裂——和333号§2.4.1同类风险**

V8原版是一个session——AI在做段划分的同时，就在思考"这个段用了x的什么角色"、"这个段用了aₙ的什么角色"。**段划分和角色特征标注是同一个认知过程**——AI对每段的理解是整体的，常规思维特征和角色特征是同时考虑的。

拆分后，V8b读V8a的segments.json——V8b看到的是V8a已经划好的段。V8b的工作变成"在已有段划分上补充角色特征"，不是"在做段划分的同时识别角色特征"。**这个认知过程断裂了。**

具体后果：
- V8原版可能因为"aₙ在这个位置的角色变化"而把一个段分成两段——V8a不会这样做（V8a只考虑常规思维特征），V8b想分也来不及了（段划分已固定）
- V8a的段划分粒度可能不适合角色特征标注——某些段从常规特征看是一个段，但从角色特征看应该是两个段

**这就是333号§2.4.1的风险——(G,M,I)的不完美。** V8拆分后，(G,M,I)的构造分两步，V8a构造时不知道V8b需要什么段划分粒度，V8b补充时受限于V8a的段划分。合并后的(G,M,I)可能不如V8原版协调。

**风险2：角色特征标注不够深入——可能导致trace退化**

V8的独特价值是"跨闭元素元模式引导"——通过标注关键实体角色特征，让形式上下文能捕获跨闭元素元模式的段集合。这个价值依赖于AI对"关键实体在证明中的角色"的深入理解。

V8原版的认知路径：读解答→划段（同时考虑常规特征和角色特征）→构造矩阵
V8b的认知路径：读V8a的段划分→识别关键实体→对每个段标注角色特征→补充矩阵

V8b的认知路径是"在已有段划分上补充特征"——这是局部的、分析的，不是整体的、直觉的。**V8b可能只标注那些"明显"的角色特征，漏掉那些"需要在段划分时才能发现"的角色特征。**

如果V8b的角色特征标注不够准确，程序枚举的闭元素会不同，综合分析的输入不同，最终trace可能退化——**这和nonlocal trace退化是同类问题：认知路径的局限导致产出退化。**

**风险3：综合分析Agent的回溯检查可能发现不了V8b的问题**

333号方案的应对措施是综合分析Agent做"形式上下文回溯检查"。但回溯检查是检查"有没有遗漏的闭元素"——不是检查"角色特征标注是否准确"。

如果V8b漏标了某个角色特征（比如段15应该有"aₙ的最大性"但V8b没标），导致程序枚举少了几个闭元素，综合分析Agent的回溯检查可能发现不了——因为回溯检查是看"有没有在思维上属于同一层的段集合没被枚举到"，不是看"某个段的角色特征标注是否准确"。

**风险4：V8a和V8b对段的理解不一致**

V8a标了"鸽巢论证"，V8b标了"x的使用"——但V8b可能不知道V8a在标"鸽巢论证"时是基于什么理解。如果V8a和V8b对同一段的理解不一致，合并后的(G,M,I)可能不协调。

### 2.3 风险综合判断

**V8拆分确实有风险，主要风险是认知过程断裂——和333号§2.4.1记录的(G,M,I)不完美风险同类，但更严重。** 333号方案的风险是"AI做段划分时可能遗漏特征"，V8拆分的风险是"段划分和角色特征标注不在同一个认知过程中完成，可能导致段划分粒度不适合角色特征标注"。

**而且，这个风险恰恰可能引入nonlocal trace退化的同类问题**——V8b的认知路径是"从V8a的段划分出发补充角色特征"，不是"从解答内容出发整体理解段的角色"。这和综合分析Agent"从闭元素出发做语义解读"而不是"从段内容出发识别nonlocal trace"是同类问题——认知路径的局限导致产出退化。

---

## 3. 决策：不拆分，采保守方案

### 3.1 决策理由

V8拆分引入的风险（认知过程断裂→角色特征标注不够深入→闭元素不同→trace退化）大于它解决的问题（thinking太大→可能truncated）。

**核心原则：不因为工程问题（thinking太大）而牺牲认知质量（段划分和角色特征标注的统一认知过程）。** 333号方案的核心思想就是"程序做确定性运算，AI做语义判断"——V8的角色特征标注是语义判断，不应该因为thinking太大就拆成两步。

### 3.2 保守方案

V8的thinking太大问题，用以下方式解决：

**措施1：简化V8提示词——减少thinking中的验证工作**

V8在0005的日志显示它写完矩阵后还做了验证+用Python脚本重新生成。这些验证工作放大了thinking量。在V8提示词中明确：

```markdown
## 执行顺序——先写文件，不做验证

1. 读解答文本
2. 划段+标注特征（常规思维特征+关键实体角色特征）
3. 构造形式上下文矩阵
4. **立即写segments.json和formal_context.json**
5. 创建DONE.md

**不要在thinking中做矩阵验证**——矩阵验证是程序的工作，
verify_lattice_completeness.py会做。你只负责标注特征和构造矩阵。
```

**措施2：如果V8仍然超时——接受V8偶尔失败，用降级选项**

333号§6的待决策问题3已经提出了这个降级选项："如果某个版本的格化session失败了，是否可以用其他3个版本的格化结果继续？"

V8偶尔失败时，用V5/V7/V10三个版本的格化结果继续阶段1.5和阶段2。V8的独特价值（跨闭元素元模式引导）在阶段2的综合分析Agent中也会做（综合分析Agent的第五步"识别跨闭元素元模式"）——即使V8的格化结果缺失，综合分析Agent仍然能识别跨闭元素元模式，只是不是通过V8的角色特征引导程序枚举来捕获。

**措施3：设置V8超时阈值**

给V8设置一个超时阈值（如900秒/15分钟）。超过阈值后判定V8失败，用降级选项继续。避免V8无限等待阻塞整个管线。

### 3.3 降级选项的实现

在`_phase1_grading`中，等待4个格化session完成时，对V8设置超时：

```python
# V8超时阈值（秒）——V8的thinking通常比其他版本大
V8_TIMEOUT = 900

# 轮询时检查V8是否超时
if version == "V8" and elapsed > V8_TIMEOUT:
    print(f"  ⚠️ V8超时({elapsed}秒)，使用降级选项——用V5/V7/V10继续")
    # V8标记为失败，不等待V8的DONE.md
    # 阶段1.5和阶段2用V5/V7/V10的格化结果继续
```

## 6. 修订v1——文件拆分流程控制方案测试发现退化

### 6.1 测试方案

在335号v0之后，引入了"文件拆分流程控制"技术（six-file-staged-flow.md规则），把V8的工作拆成4个步骤：
- step1：段划分（要求"不要标注任何特征"）
- step2：常规思维特征标注
- step3：关键实体角色特征标注
- step4：形式上下文矩阵构造

用/tmp/v8_test/目录单独测试了V8（违反数字ID命名规范，已修正为规则）。

### 6.2 测试结果——有退化

| 维度 | V8测试（文件拆分） | 0005 V8（原版） | 判定 |
|---|---|---|---|
| 段数 | **21** | **32** | **❌ 退化——少了11段** |
| 常规特征数 | 12 | 32（含角色特征） | step3未完成，无法对比 |
| 完成时间 | 2分钟（step1+step2） | 500秒 | ✅ thinking控制有效 |

**核心退化：段数从32降到21——少了11段。**

### 6.3 退化根因——改变了认知内容

文件拆分流程控制的目的应该是**确保执行顺序**（先写文件不做验证），**不应该改变认知内容**。但我们的step1要求文件中写了：

> "不要在这一步标注任何特征——特征标注是后续步骤的事，你只做段划分。"
> "features留空数组——特征标注是后续步骤的事，这一步只做段划分。"

这条指令直接导致了退化：

V8的独特价值 = 段划分和角色特征标注是**同一个认知过程**：
- aₙ在某段的角色变化可能导致V8把一个段分成两段
- x在某段的使用方式变化可能导致V8把一个段分成两段
- 这些"因为特征变化而更细的分段"在step1被禁止了
- step1只看"思维步骤"，不看"特征变化"，所以分得更粗

**我们在step1要求"不要标注特征" = 改变了认知内容 = 设计错误。**

### 6.4 用户的核心观点

用户说："我们只是为了确保一个执行顺序，按道理不应该退化。"

这指出了文件拆分流程控制的正确设计原则：

**原则：不改变认知内容，只改变执行顺序。**
- ✅ 正确：AI做和原版一样的认知工作，但按顺序执行，先写文件不做验证
- ❌ 错误：AI做和原版不一样的认知工作（如step1不标注特征）

### 6.5 不会退化的方案设计

#### 方案D：step1做完整格化认知，step2做矩阵构造

```
step1: 读解答→划段+标注所有特征（常规+角色）→输出segments.json（含所有特征）
step2: 读segments.json→构造形式上下文矩阵→输出formal_context.json
```

**为什么不会退化**：
- step1的认知过程和原版完全一样（段划分+所有特征标注统一）
- step1没有要求"不要标注特征"——AI可以因为特征变化而分段更细
- step2只是机械的矩阵构造（不需要大量thinking）
- thinking被拆成两步，但认知过程没有被拆分

**thinking控制效果**：
- step1的thinking = 格化thinking（段划分+特征标注）
- step2的thinking = 矩阵构造thinking（机械工作，thinking量小）
- 比原版少了矩阵验证+修正的thinking

**风险**：step1仍然需要做段划分+所有特征标注，thinking可能仍然大。但比原版少了矩阵构造+验证的thinking。

#### 方案E：不拆分认知过程，只用"先创建文件+不做验证"指令

```
一个step：读解答→划段+标注所有特征→构造矩阵→写文件→创建DONE.md
提示词加"先创建空文件+不做验证"指令
```

**为什么不会退化**：
- 认知过程完全和原版一样（一个thinking中做所有事情）
- 只加了"先创建文件+不做验证"指令——不改变认知内容
- 和335号v0的措施1一样

**thinking控制效果**：
- 比原版少了验证+修正的thinking
- 但thinking仍然在一个step中，可能仍然大

#### 方案选择

| 方案 | 认知过程完整性 | thinking控制 | 退化风险 | 复杂度 |
|---|---|---|---|---|
| D（step1完整格化，step2矩阵） | 完整 | 好（拆成两步） | 无 | 中（2个step要求文件） |
| E（不拆分，只不做验证） | 完整 | 中（少了验证） | 无 | 低（1个提示词改动） |

**推荐方案D**——thinking控制效果更好，且不会退化。step1的认知过程和原版完全一样，step2只是机械的矩阵构造。

### 6.6 方案D的实现

#### v8_grading.md改为2步

```
第0步：先创建所有输出文件（空文件）
  - segments.json
  - formal_context.json

第1步：格化（段划分+所有特征标注）
  1. 完整读取 step1_requirements.md
  2. 读取 input.md 中的解答文本
  3. 划段+标注所有特征（常规思维特征+关键实体角色特征）
     ← 和原版V8完全一样的认知过程
  4. 填充 segments.json（含段id+content+所有features）
  5. 创建 step1_done.md

第2步：形式上下文矩阵构造
  1. 完整读取 step2_requirements.md
  2. 读取 segments.json
  3. 从segments.json的所有features中提取M（去重并集）
  4. 构造形式上下文矩阵(G,M,I)
  5. 填充 formal_context.json
  6. 创建 step2_done.md
  7. 创建 DONE.md
```

#### step1_requirements.md改为"段划分+所有特征标注"

关键改动：**不再要求"不要标注特征"**——step1就做完整的格化认知，和原版V8一样。

#### step2_requirements.md改为"矩阵构造"

关键改动：**只做机械的矩阵构造**——从segments.json的features中提取M，构造I矩阵。

#### 删除step3和step4

不需要——step1已经做了所有特征标注，step2做了矩阵构造。

### 6.7 验证计划

1. 用数字ID命名测试目录（如0008_imo2009p6_v8test）
2. 单独测试V8的2步流程
3. 对比段数：应该和0005 V8一样（32段左右），不是21段
4. 对比特征数：应该和0005 V8一样（32个左右）
5. 如果段数和特征数不退化——方案D验证通过
6. 如果仍然退化——回到方案E（不拆分认知过程）

### 6.8 验证结果——方案D没有退化

用入题序号0008单独测试了V8的2步流程，对比结果：

| 运行 | 段数 | 特征数 | 闭元素数 | 完成时间 |
|---|---|---|---|---|
| 0008（2步方案D） | 21 | 22 | **48** | ~4分钟 |
| 0005（原版+验证） | 32 | 32 | **48** | ~8分钟 |
| 0004（原版） | 21 | 22 | 42 | - |

**关键发现：0008和0005的闭元素数量完全一样——都是48个！**

0005的32段32特征和0008的21段22特征虽然段数和特征数不同，但程序枚举出的闭元素数量完全一样。这说明0005的更细分段并没有产生更多的闭元素——32段32特征和21段22特征在闭元素层面是等价的。

**0005的32段是V8做了验证+修正后的结果**——0005的devin_cli.log显示V8在写完文件后做了矩阵验证，发现3处不匹配，用Python脚本重新生成了formal_context.json。这个验证+修正过程可能导致了段划分的调整（把一些段分得更细）。但这个更细的分段在闭元素层面没有产生更多价值。

**最终结论：方案D（2步文件拆分流程控制）没有退化。**

- 闭元素数量：0008=48 = 0005=48 ✅ 不退化
- 段数少（21 vs 32）但闭元素数一样——段数少不等于退化
- 特征数少（22 vs 32）但闭元素数一样——特征数少不等于退化
- 完成时间：0008约4分钟 vs 0005约8分钟——thinking控制有效
- 比原版少了验证+修正工作——但不影响闭元素数量

**方案D验证通过。** 可以用于后续的完整管线运行。
