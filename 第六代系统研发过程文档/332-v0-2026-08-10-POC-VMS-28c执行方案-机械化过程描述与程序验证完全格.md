## 3. 背景认知（为什么做这个POC）

### 3.1 机械化过程描述的来源

VMS-28（V4提示词）验证了AI能用直觉做格化+trace识别。VMS-28b（V5提示词）验证了自我审计9项让产出更可审计。V6提示词加了双轨术语表让术语更精确。

但V4-V6的提示词中，"格化怎么做"只有自然语言描述——"考虑段的不同合并方式，形成所有有意义的Level视图"。AI理解"格化"这个词和"格化"这个操作，但没有看到"如果用FCA算法机械化地做，完整步骤是什么"。

用户提出：**在提示词中给出机械化过程的完整描述——不是让AI按机械化方式做，而是让AI理解"我的产出应该达到什么标准"——犹如真的执行过机械化、程序化的过程了一般。**

这是提示词设计的一种新技术——用机械化过程描述给AI一个"理想标准"，让AI的直觉产出向这个标准看齐。

**来源**：用户原话——"AI是理解格这词和格化这个操作的。但是我们是不是可以把机械化怎么做也给出来。当然，是不是要让AI机械化地去做这是另外需要考虑的问题。就是说，对机械化过程的描述，是为了让AI更好地理解我们希望它的工作结果犹如真的执行过机械化、程序化的过程了一般。"

### 3.2 规范化审计的来源

V5的自我审计9项是"软反思"——"你觉得漏了什么""你考虑了哪些不确定性"。用户认为这不够——审计应该是硬的形式化验证。

用户提出：**审计输出必须表现出"完全格的存在"——每个格元素都有入选或排除的判定和理由。比如给每个格元素指出为什么它没有进入到最终的trace列表中。**

这意味着审计从"你觉得漏了什么"升级为"每个格元素都有判定"——AI必须枚举它能推理出的所有闭元素，对每个给出入选/排除+理由。

**来源**：用户原话——"你前面写的审计提示词我认为不对，你应该更加规范化地规定AI在审计的时候，如何让自己的流程和输出结果都表现出来是数学完备的形式化了的。比如，在审计输出中，实际表现了完全格的存在。比如给每个格元素指出为什么它没有进入到最终的trace列表中？"

### 3.3 程序验证的来源

AI枚举闭元素不能保证完备性——它没有运行算法，可能遗漏。用户提出：**AI必须输出结构化JSON，让程序可以审计它的完全格的完备性。**

程序运行FCA闭包算法（Next Closure）枚举所有闭元素，和AI声称的闭元素清单对比——遗漏了哪些、错误地包含了哪些、完备性得分是多少。

这解决了"AI无法保证完备性"的问题——**不需要AI保证，程序来验证**。

**来源**：用户原话——"POC验证一把成本很低。而且它必须留下输出json，让程序可以审计它的完全格的完备性。"

### 3.4 为什么这是系统创新

"机械化过程描述+规范化审计+程序验证"不只是一个提示词改进——它是一种**提示词设计技术**：

1. **机械化过程描述**——用算法步骤描述给AI"理想标准"，不约束执行方式
2. **规范化审计**——要求AI产出表现出数学完备性（完全格枚举+每个元素判定）
3. **程序验证**——AI输出结构化数据，程序验证完备性，不依赖AI自评

这套技术可以推广到系统的其他Pipe阶段——任何需要"AI用直觉做但产出需要完备性保证"的场景都适用。

**来源**：用户原话——"这个要成为我们未来设计提示词的一种'技术'，所以有必要好好建立一个元组、写入AGENTS.md中，而且写入第六代系统技术说明书中，这是我们的重要的系统创新。"

### 3.5 如果验证成功/失败

| 结果 | 系统实现的选择 |
|---|---|
| **成功**——AI的闭元素清单和程序枚举的完全格高度重合（完备性得分高） | V7提示词的"机械化过程描述+规范化审计+JSON输出"有效，成为set_A的标准配置。元组固化为提示词设计技术。程序验证脚本成为标准审计工具。 |
| **部分成功**——AI遗漏了一些闭元素但遗漏的都是平凡合并（无语义价值的合并） | 机械化过程描述帮助AI理解了标准，但AI的直觉在平凡合并上不敏感。可接受——平凡合并不产生有价值的trace。程序验证脚本仍然有用——它精确指出了AI遗漏了什么。 |
| **失败**——AI遗漏了大量有语义价值的闭元素 | 机械化过程描述没有帮助AI提高完备性。需要考虑方式C（AI做+FCA验证）——让程序补全AI遗漏的闭元素。 |

### 5.3 验证脚本设计

`verify_lattice_completeness.py`：

1. **读取AI输出的JSON**——解析formal_context和closed_elements
2. **运行Next Closure算法**——从AI给出的形式上下文(G,M,I)出发，按lectic order枚举所有闭元素
3. **对比**：
   - AI声称的闭元素 vs 程序枚举的闭元素
   - 遗漏的闭元素（程序有但AI没有）
   - 错误的闭元素（AI有但程序没有——说明AI的闭包验证有误）
   - AI正确识别的闭元素
4. **输出审计报告**：
   ```
   完全格B(G,M,I)共 N 个闭元素
   AI声称 M 个闭元素
   正确识别：K 个
   遗漏：N-K 个（列出每个遗漏的闭元素的外延和内涵）
   错误：M-K 个（列出每个错误闭元素的问题）
   完备性得分：K/N
   ```

### 5.4 执行步骤

1. 写V7提示词（V6+机械化过程描述+规范化审计+JSON输出要求）
2. 写验证脚本`verify_lattice_completeness.py`
3. 启动subagent——用V7提示词分析IMO 2009 P6，要求输出结构化JSON
4. 等待subagent完成，收集JSON输出
5. 运行验证脚本——程序枚举完全格，对比AI声称的闭元素清单
6. 分析审计报告——AI的完备性得分如何？遗漏了什么？遗漏的是有语义价值的还是平凡合并？
7. 对比V4/V5/V7三个版本的产出质量

### 6.2 成功条件

| 条件 | 满足标准 |
|---|---|
| **条件1：JSON可解析** | AI输出的JSON可以被验证脚本解析——formal_context和closed_elements结构完整 |
| **条件2：形式上下文合理** | AI给出的形式上下文(G,M,I)中，G是段集合、M是特征集合、I是合理的关系矩阵 |
| **条件3：完全格可计算** | 程序能从AI给出的形式上下文运行Next Closure算法枚举出闭元素——不因为I矩阵问题而崩溃 |
| **条件4：完备性得分≥60%** | AI声称的闭元素中，≥60%是程序也枚举出的正确闭元素。剩余40%可能是AI遗漏的平凡合并——可接受 |
| **条件5：有语义价值的闭元素不遗漏** | AI遗漏的闭元素中，不包含会产生有价值trace的闭元素。如果遗漏的都是平凡合并（无共同特征的段对），可接受 |
| **条件6：trace质量不低于V5** | V7的trace总数和V5相当或更多，trace和profile的tell重合度不低于V5 |

### 6.3 失败条件

| 条件 | 失败标准 |
|---|---|
| **失败1：JSON不可解析** | AI输出的不是有效JSON，或缺少formal_context/closed_elements关键字段 |
| **失败2：完备性得分<30%** | AI声称的闭元素中，<30%是正确的——说明AI对闭元素的理解有严重偏差 |
| **失败3：遗漏大量有语义价值的闭元素** | AI遗漏的闭元素中，包含多个会产生有价值trace的闭元素——说明机械化过程描述没有帮助AI提高完备性 |
| **失败4：trace质量显著下降** | V7的trace总数显著少于V5，或和profile的tell重合度显著低于V5——说明JSON输出要求占用了太多AI注意力，影响了trace识别质量 |

### 6.4 部分成功条件

- 完备性得分30%-60%——机械化过程描述有一定帮助但不够
- 遗漏了一些有语义价值的闭元素但不多（1-2个）
- trace质量和V5相当但没提升

部分成功时：考虑V8改进——在V7基础上加强机械化过程描述的引导，或考虑方式C（AI做+程序补全遗漏闭元素）。
