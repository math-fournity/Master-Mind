## 1. 结论

解题侧不应在“tmux 交互式”和“非交互封存式”中二选一。两者解决的是不同问题：

| 运行档 | 主要目的 | 人可以看什么 | 能否直接作为确认性证据 |
|---|---|---|---|
| `INTERACTIVE_TMUX_DEBUG` | POC、调试、运行时健康检查 | 实时 thinking spin、工具调用、阶段文件、卡点 | 默认不能；人工输入会产生干预 |
| `SEALED_NONINTERACTIVE` | 可重放的资格测试和证据生产 | stdout/stderr、export、输出和 receipt | 符合预注册、资源和完整性条件时可以 |

双运行档必须共享同一个语义合同，但拥有不同的 execution profile、receipt 和证据用途。

---

## 2. 入题侧 tmux 经验的真实价值

`system/vein_analysis.py` 的交互分支会为每个 V5/V7/V8/V10 角色建立 detached tmux session，然后运行 Devin TUI。它对 POC 非常有价值：

1. 不用等整个调用结束，就能判断模型是在思考、读文件、调工具还是已经卡死；
2. 可以亲眼看到提示词的某一段是否造成误解；
3. 可以区分“模型认知失败”、“工具权限失败”、“文件契约不清”与“载体限流”；
4. 系统检查者可以在四个并发角色间切换，而不是前台等待；
5. 对时间较长的 thinking，实时可观测本身就是调试基础设施。

这些价值不应被“最终还是要封存 trajectory”所取代。实时检查和事后重放是两种不同的可观测性。

## 3. 不能照搬的入题侧缺口

入题侧当前 tmux 分支的实现存在两个需要修复的工程点：

### 3.1 shell command 拼接

当前实现把 `cd`、路径和 prompt 拼成 tmux 的 shell command。解题侧不应让题面、prompt 或任意外部文本进入 shell 字符串。

解题侧应用一个冻结 launcher，只向 tmux 传入：

```text
validated session slug
+ fixed launcher executable
+ opaque attempt/spec ID
```

全部长 prompt、题面、角色规则和输出路径均先写入受控工作目录，launcher 再以结构化 argv 调用 Devin。

### 3.2 DONE 与 export 的竞态

历史 0013 运行中，5 个角色都有 `DONE.md`，但只有 4 份 trajectory；V8 的 export 缺失。根因是主管线看到 DONE 就 kill tmux，而 Devin 可能尚未完成退出阶段的 `--export`。

解题侧的 tmux profile 不得把 DONE 当作 kill 信号。

## 4. 共享的语义合同

两种运行档必须共享：

```yaml
role_asset_hash:
task_hash:
input_manifest_hash:
requested_model_uid: glm-5-2
normalized_effort: high
permission_mode: dangerous
sandbox_requested: false
session_policy: fresh_only
resume_or_continue: forbidden
expected_output_name:
done_contract: "<output> SHA256=<64hex>"
export_required: true
retry_policy:
resource_budget:
```

因此一份 POC 输入可以先在 tmux debug 档观察、修订；修订完后必须发布新的 asset/profile 版本，再用 sealed 档重新运行。不能把已经被人工输入干预的 tmux session 换个名字就当成独立证据。

## 5. `INTERACTIVE_TMUX_DEBUG` 合同

### 5.1 作用

该档的目标是让开发者/检查者可以：

- `tmux attach -t <session>` 实时看 thinking spin；
- 观察当前是否在读取、写入、执行或等待权限；
- 在不输入任何键的情况下做健康检查；
- 在明确标为调试干预时，手动输入修复建议并把该 run 留在 development lane。

### 5.2 必须记录的事件

```yaml
TmuxDebugReceipt:
  attempt_id:
  session_name:
  tmux_server_identity:
  created_at:
  attached_observer_events:
    - observer_id:
      attached_at:
      detached_at:
      input_bytes_sent:
  pane_capture_refs_and_hashes: []
  model_output_ref_and_hash:
  done_observed_at:
  exit_requested_at:
  process_exited_at:
  export_available_at:
  human_intervention: NONE | READ_ONLY_OBSERVATION | INPUT_SENT
  evidence_lane: DEVELOPMENT_ONLY | ELIGIBLE_IF_PREREGISTERED_READ_ONLY
```

attach 本身不能被当作干预，但 supervisor 必须能证明该 observer 没有发送按键。做不到时，一律标 `READ_ONLY_OBSERVATION_UNPROVEN`，该 run 不进确认性证据。

## 6. tmux 安全退出握手

tmux debug 档要同时满足“可看”和“export 完整”，需要显式的三步终止协议：

```text
1. Model commit
   expected-output.json + hashed DONE.md

2. Graceful Devin exit
   supervisor 不 kill tmux；
   使用经资格测试的 graceful-exit 动作，让 Devin 自己刷新 export

3. Seal
   Devin PID 已退出
   export 存在、JSON 可解析、model UID 一致
   output/DONE hash 一致
   然后才关闭空 tmux session并原子封存 bundle
```

graceful-exit 的精确键序列或 CLI 命令不能凭记忆写死。它必须使用一个不含数学任务的专用 canary 进行资格测试，同时验证不丢 output、export 和 exit code。

超时时先封存 pane snapshot 和 partial workspace，再 TERM，最后才 KILL。KILL 的 run 只能标为 `INCONCLUSIVE_PROTOCOL` 或预注册的 timeout 结果，不得根据 pane 中“看起来快做完了”升级。

## 7. 实时健康检查

不应靠开发者记得手动 attach 才有可观测性。supervisor 必须定期生成机械健康状态：

```yaml
RoleHealthSnapshot:
  attempt_id:
  observed_at:
  tmux_session_present:
  pane_process_present:
  devin_process_present:
  elapsed_seconds:
  workspace_files:
  output_candidate_present:
  done_candidate_present:
  export_candidate_present:
  last_pane_activity_at:
  process_cpu_sample:
  verdict: RUNNING | POSSIBLE_STALL | DONE_WAITING_EXIT | EXITED_WAITING_EXPORT | TERMINAL
```

这份 snapshot 只记运行健康，不从 thinking 文本推断数学正确性。数学判定仍在运行后由独立 evaluator/Judge 完成。

## 8. 并发与调试布局

入题侧的四角色并发使 tmux 特别有价值。解题侧也应支持角色池，但首次资格测试不直接继承入题侧并发数：

1. 先做 1 个 tmux debug canary；
2. 再做 2 个角色并发，检查 session/workspace/export 隔离；
3. 再逐步提高到角色池上限；
4. 仍受 Devin carrier-global limiter 统筹，避免与题海 Solver 或其他认知角色互相饿死；
5. 每个 tmux session 仍是独立 attempt/session/workspace/export，不共享可变文件。

## 9. 实现顺序

```text
TMUX-0 只读能力回源
  └─ 确认tmux版本、capture/attach能力、Devin TUI 安全退出行为

TMUX-1 单角色无数学 canary
  └─ 写小文件、hashed DONE、graceful exit、export、pane capture

TMUX-2 单角色实时健康观察
  └─ 人只读attach，证明无input bytes

TMUX-3 双角色隔离与并发
  └─ session/workspace/export 不交叉

TMUX-4 与 sealed Popen 档语义对照
  └─ 同一冻结角色资产的输出合同和evaluator 同构

TMUX-5 接入解题侧runbook
  └─ 开发/调试默认可观；确认性运行默认sealed
```

任何一步失败都保留物证，不在同一 canary ID 中试键序列试到通过。
