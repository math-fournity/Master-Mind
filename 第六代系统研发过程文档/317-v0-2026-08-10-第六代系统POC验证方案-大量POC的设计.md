## 0. 为什么需要大量POC验证

第六代系统讨论了从303号到316号共14份文档，涉及：
- 非局部trace的正式化（303/305/309号）
- FCA数学基础的对接（304号）
- 并发Telling AI方案（311号）
- 两个核心问题——Trace识别与Trace→Tell匹配（312号）
- Tell分类学研究（313号）

- 理想化工作过程规范化描述（316号）

这些讨论建立了理论框架，但**每个关键环节都需要POC验证**——不能假设理论正确，必须用实验证明。

第五代系统的POC验证（VMS-0到VMS-10）验证了核心循环、可扩展性、Pattern闭环、跨域迁移、动态引导胜率、hint端、tell端去特化、小概念标记分辨。第六代系统需要新的POC验证新的能力。

## 1. POC验证的层次组织

第六代系统的POC验证按三个层次组织：

```
第一层：基础能力验证（单点能力）
  ├── 非局部trace识别能力
  ├── 推理脉络格化能力
  └── Tell分类学基础能力

第二层：管线验证（多步骤组合）
  ├── 脉络分析管线（步骤1-4）
  ├── 并发Telling AI（步骤4的并发实现）
  └── Parser AI（步骤5过程B）

第三层：系统验证（端到端）
  ├── 端到端工作流（7阶段循环）
  ├── 引导树妖娆生长
  └── tell库持续增长闭环
```

每个层次依赖前一个层次的验证结果——第一层验证通过后才进入第二层，第二层验证通过后才进入第三层。

## 2. 第一层：基础能力验证

### POC-VMS-11：非局部trace识别——用费马大定理证明作为脉络

**验证什么**：分析AI能否在中间Level识别出非局部trace

**怎么验证**：
1. 取费马大定理的证明过程作为脉络（304号§8.11已做过手工分析，可作为参照）
2. 用分析AI对证明过程做非局部分析——不只提取整体级三元组，还要在中间Level识别跨段模式
3. 检查分析AI能否识别出以下非局部trace：
   - "反证法+归约"（整体级）
   - "跨域构造+异常识别"（中间级——模形式与椭圆曲线的对应）
   - "探索-诊断-修复循环"（中间级——Frey曲线→Ribet→Wiles的递进）
   - "同构之桥"（中间级——模形式和椭圆曲线之间的对应关系）

**预期结果**：
- 分析AI能识别出至少2个非局部trace
- 识别出的非局部trace和304号§8.11手工分析的结果有重合
- 分析AI识别出了304号§8.11没有手工识别出的非局部trace（说明系统化方法比手工分析更全面）

**和314号问题的关系**：验证314号问题1的识别侧——非局部trace识别能力

**关键判定**：如果分析AI只输出一个三元组（和第五代Pipe 0一样），说明非局部trace识别能力未建立——这是失败。必须识别出跨段模式才算成功。

### POC-VMS-12：推理脉络格化——FCA格遍历算法

**验证什么**：能否用FCA格遍历算法系统化地找出所有有意义的Level视图

**怎么验证**：
1. 取一个有10-20个推理步骤的thinking（从现有455个profile中选一个中等长度的）
2. 把推理脉络转化为FCA形式上下文（对象=脉络的段，属性=段特征）
3. 用Next Closure或In-Close算法枚举闭元素（有意义的Level视图）
4. 检查枚举出的Level视图：
   - 数量是否远小于2^(n-1)（说明算法有效过滤了无意义的合并）
   - 每个Level视图是否有段特征（说明合并是有意义的）
   - 是否覆盖了所有"应该有的"中间Level（不漏）

**预期结果**：
- 枚举出的Level视图数量远小于2^(n-1)（如10个 vs 2^19=524288）
- 每个Level视图有明确的段特征
- 覆盖了手工分析能想到的所有有意义的中间Level

**和314号问题的关系**：验证314号问题2——推理脉络格化能力

**关键判定**：如果枚举出的Level视图数量接近2^(n-1)，说明"有意义的合并"定义不够好，没有有效过滤——这是失败。如果枚举出的Level视图漏掉了手工分析能想到的中间Level，说明算法不完备——也是失败。

### POC-VMS-13：Tell分类学基础——现有4164个tell的分类现状

**验证什么**：现有4164个tell的分类现状是什么，能否在此基础上建立分类体系

**怎么验证**：
1. 查数据库，统计现有4164个tell的元数据：
   - 有没有domain标签？
   - 有没有大概念拓扑标签（problem_type/ai_method_type/gap_type）？
   - 972个"全局tell"是什么含义？是否对应非局部tell？
   - 来源分布（omni_math/other/compfiles/matharena）是否暗示domain分类？
2. 尝试用313号的四层结构（domain→trace类型→段结构模式→具体概念）对现有tell做初步分类
3. 检查分类的覆盖率——多少tell能被分类？多少tell无法分类？

**预期结果**：
- 现有tell有大概念拓扑标签（第五代Pipe 0的产物）
- 972个"全局tell"不是非局部tell（因为现有分析方法不做非局部分析）——确认314号问题1
- 现有tell可以按domain做初步分类（从来源或大概念拓扑推断）
- 局部tell的分类覆盖率较高，非局部维度为空（因为库中没有非局部tell）

**和314号问题的关系**：验证314号问题3的基础——现有tell的分类现状

**关键判定**：如果972个"全局tell"实际上是非局部tell（有非局部特征），那314号问题1的判断需要修正——库中可能已有一些非局部tell。如果972个"全局tell"只是整体级tell（最粗Level的三元组），那314号问题1的判断正确——库中没有真正的非局部tell。

## 3. 第二层：管线验证

### POC-VMS-14：脉络分析管线——步骤1-4完整管线

**验证什么**：脉络分析管线（步骤1-4）能否端到端运行

**怎么验证**：
1. 取一个推理AI的thinking（从现有实验中选一个）
2. 走完整的步骤1-4：
   - 步骤1：分析出思维脉络
   - 步骤2：格化脉络→所有Level视图
   - 步骤3：从局部到整体识别trace
   - 步骤4：trace进入Telling AI并发分类分析
3. 检查管线的输出——trace集合 + trace→tell匹配结果

**预期结果**：
- 管线能端到端运行，不中断
- 产出局部trace和非局部trace
- Telling AI能对trace做匹配（可能匹配到tell，可能匹配不到）

**和316号的关系**：验证316号§5的脉络分析管线

**关键判定**：如果管线在某一步中断（如步骤2格化失败、步骤4 Telling AI无法运行），说明管线不完整——需要修复中断点。

**依赖**：POC-VMS-11（非局部trace识别）和POC-VMS-12（脉络格化）必须先通过。

### POC-VMS-15：并发Telling AI——多个Devin CLI实例并发匹配

**验证什么**：多个Devin CLI实例能否在对应分类目录中并发做trace→tell匹配

**怎么验证**：
1. 建立Tell分类学的目录结构（至少2-3个domain目录，每个目录有AGENTS.md存放该分类的tell）
2. 从POC-VMS-14的管线产出trace集合
3. 在多个目录中并发启动Devin CLI实例
4. 每个Devin CLI加载自己目录的AGENTS.md，遍历tell，判断是否命中trace
5. 检查并发运行的结果——各Telling AI返回的trace→tell匹配结果

**预期结果**：
- 多个Devin CLI实例能并发运行
- 每个实例能加载自己目录的AGENTS.md
- 每个实例能以可审计方式遍历tell做匹配
- 各实例返回结果不需要汇总——各自直接返回

**和316号的关系**：验证316号§3.3的Telling AI和§6阶段4

**关键判定**：如果Devin CLI实例无法并发运行，或无法加载AGENTS.md，或遍历tell不可审计——说明工程实现有问题。

**依赖**：POC-VMS-13（Tell分类学基础）必须先通过——需要目录结构和AGENTS.md。

### POC-VMS-16：Parser AI——从外部解答记录识别新(tell,hint)

**验证什么**：Parser AI能否从外部解答记录中识别trace，没匹配到tell的trace能否成为新tell并建立(tell,hint)

**怎么验证**：
1. 取一个外部题目+解答记录（从数学竞赛题库中选一个有完整解答的）
2. Parser AI用脉络分析管线（步骤1-4）分析解答记录
3. 步骤5分叉到过程B：
   - 匹配到tell → 确认匹配
   - 没匹配到tell → trace成为新tell → 建立新的(tell,hint)
4. 检查新(tell,hint)是否合理——tell是否可泛化、hint是否正确
5. 把新(tell,hint)存入对应目录的AGENTS.md

**预期结果**：
- Parser AI能从解答记录中识别出trace
- 没匹配到tell的trace能成为新tell
- 新tell的(tell,hint)对合理——tell可泛化、hint正确
- 新(tell,hint)存入了对应目录的AGENTS.md

**和316号的关系**：验证316号§3.4的Parser AI和§5.2过程B

**关键判定**：如果Parser AI识别出的trace全是局部trace（和第五代一样），说明Parser AI没有做非局部分析——失败。如果新tell不可泛化（只适用于这一道题），说明tell的去特化没做好——失败。

**依赖**：POC-VMS-14（脉络分析管线）必须先通过。

## 4. 第三层：系统验证

### POC-VMS-17：端到端工作流——完整7阶段循环

**验证什么**：完整的7阶段循环能否端到端运行

**怎么验证**：
1. 选一道竞赛题（bare AI做不出来，但有已知正确解答）
2. 启动第一个推理AI（裸做题）
3. 走完整的7阶段循环：
   - 阶段1：推理AI探索
   - 阶段2：思维脉络分析（格化）
   - 阶段3：trace识别（局部到整体）
   - 阶段4：并发找tell
   - 阶段5：trace→tell匹配
   - 阶段6：tell→hint查询
   - 阶段7：引导树填充→启动新推理AI
4. 循环继续直到停机（某条脉络到达正确解答）或穷尽

**预期结果**：
- 7阶段循环能完整转一圈（三个推动关系都成立）
- 引导树有节点、有边、有分叉
- 解题树记录了探索过程
- 最终要么solved（某条脉络到达正确解答），要么exhausted（所有方向探索完）

**和316号的关系**：验证316号§6的完整工作过程

**关键判定**：如果循环只转了半圈（只有解题树在长，引导树没有新边），说明推动关系3不成立——失败。如果引导树只有一条路径没有分叉，说明树不够妖娆——需要分析原因（tell库不够？trace识别不够？）。

**依赖**：POC-VMS-14（脉络分析管线）、POC-VMS-15（并发Telling AI）必须先通过。

### POC-VMS-18：引导树妖娆生长——多Level多方向分叉

**验证什么**：引导树能否在不同Level上快速生出更多探索方向

**怎么验证**：
1. 在POC-VMS-17的基础上，观察引导树的生长过程
2. 统计：
   - 引导树的节点数、边数、深度、分叉数
   - 不同Level上的分叉分布（局部trace在单节点上开新边，非局部trace在段级位置开新边）
   - 方向数随时间增长曲线
3. 和第五代系统的引导树做对比（如有第五代的实验数据）

**预期结果**：
- 引导树有多个分叉（不只一条路径）
- 分叉分布在不同Level上（不只在最粗Level）
- 方向数随时间快速增长（妖娆）
- 比第五代系统的引导树更妖娆（更多分叉、更多Level）

**和316号的关系**：验证316号§1的"引导树妖娆生长"

**关键判定**：如果引导树只有最粗Level的分叉（和第五代一样），说明非局部trace没有产出新方向——失败。如果引导树比第五代更妖娆，说明第六代的非局部trace识别和并发Telling AI有效。

**依赖**：POC-VMS-17（端到端工作流）必须先通过。

### POC-VMS-19：tell库持续增长闭环——过程A→过程B→过程A

**验证什么**：过程A产出的孤悬trace能否启发Parser AI（过程B），过程B验证后的新tell能否用于过程A的未来匹配

**怎么验证**：
1. 运行一次POC-VMS-17（过程A），收集孤悬trace（没匹配到tell的trace）
2. 运行POC-VMS-16（过程B），Parser AI参考孤悬trace从外部解答记录中识别新(tell,hint)
3. 把新(tell,hint)存入对应目录的AGENTS.md
4. 再运行一次POC-VMS-17（过程A），检查这次能否匹配到上一步新增的tell

**预期结果**：
- 过程A产出孤悬trace
- Parser AI参考孤悬trace从外部解答记录中识别出相同模式
- 相同模式被验证后升级为正式tell
- 第二次过程A能匹配到新增的tell（之前是孤悬trace，现在有tell了）

**和316号的关系**：验证316号§5.4的两个过程形成的闭环

**关键判定**：如果第二次过程A仍然匹配不到新增的tell，说明闭环断裂——可能是新tell的分类不对（放错了目录），或trace识别不一致（两次识别同一脉络产出不同trace）。

**依赖**：POC-VMS-16（Parser AI）和POC-VMS-17（端到端工作流）必须先通过。
