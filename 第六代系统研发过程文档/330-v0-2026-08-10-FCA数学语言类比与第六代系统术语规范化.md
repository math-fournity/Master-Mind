## 1. FCA的标准术语体系

### 1.1 基础结构

FCA（Formal Concept Analysis，形式概念分析）由Bernhard Wille于1979年提出，是应用格论的一个分支。标准教材是Ganter & Wille《Formal Concept Analysis: Mathematical Foundations》（Springer）。

FCA的起点是**形式上下文**（formal context）：

**定义1.1**（形式上下文）：三元组 (G, M, I)，其中G是**对象集**（objects），M是**属性集**（attributes），I ⊆ G × M是**二元关系**（incidence relation）。(g, m) ∈ I读作"对象g具有属性m"。

### 1.2 概念形成算子

从形式上下文出发，定义两个**概念形成算子**（concept-forming operators）：

**定义1.2**（概念形成算子）：
- 对A ⊆ G：A' = {m ∈ M | ∀g ∈ A, (g, m) ∈ I}（A中所有对象共有的属性集）
- 对B ⊆ M：B' = {g ∈ G | ∀m ∈ B, (g, m) ∈ I}（具有B中所有属性的对象集）

这两个算子构成**Galois连接**（Galois connection）：

**定义1.3**（Galois连接）：两个偏序集(P, ≤)和(Q, ≤)之间的映射对φ: P→Q, ψ: Q→P，如果满足φ(p) ≥ q ⟺ p ≥ ψ(q)，则称为Galois连接。

FCA中，(·)'和(·)'在(℘(G), ⊆)和(℘(M), ⊇)之间构成Galois连接。

### 1.3 形式概念与概念格

**定义1.4**（形式概念）：(A, B)是形式上下文(G, M, I)的**形式概念**（formal concept），如果A' = B且B' = A。A称为概念的**外延**（extent），B称为概念的**内涵**（intent）。

**定义1.5**（概念格）：所有形式概念的集合B(G, M, I)在偏序(A₁, B₁) ≤ (A₂, B₂) ⟺ A₁ ⊆ A₂（等价于B₁ ⊇ B₂）下构成**概念格**（concept lattice），记作B(G, M, I)。

**关键定理**（概念格的基本定理）：概念格B(G, M, I)是完全格。外延集{A | (A, B) ∈ B(G, M, I)}和内涵集{B | (A, B) ∈ B(G, M, I)}各自构成**闭包系统**（closure system）。

### 1.4 闭包算子与闭包系统

**定义1.6**（闭包算子）：偏序集(P, ≤)上的映射c: P → P，满足三条公理：
1. **扩展性**：x ≤ c(x)
2. **单调性**：x ≤ y ⟹ c(x) ≤ c(y)
3. **幂等性**：c(c(x)) = c(x)

**定义1.7**（闭包系统）：P的子集族A是闭包系统，如果：
1. P ∈ A
2. 对交运算封闭（A中任意子集族的交集仍在A中）

**关键定理**（闭包算子与闭包系统的对应）：
- 给定闭包系统A，定义ϕ_A(X) := ∩{A ∈ A | X ⊆ A}，得到闭包算子
- 给定闭包算子ϕ，所有闭元素{ϕ(A) | A ⊆ G}构成闭包系统
- 闭包系统总是完全格

FCA中，复合算子(·)''（先取属性再取对象，或先取对象再取属性）是闭包算子。闭元素就是形式概念的外延（或内涵）。

### 1.5 Hasse图

**定义1.8**（Hasse图）：格L的Hasse图是偏序关系(L, ≤)的可视化——如果x < y且不存在z使得x < z < y，则画一条从x到y的边。最下层是格的最小元素，最上层是格的最大元素。

概念格的Hasse图是FCA的标准可视化工具——每个节点是一个形式概念，边表示subconcept-superconcept关系。

### 1.6 格遍历算法

**Next Closure算法**（Ganter 1984）：
- 按**lectic order**（字典序）枚举所有闭元素（形式概念的内涵）
- 保证完备性——一个不漏
- 是闭包系统遍历的经典算法

**In-Close算法**（Andrews 2009）：
- 更快的批量计算版本
- 按in-closure方式批量计算闭包

**Close-by-One算法**（Kuznetsov 1993）：
- 按深度优先遍历概念格

### 1.7 规模化工具

**Iceberg Lattice**（冰山格）：
- 只保留支持度≥阈值的概念
- 应对大规模形式上下文

**Frequent Concept Lattice**（频繁概念格）：
- 只计算高频概念

**Partition-based Scaling**（分片缩放）：
- 分片处理超大规模形式上下文

### 1.8 其他重要概念

**join-irreducible / meet-irreducible元素**：
- 格中不能表示为严格小于它的元素的join（supremum）的元素
- 对应概念格中"最小不可分"的概念

**Object/Attribute intent**：
- 对象g的属性集g'（g''是包含g的最小概念外延）
- 属性m的对象集m'（m''是包含m的最小概念内涵）

**Implication**（蕴涵）：
- A → B：所有具有A中所有属性的对象也具有B中所有属性
- 是FCA中规则发现的基础

**Stem base / Duquenne-Guigues base**：
- 最小蕴涵基——所有蕴涵的最小生成集

## 3. 对照分析——关键差距

### 3.1 最大的差距：没有明确的形式上下文定义

FCA的起点是形式上下文(G, M, I)——对象集G、属性集M、关系I。

第六代系统中，**形式上下文是隐含的**：
- 对象G = 脉络的段
- 属性M = 段特征
- 关系I = 段具有某个特征

但这个形式上下文**从未在任何提示词或代码中被明确定义**。V5提示词中用了"格化"、"Level视图"、"闭元素"等FCA术语，但没有说"形式上下文是什么"。

**后果**：subagent看到"格化"时，不知道形式上下文是什么，不知道闭包算子是什么，只能靠直觉理解"格化"是什么意思。这违反了自包含原则。

### 3.2 "格化"的模糊性

"格化"在系统中出现60+次，是核心术语。但它的定义是模糊的：

- 314号说"格化是三个核心问题之一"
- V5提示词说"做'格化'和'全Level Trace识别'"
- pipes.py说"step_2_grid_vein"

如果用FCA语言规范化，"格化"就是：

> **格化** = 给定形式上下文(G, M, I)（G=段，M=段特征，I=段具有特征），计算概念格B(G, M, I)的所有形式概念。

这个定义是精确的、自包含的、可验证的。

### 3.3 "Level视图"和"形式概念"的对应

V5提示词中"Level视图"的定义是：

> 脉络在某个Level上的看法。最细Level每个段是一个节点，最粗Level整个脉络是一个节点，中间Level几个段合并成一段。

如果用FCA语言规范化：

> **Level视图** = 形式上下文(G, M, I)的一个**形式概念** (A, B)。A是外延（合并的段集合，即merged_segments），B是内涵（这些段的共同特征，即view_features）。最细Level对应最细概念（每个段是一个外延），最粗Level对应最粗概念（所有段是一个外延），中间Level对应中间概念。

这个对应关系在types.py的LevelView dataclass中已经隐含了——merged_segments对应外延，view_features对应内涵——但从未被明确说出。

### 3.4 "去特化"和FCA的scaling

"去特化"在系统中出现多次，定义是：

> tell的去特化——从Level 0（题目特化）提升到Level 1（拓扑结构）

FCA中对应的概念是**缩放**（scaling）——把一个多值属性转换为多个二元属性，使得属性更抽象、更可泛化。

但"去特化"从未被定义为FCA的scaling。这导致subagent看到"去特化"时不知道这是FCA的scaling操作。

### 3.5 "trace"和"tell"的FCA对应

| 工程术语 | FCA对应 | 差距 |
|---|---|---|
| trace | 形式概念的内涵B | trace强调"可泛化的思维模式"，内涵B是"属性闭包"——两者有语义差距 |
| tell | 跨上下文概念 | tell是"trace去特化后存入库"，跨上下文概念是"在多个形式上下文中都出现的形式概念"——两者有结构差距 |
| hint | 蕴涵A → B | hint是"tell对应的提示"，蕴涵是"如果A则B"——两者有方向差距 |

这些差距不是错误——工程术语有自己的语义（trace/tell/hint强调"思维模式"和"引导"，FCA术语强调"数学结构"）。但规范化时需要明确说出对应关系和差距。

### 3.6 "看法空间"和"划分格"的gap

303号§14已经指出了这个gap：

> FCA处理的是对象-属性关系（对象集G、属性集M、关系I⊆G×M）。tell识别处理的是序列的连续划分（303号§13说的看法空间）。这两者的结构不同——FCA的Galois连接来自对象-属性的二元关系，看法格来自序列的划分。

这个gap意味着：**不能直接套用FCA的闭包算子定义到看法空间上**。需要把FCA的框架调整到序列划分的场景上——这正是VMS-28/29/30的POC要验证的（方式A：AI做全部 / 方式B：脚本做格化 / 方式C：AI做+FCA验证）。

VMS-28验证了方式A成功——AI可以不依赖FCA算法直接做格化。但这不意味着FCA语言没有用——FCA语言提供了**精确的术语体系**，即使算法不直接使用。

## 4. 规范化建议

### 4.1 建议A：在提示词中建立术语表

每个提示词文件开头建立**术语表**，定义提示词中用到的所有术语。术语表用FCA标准定义，同时给出工程对应。

**术语表模板**：

```
═══════════════════════════════════════════════════════════════════════
术语表（本提示词中用到的所有术语定义）
═══════════════════════════════════════════════════════════════════════

形式上下文 (formal context) (G, M, I)：
  三元组——G是对象集（本题中=脉络的段），M是属性集（本题中=段特征），
  I ⊆ G × M是关系（段具有某个特征）。

形式概念 (formal concept) (A, B)：
  A ⊆ G是外延（合并的段集合），B ⊆ M是内涵（这些段的共同特征），
  满足A' = B且B' = A。在本提示词中称为"Level视图"。

概念格 (concept lattice) B(G, M, I)：
  所有形式概念的集合，按包含关系排序。在本提示词中"格化"就是计算概念格。

闭包算子 (closure operator) c: P → P：
  满足扩展性(x≤c(x))、单调性、幂等性的算子。闭元素(不动点)就是形式概念。

Hasse图：
  概念格的可视化——最下层是最细概念（每个段独立），最上层是最粗概念（所有段合并）。

trace：
  形式概念的内涵B——一个可识别的思维模式的属性集。
  在本提示词中，trace是"从某个Level视图上识别出的可泛化思维模式"。

去特化：
  FCA的缩放(scaling)——从具体属性提取抽象属性。
  在本提示词中，"去特化"是"把trace从题目特化的描述提升为可泛化的描述"。

═══════════════════════════════════════════════════════════════════════
```

## 7. 一个关键判断

用户的直觉是对的——用FCA的数学语言规范化工程术语是有价值的。但规范化的层面是**术语**，不是**算法**。

**术语层面**：FCA提供了精确的数学定义。把"格化"定义为"计算概念格"，把"Level视图"定义为"形式概念"，让提示词更清晰、更自包含。这是有价值的。

**算法层面**：VMS-28验证了AI可以不依赖FCA算法直接做格化。FCA的Next Closure/In-Close算法不需要在系统中实现。这是独立的工程决策。

两层是独立的——术语规范化不意味着算法实现，算法选择不影响术语规范化。
