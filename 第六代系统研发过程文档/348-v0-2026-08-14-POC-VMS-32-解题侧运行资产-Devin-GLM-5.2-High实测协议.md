# POC-VMS-32：解题侧运行资产 Devin GLM-5.2 High 实测协议

> 状态：`PREREGISTERED`  
> 日期：2026-08-14  
> 范围：解题侧脉络分析的三个认知角色运行资产  
> 明确排除：入题侧代码、入题侧运行资产、数据库、真实 Solver、参考答案、Tell/Hint 干预

---

## 1. 为什么需要这次 POC

POC-VMS-31 只证明了：给定严格的 `ReasoningTrajectory`，确定性程序能够保留事件 DAG、折返、跨分支复用、合流和 FCA/RCA-style 结构。它没有证明自然语言 Solver 轨迹能被认知角色可靠地转换为该对象，也没有证明当前三份 AGENTS 运行资产能够被真实载体执行。

本 POC 只回答一个更小的问题：

> 在完全隔离、无参考答案、单次调用、不允许为了通过而重试的条件下，Devin CLI 的 `glm-5-2`（catalog 显示 `GLM-5.2 High`）能否分别执行 Event Extractor、State Normalizer 和 Trace Auditor 三个角色？

这是一轮 `authoring_calibration_only / component_test`，不是未见 holdout，也不支持生产能力、规模能力或端到端解题效果主张。

## 3. 信息隔离

每个角色获得一个全新工作目录。工作目录只包含：

1. 该角色对应的冻结 `AGENTS.md`；
2. 该组件允许看到的 problem/input/glossary；
3. 一份不含认证信息的专用 Devin 配置；
4. 一份只描述文件名和任务边界的 `TASK.md`。

下列内容不得进入工作目录：

- `gold.*`、`expected.*` 或 evaluator 代码；
- 参考解答、答案 key 或后来成功的 Solver 轨迹；
- Tell/Hint 干预文本；
- `system/assets/vein_analysis/` 及任何入题侧 AGENTS；
- 其他角色的输出（除非该输出就是本角色预冻结的合法组件输入）；
- repo 的 `.env`、数据库凭据或生产状态。

调用完成后，runner 才能在模型不可见的 evaluator 环境中加载 gold 并评分。

## 4. 三个独立组件实验

### 4.1 E1 · Event Extractor

输入：一个校准用数学问题，以及一条自然语言 Solver 轨迹。轨迹显式包含：

- 从根处开启失败分支；
- 失败后保留一个局部恒等式；
- 回到原命题但带着新信息；
- 开启另一个分支；
- 第三个分支复用失败分支遗产；
- 两个分支的结果发生真正合流；
- 最终结论。

主判据：

```yaml
strict_schema_valid: true
source_artifact_sha256_exact: true
source_spans_byte_exact: true
occurrence_recall: 1.0
typed_edge_recall: ">= 0.80"
revisit_occurrence_identity: true
true_merge_two_parent_recall: 1.0
false_merge_count: 0
forbidden_information_observed: false
```

不要求 event 文本与 gold 逐字相等；event 对齐按 source span 重叠、时序和数学状态共同判定。额外保守拆分可以记录为误差，但不能静默丢掉失败、折返或合流。

### 4.2 E2 · State Normalizer

输入：一份 schema-valid、但预先埋入少量语义错误的 extractor 结果，以及它已经引用的 raw source。

预埋错误只有以下三类：

1. 折返 occurrence 被赋予了新的 canonical state，而不是与原根状态共享；
2. 一条明确的跨分支遗产使用被错标为普通 `CONTINUE`；
3. 一个失败事件的 status 被写成 `ACTIVE`。

主判据：

```yaml
strict_schema_valid: true
immutable_event_history_preserved: true
preregistered_corrections_recall: 1.0
unrelated_field_mutation_count: 0
invented_event_or_edge_count: 0
forbidden_information_observed: false
```

### 4.3 E3 · Trace Auditor

输入：同一冻结 DAG/FCA/RCA-style bundle，以及一个混合 candidate trace set。集合中至少包含一个程序规则支持的真 trace 和一个使用正确术语、但引用不存在 edge 或没有双父证据的伪合流 trace。

主判据：

```yaml
top_level_contract_valid: true
valid_trace_acceptance: 1.0
invalid_trace_rejection: 1.0
fake_merge_rejected: true
does_not_use_final_answer_as_process_evidence: true
overall_verdict: FAIL
```

这里 `overall_verdict=FAIL` 是预期正结果：输入故意混入伪 trace；若 auditor 给整个集合 PASS，说明资产没有守住证据边界。

## 5. 单次调用与失败规则

每个 `role × profile × frozen input hash` 只允许一个科学 attempt：

- 正证据证明 provider 未接受请求且 generation 未开始时，可以做一次基础设施重试；
- 接受状态未知、已经开始生成、超时、截断、输出无效或数学判断错误时，不重试，封存原结果；
- 禁止修改输入、提示词、模型或权限后仍沿用同一个 POC attempt ID；
- 禁止 `retry until valid JSON`、`retry until expected graph` 或人工补写 AI 输出。

若以后修订资产，必须发布新 asset set、开新 POC ID 或新 preregistered attempt，旧负证据保留。

## 7. 结果等级

### Component PASS

单角色同时满足其全部主判据、调用收据完整、模型可观察一致、没有边界违规。

### Component PARTIAL

输出可解析且保留主要过程，但一个或多个预注册指标未达阈值；或实际 model/effort 可观察性不完整。PARTIAL 不能被人工解释升级为 PASS。

### Component FAIL

严格合同无效、关键失败/折返/合流被删除、伪合流被接受、越过信息边界，或结果稳定反驳角色资产的明确主张。

### INCONCLUSIVE_PROTOCOL

载体未接受请求、物证缺失、export 损坏、sandbox/模型身份不可审计，导致不能区分科学失败与协议失败。

### POC 总结

- 三个组件都 PASS：`RUNTIME_ASSET_COMPONENTS_PASS_WITHIN_SINGLE_CALIBRATION_CASE`；
- 至少一个 PARTIAL 且无 FAIL：`PARTIAL`；
- 至少一个有效协议下的 FAIL：`FAIL`；
- 任何决定性协议破坏：`INCONCLUSIVE_PROTOCOL`。

即使三项都 PASS，仍必须保留以下非主张：

- 不证明真实长轨迹、流式轨迹或多 Solver 并发可用；
- 不证明 Codex adapter；
- 不证明模型跨数学分支泛化；
- 不证明最终证明正确性；
- 不证明 Tell/Hint 效果；
- 不授权修改入题侧代码或运行资产。

---

## 8. 停止条件

三次预注册调用均获得终态并完成 evaluator 评分后停止。不得因为结果不好继续追加“补跑”。后续只能根据本次证据提出新版本与新实验。
