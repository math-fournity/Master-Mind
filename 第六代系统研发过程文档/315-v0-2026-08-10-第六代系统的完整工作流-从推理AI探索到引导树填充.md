## 2. 工作流的完整拆解

用户描述的完整工作流可以分为7个阶段：

### 阶段1：推理AI探索

> "第一个推理AI对题目进行了探索"

第一个推理AI（Solver）对题目进行探索，产生thinking/trajectory。这是Grove核心循环的起点——引导树→推理AI的推动关系。

### 阶段2：思维脉络分析

> "随后有AI对它的探索的全程进行了分析。并且分析出了它的整个思维脉络，可能是一棵树，或者DAG，无论是什么，我们总是把这些梳理成一个个的脉络，就是从根到叶子节点的一条条思维脉络。"

有AI（辅助AI/分析AI）对推理AI的探索全程进行分析，分析出整个思维脉络。思维脉络可能是一棵树或DAG（如果推理AI在探索中有分叉），但无论是什么结构，总是被梳理成一个个的脉络——从根到叶子节点的一条条思维脉络。

**关键点**：思维脉络不是一条，是多条——从根到每个叶子节点各一条。如果推理AI在探索中分叉了（尝试了多个方向），就有多条脉络。

**和314号问题2的关系**：这里的"梳理成一个个的脉络"就是314号问题2的"格"化——把推理AI的探索过程梳理成不同Level的脉络视图。每条从根到叶子的脉络是一个视图，不同Level的视图对应格的不同元素。

### 阶段3：trace识别（从局部到整体）

> "然后对这些脉络从局部到整体分析出trace。"

对每条脉络从局部到整体分析出trace。"从局部到整体"意味着：
- 局部trace——单点/单段特征
- 整体trace——跨段模式/高Level策略/非局部trace

**和314号问题1的关系**：这里的"从局部到整体分析出trace"就是314号问题1的"建立非局部trace的识别方法"——不只看局部，还要看整体（非局部）。

**和314号问题2的关系**：要"从局部到整体"分析，需要在所有Level的脉络视图上做分析——最细Level看局部trace，中间Level看非局部trace，最粗Level看整体trace。这就是314号问题2的"找出所有Level的脉络视图"。

### 阶段4：并发找tell（Telling AI + Tell分类学）

> "拿着这些trace并发地找tell，因为我们是用tell分类学存储和组织了全部的tell，甚至我们把这些tell放在了一个个目录的AGENTS.md文件中。我们只要在对应的目录中启动devin cli，然后让它以可审计的方式，遍历AGENTS.md中的某个分类或者是子分类中的所有tell，是不是命中了被分配给它识别的推理AI的那些需要被它这个Agent辨析的trace。"

这是311号并发Telling AI方案的工程实现，但比311号更具体：

**Tell的存储方式**：
- tell不（只）存在数据库中，而是存在文件系统的目录结构中
- 每个目录的AGENTS.md文件存放该分类（或子分类）的tell
- 目录结构对应Tell分类学（313号）的层次结构

**Telling AI的实现方式**：
- Telling AI不是抽象的"AI实例"，而是具体的Devin CLI实例
- 在对应分类的目录中启动Devin CLI
- Devin CLI加载该目录的AGENTS.md，获取该分类下的所有tell
- 以可审计的方式遍历AGENTS.md中的tell，判断是否命中被分配的trace

**可审计的方式**：
- Devin CLI的遍历过程是可审计的——每一步判断都有记录
- 这和AGENTS.md全局规则中的"可审计性纪律"一致——"重大分析、调查、审查必须留下file:line定位+理解性产物"

**和311号方案的区别**：
- 311号方案中Telling AI是抽象的"AI实例"，加载"分区的tell"
- 315号（本文档）中Telling AI是具体的Devin CLI实例，在对应目录中启动，加载该目录AGENTS.md中的tell
- 311号方案中tell存储在ArangoDB中，315号中tell存储在目录的AGENTS.md中（可能同时存在两种存储）

**和313号Tell分类学的关系**：
- Tell分类学的层次结构对应目录结构
- 每个分类/子分类是一个目录
- 每个目录的AGENTS.md存放该分类的tell
- 这使得Tell分类学不只是理论分类，而是工程化的存储和组织方案

### 阶段5：trace→tell匹配

> "之后它找到了一些trace对应了一些tells"

每个Telling AI（Devin CLI实例）在自己分类的tell中找到匹配的tell。这是312号问题2（Trace→Tell匹配）的解决——trace匹配到tell。

### 阶段6：tell→hint查询

> "然后根据tells，我们从数据库中查到了对应的hints"

从匹配到的tell，查询数据库中对应的hint。这是309号trace→tell→hint三步链路的最后一步——取用。hint存在数据库中（不是AGENTS.md中），通过tell_id关联查询。

### 阶段7：引导树填充

> "然后呢？然后当然就是用这些hints去填充引导树。我们说了我们有两棵树，一棵树是引导树，代表未来要探索的各个方向，一棵树是解题树，代表已经探索过的解题的路径。"

用查到的hint填充引导树——每个hint成为一个新方向，引导树长出新边。这是Grove核心循环的第三个推动关系——推理AI→引导树。

**两棵树**：
- 引导树=未来要探索的各个方向
- 解题树=已经探索过的解题路径

### 阶段8：引导树和解题树的Level问题

> "但是现在有了关于非局部的trace之后，我们不得不考虑引导树和解题树的Level问题，但是我相信，这是一个小问题。"

非局部trace的引入使得两棵树需要考虑Level——因为非局部trace是跨多节点的段特征，它对应的hint不是针对单个节点的提示，而是针对整段的方向转换。

**为什么需要考虑Level**：
- 局部trace对应的hint针对单个节点——在引导树的单个节点上开新边
- 非局部trace对应的hint针对一段节点——在引导树的哪个位置开新边？是在段的起点？段的终点？还是整段作为一个新节点？

**为什么用户判断这是小问题**：
- 两棵树的基本结构不变——仍然是引导树（方向）和解题树（路径）
- Level问题只是"在树的哪个位置开新边"的细节问题
- 不影响整体工作流——阶段1-7不变，只是阶段7的"填充引导树"需要考虑Level

### 6.2 缺失1：trace→tell匹配失败时怎么办——已解决（不是问题）

**用户原文（一字不差）**：

> 一个trace被识别到了，但是并发的telling ai在自己负责的分支分类tell列表中没有识别到对应的tell，这有什么问题啊？

> 说白了，就是我们的系统还没有积累到充分的tell hint数据，虽然telling ai觉得推理AI在这里的推理内容，似乎是一个值得被关注trace，可能会有tell和它对应，如果有，就有hint，那么不仅推理树那边会有数据，因为推理树也是不同层次的推理记录者，而且引导树还会在这个节点上生出未来的探索方向，用于未来的推理AI的调度。但是如果真的就是在某个telling ai负责的tells范围中没有找到，那就没有找到嘛。但是或许是可以记录一下的，因为这些trace，虽然没有tell和它们对应，但是以后的吸收外部题目和解答数据的AI——Parser AI，它们确实不仅仅应该参考已经有的tell来识别解答记录中的(tell, hint），这些没有tell对应的trace，是一种启发Parser AI对解答记录作为一种推理AI的推理内容，如何进行不同Level的观察的有力的支撑。我的这段原文请你认真体会，并完整记录。

**这不是问题。** 找不到就找不到——这次循环这个trace没有对应的tell，就没有hint，这个分叉位置这次不开新边。这不是流程断裂，是两种正常结果之一：

- **找到了** → 取hint → 填充引导树
- **没找到** → trace记录存档 → 启发Parser AI → 这次不开新边

Grove核心循环不会因为某个trace没找到tell就"只转了半圈"——其他trace找到了tell就能继续转。即使所有trace都没找到tell，那说明这道题的探索没有可匹配的已知模式，引导树不长新边，循环自然停止——这也是正常结果。

**用户原文揭示的新设计——trace的第二用途和Parser AI**：

trace无论是否匹配到tell，都有价值，但去向不同：

| trace匹配结果 | 去向 | 作用 |
|---|---|---|
| 匹配到tell | 取hint → 填充引导树 | 驱动当前循环 |
| 没匹配到tell | 记录存档 → 启发Parser AI | 从外部解答记录识别新(tell, hint)对，丰富tell库，驱动未来循环 |

**Parser AI是吸收外部题目和解答数据的AI**。它从外部解答记录中识别(tell, hint)对，丰富tell库。但它识别(tell, hint)不只参考已有的tell——还参考那些"没有tell对应的trace"。

**为什么这些trace能启发Parser AI**：因为trace是"对推理内容如何进行不同Level观察"的实例。Parser AI面对一份外部解答记录时，需要决定从什么Level观察它——而那些没匹配到tell的trace正好是"什么Level的观察能发现值得关注的模式"的示范。Parser AI参考这些示范，对外部解答记录做不同Level的观察，可能发现新的(tell, hint)对。

**所以"找不到tell"不是无结果的——它为tell库的增长提供了方向。** 没匹配到tell的trace不是废物，是Parser AI的启发信号——它们告诉Parser AI"这里有一种值得关注的模式，虽然我们还没有对应的tell，但你可以从外部解答记录中去找"。

**用户原文中的其他要点**：

1. **推理树也是不同层次的推理记录者**——推理树（解题树）不只记录单步操作，还记录不同Level的推理。这和314号问题2（脉络格化找出所有Level视图）对应——推理树也需要有Level信息。

2. **引导树在这个节点上生出未来的探索方向，用于未来的推理AI的调度**——引导树的新边是"未来的探索方向"，不是当前循环立刻用。这和Grove核心循环的"启动新推理AI"对应——新边启动新AI，新AI的探索又产生新trace，循环继续。

3. **Parser AI不仅参考已有tell，还参考没有tell对应的trace**——这是Parser AI的设计原则。Parser AI有两个输入：已有tell（用于匹配）+ 没匹配到tell的trace（用于启发观察Level）。

#### 6.2.1 Parser AI的完整定义——处理外部题目和解答数据的AI

**用户原文（一字不差）**：

**Parser AI的完整定义**：

Parser AI是处理需要导入系统的外部题目和解答数据的AI。它的输入是外部题目+解答记录，输出是新的(tell, hint)对，存入tell库。

**关键认知：题目和解答与推理AI的推理内容本质相似**——所以处理过程也相似。Parser AI处理外部解答记录的过程，和分析AI分析推理AI上下文的过程，有相同的结构：

| | 分析AI处理推理AI上下文 | Parser AI处理外部解答记录 |
|---|---|---|
| 输入 | 推理AI的thinking/trajectory | 外部题目+解答记录 |
| 分析 | 按提示分析出trace | 按提示分析出trace |
| 匹配 | trace进入Telling AI并发分类分析 | trace进入Telling AI并发分类分析 |
| 匹配到tell | 取hint→填充引导树 | （解答记录已有正确答案，不需要hint） |
| 没匹配到tell | trace存档→启发Parser AI | **trace成为新tell→建立新的(tell, hint)** |

**核心区别在"没匹配到tell"的分支**：

- 分析AI处理推理AI上下文时，没匹配到tell的trace → 存档 → 启发Parser AI（不立刻成为tell）
- Parser AI处理外部解答记录时，没匹配到tell的trace → **直接成为新tell** → 建立新的(tell, hint)

为什么Parser AI的trace可以直接成为tell？因为外部解答记录是**完整的正确解答**——解答记录中每个推理步骤都有明确的目的和结果，所以从解答记录中识别出的trace是"被验证过的思维模式"，可以直接升级为tell。而推理AI上下文中的trace是"探索中的思维模式"——可能走对了也可能走错了，不能直接升级为tell，只能存档待Parser AI验证。

**trace→tell的完整成长路径**：

```
推理AI上下文中识别出trace（有意义但没匹配到tell）
  → 按tell分类学分类存档（不是孤悬的，是按分类积累的）
  → Parser AI处理外部解答记录时参考这些存档trace
  → Parser AI从外部解答记录中识别出相同模式的trace
  → 这个trace被验证（因为外部解答是正确解答）
  → trace升级为正式tell
  → 建立新的(tell, hint)对
  → 存入对应分类目录的AGENTS.md
```

**所以"分析推理AI过程中找到的、没有对应tell也没有对应hint、但被AI认为有意义的trace，分类保留下来有没有价值？当然有了。"**

这些trace的价值在于：
1. 它们是Parser AI的启发信号——告诉Parser AI"从什么Level观察外部解答记录"
2. 它们按tell分类学分类积累——不是孤悬的，是有组织的
3. 当Parser AI从外部解答记录中验证了相同模式的trace时，这些存档trace就升级为正式tell——它们提前占好了分类位置
4. 一旦升级为tell并建立(tell, hint)对，它们就从"存档trace"变成"正式tell"——可以用于未来的trace→tell匹配

**"孤悬的trace"这个概念**：用户用了"孤悬"这个词——没有tell对应的trace是"孤悬的"，因为它们没有hint，不能驱动引导树生长。但它们不是无用的——它们按tell分类学分类积累，等待Parser AI从外部解答记录中验证后升级为正式tell。一旦有了hint，"孤悬的trace"就不再是孤悬的，就成了正式的tell。

#### 6.2.2 两个过程的统一——脉络分析管线

**用户提问**："所以，你好好梳理一下，分析推理AI的上下文和分析、吸收'素材'——也就是题目和解答过程，这两个过程，是不是有很大的可以复用的和重合的部分？"

**是的。这两个过程有非常大的可复用和重合部分——步骤1-4完全相同，共用同一套管线，只在步骤5分叉。**

**过程A：分析推理AI的上下文**（315号§5阶段2-5）

- 输入：推理AI的thinking/trajectory
- 步骤1：分析出思维脉络（可能是树/DAG），梳理成从根到叶子的一条条脉络
- 步骤2：格化脉络，找出所有Level的脉络视图（314号问题2）
- 步骤3：从局部到整体分析出trace（314号问题1）
- 步骤4：trace进入Telling AI并发分类分析（311号方案）
- 步骤5：trace→tell匹配
  - 匹配到tell → 取hint → 填充引导树
  - 没匹配到tell → trace按tell分类学分类存档 → 启发Parser AI

**过程B：分析、吸收"素材"（题目+解答过程）**（Parser AI）

- 输入：外部题目+解答记录
- 步骤1：分析出思维脉络（解答记录本身就是一个脉络）
- 步骤2：格化脉络，找出所有Level的脉络视图
- 步骤3：从局部到整体分析出trace
- 步骤4：trace进入Telling AI并发分类分析
- 步骤5：trace→tell匹配
  - 匹配到tell → 已有tell，确认匹配（不需要新建）
  - 没匹配到tell → trace直接成为新tell → 建立新的(tell, hint)

**重合部分——步骤1-4完全相同**：

分析脉络→格化→识别trace→Telling AI并发分类分析。这四步是两个过程共享的核心管线。提示词也相同——用户说了"这种提示带来的分析，在分析推理AI的推理内容的时候，也是这样做的"。Telling AI也相同——两个过程的trace都进入相同的Telling AI并发分类分析，Telling AI遍历相同的AGENTS.md中的tell做匹配。

**区别部分——步骤5分叉**：

| | 过程A（分析推理AI上下文） | 过程B（Parser AI处理外部解答记录） |

**更深层的统一——输入本质上是同一种东西**：

两个过程的输入本质上是同一种东西——**数学推理的脉络**：

### 6.4 缺失3：一个trace匹配多个tell，一个tell关联多个hint时怎么选——已解决（不是问题）

**用户原文（一字不差）**：

> 我记得你之前还有一个疑问，说一个tell对应多个hint要怎么处理？我觉得这就是很自然的现象和过程，一个完整的题目都可能出现多种解法啊！

**这不是问题。** 一个tell对应多个hint，就像一道题有多种解法——这是数学中最自然的现象。

一个tell描述的是"推理AI在这里可以分叉但没分叉"，分叉后可以走多条不同的路——每条路对应一个hint。比如"AI在枚举参数但问题是素数存在性"这个tell，对应的hint可能是"用二次剩余"，也可能是"用Dirichlet定理"，还可能是"用筛法"——都是对同一个分叉位置的不同方向。

填充引导树时全选就行——每个hint开一条新边，引导树在这个节点上分叉出多个方向，每个方向启动一个新推理AI。这正是引导树的意义——"代表未来要探索的各个方向"，多个方向就是多棵子树。

这也和Grove核心循环一致——引导树分叉→多个推理AI并发探索→每个产生新trace→每个再找tell→再取hint→再分叉。树就是这样长的。

### 6.8 边界条件
