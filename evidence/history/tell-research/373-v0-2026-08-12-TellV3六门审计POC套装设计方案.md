# 373号 · TellV3六门审计POC套装设计方案

**日期**：2026-08-12  
**状态**：POC方案稿；不启动Solver，不修改代码，不写入数据库。  
**触发原因**：372号提出“Tell必须成为可选择、可执行、可终止、可组合、可归责、可持续学习的认知策略”。用户要求将围绕该要求设计的POC套装写入方案。  
**前置文档**：348号POC升级方案，350号全面验证方案，352号实验协议审查，359号历史bare失败题索引，371号迁移工程扩展，372号非特化全需求与六门审计。  

---

## 0. 一句话结论

TellV3的POC不应再设计成一次“大实验”，而应设计成一套**六门审计POC套装**：

```text
先冻结题包
再逐门验证
最后端到端闭环
```

这套POC的目标不是简单证明“非特化有效”，而是把一条候选Tell逐步推进成：

```text
候选Tell
  → TellCore
  → TellStrategy
  → 可被Grove运行时调度的认知策略
```

每个POC只回答一个可归责问题。成功时知道哪个组件有效；失败时知道是哪一门没过。这样，POC不会再产出笼统的PASS/FAIL，而会产出可沉淀、可复查、可继续学习的`EvidenceRecord`。

---

## 1. 为什么必须是“POC套装”，不是单次POC

旧POC已经证明了很多局部能力：

- VMS-8说明脉络继承加运行时hint可以推动新AI；
- VMS-9/10说明tell端可以做粗筛与近邻细分；
- VMS-28说明trace可以被拆成分支事件、FCA视角和语义不变量；
- no-loss POC说明机械压缩会丢失关键语义；
- 350/352号说明bare、错配Tell、等强度对照和泄漏审查是必要的；
- bare筛选线说明“真实bare失败”必须作为候选题入场券。

但这些证据还没有共同证明一件事：

> 一条从trace中非特化出来的Tell，已经成为可选择、可执行、可终止、可组合、可归责、可持续学习的认知策略。

所以新POC不能问：

> 给了Tell以后AI做出来了吗？

而要分解成六个问题：

1. 系统知道什么时候选它吗？
2. AI知道拿到它以后做什么吗？
3. 系统知道什么时候停、退、让位吗？
4. 它能和其他Tell一起工作吗？
5. 成败能归因到具体组件吗？
6. 它能从新证据中修订自己吗？

这就是POC套装的设计核心。

## 2. 总体结构

推荐的首批POC套装包含九个POC：

| 编号 | 名称 | 主要审计门 | 核心问题 |
|---|---|---|---|
| POC-0 | Case Pack冻结 | 前置门 | 题包、对照、证据边界是否预先冻结？ |
| POC-1 | 因果取商 | 可归责、可持续学习 | TellCore是否保留因果有效结构，而不是源题表面？ |
| POC-2 | 可选择 | 可选择 | selector是否能选中正例、拒绝假朋友？ |
| POC-3 | 可执行 | 可执行 | HintInstance是否让AI执行预期认知动作？ |
| POC-4 | 可终止 | 可终止 | 有效、无进展、冲突场景中能否停止或让位？ |
| POC-5 | 可组合 | 可组合 | 多条Tell之间能否调度、排序、冲突处理？ |
| POC-6 | 可归责 | 可归责 | 增益能否归因到TellCore、renderer、selector或lineage？ |
| POC-7 | 可持续学习 | 可持续学习 | 反例能否修改边界、版本或退役策略？ |
| POC-8 | 端到端闭环 | 六门全覆盖 | 多trace到运行时调用再到反例修订是否完整闭环？ |

其中POC-0到POC-7是组件级证据，POC-8是系统级证据。必须先做组件级，再做端到端。否则即使端到端成功，也无法解释为什么成功。

## 3. POC套装的共同铁律

### 3.1 bare失败是入场券

进入正迁移测试的题，必须先有真实bare失败证据。否则Tell成功无法说明它解决了模型原本不会解决的问题。

最小要求：

- 同一Solver模型；
- 同一题面；
- 不给Tell、不继承lineage；
- 完整保留thinking、trajectory和最终输出；
- 失败判定区分“路线失败”“证明失败”“落盘失败”。

### 3.2 题包先冻结，实验后不能补题

POC-0必须在任何Tell测试前冻结题包。后续不能因为结果不好临时换题，不能因为某题成功就追认其为正例。

题包至少包含：

- `source_trace_cases`：用于抽取TellCore的来源trace；
- `positive_transfer_cases`：结构保持、预期应触发的迁移题；
- `metamorphic_cases`：保留关键结构但改变外壳的变形题；
- `false_friend_cases`：表面相似但关键结构缺失的假朋友题；
- `boundary_cases`：只改变一个关键条件的边界题；
- `decoy_cases`：包含强诱饵但不应触发目标Tell的题；
- `regression_cases`：用于确认修订后没有误杀旧正例。

### 3.3 所有证据都写成EvidenceRecord

POC不能只写“通过/失败”。每次实验必须说明它支持或反驳哪个组件主张：

```yaml
EvidenceRecord:
  poc_id:
  target_type: TellCore | HintRenderer | HintInstance | Selector | Protocol | Runtime
  target_component:
  intervention:
  controls:
  observations:
  supports:
  contradicts:
  alternative_explanations:
  leakage_risk:
  confidence:
  scope_limit:
  follow_up:
```

这条铁律保证旧POC、新POC和未来自动化测试能共用同一种证据语言。

### 3.4 成功率只是结果指标，不是唯一指标

每个POC至少同时记录四层指标：

- 识别层：是否触发、是否拒绝假朋友、参数是否绑定正确；
- 过程层：是否出现预期认知动作和进展信号；
- 结果层：是否完成证明、证明是否正确；
- 系统层：是否能写回证据、修订版本、影响下次选择。

TellV3尤其关心过程层。因为一个Tell可能没有立刻让AI做出整题，但仍然让AI进入了正确分支；也可能最终做出题，却完全没有执行目标Tell。

### 3.5 组件级PASS不能升级成端到端PASS

POC-2通过，只能说明selector在该题包上有选择能力；不能说明TellCore因果有效。POC-3通过，只能说明某个HintInstance可执行；不能说明它可选择、可组合、可持续学习。

最终只有POC-8能被称为端到端闭环证据。

## 4. 首批POC对象怎么选

首批套装不要同时验证26种思维力，也不要同时覆盖所有Tell类型。推荐先选一个“证据最多、组件最容易拆开”的Tell家族。

### 4.1 首选对象

首批推荐目标：

```text
目标Tell家族：
  表示切换 / 隐藏结构显化 / 语义不变量识别 型Tell
```

选择理由：

- 它与“同构之桥”“取商”“语义命名”“证书控制”等已有研究相连；
- 它容易产生结构保持变形题和假朋友题；
- 它能观察明确的过程信号，如引入新表示、构造等价对象、寻找不变量、比较两个视角；
- VMS-8/9/10/28中已有相关局部证据可复用；
- 它既不是纯计算技巧，也不是过高Level口号，适合作为TellV3第一条生产策略试验对象。

### 4.2 不推荐首批对象

首批不建议选：

- 过窄技巧型Tell，因为容易退化成题目特化提示；
- 纯抽象标签型Tell，因为大概率重复VMS-7g的负证据；
- 需要很大题量统计才显效的Tell，因为POC阶段会被样本规模拖垮；
- 需要完整自动化系统才能测的Tell，因为第一套POC应先验证策略契约。

### 4.3 首批规模

首批POC建议采用小而完整的规模：

| 项目 | 数量 |
|---|---|
| 目标Tell家族 | 1个 |
| 候选TellCore | 3个以内 |
| 正迁移题 | 4-6道 |
| 假朋友题 | 4-6道 |
| 边界题 | 2-4道 |
| 变形题 | 3-5道 |
| Solver模型 | 1个主模型 |
| 每个关键条件重复 | 1-3次 |

这个规模足够暴露系统性问题，又不会在第一轮就变成大规模统计工程。

## 5. POC-0：Case Pack冻结

### 5.1 目标

POC-0不测试Tell。它只做一件事：

> 在实验开始前，把题包、对照条件、成功标准和证据写法冻结。

这一步是防止实验后挑题、追认成功和证据越级。

### 5.2 输入

- 历史bare失败题候选；
- VMS-8/9/10中的强证据题；
- 359号历史bare失败题索引；
- 365-370号挑战池中的尚未验证题；
- 人工构造的结构保持变形题；
- 人工构造的假朋友题和边界题。

### 5.3 输出

```yaml
CasePack:
  case_pack_id:
  target_tell_family:
  frozen_at:
  source_trace_cases:
  positive_transfer_cases:
  metamorphic_cases:
  false_friend_cases:
  boundary_cases:
  decoy_cases:
  regression_cases:
  exclusion_log:
  leakage_review:
```

### 5.4 通过标准

POC-0通过，需要满足：

- 每道正迁移题有bare失败或明确的准入理由；
- 每道假朋友题说明“为什么表面相似、为什么结构不应触发”；
- 每道边界题只改变一个关键条件；
- 每道题都预注册预期触发、不触发或弃权；
- 写明哪些题来自历史记录，哪些题是新构造；
- 写明禁止在实验后移动题目类别。

## 6. POC-1：因果取商

### 6.1 目标

POC-1回答：

> 从trace中抽出的TellCore，是否保留了真正起作用的结构？

这里的“因果取商”是指：把源题对象、符号、叙事和偶然路径压掉，只保留能解释成功转向的关系结构、触发条件、动作策略和证据要求。

### 6.2 方法

从source trace中抽出3个以内候选TellCore：

```yaml
TellCoreCandidate:
  invariant_claim:
  source_branch_event:
  causal_explanation:
  trigger_boundary:
  negative_boundary:
  parameter_slots:
  binding_rules:
  internal_policy:
  progress_model:
  termination:
  critic:
```

然后逐项做字段审查：

- 删除源题对象后是否仍可执行；
- 删除某个关系字段后是否失去迁移解释；
- 替换表面外壳后是否保持作用；
- 改变关键结构后是否应拒绝；
- 是否能解释正例和负例的差异。

### 6.3 输出

- `TellCoreCandidate`列表；
- 字段消融记录；
- 正/负边界说明；
- 最小充分字段集合；
- 信息泄漏审查。

### 6.4 通过标准

POC-1通过，不要求Solver成功，只要求TellCore本身具备策略结构：

- 没有源题对象泄漏；
- 至少有一个明确trigger和一个明确negative trigger；
- 参数槽可以绑定到新题对象；
- internal policy不是一句口号；
- progress model能预测可观察中间信号；
- termination能说明何时停止或让位；
- 能解释为什么假朋友不应触发。

## 7. POC-2：可选择

### 7.1 目标

POC-2回答：

> 当Tell库中存在多个候选Tell时，系统是否知道什么时候选目标Tell，什么时候拒绝它？

这一步主要测试selector，不测试hint是否有效。

### 7.2 方法

构造一个小型Tell库：

- 1个目标TellCore；
- 2-4个近邻TellCore；
- 2个明显错配TellCore；
- 1个通用反思Tell作为干扰。

对CasePack中的题逐题执行选择：

```text
problem state
  → selector
  → top-k Tell候选
  → abstention或选择
  → 记录选择理由
```

### 7.3 输出

```yaml
SelectorEvidence:
  problem_id:
  expected_decision: select | reject | abstain | boundary
  selected_tells:
  ranking_reason:
  trigger_features:
  negative_features:
  binding_preview:
  decision_correct:
```

### 7.4 通过标准

首轮工程门槛：

- 正迁移题中，目标Tell进入top-2的比例达到80%左右；
- 假朋友题中，目标Tell被拒绝或降权的比例达到80%左右；
- 边界题可以标为boundary，不能强行归为正例；
- selector必须输出理由，不能只输出相似度分数；
- 错选时必须能归因到trigger缺失、negative trigger缺失、绑定错误或候选Tell过近。

这里的80%只是小样本工程门槛，不是科学显著性结论。

## 8. POC-3：可执行

### 8.1 目标

POC-3回答：

> AI拿到HintInstance后，是否真的执行了Tell预期的认知动作？

它不只看最终证明是否成功，而要看thinking中是否出现目标过程。

### 8.2 方法

把同一个TellCore渲染成若干HintInstance：

- 低强度根提示；
- line分叉提示；
- method-only提示；
- method+critic提示；
- full Tell提示。

对比：

- bare；
- 通用鼓励；
- 等长空流程；
- 错配Tell；
- 目标Tell。

### 8.3 过程信号

对于“表示切换 / 隐藏结构显化 / 语义不变量识别”型Tell，过程信号可以包括：

- 引入新的等价表示；
- 明确比较原表示与新表示；
- 找到保持量、单调量或证书对象；
- 把题目目标改写成新表示中的局部条件；
- 放弃原先的自然但无效入口；
- 产生可验证的中间lemma。

### 8.4 通过标准

POC-3通过，需要看到：

- 目标Tell组的目标认知动作出现率明显高于bare和通用鼓励；
- 错配Tell不应稳定触发同一动作；
- AI不是简单复述提示词，而是把提示绑定到题目对象；
- 至少部分案例出现progress model预期的中间信号；
- 失败案例能区分“没有执行”“执行但无进展”“执行后方向错误”。

## 9. POC-4：可终止

### 9.1 目标

POC-4回答：

> Tell被启动后，系统是否知道何时继续、停止、回退或让位？

这是防止高Level Tell变成无限反思陷阱的关键POC。

### 9.2 场景

至少准备三类题：

| 场景 | 预期行为 |
|---|---|
| 有效场景 | 继续执行，直到出现证书或主路线 |
| 无进展场景 | 观察不到progress signal时退出 |
| 边界冲突场景 | negative trigger出现时停止或让位 |

### 9.3 输出

```yaml
TerminationEvidence:
  problem_id:
  hint_instance_id:
  expected_termination:
  observed_progress:
  stop_or_continue_decision:
  decision_time:
  replacement_tell:
  outcome:
```

### 9.4 通过标准

- 有效场景中不应过早退出；
- 无进展场景中不应一直重复同一动作；
- 边界冲突场景中不应强行使用目标Tell；
- 退出理由必须能落到progress model或negative boundary；
- 让位时要说明被哪个Tell接管，或为什么abstain。

## 10. POC-5：可组合

### 10.1 目标

POC-5回答：

> 目标Tell能否和其他Tell共同工作，而不是互相抵消或重复？

Grove运行时不是只给一条提示。多个分支、多个Tell、多个候选方向会同时存在。因此Tell必须有组合契约。

### 10.2 组合类型

至少测试四类关系：

| 组合关系 | 含义 | 例子 |
|---|---|---|
| 顺序依赖 | A必须先于B | 先换表示，再检查证书 |
| 互补协同 | A和B可并行增强 | 一个生成新对象，一个验证不变量 |
| 冲突排斥 | A和B不能同时推 | 一个要求扩大结构，一个要求极小化 |
| 冗余重复 | A和B实质相同 | 两条Tell只是措辞不同 |

### 10.3 输出

```yaml
CompositionContract:
  tell_id:
  prerequisites:
  enables:
  conflicts_with:
  redundant_with:
  priority_rule:
  handoff_rule:
```

### 10.4 通过标准

- 能识别至少一种顺序依赖；
- 能识别至少一种冲突关系；
- 能把重复Tell合并或降权；
- 组合后的提示不应明显比单Tell更混乱；
- 失败时能说明是组合规则错误、提示过载，还是Tell本身不兼容。

## 11. POC-6：可归责

### 11.1 目标

POC-6回答：

> 如果Tell有效，增益到底来自哪里？

这是整套POC中最容易被忽略、也最重要的一门。没有归责，所有成功都会被解释成“Tell有效”，但实际上可能来自提示长度、鼓励、人工选择、lineage或泄漏。

### 11.2 干预矩阵

首轮使用轻量矩阵：

| 条件 | 检验什么 |
|---|---|
| bare | 基线能力 |
| 通用鼓励 | 额外动力效应 |
| 等长空流程 | 一般反思结构效应 |
| 等强度错配Tell | 提示强度效应 |
| method only | 操作步骤本身的作用 |
| full Tell | 完整认知Option效应 |

第二轮扩展为372号完整矩阵：

- trigger only；
- critic only；
- trigger + method；
- method + critic；
- 过强窄方法提示。

### 11.3 输出

```yaml
AttributionMatrixResult:
  problem_id:
  conditions:
    - condition:
      final_outcome:
      target_action_observed:
      progress_signal_observed:
      leakage_risk:
      notes:
  attribution_judgment:
  residual_alternatives:
```

### 11.4 通过标准

- full Tell相对bare和通用鼓励有过程层增益；
- 等长空流程不能稳定复制目标过程；
- 错配Tell不能稳定复制目标过程；
- method only若同样有效，应降级trigger或critic的贡献声明；
- 如果只有full Tell有效，说明组件协同重要；
- 如果所有提示都有效，不能宣称目标Tell特异有效。

## 12. POC-7：可持续学习

### 12.1 目标

POC-7回答：

> 新成功、失败和反例能否改变TellStrategy？

Tell库不能是静态提示库。它必须在遇到反例后修订边界、修改绑定规则、调整选择权重，甚至退役。

### 12.2 方法

给目标TellStrategy输入三类新证据：

- 正例成功；
- 假朋友误触发；
- 正例未触发或执行失败。

要求系统或人工流程产出版本修订：

```yaml
TellRevision:
  from_version:
  to_version:
  trigger_change:
  negative_boundary_change:
  binding_rule_change:
  renderer_change:
  termination_change:
  evidence_added:
  regression_plan:
```

### 12.3 通过标准

- 假朋友误触发后，negative boundary必须变窄；
- 正例未触发后，trigger或binding rule必须解释缺口；
- renderer失败后，不能修改TellCore来掩盖提示表达问题；
- 修订后必须重跑小回归；
- 修订不能牺牲已有正例而不记录代价；
- 如果反例推翻核心不变量，TellStrategy应降级或退役。

## 13. POC-8：端到端闭环

### 13.1 目标

POC-8回答：

> TellV3能否从多trace出发，自动形成可运行策略，并在新题上完成选择、执行、归责和修订？

这是唯一可以被称为“完整非特化POC”的实验。

### 13.2 闭环链条

```text
多条成功/失败trace
  → 分支事件切分
  → 候选因果解释
  → 允许变换与破坏变换
  → 多轴Tell假设格
  → 因果充分压缩
  → 编译成认知Option
  → 自动识别启动条件
  → 自动绑定当前对象
  → 生成HintInstance
  → Solver运行
  → 观察预期认知动作与进展信号
  → 在结构保持题上维持效用
  → 在结构破坏题上拒绝或失效
  → 写入EvidenceRecord
  → 用新反例修订Tell边界
```

### 13.3 通过标准

端到端POC通过，需要同时满足：

- POC-0题包冻结；
- POC-1产出TellCore；
- POC-2能自动选择或拒绝；
- POC-3能触发预期认知动作；
- POC-4能退出或让位；
- POC-5能处理至少一种组合关系；
- POC-6能归责到具体组件；
- POC-7能产生版本修订；
- 至少一个正迁移题出现结果层成功或明确过程层进展；
- 至少一个假朋友题被拒绝、降权或成为有效反例。

注意：端到端POC不要求第一轮就大规模提高成功率。第一轮的核心验收是闭环结构成立。

## 14. 验证题选择标准：怎样保证名副其实

POC套装要名副其实，题目不能只追求“难”。它必须能诊断Tell到底有没有发挥目标认知策略的作用。

最好的验证题不是“模型做不出来的怪题”，而是：

> bare会自然走错路；目标Tell指向的认知策略确实是低搜索成本主路；假朋友题又能证明系统不会乱触发。

换句话说，题包要按功能选，不按题目好看程度选。

### 14.1 四类核心验证题

第一类是**历史bare失败锚题**。

这类题优先来自VMS-7g、VMS-8/9/10、359号索引，以及已有真实Solver记录。它们最干净，因为不是为了新理论临时造出来的。历史锚题能减少“为了证明Tell有效而挑题”的嫌疑。

第二类是**奥赛母题机制题**。

这类题从真实奥赛难题里抽Level 3-4机制，但不直接复用题面。关键不是保留原题外壳，而是保留“自然入口必然失败、隐藏结构必须显化、需要换表示、需要找证书或构造不变量”的设障机制。它们用来证明Tell面对真正竞赛级结构时仍然有意义。

第三类是**结构保持变形题**。

这类题保留目标Tell的核心结构，但更换领域、符号、叙事、对象类型或目标形式。它最能证明Tell不是记题，也不是记某个表面套路。若Tell在结构保持变形题上仍能触发同一类认知动作，非特化主张才开始站得住。

第四类是**假朋友与边界题**。

假朋友题表面上很像目标题，但关键结构缺失；边界题只改动一个关键条件，使目标Tell不该再触发，或只能以boundary状态触发。这类题不是附属品，而是可选择、可归责和可持续学习三门审计的核心。

### 14.2 第一套题包的推荐配比

第一套POC不应贪大。推荐题包如下：

| 题目类别 | 数量 | 作用 |
|---|---:|---|
| source trace题 | 3-5道 | 用于抽取TellCore，提供成功/失败分支事件 |
| 正迁移题 | 4-6道 | bare失败，目标Tell应触发并推动目标过程 |
| 结构保持变形题 | 3-5道 | 换外壳但保留核心机制，测试非特化迁移 |
| 假朋友题 | 4-6道 | 表面像但结构不成立，目标Tell应拒绝或降权 |
| 边界题 | 2-4道 | 只改一个关键条件，测试trigger边界 |
| 组合题 | 2-3道 | 需要目标Tell和另一条Tell按顺序或互补合作 |

这个规模的目标不是统计显著，而是让每一种失败都有可解释位置。

### 14.3 第一套最适合的题型

首批最适合选择：

```text
隐藏结构显化
表示切换
语义不变量识别
```

这类Tell最适合第一套POC，因为它有清楚的过程信号：

- AI是否换了表示；
- AI是否构造了等价对象；
- AI是否找到保持量、单调量或证书对象；
- AI是否放弃自然错路；
- AI是否把题目目标改写成新表示中的局部条件。

这些信号可以在thinking和trajectory里被观察，也能进入`EvidenceRecord`。相比之下，“灵感”“洞察”“全局视角”这类抽象词更难直接归责，适合等六门审计机制跑通后再验证。

### 14.4 不适合进入首批POC的题

首批不要使用以下题：

- toy题，因为它测不出竞赛级非特化能力；
- 纯计算难题，因为它可能只测算力或耐心；
- 只靠长搜索能啃出来的题，因为Tell贡献会被搜索预算掩盖；
- 经典外壳过强的题，因为模型可能直接调用训练中见过的路线；
- 没有verified solution的新造题，因为无法判断Solver是真错还是题目本身有问题；
- 给出Tell后接近泄题的题，因为那测的是提示信息量，不是认知策略；
- bare未失败的题，因为Tell成功不能说明增量贡献。

### 14.5 总选题哲学：题目是测量仪器，不是装饰样本

POC题目的本质不是“样本”，而是“测量仪器”。一套好题包应像一组精密仪器，分别测出TellStrategy的不同能力：

- 正迁移题测“该触发时能否触发”；
- 假朋友题测“不该触发时能否拒绝”；
- 边界题测“边界附近能否谨慎”；
- 结构保持变形题测“换外壳后是否仍抓住核心”；
- 组合题测“多个Tell是否能排队、协作或互斥”；
- 回归题测“修订后是否误伤旧能力”。

因此，选题时要优先看六个属性：

| 属性 | 问题 | 为什么重要 |
|---|---|---|
| 诊断性 | 这道题能暴露哪一个认知动作是否发生？ | 没有诊断性，成功率无法归责 |
| 对照性 | 能否构造表面相似但结构不同的反例？ | 没有对照性，selector容易虚假PASS |
| 可观察性 | thinking里能否看见目标过程信号？ | 没有过程信号，无法区分执行和复述 |
| 可变形性 | 能否保留核心结构换外壳？ | 没有变形，无法证明非特化 |
| 非泄漏性 | Tell是否不会直接给出关键lemma或答案？ | 泄漏会把策略验证变成答案注入 |
| 可核验性 | 题目和解答是否已经被验证？ | 未核验题会污染失败归因 |

难度只排在这些属性之后。一个极难但不可诊断的题，不如一个中等难度但能精确区分Tell组件贡献的题。

### 14.6 CaseCard：每道题进入题包前必须建卡

每道候选题都必须先写成`CaseCard`，再决定是否进入`CasePack`。这样后续POC不会只面对一段题面，而是面对一个带来源、角色、预期行为和风险说明的实验对象。

```yaml
CaseCard:
  case_id:
  source:
    origin: historical_bare_failure | olympiad_mechanism | metamorphic_variant | constructed_false_friend | boundary_variant
    source_document:
    source_trace:
  role:
    primary_role: source_trace | positive_transfer | metamorphic | false_friend | boundary | decoy | composition | regression
    secondary_roles:
  problem:
    statement:
    domain:
    verified_solution:
    verification_status: verified | partial | unverified
  bare_baseline:
    required_for_positive: true | false
    attempts:
    status: failed | solved | inconclusive | not_run
    failure_mode: route_failure | proof_failure | output_failure | timeout | token_limit | not_applicable
    natural_wrong_path:
  target_tell:
    tell_family:
    expected_selector_decision: select | reject | abstain | boundary
    expected_runtime_action:
    expected_progress_signal:
    expected_termination:
  structure:
    invariant_kernel:
    surface_features:
    preserved_features:
    broken_features_if_negative:
    metamorphic_relation:
  controls:
    matched_false_friend:
    matched_boundary_case:
    matched_decoy:
    matched_regression_case:
  risks:
    leakage_risk: low | medium | high
    classicality_risk: low | medium | high
    ambiguity_risk: low | medium | high
    oversearch_risk: low | medium | high
  admission:
    score_summary:
    veto_reason:
    frozen_role:
```

`CaseCard`有两个作用：

1. 防止题目在实验中途被重新解释；
2. 让失败归因能落到题目属性，而不是只怪Tell或Solver。

### 14.7 题目评分表：分数不是替代判断，而是防漏项

每道候选题可以按0-2分粗评。0表示不满足，1表示部分满足，2表示清楚满足。

| 维度 | 0分 | 1分 | 2分 |
|---|---|---|---|
| bare基线 | 未测或bare成功 | bare结果含混 | 真实bare失败且记录完整 |
| 策略中心性 | 目标Tell只是可选路线 | 目标Tell是较自然路线之一 | 目标Tell是低搜索成本主路 |
| 过程可观察 | thinking中难以看出动作 | 有弱过程信号 | 有明确动作与进展信号 |
| 假朋友可构造 | 无法构造近似负例 | 可构造粗糙负例 | 有表面近似、结构破坏的强负例 |
| 结构可变形 | 只能原题测试 | 可改符号或外壳 | 可跨叙事、对象或领域保持结构 |
| 解答可核验 | 无可靠解答 | 解答部分核验 | 完整verified solution |
| 泄漏安全 | Tell几乎等于关键lemma | Tell有提示过强风险 | Tell只给策略，不给答案信息 |
| 经典风险 | 经典题面或高训练痕迹 | 有局部经典痕迹 | 外壳与路线有足够新鲜度 |
| 组合价值 | 只测单点成功 | 能触发弱组合 | 能明确测试依赖、冲突或让位 |
| 学习价值 | 失败后无法修订 | 失败能粗略归因 | 失败能直接修改trigger、boundary或renderer |

准入建议：

- 正迁移题必须满足：bare基线2分、解答可核验2分、泄漏安全至少1分；
- 假朋友题必须满足：假朋友可构造2分、结构破坏说明清楚；
- 变形题必须满足：结构可变形2分、目标过程信号至少1分；
- 组合题必须满足：组合价值2分；
- 任一题如果解答不可核验，不能进入结果层验证，只能作为设计素材。

总分不能替代否决项。只要出现高泄漏、无解答、bare成功却被当正迁移题、经典外壳过强且无法排除训练记忆，就应暂缓进入首批POC。

### 14.8 各类题目的细化标准

**source trace题**用于抽TellCore，不要求全部bare失败，但必须有可读的分支事件。最理想的是同一题或同一机制下同时存在成功trace和失败trace，这样才能做对照式因果取商。只有平滑成功、没有明显转向的题，不适合作为首批source trace。

**正迁移题**必须真实bare失败，并且目标Tell应是低搜索成本主路。所谓低搜索成本主路，不是唯一解法，而是指人类或强审查者能说明：如果采用该Tell，下一步会自然产生有用对象、约束、表示或证书。若目标Tell只是众多可能启发之一，正迁移证据会很弱。

**结构保持变形题**必须显式写出“保留什么、改变什么”。保留项应是目标TellCore的因果内核，改变项应覆盖符号、对象、叙事、领域或目标形式。只把变量名从`a,b,c`换成`x,y,z`，不算合格变形。

**假朋友题**必须做到“表面像，核心不像”。它不能太明显，否则selector拒绝没有意义；也不能本质上仍适用目标Tell，否则会误把正例当负例。合格假朋友题需要写清楚：哪几个表面特征诱导误触发，哪一个关键结构缺失导致目标Tell不应执行。

**边界题**最好只改一个关键条件。它不是普通负例，而是用来测trigger边缘。如果系统在边界题上选择`boundary`或`abstain`，这通常比强行选择或强行拒绝更健康。

**decoy题**包含强诱饵。它的作用是测试TellStrategy会不会被题面中醒目的熟悉信号吸走。decoy题尤其适合测试“错配Tell”和“通用鼓励”对照。

**组合题**必须预先写明需要哪两条或多条Tell，以及它们的关系是顺序依赖、互补、冲突还是冗余。不能把“题很复杂，所以可能需要多个Tell”当作组合题。

**回归题**来自旧正例、旧负例和旧边界例。它们的作用是验证Tell修订没有把过去已经学会的边界破坏掉。每次POC-7修订后，都应抽少量回归题重跑。

### 14.9 每个POC的专门选题标准

不同POC需要不同题形，不能用同一批“难题”贯穿到底。

| POC | 最需要的题 | 选题重点 | 不适合的题 |
|---|---|---|---|
| POC-0 Case Pack冻结 | 全部题类 | 来源清楚、角色冻结、解答核验、风险标注 | 来源不明、角色可随结果摇摆的题 |
| POC-1 因果取商 | source trace题、对比trace题 | 有成功/失败分支、自然错路、关键转向 | 只有最终证明、没有过程分叉的题 |
| POC-2 可选择 | 正迁移题、假朋友题、边界题 | 表面相似度与结构差异都清楚 | 正负例差异太明显或太含混的题 |
| POC-3 可执行 | 正迁移题、过程信号强的变形题 | thinking中能观察目标认知动作 | 即使执行Tell也看不出中间动作的题 |
| POC-4 可终止 | 有效题、无进展题、边界冲突题 | 能区分继续、停止、让位 | 只有成功/失败二分，缺少过程阶段的题 |
| POC-5 可组合 | 组合题、冲突题、冗余题 | 多Tell关系可预注册 | 只是复杂但Tell关系不清楚的题 |
| POC-6 可归责 | 中等规模正迁移题、强对照题 | bare、错配Tell、空流程差异可观察 | 过难到所有条件都失败，或过易到所有条件都成功的题 |
| POC-7 可持续学习 | 假朋友误触发题、正例漏触发题、回归题 | 失败能指向trigger、boundary、binding或renderer修订 | 失败原因无法定位的题 |
| POC-8 端到端闭环 | 小而完整的全题包 | 能覆盖抽取、选择、执行、归责、修订全链条 | 只覆盖结果成功、不覆盖反例和修订的题包 |

这张表的重点是：POC-6尤其不应选极端难题。可归责实验需要各条件之间有可观察差异；如果所有条件全失败，矩阵无法告诉我们Tell组件是否有效。

### 14.10 题目来源优先级

首批CasePack按来源分层：

| 层级 | 来源 | 可用方式 |
|---|---|---|
| S级 | 历史真实bare失败，且有完整thinking、trajectory、verified solution | 优先作为正迁移题或source trace题 |
| A级 | 真实奥赛母题抽出的Level 3-4机制，经换壳、解答核验、bare失败确认 | 可作为正迁移题或结构保持变形题 |
| B级 | 人工构造的变形题、假朋友题、边界题，解答已核验 | 可作为选择、边界、学习POC材料 |
| C级 | 预测bare失败但尚未测试的题 | 只能进入候选池，不能作为正迁移证据 |
| D级 | toy题、经典外壳强题、无解答题、泄漏风险高题 | 不进入首批POC |

S级题不是天然正确。即使历史bare失败，也必须重新检查目标Tell是否真是低搜索成本主路。否则它只能证明“这题难”，不能证明“这条Tell有用”。

### 14.11 选题流程

推荐按下面顺序构造题包：

1. 先确定目标Tell家族，不先挑题。
2. 从历史记录中找source trace和bare失败候选。
3. 为每道候选题写`CaseCard`。
4. 审查verified solution，排除无解答或解答不稳的题。
5. 复核bare失败记录，必要时补跑bare。
6. 标注自然错路和目标低成本路线。
7. 为每个正例构造至少一个假朋友或边界变体。
8. 为目标Tell构造至少两个结构保持变形。
9. 用评分表初筛，记录否决项。
10. 冻结`CasePack v0`，之后只能写入`exclusion_log`，不能实验后改角色。

这套流程看起来繁琐，但它能保护POC不被两个东西污染：一是挑题成功，二是事后解释。

### 14.12 选题中的典型误判

**误判1：把模型做不出来当成题目合格。**  
bare失败只是入场券，不是合格证。真正合格还要看正路是否可诊断、Tell是否是主路、假朋友是否可构造。

**误判2：把题目难度当作Tell难度。**  
题目可能难在长计算、复杂分类、繁琐边界，而目标Tell只负责其中一个很小环节。若无法隔离Tell负责的环节，这题不适合首批归责POC。

**误判3：把经典母题直接拿来测。**  
真实奥赛题很有价值，但直接使用可能触发训练记忆。更好的方式是抽机制、换外壳、保留设障脚本，再重新验证解答和bare失败。

**误判4：把提示强当认知策略强。**  
如果Tell几乎把关键lemma或关键构造说出来，成功不能证明非特化。合格Tell应告诉AI做哪类认知动作，而不是替AI完成关键数学发现。

**误判5：只准备正例，不准备负例。**  
没有假朋友和边界题，可选择审计无法成立；没有反例，可持续学习也无法成立。

**误判6：实验后移动题目角色。**  
如果某道假朋友题被Tell做出来了，不能立刻改称正例。正确做法是记录为反例：要么目标Tell边界原本写错，要么题目结构判断错，要么Tell比预期更广。

### 14.13 最终选题铁律

第一套POC的题目应满足：

```text
真实bare失败
+ 正路可诊断
+ 过程可观察
+ 变形可生成
+ 假朋友可构造
```

这五条共同保证：验证出来的不是“提示让AI更努力”，也不是“题目刚好撞上模型已有知识”，而是一条TellStrategy确实在正确处境中触发、推动了目标认知动作，并且在不该触发时能够拒绝或修订。

## 17. 读完后要记住的六句话

1. TellV3的POC目标不是证明一句提示有效，而是证明一条认知策略能被系统调度。
2. 六门审计是POC套装的骨架：可选择、可执行、可终止、可组合、可归责、可持续学习。
3. POC-0冻结题包是所有实验的地基，否则后续结果很容易被追认和挑题污染。
4. 验证题必须真实bare失败、正路可诊断、过程可观察、变形可生成、假朋友可构造。
5. POC-2到POC-7都是组件级证据，只有POC-8能被称为端到端闭环证据。
6. 失败不是废结果，只要能写成`EvidenceRecord`并触发Tell版本修订，它就是Tell系统持续学习的一部分。
