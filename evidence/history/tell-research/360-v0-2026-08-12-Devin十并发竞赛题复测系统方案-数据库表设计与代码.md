## 0. 结论

应该新增一个批量运行层，站在现有 `solver_harness.py` 上面做四件事：

1. 从 `problem_extraction_progress` / `problem_profiles` 或显式历史题面文件中选题；
2. 以题目表唯一数字 `_key` 编入 `exp_id`，让运行目录和数据库记录一一对应；
3. 通过 `solver_harness.py launch/stop/decode-all` 启动和回收 Devin Solver，绝不手写 tmux 启动；
4. 把 batch、attempt、event 三层记录写入 ArangoDB，形成“什么题做出来、怎么做出来；什么题做不出来、为什么做不出来”的可审计数据层。

## 2. 运行方案

### 2.1 主流程

1. **选题**：优先从 `problem_extraction_progress + problem_profiles` 联表选 Tier 1 / predicted fail 题；历史失败题用 `run-files` 显式传入。
2. **建批次**：创建 `devin_batch_runs` 一条记录。
3. **建 attempt**：每题创建 `devin_problem_runs` 一条记录，状态 `queued`。
4. **生成目录名**：`exp_id` 必含 `p<progress_key>`。
5. **启动 Devin**：runner 调 `solver_harness.py launch`，harness 创建 tmux。
6. **并发监控**：保持最多 `concurrency=10` 个 running；如果总题数更多，终止一个再补一个。
7. **实时观察**：检查 tmux、`proof.md`、`thinking_readable.txt`、`tmux_pipe.log`、`conversation.json`、`trajectory.jsonl`。
8. **回收与解码**：自然结束、超时或手动停止后调用 harness stop；批次结束后统一 `decode-all`。
9. **自动 verdict**：只判运行层状态，不自动声称数学正确。
10. **人工审计**：`candidate_solved` 的 proof 再按题解/solution_text 做数学审查。

### 2.2 目录命名

示例：

```text
/data/math-agent-glm5.2-tmux-agents-dir/
  dpb-20260812-153000-tier1-bare-01-p329030-g000002-compfiles_imo1963p5/

/data/math-agent-glm5.2-tmux-agents-trajectory/
  dpb-20260812-153000-tier1-bare-01-p329030-g000002-compfiles_imo1963p5/
```

其中：

- `dpb-20260812-153000-tier1-bare`：batch id
- `01`：批次内序号
- `p329030`：`problem_extraction_progress._key`
- `g000002`：`global_sequence`
- `compfiles_imo1963p5`：problem_id

这样未来看目录名就能回查数据库题目记录。

## 3. 数据库表设计

### 3.1 `devin_batch_runs`

一批实验一条记录。

| 字段 | 含义 |
|---|---|
| `_key` | batch id，如 `dpb-20260812-153000-tier1-bare` |
| `status` | `created / running / decoded / completed / stopped / decode_error` |
| `created_at / updated_at / completed_at` | 批次时间 |
| `model` | 默认 `glm-5-2` |
| `concurrency` | 默认 10 |
| `selected_count` | 本批题数 |
| `attempt_keys` | 本批 attempt key 列表 |
| `selection` | 选题参数或手动文件 case 列表 |
| `paths` | batch_dir / problems_dir / logs_dir / solver_base / trajectory_base |
| `timeouts` | max_runtime_seconds / stall_seconds |
| `status_counts` | 批次结束后各状态统计 |

索引：

- `status`
- `created_at`

### 3.2 `devin_problem_runs`

一题一次 Devin bare attempt 一条记录。

| 字段 | 含义 |
|---|---|
| `_key` | `<batch_id>-<ordinal>-p<progress_key>` |
| `batch_id` | 所属批次 |
| `ordinal` | 批次内序号 |
| `progress_key` | `problem_extraction_progress._key`，唯一数字ID |
| `global_sequence` | 难度排序序号 |
| `problem_id` | 题目ID |
| `profile_doc_id` | 若有 profile，则记录 |
| `source_dataset / source_mode` | 来源；`source_mode=profile/manual_file` |
| `case_metadata` | 手动文件来源、原始文件路径、是否找到 profile |
| `exp_id` | harness 实验ID；目录名核心 |
| `tmux_session` | `harness-<exp_id>` |
| `paths` | solver_dir、trajectory_dir、proof_path、export_path、tmux log、sessions_db 等 |
| `status` | attempt 状态 |
| `devin_session_id` | harness 从 sessions.db 回填 |
| `observability` | 文件大小、last activity、rate limit/token limit/proof markers |
| `verdict` | runner 自动 verdict，不替代数学审查 |

索引：

- `batch_id`
- `progress_key`
- `problem_id`
- `status`
- `exp_id` 唯一

### 3.3 `devin_run_events`

细粒度事件日志。

| 字段 | 含义 |
|---|---|
| `_key` | 时间戳 + uuid |
| `batch_id` | 所属批次 |
| `attempt_key` | 可为空；批次级事件为空 |
| `event_type` | `batch_created / attempt_launching / attempt_running / attempt_terminal / batch_decoded` 等 |
| `observed_at` | 事件时间 |
| `detail` | 结构化详情 |

索引：

- `batch_id`
- `attempt_key`
- `observed_at`

## 4. 状态机与判定

attempt 状态：

| 状态 | 含义 |
|---|---|
| `queued` | 已入库，未启动 |
| `launching` | 正在调用 harness launch |
| `running` | tmux session 存在且日志有活动 |
| `stalled_warning` | tmux 还在，但一段时间没有观察到文件增长 |
| `candidate_solved` | `proof.md` 存在；需要人工数学审查 |
| `failed_no_proof` | tmux 结束但无 `proof.md`，且无明确基础设施错误 |
| `failed_token_limit` | 发现 token/context limit marker |
| `failed_timeout` | 超过 max runtime |
| `failed_tool_stall` | 超过 stall threshold 且选择 stop-on-stall |
| `rate_limited` | 发现 429 / rate limit marker |
| `failed_connection` | 发现 connection/API error marker |
| `launch_error` | harness launch 失败 |
| `stopped` | 人工 stop |

`candidate_solved` 不等于“数学正确”。runner 只负责实验过程采集，数学审查应读取 `proof.md`、thinking 和参考解答后另行标注。

```bash
  select --limit 10 --tier 1 --bare-ai-expected fail
```

```bash
set -a; source .env; set +a
.venv/bin/python xishujuzhen/solver_harness/batch_problem_runner.py \
  run \
  --limit 10 \
  --tier 1 \
```

## 6. 为什么这样设计

这个系统要解决的不是“让 AI 做题”，而是稳定制造和保存观察数据：

- tmux 让我们能随时 attach 进去看 TUI 和限流提示；
- harness 保证 thinking / tool_calls / export / pipe-pane 都被采集；
- `progress_key` 进入目录名，解决“运行目录和题目表记录无法对应”的问题；
- batch/attempt/event 三表让未来能统计 bare 成功率、失败类型、卡点位置、Tell 后改变量；
- `run-files` 让历史 VMS 失败题马上能复测，不必等它们全部补 profile；
- 自动 verdict 保持克制，只做运行层分类，避免把有 `proof.md` 误判为数学正确。
