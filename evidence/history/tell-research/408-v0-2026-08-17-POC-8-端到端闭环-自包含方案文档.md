## §0 自包含POC方案文档的设计规范（本节是所有POC方案文档的共用规范）

### 0.1 设计目标

一份POC方案文档要让未来20万上下文的AI**只加载这份文档+它索引的少数核心文档**，就能完整了解做好这次POC所需的所有背景知识，不需要用户另外指点应该读什么。

### 0.2 文档结构（每份POC方案文档必须包含的10节）

| 节 | 内容 | 作用 |

### 0.3 "自包含"的含义

"自包含"不是把所有背景知识复制进文档——那样文档会膨胀到无法加载。"自包含"是指：

1. **文档本身包含这个POC执行所需的全部操作信息**——输入/方法/输出/通过标准/执行约束
2. **文档明确列出需要全文加载的背景文档清单**——每份说明加载理由（这个POC为什么需要这份文档的内容）
3. **未来AI加载这份POC方案后，按照§8清单去全文加载被索引的文档**——不需要用户另外指点

### 0.4 被索引文档的精挑细选原则

每份POC方案文档的§8清单应该精挑细选——只列这个POC真正需要的背景文档，通常3-7份。如果索引太多，未来AI加载不完。

**挑选标准**：
- **必须加载**：这个POC不加载这份文档就无法正确执行（如题包/TellCore定义/通过标准来源）
- **建议加载**：这个POC加载这份文档能更好理解为什么这么做（如理论背景/原设计文档）
- **不列**：这个POC不需要这份文档的内容（如其他POC的方案文档）

```
{编号}-v0-{日期}-POC-{POC编号}-{POC名称}-自包含方案文档.md
```

**POC-8回答**：

> TellV3能否从多trace出发，自动形成可运行策略，并在新题上完成选择、执行、归责和修订？

这是唯一可以被称为**"完整非特化POC"**的实验——373号§13和396号§9都确认了这个定位。POC-0~7都是组件级证据，只有POC-8能被称为端到端闭环证据。

### 1.4 新增内容：跨模型验证（397号§3.4）

397号§1.9审视了373号的POC-8设计，结论是：

> **合理，但缺少跨模型验证。**373号的POC只用1个Solver模型（GLM-5.2 High）。如果只测一个模型，无法证明TellCore对其他模型也有效。372号§4C路线A3提到了模型依赖差异——同一Tell族对不同模型的峰值可能不同。

397号§3.4建议在POC-8中加入1个对照模型：

> 如果GLM-5.2 High上Tell有效，在另一个模型（如GPT或Claude）上是否也有效？
> - 如果只在GLM-5.2 High上有效，TellCore可能过拟合到这个模型
> - 如果在两个模型上都有效，TellCore的跨模型泛化性得到初步支持
> - 如果在两个模型上有效但峰值不同，印证了372号§6.1的"Level是向量"和396号§3的"Pareto前沿"

POC-8在373号原设计的基础上**新增跨模型对照**——1个主模型（GLM-5.2 High）+1个对照模型。

### 1.5 为什么在Phase D

POC-8排在Phase D，因为它依赖POC-0~7全部完成——端到端闭环需要每一门的组件级证据都成立：

- POC-0/1提供了题包和TellCore
- POC-2提供了selector
- POC-2.5确认了基础因果效应
- POC-3.5确定了非特化程度
- POC-3确认了可执行
- POC-4确认了可终止
- POC-6确认了可归责
- POC-7提供了修订候选

只有这些组件级证据都成立后，端到端闭环才能把"多trace→TellCore→选择→执行→归责→修订"这条链条完整跑通。

## §2 理论背景——为什么需要这个POC

### 2.1 373号§13——唯一可以被称为"完整非特化POC"的实验

373号§13.1明确指出：

> TellV3能否从多trace出发，自动形成可运行策略，并在新题上完成选择、执行、归责和修订？这是唯一可以被称为"完整非特化POC"的实验。

POC-0~7都是组件级证据——它们分别验证了selector/基础效应/非特化程度/可执行/可终止/可归责/可持续学习的某一门。但组件级PASS不能升级成端到端PASS（373号§3.5）——只有POC-8把所有组件串成闭环链条，才能被称为端到端闭环证据。

### 2.2 396号§9——完整的非特化POC

396号§9定义了"完整的非特化POC是什么"——POC-8就是这个定义的实验实现。完整的非特化POC需要同时满足：

1. 从多trace中提取TellCore（学习端）
2. TellCore通过六门审计（可选择/可执行/可终止/可组合/可归责/可持续学习）
3. 在结构保持变换下维持作用
4. 在控制混杂后仍有因果贡献

POC-0~7分别验证了第2点的各门和第3/4点的各维度，POC-8把它们串成闭环。

### 2.3 396号§5.6——六门审计是总闸门

396号§5.6引用了372号§16的六门审计：

> TellV3的目标不是制造更抽象的提示，而是制造可选择、可执行、可终止、可组合、可归责、可持续学习的认知策略。抽象层级只是第一门，六门审计才是整个理论和技术框架的总闸门。

POC-8就是六门审计的总验收——POC-0~7分别验证了各门，POC-8验证的是"所有门一起是否成立"。

### 2.4 397号§3.4——跨模型验证的必要性

397号§3.4指出跨模型验证的必要性：

> 372号§4C路线A3：同一Tell族对不同模型的峰值可能不同。如果只测GLM-5.2 High，无法证明TellCore对其他模型也有效。TellCore可能过拟合到GLM-5.2 High的特征（比如它对模算术的理解方式、它对p-adic的熟悉程度等）。

跨模型验证是397号审视后新增的内容——373号的原始设计只用1个模型，397号建议在POC-8中加入至少1个对照模型。

### 2.5 396号§3——Pareto前沿与模型依赖

396号§3（第一层深化：钟形曲线→Pareto前沿）指出：

> 指导力是情境效用，不是Tell固有常数。同一Tell的指导力会随题目、模型和运行时变化。

跨模型验证正是检验这一点——如果TellCore在两个模型上都有效但峰值不同，印证了"Level是向量"（372号§6.1）和"Pareto前沿"（396号§3.3）。

### 2.6 闭环链条

373号§13.2定义了端到端闭环的完整链条：

```
多条成功/失败trace
  → 分支事件切分
  → 候选因果解释
  → 允许变换与破坏变换
  → 多轴Tell假设格
  → 因果充分压缩
  → 编译成认知Option
  → 自动识别启动条件
  → 自动绑定当前对象
  → 生成HintInstance
  → Solver运行
  → 观察预期认知动作与进展信号
  → 在结构保持题上维持效用
  → 在结构破坏题上拒绝或失效
  → 写入EvidenceRecord
  → 用新反例修订Tell边界
```

POC-8验证的就是这条链条能否完整跑通——从"多trace"到"修订Tell边界"。

### 2.7 不验证会留下什么gap

如果不做POC-8：
- 所有组件级证据（POC-0~7）都是孤立的——不知道它们串在一起是否能成立
- TellStrategy不能被称为"可被运行时调度的认知策略"——只有端到端闭环能证明它能在运行时被完整调度
- TellCore的跨模型泛化性无法验证——不知道它是否过拟合到GLM-5.2 High
- 非特化理论框架（396号）没有完整的实验证据——只有组件级证据，没有端到端证据

## §4 输入——这个POC需要什么

### 4.1 题包——全题包

从382号CasePack v0的22道题中取**全题包**（373号§14.9指出POC-8最需要小而完整的全题包——能覆盖抽取、选择、执行、归责、修订全链条）：

| 题目类别 | 数量 | 在闭环中的作用 |
|---|---|---|
| source trace题 | 4道 | 闭环起点——从多trace提取TellCore |
| 正迁移题 | 4道 | 验证选择→执行→归责 |
| 变形题 | 4道 | 验证结构保持变换下维持效用 |
| 假朋友题 | 5道 | 验证选择→拒绝 + 反例识别→修订候选 |
| 边界题 | 3道 | 验证边界附近的选择行为 |
| 组合题 | 2道 | 顺带观察组合行为（POC-5推迟但可在POC-8中观察） |

### 4.2 TellCore

383号确定的TellCore v0候选C（局部-全局表示切换），7字段最小充分集。

POC-8使用POC-0~7验证过的TellCore——不需要重新提取，但需要确认闭环链条中"从多trace→TellCore"这一环能跑通（即从source trace题出发，经过分支事件切分→候选因果解释→因果充分压缩→编译成认知Option，能产出与383号TellCore v0兼容的TellCore）。

### 4.3 Solver模型——主模型+对照模型

**主模型**：GLM-5.2 High（通过solver_harness启动）

**对照模型**（397号§3.4新增）：1个对照模型（如GPT或Claude，取决于可用性）

对照模型的选择标准：
- 与GLM-5.2 High有足够的差异（不同模型家族或不同训练路线）
- 能通过solver_harness或类似方式启动
- 能运行同样的题包和HintInstance

### 4.4 HintInstance

由HintRenderer把TellCore v0渲染成HintInstance。POC-8使用POC-3.5确定的**中等非特化程度的HintInstance**。

**注意**：对照模型可能需要不同的HintRenderer——不同模型对提示的响应方式不同，同一个HintInstance在不同模型上的效果可能不同。这正是跨模型验证要检验的——396号§3.4说"指导力是情境效用"，同一HintInstance在不同模型上的指导力可能不同。

### 4.5 脉络（vein）

从source trace题提取脉络。闭环链条中"自动识别启动条件→自动绑定当前对象→生成HintInstance"这一环需要脉络。

### 4.6 前置POC的EvidenceRecord

POC-8需要加载POC-0~7的所有EvidenceRecord，确认每一门的组件级结论，作为闭环验收的基础。

## §5 方法——这个POC怎么做

### 5.1 实验设计

POC-8分为两个部分：

**Part A：端到端闭环验证（主模型GLM-5.2 High）**

在全题包上跑完整闭环链条（373号§13.2）：

```
多条成功/失败trace（source trace题）
  → 分支事件切分
  → 候选因果解释
  → 允许变换与破坏变换
  → 多轴Tell假设格
  → 因果充分压缩
  → 编译成认知Option（TellCore）
  → 自动识别启动条件（selector）
  → 自动绑定当前对象（binding）
  → 生成HintInstance（HintRenderer）
  → Solver运行（GLM-5.2 High）
  → 观察预期认知动作与进展信号
  → 在结构保持题上维持效用（变形题）
  → 在结构破坏题上拒绝或失效（假朋友题）
  → 写入EvidenceRecord
  → 用新反例修订Tell边界（POC-7修订候选）
```

**Part B：跨模型对照验证（对照模型）**

在对照模型上跑同样的闭环链条（或简化版——至少跑选择→执行→归责），验证：

> 如果GLM-5.2 High上Tell有效，在对照模型上是否也有效？

### 5.2 闭环链条各环节的验证

| 环节 | 验证什么 | 对应前置POC |
|---|---|---|
| 多trace→TellCore | 从source trace能产出与383号TellCore v0兼容的TellCore | POC-1 |
| 自动识别启动条件 | selector能自动选中正迁移题的目标Tell、拒绝假朋友题 | POC-2 |
| 自动绑定当前对象 | binding rule能正确绑定当前题的对象到参数槽 | POC-1/POC-3 |
| 生成HintInstance | HintRenderer能把TellCore渲染成可执行HintInstance | POC-3.5 |
| Solver运行+观察认知动作 | AI执行预期认知动作并出现进展信号 | POC-3 |
| 结构保持题维持效用 | 变形题上Tell仍触发并有效 | POC-0.5/POC-1 |
| 结构破坏题拒绝或失效 | 假朋友题上Tell被拒绝或让位 | POC-2/POC-4 |
| 写入EvidenceRecord | 每个环节的结论被正确记录 | 全部 |
| 用新反例修订Tell边界 | 假朋友误触发/正例未触发被识别为反例并记录修订候选 | POC-7 |

### 5.3 跨模型对照验证的设计

**在对照模型上验证**：

1. **选择**：selector在对照模型上能否选中正迁移题的目标Tell、拒绝假朋友题？（可能selector需要适配不同模型）
2. **执行**：对照模型拿到HintInstance后是否执行预期认知动作？
3. **归责**：full Tell在对照模型上是否有过程层增益？干预矩阵的结论是否与主模型一致？
4. **效果差异**：如果Tell在两个模型上都有效但效果不同（如峰值位置不同、最优非特化程度不同），记录模型依赖差异

**简化版跨模型验证**：

### 5.4 观察指标

## §7 通过标准

### 7.1 通过标准（373号§13.3 + 397号§3.4新增）

**POC-8通过，需要同时满足**：

**Part A（主模型闭环）——373号§13.3原标准**：

1. **POC-0~7各门通过**——每一门的组件级证据在闭环中成立
2. **至少一个正迁移题出现结果层成功或明确过程层进展**——Tell确实在新题上有效
3. **至少一个假朋友题被拒绝、降权或成为有效反例**——Tell确实能拒绝不该触发的题

**Part B（对照模型）——397号§3.4新增标准**：

4. **至少1个对照模型上Tell也有效**（或明确记录模型依赖差异）——TellCore不是过拟合到主模型

### 7.2 重要声明：第一轮的核心验收是闭环结构成立

373号§13.3的诚实声明：

> 端到端POC不要求第一轮就大规模提高成功率。第一轮的核心验收是闭环结构成立。

这意味着：
- **不要求所有正迁移题都成功**——至少一个有结果层成功或过程层进展就够了
- **不要求所有假朋友题都被拒绝**——至少一个被拒绝或成为反例就够了
- **核心是闭环链条能跑通**——从多trace到修订Tell边界，每个环节都能执行

### 7.3 不通过的处理

**如果Part A条件1不满足（某门未通过）**：
- 记录哪门未通过
- 回到对应的前置POC修订——如POC-4未通过则修订TellCore的termination字段
- 闭环结构不成立——但其他门的结论仍然有效

**如果Part A条件2不满足（没有正迁移题成功或进展）**：
- Tell在新题上无效——可能是TellCore不够通用，或selector选错了，或HintInstance不合适
- 闭环结构可能成立（链条跑通了），但Tell没有效果——需要回到POC-2.5/POC-6确认Tell是否有效

**如果Part A条件3不满足（没有假朋友题被拒绝）**：
- Tell不能拒绝不该触发的题——selector或negative_boundary有问题
- 回到POC-2修订selector或POC-1修订negative_boundary

**如果Part B条件4不满足（对照模型上Tell无效）**：
- TellCore可能过拟合到主模型——这是重要的跨模型发现
- **必须明确记录模型依赖差异**——哪个环节在对照模型上失效（选择/执行/归责）
- 不一定是"不通过"——如果主模型上闭环成立，可以宣称"闭环结构在主模型上成立，但在对照模型上Tell无效——模型依赖差异已被记录"

**如果Part B显示Tell在两个模型上都有效但效果不同**：
- 这不是"不通过"——这是对396号§3"Pareto前沿"和"指导力是情境效用"的验证
- 记录差异——如峰值位置不同、最优非特化程度不同、过程层增益强度不同
- 印证了372号§6.1的"Level是向量"——不同模型上Tell的最优配置可能不同

### 7.4 模糊结果的处理

**如果闭环链条部分跑通（某些环节通过某些不通过）**：
- 记录哪些环节通过、哪些不通过
- 分析断裂点——是某个环节本身有问题，还是环节之间的接口有问题
- 模糊结果仍然有价值——它指出了闭环链条的薄弱环节

### 7.5 通过后意味着什么

**POC-8通过意味着**：
- 闭环结构成立——从多trace到修订Tell边界，每个环节都能执行
- Tell在新题上有效——至少一个正迁移题有结果层成功或过程层进展
- Tell能拒绝不该触发的题——至少一个假朋友题被拒绝
- TellCore有跨模型泛化性（或模型依赖差异已被记录）

**POC-8通过不意味着**：
- Tell对所有题都有效——只验证了至少一个正迁移题
- Tell对所有模型都有效——只验证了1个对照模型
- TellStrategy已经完善——POC-7简化版只做了反例识别，完整版本修订还需后续工作
- 可以大规模部署——这只是首批小规模POC的端到端验证

### 9.3 Git

- 产物文件（poc_8_result.yaml / poc_8_cross_model_report.yaml / poc_8_analysis.md / 每个run的导出）必须commit

### 9.4 POC运行记录

POC运行记录必须保留thinking、trajectory、proof或TUI导出。通过solver_harness自动保存。对照模型的运行记录也必须保留。

### 9.5 证据分层

POC结论必须写成证据分层——这是373号§3.5的核心铁律：

> 组件级PASS不能升级成端到端PASS。POC-2通过，只能说明selector在该题包上有选择能力；不能说明TellCore因果有效。POC-3通过，只能说明某个HintInstance可执行；不能说明它可选择、可组合、可持续学习。最终只有POC-8能被称为端到端闭环证据。

反过来也成立——**端到端闭环成立不意味着所有组件级问题都解决了**。POC-8通过只说明闭环结构成立，不说明每一门都完美。

### 9.6 诚实声明

POC-8的诚实声明（373号§13.3）：

> 端到端POC不要求第一轮就大规模提高成功率。第一轮的核心验收是闭环结构成立。

执行POC-8的AI必须遵守这个声明——不能为了"通过"而夸大成功率或忽略失败的环节。即使只有1个正迁移题成功，只要闭环结构成立，这就是合法的端到端验证结果。

### 9.7 跨模型验证的诚实记录

如果对照模型上Tell无效，**必须明确记录**——不能只报告主模型上的成功而忽略对照模型上的失败。跨模型验证的目的是检测过拟合，如果对照模型上无效，这本身就是重要发现——它说明TellCore可能过拟合到主模型。

### 9.8 失败不是废结果

如果POC-8不通过（闭环结构不成立），这不是废结果——它指出了闭环链条的断裂点，每一门的前置POC可以针对性地修订。不通过的结果必须完整记录。

- **不通过不阻塞POC-9（识别端验证）**——POC-9可并行进行
- **不通过阻塞完整版POC-7**——如果闭环结构不成立，版本修订没有意义
- **不通过阻塞第二个Tell家族验证**——如果第一个Tell家族的闭环都不成立，第二个Tell家族的闭环也不会成立
- **不通过触发对断裂环节对应前置POC的修订**——如POC-4环节断裂则修订POC-4，POC-6环节断裂则修订POC-6

### 10.5 POC-8在整体研究中的定位

POC-8是首批POC系列的**终点验收**——它不是另一个组件级POC，而是把所有组件级证据串成闭环的系统级验证。

- 如果POC-8通过——首批POC系列完成，TellV3的第一条生产策略试验对象（局部-全局表示切换型Tell）通过了完整的六门审计+端到端闭环验证
- 如果POC-8不通过——指出了闭环链条的断裂点，为下一轮POC修订提供了明确方向
- 无论通过与否——POC-8的结论都是非特化理论框架（396号）的第一份完整实验证据
