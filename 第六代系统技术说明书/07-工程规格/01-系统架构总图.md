## §2 数据流

thinking→domain分类→Telling AI实例选择（包括低Level和高Level）→并发trace识别（低Level遍历tell + 高Level理解概念+格化脉络+判断适用条件）→汇总精筛→tell匹配→hint取出→脉络构造→新AI启动

## §3 高Level Telling AI和低Level Telling AI的区别

架构图中标注了两类Telling AI的并行通道：

| 方面 | 低Level Telling AI | 高Level Telling AI |
|---|---|---|
| 启动目录 | 低Level AGENTS.md目录（具体tell条目） | 高Level AGENTS.md目录（概念解释+例子） |
| 识别逻辑 | 遍历tell条目，逐一匹配trace | 理解概念+格化脉络+判断适用条件 |
| 产出 | 识别到具体tell → 找hint | 认定需要新的进攻方向 → 给方向性hint |
| 启动条件 | domain分类结果包含该区 | domain分类包含"跨域"或trace显示域内打转未突破 |

两者并行运行，都是并发Telling AI的一部分。汇总AI同时处理两者的输出。

## §6 运行痕迹保留（2026-08-10新增）

**原则**：系统的运行过程要全程保留所有"痕迹"用于未来的审计和调试。系统设计必须既要考虑运行逻辑，也要考虑痕迹保留。

**Rule**：`.devin/rules/six-trace-preservation.md`（always-on，触发条件：设计或实现系统任何运行阶段时）

### 痕迹保留的两个维度

**1. 不可丢弃——所有中间产物必须落盘**

系统运行中的每个中间产物都必须落盘到文件或数据库，不可只在内存中传递后丢弃。每个阶段函数（vein_analysis/trace_match/direction_extract/guide_expand/knowledge_deposit）必须：
- 输入落盘——传给AI的完整提示词落盘到工作目录的`input.md`或`input.json`
- 输出落盘——AI的完整产出落盘到工作目录的`output.md`或`output.json`
- 程序验证报告落盘——如果有程序验证（如verify_lattice_completeness.py），验证报告也落盘

**2. 可追溯——每个产物都能追溯到产生它的上下文**

每个落盘的产物必须能追溯到：哪个AI实例产出的（ai_id）、用哪个提示词版本跑的（V5/V7/V8/V9）、在哪个会话中（session_id）、输入是什么（输入文件路径或内容hash）、什么时候产出的（时间戳）。

### 4并发方案的痕迹保留

4并发中每个版本的产出分别落盘到各自工作目录：
```
palyground/{process}/vein_analysis/{problem_id}/
├── V5/
│   ├── input.md          ← 传给V5 AI的完整提示词
│   └── output.json       ← V5 AI的产出（自由文本解析后）
├── V7/
│   ├── input.md
│   └── output.json
├── V8/
│   ├── input.md
│   └── output.json
├── V9/
│   ├── input.md
│   ├── output.json       ← V9 AI的产出（含key_entities和meta_reflection_traces）
│   └── audit_report.json ← verify_lattice_completeness.py的审计报告
├── merged_traces.json    ← 4版本trace并集（去重后）
└── meta.json             ← 本次脉络分析的元数据（4个ai_id、时间戳、去重规则）
```

### 数据库层面的痕迹保留

sessions表记录每次会话。后续需增加的表（db_schema.py的TODO中已列出）：
- **ai_instances表**——每个AI实例的启动参数和产出路径（ai_id, session_id, ai_role, prompt_version, working_directory, started_at, completed_at, input_path, output_path）
- **orphan_traces表**——孤悬trace存档（解题引导产出，解答吸收消费）
- **tell_library_changes表**——tell库变更日志（新tell添加、tell修正）

这些表不是可选的——它们是痕迹保留的数据库层面保障。

### 为什么痕迹保留和运行逻辑同等重要

1. **审计**——系统产出了某个结果，需要回溯是哪个AI在什么条件下产出的。没有痕迹就无法审计。
2. **调试**——系统某个阶段出了问题，需要看每个阶段的输入输出。没有痕迹就只能重跑。
3. **迭代**——改进某个阶段的提示词或逻辑时，需要对比改进前后的产出。没有痕迹就没有对比基准。
4. **研究**——系统的运行数据本身是研究材料。没有痕迹就没有研究素材。

## §7 AI Agent启动规范（2026-08-10新增）

**原则**：系统中所有AI Agent的启动，全部使用tmux中的运行方式。首先到达指定的工作目录，然后启动devin cli实例运行。

**Rule**：`.devin/rules/six-ai-agent-launch.md`（always-on，触发条件：启动任何AI Agent实例时）

### 启动前的准备工作

每个AI Agent启动前，必须在其工作目录中准备好以下文件：

| 文件 | 内容 | 必需 |
|---|---|---|
| `AGENTS.md` | 给AI的指令和约束——角色定义、工作规范、产出要求 | ✅ |
| `prompt.md` | 完整提示词——V5/V7/V8/V9等提示词的完整内容（可能几十KB） | ✅ |
| `input.md` 或 `input.json` | 输入数据——题目文本、解答文本、thinking文本、孤悬trace等 | ✅ |
| 其他依赖文件 | 如verify_lattice_completeness.py的路径引用、tell库片段等 | 按需 |

**关键原则：短启动提示词 + 提示词文件加载**

给devin cli的直接提示词应该很短——让AI去加载工作目录中的提示词文件，而不是把完整提示词塞在启动命令中。

```
# ❌ 错误——把完整提示词塞在启动命令中（几十KB的提示词无法放在命令行参数里）
devin "你是脉络分析AI...（30KB的完整提示词）...请分析input.md中的解答"

# ✅ 正确——短启动提示词，让AI加载提示词文件
devin "加载 {workdir}/prompt.md 中的提示词，读取 {workdir}/input.md 中的输入数据，按提示词要求工作，完成后把产出写入 {workdir}/output.json 和 {workdir}/output.md"
```

### 启动流程（标准5步）

```
步骤1：创建工作目录
  mkdir -p palyground/{process}/{stage}/{problem_id}/{version}/

步骤2：准备文件（写入工作目录）
  {workdir}/AGENTS.md      ← AI的指令和约束
  {workdir}/prompt.md      ← 完整提示词（从提示词积累目录复制+填入输入占位符）
  {workdir}/input.md       ← 输入数据（题目/解答/thinking文本）
  {workdir}/input.json     ← 结构化输入数据（如有）

步骤3：在tmux中启动devin cli实例
  tmux new-session -d -s {session_name} \
    "cd {workdir} && devin '加载 {workdir}/prompt.md，读取 {workdir}/input.md，按提示词工作，产出写入 {workdir}/output.json 和 {workdir}/output.md'"

步骤4：等待devin cli实例完成
  tmux capture-pane -t {session_name} -p  # 检查状态
  # 或轮询 {workdir}/output.json 是否出现

步骤5：收集产出
  读取 {workdir}/output.json（结构化产出）
  读取 {workdir}/output.md（人类可读产出）
  读取 {workdir}/audit_report.json（程序验证报告，如有）
```

### tmux session命名规范

```
{process}-{stage}-{problem_id}-{version}

示例：
absorb-vein_analysis-IMO2009P6-V5
absorb-vein_analysis-IMO2009P6-V7
absorb-vein_analysis-IMO2009P6-V8
absorb-vein_analysis-IMO2009P6-V9
solve-inference_explore-IMO2009P6-solver_01
solve-trace_match-IMO2009P6-telling_03
```

### 4并发方案的启动实例

脉络分析阶段4并发（V5/V7/V8/V9）的启动：

```
# 准备4个工作目录
palyground/absorb/vein_analysis/IMO2009P6/
├── V5/
│   ├── AGENTS.md          ← 通用AI约束
│   ├── prompt.md          ← V5提示词+解答文本
│   ├── input.md           ← 解答文本（和prompt.md中的解答文本相同）
│   └── (AI产出) output.json / output.md
├── V7/
│   ├── AGENTS.md
│   ├── prompt.md          ← V7提示词+解答文本
│   ├── input.md
│   └── output.json / output.md
├── V8/
│   ├── AGENTS.md
│   ├── prompt.md          ← V8提示词+解答文本
│   ├── input.md
│   └── output.json / output.md
├── V9/
│   ├── AGENTS.md
│   ├── prompt.md          ← V9提示词+解答文本
│   ├── input.md
│   ├── output.json / output.md
│   └── audit_report.json  ← verify_lattice_completeness.py产出
├── merged_traces.json     ← 4版本trace并集（去重后）
└── meta.json              ← 本次脉络分析元数据

# 启动4个tmux session
tmux new-session -d -s absorb-vein_analysis-IMO2009P6-V5 "cd .../V5 && devin '加载prompt.md...'"
tmux new-session -d -s absorb-vein_analysis-IMO2009P6-V7 "cd .../V7 && devin '加载prompt.md...'"
tmux new-session -d -s absorb-vein_analysis-IMO2009P6-V8 "cd .../V8 && devin '加载prompt.md...'"
tmux new-session -d -s absorb-vein_analysis-IMO2009P6-V9 "cd .../V9 && devin '加载prompt.md...'"

# 检查状态
tmux list-sessions | grep absorb-vein_analysis-IMO2009P6
```

### 为什么用tmux + 工作目录 + 提示词文件

1. **tmux保证可审计**——tmux session的输出可以随时capture-pane查看，AI的工作过程可追溯。这和痕迹保留rule一致。
2. **工作目录隔离**——每个AI Agent在自己的工作目录中工作，产出落盘在工作目录中。不同Agent不互相干扰。
3. **提示词文件而非命令行参数**——提示词可能几十KB（V9提示词66KB），无法放在命令行参数中。放在文件中，AI启动后读取，既支持长提示词又保持启动命令简洁。
4. **AGENTS.md在工作目录中**——每个AI Agent的AGENTS.md可以按阶段定制（脉络分析AI和trace匹配AI的约束不同）。
5. **输入文件独立**——input.md和prompt.md分离，同一个提示词可以跑不同输入（换题时只换input.md不换prompt.md）。

## §8 双重检查机制（2026-08-10新增）

**原则**：系统建立两种check机制——代码能保证的用代码检查，无法用代码完成的用流程审计AI检查。

**Rule**：`.devin/rules/six-dual-check-mechanism.md`（always-on）

### 两种check机制

| 机制 | 谁执行 | 检查什么 | 例子 |
|---|---|---|---|
| 代码检查 | Python代码自动执行 | 机械的、可自动化的检查 | 文件存在性、JSON格式、闭元素完备性得分、关键实体贯穿性验证、伪元模式过滤 |
| 流程审计AI | Master Agent（你） | 认知的、需要判断力的检查 | trace语义质量、trace去重质量、元反思trace是否有价值、AI工作过程是否跑偏、提示词版本选择是否正确 |

**流程审计AI就是Master Agent**——因为"系统就是你，不是脚本"。系统用代码运行了，但系统运行的健康情况需要你实时查看。代码能检查的是机械的部分，AI需要检查的是认知的部分。

### .ai-check文件——第三个同名文件

system/目录下每个`.py`代码文件，除了有同名的`.ref`文件外，还有同名的`.ai-check`文件：

| 文件 | 后缀 | 内容 | 谁用 |
|---|---|---|---|
| `vein_analysis.py` | `.py` | 代码实现 | Python运行时 |
| `vein_analysis.ref` | `.ref` | 参考文档路径列表 | 理解模块时阅读 |
| `vein_analysis.ai-check` | `.ai-check` | AI审计checklist | 流程审计AI（Master Agent） |

三个同名文件构成完整的"实现-参考-审计"三件套。

### 审计流程

流程审计AI（Master Agent）检查某个模块时：

```
步骤1：加载 .ref 文件 → 读取参考文档路径列表 → 按需阅读参考文档（理解设计意图）
步骤2：加载 .py 代码文件 → 理解实现逻辑 → 识别代码中的assertions（不需要AI重复检查）
步骤3：加载 .ai-check 文件 → 明确AI需要检查的项目和标准
步骤4：检查实际运行产出 → 读取工作目录中的output.json/output.md/audit_report.json → 读取tmux输出
步骤5：按checklist逐项检查 → 每项记录✅通过/⚠️部分通过/❌不通过
```

### 什么时候做流程审计

1. **系统运行中实时审计**——Master Agent作为辅助Pipe，在AI Agent运行过程中实时检查健康状态
2. **系统运行后事后审计**——一轮运行结束后，Master Agent切回审计角色，按checklist逐项检查产出质量
3. **代码变更后审计**——修改了某个模块的代码后，按该模块的.ai-check检查是否引入了问题

### 代码检查 vs AI检查的分工原则

代码能检查的全部用代码检查（效率高、可自动化）。代码不能检查的才用AI检查（需要认知判断）。两者不重复——AI检查的清单中明确排除"代码能检查的"项目。
