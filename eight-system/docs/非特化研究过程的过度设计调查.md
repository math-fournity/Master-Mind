# 非特化研究过程的过度设计调查

> **调查日期**：2026-08-15
> **调查对象**：seven-system 构建前的"非特化"研究过程（000-389号，约34,000行）
> **核心问题**：研究过程本身是否存在过度设计？
> **结论**：是的。研究过程的过度设计比 seven-system 更早开始，约 85-90% 的文档量是过早系统化、重复学习和治理膨胀，只有约 10-15% 是真正的认知推进。

## 三、研究过程中的四个过度设计模式

### 模式1：过早全面化

**定义**：在没有完成任何一次成功验证的情况下，设计覆盖全部可能性的全面方案。

**实例**：

#### 349号（664行）：68位菲尔兹奖得主逐篇分析

用户要求"梳理所有历届菲尔兹奖论文"，8个 subagent 并行研究 68 位得主，提取出 26 种思维力。

**问题**：在还没有验证任何一种思维力的 Tell 有效性时，就枚举 26 种。26 种思维力的全面清单是"先建分类再验证"的典型——而 372号后来明确指出"非特化不是分类问题而是因果问题"，使得 26 种枚举的方向价值存疑。

#### 350号（504行）：2600次实验的全面验证方案

基于 349号的 26 种思维力，设计了 26×5×20=2600 次实验的全面验证方案，估算 13.5 天连续运行。

**问题**：在还没有找到一道能通过 bare 测试的题时，就设计了 2600 次实验。后来的 355/357/358/363 四轮 bare 测试全部失败——2600 次实验方案从未可执行。

#### 372号（2,071行）：四层二十四项契约 + 十五步闭环 + 五组二十八条学术路线

372号的核心认知推进是 §2"因果充分的取商"（119行）。但全文 16 个章节中：
- §3（24项契约）：310行——在还没有验证一个 Tell 的情况下枚举 24 项需求
- §4（28条学术路线）：500行——在还没有验证一条路线的情况下枚举 28 条
- §8（15步闭环）：64行——在还没有跑通一步的情况下设计 15 步
- §15（旧POC重新定级）：227行——重新定级旧 POC 的证据等级
- §16（六门审计）：167行——设计审计框架来审计还没运行的东西

**比例**：核心认知推进 119行 = 6%；系统化/枚举/审计 = 94%。

### 模式2：重复学习同一教训

**定义**：多次执行本质相同的实验，得到本质相同的结论，但每次都写成独立文档。

**实例**：

#### 四轮 bare 淘汰（355/357/358/363号，共1,162行）

| 文档 | 行数 | 结论 |
|---|---|---|
| 355号 | 253 | 354候选题bare淘汰——题目不够难 |
| 357号 | 254 | 首轮硬化题仍被bare淘汰——题目不够难 |
| 358号 | 343 | 三并发硬题继续筛除——题目不够难 |
| 363号 | 312 | 362新造题直接bare筛除——题目不够难 |

四轮测试，同一个结论："GLM-5.2 能 bare 做出来，题目不能用于 Tell 测试"。每轮都换了新题，但每轮的 meta 教训相同。356号（出题经验库）确实在积累具体经验条目（E-001~E-009），这些是有价值的。但四份独立的测试记录文档（1,162行）中，每份都在重复"bare成功→淘汰"的叙事结构。

**更深层的问题**：四轮 bare 淘汰暴露了一个根本困境——GLM-5.2 太强了，竞赛级题目它也能 bare 做出来。这个困境在 355号就已经清晰，但研究过程没有停下来重新定义问题（"如何找到 GLM-5.2 做不出来的题"），而是继续出题、测试、淘汰，重复了三轮。

### 模式3：治理递归

**定义**：为了约束自己不越界，为每一步加 Gate；为防 Gate 被绕过，加验证器；为防验证器被绕过，加审计——在没有实际运行的情况下无限展开。

**实例**：

#### 372→373→387 的治理递归升级

| 文档 | "Gate" | "审计" | "隔离" | "因果" |
|---|---|---|---|---|
| 372号 | 0 | 20 | 2 | 36 |
| 373号 | 0 | 8 | 1 | 10 |
| 387号 | 74 | 46 | 39 | 35 |

372号提出了"六门审计"概念（20次"审计"），但还没有"Gate"（0次）。373号把"六门审计"操作化为 8 个 POC（8次"审计"），但也没有"Gate"（0次）。387号突然爆发：74次"Gate"、46次"审计"、39次"隔离"——完整的治理体系。

**递归链**：

```
372号：Tell 需要满足 24 项契约
  → 373号：需要 8 个 POC 验证 6 门
    → 387号：需要完整证据工厂来运行 POC
      → 387号：证据工厂需要 Gate 来控制每一步
        → 387号：Gate 需要验证器来防止绕过
          → 387号：验证器需要授权链来防止自我批准
            → 387号：授权链需要审计来防止伪造
              → ...（74个Gate，39个隔离）
```

**关键发现**：治理递归不是 seven-system 工程化阶段才开始的，而是在 372号就已经种下了种子（24项契约 + 六门审计），在 387号完全展开。

### 模式4：文档膨胀

**定义**：单个文档的篇幅远超其认知内容所需，大量行数用于结构化枚举、YAML schema、重复声明和"非主张"。

**实例**：

#### 352a号（1,296行）：观察性测试技术说明书

这是一份"如何启动 tmux 中的 devin 并观察 thinking"的技术说明书。1,296 行用于描述一个本质上是"启动命令 + 观察输出"的操作。对比 solver-tmux-launch skill 的 SKILL.md，后者用几百行就覆盖了相同操作。

#### 372号（2,071行）：非特化全需求

16 个章节，但核心新认知只有 §2 的 119 行（"因果充分的取商"）。其余 1,952 行是：§1 总结前人结论（99行）、§3 枚举 24 项契约（310行）、§4 枚举 28 条学术路线（500行）、§15 重新定级旧 POC（227行）、§16 六门审计（167行）。

#### 382号（2,261行）：CasePack v0

22 张 CaseCard，每张约 80-100 行。这是真实研究工件，但在 POC-0 和 POC-1 都还没运行时就构造 22 张详细卡片，是过早的——因为 POC-1（383号）的结论可能使部分卡片无效。

#### 387号（3,570行）：非特化证据工厂设计

13 个章节，20+ 个 YAML schema 定义。在还没有跑通一次实验时定义完整系统的数据模型。

## 四、372→373→387 的升级链分析

这是研究过程中过度设计的核心升级链。每一份文档都在前一份的基础上增加系统化程度，但没有任何一份被实验验证。

### 371号（08-12，1,317行）：理论扩展

提出 Tell 应成为"method + critic + trigger + exit + case pack"的迁移工程对象。8 个契约。

**认知价值**：将 Tell 从"提示词"升级为"迁移工程对象"——真正的认知推进。

### 372号（08-12，2,071行）：全需求

把 8 个契约扩展为 24 项，加上 15 步闭环、28 条学术路线、6 门审计。

**膨胀**：8→24 契约是 3 倍枚举膨胀。15 步闭环在 0 步验证时设计。28 条学术路线在 0 条验证时枚举。

### 373号（08-12，1,029行）：六门审计 POC 套装

把 372号的 6 门审计操作化为 8 个 POC，每个 POC 有目标、方法、输出、通过标准。

**膨胀**：8 个 POC 在 0 个 POC 运行时设计。每个 POC 的通过标准在还没有任何经验数据时定义。

### 387号（08-13，3,570行）：非特化证据工厂

把 373号的 8 个 POC 升级为完整系统设计：8 个逻辑组件、4 条隔离边界、20+ 数据模型、3 套坐标系、74 个 Gate。

**膨胀**：从 8 个 POC 到完整系统设计是质的跃迁。387号的 3,570 行在 1 小时 14 分钟内完成——没有迭代沉淀期。

### 升级链的本质

```
371号："Tell 是迁移工程对象"（好的认知推进）
  → 372号："Tell 需要满足 24 项契约"（过早系统化）
    → 373号："需要 8 个 POC 验证"（过早 POC 框架）
      → 387号："需要完整系统来运行 POC"（过早系统设计）
        → 389号/seven-system："需要完整代码来实现系统"（过早工程化）
```

每一层都是前一层的前提条件被无限展开。但最底层——一道能通过 bare 测试的题——始终没有找到。

| 维度 | seven-system | 研究过程 |

## 六、根本原因

研究过程过度设计的根本原因与 seven-system 相同：**试图用"系统化"来保证"科学严谨"，但在没有实验反馈的情况下无限展开**。

具体表现：

1. **没有 MVP**——整个 5 天研究过程中，没有一次完整的"bare失败→给Tell→成功"闭环被验证。唯一接近的是 283号（bare 0% → tree 67%），但它缺乏因果控制。在没有 MVP 的情况下，研究过程转向了"设计完整体系"。

2. **出题困境阻断了实验路径**——355/357/358/363 四轮 bare 测试全部失败（题目被 GLM-5.2 做出来），使得"给 Tell 测试有效性"这条路径无法执行。面对这个阻断，研究过程没有停下来重新定义问题，而是转向了"设计验证体系"——372/373/387。

3. **"系统化"替代了"实验"**——当实验路径被阻断时，研究过程用系统化（24项契约、15步闭环、8个POC、6门审计、完整系统设计）来制造"在推进"的感觉。但系统化不产生新认知——它只是把已有认知重新包装成更 elaborate 的形式。

4. **逐节批准模式**——387号的 13 个章节中 10 个标"已批准"。用户逐节批准了设计方向，但"设计批准"不等于"实现授权"。387号自身明确写着"实现授权：NOT GRANTED"，但 389号和 seven-system 的实际实现跨越了这个边界。

---

## 七、更合理的路径

研究过程在 283号之后就已经有了足够的认知基础来做一个最小实验：

```
283号的弱阳性结果
  → 选一道 283号用过的 bare 失败题（如1962）
  → 构造一个最小 TellCore（如候选C的局部-全局表示切换）
  → 跑一次 bare vs guided 对照
  → 看结果
```

这条路径只需要 1 道题、1 个 TellCore、2 次运行（bare + guided）。如果成功，就有了第一个因果证据；如果失败，就知道了什么不行。

但研究过程没有走这条路径。它走了：

```
283号弱阳性
  → 344-347号理论细化
    → 349号68人分析
      → 350号2600次实验方案
        → 355/357/358/363四轮出题失败
          → 372号24项契约
            → 373号8个POC
              → 387号完整系统设计
                → seven-system 66K行代码
```

每一步都比前一步更 elaborate，但每一步都离"跑一次实验"更远。

## 八、调查方法说明

本调查基于以下手段：

1. **全量文档行数统计**——按日期、按阶段、按文档逐个统计行数
2. **关键词频率追踪**——追踪"因果""Gate""审计""隔离""非特化"等关键词在关键文档中的出现频率，识别治理递归的升级轨迹
3. **文档内容抽样通读**——通读了 000、277、280、283、333-336、344、349、350、352a、355/357/358/363、356、371、372（全文）、373、382、387（全文）、388（全文）、389 的关键内容
4. **认知增量 vs 系统化膨胀分析**——逐个文档判断其认知推进内容占比
5. **372号各节行数分析**——分析 372号 16 个章节的行数分布，识别核心认知 vs 系统化
6. **388号全量审计文档分析**——分析 388号对 54 份文档的归类处置

本调查不否定研究过程中的真实认知推进。000号的 tell/hint 二元组、277号的泛化命题、280号的负结果、283号的弱阳性、333-336号的分类学认知、372号"因果充分的取商"定义——这些都是真正的认知贡献。问题在于这些认知贡献只占全部研究文档的约 10-15%，其余 85-90% 是过早系统化、重复学习和治理膨胀。
