## 二、实现路径

### Phase 0：最小端到端实验（1道题，4次运行）

**目标**：跑通第一条因果对照实验，得到第一条contrast级EvidenceRecord。

```
选1631（已有bare失败记录）
  → 用TellCore v0最小充分字段集（7字段）构造HintInstance
  → 跑4组对照：R（problem-only restart）/ L（lineage-only）/ D（direction-only）/ LD（lineage+direction）
  → 计算3个contrast：LD−L、(LD−L)−(D−R)、LD−R
```

**不需要的东西**（这个Phase不需要）：
- 不需要74个Gate
- 不需要3层授权链
- 不需要20+个YAML schema
- 不需要25个工作包DAG
- 不需要638条MUST条款

**需要的东西**（这个Phase最少需要）：
- solver_harness能跑4次Solver（已有）
- TellCore v0的7字段YAML（已定义）
- 1631的bare失败记录（已有）
- 1631的lineage（从283号的tree组实验中提取）
- 一个简单的contrast计算脚本

**成功标准**：
- LD成功且L/D不成功 → 初步支持"脉络+方向"组合的因果贡献
- LD成功但(LD−L)≈(D−R) → direction不依赖lineage，lineage只是载体
- LD不成功 → TellCore v0或HintInstance有问题，需要诊断

**如果成功**：有了第一个因果证据，可以进入Phase 1。
**如果失败**：知道了什么不行，诊断原因后修正TellCore v0或实验设计。

### Phase 1：跨题泛化验证（4道题，16次运行）

**目标**：验证TellCore v0能跨题泛化。

```
对1631/1843/1709/1962各跑4组对照（R/L/D/LD）
  → 4题×4组 = 16次运行
  → 看LD是否在多道题上成功
```

**关键观察**：
- 1962在283号tree组仍失败——TellCore v0的internal_policy（操作路径）是否解决了这个问题？
- 1709的2-adic赋值——TellCore v0的层次2是否被正确触发？

**需要新增的东西**：
- 4道题的lineage提取
- false_friend题（如CC-013的结构，但数学解答必须正确——需要独立数学核验）
- boundary题（如CC-018：1962变体"2的幂"改为"素数"）

### Phase 2：Selector验证（POC-2可选择）

**目标**：验证selector能选中正例、拒绝假朋友。

```
对source_trace题 + false_friend题 + boundary题
  → 跑selector（基于trigger_boundary + negative_boundary）
  → 看selector决策是否正确
```

**需要新增的东西**：
- selector实现（基于TellCore v0的trigger_boundary和negative_boundary做匹配）
- 数学正确的false_friend题（CC-013有数学错误，需要修正或新构造）

### Phase 3：从真实运行中沉淀治理结构

**目标**：基于Phase 0-2的真实运行经验，确定需要哪些Gate和隔离机制。

```
检查Phase 0-2的运行：
  → 有没有出现"Solver偷看答案"？→ 如果有，才实现答案隔离
  → 有没有出现"AI自己签了Gate"？→ 如果有，才实现人工Gate验签
  → 有没有出现"重跑结果不一致"？→ 如果有，才实现append-only
  → 有没有出现"题目被修改后沿用旧baseline"？→ 如果有，才实现版本化
```

**原则**：治理结构的规模跟随实验规模增长，不是预先最大化。

## 四、需要避免的陷阱

### 4.1 不要重蹈seven-system覆辙

| seven-system的过度设计 | eight-system应如何避免 |
|---|---|
| 561个错误码（182个从未引用） | 按需定义，从实际故障中提取 |
| 638条MUST条款（全PENDING） | 按需定义，从真实运行中沉淀 |
| 25个工作包DAG（只实现1个） | 先做1个最小端到端，成功后再扩展 |
| 3层授权链 | 人工Gate不可绕过（概念），不需要3层 |
| 74个Phase Gate | Gate数量跟随实验规模增长 |
| 文档量≈代码量47% | 精简文档自包含即可 |

### 4.2 不要跳过因果控制

283号的核心教训：没有因果控制的"成功"只是"污染性包阳性"。eight-system的每一次实验都必须有对照arm，不能只跑guided看成功不成功。

### 4.3 不要在0次验证时枚举全部可能性

349号26种思维力、350号2600次实验方案、372号24项契约——这些都是"先建分类再验证"的典型。eight-system应先验证1个TellCore，成功后再扩展。

### 4.4 不要让题包设计者充当数学Judge

CC-013的数学错误证明了这一点。eight-system的每道题的数学解答必须经过独立核验，不能由出题者自己标`verified`。

## 六、成功标准

### 6.1 Phase 0成功标准

- 1631的LD组成功（AI用了目标方向并给出正确proof）
- 1631的L组和D组不成功（或成功但proof未用目标方向）
- contrast `LD−L` 为正——direction的增量效果存在
- contrast `(LD−L)−(D−R)` 为正——direction依赖lineage
- 得到第一条contrast级EvidenceRecord

### 6.2 Phase 1成功标准

- TellCore v0在至少3/4道题上LD成功
- 1962的LD成功（操作路径解决了283号tree组失败的问题）
- false_friend题被selector拒绝
- boundary题被selector标为boundary

### 6.3 最终成功标准

- 有至少一条TellCore通过了六门审计中的前四门（可选择/可执行/可终止/可归责）
- 有因果证据支持"TellCore独立于lineage/重启/预算的因果贡献"
- 治理结构是从真实运行中沉淀的，不是预先铸造的
