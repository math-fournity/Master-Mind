## 1. 因果实验骨架（R4）

**来源**：387号 §1.1（L36-54）、§8（L1424-1808）、§9（L1812-2213）

### 为什么需要

283号实验中，lineage、方向、新AI和新token窗口同时改变，最终成功只能支持"整个干预包有效"，不能证明其中任何一个组件单独有效。387号§2.1明确指出：283号"没有隔离TellCore、Renderer、lineage、人工选择、重启与新增预算各自的因果贡献"。因此需要一套因果实验骨架来隔离各因素的贡献。

### 保留的合理工程约束

1. **预注册（Preregistration）**：实验计划（arms、contrasts、资源、随机化、停止规则）必须在看到结果前冻结。禁止"结果后修改Case角色、MechanismContract、endpoint或阈值"。（387号 L1316-1318, L1720-1745）

2. **随机化（Randomization）**：按case、source rollout、失败层和迁移距离做block；同一block中的arm交错运行，降低模型漂移、时段、限流和并发状态的影响。随机化方案（allocation table、random seed commitment、concealment rule）事前冻结。（387号 L1748-1755, L1768-1775）

3. **对照arm（Control arms）**：所有Tell干预都与"等调用次数、等新增生成预算的fresh restart + problem-only"比较。核心2×2矩阵：R（problem-only restart）、L（lineage-only）、D（direction-only）、LD（lineage + direction）。关键contrast：`LD − L`（direction的增量效果）、`(LD − L) − (D − R)`（direction是否依赖lineage）、`LD − R`（总效果）。还必须有distractor arm（LX）排除"任何额外建议都可能有帮助"的替代解释。（387号 L1447-1448, L1540-1561）

4. **盲化（Blinding）**：Proof Judge尽可能盲于arm；Solver盲于四轴Case标签和目标结论；Blinding Broker机械生成不可互相回看的角色视图。审计sealed前不得出现treated/control标签。（387号 L1774, L1308-1311, L2071）

5. **三审（Three independent audits）**：Process Auditor（判断机制执行）、Proof Judge（判断数学正确性）、Leakage Auditor（检查答案泄漏）三种真值分权，各自sealed后才能合并。禁止"从最终答对反推采纳了Tell"、"从proof中出现方向词反推认知动作已发生"、"从candidate_solved反推证明完整"。（387号 L1812-1828, L1845-1856）

6. **contrast级EvidenceRecord**：单次运行只产生观察性的RunAudit；跨arm、跨重复、按problem/source rollout聚合后的预注册randomized contrast，才允许对Tell因果效应生成EvidenceRecord。CaseFamily层只能聚合已经成立的contrast级EvidenceRecord，绝不能用无对照的成功多数票替代随机contrast。（387号 L2157-2178）

### 剔除的过度设计

- 74个Gate的完整Phase Gate定义（D3治理递归）——P0-P9每个Phase都有前置条件、必需产物、PASS/FAIL条件的完整表格（387号 L3121-3139）。保留"关键阶段需要门控"的概念，剔除74个Gate的逐字段定义。
- 3层授权链 EEA→LiveRunPermit→AuthorizationConsumptionReceipt（D3）——文档中未直接出现此名称，但GateDecision + HumanTask + HumanGateDecision的三层结构（L2909-2962）构成了类似的授权递归。保留"人工Gate不可绕过"的概念，剔除三层签名对象链。
- 20+个YAML schema的完整定义（D1过早全面化）——RoleExecutionContract、CognitiveWorkerCapabilityReport、AIInvocationReceipt、ReviewIndependenceRecord、CandidateManifest、BareBaseline、MechanismContract、TransformationPlan、ExperimentPlan、RandomizationPlan、AnalysisPlan、RunArtifactBundle、ReasoningEvent、DivergenceRecord、ProofJudgment、LeakageAuditContract、RunAudit、RevisionProposal、TellStrategyRelease、RollbackRecord、RuntimeManifest、WorkItem、WorkEvent、GateDecision、HumanTask、HumanGateDecision、ExecutionAttempt、LaunchReceipt等。**保留字段名清单作为参考**，剔除完整YAML定义。

## 2. 多系统边界隔离（R4）

**来源**：387号 §4.3（L268-273）、389号 §2（L32-76）

### 为什么需要

题海系统的科学职责是大规模测量模型能力边界，不是Tell因果实验。题海生产队列不能被证据实验的arm、重试和人工Gate污染。第六代system尚不是可依赖的完整producer（enter.py未实现、process_absorb.py未实现、solve.py未实现）。

### 保留的边界规则

1. **只读消费题海的冻结bundle**：证据工厂只读消费现有管道导出的冻结CandidateManifest，不直接消费即时Redis或未经聚合的DB标签。（387号 L172-173, 389号 L44）

2. **不写回math:\***：POC结果不回写生产流水线的原始bare记录和Redis运行队列。（387号 L270, 389号 L44）

3. **不import system.\***：Seven不能直接`import system.*`、共享其DB写模型或运行目录。未来只允许通过`versioned JSON bundle + SHA-256 + artifacts → seven anti-corruption adapter → seven内部对象`对接。（389号 L55-62）

4. **晋级隔离**：自动评分不能直接改变TellCore或分类学本体，只能提出RevisionProposal。Promotion只改变证据工厂内部Registry，未来接入生产系统需要新的明确授权和接口设计。（387号 L272, L2706-2707）

### 剔除的过度设计

- 独立`evidence:*`控制面的完整Redis队列设计（D5无关工具/流程）——`evidence:snapshot → evidence:case → evidence:plan → evidence:run → evidence:seal → evidence:audit:{process,proof,leakage} → evidence:assemble → evidence:review → evidence:quarantine`的完整队列语义（L2713-2726）。保留"独立控制面"概念，剔除完整队列设计。
- WorkEvent/WorkItemProjection/OutboxEvent的完整事件溯源设计（D3治理递归）——保留"append-only事件是真值源"概念，剔除完整事件溯源对象定义。

## 3. 答案隔离（R4）

**来源**：387号 §4.3（L271）、§7.10（L1296-1317）、§9.2（L1845-1856）、389号 §16.6（L870-880）

### 为什么需要

如果Selector、Hint生成器或Process Auditor能看到答案，它们可能（有意或无意地）把答案信息编码进Hint或过程判断中，制造伪因果。同一个AI既看答案、又生成Hint、又判断Hint是否有效，会形成不可审计的自我循环。

### 保留的规则

**永久不可见答案的角色**：Selector、HintRenderer、Solver、Process Auditor。

> "Selector、Hint生成器、Solver与Process Auditor永久不可见目标题答案/标准解答"（387号 L271）

> "permanently_denied_roles: [selector, renderer, solver, process_auditor]"（387号 L592）

**按角色分权可见内容**（387号 L1298-1314）：

| 角色 | 可见内容 | 禁止内容 |
|---|---|---|
| Trace-side Analyst | 题面、bare thinking、运行证据 | 标准解答、目标机制标签 |
| Solution-side Analyst | 题面、核验解答 | bare thinking与失败标签 |
| Question Architect | MechanismContract、CoverageCell、AuthoringBrief | 目标题未来实验结果、Devin输出 |
| Adversarial Editor | 冻结公开题面 | MechanismContract、Tell、作者scratch、密封解答 |
| Math Verifier | 公开题面、候选密封解答的核验视图 | MechanismContract、Tell、bare thinking、Devin输出、作者scratch |
| Selector | 题面、当前problem state、Tell库 | 预注册正确标签、密封答案 |
| HintRenderer | TellCore、题面、允许的lineage | 标准解答、Judge结论 |
| Solver | 题面、对应干预提示 | 答案、标准解答、四轴Case标签 |
| Process Auditor | 去除干预文本的有序trajectory、预注册过程契约 | 密封解答、真实arm、Hint文本、Proof结论 |
| Proof Judge | 题面、最终证明、密封Verification视图 | Tell、真实arm、完整trajectory、Process/Leakage结论 |
| Leakage Auditor | Solver完整可见payload、密封解答的泄漏对照视图 | 运行结果与过程结论（pre-run报告sealed前） |

**物理隔离要求**：逻辑字段隐藏不能替代物理Vault/身份/路径隔离。答案隔离必须是物理视图隔离，不是从一个JSON里删掉字段。（387号 L271, 389号 L872）

### 剔除的过度设计

- Vault/容器边界/一次性访问token/append-only access log的完整设计（D3治理递归）——保留"需要物理隔离"的概念，剔除具体隔离机制设计。
- `sealed_solution_acl`中verification_view/proof_view/leakage_view的三类最小权限视图的完整ACL设计（D1过早全面化）——保留"按角色分权"的规则表，剔除ACL对象定义。

## 4. 人工Gate不可绕过（R4）

**来源**：387号 §1.3（L76-82）、§7.5（L1145-1162）、§11.8（L3149-3179）、389号 §16.2（L790-793）

### 为什么需要

模型不能自己签发Gate——否则系统会在无人监督下自动修改TellCore、Renderer、Selector或validated scope，可能把伪学习伪装成真学习。具体需要人工Gate的场景：

1. **QuestionRelease Gate（G-Q-RELEASE）**：受控生成的题目发布前，必须由人工批准不可变QuestionRelease。AI不得自批。（387号 L1157, 389号 L824）

2. **Case Role Freeze Gate（G-CASE-ROLE）**：bare结果出来后，由人工冻结Case身份并形成CasePackVersion。实验后禁止移动题目角色（如假朋友被Tell成功解决后改成正例）。（387号 L1274-1280, L1169）

3. **Revision Gate（两次签署）**：Tell晋级、边界修改、退休必须经过人工Revision Gate。包含两次职责分离的签署：Pre-evaluation approval（审查failure localization和proposal）和Post-evaluation decision（决定PROMOTE/RESTRICT/REJECT/QUARANTINE）。（387号 L3174-3177）

### 保留的概念

- 自动系统只能形成RevisionProposal，不能静默覆盖TellCore或分类学本体。（387号 L82）
- TellStrategy的tested、restricted、validated、retired状态不得由单一自动评分直接决定。（387号 L81）
- 无人处理时保持HUMAN_PENDING，绝不超时默认通过。（387号 L3179）
- 自动紧急动作只写可逆runtime quarantine overlay，不修改release、scope或active pointer。（387号 L3179）

### 剔除的过度设计

- HumanTask + HumanGateDecision + GateDecision的三层签名对象链（D3治理递归）——HumanGateDecision包含actor_id、actor_role、actor_organization_or_team、actor_authorization_snapshot_hash、conflict_of_interest_declaration_hash、signer_key_id_or_verification_method、signature、signing_payload_canonicalization_version、signature_verification_verdict等15+字段（L2941-2962）。保留"人工Gate不可绕过"的概念，剔除完整签名对象链。
- HumanTaskPort + HumanGateService的完整接口设计（D3）——保留"人工任务与模型调用分离"的概念，剔除接口定义。

## 5. append-only + 版本化（R4）

**来源**：387号 §3（L198）、§5.8（L694-706）、§7.5（L848, L1215）、§10.1（L2220-2236）

### 为什么需要

如果原始证据、旧Tell版本或负结果可以被原地覆盖，系统就无法审计"Tell为什么被放宽、收窄、拆分、合并或退休"。如果题面可以被原地修改后沿用旧审稿或旧baseline，就会形成不可追溯的实验污染。

### 保留的规则

1. **永不原地覆盖的内容**（387号 L696-704）：
   - 原始attempt证据
   - 旧Tell版本
   - 负EvidenceRecord
   - 替代因果解释
   - 被拒绝的RevisionProposal
   - 题目角色冻结记录
   - 分类学坐标的历史版本

2. **题面变化必须新版本**：任何题面文字、条件、数值、答案或解答修改都必须创建新QuestionDraftVersion，使旧AdversarialReview、VerificationDossier、QuestionRelease和bare结果全部失效。禁止原位修补后沿用旧审稿或旧baseline。（387号 L848, L1215）

3. **修订通过新版本和显式supersedes关系**：修订通过新版本和显式supersedes关系表达，不原地修改。这样才能审计Tell为什么被放宽、收窄、拆分、合并或退休。（387号 L706）

4. **Rollback不是删除**：Rollback是原子切换registry中的active_release_pointer，不是删除失败版本或把版本号改回去。失败版本保留不可删除的tombstone。（387号 L2594-2607, L2560）

5. **证据谱系是append-only DAG**：RunArtifactBundle → RunAudit → randomized Contrast EvidenceRecord → RevisionProposal → CandidateRelease → ProspectiveEvaluation → Promotion/Restriction/RollbackRecord。每条边记录source/target hash、规则版本、时间、actor、scope。（387号 L2611-2647）

### 剔除的过度设计

- HashSpec的完整canonicalization规则（D1过早全面化）——保留"需要版本化hash"的概念，剔除RFC8785/JCS canonicalization的完整定义。
- 幂等键的完整hash公式（D1）——保留"幂等键不能只使用problem_id"的概念，剔除8个key的完整hash公式。

## 6. 387号自审警告（R1认知推进）

**来源**：387号 §12（L3507-3541）

### 完整提取

387号§12是整篇文档的自审结论，其中最关键的认知推进是**"不能一次实现到底"的警告和P0 prerequisite列表**。这是387号自身对"研究规格可审 ≠ 当前实现可运行"的清醒认识。

#### "不能一次实现到底"的警告（原文）

> "本文件是系统级umbrella spec，范围大于一个安全的单次实现计划。用户未来若授权实现，必须先把上述prerequisite及P0/P1阶段拆成分别可审、可验收的work package；**不能直接把整份387号文档交给一个脚本'一次实现到底'**。每个Epoch的样本量、效应门槛、并发、soak时间与预算继续由ExperimentPlan/RuntimeManifest预注册，不在架构层伪造全局常数。"（L3541）

#### P0 prerequisite列表（原文，L3533-3539）

以下是实现前必须解决的P0能力阻塞，不能由设计文档中的接口名称冒充已经存在：

1. **Seven StrictDatabasePort**的真实站点只读身份核验、受控DDL、ledger/outbox/CAS/唯一索引能力；
2. **Solver Harness**可强制/可观测的资源契约与结构化安全prompt传递；
3. **provider-neutral ModelRolePort**、Devin/Codex角色adapter、CognitiveWorkerCapabilityReport、AIInvocationReceipt与盲化AuthoringBakeoff；
4. **真正物理隔离的答案与holdout Vault**；
5. **WorkEvent/fencing、artifact sealing和恢复控制面**的落地；
6. 若要验证组合门，准备**真实第二TellCore与CombinationPack**；
7. 若要验证纵向持续学习，运行**多个相互独立的prospective Epoch**。

#### §2.4中的六项实现前P0能力阻塞（L176-185）

1. **数据库能力阻塞**：当前system/db.py的读取路径仍可能通过_ensure_collection产生写副作用，也没有严格只读入口、expected-DB fail-closed、append-only ledger、outbox、CAS/事务和唯一索引。
2. **Harness资源能力阻塞**：当前Solver Harness未必能够强制reasoning_effort、每次生成上限、context limit等全部ResourceContract字段。
3. **Solver无工具能力阻塞**：当前"prompt要求不要调用工具"与缺失工具事件都不能证明tool surface不存在。
4. **安全启动阻塞**：当前Harness存在把prompt或路径拼入shell命令的风险。
5. **物理答案隔离阻塞**：同一Unix身份、dangerous权限和"JSON字段不下发"不构成答案隔离。
6. **认知worker能力阻塞**：当前Seven System尚无ModelRolePort、DevinCliModelRoleAdapter、CodexExecModelRoleAdapter、角色级能力报告或调用收据实现。

## 7. 合理工程化决策（来自389号）

**来源**：389号 §0-§6（L1-208）

### 保留的合理决策

1. **代码自包含**：seven-system/的代码、运行资产、文档、Schema和测试全部自包含于repo。不依赖外部系统才能运行。（389号 L13, L134-145）

2. **大对象留D盘**：epochs、live、staging、CAS、logs、quarantine、vault等大对象留在D盘（/data/seven-system-data/）。（389号 L137-138, L564）

3. **小型DB元数据复用原逻辑数据库**：Seven使用原Arango服务和原逻辑数据库xishujuzhen_math_glm52，但只使用隔离的seven_*_v1集合和索引，不复用、不改写题海系统或第六代system/的业务集合。（389号 L559-568）

4. **物理存储与逻辑能力解耦**：Arango物理字节已经由OrbStack image由D盘承载（A-WP1-D=PASS）；未使用专用host bind只是运维告警（A-WP1-BIND=WARNING_NOT_DEDICATED），不是逻辑数据库接入的前置Gate。（389号 L565, L603-604）

5. **首版只实现P0与P1 scaffold**：不连接数据库、不写Redis、不启动Solver，也不把脚手架冒充完整证据工厂。没有start命令是安全边界，不是遗漏。（389号 L13, L165）

6. **从题海系统吸收的工程经验**（389号 L82-92）：
   - Solver工作目录必须在repo之外
   - 真实Solver只能通过solver_harness.py launch
   - Solver叶子实例在实验契约上不得做工具调用
   - 题面和干预应在启动时直接可见，避免读文件工具
   - 管道服务与Solver session解耦
   - Runner/Collector/Reporter/Retry职责分离
   - Redis、ArangoDB、文件证据三层分工
   - 3秒launch interval是当前站点重要下限
   - 基础设施失败与科学终态分开
   - status/health必须到tmux、文件、trajectory前线，不能只信DB数字
   - graceful stop、dry-run-first recovery和双向追溯

7. **不复制的实现（信任缺口）**（389号 L96-107）：
   - Runner先写严格无工具AGENTS，Harness随后二次包装，外层语义和内层存在冲突
   - CLI仍以dangerous permission运行，Prompt约束不等于工具表面被关闭
   - 现有Collector缺文件时会当成无工具，形成fail-open
   - 工具检查主要挂在proof成功分支，而不是所有终态独立执行
   - Redis claim的dequeue→running不是完整事务
   - DB写失败后仍可能ACK/删除running

8. **从第六代system吸收的设计思想**（389号 L112-127）：
   - 吸收：code/docs/assets/tests自包含的目录思想、每阶段固化AGENTS与输入资产、三阶段"AI格化→程序枚举→AI语义综合"方法、run manifest和历史基线、FormalContext闭元素枚举、多套Prompt作为版本化运行资产
   - 不直接吸收：system.schema当前wire模型、system.db当前默认库/ensure collection行为、SolutionRecord.is_verified=True默认信任、五类trace压成三类的有损转换、DONE.md或计数阈值作为科学完成门

### 剔除的过度工程化部分
