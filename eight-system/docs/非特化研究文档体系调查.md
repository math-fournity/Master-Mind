## 三、六个阶段详述

### 阶段0：引导树闭环根定义（08-08）

**文档**：`000-v0-2026-08-08-引导树闭环-识别端结构定义.md`（213行，项目根目录）

**核心贡献**：定义了系统的核心二元组——**读 tell，给 hint**。

- **tell**：从推理 AI 的 thinking 中读出的分叉信号——AI 没有考虑什么、在哪里可以分叉但没分叉。取自 poker 术语——观察对手揭示出的信息。
- **hint**：给新 AI 的翻译方向——从字典中匹配的具体翻译方向。

**修正历史**（v0→v3 四次修正）：

| 版本 | 修正内容 | 修正来源 |
|---|---|---|
| v0 | 初始认知：识别"卡点"——AI 在哪里卡住了 | — |
| v1 | 修正为：识别"AI 没有考虑的分叉位置"——往往不是 AI 卡住了，而是 AI 走错路了 | 285号/用户修正 |
| v2 | 补充：分叉位置可能在根节点——AI 从第一步就选错方向 | 用户补充 |
| v3 | 命名二元组 tell/hint | 结构定义 |

**tell 的四个组成成分**：

1. 分叉信号（Branch Signal）——识别可以分叉但 AI 没分叉的位置
2. 分叉类型（Branch Type）——对分叉的抽象分类
3. 未探索诊断（Unexplored Diagnosis）——判断 AI 为什么没走这条路
4. 方向匹配（Direction Matching）——从诊断到字典中翻译方向的映射

### 阶段1：POC-VMS 实验系列（08-08）

**文档**：277-289号（约2,453行，`dev-docs/`）

**核心演进**：

#### 277号：hint 泛化性命题

用户提出核心命题：

> hint 是可以泛化的，也就是说，不是只有 hint 来源的那道题，甚至是那一类的题目可以使用这个 hint，这个 hint 是可以在一道样子完全不同的，甚至解题思路的原题 99% 没有关系，仅仅就是在这个 hint 这个点上有关系，我们的 hint 也可以发挥作用。

这是"非特化"概念的原始直觉表述。

#### 280号：静态抽象 hint 的负结果

奥赛难题版 A/B/C 对照实验：

- bare：无 hint
- knowledge：知识性 hint（从解答中提取关键定理和步骤）
- highlevel：高 Level 思维方向 hint（统一的"翻译语言"hint，所有题完全相同）

结果：8 道 bare 失败题中，knowledge 2/8，highlevel 1/8。唯一 highlevel 成功没有体现目标"翻译语言"过程。

**结论**：静态、一次性、抽象的同文本 hint 不足以证明非特化指导力。

#### 283号：脉络继承 + 字典方向的弱阳性

POC-VMS-8 实验：bare 0% → tree 67%。

- 1843 使用 T01 模算术
- 1631 使用 T03 二次剩余
- 两个成功案例共享"翻译/表示切换"家族，但不是同一个具体 HintInstance
- tree 组同时改变了失败脉络、题目特定方向、新 AI 实例和新增 token 预算
- 方向仍是人工匹配
- 没有 `lineage only` 或"等资源重启但无 Tell"的控制臂

**最准确的证据表述**：

> "从失败 thinking 提取的脉络 + 人工匹配的题目化方向 + 运行时 HintInstance"在 3 道精选 bare 失败题上取得 2 次成功，并且成功 proof 使用了目标方向；它初步支持完整引导包的可行性，但没有隔离 TellCore、Renderer、lineage、人工选择、重启与新增预算各自的因果贡献。

#### 287-289号：tell 端去特化验证

- 287号：tell 端的去特化与规模检索——系统成败的关键
- 288号（POC-VMS-9）：tell 可以被去特化到拓扑结构级别（problem_type + ai_method_type + gap_type），形式化过滤可以命中目标 tell
- 289号（POC-VMS-10）：小概念标记分辨可以区分拓扑相同且距离极近的 tell——只要两个 tell 能用语言表达出区别，就能定义概念来区分

#### 371号：非特化策略的学术理论扩展

提出 Tell 应成为"method + critic + trigger + exit + case pack"的迁移工程对象。非特化不应只被理解为"把 trace 抽象到某个峰值 Level"，而应升级为迁移工程。

#### 372号：非特化全需求——核心定义

**这是"非特化"概念的成熟定义**：

> 非特化 = 因果归因 + 不变量提取 + 干扰因素取商 + 适用边界学习 + 认知技能编译 + 运行时选择 + 迁移与反事实验证 + 版本化持续细化

三个根本补充：

1. Tell 族不应只是一条按 Level 排列的曲线，而应是一个多轴的候选假设格
2. Tell 不应只被建模成方法说明，而应被建模成认知 Option
3. Tell 有效性不能只靠解题成功率判断，而要证明它在控制混杂后确实改变了预期推理过程

#### 373号：TellV3 六门审计 POC 套装设计方案

六个门：可选择、可执行、可终止、可组合、可归责、可持续学习。

### 发现4：387号自身已经意识到过度设计风险

387号第 12 节自审结论中明确写道：

> 本文件是系统级 umbrella spec，范围大于一个安全的单次实现计划。用户未来若授权实现，必须先把上述 prerequisite 及 P0/P1 阶段拆成分别可审、可验收的 work package；不能直接把整份 387 号文档交给一个脚本"一次实现到底"。

但 389 号和 seven-system 的实际实现恰恰没有遵循这个警告——而是试图一次性实现完整治理体系。389 号虽然声明"首版只实现 P0 与 P1 scaffold"，但实际在 2 天内写了 66K 行代码、25 个工作包 DAG、561 个错误码、638 条规范条款，远超"P0/P1 scaffold"的合理范围。

### 发现5："非特化"概念的演进有清晰的认知跃迁链

```
277号（08-08）：hint 可以泛化（直觉命题）
       ↓ 负证据
280号（08-08）：静态抽象 hint 不够（负结果）
       ↓ 弱阳性
283号（08-08）：脉络继承 + 字典方向有效但缺因果控制（弱阳性）
       ↓ 理论升级
372号（08-12）：非特化 = 因果充分的取商（理论定义）
       ↓ 系统设计
387号（08-13）：非特化证据工厂（系统设计，3570行）
       ↓ 工程化
389号/seven-system（08-13~14）：工程化落盘（66K行代码）
```

### 发现6：387号的"已批准"标注模式值得注意

387号的 13 个章节中，有 10 个标注"已批准"。这些"已批准"是用户在对话中逐节确认的。但"用户确认设计方向"不等于"用户要求实现全部治理体系"——387号第 13 节的 Verdict 明确写着 `实现授权：NOT GRANTED`。

从 387 号的 `实现授权：NOT GRANTED` 到 389 号的"首版只实现 P0/P1 scaffold"，再到 seven-system 的 66K 行代码，存在一个授权范围的跃迁——从"设计批准"跃迁到了"完整实现"，中间缺少明确的"实现范围授权"环节。
