## 第一部分：理念（完整记录）

### 1.1 实验要验证的核心命题

**非特化Hint在半路注入场景下，能否在正交题面上有效启发AI把正确解题方向推理出来。**

拆开说，这个命题包含四个要素：

1. **非特化Hint**——Hint的内容不包含任何具体题目的解法步骤、具体技巧名、具体常数。TellCore v0的direction是"当问题在全局/自然表示下陷入困境时，切换到局部表示（Z/pZ或Q_p），在局部表示下揭示隐藏的代数结构"——这是一个关于思维方向的抽象指导，不是"用mod 8"或"用二次剩余"这种具体操作。

2. **半路注入**——Hint不是预先写在prompt开头的，而是AI先跑到出错后，从中间节点注入的。AI先对新题进行推理，走到卡点（思路出错或走不通），系统从AI的thinking中识别到这个中间节点（就像引导树形成时做的那样），在中间节点上给出Hint，AI从中间继续推理。

3. **正交题面**——测试用的题目不是TellCore v0来源的原题（1631/1843），而是从原题的TellCore机制派生的正交新题。正交新题与原题在题面/领域/对象上不重叠（表面99%不同），但共享同一个深层命题机制（局部-全局表示切换）。这验证了277号用户提出的"99%不相识"命题——"这个hint是可以在一道样子完全不同的，甚至解题思路的原题99%没有关系，仅仅就是在这个hint这个点上有关系，我们的hint也可以发挥作用"。

4. **有效启发**——AI拿到半路Hint后，不是直接给出答案（Hint不包含答案），而是能够从Hint指向的方向出发，自己推理出正确的解题路径并完成证明。有效 = route finding成功 + proof completion成功。

### 1.2 为什么要做这个实验（而不是继续Phase 0/1的方式）

Phase 0和Phase 1做的是"前缀Hint对照实验"——把TellCore v0的direction文本和/或lineage文本预先写死在prompt开头，让AI从头开始推理。这偏离了用户的设计意图，也偏离了第五代系统的核心设计。

**用户的设计意图**（从对话中完整记录）：

> "是'半路提示'，就是已经有过的前期的部分推理步骤，接上了Hint，然后让AI继续进行后续推理。"

> "我们是用devin中的AI做不出来的哪些题目做测试的，测试的方案是制作正交题目，然后用制作的新题去再次测试devin cli，最好，这种情况下，devin cli是做不出来新题的，也就是说新题的难度也是能够让devin cli思路出错的。我们看到了它错误的思路，然后模拟了Tell的识别过程，识别到中间的节点，就像我们在形成引导树的时候做的那样，之后给出非特化的Hint，我们要测试我们的这种Hint，是否在接上了devin cli对于新题的推理之后，能够有效地启发到devin cli中的AI，从而把正确的解题方向进一步推理出来。"

**第五代系统的核心设计**（来自第五代系统技术说明书01-基础概念/03-引导树闭环.md）：

```
引导树（给方向Q）→ 推理AI（探索）→ 解题树（记录结果）
                                    ↓
                              在终点节点检索
                                    ↓
                              引导树（新边=新方向Q）→ 启动新推理AI → ...
```

第五代系统的核心循环是"半路提示"——AI-1从根节点开始推理，走到卡点终止，系统在卡点上检索方向Q，构造脉络（从根到卡点的路径+方向Q），启动AI-2从中间处境继续推理。Phase 0/1做的是"前缀提示"——预先把Hint写在prompt开头，AI从头开始推理——这不是第五代系统的运行方式。

**本实验回到第五代系统的核心设计**：AI先跑到出错 → 系统识别中间节点 → 给非特化Hint → AI从中间继续 → 测试Hint是否有效。

### 1.3 与283号tree组的关系

283号tree组是本实验的直接历史先例——项目历史中唯一一次完整验证了"半路提示+AI真的做出来了"的实验。

283号tree组做了什么：
1. 对3道bare全失败的题（1843/1962/1631），让bare AI先跑
2. 从bare AI的失败thinking中提取脉络到卡点
3. 从字典中匹配翻译方向（T01模算术/T02 p-adic/T03二次剩余）
4. 启动子节点AI，给它脉络+方向，从卡点继续
5. 结果：bare 0% → tree 67%（1843和1631成功，1962失败）

283号tree组的脉络文本格式（以1631_tree.txt为例）：
```
{题目}

=== 已建立的脉络（从bare AI的推理中提取，请先理解验证，然后从转折点继续）===

**已完成的推理：**
1. x_n = 2^{n-1}(a+1)-1。所以 x_1=a, x_2=2a+1, x_3=4a+3。
2. 引理：如果 y_i=2^{x_i}-1 是素数，则 x_i 必须是素数。
...

**卡点：** 不知道如何处理一般奇素数 a 的情况——枚举和covering system方法都无法收敛。

**请从这里继续（翻译方向：T03 二次剩余）：**
关键观察：当 a 是奇素数时：x_3 = 4a+3 ≡ 7 (mod 8)...
```

**本实验与283号tree组的关键区别**：

| 维度 | 283号tree组 | 本实验 |
|---|---|---|
| 题目 | 原题（1843/1962/1631） | 正交新题（题面正交，共享机制） |
| Hint特化程度 | 字典中的具体翻译方向（T01模算术/T02 p-adic/T03二次剩余） | TellCore v0的更抽象direction（局部-全局切换） |
| 验证目标 | 脉络继承+方向注入的有效性 | 非特化Hint在正交题面上的迁移有效性 |
| "99%不相识"验证 | 没有验证（用的是原题） | **核心验证**（正交新题与原题表面99%不同） |

283号验证了"半路提示"在原题上有效（bare 0% → tree 67%）。本实验要验证"半路提示"在**正交新题**上是否同样有效——这才是277号"99%不相识"命题的真正测试。

### 1.4 与277号"99%不相识"命题的关系

277号记录了用户的核心命题（第32行）：

> "实际上，我们只需要证明：hint是可以泛化的，也就是说，不是只有hint来源的那道题，甚至是那一类的题目可以使用这个hint，这个hint是可以在一道样子完全不同的，甚至解题思路的原题99%没有关系，仅仅就是在这个hint这个点上有关系，我们的hint也可以发挥作用。"

277号举例：
- hint"不要正面解，假设结论不成立找矛盾"（反证法思维模式）
- 来源题：A₄没有6阶子群（群论）
- 泛化目标题：证明√2是无理数（数论）、证明素数无穷（数论）、证明某图不存在Hamilton回路（图论）
- "这三道题表面完全不同，解题思路99%不同，但都在'反证法'这个hint点上有关系"

278号把277号的命题操作化为五项判据：
1. 领域不同——一道群论、一道数论
2. 对象不同——一道关于子群、一道关于整数方程
3. 符号不同——一道的群运算符号、一道的整数运算符号
4. 解题思路99%不同——除了共享的hint转折点，其余步骤完全不同
5. 共享同一个hint——同一个hint在两道题上都能发挥作用

280号执行了278号的设计但**静态hint失败了**（highlevel 12% < knowledge 25%）——只给抽象方向"翻译到另一种语言"，AI不知道何时翻译、往哪翻译。

283号改进后成功（bare 0% → tree 67%）——脉络继承解决"何时翻译"，字典方向解决"往哪翻译"。

**本实验是277号命题的最终验证**：用正交新题（表面99%不同）+ 非特化Hint（TellCore v0的抽象direction）+ 半路注入（脉络继承解决"何时"），测试同一个hint在99%不相识的题上能否发挥作用。

### 1.5 非特化Hint的层次结构

本实验测试的Hint是非特化的，但"非特化"有层次。需要明确本实验测试的是哪个层次：

| 层次 | Hint内容 | 特化程度 | 来源 |
|---|---|---|---|
| Level 0 | "用mod 8分析" | 完全特化（具体常数） | 1631的具体解法 |
| Level 1 | "用模算术分析" | 题类特化（具体方法名） | 283号字典T01 |
| Level 2 | "用二次剩余理论" | 方法特化（具体数学工具） | 283号字典T03 |
| **Level 3** | **"切换到局部表示（Z/pZ或Q_p），在局部表示下寻找隐藏结构"** | **非特化（思维方向）** | **TellCore v0的direction** |
| Level 4 | "当问题陷入困境时，换一种表示" | 超抽象（几乎无操作指导） | 280号的"翻译语言" |

**本实验测试Level 3**——TellCore v0的direction。这比283号字典的Level 1-2更抽象，但比280号的Level 4更具体。280号的Level 4失败了（太抽象，AI不知道往哪翻译），283号的Level 1-2成功了（够具体，AI知道用什么工具）。本实验要测试Level 3是否"够具体到能引导route finding，但又够抽象到能在正交题面上迁移"。

### 1.6 "半路提示"与第五代三个推动关系的对应

第五代系统的核心循环由三个推动关系定义（来自05-引导树闭环/01-三个推动关系.md）：

| 推动关系 | 第五代设计 | 本实验对应 |
|---|---|---|
| 推动关系1：引导树→推理AI | 构造脉络，给推理AI作为输入 | Phase C：构造脉络文本（题目+已完成推理+卡点+方向引导），启动新AI |
| 推动关系2：推理AI→解题树 | 采集thinking，提取节点写入树 | Phase A：采集bare AI的thinking；Phase B：从thinking中提取脉络到卡点 |
| 推动关系3：推理AI→引导树 | 在节点上检索方向Q，引导树长出新边 | Phase B：在卡点上匹配TellCore v0的direction（模拟检索） |

**本实验是第五代核心循环的简化版验证**——手动执行三个推动关系，验证循环的工程有效性。与第五代完整循环的区别是：
- 本实验只转一圈（bare→卡点→Hint→新AI），不循环旋转
- 本实验手动执行Tell识别（人工从thinking中找卡点），不用自动检索
- 本实验用正交新题（第五代用原题）

### 1.7 正交出题的核心理念

正交出题不是"出一道类似的题"——而是"出一道表面完全不同但深层机制相同的题"。

**几何语言**（来自386号）：原题和新题是两个向量，在"题面维度"上正交（点积为零），但在"命题机制维度"上平行（共享同一个方向）。

**同构之桥**（来自368号）：新题与源题在题面上正交，但角色关系可迁移。六类角色映射：

| 源题角色 | 目标题中必须对应什么 |
|---|---|
| 表面对象 | 一个不同领域中的本土对象（正交） |
| 合法操作 | 目标领域中自然存在的操作 |
| 自然入口 | 目标领域中也会自然想到的第一条路 |
| 失败机制 | 这条自然路在目标领域中也必然不够（共享） |
| 隐藏结构 | 一个需要迁移视角才能看见的表示/坐标/证书（共享） |
| 完成证书 | 最终能严格证明的对象、势函数、不变量或对偶证书（共享） |

**挑战制造公式**：`挑战 = 自然入口 + 必然失败 + 被遮蔽的可迁移结构 + 可验证证书`

**正交程度谱系**（来自366号）：
- Level 0（不正交）：换皮，保留对象和常数
- Level 1（低正交）：换题面，保技巧
- Level 2（中正交）：换壳，保解法骨架
- Level 3（高正交）：复用失败机制，丢掉具体步骤
- Level 4（最高正交）：复用命题机制，丢掉技巧名和证明顺序

**本实验工作在Level 3-4**——复用TellCore v0的命题机制（局部-全局切换），丢掉具体步骤（不用mod 8/二次剩余这些具体技巧名）和证明顺序。

### 1.8 bare失败题的来源

devin cli做不出来的题目存放在ArangoDB的`devin_problem_runs`集合中（数据库`xishujuzhen_math_glm52`），共6202道unique失败题。失败状态字段`status`+`end_reason`标识失败类型：
- `failed_no_proof`：AI没产出proof
- `failed_token_limit`：AI hit token limit
- `failed_tool_stall`：AI工具调用卡住

已知P0级bare失败题（359号索引，已验证适合Tell测试复用）：1631/1843/1709/1962。

本实验从这些bare失败题的TellCore机制派生正交新题。正交新题也需要经过bare失败验证——确认devin cli对新题也做不出来，且失败卡点对应TellCore机制（需要局部-全局切换）。

### 1.9 选题标准——区分"方向出错"与"token不够"

**不是所有bare失败的题都适合用来做mid-hint实验。** bare失败有两种原因，只有第一种适合测试：

| 失败原因 | 表现 | 是否适合测试 | 原因 |
|---|---|---|---|
| **方向出错** | AI的thinking中走了错误方向，没有使用目标TellCore机制（局部-全局切换） | **适合** | 半路Hint的价值在于纠正错误方向——AI走错了，Hint引导它走到正确方向 |
| **token不够** | AI的thinking中已经在正确方向上（使用了局部-全局切换），但token用尽没能完成proof | **不适合** | AI方向已经对了，Hint没有用武之地——它需要的是更多token，不是方向纠正 |

**如何区分这两种失败原因**：

1. **获取原题的标准解答**——OlympiadBench的test.json中有solution字段（`knowledge/problem_banks/aops_instruct/eval/data/olympiadbench/test.json`），problem_profiles集合中也有solution_text字段（454条有解答的profile）。
2. **获取devin cli的thinking数据**——trajectory目录在`/data/math-agent-glm5.2-tmux-agents-trajectory/{exp_id}/`，其中`exports/conversation.json`是devin cli的完整export，`mitm/thinking_readable.txt`是MITM截获的thinking文本。
3. **对照分析**——读标准解答，识别关键转折点（如1631的"x₃≡7(mod 8)→二次剩余→Euler准则"）；读AI的thinking，看AI是否走到了这个转折点附近。如果AI的thinking中完全没有出现目标方向的关键词（如mod p/二次剩余/p-adic），说明AI方向出错了；如果AI的thinking中出现了目标方向但没完成proof，说明AI方向对了但token不够。

**选题操作流程**：

```
对每道候选bare失败题：
1. 从OlympiadBench test.json或problem_profiles中获取标准解答
2. 从标准解答中识别关键转折点（用了什么TellCore机制）
3. 从trajectory目录中获取AI的thinking数据
4. 对照分析：AI的thinking中是否出现了目标方向？
   - 没出现 → 方向出错 → 适合测试
   - 出现了但没完成 → token不够 → 不适合测试
5. 只有"方向出错"的题才进入正交出题流程
```

**已有的预判**（基于283号和Phase 0/1的数据，已用`analyze_failure.py`脚本验证）：

| 题号 | 标准解答的关键转折点 | AI thinking中的方向 | 判定 | 脚本验证结果 |
|---|---|---|---|---|
| 1631 | mod 8 + 二次剩余 + Euler准则 | covering system/Cunningham/Mersenne列举（0个TellCore关键词） | **方向出错——适合** | ✅ DIRECTION_ERROR |
| 1843 | mod 4分组 | 多项式分析（0个TellCore关键词） | **方向出错——适合** | ✅ DIRECTION_ERROR |
| 1709 | mod 4/mod 8分析t函数 | mod 4×668, mod 8×170, 2-adic×8（大量TellCore关键词） | **token不够——不适合** | ❌ TOKEN_LIMIT |
| 1962 | mod 4+2-adic赋值+分case | mod 4×13, 2-adic×11（已走正确方向） | **token不够——不适合** | ❌ TOKEN_LIMIT |

**结论**：只有1631和1843适合做mid-hint实验——AI方向出错，半路Hint有纠正方向的价值。1709和1962的AI已经在正确方向上了，只是token不够——不适合测试半路Hint的方向纠正效果。

**脚本**：`eight-system/scripts/midhint/analyze_failure.py`——输入题号+exp_id，自动获取标准解答和thinking，对照分析判定失败原因。

### 1.10 选题标准——卡点类型维度（第二个参考维度）

**维度1（方向出错vs token不够）回答了"这道题能不能测"**——只有方向出错的题才适合测试。

**维度2（卡点类型）回答了"这道题适合测方案的哪个方面"**——不同题的卡点类型不同，测试TellCore v0的不同子方面。

TellCore v0不是一个单一的东西。它有：
- **parameter_slots**：p的选择、level的选择（mod p vs p-adic赋值）、objects的选择
- **internal_policy 4步**：step2确定p和level → step3映射到局部表示 → step4找隐藏结构 → step5提升为全局结论
- **progress_model 4个信号**：信号1取模 → 信号2发现隐藏结构 → 信号3建立联系 → 信号4提升为全局

不同的题，标准解答用的局部-全局切换子类型不同，测试的是TellCore v0的不同方面：

| 卡点类型 | 题号 | 标准解答的关键操作 | 测试TellCore v0的方面 | 难度 |
|---|---|---|---|---|
| **mod p分组/同余**（p显然） | 1843, 1678, 2095, 2111 | mod 4分组/同余 → 直接矛盾 | **信号1**（AI开始取模）——最基本的"切换到局部表示"。如果Hint连这个都引导不了，说明Level 3太抽象 | 低 |
| **mod p同余**（p不显然） | 2843 | mod 11同余 → B=R | **parameter p选择**——AI需要自己确定p=11，不是显然的p=2/4 | 中 |
| **二次剩余+Euler准则** | 1631 | mod 8 → 二次剩余 → Euler准则 → 全局矛盾 | **信号2**（发现隐藏结构）+ **信号4**（提升为全局）——两步局部-全局切换 | 高 |
| **LTE lemma** | 1929, 2024 | Lifting The Exponent lemma | **信号4**（提升为全局结论）——LTE lemma本身就是"局部→全局"提升工具 | 高 |
| **p-adic赋值** | 2040 | valuation（赋值） | **parameter level选择**——AI需要选Q_p（赋值）而非Z/pZ（取模） | 中 |
| **多步mod p推导** | 1964 | mod p分析×12步 | **信号2**（发现隐藏结构）——需要多步局部分析，不是一步取模 | 中高 |
| **CRT（多模数组合）** | 2921 | mod 16 + mod 625 → CRT | **信号3**（建立联系）——组合多个局部信息合成全局结论 | 高 |

**选题策略**：不是随便从11道中选2道——应该选**卡点类型不同**的题，覆盖TellCore v0的不同方面。

**推荐的选题组合**：

| 组合 | 源题1 | 源题2 | 覆盖的方面 | 推荐理由 |
|---|---|---|---|---|
| **A（最基础+最深层）** | 1843（mod 4分组） | 1631（二次剩余+Euler） | 信号1 + 信号2/4 | 一道测最基本的方向引导，一道测深层的结构发现+全局提升。如果两道都成功，说明Hint从最基础到最深层都有效 |
| **B（p选择+提升工具）** | 2843（mod 11，p不显然） | 2024（LTE lemma） | parameter p选择 + 信号4 | 一道测AI能否自己确定p，一道测AI能否用局部→全局提升工具。两道都涉及"AI需要自己做选择" |
| **C（level选择+多步推导）** | 2040（p-adic赋值） | 1964（多步mod p） | parameter level选择 + 信号2 | 一道测mod p vs p-adic的层次选择，一道测多步局部分析的持续性 |

**推荐组合A**——覆盖面最广（从最简单的信号1到最难的信号2/4），且两道题都是已有最多实验数据的P0级题（1631/1843在283号tree组中已验证过半路提示有效）。

**如果实验资源允许跑更多题**，可以追加组合B或C中的题，覆盖TellCore v0的更多方面。

## 第二部分：实验设计

### 2.1 整体流程

```
步骤1：选bare失败题（从6202道中选，优先用已验证的1631/1843）
步骤2：构造正交新题（从源题的TellCore机制派生，Level 3-4正交）
步骤3：数学核验正交新题（答案正确+关键转折点需要局部-全局切换）
步骤4：Phase A — bare跑正交新题，确认AI做不出来，采集thinking
步骤5：Phase B — 从bare thinking中提取脉络到卡点（模拟Tell识别中间节点）
步骤6：Phase B — 匹配非特化Hint（TellCore v0的direction，不泄漏具体技巧）
步骤7：Phase C — 启动新AI，给它脉络+Hint（半路提示），从中间继续
步骤8：对比bare vs mid-hint的成功率
步骤9：写实验报告
```

### 2.2 正交题目构造

**从TellCore v0派生正交题**：

TellCore v0的核心机制是"局部-全局表示切换"——当问题在全局/自然表示下陷入困境时，切换到局部表示（Z/pZ或Q_p），在局部表示下揭示隐藏的代数结构，将局部发现提升为全局结论。

| 源题 | TellCore机制 | 正交新题方向 |
|---|---|---|
| 1631（Mersenne型递推素数） | mod 8 + 二次剩余 + Euler准则 | 构造一道题面与Mersenne/递推/素数无关的题，但关键转折点需要mod p分析揭示隐藏结构 |
| 1843（多项式因式擦除） | mod 4分组 | 构造一道题面与多项式/因式/擦除无关的题，但关键转折点需要mod p分组揭示隐藏结构 |

**正交题目要求**（来自386号§3.3）：
1. **bare失败验证**——新题在bare中AI做不出来（路线层失败，且失败卡点对应目标命题机制）
2. **正交性验证**——新题与源题在题面/领域/对象上不重叠（没有共享的关键词、定理名、对象名）
3. **机制共享验证**——新题与源题共享同一个Level 3-4命题机制（失败机制+隐藏结构+证书）
4. **Tell迁移验证**——TellCore在新题上能正确触发（满足trigger_boundary，不满足negative_boundary）
5. **非泄漏验证**——TellCore不泄漏源题的具体lemma或解法步骤

**构造方法**：用368号同构之桥七步法，填写六类角色映射表（表面对象/合法操作/自然入口/失败机制/隐藏结构/完成证书）。

### 2.3 Phase A — Bare跑正交新题

对每道正交新题，启动bare AI（只有题目，无任何Hint）：
- 通过solver_harness启动，采集完整thinking（mitmproxy流式截获）
- 记录AI的推理路径和卡点
- 确认AI做不出来（路线层失败——AI没有使用局部-全局切换方向）

**产出**：每道正交新题的bare thinking + 卡点位置

**bare成功的处理**：如果bare AI做出来了，说明新题对AI不够难——需要重新构造更难的正交新题，或者放弃这道题。

### 2.4 Phase B — 脉络提取 + Hint匹配

**脉络提取**（模拟Tell识别中间节点——第五代推动关系2和3）：
1. 分析bare AI的thinking，找到AI走到哪里卡住了（思路出错或走不通的位置）
2. 提取从题目到卡点的完整推理脉络（AI自己建立的推理，不是标准解答）
3. 标注卡点："AI在这里不知道往哪走了"——描述AI当前的数学处境

**Hint匹配**（模拟Tell识别中的方向匹配——第五代推动关系3）：
1. 根据卡点的数学处境，匹配TellCore v0的direction
2. direction是非特化的——"当问题在全局/自然表示下陷入困境时，切换到局部表示（Z/pZ或Q_p），在局部表示下寻找隐藏的代数结构"
3. **不泄漏具体题目的解法**——不说"用mod 8"或"用二次剩余"或"用mod 4分组"
4. 可以指导AI"切换到局部表示"，但不指定具体切换到哪个p、用什么局部工具

**脉络文本格式**（参考283号tree组）：
```
{正交新题题目}

=== 已建立的脉络（从bare AI的推理中提取，请先理解验证，然后从转折点继续）===

**已完成的推理：**
{从bare thinking中提取的推理步骤，到卡点为止——这是AI自己建立的推理，不是标准解答}

**卡点：** {AI在这里不知道往哪走了——描述AI当前的数学处境}

**请从这里继续（方向引导）：**
{TellCore v0的direction——非特化Hint}
"当问题在当前表示下陷入困境时，尝试切换到局部表示（Z/pZ或Q_p），
在局部表示下寻找隐藏的代数结构，将局部发现提升为全局结论。"
```

### 2.5 Phase C — 半路提示实验

启动新AI（全新session），给它脉络+Hint文本：
- AI从中间处境继续推理（不是从头开始——脉络文本中已包含到卡点的推理）
- 通过solver_harness启动，采集完整thinking
- 检查AI是否找到了正确方向（局部-全局切换）并完成证明

**关键**：新AI收到的是"脉络+Hint"文本，不是"题目+前缀Hint"。脉络文本中包含了bare AI的推理到卡点为止的部分，新AI从卡点继续。这就是"半路提示"——Hint接在已有推理的后面，不是放在题目开头。

## 第三部分：对照与判定

### 3.1 Arms（每道正交新题2组对照）

| Arm | 名称 | 内容 | AI起点 |
|---|---|---|---|
| R | bare | 只有正交新题（Phase A的数据可复用） | 从头开始 |
| MH | mid-hint | 脉络（从bare thinking提取到卡点）+ 非特化Hint（TellCore v0的direction） | 从中间处境继续 |

### 3.2 Contrasts

| Contrast | 计算 | 含义 |
|---|---|---|
| C1: MH−R (proof) | MH proof成功 − R proof成功 | 半路Hint对proof completion的总效果 |
| C2: MH route finding | MH找到正确方向的比例 | 半路Hint能否引导route finding（AI是否使用了局部-全局切换） |
| C3: MH proof completion | MH完成proof的比例 | 半路Hint能否引导proof completion（从route到完整证明） |

### 3.3 成功标准（三层判定）

| 层 | 判定 | 方法 |
|---|---|---|
| 路线层 | AI是否使用了TellCore v0的方向（局部-全局切换） | 检查thinking中是否出现mod p/p-adic/局部表示/取模/赋值等关键词，且用于关键转折 |
| 证明层 | proof是否数学正确 | 人工核验proof内容 |
| 落盘层 | proof.md是否生成 | 检查文件存在性 |

**成功定义**：proof.md存在 + 数学正确 + proof中使用了局部-全局切换方向

### 3.4 正交性验证

正交新题必须通过以下验证才能用于实验：

| 验证项 | 方法 | 标准 |
|---|---|---|
| bare失败 | 跑bare AI | AI做不出来（路线层失败） |
| 正交性 | 人工检查 | 新题与源题在题面/领域/对象上不重叠 |
| 机制共享 | 人工检查 | 关键转折点需要局部-全局切换 |
| 非泄漏 | 人工检查 | TellCore v0的direction不包含源题的具体技巧名/常数/lemma |
