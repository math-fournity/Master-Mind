## 2. 本轮发现并修复的实现漂移

### 2.1 SignedObjectProfile 与 Schema 字段名漂移

问题：

- `AuditAssignment` profile 要求顶层 `owner_key_id`，但 `audit-assignment.v1.schema.json` 没有该字段；
- `AuditRecord` profile 要求顶层 `auditor_key_id`，但 `audit-record.v1.schema.json` 的实际字段是 `auditor_attestation_key_id`。

影响：

- 即使对象按 Schema 正确构造，也会被 profile 额外字段绑定拒绝；
- 这是实现与 Schema 的真实漂移，不是测试问题。

修复：

- 删除 `AuditAssignment` 的不存在顶层 key 绑定；
- 将 `AuditRecord` 的顶层 key 绑定改为 `auditor_attestation_key_id`。

复核：

- `test_p0b_ed25519.py` 40/40 PASS。

## 3. 仍未闭合的主要问题

### 3.1 DB1I Schema bootstrap 测试仍未迁移到真实人门与授权链

现象：

全量测试中的 26 个 error 主要来自：

```text
seven-system/tests/test_db1i_schema_bootstrap.py
```

典型错误：

```text
DB1I_HUMAN_GATE_DECISION_REJECTED:
canonical human_gate_service is mandatory for schema apply;
duck-typed or missing gate services are not accepted
```

原因：

- 旧测试夹具使用 `_MockHumanGateService`；
- 旧 `_make_permit()` 仍是简化 permit，不是 `live-run-permit.v1.schema.json` 对象；
- `SchemaBootstrapProtocol.prepare()` 现在正确要求：
  - canonical `HumanGateService`；
  - signed GateDecision；
  - canonical `SecurityContractVerifier`；
  - EEA；
  - LiveRunPermit；
  - AuthorizationConsumptionReceipt with `status=RESERVED`；
  - EEA / Permit / Receipt 的公钥；
  - frozen `OperatorCommandRegistry` id 与 entry ref/hash。

不得采用的错误修法：

- 不得把 `isinstance(human_gate_service, HumanGateService)` 放宽回任意 duck-typed 对象；
- 不得在 `SchemaBootstrapProtocol.prepare()` 中为缺失 EEA/Permit/Receipt 自动补默认对象；
- 不得用一个“总是 PASS”的 verifier 子类冒充真实 DB1I 集成；
- 不得把真实授权链失败改成 warning。

正确整改方向：

1. 在 `test_db1i_schema_bootstrap.py` 中复用或抽取 HG0 的真实 HumanGate fixture：
   - deterministic Ed25519 key；
   - `ActorRoster`；
   - `KeyRegistry`；
   - `GateTypeRegistry`；
   - `FakeHumanTaskPort`；
   - signed GateDecision；
   - task creator 与 approver 职责分离。
2. 为 DB1I 写专用授权链 fixture，目标必须是：
   - `expected_action_kind = DB_SCHEMA_APPLY`；
   - `expected_wp_id = WP-DB1I`；
   - permit unit `input_hash = plan.plan_hash`；
   - permit unit `target_binding_hash = schema_bootstrap_target_binding_hash(plan_hash, site_fingerprint_hash, database_name)`；
   - EEA scope `target_site_hash_if_any = site_fingerprint_hash`；
   - EEA scope `target_database_identity_hash_if_any = database_identity_hash(EXPECTED_DATABASE)`；
   - EEA scope/action registry 与 permit unit 完全一致；
   - receipt ordinal 精确选中 permit unit；
   - receipt status 为 `RESERVED`；
   - allowance 守恒。
3. 将现有 golden / negative / resume 测试全部经同一 helper 生成真实链，negative 测试只改一个目标字段。

完成标准：

```bash
.venv/bin/python -m unittest seven-system/tests/test_db1i_schema_bootstrap.py
```

必须 PASS，且不能减少对 HumanGate 和 SecurityContractVerifier 的调用。

### 3.2 R5 WorkPackage state 测试仍按旧状态模型运行

现象：

全量测试中的 9 个 failure 主要来自：

```text
seven-system/tests/test_r5_wp_state.py
```

典型错误：

```text
wp WP-DOC0 has no verified frozen Plan
generic transition cannot enter IN_PROGRESS; use start/complete/accept_audit
```

原因：

- 当前状态机要求在 `start` 前已经注册并验证冻结 `WorkPackagePlan`；
- 通用 `transition` 不能进入 `IN_PROGRESS`，必须走 `start`；
- 旧测试仍假设 `WP-DOC0` 可无 Plan 直接 start，或直接通过 transition 进入 `IN_PROGRESS`。

不得采用的错误修法：

- 不得取消 Plan Gate；
- 不得恢复“generic transition 可进入 IN_PROGRESS”；
- 不得让 implementer 直接推进 auditor-owned 节点；
- 不得把 event log 失败只改成测试忽略。

正确整改方向：

1. 为测试创建 schema-valid 的 `WorkPackagePlan` fixture；
2. 在测试启动工作包前调用状态服务的 plan 注册/验证路径；
3. 将“直接 transition 进入 IN_PROGRESS”的旧测试改为断言拒绝；
4. 只通过 `start / complete / accept_audit` 三类命令测试状态推进；
5. 对 `WP-GA1` 这类 auditor-owned 节点补充 implementer 拒绝用例。

完成标准：

```bash
.venv/bin/python -m unittest seven-system/tests/test_r5_wp_state.py
```

必须 PASS，且 event log 中仍能看到 start/complete/accept_audit 的 append-only 事件。
