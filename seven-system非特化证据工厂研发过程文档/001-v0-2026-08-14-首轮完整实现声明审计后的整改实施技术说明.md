## 1. 为什么需要这份整改说明

上一位实施 AI 声明：

- 24 个 implementer-owned 工作包全部完成 side-effect-free 开发；
- 2117 tests + 28 subtests 全部通过；

## 2. 本文的权限边界

### 2.1 本文允许实施 AI 做什么

在没有任何外部执行授权时，实施 AI 只允许：

- 读取 repo、冻结 commit/tree/hash；
- 修改 repo 内代码、测试和文档；
- 运行纯本地、无网络、无 D 盘写入、无 DB/Redis 连接、无模型调用、无 Solver 启动的测试；
- 使用临时目录中的 fake/in-memory fixture；
- 生成未签名的候选对象字节，用于 Schema 和 semantic verifier 测试；
- 明确报告 blocker、protocol deviation 和未完成项。

### 2.2 本文不授权什么

本文件本身不构成以下任何权限：

- repo 外 owner 签发的 `AuditAssignment`；
- `NormativeRequirementReviewRecord` 的独立复核和签名；
- `ExternalExecutionAuthorization`；
- `LiveRunPermit`；
- `AuthorizationConsumptionReceipt(status=RESERVED)`；
- D 盘写入；
- ArangoDB / Redis 连接或写入；
- Devin / Codex / API 远程调用；
- Target Solver 启动；
- HumanGate 批准；
- `READY_FOR_AUDIT`、`AUDITED_PASS`、active release 或科学主张。

如果某一步需要上述对象，实施 AI 必须停在明确的 `BLOCKED`，列出所缺对象及其精确 hash 绑定范围，不得自签、伪造或用 Markdown 批准代替。

### 2.3 审计独立性边界

本次审计没有有效的 repo 外签名 `AuditAssignment`，所以本次产出是诊断性审计，不是可改变工作包状态的正式 `AuditRecord`。

下一位实施 AI 修复代码后，也不能审计自己的新 revision。修复完成后必须冻结新的 subject commit/tree，由另一独立上下文在有效 Assignment 下复跑。

## 4. 三个必须首先修复的 P0

### 4.1 P0-A：CompletionContractVerifier 没有执行完整 Schema

#### 当前错误

文件：

- `seven-system/src/seven_system/contracts/completion_contract.py`
- `seven-system/docs/implementation/implementation-completion-bundle.v1.schema.json`

当前 verifier 只根据 DAG 得到期望 `schema_id`，再比较：

```python
submitted_object.get("schema_id") == expected_schema_id
```

它没有加载并验证完整 JSON Schema。因此下面的空壳对象会对 `WP-GV0 + READY_FOR_AUDIT`得到 `PASS`：

```python
{"schema_id": "seven/implementation-completion-bundle"}
```

#### 正确目标

引入唯一的、可复用的完成对象验证路径：

```text
canonical DAG
→ completion_contract
→ exact schema id + schema file ref/hash
→ Draft 2020-12 Schema validation + strict format validation
→ object self-hash validation
→ cross-object binding validation
→ actor/owner/contract/state-transition validation
→ VerifiedCompletionDecision
```

#### 必须实现

1. 建立冻结的 `CompletionSchemaRegistry`，至少映射：
   - `DOC_BOOTSTRAP_RECORD`；
   - `IMPLEMENTATION_BUNDLE`；
   - `AUDIT_RECORD`。
2. Registry entry 必须包含：
   - completion contract；
   - schema ID；
   - schema file ref；
   - schema file SHA-256；
   - validator draft/version；
   - format policy/version。
3. verifier 必须先重算 Schema 文件 hash，再运行 Schema；不能信任调用者传入的“已验证”布尔值。
4. 对 `date-time` 使用会拒绝非法日期和非canonical时间的严格检查；不能只检查字符串形状。
5. Schema PASS 后继续验证：
   - `wp_id`与请求 WP 相同；
   - bundle status 与请求状态跃迁一致；
   - implementation subject commit/tree 与冻结 subject 相同；
   - spec、DAG、Plan、test receipt refs/hashes 存在且精确；
   - self-hash 按规定算法重算；
   - CompletionBundle不能用于 auditor-owned节点；
   - AuditRecord不能由 implementer 提交。
6. 状态服务只能消费唯一 verifier 产生且绑定对象hash/DAG hash/attempt的验证结果，不能在各业务模块复制一套弱校验。

#### 必须新增的负向测试

至少新增：

- `test_empty_completion_bundle_rejected`；
- `test_every_required_bundle_field_is_enforced`；
- `test_additional_property_rejected`；
- `test_wrong_field_type_rejected`；
- `test_schema_file_hash_drift_rejected`；
- `test_invalid_rfc3339_rejected`；
- `test_bundle_self_hash_mismatch_rejected`；
- `test_bundle_wp_id_mismatch_rejected`；
- `test_bundle_subject_commit_tree_mismatch_rejected`；
- `test_auditor_owned_node_rejects_implementation_bundle`；
- `test_implementer_cannot_write_audited_state`。

任何一个失败都不得降级成 warning。

### 4.2 P0-B：HumanGate 只有“签名形状”，没有真实 Ed25519 验签

#### 当前错误

涉及：

- `seven-system/src/seven_system/human/gate_decision.py`
- `seven-system/src/seven_system/human/key_lifecycle.py`
- `seven-system/src/seven_system/human/human_gate.py`
- `seven-system/tests/test_hg0_human_gate.py`

当前实现：

- 只检查 `signature_b64`是否符合“86字符+`==`”的正则；
- KeyRegistry 只保存 `public_key_sha256`，没有可用于验签的受信任公钥材料；
- HumanGateService 检查 key ID、actor、role、有效期和replay，但没有密码学验证；
- `verification_status=HUMAN_PENDING`仍可以被接受；
- 测试把`"A" * 86 + "=="`与`"0" * 64`公钥hash当作golden fixture。

审计已经实际复现：上述伪签名得到 `PASS`。

#### 正确目标

签名对象的生命周期必须拆成：

```text
UnsignedDecision
→ canonical bytes + domain separation
→ external signer produces signature envelope
→ trusted public-key resolver
→ real Ed25519 verification
→ SignatureVerificationReceipt
→ HumanGate policy / separation / replay checks
→ AcceptedGateDecision
```

#### 必须实现

1. 定义`SignatureVerifierPort`或等价唯一接口，禁止各模块自行写“Base64看起来像签名”的判断。
2. 使用版本锁定、可审计的Ed25519实现；依赖与版本必须进入实现subject/test receipt。
3. KeyRegistry不能只保存hash。至少需要：
   - key ID；
   - actor ID；
   - 受信任公钥 bytes 的 repo 外引用或受控 resolver；
   - 公钥bytes hash；
   - algorithm；
   - valid-from / valid-to；
   - revocation状态及快照；
   - eligible roles；
   - provisioning证据。
4. 私钥永远不能进入repo、模型workspace、普通日志、DB或普通D盘对象。
5. 验签必须覆盖规范定义的 domain-separated canonical bytes，而不是只验证一个调用者提供的 `signed_bytes_hash` 字符串。
6. `verification_status`必须由verifier生成，不能由调用者自由传入。
7. `HUMAN_PENDING`、`UNVERIFIED`、未知status永远不能产生APPROVE效果。
8. HumanGateService接受前必须验证：
   - signature有效；
   - signer principal与key/actor一致；
   - key在签发时间和验收时间都符合政策；
   - payload hash、task ID、gate type、nonce与签名内容完全一致；
   - 未撤销、未过期、未重放；
   - 职责分离成立。
9. 相同的真实验签核心还必须被以下签名对象复用或等价覆盖：
   - AuditAssignment；
   - AuditRecord；
   - ExternalExecutionAuthorization；
   - LiveRunPermit；
   - AuthorizationConsumptionReceipt；
   - NormativeRequirementReviewRecord。

#### 必须新增的负向测试

- 全A Base64伪签名必须拒绝；
- 合法长度但随机bytes必须拒绝；
- 签名后修改payload必须拒绝；
- 错公钥、错actor、错role必须拒绝；
- key hash 与实际公钥bytes不一致必须拒绝；
- revoked / expired / not-yet-valid key必须拒绝；
- 错domain separator必须拒绝；
- `HUMAN_PENDING + APPROVE`必须拒绝；
- 同签名换task/gate/nonce必须拒绝；
- verification service不可达时必须`BLOCKED`，不能fallback到结构检查。

## 5. 工作包状态与依赖必须改成机器约束

### 5.1 当前问题

当前看板同时写着：

- development dependency需要`READY_FOR_AUDIT`；
- GV0仍为`IMPLEMENTED_PENDING_EVIDENCE`；
- 但允许并实际启动全部下游包。

这说明依赖规则只是Markdown描述，没有成为状态服务的不可绕过条件。

### 5.2 正确状态模型

需要实现唯一的`WorkPackageStateService`或等价应用服务。它至少消费：

- canonical DAG ref/hash；
- 当前 WP 节点；
- WorkPackagePlan ref/hash及Schema/semantic verdict；
- dependency 状态及 CompletionBundle refs/hashes；
- inherited audit debt；
- activation依赖与授权对象；
- actor/owner/completion contract；
- expected revision/fence。

状态命令执行前必须检查：

#### `start`

- 当前状态允许启动；
- Plan存在且Schema+semantic valid；
- Plan真实是在本attempt代码修改前冻结；
- 全部development dependency为`READY_FOR_AUDIT`或`AUDITED_PASS`；
- dependency bundles与Plan中的refs/hashes完全一致；
- audit debt已显式继承；
- `SIDE_EFFECT_FREE`预算全0且授权refs为null。

#### `complete`

- completion contract与owner匹配；
- 完成对象的完整 Schema + semantic verification 均为 PASS；
- test/fault/capability receipts绑定精确subject commit/tree；
- code、Schema、Plan、DAG和dependency hash没有漂移；
- unresolved blocker为空，或状态只能进入`BLOCKED/IMPLEMENTED_PENDING_EVIDENCE`；
- implementer不能写`AUDITED_*`。

#### `activate`

- 适用上游为`AUDITED_PASS`，或精确未审canary例外已由EEA覆盖；
- 本次动作有不可扩权Permit与原子RESERVED receipt；
- capability reports、site、Vault、NoTool、AnswerIsolation等仍有效；
- 任一条件未知即fail-closed。

### 5.3 看板的身份

`work-package-board.md`只能是机器状态账的可读投影，不能成为允许绕过DAG的手工真值源。

需要做到：

- 状态事件append-only；
- board由状态事件确定性生成或验证；
- 同一 WP 同一 revision 的冲突状态立即 BLOCK；
- 状态更正保留历史，不删除原错误声明；
- 机器状态、board、`implementation-status.md` 和 `seven.py capabilities` 双向对账。

### 5.4 如何处理已经写出的 22 个下游包

不要删除代码，也不要假装顺序正确。正确动作是：

1. 把这些实现标为`EXISTING_UNQUALIFIED_IMPLEMENTATION_INPUT`或在正式对象体系允许的等价状态中记录；如果canonical枚举没有该状态，先提交规范修订候选，不得自造正式状态。
2. 当前合法工作包状态回到由canonical状态机可表达的`BLOCKED`/`NOT_STARTED`，并写明unmet dependency。
3. 每个包开启新的remediation attempt：
   - baseline指向包含既有代码的commit；
   - Plan不能声称既有代码是预注册后生成；
   - `protocol_deviations`记录“prior implementation existed before valid plan/dependency”；
   - 重新执行需求覆盖、攻击测试和集成验证。
