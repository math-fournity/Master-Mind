# 原语提取：245-v0-面相独立目录与设计元素管理元组群方案

## 文档概述

本文档提出两个方案：（1）将"面相"（Facet）从散落字段提升为独立管理的概念目录，作为横切 primitives/concepts/criteria 三层的元分类维度；（2）定义4个独立管理元组（Rule+Skill），覆盖新增设计元素、实验后验证状态更新、面相演化、定期审查四个管理场景。文档中大量涉及分类维度、索引结构、引用关系、验证状态管理、触发机制等设计，这些均可作为检索机制的数据结构原语和流程支撑原语。

## 提取的原语

### 原语：面相作为元分类维度
- **ID**：245-P1
- **类型**：概念框架
- **描述**：面相（Facet）是横切多个知识层的元分类维度——不是元素自身的属性，而是元素之上的分类视角，决定用什么角度切分系统理解和设计过程。
- **溯源**：245-v0, 第27行, 原文引用："面相（Facet）= 看系统和看设计过程的切分维度。它不是原语（不能执行/放置），不是概念框架（不是观察视角），不是性质标准（不检查任何东西）——它是**元分类**，决定我们用什么角度来切分系统理解和设计过程。"
- **依赖关系**：
  - 依赖：无
  - 支撑：245-P3（横切分类维度）、245-P8（面相覆盖度健康指标）
- **与检索机制的关系**：面相提供了检索时的第一级分类过滤维度——检索 Pattern 时可以先按面相缩小范围，再在面相内部做精细匹配。元分类维度是检索索引的一级结构。

### 原语：系统面相与设计过程面相的双类划分
- **ID**：245-P2
- **类型**：概念框架
- **描述**：面相分为两类——系统面相（看系统是什么：两种计算、语料双路径、Pipeline网络）和设计过程面相（看原语从哪来：实践涌现、知识选取），分别切分系统结构和知识来源。
- **溯源**：245-v0, 第29-44行, 原文引用："**系统面相**（看系统是什么）…**设计过程面相**（看原语从哪来）"
- **依赖关系**：
  - 依赖：245-P1（面相作为元分类维度）
  - 支撑：245-P8（面相覆盖度健康指标）
- **与检索机制的关系**：双类划分提供了检索时的正交过滤维度——可以按"系统结构视角"或"知识来源视角"分别检索，两个维度可以组合查询。

### 原语：横切多层分类维度（多对多标签体系）
- **ID**：245-P3
- **类型**：结构原语
- **描述**：面相横切 primitives/concepts/criteria 三层，每个设计元素可属于一个或多个面相，形成多对多的标签矩阵——面相是列，知识层是行，每个交叉点可有多个元素。
- **溯源**：245-v0, 第101-113行, 原文引用："面相是**第四层**，但不是和前三层平行的层——它是**横切前三层的分类维度**…每个设计元素（原语/概念/标准）可以属于一个或多个面相。"
- **依赖关系**：
  - 依赖：245-P1（面相作为元分类维度）
  - 支撑：245-P7（正向引用关系记录）、245-P8（面相覆盖度健康指标）
- **与检索机制的关系**：多对多标签矩阵是检索的核心数据结构——支持按面相×层做二维过滤检索，也支持按面相做跨层检索（如"检索面相3下所有层的元素"）。

### 原语：面相文件结构化元数据格式
- **ID**：245-P4
- **类型**：结构原语
- **描述**：每个面相用结构化文件记录，包含定义、核心判断、来源、贡献、局限、包含的设计元素、被修正by、开放问题等字段——这些字段既是面相的自描述，也是检索时的元数据来源。
- **溯源**：245-v0, 第71-97行, 原文引用："```markdown\n# 面相名（中英文）\n\n## 定义…## 核心判断…## 来源…## 贡献…## 局限…## 包含的设计元素…## 被修正 by…## 开放问题```"
- **依赖关系**：
  - 依赖：245-P1（面相作为元分类维度）
  - 支撑：245-P6（面相演化记录与修正关系追踪）
- **与检索机制的关系**：结构化元数据字段是检索匹配的依据——"核心判断"可用于语义匹配，"局限"可用于排除不适用面相，"被修正by"可用于追踪面相演化链。

### 原语：面相演化记录与修正关系追踪
- **ID**：245-P6
- **类型**：结构原语
- **描述**：面相会演化（新增、修正旧面相），通过"被修正by"字段记录面相间的修正关系，形成面相演化的版本链——面相3修正面相1的局限，这种关系属于面相层而非元素层。
- **溯源**：245-v0, 第52-53行, 原文引用："**面相本身会演化**——面相3是241号新增的，修正了面相1和面相2的局限。未来可能有面相4。面相的演化需要被记录。…**面相之间的关系是理念层的**——面相3修正面相1的"AI计算黑箱"问题"
- **依赖关系**：
  - 依赖：245-P4（面相文件结构化元数据格式）
  - 支撑：无
- **与检索机制的关系**：修正关系链支持检索时的版本感知——检索到旧面相的元素时，可以提示"此面相已被面相X修正"，避免用过时视角理解检索结果。

### 原语：正向引用关系记录（低成本高频写入）
- **ID**：245-P7
- **类型**：操作原语
- **描述**：元素与面相的关系通过正向引用记录——元素文件的"来源"字段加一行面相归属，面相文件不列元素清单。高频操作（新增元素时记面相）保持低成本（写一行），低频操作（覆盖度统计）可高成本（扫描文件）。
- **溯源**：245-v0, 第326行, 原文引用："**正向引用**——元素文件"来源"字段加一行面相归属，面相文件不列元素清单 | 高频操作（新增元素时记面相）应低成本（写一行）；低频操作（覆盖度统计）可高成本（扫描文件）"
- **依赖关系**：
  - 依赖：245-P3（横切多层分类维度）
  - 支撑：245-P8（面相覆盖度健康指标）
- **与检索机制的关系**：正向引用决定了检索索引的构建方式——按面相检索时需要扫描所有元素的归属字段（倒排索引），而不是直接读面相文件的正向列表。这是读写成本权衡的设计决策。

### 原语：面相覆盖度作为健康指标
- **ID**：245-P8
- **类型**：性质标准
- **描述**：面相覆盖度（各面相下设计元素的数量分布）是知识库健康指标——如果所有原语集中在某一面相，说明项目缺乏另一维度的深化。覆盖度矩阵可用于诊断知识库的盲区。
- **溯源**：245-v0, 第55行, 原文引用："**面相覆盖度是健康指标**——如果所有原语都集中在面相A（实践涌现），说明项目缺乏理论深化；如果都集中在面相B（知识选取），说明项目缺乏实验验证。"
- **依赖关系**：
  - 依赖：245-P3（横切多层分类维度）、245-P7（正向引用关系记录）
  - 支撑：无
- **与检索机制的关系**：覆盖度矩阵是检索结果质量的诊断工具——如果检索结果集中在某一面相，提示检索可能存在偏差。也可用于检索前的预检：某面相元素过少时，降低该面相检索结果的置信度。

### 原语：分类决策树（可执行性/可验证性/构造性三判据）
- **ID**：245-P9
- **类型**：操作原语
- **描述**：新增设计元素时用三判据分类：可执行？可验证？构造性？→ 满足则归入原语（操作/结构），否则归入概念或标准或面相。这是一个确定性的分类路由机制。
- **溯源**：245-v0, 第172行, 原文引用："分类决策树：可执行？可验证？构造性？→ 原语（操作/结构）/ 概念 / 标准 / 面相"
- **依赖关系**：
  - 依赖：无
  - 支撑：245-P10（管理对象四类分类）
- **与检索机制的关系**：分类决策树是检索前的元素入库路由——决定元素进入哪个目录、用什么格式存储，直接影响后续检索的目录结构和匹配策略。

### 原语：管理对象四类分类与差异化更新频率
- **ID**：245-P10
- **类型**：结构原语
- **描述**：管理对象分为四类（原语/概念框架/性质标准/面相），各有不同目录、数量和更新频率——原语随实验更新验证状态（高频），概念随理念突破更新（中频），标准最稳定（低频），面相随系统理解深化演化（低频）。
- **溯源**：245-v0, 第123-130行, 原文引用："| 管理对象 | 目录 | 数量 | 更新频率 |…| 原语 | primitives/ | 16 | 随实验更新验证状态 |…| 概念框架 | concepts/ | 7 | 随理念突破更新 |…| 性质标准与隐喻 | criteria/ | 3 | 最稳定，偶尔新增 |…| 面相 | facets/ | 5 | 随系统理解深化演化 |"
- **依赖关系**：
  - 依赖：245-P9（分类决策树）
  - 支撑：245-P11（验证状态四等级管理）
- **与检索机制的关系**：差异化更新频率决定了检索索引的刷新策略——高频更新对象（原语验证状态）需要实时索引刷新，低频更新对象（标准、面相）可以缓存索引。这也是检索结果时效性保证的依据。

### 原语：验证状态四等级管理
- **ID**：245-P11
- **类型**：结构原语
- **描述**：原语的验证状态分为四等级：untested → tested / tested_negative / partial，实验后按状态转移规则更新。验证状态是原语的动态属性，随实验结果持续演化。
- **溯源**：245-v0, 第189-192行, 原文引用："对每个受影响的原语，判断验证状态变化：\n  - untested → tested / tested_negative / partial\n  - partial → tested / tested_negative\n  - tested → 保持或细化"
- **依赖关系**：
  - 依赖：245-P10（管理对象四类分类）
  - 支撑：245-P12（实验后受影响原语识别）
- **与检索机制的关系**：验证状态是检索结果的关键过滤和排序维度——检索 Pattern 时可以优先返回 tested 状态的原语，过滤 tested_negative 的，标记 untested 的为"未验证"。状态转移规则也支持检索结果的动态更新。

### 原语：实验后受影响原语识别
- **ID**：245-P12
- **类型**：操作原语
- **描述**：实验run完成后，从run的problem.txt、solutions.json、引导者决策中提取信息，识别实验测试了哪些原语，然后更新这些原语的验证状态。这是一个从实验产物反向定位受影响知识元素的机制。
- **溯源**：245-v0, 第188行, 原文引用："识别实验测试了哪些原语（从run的problem.txt、solutions.json、引导者决策中提取）"
- **依赖关系**：
  - 依赖：245-P11（验证状态四等级管理）
  - 支撑：无
- **与检索机制的关系**：这是反向检索的原型——从实验产物（非结构化/半结构化数据）中检索出受影响的知识元素。这种"从证据反查知识"的机制是检索机制的重要补充：正向检索是从需求找知识，反向检索是从证据更新知识状态。

### 原语：Always-on Rule 模式匹配触发机制
- **ID**：245-P13
- **类型**：操作原语
- **描述**：每个管理操作由一个 always-on Rule 负责触发——Rule 持续监控上下文，当满足触发条件时加载对应 Skill 执行工作流。Rule 包含判断标准（什么情况触发 vs 不触发）。
- **溯源**：245-v0, 第162-169行, 原文引用："**Rule**（always-on，放 `.devin/rules/`）：\n```\n当实验或讨论中产生一个新的设计想法（操作/结构/概念/标准/面相）时，\n加载 design-element-creation skill。\n判断标准：这个想法是否值得记录为设计元素？\n- 如果只是一次性的实验参数，不值得\n- 如果是可复用的设计决策或可积累的理解，值得\n```"
- **依赖关系**：
  - 依赖：无
  - 支撑：245-P14（元组间交叉触发自然处理）
- **与检索机制的关系**：Rule 的模式匹配触发是检索机制的入口——检索不需要显式调用，而是由 always-on 的模式匹配自动触发。这对应检索机制中的"自动检索触发条件"设计：什么时候需要检索、检索什么，由规则自动判断。

### 原语：元组间交叉触发自然处理（无显式编排）
- **ID**：245-P14
- **类型**：操作原语
- **描述**：多个独立元组之间有交叉关系（元组1创建元素时可能需要新面相→触发元组3），但这些交叉通过各 Rule 的触发条件自然处理，不需要显式编排——一个元组的产出如果满足另一个元组的触发条件，后者自动触发。
- **溯源**：245-v0, 第248-253行, 原文引用："元组1（新增）──创建元素时──→ 可能需要更新面相 → 触发元组3的判断…这些交叉通过Rule的触发条件自然处理——元组1创建元素时如果发现需要新面相，元组3的Rule会触发。不需要显式编排。"
- **依赖关系**：
  - 依赖：245-P13（Always-on Rule 模式匹配触发机制）
  - 支撑：无
- **与检索机制的关系**：交叉触发自然处理是检索链式调用的原型——一次检索的输出可能触发后续检索（如检索到元素后发现需要检索其面相），这种链式检索不需要显式编排，由触发条件自动驱动。

### 原语：独立元组 vs 元组群的区分判据
- **ID**：245-P15
- **类型**：概念框架
- **描述**：元组群适用于一条长工作流的分段（各段有顺序依赖），独立元组适用于独立触发的管理操作（无顺序依赖）。区分判据：操作之间是否有固定的先后顺序和数据依赖。
- **溯源**：245-v0, 第233-241行, 原文引用："元组群适用于**一条长工作流的分段**（如 guided-math-solving 的5个Skill是一条引导解题流程的5个阶段）。这4个元组不是一条流程的分段——它们是**独立触发的管理操作**…所以它们是4个独立元组，每个有自己的触发条件和完整的工作流，不依赖其他元组的产出。"
- **依赖关系**：
  - 依赖：245-P13（Always-on Rule 模式匹配触发机制）
  - 支撑：无
- **与检索机制的关系**：这个区分判据指导检索机制的工作流设计——如果检索是单步独立操作，用独立元组；如果检索是多阶段流程（如"先粗检索→精排→验证"），用元组群分阶段。这是检索流程架构选型的决策依据。

### 原语：跨层引用完整性检查
- **ID**：245-P16
- **类型**：操作原语
- **描述**：定期审查时检查所有"约束于"引用是否指向存在的文件——这是一种引用完整性约束检查，确保知识库中的交叉引用不会出现悬空指针。
- **溯源**：245-v0, 第229行, 原文引用："检查跨层引用完整性——所有"约束于"引用是否指向存在的文件？"
- **依赖关系**：
  - 依赖：245-P10（管理对象四类分类）
  - 支撑：无
- **与检索机制的关系**：引用完整性检查是检索结果有效性的保障——如果知识库中存在悬空引用，检索可能返回指向不存在元素的路径。定期检查确保检索的引用图是完整的。

### 原语：验证状态分布统计（按层×按面相）
- **ID**：245-P17
- **类型**：操作原语
- **描述**：定期审查时按层和按面相两个维度统计验证状态分布，识别长期 untested 的原语、应该被操作化的概念、面相覆盖盲区——这是一种多维聚合分析。
- **溯源**：245-v0, 第225-228行, 原文引用："验证状态分布统计（按层、按面相）\n- 识别长期untested的原语——它们是否应该被优先测试？\n- 识别应该被操作化的概念——是否有概念已经具备了变成原语的条件？\n- 检查面相覆盖度——是否有面相没有设计元素？是否有设计元素没有面相归属？"
- **依赖关系**：

  - 支撑：无
- **与检索机制的关系**：多维聚合统计是检索机制的逆向应用——不是从需求检索元素，而是从全局统计发现知识库的结构性问题（盲区、长期未验证、待操作化）。这对应检索机制中的"知识库健康诊断"功能。

### 原语：面相指导分类路由

### 原语：索引更新机制（README.md 作为目录索引）
- **ID**：245-P19
