# 原语提取：67-Subagent对照实验执行模式

## 文档概述

本文档记录了在 xishujuzhen POC-1/POC-2/POC-3 执行过程中使用的两种 subagent 编排模式：模式一（双 Subagent 并行对照）和模式二（分阶段 Subagent + 并行对照）。文档详细描述了两种模式的适用场景、执行方式、关键操作、优缺点及通用原则。虽然文档主题是实验编排而非检索机制，但其中包含多种可作为检索机制构造积木的原语：依赖关系判断决定编排策略、结构化图数据作为输入、分阶段流水线与阶段间数据传递、无状态执行单元的上下文封装、输出持久化与审计追踪等，这些原语均可复用于检索流程的编排、上下文封装、流水线设计和结果验证等环节。

## 提取的原语

### 原语：依赖关系判断决定编排策略
- **ID**：67-P1
- **类型**：操作原语
- **描述**：根据任务之间是否存在依赖关系，选择不同的执行编排模式（并行 vs 分阶段串行），无依赖时并行执行，有依赖时分阶段串行执行。
- **溯源**：67, 第9-11行, 原文引用："需要对比两种条件下的 AI 输出质量，两组之间**没有依赖关系**——A 组的输入不依赖 B 组的输出，反之亦然。"；第74-75行："两组之间没有依赖关系时才能用 / 如果 B 组的输入依赖 A 组的输出（或反过来），就不能并行"
- **依赖关系**：
  - 依赖：无
  - 支撑：67-P2（并行对照模式）、67-P3（分阶段流水线模式）
- **与检索机制的关系**：检索机制中可能存在多个检索子任务，部分可并行（如多路召回）、部分需串行（如先检索再重排）。依赖关系判断是决定检索流程编排拓扑的基础原语。

### 原语：双路并行对照执行模式
- **ID**：67-P2
- **类型**：结构原语
- **描述**：两个执行单元并行运行，各自独立处理不同输入，互不等待，完成后由主控收集结果——适用于无依赖关系的对照任务。
- **溯源**：67, 第7-11行, 原文引用："## 模式一：双 Subagent 并行对照（POC-1/POC-2）... 需要对比两种条件下的 AI 输出质量，两组之间**没有依赖关系**"
- **依赖关系**：
  - 依赖：67-P1（依赖关系判断）
  - 支撑：67-P6（background模式并行执行）
- **与检索机制的关系**：检索机制中的多路召回（如同时从不同索引/不同知识层检索）可采用此并行模式，各路召回互不依赖，完成后统一收集合并。

### 原语：分阶段流水线与阶段间数据传递
- **ID**：67-P3
- **类型**：结构原语
- **描述**：将复杂任务拆分为多个阶段，后一阶段的输入依赖前一阶段的输出，阶段间通过文件传递数据，形成串行流水线；同时无依赖的部分可与第一阶段并行。
- **溯源**：67, 第79-83行, 原文引用："B 组的执行分为多个阶段，**后一阶段的输入依赖前一阶段的输出**。同时 A 组不需要分阶段，可以和 B 组的第一阶段并行。"
- **依赖关系**：
  - 依赖：67-P1（依赖关系判断）、67-P8（阶段间文件传递）
  - 支撑：67-P4（解读→提示词→分析三阶段流水线）
- **与检索机制的关系**：检索机制可设计为多阶段流水线：第一阶段从认知图中检索候选 Pattern，第二阶段对候选 Pattern 进行重排/过滤，第三阶段封装为提示上下文。阶段间通过文件/数据结构传递中间结果。

### 原语：解读→提示词生成→分析的三阶段流水线
- **ID**：67-P4
- **类型**：操作原语
- **描述**：将"利用结构化图数据辅助分析"拆分为三阶段：①解读结构化图数据生成自然语言提示词，②在结构化图数据+提示词共同作用下执行分析，③输出结果+审计文件。阶段一输出精确控制为只给提示词、不给思考过程。
- **溯源**：67, 第162-166行, 原文引用："B 组阶段一：解读 JSON → 大师级提示词（4811 字符）/ B 组阶段二：在 JSON + 大师级提示词共同提示下分析 → 结果（8604 字符）+ 审计（5326 字符）"；第172行："阶段二的输入可以精确控制（只给阶段一的输出，不给阶段一的思考过程）"
- **依赖关系**：
  - 依赖：67-P3（分阶段流水线）、67-P11（依赖图JSON作为结构化输入）
  - 支撑：无
- **与检索机制的关系**：这是"从认知图/依赖图中检索 Pattern 并转化为可用提示"的完整流水线原型。第一阶段相当于"图数据解读/Pattern提取"，第二阶段相当于"在检索到的Pattern辅助下执行任务"。精确控制阶段间数据传递（只传输出不传过程）对应检索中"只传检索结果不传检索内部状态"的设计。

### 原语：盲评机制（消除评估者偏差）
- **ID**：67-P5
- **类型**：操作原语
- **描述**：评估结果时不看组别标记，按统一标准打分，打分完成后再揭晓组别——防止评估者因设计了某一组的方法而产生偏向。
- **溯源**：67, 第53-57行, 原文引用："主 Agent 拿到两组输出后，**不看组别标记**，按统一的 5 维度评分标准打分。打分完成后再揭晓哪个是 A 组哪个是 B 组。盲评的目的是避免主 Agent 在评分时偏向 B 组（因为 B 组用了主 Agent 自己设计的依赖图提示）。"
- **依赖关系**：
  - 依赖：67-P2（双路并行对照）或 67-P3（分阶段流水线）
  - 支撑：无
- **与检索机制的关系**：检索机制的效果评估（如对比不同检索策略的召回质量）应采用盲评，避免因设计者偏向某一检索策略而影响评估客观性。这是检索机制A/B测试的评估原语。

### 原语：background模式并行执行
- **ID**：67-P6
- **类型**：操作原语
- **描述**：所有执行单元用 `is_background: true` 启动，使主控可以在等待一个单元的同时做其他事情（如准备下一阶段材料），实现真正的并行而非伪并行。
- **溯源**：67, 第199-201行, 原文引用："所有 subagent 都用 `is_background: true` 启动。这样主 Agent 可以在等待一个 subagent 的同时做其他事情（如准备下一阶段的材料）。"
- **依赖关系**：
  - 依赖：无
  - 支撑：67-P2（双路并行对照）、67-P3（分阶段流水线）
- **与检索机制的关系**：检索机制中多路召回应采用后台并行模式，主流程在等待检索结果的同时可以执行其他准备工作（如构造查询、预处理上下文），提高整体吞吐。

### 原语：输出持久化到文件
- **ID**：67-P7
- **类型**：操作原语
- **描述**：执行单元的输出收集后立即保存到文件，原因包括：输出可能很长需文件引用、评分需引用具体内容、文件可被git跟踪形成持久化记录。
- **溯源**：67, 第203-208行, 原文引用："subagent 的输出通过 `read_subagent` 收集后，立即保存到文件。这样做的原因：subagent 的输出可能很长，保存到文件方便后续引用 / 评分报告需要引用输出中的具体内容，文件引用比对话引用更可靠 / 文件可以被 git 跟踪，形成持久化记录"
- **依赖关系**：
  - 依赖：无
  - 支撑：67-P8（阶段间文件传递）
- **与检索机制的关系**：检索结果应持久化到文件/数据库而非仅存在于内存中，方便后续阶段引用、审计追踪和版本管理。这是检索结果缓存与持久化的原语。

### 原语：阶段间文件传递（解耦上下文依赖）
- **ID**：67-P8
- **类型**：结构原语
- **描述**：分阶段流程中，前一阶段的输出保存到文件，后一阶段从文件读取输入——阶段间通过文件传递数据而非依赖对话上下文，实现阶段间解耦。
- **溯源**：67, 第146-148行, 原文引用："B 组阶段一完成后，把输出保存到文件（如 `poc3_output_b_interpretation.md`）。这份文件是阶段二的输入。"
- **依赖关系**：
  - 依赖：67-P7（输出持久化到文件）
  - 支撑：67-P3（分阶段流水线）、67-P4（三阶段流水线）
- **与检索机制的关系**：检索流水线各阶段间应通过文件/数据结构传递中间结果，而非依赖运行时上下文。这使得每个阶段可以独立调试、独立重跑、独立审计，也支持跨session恢复。

### 原语：无状态执行单元与上下文封装
- **ID**：67-P9
- **类型**：结构原语
- **描述**：执行单元是无状态的，不能依赖之前的对话上下文。因此所有必需信息必须封装在任务指令中：角色设定、任务描述、输入材料、输出要求、约束条件——形成完整自包含的执行单元。
- **溯源**：67, 第210-218行, 原文引用："subagent 是无状态的，看不到主 Agent 的对话上下文。所以 task prompt 必须包含 subagent 完成任务所需的全部信息：角色设定...任务描述...输入材料...输出要求...约束（如"解读时不能改变 JSON 中的依赖关系"）"
- **依赖关系**：
  - 依赖：无
  - 支撑：67-P10（输入材料预准备并嵌入）
- **与检索机制的关系**：检索机制中的每个检索操作可设计为无状态执行单元——接收包含完整上下文的查询请求（角色、目标、约束、输入数据），返回检索结果，不依赖外部状态。这使得检索操作可独立部署、可水平扩展、可无状态重试。

### 原语：输入材料预准备并嵌入任务指令
- **ID**：67-P10
- **类型**：操作原语
- **描述**：所有输入材料由主控在启动执行单元之前准备好，直接嵌入执行单元的任务指令中，执行单元不需要自己去读文件——保证材料完全可控、避免读取出错。
- **溯源**：67, 第190-197行, 原文引用："两组的输入材料都由主 Agent 在启动 subagent 之前准备好，直接嵌入 subagent 的 task prompt 中。subagent 不需要自己去读文件——所有需要的信息都在 task prompt 里。这样做的原因：subagent 是无状态的，不能依赖之前的对话上下文 / 嵌入 task prompt 保证 subagent 拿到的材料完全可控 / 避免 subagent 读取文件时出错"
- **依赖关系**：
  - 依赖：67-P9（无状态执行单元与上下文封装）
  - 支撑：无
- **与检索机制的关系**：检索机制的输入（查询、上下文、约束条件）应由调用方预先准备好并封装为完整的检索请求，检索引擎不需要自行获取额外信息。这保证了检索输入的可控性和可审计性。

### 原语：依赖图JSON作为结构化输入
- **ID**：67-P11
- **类型**：结构原语
- **描述**：将依赖图序列化为JSON格式作为执行单元的结构化输入，执行单元基于JSON中的节点和依赖关系进行分析——从POC-1的5节点到POC-2/POC-3的12节点，图规模可扩展。
- **溯源**：67, 第61-62行, 原文引用："POC-1：A 组（直接读 study-notes）vs B 组（5 节点依赖图 JSON 提示）/ POC-2：A 组（增强版 study-notes）vs B 组（12 节点依赖图 JSON + 知识嵌入 + 审计要求）"
- **依赖关系**：
  - 依赖：无
  - 支撑：67-P4（三阶段流水线）、67-P12（知识嵌入）
- **与检索机制的关系**：认知图/依赖图以JSON格式作为检索机制的结构化输入——检索引擎接收图结构数据，基于节点和边的关系进行Pattern检索。这是"从图中检索"的数据格式原语。

### 原语：知识嵌入
- **ID**：67-P12
- **类型**：操作原语
- **描述**：在依赖图JSON之外，额外将相关知识嵌入到执行单元的输入中，使执行单元不仅有结构化的图关系，还有配套的知识内容。
- **溯源**：67, 第62行, 原文引用："B 组（12 节点依赖图 JSON + 知识嵌入 + 审计要求）"
- **依赖关系**：
  - 依赖：67-P11（依赖图JSON作为结构化输入）
  - 支撑：无
- **与检索机制的关系**：检索机制不仅返回图结构中的Pattern节点，还应将Pattern关联的知识内容一并嵌入返回结果中——"图结构+知识内容"的组合检索，而非仅返回图的拓扑关系。

### 原语：审计文件与双重对照审计
- **ID**：67-P13
- **类型**：操作原语
- **描述**：执行单元在输出分析结果的同时输出审计文件，记录分析过程中的关键决策和依据；在分阶段模式中，阶段二可要求"双重对照审计"——在多种提示共同作用下进行交叉验证审计。
- **溯源**：67, 第32行, 原文引用："+审计文件"；第125行："+审计文件(双重对照)"；第62行："12 节点依赖图 JSON + 知识嵌入 + 审计要求"
- **依赖关系**：
  - 依赖：67-P7（输出持久化到文件）
  - 支撑：无
- **与检索机制的关系**：检索机制应支持审计追踪——记录检索了哪些Pattern、基于什么条件匹配、排序依据是什么。双重对照审计可扩展为"多检索策略交叉验证"，对比不同检索路径的结果差异。

### 原语：阶段间精确控制数据传递（只传输出不传过程）
- **ID**：67-P14
- **类型**：操作原语
- **描述**：分阶段流程中，后一阶段只接收前一阶段的输出结果，不接收前一阶段的思考过程/内部状态——精确控制阶段间信息流，避免信息泄漏。
- **溯源**：67, 第172行, 原文引用："阶段二的输入可以精确控制（只给阶段一的输出，不给阶段一的思考过程）"
- **依赖关系**：
  - 依赖：67-P3（分阶段流水线）、67-P8（阶段间文件传递）
  - 支撑：无
- **与检索机制的关系**：检索流水线各阶段间应精确控制信息传递——如第一阶段（图检索）只传候选Pattern列表给第二阶段（重排），不传检索内部的匹配分数细节或中间状态。这防止后续阶段被前阶段的内部噪声干扰，也支持阶段独立优化。

### 原语：约束嵌入任务指令
- **ID**：67-P15
- **类型**：操作原语
- **描述**：在任务指令中嵌入显式约束条件（如"解读时不能改变 JSON 中的依赖关系"），限制执行单元的操作边界，防止执行单元在处理结构化输入时篡改关键结构。
- **溯源**：67, 第217行, 原文引用："约束（如"解读时不能改变 JSON 中的依赖关系"）"
- **依赖关系**：
  - 依赖：67-P9（无状态执行单元与上下文封装）
  - 支撑：无
- **与检索机制的关系**：检索请求中应嵌入约束条件（如"检索结果不得修改图结构"、"只返回激活状态为true的Pattern"、"返回数量上限N"），约束检索引擎的操作边界，保证检索结果的结构完整性。

### 原语：阻塞式等待与完成收集
- **ID**：67-P16
- **类型**：操作原语
- **描述**：用阻塞式读取依次等待各执行单元完成，先完成的先返回（若已完成则立即返回），全部完成后统一收集结果——实现并行执行+同步收集的协调机制。
- **溯源**：67, 第49-51行, 原文引用："用 `read_subagent` 的 `block: true` 依次等待两个 subagent 完成。第一个 `read_subagent` 会阻塞到 A 组完成，第二个会阻塞到 B 组完成（如果 B 组先完成了，第二个 `read_subagent` 会立即返回）。"
- **依赖关系**：
  - 依赖：67-P6（background模式并行执行）
  - 支撑：无
- **与检索机制的关系**：多路并行检索后的结果收集可采用阻塞式等待——依次等待各路检索完成，先完成的立即返回，全部完成后统一合并。这是并行检索的结果汇聚协调原语。

### 原语：统一维度评分标准
- **ID**：67-P17
- **类型**：性质标准
- **描述**：对照评估时按统一的5维度评分标准打分，确保不同组别的结果在相同标准下比较，保证评估的可比性。
- **溯源**：67, 第55行, 原文引用："按统一的 5 维度评分标准打分"
- **依赖关系**：
  - 依赖：67-P5（盲评机制）
  - 支撑：无
- **与检索机制的关系**：评估不同检索策略/参数的效果时，需要统一的评估维度和标准（如召回率、精确率、覆盖率、相关性、多样性），确保不同策略间的比较公平可重复。

### 原语：对照实验组设计（A组对照 vs B组实验）
- **ID**：67-P18
- **类型**：概念框架
- **描述**：设计A组（对照组，使用基线方法如直接读文档）和B组（实验组，使用新方法如依赖图JSON提示），通过对比两组输出来评估新方法的效果——A组/B组唯一差异在于是否使用新方法。
- **溯源**：67, 第61-64行, 原文引用："POC-1：A 组（直接读 study-notes）vs B 组（5 节点依赖图 JSON 提示）/ POC-2：A 组（增强版 study-notes）vs B 组（12 节点依赖图 JSON + 知识嵌入 + 审计要求）/ 两组的输入材料都由主 Agent 在启动 subagent 之前准备好"
- **依赖关系**：
