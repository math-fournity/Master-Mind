# 原语提取：64-xishujuzhen-POC验证方案

## 文档概述

本文档是 xishujuzhen（细数局阵）系统的 POC 验证方案，通过对照实验验证"依赖图提示"是否比"直接读知识文档"更能提升 AI 分析质量。文档详细定义了依赖图的数据结构（节点类型、边类型、元数据）、环路检测与分类算法、子图提取与提示生成流程、知识指针机制，以及结构化评分的对照实验设计。这些内容直接涉及从认知图/依赖图中检索 Pattern 的核心机制——子图提取、上下文标注、环路处理、知识指针映射等都是检索机制的关键积木。

## 提取的原语

### 原语：依赖图节点类型分层
- **ID**：64-P01
- **类型**：结构原语
- **描述**：依赖图中的节点按认知层次分为 step（分析步骤）、substep（子步骤）、意识（底层认知意识）三种类型，每种类型携带 context 元数据。
- **溯源**：64, 第99-106行, 原文引用："节点 ID | 类型 | 内容 | `命宫分析` | step | 分析任务的入口节点 | `命主星判断` | substep | 判断命主星的强弱 | `庙旺平陷` | 意识 | 星曜在宫位的庙旺平陷状态判断"
- **依赖关系**：
  - 依赖：无
  - 支撑：64-P02（边类型）、64-P03（节点元数据）、64-P07（子图提取）
- **与检索机制的关系**：节点类型分层是检索的第一步——检索时可以按类型过滤（只检索"意识"层节点，或只检索"step"层节点），实现分层检索。类型标签是 Pattern 匹配的维度之一。

### 原语：依赖边类型分类
- **ID**：64-P02
- **类型**：结构原语
- **描述**：依赖图中的边分为 depends_on（硬依赖：必须先完成）和 calls（调用依赖：需要调用该意识/知识）两种类型，区分依赖的强度和性质。
- **溯源**：64, 第107-117行, 原文引用："命宫分析 → 命主星判断 | depends_on | 命宫分析需要先判断命主星 | 命宫分析 → 庙旺平陷 | calls | 命宫分析需要查各星曜庙旺"
- **依赖关系**：
  - 依赖：64-P01（节点类型分层）
  - 支撑：64-P07（子图提取）、64-P08（提示生成）
- **与检索机制的关系**：边类型决定了检索时的遍历策略——depends_on 边意味着必须检索到该节点（强依赖），calls 边意味着可选检索（弱依赖）。检索机制可以根据边类型决定是否深入某条路径。

### 原语：节点 context 元数据
- **ID**：64-P03
- **类型**：结构原语
- **描述**：每个节点携带 context 元数据字段，记录该节点在当前分析中的上下文路径（如"命宫/命主木星"、"命宫/昼生"），用于区分同一节点在不同上下文中的调用。
- **溯源**：64, 第147-151行, 原文引用："graph.add_node("命宫分析", type="step", context="命宫") | graph.add_node("命主星判断", type="substep", context="命宫/命主木星") | graph.add_node("阴阳昼夜", type="意识", context="命宫/昼生")"
- **依赖关系**：
  - 依赖：64-P01（节点类型分层）
  - 支撑：64-P05（环路分类）、64-P08（提示生成）
- **与检索机制的关系**：context 元数据是检索时的上下文匹配维度——检索可以按 context 过滤节点，只返回与当前分析上下文相关的 Pattern。context 路径的层级结构（用"/"分隔）也支持前缀匹配检索。

### 原语：networkx DiGraph 作为依赖图底层数据结构
- **ID**：64-P04
- **类型**：结构原语
- **描述**：使用 networkx 的有向图（DiGraph）作为依赖图的底层数据结构，节点和边都携带属性元数据，支持图算法（SCC 检测、BFS 遍历等）。
- **溯源**：64, 第139-161行, 原文引用："import networkx as nx | graph = nx.DiGraph() | graph.add_node("命宫分析", type="step", context="命宫") | graph.add_edge("命宫分析", "命主星判断", type="depends_on")"
- **依赖关系**：
  - 依赖：无
  - 支撑：64-P05（环路检测）、64-P07（子图提取）
- **与检索机制的关系**：DiGraph 是检索机制的底层数据结构——检索本质上是在图上进行遍历和子图提取。networkx 提供了成熟的图算法库（BFS、DFS、SCC、最短路径等），可以直接复用为检索算法的基础设施。

### 原语：环路检测与平面/螺旋分类
- **ID**：64-P05
- **类型**：操作原语
- **描述**：通过强连通分量（SCC）检测图中的环路，再根据 SCC 内节点的 context 集合是否唯一，将环路分类为"平面环路"（同一上下文中的循环，应停止追溯）或"螺旋环路"（跨上下文的深化，应继续追溯）。
- **溯源**：64, 第164-190行, 原文引用："def classify_cycles(graph): sccs = list(nx.strongly_connected_components(graph)) ... if len(contexts) == 1: cycles.append({'type': 'planar', ... 'note': '平面环路：同一上下文中的循环，应停止追溯'}) else: cycles.append({'type': 'spiral', ... 'note': '螺旋环路：跨上下文的深化，应继续追溯'})"
- **依赖关系**：
  - 依赖：64-P03（节点 context 元数据）、64-P04（DiGraph 数据结构）
  - 支撑：64-P08（提示生成中的 cycles 字段）
- **与检索机制的关系**：这是检索机制中处理循环依赖的核心算法——检索时遇到环路不能无限递归，需要判断是"平面环路"（停止检索，避免重复）还是"螺旋环路"（继续检索，因为上下文不同意味着新的信息）。这直接决定了检索的终止条件。

### 原语：螺旋环路的上下文区分原理
- **ID**：64-P06
- **类型**：概念框架
- **描述**：同一组节点形成的环路，如果在不同上下文中被调用，则不是平面循环而是螺旋上升——每次调用因为上下文不同而获得新的语义，是深化而非重复。
- **溯源**：64, 第119-124行, 原文引用："这个环路在 POC 中是螺旋环路——第一次五行生克在'命主星木在寅'上下文中被调用，第二次五行生克在'昼生木旺'上下文中被调用。上下文不同，是螺旋上升，不是平面循环。"
- **依赖关系**：
  - 依赖：64-P03（节点 context 元数据）
  - 支撑：64-P05（环路分类算法）
- **与检索机制的关系**：这是检索机制中"是否重复检索"的判断原理——同一 Pattern 在不同上下文中被检索不算重复，因为上下文赋予了它不同的语义。检索机制需要记录每次检索的上下文，以此区分重复检索和深化检索。

### 原语：BFS 子图提取
- **ID**：64-P07
- **类型**：操作原语
- **描述**：从指定节点出发，通过 BFS（广度优先搜索）遍历依赖图，提取该节点的全部依赖子图。POC 中图较小不需要限制深度，但机制上支持深度限制。
- **溯源**：64, 第194-196行, 原文引用："从'命宫分析'节点出发，BFS 遍历，提取全部依赖子图（POC 图很小，不需要限制深度）。"
- **依赖关系**：
  - 依赖：64-P04（DiGraph 数据结构）、64-P02（边类型）
  - 支撑：64-P08（提示生成）
- **与检索机制的关系**：这是检索机制的核心操作——给定一个检索起点（分析任务节点），通过图遍历提取所有相关的 Pattern（依赖子图）。BFS 保证按依赖层级逐层展开，符合"先检索直接依赖，再检索间接依赖"的检索顺序。

### 原语：依赖图提示 JSON 生成
- **ID**：64-P08
- **类型**：操作原语
- **描述**：将提取的依赖子图序列化为结构化 JSON 提示，包含 analysis_task、current_context、chart_data、dependency_graph（nodes+edges）、cycles（含螺旋环路说明）、knowledge_pointers、analysis_guidance 等字段，为 AI 提供完整的分析路径指引。
- **溯源**：64, 第198-252行, 原文引用："{"analysis_task": "分析此命的命宫", "current_context": "命宫", ... "dependency_graph": {"nodes": [...], "edges": [...]}, "cycles": [{"type": "spiral", ...}], "knowledge_pointers": {...}, "analysis_guidance": "请沿依赖图路径分析..."}"
- **依赖关系**：
  - 依赖：64-P07（子图提取）、64-P05（环路检测）、64-P09（知识指针）
  - 支撑：无
- **与检索机制的关系**：这是检索机制的输出格式——检索的结果不是简单的 Pattern 列表，而是结构化的依赖图提示，包含节点、边、环路、知识指针和分析引导。这种结构化输出让 AI 能理解 Pattern 之间的依赖关系和分析顺序，而非平铺的知识点。

### 原语：知识指针机制
- **ID**：64-P09
- **类型**：结构原语
- **描述**：依赖图中的意识节点通过 knowledge_pointers 字段映射到具体的 study-notes 文件路径，实现"图节点 → 知识文档"的指针引用，使图结构不重复存储知识内容，只存储知识的位置。
- **溯源**：64, 第245-249行, 原文引用："knowledge_pointers": {"庙旺平陷": "study-notes/08-状态判断.md", "五行生克": "study-notes/星学意识/五行生克.md", "阴阳昼夜": "study-notes/星学意识/阴阳昼夜.md"}"
- **依赖关系**：
  - 依赖：64-P01（节点类型分层）
  - 支撑：64-P08（提示生成）
- **与检索机制的关系**：这是检索机制中"图-文分离"的关键设计——依赖图只存储结构关系和指针，不存储知识内容本身。检索时先在图中找到相关节点，再通过知识指针定位到具体的知识文档。这种分离使得图可以独立于知识内容演进，知识文档可以独立于图结构更新。

### 原语：analysis_guidance 分析路径引导
- **ID**：64-P10
- **类型**：操作原语
- **描述**：在提示 JSON 中生成 analysis_guidance 字段，用自然语言描述沿依赖图路径的分析步骤，包括每一步调用哪个意识、注意事项、以及螺旋环路的处理方式，将图结构翻译为 AI 可执行的分析指引。
- **溯源**：64, 第250行, 原文引用："analysis_guidance": "请沿依赖图路径分析：1) 先判断命主星木星的庙旺状态（庙旺平陷意识）；2) 判断木星五行强弱（五行生克意识），注意寅属木、木星同宫；3) 结合昼生条件判断五行强弱（阴阳昼夜意识），昼生木旺；4) 综合判断命主星强弱；5) 判断命宫其他星曜配置的吉凶。注意五行生克→阴阳昼夜→五行生克是螺旋环路，第二次调用五行生克时在昼生条件下深化判断。"
- **依赖关系**：
  - 依赖：64-P07（子图提取）、64-P05（环路检测）、64-P08（提示生成）
  - 支撑：无
- **与检索机制的关系**：这是检索机制将结构化检索结果转化为可执行指引的环节——检索不仅要返回 Pattern，还要返回 Pattern 的使用顺序和注意事项。analysis_guidance 是图遍历结果的"自然语言编译"，让 AI 能按检索到的依赖路径执行分析。
