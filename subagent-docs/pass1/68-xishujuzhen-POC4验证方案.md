# 原语提取：68-xishujuzhen-POC4验证方案

## 文档概述

本文档是稀疏矩阵（xishujuzhen）系统的 POC-4 验证方案，核心内容是将依赖图从单宫（命宫）分析扩展到双宫联动（命宫+官禄）分析，引入跨宫依赖边。文档详细描述了扩展依赖图的节点/边设计、知识内容嵌入、三步流程（JSON生成→AI解读→AI分析）、对照实验设计、评判标准及成功/失败定义。与检索机制的关系在于：依赖图本身就是一种检索结构（从认知图中检索 Pattern 的导航图），跨宫依赖边体现了跨域检索的需求，三步流程体现了"生成检索结构→解读检索结构→在检索结构引导下执行"的检索流程范式。

## 提取的原语

### 原语：跨域依赖边（Cross-Domain Dependency Edge）
- **ID**：68-P1
- **类型**：结构原语
- **描述**：在依赖图中连接不同领域/子图的边，表示一个领域的分析结果决定另一个领域的分析入口，使检索可以跨域传递。
- **溯源**：68, 第124-132行, 原文引用："跨宫依赖边（5 条）... 命宫分析 → 官禄宫分析 depends_on 跨宫依赖：命宫分析完成后才能分析官禄宫... 命主星判断 → 官主星判断 depends_on 跨宫依赖：命主星判断结果决定官主星判断（命官同主=木星）"
- **依赖关系**：
  - 依赖：依赖图节点结构（68-P3）
  - 支撑：跨域检索传递（68-P2）
- **与检索机制的关系**：跨域依赖边是检索机制中跨子图导航的核心结构——当检索从一个知识域跳转到另一个知识域时，跨域依赖边定义了合法的跳转路径和传递关系，避免检索在跨域时丢失上下文。

### 原语：分析结果传递机制（Analysis Result Propagation）
- **ID**：68-P2
- **类型**：操作原语
- **描述**：一个分析步骤的结果通过依赖边"传递"到另一个分析步骤，使下游步骤可以复用上游步骤的判断结果，而非独立重新计算。
- **溯源**：68, 第97-101行, 原文引用："官禄宫的分析几乎完全依赖跨宫依赖——不能独立分析，必须从命宫分析结果'传递'过来。这最大化了跨宫依赖的价值。"
- **依赖关系**：
  - 依赖：跨域依赖边（68-P1）
  - 支撑：空宫判断的知识传递（68-P8）
- **与检索机制的关系**：检索机制中，Pattern 的检索结果需要沿依赖链传递——上游 Pattern 的匹配结果影响下游 Pattern 的检索条件和权重。这个原语定义了"结果传递"而非"独立检索"的检索模式。

### 原语：依赖图节点类型分层（Node Type Layering）
- **ID**：68-P3
- **类型**：结构原语
- **描述**：依赖图节点按类型分层：step（分析步骤入口）、substep（子步骤）、意识（知识/判断意识），不同类型承担不同角色。
- **溯源**：68, 第114-122行, 原文引用："| 节点 ID | 类型 | 上下文 | 说明 |... 官禄宫分析 | step |... 官主星判断 | substep |... 官禄庙旺判断 | 意识 |... 命官关系判断 | 意识 |..."
- **依赖关系**：
  - 依赖：无
  - 支撑：知识内容嵌入（68-P5）、节点覆盖率审计（68-P11）
- **与检索机制的关系**：节点类型分层使检索机制可以按类型过滤和路由——step 节点是检索入口点，substep 是中间处理节点，意识节点是知识/Pattern 的载体。检索时可以按类型选择不同的检索策略。

### 原语：依赖边类型区分（Edge Type Discrimination）
- **ID**：68-P4
- **类型**：结构原语
- **描述**：依赖图的边区分为 depends_on（必须先完成）和 calls（调用/引用）两种类型，表达不同的依赖强度和执行语义。
- **溯源**：68, 第126-141行, 原文引用："命宫分析 → 官禄宫分析 | depends_on | 跨宫依赖... 恩用仇难定局 → 命官关系判断 | calls | 跨宫依赖... 官主星判断 → 官禄庙旺判断 | calls | 官主星强弱需要庙旺判断"
- **依赖关系**：
  - 依赖：依赖图节点类型分层（68-P3）
  - 支撑：边覆盖率审计（68-P12）、路径忠实率审计（68-P13）
- **与检索机制的关系**：边类型区分使检索机制可以区分"硬依赖"（depends_on：必须检索的前置 Pattern）和"软依赖"（calls：可选引用的关联 Pattern），从而控制检索的深度和广度。

### 原语：知识内容嵌入节点（Knowledge Content Embedded in Nodes）
- **ID**：68-P5
- **类型**：结构原语
- **描述**：意识类型节点直接嵌入 knowledge_content（知识文本），使依赖图不仅是结构导航图，也是知识载体——检索到节点即获得知识。
- **溯源**：68, 第180-226行, 原文引用："新增意识节点的 knowledge_content... 官禄庙旺判断：官禄宫在亥，亥属木。官主星为木星（与命主星相同——命官同主）... 命官关系判断：命宫与官禄宫的联动关系：1. 命官同主..."
- **依赖关系**：
  - 依赖：依赖图节点类型分层（68-P3）
  - 支撑：三步流程中的JSON生成（68-P6）
- **与检索机制的关系**：知识内容嵌入节点是检索机制中"检索即获取"的原语——Pattern 不是独立于图结构存储的，而是直接嵌入在图节点中。检索到节点 = 获取到 Pattern 的完整知识内容，无需二次查询。

### 原语：三步流程（Three-Step Pipeline: Generate→Interpret→Execute）
- **ID**：68-P6
- **类型**：操作原语
- **描述**：检索流程分为三步：第一步系统生成结构化JSON（依赖图+知识嵌入+要求），第二步AI解读JSON生成自然语言提示词，第三步AI在JSON+提示词共同引导下执行分析。
- **溯源**：68, 第228-243行, 原文引用："三步流程（复用 POC-3）... 第一步：经典计算生成 JSON（系统做）... 第二步：AI 解读 JSON 生成大师级提示词（AI 做）... 第三步：AI 在 JSON + 大师级提示词共同提示下分析（AI 做）"
- **依赖关系**：
  - 依赖：知识内容嵌入节点（68-P5）、依赖图结构（68-P3, 68-P4）
  - 支撑：双重对照审计（68-P10）
- **与检索机制的关系**：三步流程是检索机制的完整执行范式——生成检索结构（索引构建）→解读检索结构（查询理解）→在检索结构引导下执行（检索+推理）。第二步的"解读"环节是检索机制中"查询重写/查询理解"的对应物。

### 原语：复用已有子图（Subgraph Reuse）
- **ID**：68-P7
- **类型**：操作原语
- **描述**：扩展依赖图时保留已有子图（命宫12节点16边），在其基础上新增节点和边，而非重新设计——实现图的增量扩展。
- **溯源**：68, 第106-110行, 原文引用："POC-4 的依赖图在 POC-3 的 12 节点 16 边基础上扩展：保留命宫分析的全部 12 节点（复用 POC-2/POC-3 的图）... 新增官禄宫分析节点（约 6-8 个新节点）... 新增跨宫依赖边（约 4-6 条新边）"
- **依赖关系**：
  - 依赖：无
  - 支撑：跨域依赖边（68-P1）
- **与检索机制的关系**：复用已有子图是检索机制中索引增量更新的原语——当知识库扩展时，不需要重建整个索引，而是在已有索引基础上增量添加新节点和边。这保证了检索机制的可扩展性。

### 原语：空节点设计（Empty Node / Null Pattern）
- **ID**：68-P8
- **类型**：概念框架
- **描述**：设计一个"空宫"节点——该节点本身无内容，其判断完全依赖从其他节点传递过来的结果，最大化跨域依赖的价值。
- **溯源**：68, 第96-101行, 原文引用："官禄宫（亥宫）内没有星曜落入。这是一个'空宫'——官禄宫本身无星，其判断完全依赖：1. 宫主星（木星）的状态... 2. 命宫对官禄宫的'照射'... 空宫设计的好处：官禄宫的分析几乎完全依赖跨宫依赖——不能独立分析，必须从命宫分析结果'传递'过来。"
- **依赖关系**：
  - 依赖：分析结果传递机制（68-P2）
  - 支撑：无
- **与检索机制的关系**：空节点设计是检索机制中"纯依赖型 Pattern"的原语——某些 Pattern 本身不包含知识内容，其检索结果完全由上游 Pattern 的检索结果决定。这种设计可以测试检索机制的传递能力是否可靠。

### 原语：环路保持（Cycle Preservation）
- **ID**：68-P9
- **类型**：结构原语
- **描述**：依赖图中允许存在环路（如五行生克↔阴阳昼夜的螺旋环路），扩展图时保持环路不变——检索机制需要能处理循环依赖。
- **溯源**：68, 第149行, 原文引用："环路数 | 1 | 1（五行生克↔阴阳昼夜，不变）"
- **溯源2**：68, 第165行, 原文引用："五行生克 ←──calls── 阴阳昼夜（螺旋环路）"
- **依赖关系**：
  - 依赖：依赖边类型区分（68-P4）
  - 支撑：环路处理正确性审计（68-P14）
- **与检索机制的关系**：环路保持是检索机制中处理循环依赖的原语——认知图中存在循环引用（A依赖B，B也依赖A），检索机制不能假设图是DAG，需要能处理环路（如迭代检索、收敛检测）。

- **描述**：当实验场景过于简单导致B组已满分（天花板效应）无法体现差异时，主动选择更复杂的场景来消除天花板，让差异能真正体现。
- **溯源**：68, 第26-33行, 原文引用："换更复杂的场景，让依赖图提示的边际增益不再被天花板遮蔽。POC-4 从命宫分析（单宫）扩展到双宫联动（命宫+官禄），增加跨宫依赖。在复杂场景中：A 组不知道该在什么时候用什么、按什么顺序思考 → B 组的依赖图优势会显现... 满分天花板不会被触及 → 分数差异能真正体现"

  - 支撑：无
- **与检索机制的关系**：天花板规避是检索机制验证中的关键方法论——如果测试场景太简单，检索机制的优势无法体现（无检索也能做对）。需要选择足够复杂的场景，使"有检索"和"无检索"的差异可测量。

### 原语：显著优于的多条件定义（Multi-Criteria Significance Definition）

- **类型**：性质标准
- **描述**：定义"显著优于"需要同时满足6个条件（综合评分差距、维度不低于数、维度高1分数、覆盖率、忠实率、转译率），避免单一指标导致的假阳性。
- **溯源**：68, 第310-317行, 原文引用："B 组显著优于 A 组需要同时满足：1. B 组结果文件综合评分比 A 组高 0.50 分以上 2. B 组在至少 3 个维度上不低于 A 组 3. B 组在至少 2 个维度上比 A 组高 1 分以上 4. B 组审计 JSON 覆盖完备性 ≥ 90% 5. B 组审计思考路径忠实性 ≥ 80% 6. B 组解读转译忠实性 = 100%"
- **依赖关系**：

  - 支撑：无
- **与检索机制的关系**：多条件显著性定义是检索机制效果验证的严格标准——不能只看最终结果是否更好，还要看检索过程是否忠实（覆盖率、忠实率）、检索理解是否准确（转译率）。这防止了"结果好但过程不忠实"的假阳性。

### 原语：分阶段并行执行（Staged Parallel Execution）

### 原语：同主共享节点（Shared-Owner Cross-Domain Linkage）

  - 支撑：无
- **与检索机制的关系**：同主共享节点是检索机制中"共享键跨域检索"的原语——当两个知识域共享同一个关键实体（如同一个概念/定理），对该实体的检索结果可以同时服务于两个域，形成跨域检索的最短路径。
