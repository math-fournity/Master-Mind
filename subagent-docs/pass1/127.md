# 原语提取：127-Schema冻结与角色隔离矩阵

## 文档概述

127号文档是Phase 0核心交付物，冻结了8类schema（Task/Workspace/Event/Obligation/Representation/Evidence/HeuristicRule/Visibility）、8角色可见性矩阵、逐组件最小输入/输出契约、启发规则生命周期状态机和Truth Vault隔离机制。文档定义了系统所有动态数据对象的严格模式，以及角色之间的访问控制机制。

与253号检索问题的关系：127号文档是检索机制的**基础设施层**——它定义了检索的输入（工作智能体状态如何表示）、检索的对象（Pattern/HeuristicRule如何结构化存储）、检索的角色边界（谁能看到什么、谁能做什么）、检索的质量控制（Pattern的生命周期和效果后验）。253号检索问题的三层结构（状态感知→Pattern提取→知识悖论）在127号中都能找到对应的结构原语：Workspace Schema支撑状态感知、HeuristicRule Schema支撑Pattern提取、Visibility Schema和Truth Vault支撑知识悖论的破解。

## 提取的原语

### 原语：Task Schema——结构化任务表示
- **ID**：127-P1
- **类型**：结构原语
- **描述**：将数学任务结构化为包含type/domain/objects/premises/goal/success_conditions/stop_conditions/failure_conditions的严格模式，作为检索输入的结构化表示。
- **溯源**：127-v1-2026-08-05-Schema冻结与角色隔离矩阵.md, 第19-31行, 原文引用："Task { task_id: string, type: enum, domain: string, objects: list[string], premises: list[string], goal: string, success_conditions: list[string], stop_conditions: list[string], failure_conditions: list[string] }"
- **依赖关系**：依赖：无（顶层定义） / 支撑：Workspace Schema（127-P4）、Retriever角色契约（127-P39）
- **与检索机制的关系**：直接支撑检索第一层（状态感知）。253号第3.4节"检索问题的完整描述"中"给定"的第3项是"题目本身"。Task Schema定义了题目本身的结构化表示——不是自然语言文本，而是类型化的字段集合。检索系统可以通过task.type和task.domain做粗筛（对应253号第6.4节"按数学结构分类索引"），通过task.objects和task.premises做细筛。Task Schema的冻结特性（Q_0运行时保持冻结）保证了检索输入的稳定性。

### 原语：Task type枚举——9种任务类型分类
- **ID**：127-P2
- **类型**：结构原语
- **描述**：定义9种任务类型（prove/refute/construct/compute/classify/optimize/conjecture/explain/value），作为检索的第一级分类维度。
- **溯源**：127-v1-2026-08-05-Schema冻结与角色隔离矩阵.md, 第33-45行, 原文引用："prove | 证明 | Lean proof state是prove的严格特例；refute | 证伪/找反例；construct | 构造对象；compute | 计算；classify | 分类；optimize | 优化/上下界；conjecture | 生成并筛选猜想；explain | 解释结构；value | 研究方向价值判断"
- **依赖关系**：依赖：Task Schema（127-P1） / 支撑：检索索引的一级分类
- **与检索机制的关系**：支撑检索第二层（Pattern提取）的索引结构。253号第6.4节提出"按数学结构分类索引"和"多级索引"——Task type枚举提供了最粗粒度的索引分类。检索时先按task.type过滤Pattern集合，再在子集内做精细匹配。例如253号案例中矩条件极差题第二问的type是`optimize`（优化/上下界），检索可以先过滤出所有`optimize`类型的Pattern。

### 原语：Task冻结声明——Q_0运行时不可变
- **ID**：127-P3
- **类型**：性质标准
- **描述**：初始任务Q_0在运行时保持冻结，不混入临时假设，确保检索输入的稳定性。
- **溯源**：127-v1-2026-08-05-Schema冻结与角色隔离矩阵.md, 第47-49行, 原文引用："`Q_0`在运行时保持冻结。任务类型不只是`prove`——不让整个系统只适配定理证明。"
- **依赖关系**：依赖：Task Schema（127-P1） / 支撑：检索输入稳定性保证
- **与检索机制的关系**：间接相关。冻结声明保证了检索的输入（题目本身）在运行过程中不变，使得基于Task字段的索引和检索结果具有可复现性。如果Task在运行过程中被修改，基于Task的检索结果将不可复现。

### 原语：Workspace Schema——六类工作区状态表示
- **ID**：127-P4
- **类型**：结构原语
- **描述**：将工作智能体的动态状态结构化为六类字段：V_t（已验证核心）、F_t（猜想前沿）、O_t（开放研究义务）、R_t（当前表示及转换）、D_t（被证伪/拒绝/暂停分支）、E_t（证据），作为状态感知的结构化输入。
- **溯源**：127-v1-2026-08-05-Schema冻结与角色隔离矩阵.md, 第59-95行, 原文引用："Workspace { V_t: { verified_premises, verified_lemmas, verified_tool_results }, F_t: { candidates, temporary_assumptions, unverified_bridges }, O_t: { obligation_ids }, R_t: { active_representations, pending_transforms }, D_t: { rejected_branches, suspended_branches, recoverable_branches }, E_t: { evidence_ids } }"
- **依赖关系**：依赖：Task Schema（127-P1）、Obligation Schema（127-P13）、Evidence Schema（127-P20） / 支撑：状态感知（检索第一层）、HeuristicRule.LHS匹配模式（127-P26）
- **与检索机制的关系**：直接支撑检索第一层（状态感知）。253号第3.3节第一层问"工作智能体停在某个状态，这个状态以什么形式被助理智能体看到？"Workspace Schema给出了答案——状态不是一段非结构化的自然语言文本，而是六类结构化字段的快照。V_t告诉检索系统"已证明了什么"，F_t告诉"正在尝试什么"，O_t告诉"还有什么未完成"，R_t告诉"在用什么表示"，D_t告诉"哪些路线被否定了"。这些字段可以直接作为Pattern触发条件的匹配对象。253号第6.1节"结构化表示"方向——"把推理过程解析为结构化的步骤图"——Workspace Schema正是这种结构化表示的基础。

### 原语：RunState——完整运行状态元组
- **ID**：127-P5
- **类型**：结构原语
- **描述**：将完整运行状态定义为六元组S_t = (Q_0, W_t, L_≤t, b_t, B_t, M_t)，分别表示冻结任务、当前工作区、不可变事件历史、控制器信念、预算、模型配置。
- **溯源**：127-v1-2026-08-05-Schema冻结与角色隔离矩阵.md, 第100-114行, 原文引用："RunState { S_t = (Q_0, W_t, L_≤t, b_t, B_t, M_t) } | Q_0 | 冻结的初始任务 | W_t | 当前工作区 | L_≤t | 不可变事件历史 | b_t | 控制器对卡点/策略/缺失信息的带不确定性信念 | B_t | token/计算/工具/分支/Hint预算 | M_t | 模型版本/推理配置/权限/工具能力"
- **依赖关系**：依赖：Task Schema（127-P1）、Workspace Schema（127-P4）、Event Schema（127-P7） / 支撑：检索的完整上下文输入
- **与检索机制的关系**：直接支撑检索第一层（状态感知）。253号第3.4节"检索问题的完整描述"中"给定"的第1-3项（当前推理输出、累积context、题目本身）对应RunState的各分量。特别是b_t（控制器信念）——它记录了"卡点/策略/缺失信息的带不确定性信念"，这直接对应253号案例中"工作智能体停在这里，它有稳定性方程但不知道下一步该做什么"的状态描述。b_t可以作为状态感知的中间表示——从原始事件到"需要什么提示"的桥梁。

### 原语：Workspace冻结声明——状态隔离规则
- **ID**：127-P6
- **类型**：性质标准
- **描述**：规定临时假设进入F_t不进入V_t、被拒绝路线进入D_t不与representation共用R、W_t只能由版本化Reducer派生不能被直接修改，确保状态表示的层次隔离。
- **溯源**：127-v1-2026-08-05-Schema冻结与角色隔离矩阵.md, 第115-120行, 原文引用："`Q_0`保持冻结，不混入临时假设；临时假设进入`F_t`，不进入`V_t`；被拒绝路线进入`D_t`，不与representation共用`R`；`W_t`只能由版本化Reducer按明确字段规则派生，不能被直接修改"
- **依赖关系**：依赖：Workspace Schema（127-P4） / 支撑：状态表示的可信度分层
- **与检索机制的关系**：间接相关。隔离规则确保了状态感知的输入具有可信度分层——V_t中的内容是已验证的（高可信），F_t中的是猜想（低可信），D_t中的是被否定的（负信号）。检索系统在匹配Pattern触发条件时，可以对不同层次的状态赋予不同权重：V_t匹配的Pattern优先级高于F_t匹配的。这对应253号第3.2.4节"难点2"——"接近的定义是什么"——隔离规则提供了一种分层接近度的可能定义。

### 原语：RawEvent——不可变原始事件
- **ID**：127-P7
- **类型**：结构原语
- **描述**：将工作智能体的每次输出定义为不可变原始事件，包含event_id/type/timestamp/run_id/raw_payload/content_hash和causal_predecessors（DAG边），作为检索的时序因果基础。
- **溯源**：127-v1-2026-08-05-Schema冻结与角色隔离矩阵.md, 第130-141行, 原文引用："RawEvent { event_id: string, type: enum, timestamp: string, run_id: string, workspace_ref: string, raw_payload: object, content_hash: string, causal_predecessors: list[string] }"
- **依赖关系**：依赖：无（底层定义） / 支撑：SemanticEvent（127-P8）、事件因果DAG（127-P12）、累积context表示
- **与检索机制的关系**：直接支撑检索第一层（状态感知）。253号第3.4节"给定"的第2项是"累积context（完整QA历史）"。RawEvent定义了累积context的不可变存储格式——每次工作智能体的输出都是一个RawEvent，通过causal_predecessors形成DAG。检索系统可以通过遍历这个DAG重建推理路径，作为状态感知的输入。content_hash提供了快速比较和去重的能力。

### 原语：SemanticEvent——语义抽取事件
- **ID**：127-P8
- **类型**：结构原语
- **描述**：在RawEvent之上抽取语义事件，增加obligation_ref/evidence_ref/payload/conflict_with/confidence/source字段，将原始文本转化为结构化语义内容。
- **溯源**：127-v1-2026-08-05-Schema冻结与角色隔离矩阵.md, 第143-162行, 原文引用："SemanticEvent { event_id: string, raw_event_id: string, type: enum, timestamp: string, run_id: string, workspace_ref: string, obligation_ref: string, evidence_ref: string, payload: object, content_hash: string, causal_predecessors: list[string], conflict_with: list[string], confidence: float, source: string }"
- **依赖关系**：依赖：RawEvent（127-P7） / 支撑：状态感知的语义层、事件类型分类（127-P9）
- **与检索机制的关系**：直接支撑检索第一层（状态感知）。253号第3.2.4节"难点1"指出"助理智能体怎么看到该发Q8了？"——RawEvent是原始文本，SemanticEvent是抽取后的语义内容。检索系统不需要直接处理自然语言文本，而是处理SemanticEvent的payload——结构化的语义内容。confidence字段提供了事件可信度，source字段标注了事件来源，这些都可以作为Pattern匹配的辅助信息。这对应253号第6.1节"混合表示"方向——"结构化表示（骨架）+ 语义嵌入（血肉）"中的骨架部分。

### 原语：事件类型枚举——14种语义事件分类
- **ID**：127-P9
- **类型**：结构原语
- **描述**：定义14种语义事件类型（observation/claim/representation/subgoal/candidate/test/tool_result/contradiction/stall/backtrack/resolution/hint_injection/state_reduction/verification），作为推理状态的分类标签。
- **溯源**：127-v1-2026-08-05-Schema冻结与角色隔离矩阵.md, 第164-170行, 原文引用："observation / claim / representation / subgoal / candidate / test / tool_result / contradiction / stall / backtrack / resolution / hint_injection / state_reduction / verification"
- **依赖关系**：依赖：SemanticEvent（127-P8） / 支撑：状态感知的事件类型过滤、Pattern触发条件的事件类型匹配
- **与检索机制的关系**：直接支撑检索第一层（状态感知）和第二层（Pattern提取）。事件类型枚举提供了一种"推理状态分类法"——工作智能体的每一步输出都可以归类为这14种类型之一。253号案例中，A7（导出稳定性方程）的语义事件类型可能是`claim`（提出了一个数学声明），而工作智能体"停在这里"的状态可能是`stall`。检索系统可以通过事件类型做粗筛——例如当检测到`stall`事件时，触发"卡点处理"类Pattern的检索；当检测到`contradiction`时，触发"矛盾处理"类Pattern的检索。这对应253号第6.4节"按思维模式分类索引"的一种实现方式。

### 原语：冲突关系——事件互斥标记
- **ID**：127-P10
- **类型**：操作原语
- **描述**：定义事件间的冲突关系conflict_with，满足对称性和非自反性，冲突事件不能属于同一有效分支，用于检索时的分支过滤。
- **溯源**：127-v1-2026-08-05-Schema冻结与角色隔离矩阵.md, 第172-178行, 原文引用："`conflict_with`满足对称和非自反；若`e1 # e2`，两事件不能属于同一有效分支；首版只标记显式选择的互斥候选、被回退分支与其替代分支；不能仅因两个命题矛盾就推断生成事件冲突"
- **依赖关系**：依赖：SemanticEvent（127-P8） / 支撑：检索中的分支过滤、有效分支判定
- **与检索机制的关系**：支撑检索第二层（Pattern提取）的精确化。253号第3.2.4节"难点2"指出"有多个Pattern部分匹配"——冲突关系提供了一种过滤机制：如果两个候选Pattern关联的事件互相冲突，它们不能同时被选中。这缩小了候选集，提高了检索精度。冲突关系还支撑了DFS回溯——253号第1.3节"走不通就回溯"，回溯时被回退的分支与其替代分支标记为冲突，检索系统在回溯后不应再检索到被回退分支的Pattern。

### 原语：三层保留——原始/语义/快照的多层表示
- **ID**：127-P11
- **类型**：概念框架
- **描述**：事件数据分三层保留：原始事件（不可变）、语义抽取（可重抽）、状态快照（可重建），提供同一状态的多粒度表示。
- **溯源**：127-v1-2026-08-05-Schema冻结与角色隔离矩阵.md, 第179-183行, 原文引用："1. 原始事件（不可变）2. 语义抽取（可重抽）3. 状态快照（可重建）"
- **依赖关系**：依赖：RawEvent（127-P7）、SemanticEvent（127-P8）、Workspace Schema（127-P4） / 支撑：多粒度状态表示、多粒度匹配
- **与检索机制的关系**：直接支撑检索第一层（状态感知）的多粒度匹配。253号第6.1节提出"混合表示"方向——"结构化表示（骨架）+ 语义嵌入（血肉），用骨架做粗筛、用嵌入做精排"。三层保留正是这种多粒度表示的基础设施：原始事件层可以做文本嵌入匹配（粗筛），语义事件层可以做结构化字段匹配（中筛），状态快照层可以做拓扑匹配（精筛）。三层之间可以灵活组合，对应253号第6.2节"图嵌入"和"LLM作为匹配器"等不同匹配策略的输入需求。

### 原语：事件因果DAG——时序因果图
- **ID**：127-P12
- **类型**：结构原语
- **描述**：事件因果图是有向无环图（DAG），通过causal_predecessors字段记录每个事件的直接前驱，时间不倒流，"又回到同一想法"是两个不同时刻事件投影到相同语义状态而非事件循环。
- **溯源**：127-v1-2026-08-05-Schema冻结与角色隔离矩阵.md, 第185-189行, 原文引用："原始事件append-only，不允许修改或删除；事件因果图是DAG（时间不倒流）；'又回到同一想法'是两个不同时刻事件投影到相同语义状态，不是事件循环"
- **依赖关系**：依赖：RawEvent（127-P7） / 支撑：检索中的图遍历方向、推理路径重建
- **与检索机制的关系**：直接支撑检索第二层（Pattern提取）的图遍历方案。253号第3.3节第二层提出"图遍历——从当前状态对应的节点出发，在依赖图中遍历"。事件因果DAG提供了遍历的基础结构——从当前事件出发，沿着causal_predecessors回溯可以重建完整推理路径，这条路径的拓扑结构可以作为Pattern匹配的输入。DAG特性保证了遍历不会陷入循环。"投影到相同语义状态而非事件循环"的设计哲学也支撑了253号第6.2节"图同构/子图同构"——两个不同时刻的推理路径可能投影到相同的拓扑结构，这正是近似同构匹配的基础。

### 原语：Obligation Schema——开放义务节点
- **ID**：127-P13
- **类型**：结构原语
- **描述**：将未完成的研究目标定义为义务节点，包含status（open/discharged/suspended/failed）、parent_obligation、evidence_refs、evidence_gate和sub_obligations，作为状态感知的"未完成什么"信号。
- **溯源**：127-v1-2026-08-05-Schema冻结与角色隔离矩阵.md, 第199-211行, 原文引用："Obligation { obligation_id: string, type: enum, status: enum, task_id: string, parent_obligation: string, description: string, evidence_refs: list[string], evidence_gate: string, sub_obligations: list[string] }"
- **依赖关系**：依赖：Task Schema（127-P1）、Evidence Schema（127-P20） / 支撑：状态感知的"缺口"识别、检索需求的来源
- **与检索机制的关系**：直接支撑检索第一层（状态感知）。253号案例中，工作智能体在A7之后"停在这里，它有稳定性方程，但不知道下一步该做什么"——这个"不知道下一步该做什么"在127号框架中对应一个open状态的Obligation。Obligation的description字段可以描述"需要估计量D的下界"，这直接就是检索的输入——"此刻需要关于D下界的提示"。Obligation的status字段告诉检索系统哪些义务已完成（discharged）、哪些在进行中（open）、哪些被暂停（suspended）——只有open状态的义务才需要检索Pattern。evidence_gate字段定义了义务完成的证据要求，可以用来判断检索到的Pattern是否足以完成义务。

### 原语：ObligationHyperEdge——AND/OR义务超边
- **ID**：127-P14
