# 原语提取：82-题库作为数学思维积累方向

## 文档概述

本文档论证了题库作为数学思维路径积累的主要方向，将解题过程映射为依赖图中的实证边、跨领域映射边和图缺口。文档详细定义了题目记录的结构化格式、从题目记录到依赖图的构建算法、ArangoDB集合分层设计，以及题库建设与POC验证的整合路径。这些内容直接为检索机制提供了数据结构基础（题目记录结构、解法路径序列）、图构建算法（从语料到图的增量构建）、索引分层（按难度/领域/解法分集合存储）和质量标准（标杆级路径筛选），是检索机制底层语料组织和图构建的核心原语来源。

## 提取的原语

### 原语：解法路径作为依赖图实证边
- **ID**：82-P1
- **类型**：概念框架 / 结构原语
- **描述**：一道题的解法路径（从问题节点到答案节点的逐步推理序列）本身就是依赖图中一条思维路径的完整记录，每一步都是一条带实证来源的边。
- **溯源**：82, 第15-31行, 原文引用："一道题的解法路径，本身就是依赖图中一条思维路径的完整记录。……每一步都是一条边，每条边都有实证来源（这道题确实这么解的）。"
- **依赖关系**：
  - 依赖：依赖图节点/边模型（来自80号文档）
  - 支撑：82-P6（题目记录结构中的path字段）、82-P7（从题目记录到依赖图的构建算法）
- **与检索机制的关系**：解法路径是检索机制要检索的Pattern的原始语料形态——检索的本质是在依赖图中找到从问题节点到目标节点的路径，而解法路径就是这些路径的实证记录。检索机制需要以这些路径为索引基础。

### 原语：一题多解作为图结构（非线性链）的实证
- **ID**：82-P2
- **类型**：概念框架
- **描述**：同一道题的多种解法对应依赖图中从问题节点到答案节点的多条路径，验证了思维是图结构而非线性chain-of-thought。
- **溯源**：82, 第35-39行, 原文引用："同一道题往往有多种解法：代数法、几何法、组合法、分析法。这对应依赖图中从问题节点到答案节点的多条路径。这直接验证了 xishujuzhen 的核心设计——思维是图结构的，不是线性的 chain-of-thought。"
- **依赖关系**：
  - 依赖：82-P1（解法路径作为依赖图实证边）
  - 支撑：82-P3（跨领域映射边）、检索机制的多路径返回能力
- **与检索机制的关系**：检索机制必须支持返回多条路径（而非单一最优路径），因为同一问题存在多种有效思维路径。这决定了检索结果的结构是路径集合而非单一路径，检索算法需要支持多路径枚举和排序。

### 原语：跨领域映射边
- **ID**：82-P3
- **类型**：结构原语
- **描述**：同一问题的不同解法路径之间的对应关系构成跨领域映射边，是不同数学领域间结构同构的实证来源。
- **溯源**：82, 第41-50行, 原文引用："一道题既可以用代数方法解，又可以用拓扑方法解——两条路径之间的对应关系，就是 80 号文档中说的'跨领域映射边'……三条路径之间的映射，就是代数→模论→多项式环的跨领域结构同构。"
- **依赖关系**：
  - 依赖：82-P2（一题多解作为图结构实证）
  - 支撑：跨领域检索能力、Pattern的领域迁移
- **与检索机制的关系**：跨领域映射边是检索机制中"类比检索"的基础——当在一个领域内找不到直接路径时，可以通过跨领域映射边跳转到另一个领域的等价路径。检索机制需要将跨领域映射边作为一种特殊的边类型进行索引和遍历。

### 原语：难度梯度作为POC扩展的自然阶梯
- **ID**：82-P4
- **类型**：概念框架 / 性质标准
- **描述**：题目难度天然对应依赖路径长度和跨领域程度，形成从2-3节点到100+节点的复杂度阶梯，可作为检索机制和系统能力的渐进验证基础。
- **溯源**：82, 第52-61行, 原文引用："星学 POC 从 5 节点到 71 节点的扩展路径，在数学中可以自然地用题目难度梯度来实现——不需要人为设计复杂场景，题目本身就有天然的复杂度阶梯。"
- **依赖关系**：
  - 依赖：82-P1（解法路径作为依赖图实证边）
  - 支撑：82-P11（题库与POC验证整合）、检索机制的渐进式性能验证
- **与检索机制的关系**：难度梯度为检索机制提供了天然的测试基准分层——可以按难度梯度分层验证检索机制在不同路径长度和跨领域程度下的性能，从简单检索逐步扩展到复杂检索。

### 原语：卡点作为依赖图缺口的发现机制
- **ID**：82-P5
- **类型**：操作原语
- **描述**：解题时卡住的地方（不知道该调用什么知识）就是依赖图中缺失的边，收集卡点就是在发现依赖图的缺口，且卡点可以明确标注（第几步、什么类型）。
- **溯源**：82, 第63-67行, 原文引用："解题时卡住的地方，几乎总是因为'不知道该调用什么知识'——这正是依赖图中缺失的边。收集卡点（'我在这道题的第3步卡住了，不知道下一步该用什么'）就是在发现依赖图的缺口。"
- **依赖关系**：
  - 依赖：82-P1（解法路径作为依赖图实证边）
  - 支撑：82-P6（题目记录结构中的stuck_points字段）、82-P7（构建算法中的缺口记录）、检索机制的覆盖率诊断
- **与检索机制的关系**：卡点是检索失败的精确标注——当检索机制无法找到从当前节点到目标节点的路径时，卡点记录了缺口的位置和类型。这为检索机制提供了反馈闭环：通过卡点发现图缺口 → 补充缺口边 → 提升检索覆盖率。卡点的结构化标注（步骤号、缺失边描述）使反馈可精确定位。

### 原语：题目记录结构（结构化数据格式）
- **ID**：82-P6
- **类型**：结构原语
- **描述**：每道题结构化为包含problem_id、source、difficulty、domain[]、statement、solutions[]（每个解法含method、path[]、domains_traversed[]、cross_domain_edges[]、elegant、source）、stuck_points[]、lean_formalized的JSON记录，是检索机制的基础数据结构。
- **溯源**：82, 第125-167行, 原文引用：完整的题目记录JSON结构，包含 `"problem_id": "IMO-2025-P3"`, `"solutions": [{"method": "generating_function", "path": [...], "cross_domain_edges": [...], "elegant": false, ...}]`, `"stuck_points": [...]` 等字段。
- **依赖关系**：
  - 依赖：82-P1（解法路径作为实证边）、82-P3（跨领域映射边）、82-P5（卡点作为缺口）
  - 支撑：82-P7（从题目记录到依赖图的构建算法）、82-P8（ArangoDB Collections分层）、检索机制的索引构建
- **与检索机制的关系**：这是检索机制的核心数据结构——所有检索操作都基于此结构。path[]字段是路径检索的索引基础，domain[]和difficulty是过滤条件，cross_domain_edges[]是跨领域检索的入口，elegant是质量排序依据，stuck_points是覆盖率诊断依据。检索机制的查询语言和索引设计直接由此结构决定。

### 原语：从题目记录到依赖图的增量构建算法
- **ID**：82-P7
- **类型**：操作原语
- **描述**：遍历每道题的每个解法的path，若concept不在图中则新增节点、若相邻step间的边不在图中则新增边（类型：解法路径）；遍历cross_domain_edges新增跨领域映射边；遍历stuck_points记录为依赖图缺口。
- **溯源**：82, 第169-182行, 原文引用："对每道题的每个解法：对 path 中的每一步：如果 concept 不在依赖图节点中 → 新增节点；如果相邻 step 之间的边不在依赖图中 → 新增边（类型：解法路径）；对 cross_domain_edges 中的每条边：如果边不在依赖图中 → 新增边（类型：跨领域映射）；对 stuck_points 中的每个卡点：记录为依赖图缺口（missing_edge）"
- **依赖关系**：
  - 依赖：82-P6（题目记录结构）
  - 支撑：依赖图的增量构建、检索机制的图索引维护
- **与检索机制的关系**：这是检索机制所依赖的图索引的构建算法。检索机制在图上运行，而此算法定义了图如何从语料中增量构建——每新增一道题的结构化记录，就增量更新图索引。这种增量构建方式使检索机制可以随题库增长持续扩展，无需全量重建。

### 原语：ArangoDB Collections分层设计（题库集合）
- **ID**：82-P8
- **类型**：结构原语
- **描述**：在ArangoDB中新增三个集合：problems（题目库，含problem_id/source/difficulty/domain[]/statement等）、solutions（解法库，含solution_id/problem_id/method/path[]/domains_traversed[]/cross_domain_edges[]/elegant/source等）、stuck_points（卡点库，含stuck_id/problem_id/step/description/missing_edge/resolved等），实现题目、解法、卡点的分离存储。
- **溯源**：82, 第184-196行, 原文引用："├── 题库集合（新增）│   ├── problems（题目库）│   │   └── {problem_id, source, difficulty, domain[], statement, ...} │   ├── solutions（解法库）│   │   └── {solution_id, problem_id, method, path[], domains_traversed[], cross_domain_edges[], elegant, source, ...} │   └── stuck_points（卡点库）│       └── {stuck_id, problem_id, step, description, missing_edge, resolved, ...}"
- **依赖关系**：
  - 依赖：82-P6（题目记录结构）、81号文档的Collections设计
  - 支撑：检索机制的多集合联合查询、按集合分层的索引策略
- **与检索机制的关系**：集合分层决定了检索机制的查询路径——检索可以按集合分层进行：先在problems中按difficulty/domain过滤题目，再在solutions中按method/path检索解法路径，再在stuck_points中诊断缺口。这种分层使检索可以针对不同粒度（题目级、解法级、卡点级）进行，也支持跨集合的联合检索。

### 原语：能力分层与题库覆盖矩阵
- **ID**：82-P9
- **类型**：概念框架
- **描述**：将数学能力分为七层（解题级研究、证明构造、猜想提出、跨领域类比、识别问题本质、研究方向价值判断、大型证明组织），题库覆盖1/2/4层，部分覆盖3/5层，不覆盖6/7层，明确了题库作为检索语料的适用边界。
- **溯源**：82, 第73-85行, 原文引用："题库覆盖 1、2、4 层，部分覆盖 3、5 层，不覆盖 6、7 层。所以题库是起点和基础，不是终态。"
- **依赖关系**：
  - 依赖：80号文档的七层能力模型
  - 支撑：检索机制的能力边界意识、检索结果的适用性判断
- **与检索机制的关系**：能力分层为检索机制定义了适用边界——检索机制基于题库构建的依赖图，其检索能力上限受限于题库覆盖的能力层。检索机制需要知道哪些类型的问题可以通过题库语料检索到有效Pattern（1/2/4层），哪些需要其他语料补充（6/7层）。这是检索机制"知道自己的边界"的原语。

### 原语：标杆质量标准（天书级优美证明）
- **ID**：82-P10
- **类型**：性质标准
- **描述**：依赖图的质量上限等于构建者的数学水平，需要高质量的思维路径样本作为标杆；Proofs from THE BOOK提供的"最优美的路径"即大师会选择的路径，是"什么是好的思维路径"的标准。
- **溯源**：82, 第100-104行, 原文引用："依赖图的质量上限 = 构建者的数学水平（80 号文档'关键的诚实面对'）。要构建高质量的依赖图，需要高质量的思维路径样本。Proofs from THE BOOK 提供的就是'什么是好的思维路径'的标准——它不是最长的路径，不是最短的路径，而是最优美的路径，即大师会选择的路径。"
- **依赖关系**：
  - 依赖：80号文档的"关键的诚实面对"
  - 支撑：82-P6（题目记录结构中的elegant字段）、检索结果的质量排序
- **与检索机制的关系**：标杆质量标准为检索机制提供了结果排序的依据——当检索返回多条路径时，elegant标记（是否属于天书级优美证明）可以作为质量权重，使检索机制优先返回大师级思维路径。这使检索不仅是"找到路径"，更是"找到好路径"。

### 原语：形式化验证基准（Lean 4双重价值）
- **ID**：82-P11

- **描述**：MathLib 100 Theorems既作为思维路径语料，又作为形式化验证基准——这些定理已在Lean 4中形式化，可以验证AI提出的证明是否正确，实现语料与验证基准的统一。
- **溯源**：82, 第106-109行, 原文引用："1. 思维路径语料：100 个经典定理的形式化证明，每个都是一条完整的思维路径 2. 形式化验证基准：这些定理已经在 Lean 4 中形式化，可以用来验证 xishujuzhen 提示下 AI 提出的证明是否正确"
- **依赖关系**：
  - 依赖：82-P6（题目记录结构中的lean_formalized/lean_proof字段）
  - 支撑：检索结果的正确性验证、检索机制的精度评估
- **与检索机制的关系**：形式化验证基准为检索机制提供了精度评估手段——可以用Lean 4形式化的题目作为检索机制的测试集，验证检索到的路径是否能通过形式化验证。这使检索机制的性能评估从"主观判断"升级为"形式化可验证"。

### 原语：题库建设分阶段路径（质量递降、规模递增）
- **ID**：82-P12
- **类型**：操作原语
- **描述**：题库建设分四阶段：Phase A手工标杆题库（20-50道，建立结构化标准）→ Phase B半自动竞赛题库（100-200道，AI提取+人工审核，验证可扩展性）→ Phase C自动教材习题库（数千道，AI自动+抽样审核，积累规模）→ Phase D arXiv研究级（HTML管道，扩展到6/7层能力），质量从高到低、规模从小到大。
- **溯源**：82, 第200-216行, 原文引用："Phase A：标杆题库（手工，高质量）……这个阶段的目标不是数量，而是建立结构化标准……Phase B：竞赛题库（半自动，中等规模）……验证结构化方案的可扩展性。Phase C：教材习题库（自动，大规模）……积累规模。Phase D：arXiv 研究级（HTML 管道，研究级）……扩展到 6、7 层能力。"
- **依赖关系**：
  - 依赖：82-P6（题目记录结构）、82-P7（构建算法）、82-P10（标杆质量标准）
  - 支撑：82-P13（题库与POC验证整合）、检索机制的渐进式语料积累
- **与检索机制的关系**：分阶段建设路径为检索机制提供了渐进式语料积累策略——检索机制先在高质量小规模语料上验证（Phase A），再逐步扩展到大规模语料（Phase C/D）。每个阶段的质量-规模权衡也决定了检索机制在不同阶段的精度-覆盖率特性。

### 原语：题库与POC验证的整合（难度梯度对应POC阶梯）
- **ID**：82-P13
- **类型**：概念框架
- **描述**：题库的难度梯度天然对应POC的扩展阶梯（POC-1基础题5-10节点 → POC-8研究级70-100节点），题库建设本身就是POC验证的准备过程——每结构化一批题就为对应POC准备好实验材料。
- **溯源**：82, 第220-235行, 原文引用："这个对应关系意味着：题库建设本身就是 POC 验证的准备过程。每结构化一批题，就为对应的 POC 准备好了实验材料。二者不是独立工作线，而是同一条工作线的两个面。"
- **依赖关系**：
  - 依赖：82-P4（难度梯度作为POC阶梯）、82-P12（分阶段建设路径）
  - 支撑：检索机制的实验验证方案设计
- **与检索机制的关系**：题库-POC整合为检索机制提供了完整的实验验证框架——每个POC阶段对应特定难度梯度的题库子集，检索机制可以在对应规模的依赖图上验证其检索能力。这种对应关系使检索机制的性能评估有明确的实验设计基础，而非临时拼凑测试集。

### 原语：解法路径的步骤级结构化表示（step/concept/action三元组）
- **ID**：82-P14
- **类型**：结构原语
- **描述**：解法路径中的每一步表示为{step, concept, action}三元组——step是序号、concept是调用的知识概念、action是对该概念执行的操作（如construct/extract/decompose/estimate/derive），使路径不仅是概念序列，而是概念-操作的对偶序列。
- **溯源**：82, 第139-144行, 原文引用："{"step": 1, "concept": "generating_function", "action": "construct"}, {"step": 2, "concept": "coefficient_extraction", "action": "extract"}, {"step": 3, "concept": "partial_fraction", "action": "decompose"}, {"step": 4, "concept": "asymptotic_analysis", "action": "estimate"}, {"step": 5, "concept": "conclusion", "action": "derive"}"
- **依赖关系**：
