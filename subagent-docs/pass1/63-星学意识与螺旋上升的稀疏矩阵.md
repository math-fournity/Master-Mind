## 文档概述

本文档记录了 xishujuzhen（稀疏矩阵）系统的完整设计思想——从用户对"思考过程中依赖追溯"的直觉画面（二维稀疏矩阵→三维化→两种环路），到工程实现方案（图存储、依赖计算、环检测、提示生成），再到哲学综合（大师角色的数字化、完美提示词的经典计算可产生性）和流程细化（AI自解读、输出审计）。文档虽然是占星分析领域的，但其核心机制——依赖图的子图提取、环路分类、状态积累遍历、提示生成、审计闭环——全部可直接迁移为数学大师系统中从认知图/依赖图检索 Pattern 的检索机制原语。这是整个项目中最核心的检索机制设计源头文档之一。

## 提取的原语

### 原语：稀疏矩阵作为依赖矩阵（二维）
- **ID**：63-P1
- **类型**：结构原语
- **描述**：用稀疏矩阵表示分析节点与知识/意识之间的调用关系——行是分析节点，列是知识/意识单元，格子值是"该节点是否调用该意识"，大部分格子为空（稀疏性）。
- **溯源**：63, 第45行, 原文引用："不是每个步骤都要调用每个意识。命宫分析可能调用五行生克+阴阳昼夜，但不需要调用虚实；格局分析可能调用庙旺平陷+恩用仇难，但不需要调用阴阳昼夜。这些调用关系构成一个稀疏矩阵——大部分格子是空的，只有特定的步骤和特定的意识之间有连接。"
- **依赖关系**：
  - 依赖：无（基础结构原语）
  - 支撑：63-P2（三维扩展）、63-P25（稀疏性原理）
- **与检索机制的关系**：这是检索机制的基础数据结构——检索的本质是从"分析节点×知识单元"的稀疏矩阵中提取当前节点相关的非空格子。Pattern 检索就是在这个稀疏矩阵中按当前问题上下文提取激活的 Pattern 子集。

### 原语：三维稀疏矩阵（行×列×上下文层）
- **ID**：63-P2
- **类型**：结构原语
- **描述**：二维矩阵不足以表达"同一节点在不同上下文下调用同一知识产生不同结论"，需要扩展为三维：行×列×上下文层。第三维是上下文层，使环路可被正确理解为螺旋上升而非平面循环。
- **溯源**：63, 第271行, 原文引用："但这个二维矩阵不够——因为同一个节点在不同上下文下调用同一个意识，产生不同结论。所以实际上是三维的：行×列×上下文层。"
- **依赖关系**：
  - 依赖：63-P1（二维稀疏矩阵）
  - 支撑：63-P3（环路判别）、63-P8（状态积累遍历）、63-P16（上下文状态追踪）
- **与检索机制的关系**：检索不能只按"节点×Pattern"二维匹配，必须引入上下文层——同一 Pattern 在不同问题上下文中被检索时，其激活含义和输出结论不同。检索机制必须携带上下文维度。

### 原语：螺旋上升环路 vs 平面环路判别标准
- **ID**：63-P3
- **类型**：概念框架
- **描述**：依赖图中的环路分两种：平面环路（同一上下文中的循环论证，应停止追溯）和螺旋上升环路（不同上下文层的深化，应继续追溯）。判别标准是"追溯一圈后是否产生了新的判断维度/上下文是否变化"。
- **溯源**：63, 第53-58行, 原文引用："判别标准：追溯一圈之后，是否产生了新的判断维度。...如果回路的每一段都在为同一条判断提供支撑，那是平面环路（冗余）；如果回路的不同段在为不同层次的判断提供支撑，那是螺旋上升（深化）。"
- **依赖关系**：
  - 依赖：63-P2（三维稀疏矩阵/上下文层）
  - 支撑：63-P4（环路检测算法）、63-P8（状态积累遍历）
- **与检索机制的关系**：检索过程中遇到依赖环路时，需要判别是停止还是继续追溯。平面环路=冗余检索（已检索过的相同上下文，停止）；螺旋环路=深化检索（不同上下文层，继续）。这是检索终止条件的核心判据。

### 原语：环路检测算法（SCC + 上下文元数据分类）
- **ID**：63-P4
- **类型**：操作原语
- **描述**：用 Tarjan 强连通分量（SCC）算法发现图中所有环，然后对每个 SCC 检查节点的上下文元数据：所有节点上下文相同→平面环路（标记已处理）；上下文不同→螺旋环路（允许继续）。
- **溯源**：63, 第332-335行, 原文引用："1. 用 Tarjan 找到所有 SCC（环）2. 对每个 SCC，检查其中所有节点的上下文元数据 3. 如果所有节点上下文相同 → 平面环路，标记为'已处理，结论为 X' 4. 如果节点上下文不同 → 螺旋环路，标记为'新层，允许继续'"
- **依赖关系**：
  - 依赖：63-P3（环路判别标准）、63-P11（带元数据有向图）
  - 支撑：63-P17（环路检测作为呈现的一部分）
- **与检索机制的关系**：这是检索流程中环路处理的可执行算法。检索依赖图时遇到环，用此算法自动分类，决定哪些环停止追溯（避免冗余）、哪些环继续追溯（深化检索）。

### 原语：依赖子图提取（BFS + 深度限制 + 激活历史标注）
- **ID**：63-P5
- **类型**：操作原语
- **描述**：给定当前分析上下文，从当前节点出发沿依赖边广度优先遍历，收集 1-2 跳邻居以控制子图大小，每条边带上元数据（依赖类型、上下文、是否已激活），输出一个合理大小的依赖子图。
- **溯源**：63, 第298-304行, 原文引用："从当前节点出发，遍历依赖图，提取一个合理大小的子图...沿依赖边广度优先遍历，收集 1-2 跳的邻居（控制子图大小）...每条边带上元数据：依赖类型、上下文、是否已被激活过...输出一个子图"
- **依赖关系**：
  - 依赖：63-P11（带元数据有向图）、63-P15（合理大小条件）
  - 支撑：63-P6（提示生成器）、63-P13（JSON传送格式）
- **与检索机制的关系**：这是检索机制的核心操作——从认知图中按当前问题上下文提取相关 Pattern 子图。深度限制控制检索范围（避免全图爆炸），激活历史标注避免重复检索。

### 原语：依赖图作为提示生成器（非自动推理引擎）
- **ID**：63-P6
- **类型**：概念框架
- **描述**：系统不做推理判断，只做依赖关系的计算和呈现——把依赖子图作为提示呈现给 AI，AI 看懂依赖关系后完成综合性分析。系统的智能在于把依赖图拆分到合理大小，AI 的智能在于在依赖图提示下完成判断。
- **溯源**：63, 第151行, 原文引用："这段话澄清了系统的本质：它不是一个自动推理引擎，而是一个提示生成器。脚本计算依赖关系，把依赖关系作为提示呈现给 AI，AI 看懂依赖关系后完成综合性分析。"
- **依赖关系**：
  - 依赖：63-P5（子图提取）
  - 支撑：63-P7（粒度拆分）、63-P19（AI自解读）
- **与检索机制的关系**：定义了检索机制的角色边界——检索机制不替代 AI 做数学判断，只提供"此刻该考虑哪些 Pattern、它们之间什么关系"的结构化提示。检索结果是提示，不是答案。

### 原语：粒度拆分→小图分析→大图综合
- **ID**：63-P7
- **类型**：操作原语
- **描述**：当依赖关系复杂时，不一次性呈现所有依赖，而是拆分成多个小的依赖路径图：先完成每个小图的智能分析（中间结论保存），再在上下文允许时把多个小图结果汇总成更大的依赖路径图网，完成更高层综合。
- **溯源**：63, 第178-184行, 原文引用："拆分成多个小的依赖路径图：1. 先完成每个小依赖路径图的智能分析...2. 每个小图的分析结果作为中间结论保存 3. 在上下文允许的情况下，把多个小图的分析结果汇总，呈现一个更大的依赖路径图网"
- **依赖关系**：
  - 依赖：63-P5（子图提取）、63-P6（提示生成器）
  - 支撑：无
- **与检索机制的关系**：检索的粒度控制策略——分层检索。先检索小范围 Pattern 子图做局部分析，再汇总多个局部结果做全局综合。避免一次性检索全图导致上下文溢出。

### 原语：激活日志（带状态积累的图遍历）
- **ID**：63-P8
- **类型**：结构原语
- **描述**：激活日志记录"哪个意识在哪个上下文下被激活，产生了什么中间结论"。螺旋上升的数学本质是带状态积累的图遍历——遍历过程中每个节点的输出更新全局状态，全局状态又影响后续节点的输入。没有状态积累，环路只是平面环路。
- **溯源**：63, 第775-776行, 原文引用："螺旋上升在数学上是：带状态积累的图遍历。不是无状态的 BFS（每次遍历独立），是有状态的遍历——遍历过程中每个节点的输出会更新全局状态，全局状态又影响后续节点的输入。"
- **依赖关系**：
  - 依赖：63-P2（三维/上下文层）、63-P3（螺旋vs平面）
  - 支撑：63-P16（上下文状态追踪）、63-P18（审计机制）
- **与检索机制的关系**：检索不是无状态的查表，是有状态的过程——每次检索 Pattern 产生的中间结论会更新全局状态，影响后续检索的输入。激活日志是检索过程的 state，使螺旋检索成为可能。

### 原语：意识注册表（垂直维度层）
- **ID**：63-P9
- **类型**：结构原语
- **描述**：意识注册表是所有可被调用的知识/意识单元（五行生克、恩用仇难、阴阳昼夜等）的注册表，对应稀疏矩阵的列/垂直维度上的"层"。它定义了检索空间中可被激活的 Pattern 集合。
- **溯源**：63, 第106-107行, 原文引用："意识注册表（五行生克、恩用仇难、阴阳昼夜…）| 垂直维度上的'层'"
- **依赖关系**：
  - 依赖：无（基础结构）
  - 支撑：63-P1（稀疏矩阵的列）、63-P10（激活接口）
- **与检索机制的关系**：这是 Pattern 库的注册表——检索机制可检索的 Pattern 全集。每个 Pattern 在注册表中有唯一标识，检索时通过注册表定位。

### 原语：结构化但不僵化的激活接口
- **ID**：63-P10
- **类型**：结构原语
- **描述**：知识/意识激活的接口需要结构化但不僵化——输入不是固定参数列表而是"当前分析上下文"（可能是命宫+命主星，也可能是大限+限宫宫主），输出不是数值而是"判断"。足够结构化让系统能记录追踪，但不僵化到限制 AI 判断空间。
- **溯源**：63, 第135行, 原文引用："这意味着意识激活的接口需要是结构化但不僵化的——足够结构化让系统能记录和追踪，但不僵化到限制 AI 的判断空间。"
- **依赖关系**：
  - 依赖：63-P9（意识注册表）
  - 支撑：63-P13（JSON传送格式）
- **与检索机制的关系**：定义了 Pattern 检索的接口契约——检索输入是上下文（灵活的、非固定参数），检索输出是结构化的 Pattern 调用记录（可追踪可审计），但 Pattern 的运用方式留给 AI。

### 原语：带元数据的有向图存储
- **ID**：63-P11
- **类型**：结构原语
- **描述**：稀疏矩阵的本质是带元数据的有向图——节点=知识单元+分析上下文，边="依赖于"关系，节点和边上都有元数据（上下文、激活历史、依赖类型）。用 networkx 等图计算库存储。
- **溯源**：63, 第279-282行, 原文引用："我们的'稀疏矩阵'本质是一个带元数据的有向图：节点 = 知识单元（来自 study-notes）+ 分析上下文，边 = '依赖于'关系，节点和边上都有元数据（上下文、激活历史、依赖类型）"
- **依赖关系**：
  - 依赖：无（基础结构）
  - 支撑：63-P4（环路检测）、63-P5（子图提取）、63-P12（稀疏矩阵存储）
- **与检索机制的关系**：这是认知图/依赖图的底层数据结构。Pattern 作为节点，Pattern 间依赖作为边，上下文和激活历史作为元数据。检索在这个有向图上进行。

### 原语：稀疏邻接矩阵存储（CSR/CSC格式）
- **ID**：63-P12
- **类型**：结构原语
- **描述**：当图变大时，用邻接矩阵的稀疏存储（CSR/CSC格式）做高效计算。scipy.sparse.csgraph 提供基于稀疏矩阵的图算法（连通分量、最短路径、遍历）。networkx 做灵活图操作，scipy.sparse 做高效矩阵运算，两者可互转。
- **溯源**：63, 第288-290行, 原文引用："用邻接矩阵的稀疏存储（CSR/CSC 格式）做高效计算。scipy.sparse.csgraph 提供了基于稀疏矩阵的图算法：连通分量、最短路径、广度/深度优先遍历。networkx 和 scipy.sparse 可以互转"
- **依赖关系**：
  - 依赖：63-P11（有向图存储）
  - 支撑：63-P5（子图提取的高效实现）
- **与检索机制的关系**：大规模 Pattern 库的检索性能保障。当 Pattern 数量增长到万级以上时，稀疏矩阵存储和计算使检索保持高效。

### 原语：依赖图JSON传送格式
- **ID**：63-P13
- **类型**：结构原语
- **描述**：依赖子图传送给AI的格式是结构化JSON，包含：current_context（当前上下文）、depth（遍历深度）、nodes（节点列表带type和context）、edges（边列表带type）、cycles（环路列表带type/note/contexts）、previous_activations（之前激活记录带结论）。
- **溯源**：63, 第354-383行, 原文引用：JSON结构包含 "current_context", "depth", "nodes" [{"id","type","context"}], "edges" [{"from","to","type"}], "cycles" [{"type","nodes","contexts","note"}], "previous_activations" [{"意识","context","conclusion"}]
- **依赖关系**：
  - 依赖：63-P5（子图提取）、63-P10（激活接口）、63-P4（环路检测）
  - 支撑：63-P19（AI自解读JSON）、63-P20（双重对照审计）
- **与检索机制的关系**：这是检索结果的标准输出格式——检索机制输出的不是裸 Pattern 列表，而是结构化的依赖子图JSON，包含节点、边、环路分类、历史激活。这个格式同时是后续审计的基准。

### 原语：编排层不拥有后端资源
- **ID**：63-P14
- **类型**：结构原语
- **描述**：导航/编排系统编排一切但不拥有一切——它引用知识仓库的路径而不搬移文件，import 计算引擎而不包含其代码。系统是唯一对AI暴露的接口，后端资源（知识、计算）是被编排的后端。
- **溯源**：63, 第452行, 原文引用："正确的做法是：xishujuzhen 编排一切，但不拥有一切。"
- **依赖关系**：
  - 依赖：63-P21（知识仓库与思维导航分离）
  - 支撑：无
- **与检索机制的关系**：检索机制作为编排层，不拥有 Pattern 内容本身（Pattern 内容在知识仓库中），只拥有 Pattern 间的依赖关系和检索路径。检索机制是 AI 与 Pattern 库之间的唯一接口。

### 原语：完美提示词四条件
- **ID**：63-P15
- **类型**：性质标准
- **描述**：完美提示词（检索结果）需满足四个条件：完整性（包含当前上下文所需的全部依赖，不遗漏）、无冗余（不包含当前上下文不需要的依赖）、正确结构（呈现依赖间结构——谁依赖谁、分叉、汇聚、环路，而非扁平列表）、合理大小（总大小在AI上下文窗口合理比例内，需粒度控制）。
- **溯源**：63, 第718-728行, 原文引用："条件一：完整性...条件二：无冗余...条件三：正确的结构...条件四：合理的大小...完美提示词 = 完整 + 无冗余 + 正确结构 + 合理大小。这四个条件中，前两个是内容条件（依赖图的内容决定），后两个是工程条件（子图提取和提示生成的实现决定）。"
- **依赖关系**：
  - 依赖：63-P5（子图提取）、63-P7（粒度拆分）
  - 支撑：无（这是检索质量的评判标准）
- **与检索机制的关系**：这是检索机制的质量标准——检索结果必须完整（不漏 Pattern）、无冗余（不多检索）、结构正确（保留 Pattern 间依赖关系）、大小合理（不溢出上下文）。前两个是内容标准，后两个是工程标准。

### 原语：上下文状态追踪（螺旋圈编号）
- **ID**：63-P16
- **类型**：操作原语
