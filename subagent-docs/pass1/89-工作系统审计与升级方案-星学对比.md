# 原语提取：89-工作系统审计与升级方案·星学对比

## 文档概述

本文档是星学项目工作系统升级的审计报告，对比数学项目的当前状态，提出升级方向。文档详细描述了星学项目的5层系统架构、Capsule机制、Stop Gate机制、Master-Worker-Auditor三角色分离、认知单元图、CP1-CP6工作流等核心机制，以及数学项目可以借鉴和超越的部分。与检索机制的关系极为密切——认知单元图的图遍历检索、AQL图遍历找前置认知、认知覆盖验证、版本链管理、动态查询检查清单等都是直接的检索机制原语或其支撑结构。

## 提取的原语

- **ID**：89-P1
- **类型**：结构原语
- **描述**：将工作系统分为运行时协议层、CLI集成层、核心控制脚本层、运行时工具层、运行时状态层五层，每层有明确的组件和功能边界。

- **依赖关系**：
  - 依赖：无（顶层架构定义）
  - 支撑：89-P2（Capsule机制）、89-P5（自我迭代机制）等所有其他机制都在此架构内运作
- **与检索机制的关系**：5层架构为检索机制提供了分层放置的框架——检索所需的状态存储（L5）、控制脚本（L3）、协议清单（L1）各有归属层，检索机制可以嵌入其中。

### 原语：Capsule 机制（实时上下文注入）
- **ID**：89-P2
- **类型**：操作原语
- **描述**：每次session start或user prompt submit时，从文件系统实时生成一个capsule注入AI上下文，包含协议审计结果、任务状态计数、Worker状态、非线性状态、停止策略、活跃锚点、角色命令简报、下一步必需动作——不依赖记忆恢复上下文。
- **溯源**：89, 第23-35行, 原文引用："每次 session start 或 user prompt submit 时，hook 调用 `moira_runtime.py hook <event>`，生成一个 capsule 注入到 AI 上下文中。Capsule 包含：协议审计结果...任务状态计数...Worker 状态计数...非线性状态...停止策略...活跃锚点...角色命令简报...下一步必需动作" + "AI 不需要依赖记忆来恢复上下文——capsule 从文件系统实时生成，是'机器派生的控制上下文'，比记忆和终端印象更强。"
- **依赖关系**：
  - 依赖：89-P1（5层架构，capsule在L4工具层生成）
  - 支撑：检索机制的查询结果可以通过capsule注入到AI上下文中——capsule是检索结果到达AI认知的通道
- **与检索机制的关系**：Capsule是检索结果的交付通道。检索机制从认知图/依赖图中检索到的Pattern，可以通过capsule机制注入到AI工作上下文中。数学项目的capsule可以包含"当前POC进度、ArangoDB状态、拓扑覆盖验证结果"（第137行），这些本身就是检索结果的呈现。

### 原语：Stop Gate 机制
- **ID**：89-P3
- **类型**：操作原语
- **描述**：当AI尝试停止时，hook检查协议审计是否PASS、是否有未完成任务、是否有busy worker，如果有任何未完成工作则返回block阻止AI停止。
- **溯源**：89, 第37-45行, 原文引用："当 AI 尝试停止时，hook 检查：协议审计是否 PASS...是否有 failed/blocked/error 任务...是否有 queued/leased/in_progress 任务...是否有 busy worker。如果有任何未完成的工作，hook 返回 `block`，阻止 AI 停止。"
- **依赖关系**：
  - 依赖：89-P1（5层架构中的hook集成）
  - 支撑：检索流程的完整性保障——确保检索+处理流程不会过早终止
- **与检索机制的关系**：Stop Gate可以检查检索流程是否完成——例如认知覆盖验证是否通过、所有需要的Pattern是否已检索到。它是检索流程的完整性守卫。

- **依赖关系**：
