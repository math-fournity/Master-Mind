# 原语提取：99-工作系统经验反哺大师系统升级方案

## 文档概述

本文档分析工作系统升级（89-98号）中产生的6个机制如何反哺大师系统（目标系统），形成大师系统的下一代升级方案。6个反哺点涵盖经典计算展开、CP1-CP3认知加载、版本链管理、回归验证、自动发现新意识、三层提取版本链管理。文档与检索机制高度相关——CP1-CP3本质上是图遍历检索流程，种子推荐表是检索路由机制，版本链是检索结果的版本管理结构，回归验证是检索质量保障机制。

## 提取的原语

### 原语：CP1种子选择——检索入口的种子确定
- **ID**：99-P1
- **类型**：操作原语
- **描述**：在图遍历检索前，先确定本次任务需要哪些种子认知单元作为检索起点，种子不仅包括工作流认知单元，还包括与题目相关的数学意识。
- **溯源**：99号文档, 第63-66行, 原文引用："CP1：种子选择（确定本次任务需要哪些种子认知单元）"
- **溯源**：99号文档, 第95-97行, 原文引用："种子选择时，不仅选工作流认知单元，还要选**与题目相关的数学意识**作为种子。比如：矩条件极差题 → 种子包含`numerical_check`（数值检验意识）和`extreme_testing`（极端检验）"
- **依赖关系**：
  - 依赖：无（这是检索流程的入口步骤）
  - 支撑：99-P2（CP2图遍历需要种子作为起点）
- **与检索机制的关系**：种子选择是检索的第一步——确定从哪些节点开始图遍历。种子的质量直接决定检索覆盖范围。将数学意识纳入种子选择，扩展了检索的语义范围。

### 原语：CP2认知加载——AQL图遍历检索
- **ID**：99-P2
- **类型**：操作原语
- **描述**：从种子认知单元出发，沿depends_on边进行AQL图遍历，自动找到所有前置认知（包括AI没想到但任务需要的意识），实现系统性认知加载。
- **溯源**：99号文档, 第65-66行, 原文引用："CP2：认知加载（AQL图遍历，从种子出发沿depends_on边找到所有前置认知）"
- **溯源**：99号文档, 第68行, 原文引用："98号测试验证：从seven_step_workflow出发，depth=7找到26个认知单元，覆盖所有前置依赖。"
- **依赖关系**：
  - 依赖：99-P1（CP1种子选择提供遍历起点）
  - 支撑：99-P3（CP3缺口检查验证遍历结果）
- **与检索机制的关系**：这是检索机制的核心——图遍历是依赖图检索的基本算法。depth参数控制检索深度，depends_on边定义检索路径。AQL是ArangoDB的图遍历查询语言，直接对应图检索操作。

### 原语：CP3缺口检查——检索完整性验证
- **ID**：99-P3
- **类型**：操作原语
- **描述**：验证已加载的认知是否覆盖任务所需，检查是否遗漏了任务相关但与种子无依赖边的意识节点。
- **溯源**：99号文档, 第67行, 原文引用："CP3：缺口检查（验证已加载的认知是否覆盖任务所需）"
- **溯源**：99号文档, 第90-91行, 原文引用："CP3：缺口检查 / 验证是否遗漏了任务相关但与种子无依赖边的意识"
- **依赖关系**：
  - 依赖：99-P2（CP2图遍历的结果需要被验证）
  - 支撑：无
- **与检索机制的关系**：缺口检查是检索结果的验证环节——图遍历只能找到有依赖边的节点，但任务可能需要无直接依赖边但语义相关的意识。这揭示了纯图遍历检索的局限性，需要补充语义检索。

### 原语：种子推荐表——问题类型到检索种子的路由映射
- **ID**：99-P4
- **类型**：结构原语
- **描述**：为每类数学问题建立"种子推荐表"——什么类型的题应该选哪些意识作为种子，实现从问题特征到检索起点的路由。
- **溯源**：99号文档, 第100行, 原文引用："为每类数学问题建立'种子推荐表'——什么类型的题应该选哪些意识作为种子"
- **溯源**：99号文档, 第101行, 原文引用："AI接到题目后，先查种子推荐表，再执行CP1-CP3"
- **依赖关系**：
  - 依赖：99-P1（种子推荐表为CP1种子选择提供输入）
  - 支撑：无
- **与检索机制的关系**：种子推荐表是检索路由机制——将问题类型映射到检索起点。这类似于搜索引擎中的查询理解/查询扩展，把用户的问题特征转化为图遍历的起始节点集合。

### 原语：意识节点双重身份——跨图检索的数据结构基础
- **ID**：99-P5
- **类型**：结构原语
- **描述**：意识节点在cognition_units（工作认知图）和dg_nodes（数学依赖图）中都有对应记录，具有双重身份——既是AI的工作认知，也是数学证明的依赖节点。
- **溯源**：99号文档, 第18行, 原文引用："两套图共享同一个ArangoDB实例（xishujuzhen_math），意识节点有双重身份。"
- **溯源**：99号文档, 第80行, 原文引用："意识节点双重身份已经实现（cognition_units + dg_nodes）。cognition_units中的意识节点是AI的工作认知——做数学证明时需要的思维方式。"
- **依赖关系**：
  - 依赖：无（这是基础数据结构设计）
  - 支撑：99-P2（图遍历检索可以在两个集合间跨越检索）
- **与检索机制的关系**：双重身份使得检索可以跨图进行——从工作认知图检索到的意识节点可以直接在数学依赖图中使用，反之亦然。这是跨域检索的数据结构基础。

### 原语：经典计算展开——确定性骨架生成替代AI规划
- **ID**：99-P6
- **类型**：操作原语
- **描述**：用经典计算（L0拓扑排序+L1类型推断+L2 section划分）从依赖图G直接生成G'_topo骨架，保证100%覆盖节点集和边集，AI只做L3语义细化（section命名+spiral类型确认）。
- **溯源**：99号文档, 第28行, 原文引用："92号方案设计了topo_generator.py，实现经典计算展开G'_topo骨架（L0拓扑排序+L1类型推断+L2 section划分）。98号测试报告验证：**1次通过100%覆盖**（18/18节点，25/25边，2/2环路）。"
- **溯源**：99号文档, 第40行, 原文引用："**步骤2从'meta AI生成'升级为'经典计算生成骨架（L0+L1+L2）+ AI语义细化（L3）'**"
- **依赖关系**：
  - 依赖：无（topo_generator.py已实现）
  - 支撑：99-P7（拓扑覆盖验证）
- **与检索机制的关系**：经典计算展开是一种确定性的结构检索——从源图G中检索所有节点和边，按拓扑序排列生成骨架。这比AI从零规划更可靠，因为它是从图中确定性提取而非生成。L0/L1/L2/L3的分层也是检索结果的分层细化。

### 原语：拓扑覆盖验证——检索完整性的确认性验证
- **ID**：99-P7
- **类型**：操作原语
- **描述**：TopologyVerifier验证生成的G'_topo是否100%覆盖源图G的节点集和边集，经典计算展开后验证必然1次通过，不需要回退。
- **溯源**：99号文档, 第45行, 原文引用："TopologyVerifier验证（**必然1次通过，不需要回退**）"
- **溯源**：99号文档, 第57行, 原文引用："步骤3不需要回退——L0骨架展开从G直接拷贝节点集和边集"
- **依赖关系**：
  - 依赖：99-P6（经典计算展开生成骨架后才能验证）
  - 支撑：无
- **与检索机制的关系**：拓扑覆盖验证是检索结果完整性检查——确认检索到的节点集和边集与源图完全一致。从"catch性验证"（可能遗漏）升级为"确认性验证"（必然通过），是检索质量保障的范式转变。

### 原语：版本链——认知演化的版本追踪结构
- **ID**：99-P8
- **类型**：结构原语
- **描述**：每个认知单元有多个版本（v1→v2→v3...），current_version指向最新版本，版本链记录认知的演化历史，每个版本记录包含来源POC编号、验证结果、新发现。
- **溯源**：99号文档, 第113行, 原文引用："91号方案设计了cog_versions版本链——每个认知单元有多个版本，current_version指向最新版本。版本链记录了认知的演化历史。"
- **溯源**：99号文档, 第142行, 原文引用："版本记录包含：POC编号、验证结果、新发现"
- **依赖关系**：
  - 依赖：无（版本链是基础数据结构）
  - 支撑：99-P9（current_version指针）、99-P10（三层提取版本管理）、99-P12（回归验证D3）
- **与检索机制的关系**：版本链是检索结果的版本管理结构——检索到一个认知单元后，可以通过版本链了解其演化历史和当前理解深度。跨session的AI可以通过版本链快速恢复"某个意识当前的理解深度"，这是检索结果的上下文恢复机制。

### 原语：current_version指针——检索最新版本的快速定位
- **ID**：99-P9
- **类型**：结构原语
- **描述**：每个认知单元的current_version字段指向最新版本，检索时可以直接获取最新理解，无需遍历整个版本链。
- **溯源**：99号文档, 第113行, 原文引用："current_version指向最新版本"
- **溯源**：99号文档, 第115行, 原文引用："3个多版本认知单元（math_master_system, poc_methodology, seven_step_workflow）的current_version全部正确指向latest。"
- **依赖关系**：
  - 依赖：99-P8（版本链结构）
  - 支撑：无
- **与检索机制的关系**：current_version是检索的索引指针——类似数据库中的指针索引，让检索直接定位到最新版本，避免全量遍历。这是检索效率优化的数据结构。

### 原语：三层提取版本链管理——L1/L2/L3的版本化存储与检索
- **ID**：99-P10
- **类型**：操作原语
- **描述**：用版本链管理三层提取的演化——L1解题思路是v1（具体步骤序列），L2数学思维是v2（从L1抽象出的思维模式），L3范式思维是v3（从多个L2综合出的范式），current_version标识当前提取层次。
- **溯源**：99号文档, 第263行, 原文引用："**用版本链管理三层提取的演化——L1是v1，L2是v2，L3是v3**"
- **溯源**：99号文档, 第292行, 原文引用："跨题复用时，AI通过current_version知道'这个认知是L1/L2/L3哪个级别'——L1只在类似题中复用，L3可以跨领域复用"
- **依赖关系**：
  - 依赖：99-P8（版本链结构）、99-P9（current_version指针）
  - 支撑：无
- **与检索机制的关系**：三层提取版本链管理是检索结果的分层存储与分层检索——不同抽象层次的认知有不同的复用范围（L1近迁移、L3远迁移），检索时可以通过current_version判断认知层次，决定复用策略。这是基于认知层次的分层检索机制。

### 原语：图遍历depth参数——检索深度控制
- **ID**：99-P11

- **描述**：图遍历时通过depth参数控制检索深度，depth=7可以覆盖所有前置依赖，depth=9用于验证遍历完整性。
- **溯源**：99号文档, 第68行, 原文引用："从seven_step_workflow出发，depth=7找到26个认知单元，覆盖所有前置依赖。"
- **溯源**：99号文档, 第185行, 原文引用："D4：图遍历完整性（depth=7 vs depth=9是否一致）"
- **依赖关系**：
  - 依赖：99-P2（图遍历检索）
  - 支撑：99-P12（回归验证D4用depth参数验证完整性）
- **与检索机制的关系**：depth参数是图遍历检索的核心控制参数——决定了检索的覆盖范围。depth=7 vs depth=9的一致性检查是验证检索是否已收敛（增加深度不再发现新节点），这是检索完备性的验证方法。

### 原语：回归验证——检索质量的持续保障
- **ID**：99-P12
- **类型**：操作原语
- **描述**：依赖图变更后，对所有POC的ground truth跑回归验证，覆盖D1图遍历覆盖率、D3版本链正确性、D4图遍历完整性、拓扑覆盖验证，检测变更是否破坏已有检索功能。
- **溯源**：99号文档, 第161行, 原文引用："94号方案设计了POC回归验证——D1覆盖率+D3版本链+D4图遍历完整性+D2约束保留+D5流程可执行性，满分100。"
- **溯源**：99号文档, 第182-186行, 原文引用："D1：图遍历是否仍然覆盖所有ground truth认知单元 / D3：版本链是否仍然正确（current_version=latest）/ D4：图遍历完整性（depth=7 vs depth=9是否一致）/ 拓扑覆盖验证：TopologyVerifier是否仍然1次通过100%覆盖"
- **依赖关系**：
  - 依赖：99-P8（版本链）、99-P11（depth参数）、99-P7（拓扑覆盖验证）
  - 支撑：无
- **与检索机制的关系**：回归验证是检索系统的持续质量保障——图结构变更后验证检索功能是否仍然正常。ground truth是检索的预期结果集，回归验证就是"变更后检索结果是否仍然与预期一致"。这是检索系统的集成测试机制。

### 原语：ground truth——检索预期结果集
- **ID**：99-P13
- **类型**：结构原语
- **描述**：为每个POC建立ground truth——该POC验证时图遍历应该找到的认知单元集合，作为回归验证的基准。
- **溯源**：99号文档, 第189行, 原文引用："为每个POC建立ground truth（该POC验证时图遍历应该找到的认知单元集合）"
- **溯源**：99号文档, 第190行, 原文引用："依赖图变更后，对所有POC的ground truth跑回归验证"
- **依赖关系**：
  - 依赖：99-P2（图遍历检索产生ground truth）
  - 支撑：99-P12（回归验证以ground truth为基准）
- **与检索机制的关系**：ground truth是检索的黄金标准——定义了"正确检索结果应该是什么"。这是检索评估的基础数据结构，类似于信息检索中的relevant documents集合。

### 原语：增量来源分析——从POC对比中发现隐含意识
- **ID**：99-P14
- **类型**：操作原语
- **描述**：分析POC评分结果中B组优于A组的增量来源，如果增量来自一个尚未被显式标注的数学意识，则标记为"候选新意识"，在B组提示材料中找到这个隐含的意识。
- **溯源**：99号文档, 第218-222行, 原文引用："POC验证完成，评分结果显示B组在某个维度显著优于A组 / ↓ 分析增量来源 / B组优于A组的根源是什么？ / ↓ 如果增量来自一个尚未被显式标注的数学意识 / 在B组的提示材料中找到这个隐含的意识"
- **依赖关系**：
  - 依赖：无（增量来源分析是独立的分析步骤）
  - 支撑：99-P15（自动发现新意识节点）
- **与检索机制的关系**：增量来源分析是检索反馈闭环的分析环节——通过对比实验组的差异，发现检索系统中缺失的意识节点。这是"从使用中发现检索缺口"的机制，类似于推荐系统中的隐式反馈挖掘。

### 原语：自动发现新意识节点——从POC结果中生长依赖图
- **ID**：99-P15
- **类型**：操作原语
- **描述**：从增量来源分析中自动发现候选新数学意识，在dg_nodes中创建新意识节点，在cognition_units中创建对应认知单元（双重身份），在cog_versions中创建v1版本记录，下次POC验证其价值——有价值则升级版本，无价值则标记deprecated。
- **溯源**：99号文档, 第223-231行, 原文引用："↓ 自动创建新意识节点 / 在dg_nodes中创建新意识节点（type=意识）/ 在cognition_units中创建对应认知单元（双重身份）/ 在cog_versions中创建v1版本记录（来源=本次POC）/ ↓ 下次POC验证这个新意识的价值 / 下次POC的种子选择中包含这个新意识 / 如果POC结果确认它有价值 → 版本链升级到v2 / 如果POC结果确认它无价值 → 标记为deprecated"
- **依赖关系**：
  - 依赖：99-P14（增量来源分析）、99-P5（双重身份）、99-P8（版本链）
  - 支撑：无
- **与检索机制的关系**：自动发现新意识是检索系统的自我扩展机制——从使用反馈中发现新的可检索单元并加入图中。这使依赖图从"手动设计"升级为"从使用中生长"，是检索系统的动态扩展闭环。deprecated标记则是检索结果的淘汰机制。

### 原语：CP4-CP6认知更新闭环——检索后的认知捕获与映射
- **ID**：99-P16
