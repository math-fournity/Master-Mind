### 原语：稀疏性激活原理
- **ID**：110-P1
- **类型**：概念框架
- **描述**：总知识量很大，但在每个具体研究点上只有一小部分被激活；系统的功力不在于知道多少，而在于知道在什么时候激活什么。
- **溯源**：110-大规模依赖图可操作性方案-三层访问架构.md, 第24行, 原文引用："稀疏性：总知识量很大，但在每个具体研究点上，只有一小部分被激活。大师的功力不在于知道多少，而在于知道在什么时候激活什么。"
- **依赖关系**：依赖：无（ foundational ） / 支撑：三层访问架构(110-P3)、种子选择机制(110-P9)、稀疏矩阵检索问题整体
- **与检索机制的关系**：这是253号检索问题的理论基础——Pattern数量巨大但此刻相关的极少，检索的本质就是"在稀疏存储中找到该激活的那一小部分"。110号文档将这个隐含原理显式化为工程架构。

### 原语：子图提取约束
- **ID**：110-P2
- **类型**：性质标准
- **描述**：不是把整个三维稀疏矩阵一次性呈现给AI，而是提取当前上下文相关的子图；依赖图的大小必须被控制在一个合理范围内。
- **溯源**：110-大规模依赖图可操作性方案-三层访问架构.md, 第26行, 原文引用："关键约束：依赖图的大小必须被控制在一个合理范围内。不是把整个三维稀疏矩阵一次性呈现给AI，而是提取当前上下文相关的子图。"
- **依赖关系**：依赖：稀疏性激活原理(110-P1) / 支撑：热工作集(110-P5)、Token预算控制(110-P7)
- **与检索机制的关系**：直接定义了检索的输出形态——不是返回全部Pattern，而是提取与当前状态相关的Pattern子集。253号文档的"提取此刻最需要的一个（或一批）Pattern"正是这个约束的体现。

### 原语：三层访问架构
- **ID**：110-P3
- **类型**：结构原语
- **描述**：将知识存储分为三层——冷存储层（全量数据，永久存储，不装入上下文）、热工作集（当前相关子图，装入上下文）、温查询层（按需查询，追加到热工作集）。
- **溯源**：110-大规模依赖图可操作性方案-三层访问架构.md, 第69-100行, 原文引用："三层访问架构……冷存储层 (Cold Layer)……热工作集 (Hot Layer)……温查询层 (Warm Layer)"
- **依赖关系**：依赖：稀疏性激活原理(110-P1)、子图提取约束(110-P2) / 支撑：冷存储层(110-P4)、热工作集(110-P5)、温查询层(110-P6)
- **与检索机制的关系**：直接对应253号检索问题的三层结构。冷存储层=稀疏矩阵全量Pattern存储；热工作集=此刻提取出的候选Pattern集合；温查询层=助理智能体在候选不足时发起的补充检索。三层架构为检索提供了存储-提取-补充的完整数据流骨架。

### 原语：层次索引
- **ID**：110-P10
- **类型**：结构原语
- **描述**：3层主题树（领域→子领域→主题），~60个主题叶节点，~15-20K token可常驻上下文；AI看到问题后先扫描主题树定位到2-5个相关主题，每个主题指向ArangoDB中~100-300个节点的子集。
- **溯源**：110-大规模依赖图可操作性方案-三层访问架构.md, 第170-259行, 原文引用："3层主题树，始终可装入上下文（~20K token）……规模：~60个主题叶节点 × ~100 token描述 = ~6K token……作用：AI看到问题后，先扫描主题树，定位到2-5个相关主题"
- **依赖关系**：依赖：无 / 支撑：三级种子选择机制(110-P9)、层次索引与语义检索互补(110-P14)
- **与检索机制的关系**：对应253号文档6.4节"按思维模式分类索引"和"按数学结构分类索引"——层次索引是Pattern检索的第一级粗筛机制，将海量Pattern按主题分类，先缩小搜索空间到~100-300个Pattern的子集。

### 原语：语义检索
- **ID**：110-P11
- **类型**：操作原语
- **描述**：对每个节点预计算embedding向量存储在ArangoDB中；运行时计算问题embedding，通过cosine similarity返回top-20最近节点作为种子。
- **溯源**：110-大规模依赖图可操作性方案-三层访问架构.md, 第261-275行, 原文引用："预计算：对325000个节点，每个节点计算一个embedding向量……运行时：问题输入 → 计算问题embedding……ArangoDB AQL + cosine similarity → 返回top-20最近节点……这20个节点就是种子"
- **依赖关系**：依赖：无 / 支撑：三级种子选择机制(110-P9)、层次索引与语义检索互补(110-P14)
- **与检索机制的关系**：对应253号文档3.3节第二层"嵌入向量"方案——把Pattern和当前状态都编码为向量做最近邻搜索。110号文档提供了具体的工程实现（预计算embedding + cosine similarity + top-K返回）。注意253号文档指出了此方案的局限（文本相似≠思维状态相似），但作为粗筛仍有价值。

### 原语：剪枝策略
- **ID**：110-P13
- **类型**：操作原语
- **描述**：图遍历中的多维剪枝——深度控制（默认max_depth=3避免爆炸）、宽度剪枝（每节点只保留top-K最相关邻居）、Token预算剪枝（累计Token达70K时停止）、螺旋环路优先保留、跨领域边优先保留。
- **溯源**：110-大规模依赖图可操作性方案-三层访问架构.md, 第282-286行, 原文引用："深度控制：默认max_depth=3（不是7），避免爆炸……宽度剪枝：每个节点只保留top-K个最相关的邻居……Token预算剪枝：遍历过程中累计token，达到70K时停止……螺旋环路优先：如果遍历路径经过螺旋环路节点，优先保留……跨领域边优先：跨领域映射边是高价值连接，优先保留"
- **依赖关系**：依赖：Token预算分配(110-P7)、节点容量估算(110-P8) / 支撑：图遍历扩展(110-P12)、热工作集(110-P5)
- **与检索机制的关系**：直接对应253号文档约束1"提取必须在合理时间内完成（不能全量扫描海量存储）"——剪枝策略是控制检索复杂度的核心机制。螺旋环路优先和跨领域边优先为Pattern检索提供了"哪些Pattern更值得保留"的优先级判据。
