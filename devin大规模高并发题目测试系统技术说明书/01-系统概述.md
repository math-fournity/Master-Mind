# 01 · 系统概述

## 1.1 系统定位

Devin 大规模高并发题目测试系统是一个**批量解题 Profiling 系统**——通过并发运行大量 Devin CLI 实例，让 GLM-5.2 模型对大规模数学题库进行解题，采集解题过程和结果，构建模型的能力边界 Profile。

**核心目标**：
1. **规模** — 对数万道数学题进行批量解题
2. **并发** — 同时运行 50-60 个 Devin CLI 实例
3. **采集** — 完整采集每次解题的 trajectory、thinking、proof
4. **判定** — 自动判定每次解题的终态（成功/失败/放弃/超时）
5. **Profile** — 从有效运行中构建 GLM-5.2 的数学能力边界

## 1.2 核心概念

### 管道化架构

系统采用**管道化 4+1 服务架构**——5 个独立进程通过 Redis 队列协作，每个服务职责单一：

| 服务 | 职责 | 运行方式 |
|---|---|---|
| Feeder | 从 ArangoDB 选题入 Redis pending 队列 | 独立进程，持续运行 |
| Runner | 从 pending 取题，启动 Devin CLI | 独立进程，维持固定并发 |
| Collector | 扫描 running 队列，判定终态，写回 DB | 独立进程，轮询 |
| Reporter | 定时输出统计报告和告警 | 独立进程，轻量级 |
| Retry | 扫描 failed 队列，重试基础设施失败 | 独立进程，定时 |

**为什么是 4+1**：Feeder/Runner/Collector/Reporter 是核心管道，Retry 是辅助服务（处理基础设施失败的自动重试）。

### 眼见为实判定

Collector 的终态判定遵循**眼见为实**原则——不依赖 DB status 数字，而是直接检查：
1. **tmux pane 内容** — `tmux capture-pane` 抓取实际屏幕输出
2. **tmux_pipe.log** — `-p` 模式下 Devin CLI 的完整 stdout
3. **sessions.db** — 检查是否有工具调用（违反"纯 thinking"约束）

### 解题约束

每道题通过 AGENTS.md 文件注入解题约束：
1. **不要使用任何工具** — 不写文件、不执行命令、不搜索、不浏览
2. **直接在 TUI 中输出证明** — 完成后输出 `### PROOF COMPLETE`
3. **无法做出时直接说** — 输出 `### I CANNOT SOLVE THIS`
4. **发现答案泄漏时** — 输出 `### ANSWER LEAK DETECTED`

这些约束确保采集到的是**纯 thinking 能力**，不受工具调用干扰。

### 失败分类

系统将每次解题的终态分为 **13 类 verdict**，归为三大类：

| 类别 | verdict | 含义 | 是否重试 | 是否计入 Profile |
|---|---|---|---|---|
| 成功 | `candidate_solved` | 检测到真实 proof + 无工具调用 | 否 | 是 |
| 成功 | `answer_leak` | 题目本身泄漏答案 | 否 | 是（题目问题） |
| 模型能力失败 | `ai_gave_up` | AI 主动放弃 | 否 | 是 |
| 模型能力失败 | `failed_token_limit` | 输出达到 token 上限 | 否 | 是 |
| 模型能力失败 | `failed_output_limit` | 输出长度限制 | 否 | 是 |
| 模型能力失败 | `failed_thinking_spin` | thinking 死循环 | 否 | 是 |
| 模型能力失败 | `failed_no_proof` | session 结束但无 proof | 否 | 是 |
| 模型能力失败 | `failed_stall` | 卡住超过 stall_time | 否 | 是 |
| 模型能力失败 | `failed_timeout` | 超过 timeout | 否 | 否（可能是基础设施） |
| 模型能力失败 | `invalid_tool_use` | 有 proof 但检测到工具调用 | 否 | 否（运行无效） |
| 基础设施失败 | `failed_connection` | 网络连接错误 | 是 | 否 |
| 基础设施失败 | `rate_limited` | API 限流 | 是 | 否 |
| 基础设施失败 | `launch_error` | 启动失败 | 是 | 否 |
| 基础设施失败 | `dead_session` | Devin CLI 异常退出无 proof | 是 | 否 |

详见 [07-失败分析与Profile.md](07-失败分析与Profile.md)。

## 1.3 系统边界

**系统做什么**：
- 批量启动 Devin CLI 实例解题
- 采集解题过程（tmux pane、pipe.log、sessions.db、export）
- 判定每次解题的终态
- 构建能力边界 Profile

**系统不做什么**：
- 不评判 proof 的数学正确性（只检测"是否有真实 proof 内容"）
- 不做题目难度评估（难度来自数据集自带字段）
- 不做模型对比（只针对 GLM-5.2 单一模型）
- 不做实时干预（系统运行时 Master Agent 是检查者，不参与循环）

## 1.4 演进背景

本系统是第五代系统的产物，替代了旧版 `batch_problem_runner`：

| 维度 | 旧版 batch_problem_runner | 管道化系统 |
|---|---|---|
| 架构 | 单进程串行管理 | 4+1 服务分离 |
| 并发上限 | 60 并发 51% 雪崩 | 60 并发稳定运行 |
| 失败处理 | 手动重试 | 自动重试基础设施失败 |
| 状态判定 | DB status 数字 | 眼见为实（pane + pipe.log） |
| 恢复能力 | 断电需手动恢复 | recover_from_crash.py 自动恢复 |

旧版系统已废弃，本说明书只描述管道化系统。
