# 06 · 验证与审计

## 6.1 验证工具体系

系统提供 4 个验证工具，覆盖不同维度：

| 工具 | 维度 | 用途 |
|---|---|---|
| `verify_completeness.py` | 数据完备性 | ID 完整性、Redis-DB 一致性、tmux 一致性 |
| `verify_run_integrity.py` | 运行完整性 | 无工具调用、真实 thinking、真实 proof |
| `audit_trace.py` | 双向追溯 | DB→文件、文件→DB、problem→runs、run→problem |
| `concurrency_safety_check.py` | 并发安全 | 10 个维度的竞态条件和资源泄漏检查 |

## 6.2 数据完备性验证（verify_completeness.py）

### 检查项

<ref_snippet file="~/master-mind-glm5.2-worktree/xishujuzhen/solver_harness/pipe/verify_completeness.py" lines="1-12" />

| 命令 | 检查内容 |
|---|---|
| `--check-ids` | DM-01: 题目唯一 ID 完整性（空 _key、重复 _key、空 problem_hash） |

## 6.3 运行完整性验证（verify_run_integrity.py）

<ref_snippet file="~/master-mind-glm5.2-worktree/xishujuzhen/solver_harness/pipe/verify_run_integrity.py" lines="1-13" />

```bash

python verify_run_integrity.py --batch --limit 100
python verify_run_integrity.py --all
```

## 6.5 并发安全检查（concurrency_safety_check.py）

### 检查维度（10 个）

<ref_snippet file="~/master-mind-glm5.2-worktree/xishujuzhen/solver_harness/pipe/scripts/concurrency_safety_check.py" lines="1-24" />

| 维度 | 检查内容 |
|---|---|
| A. Redis 操作原子性 | dequeue + add_running 间隙的丢题风险 |
| B. DB-Redis 一致性 | DB running 数 vs Redis running 数，孤儿记录 |
| C. 重复 attempt 检测 | 同一 problem_key 被多个 attempt 同时 running |
| D. 并发上限实际验证 | 设定并发 vs Redis running vs harness session 数 |
| E. devin 进程数 vs 并发数 | 僵尸 devin 进程堆积 |
| F. collector 处理速率 vs runner 启动速率 | 速率比，running 是否堆积 |
| G. auto-restart 验证 | 服务退出后是否真的 5 秒内重启 |
| H. 日志重复写入 | tee -a + RotatingFileHandler 导致每行写两遍 |
| I. 网络连接健康度 | API 可达性、HTTP 错误率、rate limit |
| J. devin 异常退出率 | dead_session 占比、solved 率、趋势 |

### 用法

```bash
cd ~/master-mind-glm5.2-worktree
set -a; source .env; set +a
PYTHONPATH=xishujuzhen/solver_harness/pipe .venv/bin/python3 \
  xishujuzhen/solver_harness/pipe/scripts/concurrency_safety_check.py
```

## 6.6 审计字段体系

Collector 在判定终态时写入 ArangoDB 的审计字段：

<ref_snippet file="~/master-mind-glm5.2-worktree/xishujuzhen/solver_harness/pipe/collector.py" lines="470-533" />

| 字段 | 用途 | 事后审计价值 |
|---|---|---|
| `solve_time_seconds` | 精确解题时间 | 区分推理时间 vs 等待时间 |
| `solve_time_source` | 时间来源 | 判断时间可信度 |
| `pane_snapshot` | pane 快照路径 | 找到物理证据 |
| `init_overhead_seconds` | 初始化开销 | 排除启动开销后的净解题时间 |
| `truncated_stall_seconds` | token_limit 卡住时间 | 区分推理时间 vs 卡住时间 |
| `end_reason` | 结束原因 | 快速定位终态判定依据 |

### solve_time 提取优先级

<ref_snippet file="~/master-mind-glm5.2-worktree/xishujuzhen/solver_harness/pipe/extract_solve_time.py" lines="1-26" />

1. `tmux_pipe.log` 的文件创建/修改时间（最可靠——覆盖完整解题过程）
2. `exports/conversation.json` 的 steps 时间戳（ATIF-v1.7，毫秒级 ISO 格式）
3. `sessions_db/trajectory.jsonl` 的 created_at（Unix timestamp）

### failed_token_limit 的时间标注

<ref_snippet file="~/master-mind-glm5.2-worktree/xishujuzhen/solver_harness/pipe/collector.py" lines="748-759" />

`failed_token_limit` 时，`solve_time_seconds` 是 AI 实际推理时间，`runtime_seconds` 包含卡在"Send a message to continue"的等待时间。`truncated_stall_seconds` = runtime - solve_time，让事后审计能区分推理时间 vs 卡住时间。

## 6.7 答案泄漏检查（check_answer_leak.py）

### 检查逻辑

<ref_snippet file="~/master-mind-glm5.2-worktree/xishujuzhen/solver_harness/pipe/check_answer_leak.py" lines="27-60" />

1. **answer 字段检查** — answer 值（>10 字符）是否出现在 problem_text 中
2. **solution 片段检查** — solution_text 前 200 字符是否出现在 problem_text 中
3. **答案标记模式** — 检查 "the answer is" / "final answer is" / "答案是" 等标记，排除占位符

### 用法

```bash
python check_answer_leak.py --problem-key <key>
python check_answer_leak.py --batch --tier 1 --limit 1000
python check_answer_leak.py --pending  # 检查 Redis pending 队列中的题
```

### 两层检查

- **Runner 预检**（启动前）— 发现泄漏直接标记 `answer_leak_in_input`，不入 running
- **Collector 检测**（运行中）— 检测 AI 输出的 `ANSWER LEAK DETECTED` 标记
