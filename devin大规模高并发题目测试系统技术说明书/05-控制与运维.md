# 05 · 控制与运维

## 5.1 pipe_control.py — 统一控制工具

`pipe_control.py` 是管道化系统的统一控制入口，所有运维操作通过它执行。

### 命令一览

<ref_snippet file="~/master-mind-glm5.2-worktree/xishujuzhen/solver_harness/pipe/pipe_control.py" lines="1-13" />

| 命令 | 用途 |
|---|---|
| `start` | 启动所有服务 |
| `stop` | 停止所有服务 |
| `status` | 查看状态 |
| `health` | 完备健康检查（8 个维度） |
| `clear` | 清空 Redis 队列 |
| `concurrency <N>` | 实时调整并发数 |
| `poll-interval <N>` | 实时调整 poll 间隔 |
| `recover` | 断电恢复 |

## 5.3 停止系统

### 优雅停止

```bash
python pipe_control.py stop
```

- 发送 SIGINT 给每个服务进程
- 服务完成当前操作后退出
- **不 kill harness-xxx session**——正在运行的解题继续

### 强制停止

```bash
python pipe_control.py stop --force
```

- 直接 `tmux kill-session`
- 不等待优雅退出

### 停止并 kill 所有解题 session

```bash
python pipe_control.py stop --kill-harness
```

- 停止服务 + kill 所有 `harness-xxx` session
- 用于完全清空系统

详见 <ref_snippet file="~/master-mind-glm5.2-worktree/xishujuzhen/solver_harness/pipe/pipe_control.py" lines="160-189" />。

## 5.5 完备健康检查

```bash
python pipe_control.py health
```

一次检查覆盖 8 个维度：

<ref_snippet file="~/master-mind-glm5.2-worktree/xishujuzhen/solver_harness/pipe/pipe_control.py" lines="280-292" />

| 维度 | 检查内容 |
|---|---|
| 1. 并发量 | 设定 vs running vs harness-p vs harness-dbmon |
| 2. tmux 泄漏 | dbmon 残留 + 孤儿 harness-p |
| 3. TUI 状态分类 | Thinking / PROOF COMPLETE / Ask Devin / truncated / rate limit / 其他 |
| 4. export 落盘 | running 中 PROOF COMPLETE 的 session 是否有 export |
| 5. DB 字段完整度 | 最近 candidate_solved 记录的 10 个关键字段 |
| 6. solve_time 可信度 | solve_time > runtime 的比例 |
| 7. failed 队列分类 | 按 verdict 统计 |
| 8. 整体进度 | completed/failed/success 率/ETA |

最终给出整体判定：✅ 全部健康 或 ⚠️ 有 N 个问题需要关注。

## 5.6 实时调整并发

```bash
python pipe_control.py concurrency 50
```

- 修改 Redis 中的 `math:config:concurrency`
- Runner 下次 poll 时自动读取（通常 2-5 秒内生效）

## 5.7 断电恢复

### 恢复工具

```bash
python pipe_control.py recover --dry-run  # 只检查不修改
python pipe_control.py recover             # 执行恢复
python pipe_control.py recover --auto-restart  # 恢复后自动重启
```

### 恢复流程

<ref_snippet file="~/master-mind-glm5.2-worktree/xishujuzhen/solver_harness/pipe/recover_from_crash.py" lines="1-26" />

1. 扫描 Redis `math:running` 队列
2. 对每个 running 记录，检查 tmux session 是否存在
   - session 存在 → 保留（让 Collector 处理）
   - session 不存在 → 标记 `crash_recovered`，移到 failed 队列
3. 修复 ArangoDB 中 `status=running` 但实际已结束的 attempt
4. 报告恢复结果

### 故障场景

| 场景 | 现象 | 恢复方式 |
|---|---|---|
| 断电 | Redis 有 AOF 持久化可恢复队列，但 tmux session 全部丢失 | recover 清理僵尸 running 记录 |
| 服务被 kill | 服务进程被 kill，harness session 可能还在 | recover 检查 session 存在性 |
| 代码热替换 | 停 Collector 替换代码，重启 Collector | running 中的记录保留，新 Collector 继续处理 |

## 5.8 健康检查铁律

### 铁律0：检查不用长 sleep 等待

简单查询立即执行——`pipe_control.py status`、`tmux list-sessions`、看日志 tail 等都是秒级返回的命令，不需要任何 sleep 前置。

### 铁律1：用 pipe_control.py，不现写脚本

新增查询需求时更新 `pipe_control.py`，不另写脚本。

### 铁律2：DB status 数字会骗人，必须到最前线

DB 显示 `running` 不代表 Solver 在工作。必须验证三个层面：
1. **tmux pane 内容** — `tmux capture-pane -t <session> -p`，pane 空白 = Devin CLI 已退出
2. **文件实际大小** — `tmux_pipe.log` 的大小，0KB = 没产出
3. **idle 时间真实性** — activity_signature 可能因 tmux_log_path 变化永远在变

### 铁律3：发现问题先修检查工具再修服务代码

检查脚本和监控代码是两层。`pipe_control.py` 是检查工具，runner/collector 是服务代码。发现问题后：
1. 先在 `pipe_control.py` 中加检测命令
2. 再在 runner/collector 中修服务逻辑
