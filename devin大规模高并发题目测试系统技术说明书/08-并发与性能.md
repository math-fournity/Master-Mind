# 08 · 并发与性能

## 8.1 3 秒启动间隔铁律

### 硬约束

<ref_snippet file="~/master-mind-glm5.2-worktree/xishujuzhen/solver_harness/pipe/runner.py" lines="306-334" />

**Runner 启动 Devin CLI 时，每 3 秒启动 1 个，不可改。**

`runner.py` 第 333 行的 `time.sleep(3)` 是铁律。

### 为什么是 3 秒

- 并行启动 60 个 session 会导致 58/60 个遇到 rate limit
- 3 秒间隔让 API 端有时间处理连接建立
- 3 秒间隔意味着：填满 60 并发需要 180 秒（3 分钟），填满 80 并发需要 240 秒（4 分钟）

### 恢复慢是正常的

Collector 清理完积压 session 后，Runner 按 3 秒间隔逐步填充——这不是 bug，是设计。

详见 <ref_file file="~/master-mind-glm5.2-worktree/.devin/rules/solver-concurrency.md" />。

## 8.4 调试反模式：看到 dead_session 就降并发

### 2026-08-13 教训

> 看到 dead_session 激增时，先查根因，不要急着降并发。

80 并发时出现大量 dead_session（81 个/10 分钟），反复降回 60。但根因不是 80 并发触发限流——是 Collector 的 `pane_is_empty` 误杀初始化中的 session：

- `-p` 模式下 Devin CLI 连接 API、初始化期间无 stdout 输出，pane 和 pipe.log 都是 0 字节
- Collector 用 `pane_is_empty` 判 dead_session，把正在初始化的 session 杀掉
- Runner 启动 1 个，Collector 杀好几个，导致并发数无法维持

### 修复后的正确做法

1. 看到 dead_session 激增 → 先查 dead_session 的 pipe.log 是否为空（空 = 初始化中被误杀）
2. 确认 Collector 是否在用 `pane_is_empty` 判断（已改为 `DEVIN_CLI_EXITED`）
3. 修复 Collector 后再观察并发本身的表现

**关键**：不要把 Collector bug 和并发问题混为一谈。

### 当前判定逻辑

<ref_snippet file="~/master-mind-glm5.2-worktree/xishujuzhen/solver_harness/pipe/collector.py" lines="390-398" />

`-p` 模式下用 `DEVIN_CLI_EXITED` 标记判断 Devin CLI 是否已退出，不用 `pane_is_empty`。

## 8.5 性能优化要点

### 启动阶段优化

- **串行预处理**（读题目、检查泄漏、写文件）——快，不耗时
- **串行启动**（3 秒间隔）——防 rate limit，不可改
- **填满并发的时间** = 并发数 × 3 秒

### Collector 轮询优化

- **poll 间隔**（默认 10 秒）——太短会浪费 CPU，太长会延迟判定
- **每轮处理所有 running**——不限制每轮处理数量
- **export 等待**（最多 120 秒）——只对非基础设施失败等待

### Retry 优化

- **扫描间隔**（默认 120 秒）——不要太频繁，避免与 Runner 竞争
- **重试次数限制**（默认 3 次）——避免无限重试

## 8.6 并发安全性

### 已知风险

<ref_snippet file="~/master-mind-glm5.2-worktree/xishujuzhen/solver_harness/pipe/scripts/concurrency_safety_check.py" lines="42-54" />

- `ZPOPMIN` 是原子操作 ✅
- `dequeue_pending` → `add_running` 之间 crash 会丢题（已知风险，auto-restart 兜底）
- running 中的 attempt_key 为空 = dequeue 后没来得及写 DB

### 兜底机制

| 风险 | 兜底机制 |
|---|---|
| 服务 crash | auto-restart（5 秒后自动重启） |
| 丢题 | Retry 扫描 failed 队列，基础设施失败重新入队 |
| 断电 | recover_from_crash.py 清理僵尸记录 |
| tmux 泄漏 | pipe_control.py health 检测 + stop_tmux 同时 kill dbmon |
