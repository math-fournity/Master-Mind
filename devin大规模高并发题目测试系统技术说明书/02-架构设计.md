# 02 · 架构设计

## 2.1 4+1 服务架构

系统由 5 个独立进程组成，通过 Redis 队列协作。每个服务运行在独立的 tmux session 中，互不依赖。

```
┌─────────┐     ┌──────────┐     ┌───────────┐     ┌──────────┐
│ Feeder  │────▶│  Runner  │────▶│ Collector │────▶│ Reporter │
└─────────┘     └──────────┘     └───────────┘     └──────────┘
   │ 选题         │ 启动CLI         │ 判定终态         │ 统计报告
   ▼              ▼                ▼                ▼
 ArangoDB      Redis队列       ArangoDB         Redis队列
 problem_      math:pending    devin_           math:stats
 extraction    math:running    problem_runs
 _progress                     problem_
   ▲                          extraction
   │                            _progress
   │     ┌────────┐              ▲
   └─────│ Retry  │──────────────┘
         └────────┘
           基础设施失败重试
```

### 服务职责

| 服务 | 输入 | 输出 | 运行节奏 |
|---|---|---|---|
| Feeder | ArangoDB 中 `extraction_status='pending'` 的题 | Redis `math:pending` 队列 | 持续运行，低水位时补充 |
| Runner | Redis `math:pending` 队列 | Devin CLI tmux session + Redis `math:running` | 维持固定并发数，3 秒间隔启动 |
| Collector | Redis `math:running` 队列 | Redis `math:completed`/`math:failed` + ArangoDB 更新 | 轮询（默认 10 秒） |
| Reporter | Redis `math:stats` | 日志报告 + 告警 | 定时（默认 60 秒） |
| Retry | Redis `math:failed` 队列 | Redis `math:pending`（重新入队） | 定时（默认 120 秒） |

### 服务解耦设计

**关键设计决策**：停止服务（`pipe_control.py stop`）不 kill `harness-xxx` tmux session。

- 每个 Devin CLI 运行在独立的 `harness-{exp_id}` tmux session 中
- 这些 session 独立于管道服务存在——服务停止时，正在运行的解题不受影响
- Collector 重启后会继续处理 `math:running` 队列中的 attempt
- 这使得**代码热替换**成为可能：停 Collector → 替换代码 → 重启 Collector，正在运行的解题不中断

详见 <ref_snippet file="~/master-mind-glm5.2-worktree/xishujuzhen/solver_harness/pipe/pipe_control.py" lines="160-189" />。

## 2.2 Redis 队列结构

Redis 是 5 个服务的协作中枢，所有状态通过 Redis 队列传递。

| 队列名 | Redis 类型 | 用途 | 操作者 |
|---|---|---|---|
| `math:pending` | Sorted Set | 待解题队列，score=priority | Feeder 写入，Runner 取出 |
| `math:running` | Hash | 运行中 attempt，field=exp_id，value=JSON metadata | Runner 写入，Collector 移除 |
| `math:completed` | List | 已完成（含成功和 answer_leak） | Collector 写入 |
| `math:failed` | List | 已失败 | Collector 写入，Retry 读取 |
| `math:stats` | Hash | 实时统计 | Reporter 更新 |
| `math:config:concurrency` | String | 并发数配置（实时可改） | Runner 读取 |
| `math:config:poll_interval` | String | poll 间隔配置（实时可改） | Runner 读取 |

详见 <ref_file file="~/master-mind-glm5.2-worktree/xishujuzhen/solver_harness/pipe/redis_queue.py" />。

### 队列操作原子性

- `math:pending` 用 `ZPOPMIN` 取题——原子操作，多 Runner 不会取到同一题
- `math:running` 用 `HSET`/`HDEL`——Hash 操作原子
- **已知风险**：`dequeue_pending` → `add_running` 之间如果进程 crash，会丢题。由 `auto-restart` 机制兜底（服务退出后 5 秒自动重启）

## 2.3 数据流

### 完整数据流（一道题的生命周期）

```
1. ArangoDB: problem_extraction_progress
   extraction_status = "pending"
        │
        ▼ Feeder 选题
2. Redis: math:pending (Sorted Set, score=priority)
        │
        ▼ Runner 取题 (ZPOPMIN)
3. ArangoDB: problem_extraction_progress
   extraction_status = "queued"
        │
        ▼ Runner 预处理（读题目、检查泄漏、写 AGENTS.md）
4. 文件系统: /data/.../problems/{exp_id}/AGENTS.md
        │
        ▼ Runner 启动 Devin CLI (solver_harness.py launch)
5. tmux: harness-{exp_id} session
   文件系统: /data/.../{exp_id}/tmux/tmux_pipe.log
   文件系统: /data/.../{exp_id}/sessions_db/*.db
        │
        ▼ Runner 写入 running 队列
6. Redis: math:running (Hash, field=exp_id)
   ArangoDB: devin_problem_runs (status="running")
        │
        ▼ Collector 轮询判定
7. Collector 检测终态:
   - capture-pane → pane 文本
   - 读 tmux_pipe.log → 完整输出
   - 检查 sessions.db → 是否有工具调用
        │
        ▼ 终态确定
8. Redis: math:completed 或 math:failed
   ArangoDB: devin_problem_runs (status + verdict + 审计字段)
   ArangoDB: problem_extraction_progress (extraction_status 更新)
   文件系统: /data/.../{exp_id}/collector/pane_snapshot.txt
   文件系统: /data/.../{exp_id}/exports/conversation.json
        │
        ▼ 如果是基础设施失败
9. Retry 扫描 math:failed
   → 重新入 math:pending
   → ArangoDB: problem_extraction_progress 回退为 "pending"
```

### 三层存储分工

| 层 | 技术 | 存什么 | 为什么 |
|---|---|---|---|
| 队列层 | Redis | 运行时状态（pending/running/completed/failed） | 高频读写，多进程协作 |
| 持久层 | ArangoDB | 题目元数据、attempt 记录、审计字段 | 持久化，AQL 查询 |
| 证据层 | 文件系统 | tmux pane 快照、pipe.log、sessions.db、export | 物理证据，眼见为实 |

详见 [03-数据存储.md](03-数据存储.md)。

## 2.4 tmux session 体系

系统使用 tmux 管理所有进程，有两类 session：

### 管道服务 session

| session 名 | 进程 | 生命周期 |
|---|---|---|
| `pipe-feeder` | feeder.py | 服务运行期间 |
| `pipe-runner` | runner.py | 服务运行期间 |
| `pipe-collector` | collector.py | 服务运行期间 |
| `pipe-reporter` | reporter.py | 服务运行期间 |
| `pipe-retry` | retry_infrastructure.py | 服务运行期间 |

### 解题 session（每道题两个）

| session 名 | 进程 | 生命周期 |
|---|---|---|
| `harness-{exp_id}` | Devin CLI | 解题期间，Collector 判定终态后 kill |
| `harness-dbmon-{exp_id}` | db monitor | 同上，必须同时 kill |

**关键约束**：`stop_tmux` 函数会同时 kill 两个 session，否则 dbmon session 会泄漏。详见 <ref_snippet file="~/master-mind-glm5.2-worktree/xishujuzhen/solver_harness/pipe/collector.py" lines="416-441" />。

## 2.5 优雅退出机制

所有服务通过 `graceful_shutdown.py` 注册 SIGTERM/SIGINT 处理：

1. 收到信号 → 设置 `_stop_flag`（不直接退出）
2. 主循环检查 `should_stop()` → 完成当前操作后退出
3. **不 kill 任何 `harness-xxx` session**——它们独立运行

详见 <ref_file file="~/master-mind-glm5.2-worktree/xishujuzhen/solver_harness/pipe/graceful_shutdown.py" />。

这使得：
- `pipe_control.py stop` → 服务优雅退出，解题继续
- `pipe_control.py stop --kill-harness` → 同时 kill 所有解题 session
- 断电恢复后，`recover_from_crash.py` 清理僵尸记录
